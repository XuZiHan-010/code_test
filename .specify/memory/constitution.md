# 面试题答题系统 Constitution

## Core Principles

### I. 内容忠于原文

- 每道题目必须能用它所在章节对应的那篇原文回答；原文没有讲的内容不得出题。
- 选择题的选项和干扰项必须只取材于同一章节的原文内容。
- 解答必须只转述所引原文小节的内容，并附带至少一条该小节的链接；不得用其他来源补充。
- 展示解答的页面必须注明内容来源，并说明其中的经验数字、产品命令和阈值以原文写作时为准。

理由：题库的价值在于每一条都能追溯到出处。一旦混入出处之外的说法，用户就无法核对，题库也失去了可信度。

### II. 题号永久稳定

- 题号一经发布不得更改、不得挪给另一道题；题目被删除后其题号不得复用。
- 用户的作答记录、错误次数和错题本必须只通过题号引用题目，不得复制题目内容。
- 任何内容更新（修订措辞、改题型、新增专题或章节）发布后，已有用户的记录必须保持有效且数值不变。

理由：题号是用户记录与题目内容之间唯一的关联。题号一变，“这道题错了几次”就对不上了。

### III. 内容先校验后发布

- 任何题目在面向用户之前，必须通过自动校验：题号唯一且无缺失、题型合法、选项数量与正确项数量符合规格、每题带有解答和原文引用。
- 由模型生成的题目必须经过人工抽查才能发布；抽查发现的问题必须在发布前修正。
- 校验不通过的内容不得发布，不得以“先上线再修”为由绕过。

理由：现有题库在人工核查中修订过 71 道题。生成内容的错误不会自己暴露，只能靠发布前的检查拦住。

### IV. 答案与用户数据不外泄

- 交卷之前，正确答案、选项对错和解答不得以任何形式到达用户的浏览器；判分必须在服务端完成。
- 用户必须只能读写自己的作答记录、错题和错题本；每个涉及用户数据的入口都必须校验当前登录用户。
- 密码不得以明文保存；密钥和凭据必须只通过部署环境的配置提供，不得写入代码或提交到仓库。

理由：答案提前可见会让正确率失去意义；用户之间的数据隔离是多用户系统的底线。

### V. 核心规则必须有行为测试

- 承载业务规则的部分（题库解析、题目数据校验、判分、作答与完成状态、错误次数统计、错题本、账号）必须有自动化测试，并在合入前通过。
- 测试必须只验证对外行为：给定输入，断言输出或可观察到的状态；不得断言内部调用方式。
- 涉及数据存取的规则必须对真实数据库测试，不得用模拟的数据库代替。

理由：正确率和错误次数是用户最直接依赖的数字，算错一次就失去信任；只测外部行为，重构时测试才不会成为负担。

### VI. 按版本范围交付

- 需求以当前功能目录下的 `spec.md` 为准。规格里没有的功能不得实现；需要改变范围时必须先改规格。
- 不得为尚未写入规格的后续功能预先搭建结构。1.0 中对战模式只保留入口，不得实现任何对战逻辑。
- 在满足规格的方案中，必须选择最简单的那个；引入额外的复杂度必须在计划中写明理由。

理由：对战模式的详细需求还没有确定，现在为它设计的任何结构都是猜测，猜错的代价高于以后再做。

## 约束

- 部署目标是 Railway。
- 界面语言为简体中文；页面必须在手机浏览器上可用。
- 题库内容可以公开发布，前提是遵守原则 I 的出处要求。
- 技术栈在规划阶段确定，确定后必须记入 `CLAUDE.md`，连同构建、测试和运行命令。
- 题库文件为 UTF-8 编码；读写这些文件的脚本和工具必须显式指定 UTF-8。

## 开发流程

- 功能开发按 Spec Kit 的顺序进行：规格（`/speckit-specify`）、澄清（`/speckit-clarify`）、计划（`/speckit-plan`）、任务（`/speckit-tasks`）、实现（`/speckit-implement`）。
- 计划必须包含对本文件六条原则的逐条检查；有违反的地方必须写明理由，否则计划不得通过。
- 题库内容的任何改动（包括新增章节）必须重新运行自动校验，并按原则 III 抽查后才能发布。
- 新增或改变常用命令、目录约定时，必须同步更新 `CLAUDE.md`。

## Governance

- 本文件的效力高于项目内的其他文档和约定；出现冲突时以本文件为准，或者先修订本文件。
- 修订由项目所有者决定。每次修订必须写明改了什么、为什么改，并更新版本号和修订日期。
- 版本号遵循语义化版本：删除或重新定义原则为主版本；新增原则、新增章节或实质性扩充为次版本；措辞澄清和勘误为修订版本。
- 每份计划和每次实现完成前，必须对照本文件检查一遍。
- 日常开发的具体指引（命令、目录结构、题库格式）记录在 `CLAUDE.md`，不写入本文件。
