O5-26 [short] 介绍一下Redis 内存淘汰策略

Answer (L446): Redis 通过 maxmemory 控制内存使用上限，通过 maxmemory-policy 选择超过上限时的处理方式。常见的 64 位环境下 maxmemory 默认是 0，表示不设上限，32 位环境默认限制为 3GB；生产环境通常需要显式配置，并给操作系统、复制缓冲区和持久化时的写时复制预留内存，且它不是进程实际占用物理内存的硬上限。以 Redis 7.0 为例共有八种策略，分为两类。一类是不进行数据淘汰的 noeviction（Redis 3.0 之后的默认策略），超限时可能继续增加内存的写命令返回 OOM 错误，普通查询和删除通常仍可执行，也不等于关闭过期删除。另一类是进行数据淘汰的策略：在设置了过期时间的数据中淘汰的有 volatile-random、volatile-ttl、volatile-lru（3.0 之前的默认策略）、volatile-lfu（4.0 后新增）；在所有数据范围内淘汰的有 allkeys-random、allkeys-lru、allkeys-lfu（4.0 后新增）。选 volatile 系列但没有可淘汰的过期键时，写入仍可能报 OOM。纯缓存场景可考虑 allkeys-lru 或 allkeys-lfu；如果还放了锁、库存等不能随意丢的数据，应考虑拆分实例。[原文§介绍一下Redis 内存淘汰策略](https://xiaolincoding.com/interview/redis.html#%E4%BB%8B%E7%BB%8D%E4%B8%80%E4%B8%8Bredis-%E5%86%85%E5%AD%98%E6%B7%98%E6%B1%B0%E7%AD%96%E7%95%A5)

O5-53 [short] 介绍一下Redis过期删除策略

Answer (L479): Redis 选择惰性删除加定期删除配合使用，在合理使用 CPU 时间和避免内存浪费之间取得平衡。惰性删除是在访问或修改 key 之前，调用 expireIfNeeded 等函数检查 key 是否过期：已过期时，在主节点上删除该 key，对 GET 这样的读取命令表现为 key 不存在，底层内存同步还是异步释放由 lazyfree-lazy-expire 等配置和释放成本决定；没过期则继续执行。定期删除是每隔一段时间随机取一定数量的 key 检查并删除过期的：周期性任务由 hz 控制，默认 10，约每秒 10 次，但动态 hz、快速过期检查等机制也会影响实际频率；每轮从设置了过期时间的 key 中抽样，过期比例较高就继续，比例下降或用完时间预算就退出，把时间留给客户端请求。以 Redis 7.0 为例，active-expire-effort 默认 1，基础每轮扫描 20 个，继续扫描的过期比例阈值是 10%，慢速检查的时间预算约为两次周期性任务间隔的 25%（hz 为 10 时约 25ms），这些值并非所有版本都固定。定期删除是在 CPU 开销和内存回收之间做平衡，不会每次遍历所有 key。[原文§介绍一下Redis过期删除策略](https://xiaolincoding.com/interview/redis.html#%E4%BB%8B%E7%BB%8D%E4%B8%80%E4%B8%8Bredis%E8%BF%87%E6%9C%9F%E5%88%A0%E9%99%A4%E7%AD%96%E7%95%A5)
