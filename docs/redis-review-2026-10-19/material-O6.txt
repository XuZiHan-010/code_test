O6-30 [short] Redis主从同步中的增量和完全同步怎么实现？

Answer (L551): 完全同步主要发生在三种情况：首次建立复制关系；主节点无法根据从节点提供的复制 ID 找到兼容的复制历史；断连较久、从节点缺失的命令不再位于复制积压缓冲区中。所以是全量还是增量，看复制历史能不能衔接，以及需要的增量数据还在不在。第一次同步分三个阶段：建立链接、协商同步，主服务器同步数据给从服务器，主服务器发送新写操作命令给从服务器。具体是：从节点发送 PSYNC ? -1，主节点回复 FULLRESYNC 并返回复制 ID 和基准偏移量；主节点用子进程生成 RDB 快照（可先写磁盘，也可无盘复制）；期间的写命令保存在待发送的复制数据中；从节点加载 RDB 替换原数据集；主节点再发送快照之后的写命令。要区分 replication buffer（给从节点发送复制数据）和 repl_backlog_buffer（保留最近复制历史，支持断线后增量同步）。增量同步基于 PSYNC，用复制 ID 和偏移量判断能否续传：从节点恢复网络后发送 offset 不是 -1 的 psync，主服务器若判断复制 ID 兼容、且请求的偏移量仍在 repl_backlog_buffer 范围内，就回复 CONTINUE，并把断线期间的写命令发给从服务器；否则采用全量同步。主服务器用 master_repl_offset 记录写到的位置，从服务器用 slave_repl_offset 记录读到的位置。repl-backlog-size 默认 1MB，可按每秒复制流量乘以希望容忍的断连时间再加余量设置，但要结合内存预算，不是越大越好。[原文§Redis主从同步中的增量和完全同步怎么实现？](https://xiaolincoding.com/interview/redis.html#redis%E4%B8%BB%E4%BB%8E%E5%90%8C%E6%AD%A5%E4%B8%AD%E7%9A%84%E5%A2%9E%E9%87%8F%E5%92%8C%E5%AE%8C%E5%85%A8%E5%90%8C%E6%AD%A5%E6%80%8E%E4%B9%88%E5%AE%9E%E7%8E%B0)

O6-39 [short] redis主从和集群可以保证数据一致性吗 ？

Answer (L563): 不能保证主从强一致，也不能保证故障切换时已经确认的写入一定不丢失，因为 Redis 的主从复制默认是异步的。比如客户端往主节点写入一条数据，主节点返回成功，但还没复制到从节点，这时主节点宕机，哨兵或 Cluster 把从节点提升为主节点，新主节点上就没有这条数据了。读写分离也有类似问题：刚写完主节点马上去从节点读，可能读到旧值，所以「写完马上读」的场景可以优先读主节点，但这也不能消除故障切换造成的数据丢失窗口。可以通过 WAIT 等机制等待副本确认，或用 min-replicas-to-write、min-replicas-max-lag 限制副本状态不好时的写入来降低风险，但这些措施不会把 Redis 变成强一致系统。另外不能简单说 Redis Cluster 属于 AP、网络分区时一直可用：Cluster 在失去多数主节点联系时会停止接受写入，默认要求所有槽都可服务，槽不可用也可能影响整个集群，可用性是有条件的。[原文§redis主从和集群可以保证数据一致性吗 ？](https://xiaolincoding.com/interview/redis.html#redis%E4%B8%BB%E4%BB%8E%E5%92%8C%E9%9B%86%E7%BE%A4%E5%8F%AF%E4%BB%A5%E4%BF%9D%E8%AF%81%E6%95%B0%E6%8D%AE%E4%B8%80%E8%87%B4%E6%80%A7%E5%90%97)

O6-45 [short] 哨兵机制原理是什么？

Answer (L572): 在 Redis 主从架构中，写请求通常由主节点处理，主节点挂了就没有节点服务写请求，也没有主节点给从节点同步数据。没有哨兵时需要人工介入：选一个从节点切换为主节点，让其他从节点指向新主节点，并通知上游客户端更新主节点 IP。哨兵（Sentinel）机制用来实现主从节点故障转移：它是运行在特殊模式下的 Redis 进程，也是一个节点，相当于观察主从节点的观察者。它监测主节点是否存活，发现主节点挂了就选举一个从节点切换为主节点，并把新主节点的信息通知从节点和客户端。哨兵节点主要负责三件事：监控、选主、通知。[原文§哨兵机制原理是什么？](https://xiaolincoding.com/interview/redis.html#%E5%93%A8%E5%85%B5%E6%9C%BA%E5%88%B6%E5%8E%9F%E7%90%86%E6%98%AF%E4%BB%80%E4%B9%88)

O6-63 [short] 哨兵机制的选主节点的算法介绍一下

Answer (L593): 这里说的是哨兵管理的主从架构，Redis Cluster 有自己的故障检测和选举机制，不依赖 Sentinel。主节点故障时，Sentinel 协调故障转移，经过四步：故障节点主观下线、故障节点客观下线、Sentinel 集群选举 Leader、Sentinel Leader 决定新主节点。主观下线：Sentinel 定时向所有节点发心跳包，节点在 down-after-milliseconds 时间内没有回复，就被该 Sentinel 主观下线。客观下线：被一个 Sentinel 标记为主观下线不代表真的故障，该 Sentinel 会询问其他 Sentinel，认为主节点下线的数量达到 quorum（包括自己）就标记为客观下线，客观下线只针对主节点。选举 Leader：确认主节点客观下线并准备发起故障转移的 Sentinel 请求其他 Sentinel 选自己，每轮选举有纪元，一个 Sentinel 在同一纪元只投给一个候选者；票数达到 quorum 与 floor(Sentinel 节点数 / 2) + 1 的最大值才当选，否则重新选举。比如 3 个哨兵、quorum 为 2，拿到 2 张赞成票即可。决定新主节点：先过滤不可用、与主节点断连过久、replica-priority 为 0（不参与晋升）的从节点；再依次比较 replica-priority（数值小的优先，旧版叫 slave-priority）、复制偏移量（大的优先）、run ID（字典序小的优先），这些条件按顺序比较。选出后，Sentinel 将它提升为主节点，让其他从节点重新复制它，并通知支持 Sentinel 的客户端发现新主节点。[原文§哨兵机制的选主节点的算法介绍一下](https://xiaolincoding.com/interview/redis.html#%E5%93%A8%E5%85%B5%E6%9C%BA%E5%88%B6%E7%9A%84%E9%80%89%E4%B8%BB%E8%8A%82%E7%82%B9%E7%9A%84%E7%AE%97%E6%B3%95%E4%BB%8B%E7%BB%8D%E4%B8%80%E4%B8%8B)

O6-89 [short] Redis集群的模式了解吗 优缺点了解吗

Answer (L625): 当缓存数据量大到一台服务器无法缓存时，就用 Redis 切片集群（Redis Cluster）：数据分布在不同服务器上，降低对单主节点的依赖，提高读写性能。它采用哈希槽处理数据和节点的映射：一个集群共有 16384 个哈希槽，key 先用 CRC16 算出 16 bit 的值，再对 16384 取模，得到 0~16383 的槽号。槽映射到节点有两种方式：用 cluster create 创建集群时自动平均分配，或用 cluster meet 建立连接后再用 cluster addslots 手动指定。槽只分配给主节点，从节点复制对应主节点的数据，不独立分配槽；真实集群固定 16384 个槽，默认 cluster-require-full-coverage 为 yes，需要全部槽可服务。优点：容量和吞吐量可以扩展，支持故障转移（前提是有可用副本并满足选举条件），可以通过迁移哈希槽及其数据在线扩缩容。缺点：维护更复杂，要管理主从关系、槽位、迁移、客户端路由以及数据和请求分布是否均衡；多 key 操作受限制，事务、Lua 脚本和许多多 key 命令要求相关 key 在同一个槽，同节点的两个 key 也不一定同槽；不能解决所有热点问题，一个 key 仍只属于一个槽、由一个主节点处理；存在复制延迟和数据丢失窗口，主从异步复制，故障切换不能保证强一致，并且 Cluster 只支持数据库 0。另外，原生 Redis Cluster 节点不充当代理转发普通请求，而是让客户端根据槽位路由，必要时返回重定向。[原文§Redis集群的模式了解吗 优缺点了解吗](https://xiaolincoding.com/interview/redis.html#redis%E9%9B%86%E7%BE%A4%E7%9A%84%E6%A8%A1%E5%BC%8F%E4%BA%86%E8%A7%A3%E5%90%97-%E4%BC%98%E7%BC%BA%E7%82%B9%E4%BA%86%E8%A7%A3%E5%90%97)

O6-98 [short] cluster集群客户端是怎样知道该访问哪个分片的？

Answer (L637): Redis Cluster 把所有数据映射到 16384 个哈希槽里，每个节点负责一部分槽位。客户端启动后先和集群中任意一个节点建立连接，通过 CLUSTER SLOTS，或 Redis 7.0 起提供的 CLUSTER SHARDS，获取「槽位 - 节点」映射关系，并缓存到本地。访问某个 key 时，先对 key 做 CRC16 哈希计算，再对 16384 取模算出槽位，查本地缓存的映射表找到对应节点，直接访问。如果槽位迁移，或故障切换使槽位对应的主节点变化，客户端可能收到 MOVED 或 ASK，两者处理不同：MOVED 表示当前槽位应访问另一个节点，客户端重发请求并更新这个槽的路由或刷新整个槽位映射；ASK 通常出现在槽位迁移过程中，只要求这一次请求去目标节点，客户端在目标节点的同一连接上先发送 ASKING 再发原命令，不能据此永久修改槽位映射。连接直接断开时可能先遇到连接错误，再由客户端刷新拓扑或重试。简单说，客户端缓存全量槽位映射表，访问 key 时算槽位、查缓存找节点，遇到变动就更新缓存，全程自动完成，不用开发者手动指定分片，这是 Redis Cluster 能做到透明分片访问的核心。[原文§cluster集群客户端是怎样知道该访问哪个分片的？](https://xiaolincoding.com/interview/redis.html#cluster%E9%9B%86%E7%BE%A4%E5%AE%A2%E6%88%B7%E7%AB%AF%E6%98%AF%E6%80%8E%E6%A0%B7%E7%9F%A5%E9%81%93%E8%AF%A5%E8%AE%BF%E9%97%AE%E5%93%AA%E4%B8%AA%E5%88%86%E7%89%87%E7%9A%84)
