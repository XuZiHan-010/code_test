O1-25 [short] 讲一下Redis底层的数据结构

Answer (L35): Redis 常见的五种数据类型是 String、Hash、List、Set、Zset，后续版本又新增了 BitMap（2.2 版）、HyperLogLog（2.8 版）、GEO（3.2 版）、Stream（5.0 版）。其中 BitMap 和 HyperLogLog 底层基于 String，GEO 底层基于 Zset，Stream 是独立的数据类型。要区分数据类型和底层数据结构：String、Hash、List 等是使用时看到的数据类型，SDS、哈希表、跳表、listpack、quicklist 等才是底层实现，同一种类型还会根据数据大小和版本选择不同的编码。以 Redis 7.0 为例：String 用 int、embstr、raw；Hash 用 listpack 或哈希表（字段少且小时用 listpack，默认字段数量不超过 512、每个字段和值不超过 64 字节）；List 用 quicklist；Set 用 intset 或哈希表（intset 默认最多 512 个整数）；Zset 用 listpack 或跳表 + 哈希表。后续版本还会增加编码，比如 Redis 7.2 的小型 Set 可以使用 listpack，所以面试时最好先说明讨论的是哪个版本。应用场景：String 用于缓存对象、常规计数、分布式锁、共享 session；List 可做消息队列，但生产者要自行实现全局唯一 ID，也不能以消费组形式消费；Hash 用于缓存对象、购物车；Set 用于点赞、共同关注、抽奖等聚合计算；Zset 用于排行榜等排序场景；BitMap 用于签到等二值状态统计；HyperLogLog 用于百万级网页 UV 等基数统计；GEO 用于地理位置；Stream 用于消息队列，能自动生成同一个 Stream 内唯一且递增的消息 ID，并支持消费组、消息确认和待处理消息追踪。

O1-47 [short] Redis 中 set和zset区别是什么？

Answer (L63): Set 和 ZSet 都是存储多个元素的集合类型，核心区别在于是否对元素排序以及排序方式，这直接影响适用场景。Set 是无序、唯一元素的集合，适合存储不重复且无需排序的数据（如用户 ID 列表、标签集合），常用命令有 SADD 添加元素、SMEMBERS 查看所有元素（结果无序）、SISMEMBER 判断元素是否存在、SINTER 和 SUNION 求交集和并集。ZSet 是有序、唯一元素的集合，每个元素关联一个分数（score），按分数从小到大排序，元素唯一但分数可重复，适合排行榜、带权重的任务等需要排序或排名的场景，常用命令有 ZADD 添加元素、ZRANGE 按排名范围获取、ZRANGEBYSCORE 按分数范围获取、ZINCRBY 增减分数、ZRANK 获取排名（从 0 开始）。ZSet 相比 Set 多了很多基于分数的操作，而 Set 没有分数概念，只能按元素本身操作，无法直接获取“第 N 个元素”或“某个范围内的元素”。总结：有序性上 Set 完全无序、ZSet 通过分数维持有序；操作特性上 ZSet 多了排序、范围查询、排名计算，Set 只有交并差等集合运算；适用场景上 Set 用于去重且无需排序，ZSet 用于排序、排名或权重相关的场景。

O1-105 [short] 压缩列表是怎么实现的？

Answer (L136): 压缩列表是 Redis 为了节约内存而开发的，是由连续内存块组成的顺序型数据结构，有点类似数组。头部有三个字段，末尾有一个结束标记：zlbytes 记录整个压缩列表占用的字节数，zltail 记录尾部节点距离起始地址的字节数（尾偏移量），zllen 记录节点数量，zlend 标记结束点，固定值 0xFF（十进制 255）。第一个元素紧跟在头部后面，最后一个元素可通过 zltail 定位，所以定位首尾元素是 O(1)；zllen 记录的是元素数量，达到 65535 时还需要遍历才能得到实际数量；查找其他元素只能逐个查找，复杂度 O(N)，因此不适合保存过多元素。节点（entry）包含三部分：prevlen 记录前一个节点的长度，用于从后向前遍历；encoding 记录当前节点实际数据的类型（字符串或整数）和长度；data 记录实际数据。根据数据类型和大小使用不同空间大小的 prevlen 和 encoding，是 Redis 为节省内存采用的设计。缺点是会发生连锁更新：元素数量增加或元素变大导致内存重新分配，最糟糕时连锁更新要多次重新分配内存，直接影响访问性能，所以压缩列表只用于节点数量不多的场景。后来 Redis 新增了 quicklist（3.2 版本引入，拆成多个小容器减轻大块内存操作和连锁更新的影响）和 listpack（5.0 版本引入，从节点编码上消除连锁更新的根源）。

O1-116 [short] 介绍一下 Redis 中的 listpack

Answer (L150): 使用压缩列表的旧版 quicklist 通过控制节点内部容器的大小或元素个数，减少了连锁更新带来的影响，但没有彻底解决：旧版 quicklistNode 仍用压缩列表保存元素，连锁更新来源于压缩列表的结构设计。于是 Redis 在 5.0 新设计了 listpack，目的是替代压缩列表，最大特点是每个节点不再包含前一个节点的长度，而压缩列表每个节点要保存前一个节点的长度，才有连锁更新的隐患。listpack 沿用了压缩列表的优秀设计：用一块连续的内存空间紧凑地保存数据，并用不同的编码方式保存不同大小的数据来节省内存。结构上，listpack 头包含总字节数和元素数量两个属性，末尾有结尾标识；每个节点包含 encoding（定义元素的编码类型）、data（实际数据）、len（encoding + data 的总长度）三部分。因为只记录当前节点的长度，加入新元素不会影响其他节点的长度字段，避免了连锁更新。版本方面，从 Redis 7.0 起，小型 Hash、Zset 直接使用 listpack 作为紧凑编码，quicklist 的普通 packed 节点内部也由压缩列表改为 listpack；Redis 7.2 中小型 List 还可以直接使用一个 listpack，超过 list-max-listpack-size 控制的限制后再转成 quicklist。不过避免连锁更新不代表插入、删除变成 O(1)：listpack 仍使用连续内存，中间插入或删除可能要移动后面的数据，扩容也可能重新分配内存，所以更适合保存较小的数据集合。

O1-153 [short] String 的 int、embstr 和 raw 编码有什么区别？
