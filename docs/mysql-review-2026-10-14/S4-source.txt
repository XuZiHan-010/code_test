# 事务

# 事务的特性是什么？如何实现的？

原子性（Atomicity） ：事务中的修改，要么整体提交，要么整体回滚，不会只提交其中一部分。就好比买一件商品，购买成功时，钱付给商家、商品到手；购买失败并回滚时，商品还在商家手中，消费者的钱也没花出去。不过，单条 SQL 报错不一定会自动回滚整个事务，应用仍需要正确处理失败。 一致性（Consistency） ：是指事务操作前和操作后，数据满足完整性约束，数据库保持一致性状态。比如，用户 A 和用户 B 在银行分别有 800 元和 600 元，总共 1400 元，用户 A 给用户 B 转账 200 元，分为两个步骤，从 A 的账户扣除 200 元和对 B 的账户增加 200 元。一致性就是要求上述步骤操作后，最后的结果是用户 A 还有 600 元，用户 B 有 800 元，总共 1400 元，而不会出现用户 A 扣除了 200 元，但用户 B 未增加的情况（该情况，用户 A 和 B 均为 600 元，总共 1200 元）。 隔离性（Isolation） ：控制并发事务之间能看到哪些数据，以及冲突操作如何执行。实际隔离程度取决于隔离级别，并不是给每个事务分配一份独立数据库。比如多个消费者同时购买最后一件商品，就需要通过锁或条件更新处理竞争。 持久性（Durability） ：事务处理结束后，对数据的修改就是永久的，即便系统故障也不会丢失。

MySQL InnoDB 引擎通过什么技术来保证事务的这四个特性的呢？

持久性是通过 redo log （重做日志）来保证的； 原子性是通过 undo log（回滚日志） 来保证的； 隔离性是通过 MVCC（多版本并发控制） 或锁机制来保证的； 一致性需要这些机制、数据库约束和正确的业务逻辑一起保证。比如转账时扣款和入账金额写错了，即使事务正常提交，也不能保证业务一致性。

# mysql可能出现什么和并发相关问题？

MySQL 服务端是允许多个客户端连接的，这意味着 MySQL 会出现同时处理多个事务的情况。

那么 在同时处理多个事务的时候，就可能出现脏读（dirty read）、不可重复读（non-repeatable read）、幻读（phantom read）的问题 。

接下来，通过举例子给大家说明，这些问题是如何发生的。

脏读

如果一个事务「读到」了另一个「未提交事务修改过的数据」，就意味着发生了「脏读」现象。

举个栗子。

假设有 A 和 B 这两个事务同时在处理，事务 A 先开始从数据库中读取小林的余额数据，然后再执行更新操作，如果此时事务 A 还没有提交事务，而此时正好事务 B 也从数据库中读取小林的余额数据，那么事务 B 读取到的余额数据是刚才事务 A 更新后的数据，即使没有提交事务。



因为事务 A 是还没提交事务的，也就是它随时可能发生回滚操作， 如果在上面这种情况事务 A 发生了回滚，那么事务 B 刚才得到的数据就是过期的数据，这种现象就被称为脏读。

不可重复读

在一个事务内多次读取同一个数据，如果出现前后两次读到的数据不一样的情况，就意味着发生了「不可重复读」现象。

举个栗子。

假设有 A 和 B 这两个事务同时在处理，事务 A 先开始从数据库中读取小林的余额数据，然后继续执行代码逻辑处理， 在这过程中如果事务 B 更新了这条数据，并提交了事务，那么当事务 A 再次读取该数据时，就会发现前后两次读到的数据是不一致的，这种现象就被称为不可重复读。



幻读

一个事务重复查询同一个条件，发现符合条件的记录集合因为其他事务的修改而发生变化，就叫幻读。 常见表现是多了或少了记录，不过不只是比较 COUNT：即使数量相同，符合条件的记录被换成了另一批，也可能出现问题。

举个栗子。

假设有 A 和 B 这两个事务同时在处理，事务 A 先开始从数据库查询账户余额大于 100 万的记录，发现共有 5 条，然后事务 B 也按相同的搜索条件也是查询出了 5 条记录。



接下来，事务 A 插入了一条余额超过 100 万的账号，并提交了事务，此时数据库超过 100 万余额的账号个数就变为 6。

然后事务 B 再次查询账户余额大于 100 万的记录，此时查询到的记录数量有 6 条， 发现和前一次读到的记录数量不一样了，就感觉发生了幻觉一样，这种现象就被称为幻读。

# 哪些场景不适合脏读，举个例子？

脏读是指一个事务在读取到另一个事务未提交的数据时发生。脏读可能会导致不一致的数据被读取，并可能引起问题。以下是一些不适合脏读的场景：

银行系统 ：在银行系统中，如果一个账户的余额正在被调整但尚未提交，另一个事务读取了这个临时的余额，可能会导致客户看到不正确的余额。 库存管理系统 ：在一个库存管理系统中，如果一个商品的数量正在被更新但尚未提交，另一个事务读取了这个临时的数量，可能会导致库存管理错误。 在线订单系统 ：在一个在线订单系统中，如果一个订单正在被修改但尚未提交，另一个事务读取了这个临时的订单状态，可能导致订单状态显示错误，客户收到不准确的信息。

在以上这些场景中，脏读可能导致严重的问题，因此应该避免发生脏读，保证数据的一致性和准确性。

# mysql的是怎么解决并发问题的？

锁机制：MySQL 提供了多种锁机制来保证数据的一致性，主要包括 行级锁 （InnoDB 支持）和 表级锁 （InnoDB 和 MyISAM 都支持）。注意：网上常提到的"页级锁"是已移除的 BDB 存储引擎的特性，InnoDB / MyISAM 都不提供页级锁。通过锁机制，可以控制冲突操作的执行顺序。多个共享锁可以共存，普通快照读也通常不会被记录的排他锁阻塞，并不是所有访问都只能排队。 事务隔离级别：Mysql提供了多种事务隔离级别，包括读未提交、读已提交、可重复读和串行化。通过设置合适的事务隔离级别，可以在多个事务并发执行时，控制事务之间的隔离程度，以避免数据不一致的问题。 MVCC（多版本并发控制）：Mysql使用MVCC来管理并发访问，它通过在数据库中保存不同版本的数据来实现不同事务之间的隔离。在读取数据时，Mysql会根据事务的隔离级别来选择合适的数据版本，从而保证数据的一致性。

# 事务的隔离级别有哪些？

读未提交（read uncommitted） ，指一个事务还没提交时，它做的变更就能被其他事务看到； 读提交（read committed） ，指一个事务提交之后，它做的变更才能被其他事务看到； 可重复读（repeatable read） ，指同一个事务中的普通快照读复用同一个快照，通常在第一次快照读时建立，后续不会因为其他事务提交就改变， MySQL InnoDB 引擎的默认隔离级别 ； 串行化（serializable） ；会对记录加上读写锁，在多个事务对这条记录进行读写操作时，如果发生了读写冲突的时候，后访问的事务必须等前一个事务执行完成，才能继续执行；

也就是说：

在「读未提交」隔离级别下，可能发生脏读、不可重复读和幻读现象； 在「读提交」隔离级别下，可能发生不可重复读和幻读现象，但是不可能发生脏读现象； 按 SQL 标准，「可重复读」仍允许幻读；不过 MySQL InnoDB 在普通快照读中通过 MVCC 保持同一快照，在范围锁定读中通过间隙锁、next-key lock 阻止插入。混用快照读与当前读时，还需要区分两种读的可见范围； 在「串行化」隔离级别下，脏读、不可重复读和幻读现象都不可能会发生。

在「读未提交」隔离级别下，事务 B 修改余额后，虽然没有提交事务，但是此时的余额已经可以被事务 A 看见了，于是事务 A 中余额 V1 查询的值是 200 万，余额 V2、V3 自然也是 200 万了； 在「读提交」隔离级别下，事务 B 修改余额后，因为没有提交事务，所以事务 A 中余额 V1 的值还是 100 万，等事务 B 提交完后，最新的余额数据才能被事务 A 看见，因此额 V2、V3 都是 200 万； 在「可重复读」隔离级别下，假设事务 A 在 B 修改前已经建立快照，普通查询的 V1、V2 都是 100 万。A 提交后，在新的查询事务中建立新快照，就能看到 B 已提交的 200 万。单独执行 BEGIN 并不意味着马上建立快照； 在「串行化」隔离级别下，事务 B 在执行将余额 100 万修改为 200 万时，由于此前事务 A 执行了读操作，这样就发生了读写冲突，于是就会被锁住，直到事务 A 提交后，事务 B 才可以继续执行，所以从 A 的角度看，余额 V1、V2 的值是 100 万，余额 V3 的值是 200万。

这四种隔离级别具体是如何实现的呢？

对于「读未提交」隔离级别的事务来说，因为可以读到未提交事务修改的数据，所以直接读取最新的数据就好了； 对于「串行化」隔离级别的事务来说，通过加锁让冲突的读写互相等待；访问不冲突的数据仍然可以并发； 对于「读提交」和「可重复读」隔离级别的事务来说，它们是通过 Read View来实现的，它们的区别在于创建 Read View 的时机不同， 「读提交」通常在每条普通 SELECT 的一致性读开始时创建新 Read View；「可重复读」通常在事务第一次一致性读时创建，后续一致性读复用 。在可重复读下， START TRANSACTION WITH CONSISTENT SNAPSHOT 可以在开启事务时建立快照。这里说的是快照读，UPDATE、DELETE 和锁定读不能套用这个规则。

# mysql默认级别是什么？

MySQL InnoDB 默认是可重复读，也就是 REPEATABLE READ。实际环境可能修改过，可以这样查看当前会话的隔离级别：

SELECT @ @transaction_isolation ;

MySQL 默认还开启 autocommit。如果没有显式开启事务，每条 SQL 通常都是一个独立事务，多次 SELECT 也就不一定共用同一个快照。

# 可重复读隔离级别下，A事务提交的数据，在B事务能看见吗？

要看 B 有没有建立快照，以及使用的是快照读还是当前读。

B 已经建立快照，继续普通 SELECT ：如果 A 在快照建立后才提交，B 通常看不到 A 的修改，而是沿 undo 版本链读取快照可见的旧版本。 B 只是执行了 BEGIN，还没有快照读 ：如果 A 在 B 第一次快照读前已经提交，那么 B 建立快照时就可以看到 A 的数据。 B 使用 SELECT ... FOR UPDATE 等当前读 ：不会复用普通 SELECT 的旧快照，而是读取并锁定当前记录；遇到未提交事务持有冲突锁时会等待。

另外，B 自己修改过的数据对自己可见。所以，不能只根据「B 比 A 先开启事务」，就断言 B 一定看不到 A 的提交。



# 举个例子说可重复读下的幻读问题

普通快照读复用同一个 Read View，可以避免其他事务插入记录导致两次快照查询结果变化；不过混用快照读和当前读，还可能出现看起来像幻读的现象 。

我举例一个可重复读隔离级别发生幻读现象的场景。以这张表作为例子：



事务 A 执行查询 id = 5 的记录，此时表中是没有该记录的，所以查询不出来。

# 事务 A mysql > begin ; Query OK , 0 rows affected ( 0.00 sec ) mysql > select * from t_stu where id = 5 ; Empty set ( 0.01 sec )

然后事务 B 插入一条 id = 5 的记录，并且提交了事务。

# 事务 B mysql > begin ; Query OK , 0 rows affected ( 0.00 sec ) mysql > insert into t_stu values ( 5 , '小美' , 18 ) ; Query OK , 1 row affected ( 0.00 sec ) mysql > commit ; Query OK , 0 rows affected ( 0.00 sec )

此时， 事务 A 虽然在旧快照里看不到 id = 5，但 UPDATE 使用的是当前读，所以能更新 B 已经提交的记录 。更新后，这个新版本属于 A 自己，后续普通 SELECT 就可以看到，于是出现了前一次查询没有、后一次却有的现象。

# 事务 A mysql > update t_stu set name = '小林coding' where id = 5 ; Query OK , 1 row affected ( 0.01 sec ) Rows matched : 1 Changed: 1 Warnings : 0 mysql > select * from t_stu where id = 5 ; + ----+--------------+------+ | id | name | age | + ----+--------------+------+ | 5 | 小林coding | 18 | + ----+--------------+------+ 1 row in set ( 0.00 sec )

整个发生幻读的时序图如下：

在可重复读隔离级别下，事务 A 第一次执行普通的 select 语句时生成了一个 ReadView，之后事务 B 向表中新插入了一条 id = 5 的记录并提交。接着，事务 A 对 id = 5 这条记录进行了更新操作，在这个时刻，这条新记录的 trx_id 隐藏列的值就变成了事务 A 的事务 id，之后事务 A 再使用普通 select 语句去查询这条记录时就可以看到这条记录了，于是就发生了幻读。

这个例子的关键是 UPDATE 使用当前读，而且事务始终能看到自己的修改 ，不是 Read View 在中途自动更新了。如果 A 不执行 UPDATE，只是再次做相同的普通 SELECT，仍然看不到 B 后插入的记录。

同样，如果第一次是普通 SELECT，第二次改成 SELECT ... FOR UPDATE，也可能因为两种读的语义不同而看到不同的记录集合。需要先查询、再依据结果修改的业务，通常应从一开始就使用合适的锁定读或条件更新。

# Mysql 设置了可重读隔离级后，怎么保证不发生幻读？

要先区分业务是在做一致性查询，还是要根据查询结果继续修改。

只做普通快照读 ：在同一个可重复读事务里复用 Read View，就不会因为其他事务插入记录，让相同条件的快照查询突然多出记录。 先查后改，需要阻止条件范围内出现新记录 ：在显式事务中，从第一次查询就使用 SELECT ... FOR UPDATE 等锁定读。InnoDB 会根据索引扫描范围加记录锁、间隙锁或 next-key lock，锁一直持有到事务结束。

比如，要查询并处理余额在一个区间内的账户，可以给 balance 建索引，再执行：

BEGIN ; SELECT id , balance FROM accounts WHERE balance >= 1000000 AND balance < 2000000 FOR UPDATE ; -- 根据查询结果执行后续操作 COMMIT ;

这里锁的是实际扫描的索引范围，有时比 WHERE 表达的范围更大。如果是唯一索引的等值查询，并且记录存在，就可能退化成记录锁，并不是所有 FOR UPDATE 都加 next-key lock。缺少合适索引时，加锁范围还可能明显扩大。

# 串行化隔离级别是通过什么实现的？

对于 InnoDB，在 SERIALIZABLE 隔离级别下，如果是显式多语句事务，普通 SELECT 会隐式变成类似 SELECT ... FOR SHARE 的锁定读，通过共享记录锁或 next-key lock 与其他事务的写操作形成互斥。

比如事务 A 读了一段记录，事务 B 想修改这些记录，或者向被锁住的间隙插入，就需要等待 A 结束。这种方式可以阻止不可重复读和幻读，但锁竞争也会更多。

如果开启 autocommit，并且 SELECT 自己就是一个只读事务，InnoDB 可以用非锁定一致性读完成。串行化也不等于整个数据库只能执行一个事务，不冲突的数据操作仍然可以并发。

# 介绍MVCC实现原理

MVCC 通过数据的多个版本，让普通快照读和写操作尽量不互相阻塞。读取时不一定取最新版本，而是根据 Read View 判断哪个版本对当前事务可见。

MVCC 的核心是「隐藏字段 + undo 版本链 + Read View」 ，不是在开启事务时把整张表复制一份。读提交和可重复读都用到 MVCC，不过快照的创建时机不同。

对于「读提交」和「可重复读」隔离级别的事务来说，它们是通过 Read View 来实现的，它们的区别在于创建 Read View 的时机不同，大家可以把 Read View 理解成一个数据快照，就像相机拍照那样，定格某一时刻的风景。

「读提交」隔离级别是每条普通 SELECT 的一致性读开始时创建新的 Read View； 「可重复读」隔离级别通常在第一次一致性读时创建 Read View，后续快照读复用；锁定读不复用这个快照。

Read View 有四个重要的字段：



m_ids ：指的是在创建 Read View 时，当前数据库中「活跃事务」的 事务 id 列表 ，注意是一个列表， 这里关注的是已经分配事务 ID、但还没提交的读写事务 ，只读事务不一定会分配这种事务 ID。 min_trx_id ：指的是在创建 Read View 时，当前数据库中「活跃事务」中事务 id 最小的事务 ，通常是 m_ids 的最小值；如果没有其他活跃读写事务，这个边界与 max_trx_id 相同。 max_trx_id ：这个并不是 m_ids 的最大值，而是 创建 Read View 时当前数据库中应该给下一个事务的 id 值 ，也就是全局事务中最大的事务 id 值 + 1； creator_trx_id ：指的是 创建该 Read View 的事务的事务 id 。

对于使用 InnoDB 存储引擎的数据库表，它的聚簇索引记录中都包含下面两个隐藏列：



trx_id，当一个事务对某条聚簇索引记录进行改动时，就会 把该事务的事务 id 记录在 trx_id 隐藏列里 ； roll_pointer，每次对某条聚簇索引记录进行改动时，都会把旧版本的记录写入到 undo 日志中，然后 这个隐藏列是个指针，指向每一个旧版本记录 ，于是就可以通过它找到修改前的记录。这里的旧版本通常是通过 undo 中的回滚信息重建出来的，不一定是每次修改都复制一份完整行。

一个事务去访问记录的时候，除了自己的更新记录总是可见之外，还有这几种情况：

如果记录的 trx_id 值小于 Read View 中的 min_trx_id 值，表示这个版本的记录是在创建 Read View 前 已经提交的事务生成的，所以该版本的记录对当前事务 可见 。 如果记录的 trx_id 值大于等于 Read View 中的 max_trx_id 值，表示这个版本来自创建 Read View 后才分配事务 ID 的事务，所以该版本对当前事务 不可见 。 如果记录的 trx_id 值在 Read View 的 min_trx_id 和 max_trx_id 之间，需要判断 trx_id 是否在 m_ids 列表中： 如果记录的 trx_id 在 m_ids 列表中，表示这个事务在创建 Read View 时还没有提交，所以该版本 不可见 。即使它后来提交了，也不会改变这个旧 Read View 的判断。 如果记录的 trx_id 不在 m_ids 列表中，表示这个事务在创建 Read View 前已经提交，所以该版本 可见 。

如果当前版本不可见，就沿 roll_pointer 找到 undo 中的旧版本，再按相同规则判断，直到找到可见版本或确认这条记录对当前快照不存在。



这种通过「版本链」来控制并发事务访问同一个记录时的行为就叫 MVCC（多版本并发控制）。

# 快照读和当前读有什么区别？

快照读读取的是 Read View 可见的数据版本，当前读读取的是当前记录，并根据操作加锁 。

在读提交、可重复读下，普通 SELECT 通常是快照读，通过 MVCC 获取可见版本，不会因为别的事务给记录加了排他锁就一定等待。 SELECT ... FOR UPDATE 、 SELECT ... FOR SHARE ，以及 UPDATE、DELETE 等属于当前读相关操作。如果遇到其他事务持有冲突锁，需要等待，不能直接绕过锁读未提交的修改。

举个栗子，A 在可重复读事务中通过普通 SELECT 读到余额 100，B 把余额改成 200 并提交。A 再做普通 SELECT，仍然可能看到 100；但 A 执行 UPDATE accounts SET balance = balance + 10 WHERE id = 1 ，是基于当前的 200 更新，结果是 210，不是 110。



所以，判断可重复读下的查询和更新行为时，一定要先说明用的是哪一种读。

# 有了事务，为什么还会出现丢失更新？

因为单条 UPDATE 虽然会加锁，但是 「先读到应用里，再计算，最后写回」不一定是一个受保护的整体 。

比如库存原来是 10，两个请求都用普通 SELECT 读到 10，各自在应用里减 1，然后执行 UPDATE products SET stock = 9 WHERE id = 1 。两次 UPDATE 可以先后成功，但最终库存还是 9，相当于丢了一次扣减。



常见的处理方式有三种：

原子条件更新 ：直接让数据库基于当前值计算，比如 SET stock = stock - 1 WHERE stock > 0 。 悲观锁 ：在同一个事务里先 SELECT ... FOR UPDATE ，拿到锁后再计算和更新。 乐观锁 ：增加 version 字段，更新时同时检查原版本：

UPDATE products SET stock = stock - 1 , version = version + 1 WHERE id = 1 AND version = 5 AND stock > 0 ;

影响行数为 1，说明更新成功；为 0，说明版本变化或库存条件不满足，应用需要重新判断。不能把 UPDATE 执行时的行锁，理解成之前普通 SELECT 的结果也自动受到了保护。

# 如何用 MySQL 扣减库存，避免超卖？

对于单个商品的库存，可以用一条带条件的 UPDATE：

UPDATE products SET stock = stock - 1 WHERE id = 100 AND stock > 0 ;

InnoDB 更新时会锁住对应记录，多个事务的扣减会按锁的顺序执行，并根据当前库存判断是否满足 stock > 0。库存只剩 1 时，第一个事务扣成 0，后面的事务就不能再满足条件。



应用需要检查影响行数： 1 表示扣减成功，0 表示库存不足或商品不存在 。不能只看 SQL 有没有报错。如果扣减数量是 n，还要保证 n 大于 0，并写成 stock = stock - n WHERE stock >= n 。

如果还需要创建订单，就把库存扣减和订单写入放到同一个事务，任一步失败都回滚。同时给业务请求或订单号建立唯一约束，避免请求重试重复扣库存。数据库的条件更新能防止库存变负数，业务幂等还需要单独保证。

# 一条update是不是原子性的？为什么？

对于 InnoDB，普通的一条 UPDATE 是事务中的原子操作，即使影响多行，也不能只提交其中一部分修改。

undo log 负责回滚 ：如果语句执行失败需要撤销修改，可以通过 undo 恢复更新前的状态，这是原子性的核心。 锁负责并发控制 ：更新时加排他锁，让其他冲突的更新等待，但锁本身不是实现回滚的机制。

开启 autocommit 时，一条 UPDATE 通常就是一个独立事务；在显式事务中，UPDATE 执行成功还不等于整个事务已经提交。

还要注意， 一条语句报错，不代表整个多语句事务已经自动回滚 。比如普通重复键错误通常只回滚当前语句；死锁会回滚被选中的整个事务；锁等待超时默认通常只回滚当前语句。应用要根据错误处理，必要时主动 ROLLBACK，不能失败后继续提交前面的修改。

# 滥用事务，或者一个事务里有特别多sql的弊端？

问题主要在于事务持有锁和旧版本的时间太长，不只是 SQL 数量多。

锁竞争加重 ：写事务长时间占有记录锁，其他更新容易等待、超时，交叉加锁还可能出现死锁。 undo 积累 ：大量修改产生很多 undo；长时间持有旧快照的读事务，即使自己不更新，也可能阻碍旧版本清理，增加空间和版本链遍历成本。 提交、回滚成本高 ：大事务的 binlog 和 undo 较多，出错后回滚也可能耗时很长。 主从延迟增加 ：从库需要应用已经提交的事务，大事务提交后可能产生大量回放工作，也会影响并行复制的效率。 DDL 被阻塞 ：事务访问过的表可能一直持有 MDL 读锁，让 ALTER TABLE 等结构变更等待。



所以，尽量把事务范围控制在必要的数据库操作里，不要在事务中长时间调用外部接口、等待用户输入。批量任务可以结合业务一致性要求分批提交，但不能为了缩短事务，把必须原子完成的业务步骤随意拆开。
