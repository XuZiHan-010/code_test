# 锁

# 讲一下mysql里有哪些锁？

在 MySQL 里，根据加锁的范围，可以分为 全局锁、表级锁和行锁 三类。



全局锁 ：通过flush tables with read lock 语句会将整个数据库就处于只读状态了，这时其他线程执行以下操作，增删改或者表结构修改都会阻塞。全局锁主要应用于做 全库逻辑备份 ，这样在备份数据库期间，不会因为数据或表结构的更新，而出现备份文件的数据与预期的不一样。 表级锁 ：MySQL 里面表级别的锁有这几种： 表锁：通过lock tables 语句可以对表加表锁，表锁除了会限制别的线程的读写外，也会限制本线程接下来的读写操作。 元数据锁：当我们对数据库表进行操作时，会自动给这个表加上 MDL，对一张表进行 CRUD 操作时，加的是 MDL 读锁 ；对一张表做结构变更操作的时候，加的是 MDL 写锁 ；MDL 是为了保证当用户对表执行 CRUD 操作时，防止其他线程对这个表结构做了变更。 意向锁：当执行插入、更新、删除操作，需要先对表加上「意向独占锁」，然后对该记录加独占锁。 意向锁的目的是为了快速判断表里是否有记录被加锁 。 行级锁 ：InnoDB 引擎是支持行级锁的，而 MyISAM 引擎并不支持行级锁。 记录锁，锁住的是一条记录。而且记录锁是有 S 锁和 X 锁之分的，满足读写互斥，写写互斥 间隙锁，锁住两条索引记录之间的间隙，主要用于阻止其他事务向间隙插入。可重复读的范围查询中经常使用，串行化下也可能使用；读提交下通常不为普通搜索加间隙锁，但外键检查、重复键检查等仍可能使用。 Next-Key Lock 称为临键锁，是 Record Lock + Gap Lock 的组合，通常表示「前一个索引值到当前索引值」的左开右闭区间，比如 (5, 10]。



另外还有插入意向锁，插入记录前需要申请对应间隙的插入意向锁。它属于间隙锁的一种，不要和表级的意向锁混淆；向同一间隙的不同位置插入，通常可以并发。

# 数据库的表锁和行锁有什么作用？

表锁的作用：

整体控制 ：表锁按共享、排他等兼容关系控制整张表的访问。比如显式 READ 表锁允许其他会话读、阻止写；显式 WRITE 表锁会阻止其他会话读写，不能把所有表级锁都理解成禁止任何访问。 粒度大 ：表锁的粒度比较大，在锁定表的情况下，可能会影响到整个表的其他操作，可能会引起锁竞争和性能问题。 适用于大批量操作 ：表锁适合于需要大批量操作表中数据的场景，例如表的重建、大量数据的加载等。

行锁的作用：

细粒度控制 ：行锁可以精确控制对表中某行数据的访问，使得其他事务可以同时访问表中的其他行数据，在并发量大的系统中能够提高并发性能。 减少锁冲突 ：行锁不会像表锁那样造成整个表的锁冲突，减少了锁竞争的可能性，提高了并发访问的效率。 适用于频繁单行操作 ：行锁适合于需要频繁对表中单独行进行操作的场景，例如订单系统中的订单修改、删除等操作。

# MySQL两个线程的update语句同时处理一条数据，会不会有阻塞？

如果是两个事务同时更新了 id = 1，比如 update ... where id = 1，那么是会阻塞的。因为 InnoDB 存储引擎实现了行级锁。

当A事务对 id =1  这行记录进行更新时，会对主键 id 为 1 的记录加X类型的记录锁，这样第二事务对 id = 1 进行更新时，发现已经有记录锁了，就会陷入阻塞状态。

# 两条update语句处理一张表的不同的主键范围的记录，一个<10，一个>15，会不会遇到阻塞？底层是为什么的？

如果两条语句都按主键做范围扫描，没有其他关联操作，实际加的记录锁互不冲突，通常可以并发执行。

不过， 不能只把 WHERE 的数字范围画出来，就当成实际加锁范围 。在可重复读下，范围更新通常还涉及间隙锁或 next-key lock，边界取决于真实索引记录和扫描过程。例如 id < 10 扫描到边界时，可能还会锁住最后一条符合条件记录之后的间隙，而不是只锁所有 id < 10 的现有行。

还要注意两点：

间隙锁之间可以共存，所以间隙有重叠，也不等于两个 UPDATE 一定互相阻塞；插入意向锁遇到相应间隙锁才可能等待。 UPDATE 如果还要维护其他索引、检查唯一键或外键，也可能产生额外锁冲突。

因此，普通主键范围更新能否并发，要看实际访问的索引和锁是否冲突，不能仅凭条件范围一概判断。



# 如果2个范围不是主键或索引？还会阻塞吗？

如果过滤字段没有可用索引，UPDATE 可能需要扫描聚簇索引上的所有记录，加锁范围就会明显扩大，即使两条语句在业务上更新的是不同记录，也可能互相等待。

在读提交下，UPDATE 可以在判断条件后释放不匹配记录的锁，普通搜索也通常不加间隙锁，所以不能把可重复读下的结论原样套过去。不过扫描量仍然很大，锁等待也仍可能发生。

这里不是把行锁升级成了表锁 ，而是由于扫描范围变大，加了很多行级锁。给更新条件建立合适索引，既能减少扫描，也能减少锁冲突。

# InnoDB 的行锁锁的是行，还是索引？

InnoDB 的行级锁是加在索引记录上的 ，不是给磁盘里的某一行地址单独挂一把锁。

比如按主键更新，锁住的是主键索引记录；按二级索引更新，通常既会对扫描到的二级索引记录加锁，也会锁住对应的聚簇索引记录。没有显式主键时，InnoDB 也会有聚簇索引，并不是没有索引就无法加行锁。



所以，「没有用索引就会升级成表锁」这个说法不准确。真正的问题是扫描和加锁范围扩大，可能让整个表的大量操作都受到影响。

# MySQL 为什么会死锁？怎么处理？

死锁就是多个事务各自持有对方需要的锁，又都在等待对方释放，形成循环等待。

举个栗子：

-- 事务 A BEGIN ; UPDATE accounts SET balance = balance - 100 WHERE id = 1 ; -- 接着尝试更新 id = 2 -- 事务 B，在另一个连接中执行 BEGIN ; UPDATE accounts SET balance = balance - 100 WHERE id = 2 ; -- 接着尝试更新 id = 1

A 持有 id = 1 的锁、等待 id = 2；B 持有 id = 2 的锁、等待 id = 1，就形成死锁。不是只有跨表才会死锁，同一张表的多行、索引记录和间隙之间也可能形成循环等待。



InnoDB 默认开启死锁检测，发现死锁后会选择一个事务回滚，通常倾向于修改记录较少、回滚代价较小的事务，应用需要对整个事务做有限次数重试。

减少死锁可以从这些方向入手：

多个事务按相同顺序访问记录，比如转账时统一先锁较小的账户 ID。 缩短事务，避免拿着数据库锁调用耗时的外部接口。 为条件建立合适索引，减少扫描和加锁范围。 通过 SHOW ENGINE INNODB STATUS 查看最近一次死锁；MySQL 8.0 还可以结合 performance_schema.data_locks 和 data_lock_waits 分析当前锁等待。

死锁回滚通常针对整个事务，而锁等待超时默认通常只回滚当前语句。业务重试前要确认事务状态，必要时先主动回滚，再重新执行完整业务流程。

# 为什么执行 ALTER TABLE 会把后续查询也堵住？

常见原因是 MDL，也就是元数据锁。

比如事务 A 查询过一张表，但一直没有提交，它持有这张表的 MDL 读锁。此时 B 执行 ALTER TABLE，需要 MDL 写锁，就要等待 A 结束。

后续新的查询也需要 MDL 读锁，但在有写锁请求排队时，也可能继续排队，避免结构变更一直抢不到锁。这样就会出现「一个长事务阻塞 ALTER TABLE，ALTER TABLE 又挡住后续查询」的情况。



排查时可以查看进程状态是否有 Waiting for table metadata lock ，再结合 performance_schema.metadata_locks 、 information_schema.innodb_trx 找到未结束的事务。即使使用在线 DDL，开始或结束等阶段也仍需要元数据锁，不能理解成全程不阻塞。
