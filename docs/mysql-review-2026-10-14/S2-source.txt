先来一个上帝视角图，下面就是 MySQL 执行一条 SQL 查询语句的流程，也从图中可以看到 MySQL 内部架构里的各个功能模块。



连接器：建立连接，管理连接、校验用户身份； 查询缓存：查询语句如果命中查询缓存则直接返回，否则继续往下执行。MySQL 8.0 已删除该模块； 解析 SQL，通过解析器对 SQL 查询语句进行词法分析、语法分析，然后构建语法树，方便后续模块读取表名、字段、语句类型； 执行 SQL：执行 SQL 共有三个阶段： 预处理阶段：检查表或字段是否存在；将 select * 中的 * 符号扩展为表上的所有列。 优化阶段：基于查询成本的考虑， 选择查询成本最小的执行计划； 执行阶段：根据执行计划执行 SQL 查询语句，从存储引擎读取记录，返回给客户端；

# 讲一讲mysql的引擎吧，你有什么了解？

InnoDB：InnoDB是MySQL的默认存储引擎，具有ACID事务支持、行级锁、外键约束等特性。它适用于高并发的读写操作，支持较好的数据完整性和并发控制。 MyISAM：MyISAM 是较早版本中常用的存储引擎，数据和索引分开保存，使用表级锁，不支持事务和外键。它在部分只读场景中有优势，但不能简单认为读多的业务就一定适合 MyISAM，实际还要考虑并发写入和故障恢复需求。 Memory：Memory引擎将数据存储在内存中，适用于对性能要求较高的读操作，但是在服务器重启或崩溃时数据会丢失。它不支持事务、行级锁和外键约束。

# MySQL为什么InnoDB是默认引擎？

InnoDB引擎在事务支持、并发性能、崩溃恢复等方面具有优势，因此被MySQL选择为默认的存储引擎。

事务支持：InnoDB引擎提供了对事务的支持，可以进行ACID（原子性、一致性、隔离性、持久性）属性的操作。Myisam存储引擎是不支持事务的。 并发性能：InnoDB引擎采用了行级锁定的机制，可以提供更好的并发性能，Myisam存储引擎只支持表锁，锁的粒度比较大。 崩溃恢复：InnoDB 引擎通过 redo log 日志实现了崩溃恢复，可以在数据库发生异常情况（如断电）时，通过日志文件进行恢复，保证数据的持久性和一致性。MyISAM 是不支持崩溃恢复的。

# 说一下mysql的innodb与MyISAM的区别？

事务 ：InnoDB 支持事务，MyISAM 不支持事务，这是 MySQL 将默认存储引擎从 MyISAM 变成 InnoDB 的重要原因之一。 索引结构 ：InnoDB 使用聚簇索引组织数据，MyISAM 的索引与数据分开保存。InnoDB 聚簇索引的叶子节点保存行数据，即使没有显式主键，也会选择合适的唯一索引或生成隐藏行 ID 来组织数据。辅助索引保存索引列和主键值，需要读取索引中没有的字段时才会回表；覆盖索引查询不需要为了获取这些字段而回表。因此，主键不应该过大，因为主键太大，其他索引也都会很大。而 MyISAM 的数据文件是分离的，索引保存的是数据记录的位置，主键索引和辅助索引都通过这个位置访问数据。 锁粒度 ：InnoDB 最小的锁粒度是行锁，MyISAM 最小的锁粒度是表锁。一个更新语句会锁住整张表，导致其他查询和更新都会被阻塞，因此并发访问受限。 count 的效率 ：InnoDB 不保存所有事务都能直接使用的精确总行数，执行无 WHERE 的 COUNT(*) 通常需要扫描索引，统计当前事务可见的记录。MyISAM 保存了整张表的行数，简单的无 WHERE 计数可以直接读取；加了 WHERE 条件后，也不能只靠这个总行数返回结果。

# 数据管理里，数据文件大体分成哪几种数据文件？

先区分一下版本和表空间配置。下面以 MySQL 5.7、InnoDB 独立表空间为例，数据目录假设是 /var/lib/mysql/ ，实际位置可以通过 SHOW VARIABLES LIKE 'datadir' 查看。每个数据库通常有对应的目录，用来保存该数据库的表文件。

比如，我这里有一个名为 my_test 的 database，该 database 里有一张名为 t_order 数据库表。



然后，我们进入 /var/lib/mysql/my_test 目录，看看里面有什么文件？

[root@xiaolin ~]#ls /var/lib/mysql/my_test
db.opt  
t_order.frm  
t_order.ibd

可以看到，共有三个文件，这三个文件分别代表着：

db.opt，用来存储当前数据库的默认字符集和字符校验规则。 t_order.frm ，t_order 的表结构会保存在这个文件。在 MySQL 中建立一张表都会生成一个.frm 文件，该文件是用来保存每个表的元数据信息的，主要包含表结构定义。 t_order.ibd，t_order 的表数据会保存在这个文件。表数据既可以存在共享表空间文件（文件名：ibdata1）里，也可以存放在独占表空间文件（文件名：表名字.ibd）。这个行为是由参数 innodb_file_per_table 控制的，若设置了参数 innodb_file_per_table 为 1，则会将存储的数据、索引等信息单独存储在一个独占表空间，从 MySQL 5.6.6 版本开始，它的默认值就是 1 了，默认情况下，新建表会使用独立的 .ibd 文件，但已有表或显式使用其他表空间的表不一定如此。

MySQL 8.0 已经取消了 .frm 文件 ，表结构等元数据改为保存在事务型数据字典中。独立表空间的 .ibd 文件仍然保存表数据和索引，所以不能把上面的 5.7 文件布局直接套到 8.0 上。

# Buffer Pool 是什么？有什么作用？

Buffer Pool 是 InnoDB 的内存缓冲区，主要缓存数据页和索引页。大家可以把它理解成磁盘数据在内存里的「工作区」。

查询时，先看需要的页是否已经在 Buffer Pool 中，命中就直接读取；没命中才从磁盘加载。 更新时，通常先修改 Buffer Pool 中的页，修改后的页叫脏页，再由后台线程择机刷回磁盘。 事务提交时，如果 redo log 已经按要求持久化，就不需要等所有脏页刷盘，这样能减少提交时的随机 I/O。



它和 MySQL 8.0 已删除的查询缓存不是一回事： Buffer Pool 缓存的是页，查询缓存缓存的是 SQL 的结果 。

为了避免一次大表扫描把热点页全部挤出去，InnoDB 采用改进的 LRU 策略，把链表分成新、老两个区域，新加载的页先进入老区域，再结合访问时机决定是否移到新区域。
