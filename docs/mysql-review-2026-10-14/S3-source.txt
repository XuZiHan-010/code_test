# 索引

# 索引是什么？有什么好处？

索引类似于书籍的目录，可以减少扫描的数据量，提高查询效率。

没有合适索引时，通常需要扫描整张表，逐行判断是否满足条件，时间复杂度可以理解为 O(N)。 有合适索引时，可以沿 B+ 树逐层定位，查找复杂度可以理解为 O(log N)，再扫描满足条件的记录。

不过，索引的价值不只是「找得快」，还可以帮助完成排序、分组，或者通过覆盖索引减少回表。对于范围查询，返回的数据越多，扫描和读取的成本也会越大，不能认为只要用了索引，整条 SQL 就一定很快。

# 讲讲索引的分类是什么？

MySQL可以按照四个角度来分类索引。

按「数据结构」分类： B+tree索引、Hash索引、Full-text索引 。 按「物理存储」分类： 聚簇索引（主键索引）、二级索引（辅助索引） 。 按「字段特性」分类： 主键索引、唯一索引、普通索引、前缀索引 。 按「字段个数」分类： 单列索引、联合索引 。

接下来，按照这些角度来说说各类索引的特点。

按数据结构分类

从数据结构的角度来看，MySQL 常见索引有 B+Tree 索引、HASH 索引、Full-Text 索引。

每一种存储引擎支持的索引类型不一定相同，我在表中总结了 MySQL 常见的存储引擎 InnoDB、MyISAM 和 Memory 分别支持的索引类型。



InnoDB 是在 MySQL 5.5 之后成为默认的 MySQL 存储引擎，B+Tree 索引类型也是 MySQL 存储引擎采用最多的索引类型。

在创建表时，InnoDB 存储引擎会根据不同的场景选择聚簇索引：

如果有主键，默认会使用主键作为聚簇索引的索引键（key）； 如果没有主键，就选择第一个所有索引列都定义为 NOT NULL 的唯一索引作为聚簇索引的索引键（key）； 在上面两个都没有的情况下，InnoDB 会生成一个 6 字节的隐藏行 ID，作为聚簇索引的索引键（key）；

其它索引都属于辅助索引（Secondary Index），也被称为二级索引或非聚簇索引。 创建的主键索引和二级索引默认使用的是 B+Tree 索引 。

按物理存储分类

从物理存储的角度来看，索引分为聚簇索引（主键索引）、二级索引（辅助索引）。

这两个区别在前面也提到了：

主键索引的 B+Tree 的叶子节点存放的是实际数据，所有完整的用户记录都存放在主键索引的 B+Tree 的叶子节点里； 二级索引的 B+Tree 的叶子节点保存索引列的值和主键值，不保存完整的行数据。

所以，在查询时使用了二级索引，如果查询的数据能在二级索引里查询的到，那么就不需要回表，这个过程就是覆盖索引。如果查询的数据不在二级索引里，就会先检索二级索引，找到对应的叶子节点，获取到主键值后，然后再检索主键索引，就能查询到数据了，这个过程就是回表。

按字段特性分类

从字段特性的角度来看，索引分为主键索引、唯一索引、普通索引、前缀索引。

主键索引

主键索引就是建立在主键字段上的索引，通常在创建表的时候一起创建，一张表最多只有一个主键索引，索引列的值不允许有空值。

在创建表时，创建主键索引的方式如下（这里只展示定义方式，其他字段省略）：

CREATE TABLE table_name ( . . . . PRIMARY KEY ( index_column_1 ) USING BTREE ) ;

唯一索引

唯一索引用来限制索引键不重复，一张表可以有多个唯一索引。如果是联合唯一索引，限制的是多个字段的组合唯一，不是每个字段分别唯一。MySQL 的唯一索引允许多个 NULL，需要禁止空值时再加 NOT NULL。

在创建表时，创建唯一索引的方式如下：

CREATE TABLE table_name ( . . . . UNIQUE KEY ( index_column_1 , index_column_2 , . . . ) ) ;

建表后，如果要创建唯一索引，可以使用这面这条命令：

CREATE UNIQUE INDEX index_name ON table_name ( index_column_1 , index_column_2 , . . . ) ;

普通索引

普通索引就是建立在普通字段上的索引，既不要求字段为主键，也不要求字段为 UNIQUE。

在创建表时，创建普通索引的方式如下：

CREATE TABLE table_name ( . . . . INDEX ( index_column_1 , index_column_2 , . . . ) ) ;

建表后，如果要创建普通索引，可以使用这面这条命令：

CREATE INDEX index_name ON table_name ( index_column_1 , index_column_2 , . . . ) ;

前缀索引

前缀索引是指对字符类型字段的前几个字符建立的索引，而不是在整个字段上建立的索引，前缀索引可以建立在 CHAR、VARCHAR、BINARY、VARBINARY 等列上，TEXT、BLOB 列建立普通 B+ 树索引时也需要指定前缀长度。

使用前缀索引的目的是为了减少索引占用的存储空间，提升查询效率。

在创建表时，创建前缀索引的方式如下：

CREATE TABLE table_name ( column_list , INDEX ( column_name ( length ) ) ) ;

建表后，如果要创建前缀索引，可以使用这面这条命令：

CREATE INDEX index_name ON table_name ( column_name ( length ) ) ;

按字段个数分类

从字段个数的角度来看，索引分为单列索引、联合索引（复合索引）。

建立在单列上的索引称为单列索引，比如主键索引； 建立在多列上的索引称为联合索引；

通过将多个字段组合成一个索引，该索引就被称为联合索引。

比如，将商品表中的 product_no 和 name 字段组合成联合索引(product_no, name)，创建联合索引的方式如下：

CREATE INDEX index_product_no_name ON product ( product_no , name ) ;

联合索引(product_no, name) 的 B+Tree 示意图如下（图中叶子节点之间我画了单向链表，但是实际上是双向链表，原图我找不到了，修改不了，偷个懒我不重画了，大家脑补成双向链表就行）。



可以看到，联合索引的非叶子节点用两个字段的值作为 B+Tree 的 key 值。当在联合索引查询数据时，先按 product_no 字段比较，在 product_no 相同的情况下再按 name 字段比较。

也就是说，联合索引查询的 B+Tree 是先按 product_no 进行排序，然后再 product_no 相同的情况再按 name 字段排序。

因此，使用联合索引定位数据时，要关注 最左匹配原则 ，也就是从最左边的字段开始，连续匹配索引列。跳过最左列后，通常就不能直接按后面的字段定位到一段连续的索引范围。

比如，如果创建了一个 (a, b, c) 联合索引，如果查询条件是以下这几种，就可以匹配上联合索引：

where a=1； where a=1 and b=2 and c=3； where a=1 and b=2；

需要注意的是，因为有查询优化器，所以 a 字段在 where 子句的顺序并不重要。

但是，如果查询条件是以下这几种，缺少最左边的 a，通常就不能使用这个索引进行常规的前缀定位：

where b=2； where c=3； where b=2 and c=3；

原因是 (a, b, c) 联合索引先按 a 排序，a 相同再按 b 排序，b 也相同再按 c 排序。所以， b 和 c 是全局无序、局部有序的 。

这里说的是不能按常规最左前缀快速定位，不代表索引完全不会被读取。覆盖索引时仍可能全索引扫描，MySQL 8.0 在满足条件时还可能采用索引跳跃扫描，最终要看执行计划。

联合索引有一些特殊情况， 并不是查询过程使用了联合索引查询，就代表联合索引中的所有字段都用到了联合索引进行索引查询 ，也就是可能存在部分字段用到联合索引的 B+Tree，部分字段没有用到联合索引的 B+Tree 的情况。

比如对于 WHERE a = 1 AND b > 2 AND c = 3 ，a、b 可以确定扫描范围，但这个范围里 c 并不是全局有序的，所以不能继续用 c = 3 把整段扫描范围缩成只包含目标记录的区间。

后面的字段不能继续缩小扫描范围，不代表完全没用 。它仍可能用于索引下推、覆盖索引等优化。IN 等条件还可能拆成多个等值范围，面试时不要把所有写法都机械地归成「范围之后全部失效」。



# 哈希索引使用场景是什么？

哈希索引优势是等值查询极快、能直接通过哈希函数定位数据位置，而短板是不支持范围查询、排序和前缀匹配，所以使用场景必然是那些以等值查询为核心，且不需要复杂查询操作的场景。

比如 MySQL 的 Memory 存储引擎，默认就用哈希索引。因为内存表本身是基于内存存储的，追求极致的查询速度，而这类场景通常都是简单的等值查询，比如缓存用户登录信息，通过用户 ID 快速查找对应的登录状态、权限信息，这时候哈希索引能直接通过用户 ID 计算哈希值，定位到数据所在的桶，查询效率接近 O(1)，比 B+ 树索引的等值查询更快。

# MySQL聚簇索引和非聚簇索引的区别是什么？



数据存储 ：在聚簇索引中，数据行在 B+ 树中按照索引键值组织，也就是说，索引的叶子节点包含了实际的数据行。这意味着索引结构本身就是数据的物理存储结构。非聚簇索引的叶子节点不包含完整的数据行，而是包含指向数据行的指针或主键值。数据行本身存储在聚簇索引中。 索引与数据关系 ：由于数据与索引紧密相连，当通过聚簇索引查找数据时，可以直接从索引中获得数据行，而不需要额外的步骤去查找数据所在的位置。当通过非聚簇索引查找数据时，首先在非聚簇索引中找到对应的主键值，然后通过这个主键值回溯到聚簇索引中查找实际的数据行，这个过程称为“回表”。 唯一性 ：聚簇索引通常是基于主键构建的，因此每个表只能有一个聚簇索引，因为数据只能有一种物理排序方式。一个表可以有多个非聚簇索引，因为它们不直接影响数据的物理存储位置。 效率 ：对于范围查询和排序查询，聚簇索引通常更有效率，因为它避免了额外的寻址开销。非聚簇索引在使用覆盖索引进行查询时效率更高，因为它不需要读取完整的数据行。但是需要进行回表的操作，使用非聚簇索引效率比较低，因为需要进行额外的回表操作。

# 如果聚簇索引的数据更新，它的存储要不要变化？

要看更新的是哪个字段，以及记录长度有没有变化。

更新主键 ：记录在聚簇索引中的排序位置会变化，需要调整聚簇索引；二级索引里也保存了主键值，所以也要维护。 更新二级索引列 ：聚簇索引中的主键顺序不变，但相关二级索引中的记录需要调整。 更新普通非索引列 ：如果记录长度基本不变，通常可以在原位置更新；如果变长字段增长导致当前页空间不足，仍可能涉及记录迁移、页分裂或页外存储等处理。

所以，不能简单说「更新非索引字段，存储结构一定不会变」。

# MySQL主键是聚簇索引吗？

在MySQL的InnoDB存储引擎中，主键确实是以聚簇索引的形式存储的。

InnoDB将数据存储在B+树的结构中，其中主键索引的B+树就是所谓的聚簇索引。这意味着表中的数据行在 B+ 树中按主键有序组织，聚簇索引的叶节点包含了实际的数据行。但有序说的是索引的逻辑顺序，不代表这些页在磁盘上一定连续存放。



InnoDB 在创建聚簇索引时，会根据不同的场景选择不同的列作为索引：

如果有主键，默认会使用主键作为聚簇索引的索引键； 如果没有主键，就选择第一个所有索引列都定义为 NOT NULL 的唯一索引作为聚簇索引的索引键； 在上面两个都没有的情况下，InnoDB 会生成一个 6 字节的隐藏行 ID，作为聚簇索引的索引键；

一张表只能有一个聚簇索引，那为了实现非主键字段的快速搜索，就引出了二级索引（非聚簇索引/辅助索引），它也是利用了 B+ 树的数据结构，不过叶子节点保存的是索引列和主键值，不包含完整的行数据。

# 什么字段适合当做主键？

字段具有唯一性，且不能为空的特性 字段尽量短、稳定、不频繁修改，因为二级索引也要保存主键值，主键越宽，所有二级索引的空间和维护成本也会增加。 字段最好有递增的趋势，如果字段的值是随机无序的，可能会引发页分裂的问题，造成性能影响。 不建议用业务数据作为主键，比如会员卡号、订单号、学生号之类的，因为我们无法预测未来会不会因为业务需要，而出现业务字段重复或者重用的情况。 通常情况下会用自增字段来做主键，对于单机系统来说是没问题的。但是，如果有多台服务器，各自都可以录入数据，那就不一定适用了。因为如果每台机器各自产生的数据需要合并，就可能会出现主键重复的问题，这时候就需要考虑分布式 id 的方案了。

# 性别字段能加索引么？为啥？

能加，但如果只是建立性别的单列索引，通常收益不大。

比如有 100 万条数据，男女各 50 万条，执行 SELECT * FROM users WHERE sex = '男' ，即使先通过二级索引找到 50 万条记录，还要大量回表读取其他字段，这时可能不如全表扫描，优化器就可能放弃这个索引。

不过， 值的种类少，不代表任何场景都不适合索引 ：

如果数据分布很不均匀，查询的是数量很少的那一类，索引可能有效。 如果只统计数量，索引可以覆盖查询，避免为获取其他列而回表。 如果和其他字段组成联合索引，例如 (sex, age) ，查询某个性别下指定年龄范围的用户，也可能有效。

所以，要结合实际查询、命中比例和回表成本判断，不能只看字段有几种取值。

# 表中十个字段，你主键用自增ID还是UUID，为什么？

用的是自增 id。

因为常见的随机 UUID 相对顺序的自增 id 来说，生成顺序和索引排序顺序不一致，新行的值不一定要比之前的主键的值要大，所以 innodb 无法做到总是把新行插入到索引的最后，而是需要为新行寻找新的合适的位置从而来分配新的空间。

这个过程需要做很多额外的操作，数据的毫无顺序会导致数据分布散乱，将会导致以下的问题：

写入的目标页很可能已经刷新到磁盘上并且从缓存上移除，或者还没有被加载到缓存中，innodb 在插入之前不得不先找到并从磁盘读取目标页到内存中，这将导致大量的随机 IO。 因为写入是乱序的，innodb 不得不频繁的做页分裂操作，以便为新的行分配空间，页分裂导致移动大量的数据，影响性能。 由于频繁的页分裂，页会变得稀疏并被不规则的填充，最终会导致数据会有碎片。

所以，单机业务通常优先选择短小、递增的主键。分布式系统还要考虑跨节点唯一性，可以使用合适的分布式 ID。这里主要说的是随机 UUID，不同 UUID 方案的有序性不同，不能把所有 UUID 都当成完全随机。



# 什么自增ID更快一些，UUID不快吗，它在B+树里面存储是有序的吗?

UUID 放进 B+ 树之后也是有序的，问题在于新生成的 UUID 不一定比前一个大 ，所以插入位置可能落到树的中间。

自增 ID 通常在聚簇索引的右侧追加，新插入的记录更容易集中在已经缓存的页上，减少随机读页、页分裂和空间碎片。随机 UUID 则可能需要访问不同的数据页，写入成本更高。

另外，BIGINT 只有 8 字节，常见的 UUID 字符串有 36 个字符。主键越宽，一个索引页能容纳的记录就越少，而且所有二级索引都要保存这个主键值，也会一起变大。

UUID 也可以用 BINARY(16) 保存，减少字符串存储和比较的开销；如果采用按时间有序的 UUID 方案，还可以改善插入局部性。不过，自增也不意味着完全没有页分裂或竞争，只是一般更适合 InnoDB 的写入方式。

# 自增主键一定连续吗？

不一定。 自增保证的是自动分配 ID，不保证没有空洞 。

比如，一个事务拿到了自增 ID，插入后又回滚，这个 ID 通常不会退回；插入失败、并发批量插入预分配 ID，也可能留下空洞。

而且，自增 ID 的分配顺序不等于事务提交顺序。事务 A 先拿到 100，事务 B 后拿到 101，但 B 完全可能先提交。所以，不能用「ID 连续」判断数据是否完整，也不能把 ID 顺序直接当成业务完成顺序。

# Mysql中的索引是怎么实现的  ？

MySQL InnoDB 引擎是用了B+树作为了索引的数据结构。

B+Tree 是一种多叉树，叶子节点才存放数据，非叶子节点只存放索引，而且每个节点里的记录都按该索引的键值有序组织：聚簇索引按主键排序，二级索引按索引列及主键值排序。每一层父节点的索引值都会出现在下层子节点的索引值中，因此在叶子节点中，包括了所有的索引值信息，并且每一个叶子节点都有两个指针，分别指向下一个叶子节点和上一个叶子节点，形成一个双向链表。

主键索引的 B+Tree 如图所示：



比如，我们执行了下面这条查询语句：

select * from product where id = 5 ;

这条语句使用了主键索引查询 id 号为 5 的商品。查询过程是这样的，B+Tree 会自顶向下逐层进行查找：

将 5 与根节点的索引数据 (1，10，20) 比较，5 在 1 和 10 之间，所以根据 B+Tree的搜索逻辑，找到第二层的索引数据 (1，4，7)； 在第二层的索引数据 (1，4，7)中进行查找，因为 5 在 4 和 7 之间，所以找到第三层的索引数据（4，5，6）； 在叶子节点的索引数据（4，5，6）中进行查找，然后我们找到了索引值为 5 的行数据。

如果这些索引页都不在 Buffer Pool 中，可以把读取一个节点近似看成一次磁盘 I/O，上面的定位过程就需要读取 3 个页。如果页已经在缓存里，就不需要为它再次读取磁盘。

B+Tree 的分叉数很大，千万级数据在很多场景下只需要 3～4 层就能组织起来，所以定位一条记录需要访问的页比较少。具体高度还取决于主键宽度、记录大小和页面填充率；二级索引回表、页外数据和范围扫描也会增加访问量，不能把 3～4 次当成整条查询固定的 I/O 上限。

# 查询数据时，到了B+树的叶子节点，之后的查找数据是如何做？

聚簇索引数据页中的记录按照「主键」顺序组成单向链表 ，单向链表的特点就是插入、删除非常方便，但是检索效率不高，最差的情况下需要遍历链表上的所有节点才能完成检索。

因此，数据页中有一个 页目录 ，起到记录的索引作用，就像我们书那样，针对书中内容的每个章节设立了一个目录，想看某个章节的时候，可以查看目录，快速找到对应的章节的页数，而数据页中的页目录就是为了能快速找到记录。那 InnoDB 是如何给记录创建页目录的呢？

将所有的记录划分成几个组，这些记录包括最小记录和最大记录。被标记删除、但还没有被 purge 物理清理的记录，仍可能留在页内链表中； 每个记录组的最后一条记录就是组内最大的那条记录，并且最后一条记录的头信息中会存储该组一共有多少条记录，作为 n_owned 字段（上图中粉红色字段） 页目录用来存储每组最后一条记录的地址偏移量，这些地址偏移量会按照先后顺序存储起来，每组的地址偏移量也被称之为槽（slot），每个槽相当于指针指向了不同组的最后一个记录。

# B+树的特性是什么？

所有叶子节点都在同一层 ：这是B+树的一个重要特性，使单条记录定位经过的树层数相同，实际 I/O 延迟还要看缓存命中情况，提高了搜索效率。每个叶子节点都包含指向相邻叶子节点的指针，形成一个链表，由于叶子节点之间的链接，B+树非常适合进行范围查询和排序扫描。可以沿着叶子节点的链表顺序访问数据，而无需进行多次随机访问。 非叶子节点存储键值 ：非叶子节点仅存储键值和指向子节点的指针，不包含数据记录。这些键值用于指导搜索路径，帮助快速定位到正确的叶子节点。并且，由于非叶子节点只存放键值，当数据量比较大时，相对于B树，B+树的层高更少，查找效率也就更高。 叶子节点存储数据记录 ：与B树不同，B+树的叶子节点存储实际的数据记录或指向数据记录的指针。这意味着每次搜索都会到达叶子节点，才能找到所需数据。 自平衡 ：B+树在插入、删除和更新操作后会自动重新平衡，确保树的高度保持相对稳定，从而保持良好的搜索性能。每个节点最多可以有M个子节点，最少可以有ceil(M/2)个子节点（除了根节点），这里的M是树的阶数。

# 说说B+树和B树的区别

在B+树中，数据都存储在叶子节点上，而非叶子节点只存储索引信息；而B树的非叶子节点既存储索引信息也存储部分数据。 B+树的叶子节点使用链表相连，便于范围查询和顺序访问；B树的叶子节点没有链表连接。 B+树的查找性能更稳定，每次查找都需要查找到叶子节点；而B树的查找可能会在非叶子节点找到数据，性能相对不稳定。

# B+树的好处是什么？

B 树和 B+ 都是通过多叉树的方式，会将树的高度变矮，所以这两个数据结构非常适合检索存于磁盘中的数据。

但是 MySQL 默认的存储引擎 InnoDB 采用的是 B+ 作为索引的数据结构，原因有：



B+ 树的非叶子节点不存放实际的记录数据，仅存放索引，因此数据量相同的情况下，相比存储即存索引又存记录的 B 树，B+树的非叶子节点可以存放更多的索引，因此 B+ 树可以比 B 树更「矮胖」，查询底层节点的磁盘 I/O次数会更少。 B+ 树把完整记录集中在叶子节点，非叶子节点只负责导航，比较适合按页组织和缓存。插入、删除仍可能触发页分裂、合并以及父节点调整，不能认为一定比 B 树的每次操作都快； B+ 树叶子节点之间用链表连接了起来，有利于范围查询，而 B 树要实现范围查询，因此只能通过树的遍历来完成范围查询，这会涉及多个节点的磁盘 I/O 操作，范围查询效率不如 B+ 树。

# B+树的叶子节点链表是单向还是双向？

双向的，为了实现倒序遍历或者排序。



Innodb 使用的 B+ 树有一些特别的点，比如：

B+ 树的叶子节点之间是用「双向链表」进行连接，这样的好处是既能向右遍历，也能向左遍历。 B+ 树的节点内容是数据页，数据页里存放了用户的记录以及各种信息，每个数据页默认大小是 16 KB。

InnoDB 根据索引类型不同，分为聚簇索引和二级索引。聚簇索引的叶子节点保存行数据，二级索引的叶子节点保存索引列和主键值，不保存完整行。

因为表的数据都是存放在聚集索引的叶子节点里，所以 InnoDB 存储引擎一定会为表创建一个聚集索引，且由于数据在物理上只会保存一份，所以聚簇索引只能有一个，而二级索引可以创建多个。

# MySQL为什么用B+树结构？和其他结构比的优点？

B+Tree vs B Tree： B+Tree 的非叶子节点只保存索引键和子节点指针，而 B 树的非叶子节点还要保存数据。因此同样大小的页里，B+Tree 通常可以容纳更多导航项，让树更矮，定位记录需要访问的页更少。另外，InnoDB 的 B+Tree 叶子节点用双向链表连接，范围查询找到起点后就能顺序扫描；B 树通常需要通过树的遍历获取范围内的数据。 B+Tree vs 二叉树： B+Tree 一个节点可以有很多子节点，而平衡二叉树每个节点最多只有两个子节点。相同数据量下，B+Tree 的高度通常更低，更适合以页为单位读取和缓存的磁盘存储。千万级数据的索引在很多场景下只有 3～4 层，实际磁盘 I/O 还要结合缓存命中、回表和扫描范围判断。 B+Tree vs Hash： Hash 做等值查询很快，平均查找复杂度接近 O(1)，不过需要处理哈希冲突，而且不适合范围查询、排序和前缀匹配。B+Tree 可以同时服务等值和范围查询，所以适用场景更广。

# 为什么 MySQL 不用跳表？

B+树的高度在3层时存储的数据可能已达千万级别，但对于跳表而言同样去维护千万的数据量那么所造成的跳表层数过高而导致的磁盘io次数增多，也就是使用B+树在存储同样的数据下磁盘io次数更少。

# 联合索引的实现原理？

将多个字段组合成一个索引，该索引就被称为联合索引。

比如，将商品表中的 product_no 和 name 字段组合成联合索引(product_no, name)，创建联合索引的方式如下：

CREATE INDEX index_product_no_name ON product ( product_no , name ) ;

联合索引(product_no, name) 的 B+Tree 示意图如下：



可以看到，联合索引的非叶子节点用两个字段的值作为 B+Tree 的 key 值。当在联合索引查询数据时，先按 product_no 字段比较，在 product_no 相同的情况下再按 name 字段比较。

也就是说，联合索引查询的 B+Tree 是先按 product_no 进行排序，然后再 product_no 相同的情况再按 name 字段排序。

因此，使用联合索引定位数据时，要关注 最左匹配原则 ，也就是从最左边的字段开始，连续匹配索引列。跳过最左列后，通常就不能直接按后面的字段定位到一段连续的索引范围。

比如，如果创建了一个 (a, b, c) 联合索引，如果查询条件是以下这几种，就可以匹配上联合索引：

where a=1； where a=1 and b=2 and c=3； where a=1 and b=2；

需要注意的是，因为有查询优化器，所以 a 字段在 where 子句的顺序并不重要。

但是，如果查询条件是以下这几种，缺少最左边的 a，通常就不能使用这个索引进行常规的前缀定位：

where b=2； where c=3； where b=2 and c=3；

原因是 (a, b, c) 联合索引先按 a 排序，a 相同再按 b 排序，b 也相同再按 c 排序。所以， b 和 c 是全局无序、局部有序的 。

这里说的是不能按常规最左前缀快速定位，不代表索引完全不会被读取。覆盖索引时仍可能全索引扫描，MySQL 8.0 在满足条件时还可能采用索引跳跃扫描，最终要看执行计划。

我这里举联合索引（a，b）的例子，该联合索引的 B+ Tree 如下：



可以看到，a 是全局有序的（1, 2, 2, 3, 4, 5, 6, 7 ,8），而 b 是全局是无序的（12，7，8，2，3，8，10，5，2）。因此，直接执行 WHERE b = 2 ，通常不能像 WHERE a = 2 AND b = 2 那样按最左前缀定位。这里要区分「利用索引定位」和「扫描索引后过滤」，两者的查询成本并不一样。

只有在 a 相同的情况才，b 才是有序的，比如 a 等于 2 的时候，b 的值为（7，8），这时就是有序的，这个有序状态是局部的，因此，执行where a = 2 and b = 7是 a 和 b 字段能用到联合索引的，也就是联合索引生效了。

# 创建联合索引时需要注意什么？

先看常用 SQL 的过滤、排序和返回字段，再决定字段顺序 ，不能只背「区分度高的字段放前面」。

比如订单表经常执行下面这个查询：

SELECT id , created_at FROM orders WHERE user_id = 100 AND status = 0 ORDER BY created_at DESC LIMIT 20 ;

可以考虑 (user_id, status, created_at) ：前两列是等值条件，先缩小候选范围，再按 created_at 的索引顺序获取最近的订单。虽然 status 只有几种值，放在这里仍然有作用。

创建时主要考虑这几个方面：

最左前缀能否复用 ：如果常按 user_id 单独查询，把它放前面就能同时服务这类 SQL。 等值、范围和排序怎么配合 ：常见做法是先安排等值条件，再结合范围条件和 ORDER BY 决定后续列，避免排序列前面还有未固定的字段。 是否能覆盖查询 ：二级索引自带主键值，上面的返回字段就可能直接从索引里取得。 索引宽度和维护成本 ：字段越多、越长，索引越大，写入成本也越高，不是把所有列塞进去就好。

优化器是否选择索引取决于成本， 没有「命中超过 30% 就一定不走索引」这种固定规则 。最后通过 EXPLAIN 和实际执行情况验证。

# 联合索引ABC，现在有个执行语句是A = XXX and C < XXX，索引怎么走

如果优化器选择 (A, B, C) 这个索引，A 的等值条件可以用于定位，但因为中间缺少 B，通常不能继续用 C 的条件缩小索引扫描范围。

不过 C 已经保存在二级索引里。如果查询需要回表，并且满足索引下推的条件，就可以先判断 C 是否符合条件，只有符合的记录才回表。如果查询被索引覆盖，就直接在索引中完成过滤和取值。

所以，C 不能用于连续的前缀定位，不代表 C 完全没有参与查询。

# 联合索引(a,b,c) ，查询条件 where b > xxx and a = x 会生效吗

a 的等值条件和 b 的范围条件符合最左匹配原则，可以利用联合索引定位扫描范围。WHERE 中先写 b 再写 a 不影响这个判断，优化器会分析条件，不是按 SQL 文本从左往右匹配。不过最终是否选择这个索引，还要看成本估算。

# 联合索引 (a, b，c)，where条件是 a=2 and c = 1，能用到联合索引吗？

能，a = 2 符合最左前缀，可以用来定位 a 对应的索引范围。但缺少 b，c = 1 通常不能继续缩小扫描范围。

如果查询需要回表，c 的条件可能通过索引下推，在读取完整记录前先过滤一部分数据；如果查询被索引覆盖，也可以直接利用索引里的 c 进行判断。具体采用哪种方式要看执行计划。

# 索引失效有哪些？

面试里说的「索引失效」，通常是指查询条件没办法利用索引快速定位。常见有下面几种情况：

左模糊匹配 ： LIKE '%小林' 、 LIKE '%小林%' 不能按普通 B+ 树索引的前缀定位， LIKE '小林%' 则可能使用范围扫描。 对索引列使用函数或计算 ：比如 YEAR(created_at) = 2024 、 price + 1 = 10 ，普通索引通常不能直接用于定位。可以改成时间范围，或者改写为 price = 9 ；MySQL 8.0 的函数索引也可以服务匹配的表达式。 隐式类型转换 ：比如 phone 是 VARCHAR，却写 phone = 13800138000 ，可能需要把索引列转换成数字再比较。应该保持参数类型和列类型一致。 缺少联合索引最左列 ：例如只有 (a, b, c)，却只按 b 查询，通常不能按最左前缀定位。 OR 的某个分支无法利用索引 ：比如 a 有索引、b 没有索引， a = 1 OR b = 2 往往需要全表扫描。多个分支都有索引时，也可能使用 index_merge，但是否采用仍取决于成本。

另外， 能用索引，但优化器认为全表扫描更便宜，和条件本身无法使用索引是两回事 。比如查询命中大部分记录，还要大量回表，优化器可能主动选择全表扫描。

左模糊匹配、缺少最左列也不代表索引绝对不会被读取，仍可能存在覆盖索引全扫描或索引跳跃扫描。判断时要结合 EXPLAIN 的 key、type 和 Extra。

# 什么是索引下推？和覆盖索引有什么区别？

索引下推，也叫 ICP，是把能够利用索引列判断的条件交给存储引擎， 先过滤，再决定是否回表 ，减少完整行的读取次数。

举个栗子，用户表有联合索引 (name, age) ，现在查询：

SELECT * FROM users WHERE name LIKE '张%' AND age = 20 ;

没有索引下推时，先根据 name 找到候选记录，再逐条回表读取整行，之后判断 age 是否等于 20。 有索引下推时，在二级索引里就判断 age 是否等于 20，不满足的记录直接跳过，只有满足的记录才回表。



执行计划中，索引下推通常表现为 Using index condition 。对于 InnoDB，它主要用于二级索引，因为聚簇索引本身已经拿到了完整行。

覆盖索引则是查询需要的列都在索引里，可以直接从索引获取，通常表现为 Using index 。 一个是减少回表次数，一个是直接从索引取得所需字段 ，不能把这两个 Extra 当成一个意思。



# 什么情况下会回表查询

从物理存储的角度来看，索引分为聚簇索引（主键索引）、二级索引（辅助索引）。

它们的主要区别如下：

主键索引的 B+Tree 的叶子节点存放的是实际数据，所有完整的用户记录都存放在主键索引的 B+Tree 的叶子节点里； 二级索引的 B+Tree 的叶子节点保存索引列的值和主键值，不保存完整的行数据。

所以，在查询时使用了二级索引，如果查询的数据能在二级索引里查询的到，那么就不需要回表，这个过程就是覆盖索引。

如果查询的数据不在二级索引里，就会先检索二级索引，找到对应的叶子节点，获取到主键值后，然后再检索主键索引，就能查询到数据了，这个过程就是回表 。

# 什么是覆盖索引？

覆盖索引是指一个索引包含了查询所需的所有列，因此不需要访问表中的数据行就能完成查询。

换句话说，查询所需的所有数据都能从索引中直接获取，而不需要进行回表查询。覆盖索引能够显著提高查询性能，因为减少了访问数据页的次数，从而减少了I/O操作。

假设有一张表 employees，表结构如下：

CREATE TABLE employees ( id INT PRIMARY KEY , name VARCHAR ( 100 ) , age INT , department VARCHAR ( 100 ) , salary DECIMAL ( 10 , 2 ) ) ; CREATE INDEX idx_name_age_department ON employees ( name , age , department ) ;

如果我们有以下查询：

SELECT name , age , department FROM employees WHERE name = 'John' ;

在这种情况下，idx_name_age_department 是一个覆盖索引，因为它包含了查询所需的所有列：name、age 和 department。查询所需字段可以直接从索引取得。

对于 InnoDB，二级索引还保存了主键 id，所以查询增加 id 列通常仍然可以覆盖。如果查询增加 salary，就需要回表。覆盖索引说的是索引能提供所需列；锁定读、MVCC 可见性检查等情况仍可能需要访问聚簇索引记录。

# 如果一个列即使单列索引，又是联合索引，单独查它的话先走哪个？

没有固定的优先顺序，优化器会估算成本，再选择执行计划。

比如同时有单列索引 (a) 和联合索引 (a, b)：

SELECT a FROM t WHERE a = 1 ; SELECT a , b FROM t WHERE a = 1 ; SELECT * FROM t WHERE a = 1 ;

第一条两个索引都能覆盖，单列索引更小，可能成本更低。 第二条联合索引可以提供 a、b，通常更有优势。 第三条两个索引都可能需要回表，还要看统计信息、命中行数等因素。

联合索引已经能服务按 a 查询的场景时，单列索引 (a) 可能冗余，但是否删除要结合其他查询和写入成本评估，不能只看列名重复就直接删除。

# 索引已经建好了，那我再插入一条数据，索引会有哪些变化？

插入新数据可能导致B+树结构的调整和索引信息的更新，以保持B+树的平衡性和正确性，这些变化通常由数据库系统自动处理，确保数据的一致性和索引的有效性。

如果插入的数据导致叶子节点已满，可能会触发叶子节点的分裂操作，以保持B+树的平衡性。

# 索引字段是不是建的越多越好？

不是，建的的越多会占用越多的空间，而且在写入频繁的场景下，对于B+树的维护所付出的性能消耗也会越大

# 如果有一个字段是status值为0或者1，适合建索引吗

要看数据分布和查询方式，不能只因为只有 0、1 两种值就否定索引。

比如订单表里，99.9% 的订单已经处理，只有 0.1% 待处理。后台经常查询 WHERE status = 0 获取少量待处理订单，索引就可能有效。如果经常查询某个用户的订单，可以考虑 (user_id, status) ；如果按状态取最近的订单，可以结合查询建立 (status, created_at) 。

反过来，如果 0、1 各占一半，查询还要 SELECT *，大量回表就可能比全表扫描更贵，这时单列索引通常收益不大。

# 索引的优缺点？

索引最大的好处是提高查询速度，但是索引也是有缺点的，比如：

需要占用物理空间，数量越大，占用空间越大； 创建索引和维护索引要耗费时间，这种时间随着数据量的增加而增大； 会降低表的增删改的效率，因为每次增删改索引，B+ 树为了维护索引有序性，都需要进行动态维护。

所以，索引不是万能钥匙，它也是根据场景来使用的。

# 怎么决定建立哪些索引?

什么时候适用索引？

字段有唯一性限制的，比如商品编码； 经常用于 WHERE 查询条件的字段，这样能够提高整个表的查询速度，如果查询条件不是一个字段，可以建立联合索引。 经常用于 GROUP BY 和 ORDER BY 的字段，合适的索引顺序有机会减少排序或分组开销，因为我们都已经知道了建立索引之后在 B+Tree 中的记录都是排序好的。

什么时候不需要创建索引？

WHERE 条件， GROUP BY ， ORDER BY 里用不到的字段，索引的价值是快速定位，如果起不到定位的字段通常是不需要创建索引的，因为索引是会占用物理空间的。 字段区分度低、查询命中比例高，并且需要大量回表时，单列索引通常收益不大。但查询少数值、覆盖查询或组成合适的联合索引时，仍可能有效。 表数据太少的时候，不需要创建索引； 经常更新、但很少参与过滤或排序的字段，通常不值得建立索引。频繁更新会增加索引维护和日志开销，不过如果它承担关键查询，也需要权衡读写成本，不能一概不建。

# 索引优化详细讲讲

常见的索引优化，可以从下面几个方向回答：

根据实际 SQL 设计联合索引 ：把过滤条件、排序和返回字段一起考虑，利用最左前缀，不要只按字段区分度排序。 覆盖索引优化 ：查询只取需要的列，尽量让高频查询从二级索引直接得到所需字段，减少回表。 前缀索引优化 ：对很长的字符串只建立前缀索引，节省空间，但要在前缀长度和区分度之间做取舍。 主键尽量短小、稳定、递增 ：减少聚簇索引随机插入的成本，也减少二级索引存储主键的开销。 让条件便于使用索引 ：避免对普通索引列做不必要的函数、计算和隐式类型转换，时间条件优先写成范围。 清理重复和低收益索引 ：减少磁盘占用和增删改时的维护成本，删除前需要确认没有影响其他查询。

最后用 EXPLAIN 和实际执行情况验证，关注扫描行数、回表次数、排序和耗时。不能只看 key 有值，就认为优化成功了。

# 了解过前缀索引吗？

前缀索引就是只取字符串前面一部分建立索引，比如邮箱比较长，可以先对前 20 个字符建索引：

CREATE INDEX idx_email_prefix ON users ( email ( 20 ) ) ;

这样索引更小，一个页里可以放下更多索引项。不过，如果很多邮箱前 20 个字符相同，就需要扫描更多候选记录，再检查完整值，所以前缀长度不能只图短。



可以比较完整值和不同长度前缀的区分度，选择一个尽量接近完整值区分度的长度：

SELECT COUNT ( DISTINCT email ) / COUNT ( * ) AS full_selectivity , COUNT ( DISTINCT LEFT ( email , 20 ) ) / COUNT ( * ) AS prefix_selectivity FROM users ;

还要注意： 前缀索引不能直接提供完整字符串，也不能保证按完整字符串排序 。如果查询要返回 email 完整值，仍需要读取完整记录；唯一前缀索引限制的也是前缀唯一，可能把前缀相同、完整值不同的两条记录当成冲突。
