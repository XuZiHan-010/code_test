## 建议修订的题目

### 1. S7-15：固定 SQL 却把另一条 SQL 的条件算作其不走索引原因

- 严重度：高；类型：出题转述错误、正确选项与题干矛盾。
- 实际题干：执行 `EXPLAIN SELECT * FROM user WHERE name = '张三'` 后 `key` 为 NULL，询问可能原因。
- 问题：B 选项“查询条件对 name 字段做了函数操作，例如 WHERE SUBSTR(name,1,1) = '张'”被标为正确。但是题干已给出的 SQL 使用 `name = '张三'`，并没有任何 `SUBSTR` 操作。它不能成为这条固定 SQL 的原因。D“索引选择性太差”与原文一致，无此矛盾。
- 原文短证据：“或者查询条件导致索引失效（比如用了函数操作 name 字段）”。原文在展示等值查询后转为泛举可能原因；题型转换后把泛举案例套进了固定查询。
- 原文位置：[怎么查看是否有走索引？](https://xiaolincoding.com/interview/mysql.html#%E6%80%8E%E4%B9%88%E6%9F%A5%E7%9C%8B%E6%98%AF%E5%90%A6%E6%9C%89%E8%B5%B0%E7%B4%A2%E5%BC%95)。
- 建议改法：将题干改为“name 字段建了普通索引，但某条按 name 查询的 SQL 在 EXPLAIN 中 key 为 NULL，原文列举的可能原因有哪些？”保留 B、D 正确；或保留固定等值 SQL，删除函数操作这个正确选项，并调整为单选。前者最贴近题卷原有泛问法。

### 2. S7-7：第二空不足以唯一确定 eq_ref

- 严重度：中；类型：填空提示歧义，沿用原文简化后产生。
- 问题：第二空的提示仅为“使用主键或唯一索引、通常用在多表联查中的 type”。使用唯一索引的非唯一前缀也可以是 `ref`，第一空自己就已提到这个情况；仅知道“使用主键或唯一索引”不能确定 `eq_ref`。参考答案同样缺少完整索引列及非空唯一性限定。
- 原文短证据：“eq_ref 类型是使用主键或唯一索引时产生的访问方式，通常使用在多表联查中”。忠实转述，但原文定义是简化表述，不能直接作为排他的填空线索。
- 官方核对：[EXPLAIN Output Format](https://dev.mysql.com/doc/refman/8.0/en/explain-output.html) 在 `eq_ref` 下要求连接使用索引所有部分，且索引为 `PRIMARY KEY` 或 `UNIQUE NOT NULL`；`ref` 下明确包含仅使用键的最左前缀的场景。
- 建议改法：第二空改为“关联查询中，通过完整主键或完整 UNIQUE NOT NULL 索引等值查找，针对前面每一行组合最多读取一行的 type 是____”。参考答案注明“原文简写为使用主键或唯一索引；这里按官方定义补齐适用条件”，并加官方核对链接。S7-8 的 E 选项已突出“针对前面每一行组合做一次唯一键查找”，没有相同程度的填空歧义，不计为另一项硬错。

## 原文限定缺失：与题库转述错误分开处理

### 3. S2-20：把获取缺失字段回表说成唯一回表原因

- 严重度：低；类型：原文常规简化缺少 MVCC 例外限定，非答案标错。
- 实际正确选项 C：“只有需要读取索引中没有的字段时才回表，覆盖索引查询不需要为此回表”。
- 原文短证据：“需要读取索引中没有的字段时才会回表”；随后明确说覆盖索引不需要“为了获取这些字段”回表。答案保留了后半句的目的限定，但选项前半句“只有”仍容易被理解为排除所有其他聚簇索引访问原因。
- 官方核对：[InnoDB Multi-Versioning](https://dev.mysql.com/doc/refman/8.0/en/innodb-multi-versioning.html) 的“Multi-Versioning and Secondary Indexes”说明：辅助索引记录被标记删除，或辅助索引页由较新的事务更新时，需要访问聚簇索引核查可见版本，此时不能仅靠覆盖索引返回值。
- 建议改法：把 C 改为“为取得索引中缺少的字段时需要回表；覆盖索引可避免为获取字段而回表”，删除“只有”。若扩展答案解释 MVCC，须按项目规则说明原文简化及官方核对来源。
- 本项作为限定建议，不应据此把用户按原文作答判错；本轮不把常规覆盖索引教学简化升级为确定硬错。

### 4. S8-39：跨 database 不等于跨实例事务

- 严重度：中；类型：沿用原文，但缺少跨实例/独立事务资源前提。
- 实际题干：“分库分表后，一次操作涉及多个数据库时，下列说法符合原文的是哪一项？”正确 C 为“单库事务不能直接保证全部成功，需要结合业务采用分布式事务或补偿等方案”。
- 原文短证据：“一次操作涉及多个数据库时，单库事务不能直接保证全部成功”。同篇此前也明确指出分库可只是“同一实例里多建几个库”，因此整篇上下文没有把所有分库限定在多个实例。
- 问题：如果多个 database/schema 仍在同一个 MySQL 实例中，同一会话的一次 InnoDB 本地事务可以修改这些库里的表并一起提交或回滚；不因跨 schema 就必须改为分布式事务。题干的“符合原文”使 C 是预设答案，但读者若把它当通用事实，会获得错误边界。
- 官方核对：[Transactional and Locking Statements](https://dev.mysql.com/doc/refman/8.0/en/sql-transactional-statements.html) 将本地事务界定在客户端会话内；[Identifier Qualifiers](https://dev.mysql.com/doc/refman/8.0/en/identifier-qualifiers.html) 说明可以通过 `db_name.table_name` 操作非默认数据库的表；[XA Transactions](https://dev.mysql.com/doc/refman/8.0/en/xa.html) 将多个独立事务资源、多个数据库服务器作为分布式事务情形。依据这些官方规则可推得：本地事务边界不是 schema 名称。这是依据官方文档的推论，本轮没有另起 MySQL 实例执行演示。
- 建议改法：题干与 C 改为“一次操作跨多个 MySQL 实例/独立事务资源时，单个实例的本地事务不能直接保证跨资源原子提交，需要采用分布式事务或业务补偿等方案”。答案按项目规则注明原文用“多个数据库”作简化表述，并添加官方核对链接。

## 低优先级措辞建议

### 5. S8-15：问“避免读旧数据”，答案却包含接受最终一致性

- 严重度：低；类型：题干范围措辞，不是填空答案错误。
- 问题：题干“业务怎么避免读到旧数据，原文给出的四类做法……”的第四类答案为“接受最终一致性”。这类做法允许读到稍旧数据，本身不保证避免旧值；固定时间窗口同样只降低概率。
- 原文短证据：“接受最终一致性”；该段也明确说此类场景允许短暂延迟，故答案本身忠实。
- 建议改法：把题干改为“面对主从复制延迟，原文列出的四类业务读取策略是……”，保留四空无序和现有答案。
