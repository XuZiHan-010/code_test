# 架构

# MySQL主从复制了解吗

MySQL 的主从复制依赖于 binlog ，也就是把需要复制的数据库变更记录为二进制日志事件。复制的过程就是将 binlog 中的数据从主库传输到从库上。

这个过程一般是 异步 的，也就是主库上执行事务操作的线程不会等待复制 binlog 的线程同步完成。



MySQL 集群的主从复制过程梳理成 3 个阶段：

写入 Binlog ：主库执行数据修改，在提交阶段记录并提交相应 binlog 事务。 同步 Binlog ：把 binlog 复制到所有从库上，每个从库把 binlog 写到暂存日志中。 回放 Binlog ：回放 binlog，并更新存储引擎中的数据。

具体详细过程如下：

主库在事务执行过程中已经修改内存中的数据，提交时协调 redo 和 binlog，完成本地提交后即可返回客户端。普通异步复制不需要等待从库接收或执行完成。 从库的接收线程连接主库的 binlog dump 线程，获取日志事件并写入本地 relay log。接收到日志不等于已经应用到从库数据，也不能把这个过程当成主库提交必须等待的确认。 从库的应用线程读取 relay log，再更新自己的存储引擎数据。开启并行复制后，可以由协调线程分配给多个 worker 应用事务，不过并行程度受到事务依赖等因素限制。

主从复制可以用来做读写分离，写入走主库，允许读取稍旧数据的查询走从库。不过，普通 InnoDB 快照读本身就不一定被主库行锁阻塞，读写分离主要是分担负载。 主库提交成功不代表从库马上能读到 ，业务必须考虑复制延迟。

# 主从延迟都有什么处理方法？

先分清两个问题：一是为什么复制追不上，二是业务怎么避免读到旧数据。

先定位延迟原因

主库大事务或批量修改 ：从库接收到已提交事务后，需要较长时间应用。 从库资源不足 ：CPU、磁盘 I/O 或 Buffer Pool 不够，回放比主库写入慢。 从库查询或锁等待 ：重查询争抢资源，或者应用线程被长事务、DDL 阻塞。 网络或复制线程异常 ：日志传输变慢，或者复制报错停止，不能只当成正常延迟等待。 并行复制能力不足 ：事务可以并行的程度低，增加 worker 也不一定能线性提速。

可以通过 SHOW REPLICA STATUS 和复制相关的 Performance Schema 信息，区分日志是否还没接收到，还是已经收到、但应用不完。旧版本对应 SHOW SLAVE STATUS 。Seconds_Behind_Source 等时间指标适合辅助监控，但显示为 0 也不能单独证明从库已经应用了某个指定业务事务。

处理时，可以拆分允许拆分的大事务、优化从库 SQL 和硬件、排查锁等待、合理配置并行复制。 把大事务继续放到主库执行，并不能消除它在从库上的回放成本 。

业务怎么避免读旧数据

关键查询走主库 ：支付状态、下单后的订单确认等需要读到最新提交的查询，可以直接路由到主库。 写后短时间读主库 ：对刚完成写入的用户或请求，临时把相关读取切到主库，降低读旧数据的概率，不过固定时间窗口不是严格保证。 等待指定事务应用 ：使用 GTID 时，可以获取本次写入事务的 GTID，在从库执行 WAIT_FOR_EXECUTED_GTID_SET() 等待，成功后再建立新的读取快照；超时就回退主库或返回可重试结果。 接受最终一致性 ：报表、非关键列表等允许短暂延迟的场景，可以继续读从库，配合延迟监控和异常从库摘除。

不能靠「写完 sleep 一秒」就断言数据同步完成，要按业务的一致性要求选择方案。



# 异步复制和半同步复制有什么区别？

异步复制 ：主库本地提交成功就可以响应客户端，不需要等从库。延迟较低，但主库发生故障时，已经返回成功的事务可能还没复制到从库，切换后可能丢失。 半同步复制 ：主库在返回提交成功前，通常需要等至少一个半同步从库确认已接收事务日志，并写入、刷盘到 relay log。

半同步等待的是日志接收和持久化确认， 不是等待从库把事务应用到数据表 ，所以它仍不能保证提交后立即在从库读到新值。



另外，半同步等待超过配置的超时时间后，可能退化成异步复制。故障切换时还要选择包含目标事务的从库，并确认日志应用进度，不能仅凭「开启了半同步」就认为任何切换都绝对不会丢数据。

# GTID 是什么？有什么作用？

GTID 是全局事务标识，可以把它理解成每个复制事务的唯一编号，常见形式是「源服务器 UUID:事务序号」。事务复制到其他节点后，仍然携带同一个 GTID。

传统复制需要指定从某个 binlog 文件的哪个位置开始；GTID 复制可以根据从库已经执行过的事务集合，判断还缺哪些事务，让切换主库和恢复复制位置更方便，也能帮助避免重复应用同一个复制事务。

GTID 还可以用于判断某笔事务是否已经在从库执行。例如在从库等待本次写入对应的 GTID，等待成功后再读取，就可以处理一部分写后读一致性需求。

不过，GTID 只是标识和跟踪事务， 不会自动消除主从延迟，也不是应用业务请求的幂等键 。

# 分表和分库是什么？有什么区别？



分库 是把业务表或数据分散到多个数据库中，可以按业务拆，也可以按数据分片拆。如果落到不同实例或服务器上，就能分担存储、连接和读写压力；如果只是同一实例里多建几个库，仍然共享同一套物理资源。 分表 是把一张表拆成多张表。按行拆叫水平分表，每张子表保存部分记录；按列拆叫垂直分表，各表通过主键关联。它们主要解决单表访问和存储方面的问题，但如果仍在同一个实例，并不会自动突破单机 CPU、I/O 等资源上限。

分库与分表可以从：垂直（纵向）和 水平（横向）两种纬度进行拆分。下边我们以经典的订单业务举例，看看如何拆分。



垂直分库 ：一般来说按照业务和功能的维度进行拆分，将不同业务数据分别放到不同的数据库中，核心理念 专库专用。按业务类型对数据分离，剥离为多个数据库，像订单、支付、会员、积分相关等表放在对应的订单库、支付库、会员库、积分库。垂直分库把一个库的压力分摊到多个库，提升了一些数据库性能，但并没有解决由于单表数据量过大导致的性能问题，所以就需要配合后边的分表来解决。 垂直分表 ：针对业务上字段比较多的大表进行的，一般是把业务宽表中比较独立的字段，或者不常用的字段拆分到单独的数据表中，是一种大表拆小表的模式。InnoDB 主要以页为单位读取和缓存数据，这样拆分以后核心表大多是访问频率较高的字段，而且字段长度也都较短，因而可以加载更多数据到内存中，减少磁盘IO，增加索引查询的命中率，进一步提升数据库性能。 水平分库 ：是把同一个表按一定规则拆分到不同的数据库中，每个库可以位于不同的服务器上，以此实现水平扩展，是一种常见的提升数据库性能的方式。这种方案往往能解决单库存储量及性能瓶颈问题，但由于同一个表被分配在不同的数据库中，数据的访问需要额外的路由工作，因此系统的复杂度也被提升了。 水平分表 ：是在 同一个数据库内 ，把一张大数据量的表按一定规则，切分成多个结构完全相同表，而每个表只存原表的一部分数据。水平分表尽管拆分了表，但子表都还是在同一个数据库实例中，只是解决了单一表数据量过大的问题，并没有将拆分后的表分散到不同的机器上，还在竞争同一个物理机的CPU、内存、网络IO等。要想进一步提升性能，就需要将拆分后的表分散到不同的数据库中，达到分布式的效果。

# 分库分表后会遇到哪些问题？怎么选分片键？

分库分表把单机压力分散了，但也把原来一个数据库里能直接完成的操作变复杂了。

跨分片查询 ：没有分片键的查询可能需要访问多个分片，再合并、排序或聚合结果。 跨分片事务 ：一次操作涉及多个数据库时，单库事务不能直接保证全部成功，需要结合业务采用分布式事务或补偿等方案。 全局唯一性 ：各分片独立自增可能重复，跨分片唯一约束也不能靠某一个库的 UNIQUE 保证，需要分布式 ID 或额外的唯一性设计。 分页和统计 ：全局排序、COUNT 和深分页可能需要从多个分片取数据再汇总，成本和实现难度都会增加。 扩容和迁移 ：分片规则变化时，需要迁移数据、切换路由，并处理迁移期间的新写入与校验。

分片键通常要看三个方面： 高频查询能不能带上它、数据能不能均匀分布、相关业务数据能不能尽量落到同一分片 。

比如订单主要按用户查询，可以考虑按 user_id 分片，让同一用户的订单集中在一起。不过，大客户可能产生热点，按订单号查询又可能需要额外路由；按时间拆分便于归档，却可能让最新分片承受大部分写入。



所以，分片键没有通用答案，要从主要访问路径出发，再权衡热点、事务边界和扩容方式。
