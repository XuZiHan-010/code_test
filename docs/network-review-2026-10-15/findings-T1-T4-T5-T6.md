## 需要优先修正的问题

### 1. T5-20：部分有序的工具角色被定义为全部无序

**实际证据**：`content/typed/network.json:12635`，填空 3 空、`blankOrder: unordered`。stem 为“浏览器信息不够时，原文提到可以用____查看分段耗时，用____或____抓包，并把客户端时间和服务端日志对起来。”参考答案是“curl、tcpdump、Wireshark（后两者顺序可互换）”。

**原文依据**：§网页非常慢转圈圈的时候，要定位问题需要从哪些角度？，第 1425 行，把 curl 对应到分段耗时，把 tcpdump/Wireshark 对应到抓包；原文使用“或”，不是要求按先 curl 再抓包的固定顺序。

**判分影响**：填入 `[tcpdump, curl, Wireshark]` 覆盖了全部三个词，符合目前传给评分器的“各空顺序不限”，却把 curl 放进抓包位置；参考答案自身只允许后两空交换，与题型配置冲突。

**最小建议**：保持题号和无序配置，改成“该小节提到的三种辅助排查工具名称是____、____、____”，在答案解释各自用途。不能仅改为 ordered，否则 tcpdump/Wireshark 合理交换仍会违反位置契约。若要保留角色考点，需另用能明确容纳后两空交换的结构。同步把答案“先……再……”改为原文的可选工具关系。

**归类**：题型改写产生的实质性判分风险；不是原文技术错误。

### 2. T5-21：把无保活的闲置连接结论当成无条件结论

**实际证据**：`content/typed/network.json:12642`。stem 只写“客户端突然宕机或断网，而服务端一直不向客户端发送数据”；D 标为 correct：“服务端无法感知，连接一直处于 ESTABLISHED 状态，占用系统资源”。答案还使用“永远感知不到”。

**原文依据**：§server a和server b，如何判断两个服务器正常连接？出错怎么办？，第 1430 行给出同样的闲置连接例子；第 1431～1460 行马上引入 TCP 保活和 SO_KEEPALIVE，并解释保活失败可报告连接死亡；第 1461～1467 行又讨论应用心跳、请求超时及空闲连接回收。因此同一小节本身提供了 D 并非普遍成立的条件。[RFC 9293 §3.8.4](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.8.4) 明确保活按连接启停、默认关闭。

**判分影响**：题干没有说未开启 SO_KEEPALIVE、没有应用心跳/超时/主动回收，读者合理考虑这些机制时，D 的“一直”不成立。题目不是单选有第二个明确正确选项，而是缺少使指定答案成立的条件。

**最小建议**：加上“假设未开启 TCP 保活，应用也没有心跳、超时或主动回收，且双方不再有连接相关报文交互”；D 和答案改为“仅靠闲置 TCP 连接不能感知对端故障，连接会继续保留”，避免脱离假设的“永远”。

**归类**：原文开头的简化表述被独立抽题后暴露条件缺失；原文后文已经提供限制，不需另补原文之外的新知识。

### 3. T5-56：返回值小于长度包括失败的 -1，不能一律继续发送

**实际证据**：`content/typed/network.json:13484`。stem：“send 的返回值小于要发送的长度时，应用应该怎么做？”C correct：“继续发送剩余部分”。题干没有“调用成功”或“返回正数”的限制。

**原文依据**：§TCP 连接里，send 成功是不是说明对方收到数据了？，第 1513 行也笼统说返回值可能小于长度、继续发剩余部分。它位于讨论 send 成功的小节中，独立题干未保留这一语境。[官方 send 规范](https://pubs.opengroup.org/onlinepubs/000095399/functions/send.html) 区分成功时的字节数与失败时的 -1；失败还需依据 errno 处理。

**判分影响**：`send` 返回 -1 同样满足题干“小于长度”，而连接重置/写端关闭等错误时不能直接套用 C。现有选项没有完整覆盖失败分支，不能靠其他选项挽救唯一答案。

**最小建议**：stem 限定“send 成功返回正数 n，且 n 小于要发送的长度时……”，C 说明“从已接受的 n 字节之后继续发送剩余部分”。答案注明原文省略了成功短写条件，并按项目例外规则附官方核对链接。

**归类**：原文接口描述条件不严谨，独立抽题进一步丢失 send 成功的上下文；correct C 在补足条件后成立。

### 4. T5-57：send 返回值与 errno 混淆，原文自身需要核对修订

**实际证据**：`content/typed/network.json:13511`。stem：“非阻塞发送时，如果缓冲区暂时没有空间，send 可能返回错误码____或____。”答案要求 EAGAIN、EWOULDBLOCK，并复述“返回 EAGAIN 或 EWOULDBLOCK”。

**原文依据**：上述 send 小节第 1513 行也如此写。[官方 send 规范](https://pubs.opengroup.org/onlinepubs/000095399/functions/send.html) 的 RETURN VALUE/ERRORS 区分：失败返回 -1，errno 表示错误；非阻塞操作将阻塞时对应 EAGAIN 或 EWOULDBLOCK。

**判分影响**：问题把一个可以直接检查的 API 行为教错了；回答“-1，errno 为 EAGAIN/EWOULDBLOCK”的用户可能被当前两空结构判作未覆盖要求。两种错误符号本身没有问题，错误在所属字段。

**最小建议**：保留两空、无序，改为“send 失败返回 -1，此时 errno 可能是____或____”；答案同样改写，括注原文把 errno 简称为返回错误码，按规则追加“核对来源：”官方链接。

**归类**：忠实继承原文技术错误，不是出题者凭空改错。

### 5. T5-58：没有限定是确认所讨论字节的 ACK

**实际证据**：`content/typed/network.json:13518`。stem：“发送方后来收到了 TCP ACK，这能说明什么？”A correct：“只能说明对端 TCP 层确认收到了相关字节”。

**原文依据**：send 小节第 1514 行的 ACK 结论跟在发送数据的上下文中，独立题没有明确“相关字节”是什么、ACK 是否覆盖它们。[RFC 9293 §3.1](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.1) 说明确认号代表接收方期待的下一个序号，连接建立后该字段一直随报文发送。由此可以推导：只收到一个带 ACK 的报文不等于刚发送的数据被确认。

**判分影响**：重复 ACK 或未覆盖所发送数据的 ACK 都不能证明那些字节已经收到。这个限制只影响“哪些字节被确认”，不改变原文“TCP 确认不代表应用读取/业务成功”的核心结论。

**最小建议**：stem 改为“发送方收到了确认号覆盖所发送这些字节的 TCP ACK，这能说明什么？”A 保留 TCP 层确认、不能推出应用成功的含义；参考答案补相同条件。

**归类**：抽取独立题后的指代/确认范围不清；优先级低于 T5-56、T5-57，不主张把所有 ACK 相关题重做。

### 7. T4-7：ARP 广播对象应明确为本地链路上的待解析 IP

**证据**：`content/typed/network.json:11911` 的独立 stem 是“主机的 ARP 缓存里没有目标 IP 的记录时，ARP 是怎样查到对应 MAC 地址的？”答案是广播询问，目标主机应答。原文§ARP 是什么？访问外网时查询谁的 MAC 地址？第 1359～1365 行先限定 IPv4 本地链路，并区分访问外网时查询的是网关。

**判分影响**：“目标 IP”可能被理解为最终外网服务器 IP；这时没有对应缓存并不触发跨互联网查服务器 MAC。题内没有第二个错误选项，主要是问答上下文的丢失。

**最小建议**：加“在 IPv4 本地以太网链路上，待解析的下一跳 IP 的 ARP 缓存记录不存在时……”，或明确同一子网目标主机。建议程度低，不据此认定整个 T4 ARP 题组错误。
