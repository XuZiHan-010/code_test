## 一、题目改写或抽取问题

### T3-75：单选缺少“对方 FIN 尚未到达”，A 与 C 对应不同合法场景（高优先级）

- 实际题干：`主动关闭方收到对自己 FIN 的确认后，会进入什么状态？此时它在等什么？`
- A（incorrect）：`进入 TIME_WAIT，等待 2MSL 后释放连接`。
- C（correct）：`进入 FIN_WAIT_2，等待对方的 FIN`。
- 原文依据：[第三次挥手一直没发，会发生什么？](https://xiaolincoding.com/interview/network.html#第三次挥手一直没发-会发生什么)，`source.txt:1017` 起。该小节的标题明确限定被动方的 FIN 未发；题目抽取掉了这个背景。同章[第二次和第三次挥手能合并嘛](https://xiaolincoding.com/interview/network.html#第二次和第三次挥手能合并嘛)及 T3-73 又明确允许 FIN 与确认合并。
- 判分影响：如果主动关闭方在 FIN_WAIT_1 收到同时确认本端 FIN 的对方 FIN+ACK，处理完成后进入 TIME_WAIT，A 成立；仅收到对本端 FIN 的确认而还没收到对端 FIN 时，C 成立。单题展示无法依赖小节标题排除前者。这个问题来自抽取条件丢失，不能靠把 A 一概标错解决。[RFC 9293 §3.10.7.4](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.10.7.4) 的 ACK 和 FIN 处理规则确认了这两个分支。
- 最小修正：题干改为 `主动关闭方收到只确认本端 FIN 的 ACK，且尚未收到对方 FIN 时，会进入什么状态？此时它在等什么？`，保留 C 标记与答案。

### T3-165：零窗口前提和“暂不考虑探测”的教学前提被丢失（高优先级）

- 实际题干：`接收方腾出空间后发送的窗口更新报文如果丢了，会出现什么问题？`
- B（correct）：`发送方一直等窗口打开，接收方一直等新数据，互相等待`。
- 答案把这写为可能发生的互等。
- 原文依据：[TCP 接收窗口变成 0，会发生什么？](https://xiaolincoding.com/interview/network.html#tcp-接收窗口变成-0-会发生什么)，`source.txt:1226—1234`。原文先介绍接收方通告零窗口、发送方暂停，再提出丢失重开通告可能造成等待的问题，随后立即介绍持续计时器与零窗口探测如何避免卡住。
- 判分影响：题干既没有说明先前窗口为零，也没有说明这是引出探测必要性的假设问题。普通非零窗口更新丢失不必使发送方完全停发；实际 TCP 的零窗口探测也会重新取得窗口信息。选项 B 把“可能的等待风险”写成实际 TCP 必然一直互等，四个选项中没有探测恢复这一正确行为。[RFC 9293 §3.8.6.1](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.8.6.1) 明确要求支持零窗口探测。
- 最小修正：题干改为 `接收方此前已通告零窗口，腾出空间后通告窗口重开的报文丢失；若不考虑持续计时器和零窗口探测，会有什么风险？`；B 改为 `双方可能互相等待：发送方等窗口打开，接收方等新数据`。该改法保留原文用于解释探测必要性的考点。

### T3-21：历史 SYN 示例漏掉同一四元组（中优先级）

- 实际题干完整给出了旧 SYN `seq=90`、客户端宕机后新 SYN `seq=100`、旧 SYN 先到，但没有给出两次连接的地址和端口是否一致。
- 答案要求客户端把 SYN+ACK 的确认号 91 与新连接期待的 101 比较，然后发送 RST。
- 原文依据：[tcp为什么需要三次握手建立连接？](https://xiaolincoding.com/interview/network.html#tcp为什么需要三次握手建立连接)，`source.txt:843` 限定两次 SYN 使用相同四元组。
- 判分影响：重启后若客户端换了源端口，旧 SYN+ACK 不属于新连接，不能用新连接期待的确认号解释其处理。回答“需要先说明两次连接四元组相同”或按不同四元组解释，也符合题干允许的场景，却不符合参考答案的特定推演。
- 最小修正：在题干加入 `两次 SYN 使用相同四元组，客户端当前已在该四元组上以 seq=100 发起新连接`。无需扩展原文考点。

### T3-70：把客户端主动关闭的例子抽成没有角色前提的题（中优先级）

- 实际题干：`客户端收到服务端的 FIN 并回复 ACK 之后，双方的最终状态变化是怎样的？`
- C（correct）：`客户端进入 TIME_WAIT，经过 2MSL 后进入 CLOSED；服务端收到 ACK 后直接进入 CLOSED`。
- 原文依据：[TCP 四次挥手过程说一下？](https://xiaolincoding.com/interview/network.html#tcp-四次挥手过程说一下)，`source.txt:994—1001`，整段从客户端先主动关闭开始。T3-65、T3-66 已写客户端主动关闭，T3-70 的实际 stem 没有保留。
- 判分影响：若服务端先关闭，客户端第一次收到服务端 FIN 并回复 ACK 时通常进入 CLOSE_WAIT，随后仍由客户端应用决定何时结束本端发送方向；题干描述的事件本身不能推出 C。此时也没有合适选项。属于单题必须独立成立的条件遗漏，不是 C 在原文具体场景中错误。
- 最小修正：在题干开头补 `客户端主动关闭，已经收到对自己 FIN 的确认；此后`，并限定正常挥手、最后 ACK 成功到达的过程。

## 二、原文自身技术措辞问题

### T3-194：把乱序与真实丢包混为一谈（中优先级）

- 实际题干：`拥塞发生时出现丢包，是否可以把丢包和拥塞完全画等号？`
- C（correct）：`不能，丢包也可能来自链路错误或乱序`；答案也采用这个表述。
- 原文依据：[TCP的拥塞控制介绍一下？](https://xiaolincoding.com/interview/network.html#tcp的拥塞控制介绍一下)，`source.txt:1317` 原文已有相同措辞，题目没有擅自添加它。
- 核对结论：乱序能产生重复 ACK、造成发送方误判丢包或触发不必要的重传；乱序本身不等于真实丢弃数据段。[RFC 5681 §3.2](https://www.rfc-editor.org/rfc/rfc5681.html#section-3.2) 分别列出丢弃、重新排序、复制作为重复 ACK 的来源。T3-175 已准确表述重复 ACK 不一定是实际丢包，和本题措辞形成理解冲突。
- 判分影响：C 是唯一打算表达“不能画等号”的选项，但还包含不准确的因果解释；认真区分乱序和真实丢包的考生会发现没有完全准确的选项。
- 最小修正：C 改为 `不能，真实丢包也可能来自链路错误；乱序还可能产生重复 ACK，使发送方误判丢包`。答案注明原文把乱序写作丢包来源，并增加 `核对来源：RFC 5681 §3.2`。按项目规则，这属于原文核对修订，不能只悄悄改变答案而保留错误选项。

## 三、低优先级清晰度建议，不按确定错误计数

### T3-192、T3-201、T3-202：独立题缺少 cwnd 数值单位及经典 Reno 模型提示

- T3-192 正确 D：`每收到一个 ACK，cwnd 加 1/cwnd，线性增长，比慢启动缓慢`。
- T3-201 正确 A：`cwnd = ssthresh + 3，并重传丢失的数据包`。
- T3-202 正确 D：`重复 ACK 时 cwnd 加 1；收到新数据 ACK 后 cwnd 收缩到 ssthresh，进入拥塞避免`。
- 原文依据：[TCP的拥塞控制介绍一下？](https://xiaolincoding.com/interview/network.html#tcp的拥塞控制介绍一下)，`source.txt:1281—1289` 定义经典 Reno 教学模型，按 MSS 为单位，后续公式沿用该背景；T3-202 答案有模型说明，实际 stem 没有。
- 影响及边界：这些标记均符合原文教学模型，不应报告为“公式标错”。但按字节理解时 `+3` 与 `+1` 容易被误学为加 3/1 字节，`1/cwnd` 也没有相同量纲。另把 T3-202 泛化到 NewReno 会混淆部分确认处理。RFC 的字节表示分别使用 `SMSS²/cwnd`、`3×SMSS`、`SMSS`；这里只用于验证单位差异，不用来新增出题内容。[RFC 5681 §3.1—3.2](https://www.rfc-editor.org/rfc/rfc5681.html#section-3)
- 最小建议：三题题干分别补 `按原文经典 Reno 简化模型，窗口数值以 MSS 为单位`；T3-192 把 ACK 限定为确认新数据的 ACK。T3-202 保留答案已有的 NewReno/SACK 边界说明。

### T3-193：9 MSS 是原文按轮次近似计算，题干宜直接注明

- 实际题干：`假定 ssthresh 为 8，cwnd 已达到 8 并进入拥塞避免，当 8 个 ACK 到来后，一共能发送多少个 MSS 大小的数据？`；A（correct）为 `9 个`。
- 原文依据：同一拥塞控制小节 `source.txt:1291` 明确假定 cwnd 与发送窗口相等；`source.txt:1309—1310` 按该轮 cwnd=8，以每次增加 1/8 的近似教学计算得到 9。
- 影响及边界：答案符合原文该轮教学计算，不标为算术错误。但单题没有接收窗口足够、每 ACK 确认完整新数据段、无其他未确认数据以及按轮次近似的背景，不能把 9 当作任意连接此刻实际可新发的数据量。
- 最小建议：把末句改为 `按原文以 MSS 为单位、cwnd 等于发送窗口的按轮次近似例子，8 个 ACK 到来后 cwnd 约为多少？`，保留 A。

## 四、保留项及审查限制

- **T3-98、T3-107、T3-108**：T3-98 的 E（incorrect）为 `服务端从未收到过任何请求`，但 T3-107/108 将建立 TCP 后长时间没有数据解释为 HTTP 长连接超时，容易让考生把 E 视为该超时场景。这不只是改字母即可解决：原文诊断段落本身没有区分“首次请求未到”与“完成请求后等待复用”。本次不把它计为已经证实的错误标记，也未使用非 RFC/内核的 Nginx 文档作额外核实。建议下轮明确 HTTP/1.x 教学场景及是否已完成第一次请求，或把 E 换成明确不会导致服务端主动关闭的场景。
- **T3-49**：原文先在主动 SYN 小节说明较新 Linux 可以采用线性重试，后在丢失第二次握手例子中使用指数等待。题干仅给两个 retries 参数，没有说明指数模型。已核对[内核 tcp_syn_linear_timeouts 文档](https://docs.kernel.org/networking/ip-sysctl.html#tcp-syn-linear-timeouts)，它只影响主动 SYN，不影响被动 SYNACK。报告只建议加“按原文指数退避示例”，不把它当作已证实的次数/时间答案错误，未模拟具体内核版本或核对快照图像里的时间轴。
- **T3-190**：`cwnd >= ssthresh` 使用拥塞避免符合原文采用的算法选择。RFC 5681 在相等处允许两种算法，原文选择其中一种不构成错误；题干可加“按原文模型”，不建议因这个差异退役题目。
- **T3-195、T3-199**：减半是在原文近似教学模型里的阶段叙述，且原文说明在途量近似 cwnd、实际门限有最小值。T3-195 已明确模型；T3-199 可加“原文经典 Reno 近似模型、进入快速恢复前”，不把它与 T3-201 后续加 3 的步骤误报成矛盾。
- 本次对所有 203 题做来源与判分审查，但没有宣称逐条用 RFC 验证所有原文技术事实。官方联网核对仅用于上述具体疑点，使用 RFC Editor 和 Linux Kernel 官方文档。没有运行业务测试、构建或评分 API，审查报告无需改动业务代码，也无法以结构校验代替语义审查。
