## 一、明确影响判分的题目构造问题

### 1. T2-63：A 与 D 都能请求剩余内容（高优先）

- 实际题干：`一个文件大小为 1048576 字节，客户端已经下载了前 524288 字节（字节位置从 0 开始），网络恢复后要请求剩余部分，Range 请求头应写成哪一项？`
- A 标正确：`Range: bytes=524288-`；D 标错误：`Range: bytes=524288-1048576`。
- 原文依据：[http 断点重传是什么？](https://xiaolincoding.com/interview/network.html#http-断点重传是什么) 给出了开放末尾的 Range 示例，并说明文件实际末位为 1048575；**原文没有说请求中的末位超过实际末位就非法**。
- 官方核对：[RFC 9110 §14.1.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-14.1.2) 规定，末位省略，或末位大于等于表示长度时，都按资源剩余部分解释。因此 D 也请求 524288～1048575，不能以“1048576 比末位大一”判错。这是出题新增干扰项的问题，原文示例本身正确。
- 判分影响：选择合法且满足题干的 D 会被判错。
- 最小修正：把 D 改成确实漏掉一个字节的 `Range: bytes=524288-1048574`；或将题干明确改为“原文示例中使用的、不指定结束位置的请求头是哪一项”，避免考原文没有讲的越界请求规则。

### 2. T2-265：B 是 A 的充分条件，不能当错误选项（高优先）

- 实际题干：`按同源策略，两个地址在什么情况下属于不同源？`
- A 标正确：`协议、主机或端口三者中任意一个不同`；B 标错误：`协议、主机和端口三者都不同`。
- 原文依据：[什么是跨域？CORS 是怎么解决跨域问题的？](https://xiaolincoding.com/interview/network.html#什么是跨域-cors-是怎么解决跨域问题的) 以协议/主机/端口任意一项不同解释不同源。
- 问题：三项都不同当然也满足“任意一项不同”。B 只是范围更窄，没有说“只有三项都不同才算”，所以当前题干下 A、B 都成立；无需外部规范即可由原文推出。
- 判分影响：选择 B 的正确判断会被判错。
- 最小修正：把 B 改成 `只有协议、主机和端口三者都不同才属于不同源，任意一项不同不算`，或题干明确问“完整判定条件”。

### 3. T2-97：第二空有位置限定，却设置为 unordered（中优先）

- 实际题干：`以常见的、基于证书和 ECDHE 的 TLS 1.3 完整握手为例，客户端发送的 ClientHello 带上支持的版本、____和____（也就是 key share）。`
- 数据：`blankCount: 2`、`blankOrder: "unordered"`；答案为“密码套件和临时公钥”。
- 原文依据：[HTTPS握手过程说一下](https://xiaolincoding.com/interview/network.html#https握手过程说一下) 区分密码套件和临时公钥，key share 指临时公钥。
- 问题：括号限定第二空只能是临时公钥，密码套件不等于 key share。实际评分提示会将 unordered 呈现为“各空顺序不限”（`src/server/grading/deepseek-grader.ts:57`），与题干位置要求相反。
- 判分影响：把第一空写成临时公钥、第二空写成密码套件，有机会按整体覆盖获得正确判定，尽管括号对应错误。
- 最小修正：题卷标记和题型数据都改成有序；第一空密码套件，第二空临时公钥。无需改知识点。

### 4. T2-141：开启探测/超时不代表立即退出 ESTABLISHED（中优先）

- 实际题干：`网线被拔掉或者对端突然断电后，在什么情况下本地可能仍然显示 ESTABLISHED？`
- C 标正确：`连接没有数据交互，也没有开启保活或应用层超时的时候`。
- A 标错误：`连接正在发送数据，但长期收不到确认的时候`；D 标错误：`连接已经开启保活，并且应用层设置了超时的时候`。
- 原文依据：[HTTP进行TCP连接之后，在什么情况下会中断](https://xiaolincoding.com/interview/network.html#http进行tcp连接之后-在什么情况下会中断) 说明失去物理连通不一定立即清理本地连接；重传关闭还需要达到超时条件。原文给 C 作为可能情形，并没有排除所有其他情形。
- 官方核对：[RFC 9293 §3.8.3](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.8.3)、[§3.8.4](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.8.4) 描述重传关闭阈值和保活的等待间隔。仅“开启/设置”不足以推出连接已经终止。
- 判分影响：D 在计时尚未到期时仍可能 ESTABLISHED；A 在超过一些等待时间、但尚未达到最终关闭阈值时也可能成立。“可能”问法使 C 不能稳定唯一。
- 最小修正：将 A 改成“达到最终重传失败阈值且内核已报告连接失败之后”；D 改成“保活已判定失败或应用超时已触发并关闭连接之后”。或问“原文举出的无活动且无存活检测的情形是哪项”。

### 5. T2-179：Cookie 作为 Session ID 载体也可能涉及会话固定（中优先）

- 实际题干：`为什么说 Cookie 相对不安全？可能面临哪种威胁？`
- C 标正确：`数据存储在客户端，容易受到 XSS（跨站脚本攻击）的威胁`；D 标错误：`数据存储在客户端，容易受到会话固定攻击的威胁`。
- 原文依据：[cookie和session有什么区别？](https://xiaolincoding.com/interview/network.html#cookie和session有什么区别) 在同一小节说明 Session ID 可通过 Cookie 携带，并把会话固定列为 Session 需要防范的威胁；它没有说明 Cookie 承载会话标识就不会受此威胁。
- 官方核对：[RFC 6265 §8](https://www.rfc-editor.org/rfc/rfc6265.html#section-8)、[§8.4](https://www.rfc-editor.org/rfc/rfc6265.html#section-8.4) 明确讨论 Cookie 中保存 Session ID 时的会话固定风险。
- 判分影响：当前题干没有“原文专门用于说明 Cookie 一侧的风险”限制，D 的威胁不能一概排除。问题在于把教学比较中提到某一侧的风险，当作另一侧不可能发生的错误选项。
- 最小修正：替换 D 为明确错误的“数据存储在服务器端，因此不会受客户端脚本影响”；或将题干限定为“原文在比较 Cookie 与 Session 的安全性时，专门用来说明 Cookie 的客户端数据风险是哪一项”。

## 二、抽取时的条件澄清建议（不按硬判分错误计）

### 6. T2-98：补回“基于证书和 ECDHE”的限定

- 实际题干：`TLS 1.3 的完整握手中，服务端收到 ClientHello 后返回什么？`
- A 标正确：`返回 ServerHello 和自己的 key share，双方由此计算握手密钥；随后发送加密保护的证书、证书签名和 Finished 消息`。
- 原文依据：[HTTPS握手过程说一下](https://xiaolincoding.com/interview/network.html#https握手过程说一下) 将这组消息限定在常见的证书 + ECDHE 完整握手示例。T2-97 保留了该限定，T2-98 没有。
- 判分影响：按此教学示例 A 正确，未发现另一个应标正确的现有选项；但单题展示时不应靠上一题补条件，也不宜把消息组推广到所有认证方式。[RFC 8446 §2.2](https://www.rfc-editor.org/rfc/rfc8446.html#section-2.2) 对 PSK 认证给出不同消息组。
- 最小修正：题干开头补为“以常见的、基于证书和 ECDHE 的 TLS 1.3 完整握手为例”。答案同步保留这句限定。

### 7. T2-105：C 与参考答案漏掉“在 ECDHE 等握手中”

- 实际题干：`下列哪些机制属于原文所说的 HTTPS 防范中间人攻击的主要机制？`
- C 标正确：`证明私钥的持有：服务端用证书对应的私钥对握手内容签名，客户端用公钥验证`；参考答案同样无条件陈述该签名机制。
- 原文依据：[HTTPS是如何防范中间人的攻击？](https://xiaolincoding.com/interview/network.html#https是如何防范中间人的攻击) 对此项写有 ECDHE 场景限制。T2-107、T2-110 保留了它。
- 判分影响：按所引小节应选 C，但不带限制会与本章前面的 TLS 1.2 RSA 示例混淆。RSA 密钥交换的服务器私钥用来解预主密钥，不能套用相同的握手签名叙述；[RFC 5246 §7.4.3](https://www.rfc-editor.org/rfc/rfc5246.html#section-7.4.3) 区分 RSA 与签名临时 DH 参数的消息。
- 最小修正：C 与答案补回“在 ECDHE 等握手中”；不改变选项 correct。

## 三、原文自身问题，与题目改写问题分开

### 8. T2-150：从所有 DNS 服务器推到任意服务器可完成查找，范围过宽

- 实际题干：`根域的 DNS 服务器信息保存在哪里？这带来什么好处？`
- B 标正确：`保存在互联网中所有 DNS 服务器中，因此客户端找到任意一台 DNS 服务器，就能找到根域 DNS 服务器`。
- 原文依据：[DNS的全称了解么？](https://xiaolincoding.com/interview/network.html#dns的全称了解么) 本身就作此泛化，题型与答案忠实转述，**不是改写产生的错误**。
- 官方核对：[RFC 1034 §4.3.1](https://www.rfc-editor.org/rfc/rfc1034.html#section-4.3.1) 明确递归服务可选，也可限制客户端；权威服务与递归解析能力不能统称。找到任意 DNS 服务器不保证它替客户端一路完成公网解析。“所有服务器都保存根信息”也不能作为普遍配置要求。
- 判分影响：按原文 B 是既定答案，但未限定“按原文”的现有题干会让正确区分服务器职责的人对 B 提出合理异议；其余选项也不足以表达准确说法。
- 最小修正：按项目允许的“原文自身错误”流程，答案注明原文泛化，改为递归解析器通常利用根提示或上游解析器完成解析，并附官方核对链接；题干及 B 同步限定可向该客户端提供递归服务的解析器。不要仅把 B 改成 incorrect，那会变成无正确答案。

- 实际题干：`关于最短时间 least_time 算法，下列说法符合原文的是哪一项？`
