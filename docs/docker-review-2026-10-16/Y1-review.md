## 必须修复

### M1：把虚拟机的虚拟化对象写成「操作系统」

涉及 **Y1-24、Y1-36**。

| 题号 | 精确位置与现有文本 |
| --- | --- |
| Y1-24 | Q40；J572 题干「虚拟机虚拟化的是 ____，Docker 虚拟化的是 ____」；A40「2 个空依次是操作系统、进程」。`blankCount: 2`、`blankOrder: ordered` 本身匹配题干，但第一空的目标术语不准确。 |
| Y1-36 | Q52；J869–870 为简答题；A52 首句「虚拟机虚拟化的是操作系统，Docker 虚拟化的是进程」。 |

原文证据：S39–42 同样写「虚拟机虚拟化的是操作系统，Docker 虚拟化的是进程」；但 S45 自己又说 Hypervisor 模拟一整套硬件、VM 运行 Guest OS 内核。错误来自原文。

官方证据：[Docker：Comparing Containers and Virtual Machines](https://www.docker.com/resources/what-container/#comparing-containers-and-virtual-machines) 将 VM 定义为物理硬件的抽象，并将容器描述为操作系统层面的虚拟化、用户空间中的隔离进程。这里要区分「运行完整 Guest OS」与「虚拟化的对象」。

影响：填空可能把合理的「硬件」判为不符参考答案；简答固化错误对比。

最小建议：第一空改为「硬件」，第二空可保留「进程」并把题干改成「VM 虚拟化硬件，容器在共享内核上隔离 ____」等清楚的对应问法；或保持两空但明确问「VM 的虚拟化层级、容器的运行实体」。A40/A52 注明「原文将 VM 的虚拟化对象写为操作系统，这里按官方资料更正」，附「核对来源：」官方链接。保持两空有序，不额外要求填入新知识。

### M2：把按层复用简化成 pull 永远「只下载变化的那一层」

涉及 **Y1-60、Y1-62、Y1-64、Y1-65**。

| 题号 | 精确位置与现有文本 |
| --- | --- |
| Y1-60 | Q85；J1379/B 为 false：「docker pull 时只下载变化的那一层」；A85 却解释「只下载变化的层属于增量分发」。本题正确 C 的共享复用结论正常，问题在把错误简化当作另一项正确机制来解释。 |
| Y1-62 | Q87；J1428–1429/A 标 true：「只下载变化的那一层」；J1433–1434/B 标 false：「下载整个镜像的所有层」；A87 同样断言只会下载一层。 |
| Y1-64 | Q89；J1482–1483/A false：「docker pull 每次都会下载镜像的全部层」可判错，正确集合 B/C/E 不受影响；A89 的「docker pull 只下载变化的那一层」不准确。 |
| Y1-65 | Q90；J1508–1509 为简答；A90「增量分发（docker pull 只下载变化的那一层）」。 |

原文证据：S110–113 原话即「docker pull 只会下载变化的那一层」，没有给出「本地已有其余全部层，且只新增一层」的前提。

官方证据：[docker image pull](https://docs.docker.com/reference/cli/docker/image/pull/#pull-an-image-from-docker-hub) 说明镜像由多层组成，本地已有的共享层无需重复下载；[Storage drivers：Sharing promotes smaller images](https://docs.docker.com/engine/storage/drivers/#sharing-promotes-smaller-images) 给出一次拉取多个层的官方示例。因此所需层可能为零、一层或多层；首次拉取且本地无可复用层时也可以下载所有所需镜像层。

影响：Y1-62 没有无条件成立的正确选项，且其 B 只在部分场景成立，不能只靠「按原文」把 A 当成普遍技术结论。其余题的解析在传播同一简化。

最小建议：Y1-62/A 改「复用本地已有的相同层，仅下载本地缺失的镜像层」；B 改为「每次都重新下载全部镜像层」使其无歧义可判错。A87/A89/A90 同步改；A85 不再肯定「只变化一层」，J1379/B 可改成准确描述「只下载本地缺失层」（它仍不回答题目所问共享底层的直接好处），或换成明显无关机制。答案保留原文说法说明并附官方核对链接，不需改题号或 Y1-64 正确集合。

### M3：只凭某一层自身未变化，就保证命中构建缓存

涉及 **Y1-60、Y1-61、Y1-65**。

| 题号 | 精确位置与现有文本 |
| --- | --- |
| Y1-60 | J1374/A false：「重新构建时只执行发生变化的层」；A85「只执行变化的层属于构建缓存」。false 标记不是问题，解释反而认可了条件不足的结论。 |
| Y1-61 | Q86；J1397「只要某一层没有变化，会怎样？」；J1416–1417/D true「直接复用缓存，构建速度极快」；A86「只要某一层没变就直接复用缓存」。 |
| Y1-65 | A90「构建缓存（某一层没变就直接复用缓存）」。 |

原文证据：S108–109 原话如此；S115 的「不常变的层放在常变的层之前」又暗示缓存与前序有关。不是缺少原文未讲的新考点，而是现有条件过宽。

官方证据：[Build cache invalidation](https://docs.docker.com/build/cache/invalidation/#general-rules) 说明从基础镜像开始检查各指令及输入；前序缓存失效后，后续指令也重新执行。指令文字相同不等于输入和前序状态相同；已有缓存是否存在也不能省略。

影响：Y1-61 会把「前面层已变化、当前指令未变化」也判成一定复用，技术上不成立；A85 把重建范围说窄。

最小建议：Q86/J1397 增加「已有可用缓存，且相关输入与前序层均未变化」前提；D 改「可复用相应缓存，避免重复执行」。A85 改为「命中缓存的步骤可复用，前序失效可能使后续重建」；A86/A90 同步改，并注明原文省略了缓存成立条件、附核对来源。无需改变题型与正确字母。

## 可选澄清（不据此认定现有 correct 错标）

### C1：cgroup v1 分树是原文示例，不是每个控制器必须各占一树

主要涉及 **Y1-13、Y1-16、Y1-22、Y1-23**；同口径解释还出现在 **Y1-12、Y1-17、Y1-18、Y1-21**。

精确位置：Q26、J315/A true、A26「每个控制器使用独立的树」；Q29、J406–407/C false「所有控制器共用同一个层次结构，只需操作一次」、A29；A35/A36 对比 v1/v2；A25/A30/A31/A34 也使用 v1 分树的概括。

原文证据：S21–35 多次如此概括，S22 实际列出的 `cpuacct,cpu` 等挂载又体现了控制器可合并。官方 [Linux cgroup v1：Why are cgroups needed?](https://docs.kernel.org/admin-guide/cgroup-v1/cgroups.html#why-are-cgroups-needed) 明确允许从每控制器独立 hierarchy 到全部控制器同一 hierarchy 的配置；[cgroup v2：Mounting](https://docs.kernel.org/admin-guide/cgroup-v2.html#mounting) 的真正区别是 v2 **只提供单一 hierarchy**。

影响：读者可能把「v1 支持多个层次且常按控制器分挂载」误学成「v1 禁止合并」。按题目明确要求的原文示例，选项和答案仍能对应，因此列条件澄清，不直接改正确集合。

最小建议：题干或答案加「在原文展示的分挂载布局中」；把「v1 为每个控制器使用独立树」改「v1 允许多棵独立树，原文示例分别挂载各控制器；v2 使用统一层次」，括注原文简化及核对来源。Y1-16/C 如保留 false，应明确「在上述已分开挂载的示例中」。

### C2：Docker 的 cgroup 路径需要 cgroupfs 驱动条件

涉及 **Y1-15、Y1-22**。Q28/J365、J379/C true、A28，以及 A35 都写「在 cpu、memory 等目录下创建 docker，再按 containerID 建子目录」。原文 S24 是「比如 Docker」的示例。

官方 [Runtime metrics：Find the cgroup for a given container](https://docs.docker.com/engine/containers/runmetrics/#find-the-cgroup-for-a-given-container) 将 `/sys/fs/cgroup/memory/docker/<longid>/` 对应到 v1+cgroupfs；v1+systemd 则使用 `system.slice/docker-<longid>.scope`。不影响本例答案，但不应把目录布局当作全部 Docker v1 的强制规则。最小建议：Q28/J365、A28/A35 加「在原文采用的 cgroup v1+cgroupfs 示例中」，不增考驱动知识。

### C3：进程可见范围和「互不影响」需要默认隔离条件

涉及 **Y1-5、Y1-10、Y1-50、Y1-51、Y1-53、Y1-54**。主要位置：Q15/J112–113/A true、A15「因此也不会影响其他容器中的进程」；A20；Q72/A72；J1194–1195/B true、A73「所以不会共用，也不会相互影响」；J1258–1259/D true、A75；A76。原文 S6、S72–73 同样简写默认隔离情况。

官方 [pid_namespaces(7)](https://man7.org/linux/man-pages/man7/pid_namespaces.7.html) 说明 PID namespace 是可嵌套的；可见范围不能简单推广为任何配置下只能见本层。官方 [Volumes：A volume's lifecycle](https://docs.docker.com/engine/storage/volumes/#a-volumes-lifecycle) 明确同一卷可以同时挂到多个容器，容器因而可通过共享数据相互影响。

影响：默认独立 namespace、各自可写层下的教材表述可以理解，但「所以不会共用/互不影响」若不限范围会掩盖共享卷、共享 namespace 等配置。本报告不把这些新条件算漏考点。最小建议：限定为「默认分别隔离、未显式共享的资源」；「容器可写层的修改不会写回镜像或其他容器的可写层」。Y1-5 删去可见性推导「不会影响」的因果连接。保持原题考点和正确集合。

### C4：可写层说明只针对容器根文件系统，不能包含所有挂载

涉及 **Y1-58、Y1-65**。Q83/J1336、J1345–1346/B true；A83/A90 写「容器对文件的任何修改都发生在可写层」。原文 S98–102 同样写「任何修改」。

官方 [Volumes：When to use volumes](https://docs.docker.com/engine/storage/volumes/#when-to-use-volumes) 说明卷直接写宿主机文件系统、绕过容器可写层；[Storage drivers：The copy-on-write strategy](https://docs.docker.com/engine/storage/drivers/#the-copy-on-write-cow-strategy) 描述的是下层已有文件首次修改时复制到上层。

影响：默认未额外挂载的根文件系统语境下 B 可判对，不认定错标；「任何修改」容易同 Y3 的 volume/bind mount 知识冲突。最小建议：Q83/J1336 加「对容器根文件系统中未被挂载覆盖的文件」；A83/A90 删「任何」，说明是在容器可写层修改、首次修改来自镜像的已有文件时用 CoW；括注原文概括范围，附核对来源即可。

### C5：overlay2 的默认值已有历史口径说明，可再补精确范围

涉及 **Y1-56、Y1-65**。Q81/J1302、A81 参考两空为「UnionFS、overlay2」；A90 已写「按原文现代 Docker 主要使用 overlay2」。原文 S76–82 如此表述，README141 明确将默认驱动列为按写作时口径转述的版本事实。

官方 [containerd image store with Docker Engine](https://docs.docker.com/engine/storage/containerd/) 说明 Docker Engine 29.0 及之后的全新安装默认使用 containerd image store，而升级安装可能继续使用旧 graph driver；containerd 使用 snapshotter。不能拿现行默认值直接宣布本题在「按原文」前提下错标，填空顺序也无错误。

最小建议：把「现代 Docker」改「原文所述传统存储后端场景」，答案补版本/安装方式适用范围和核对链接；不把 containerd 的新知识作为原文覆盖缺口，不要求因此改题型。

### C6：「公有 Registry」与「私有 repository」容易混为一谈

涉及 **Y1-40、Y1-43、Y1-46**。Q59/A59「仓库（Registry）分公有仓库和私有仓库」；Q62/J1005–1030、A62 将 Docker Hub 排为非私有、Harbor/ACR/TCR 排为私有；A65 同口径列举。原文 S58–59 就是按 Registry 服务举例。
