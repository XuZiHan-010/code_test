## 1. 底层原理与核心概念

原文：[Docker 面试题 · 底层原理与核心概念](https://xiaolincoding.com/interview/docker.html#docker%E5%BA%95%E5%B1%82%E4%BE%9D%E6%89%98%E4%BA%8Elinux%E6%80%8E%E4%B9%88%E5%AE%9E%E7%8E%B0%E8%B5%84%E6%BA%90%E9%9A%94%E7%A6%BB%E7%9A%84)。

### docker底层依托于linux怎么实现资源隔离的？

- **Y1-1** 2 个空是 Namespace（命名空间）、cgroups（顺序不限）。Namespace 负责视图隔离，cgroups 负责资源隔离。[原文§docker底层依托于linux怎么实现资源隔离的？](https://xiaolincoding.com/interview/docker.html#docker%E5%BA%95%E5%B1%82%E4%BE%9D%E6%89%98%E4%BA%8Elinux%E6%80%8E%E4%B9%88%E5%AE%9E%E7%8E%B0%E8%B5%84%E6%BA%90%E9%9A%94%E7%A6%BB%E7%9A%84)
- **Y1-2** Namespace（命名空间）。每个容器都运行在自己的一组命名空间中，以此实现容器之间的视图隔离。cgroups 管的是 CPU、内存、磁盘 I/O 等资源的分配与限制；UnionFS 是镜像分层的底层；Hypervisor 是虚拟机用来模拟硬件的，都不是视图隔离的机制。[原文§docker底层依托于linux怎么实现资源隔离的？](https://xiaolincoding.com/interview/docker.html#docker%E5%BA%95%E5%B1%82%E4%BE%9D%E6%89%98%E4%BA%8Elinux%E6%80%8E%E4%B9%88%E5%AE%9E%E7%8E%B0%E8%B5%84%E6%BA%90%E9%9A%94%E7%A6%BB%E7%9A%84)
- **Y1-3** cgroups。它是 Linux 内核的一个功能，允许在进程组之间分配、限制和优先处理系统资源。Namespace 做的是视图隔离，不管资源配额；写时复制和 UnionFS 属于镜像分层与容器可写层的机制，答非所问。[原文§docker底层依托于linux怎么实现资源隔离的？](https://xiaolincoding.com/interview/docker.html#docker%E5%BA%95%E5%B1%82%E4%BE%9D%E6%89%98%E4%BA%8Elinux%E6%80%8E%E4%B9%88%E5%AE%9E%E7%8E%B0%E8%B5%84%E6%BA%90%E9%9A%94%E7%A6%BB%E7%9A%84)
- **Y1-4** 正确的是 PID（进程）、网络、挂载点和 IPC（进程间通信）。原文说每个容器都运行在自己的一组命名空间中，包括这些内容。CPU 与内存的使用上限是 cgroups 做的资源限制，镜像的只读分层结构是镜像分层原理，都不是命名空间所隔离的内容。[原文§docker底层依托于linux怎么实现资源隔离的？](https://xiaolincoding.com/interview/docker.html#docker%E5%BA%95%E5%B1%82%E4%BE%9D%E6%89%98%E4%BA%8Elinux%E6%80%8E%E4%B9%88%E5%AE%9E%E7%8E%B0%E8%B5%84%E6%BA%90%E9%9A%94%E7%A6%BB%E7%9A%84)
- **Y1-5** 只能看到自己所在命名空间内的进程，因此也不会影响其他容器中的进程。原文并没有说容器能看到宿主机或其他容器的进程，也不是按镜像来划分可见范围。[原文§docker底层依托于linux怎么实现资源隔离的？](https://xiaolincoding.com/interview/docker.html#docker%E5%BA%95%E5%B1%82%E4%BE%9D%E6%89%98%E4%BA%8Elinux%E6%80%8E%E4%B9%88%E5%AE%9E%E7%8E%B0%E8%B5%84%E6%BA%90%E9%9A%94%E7%A6%BB%E7%9A%84)
- **Y1-6** cgroups 是 Linux 内核的一个功能，允许在进程组之间分配、限制和优先处理系统资源，如 CPU、内存和磁盘 I/O。把镜像按层存储的是存储驱动，让容器只看到自己空间内进程的是命名空间，存储和分发镜像的是仓库，都不是 cgroups。[原文§docker底层依托于linux怎么实现资源隔离的？](https://xiaolincoding.com/interview/docker.html#docker%E5%BA%95%E5%B1%82%E4%BE%9D%E6%89%98%E4%BA%8Elinux%E6%80%8E%E4%B9%88%E5%AE%9E%E7%8E%B0%E8%B5%84%E6%BA%90%E9%9A%94%E7%A6%BB%E7%9A%84)
- **Y1-7** 正确的是 CPU、内存和磁盘 I/O。挂载点和 IPC 的可见范围属于命名空间做的视图隔离，不是 cgroups 管理的资源。[原文§docker底层依托于linux怎么实现资源隔离的？](https://xiaolincoding.com/interview/docker.html#docker%E5%BA%95%E5%B1%82%E4%BE%9D%E6%89%98%E4%BA%8Elinux%E6%80%8E%E4%B9%88%E5%AE%9E%E7%8E%B0%E8%B5%84%E6%BA%90%E9%9A%94%E7%A6%BB%E7%9A%84)
- **Y1-8** 正确的是资源限制、工作负载隔离，以及在不同进程组之间进行资源优先处理。隐藏其他容器中的进程是命名空间的作用，把镜像拆成可复用的只读层是镜像分层的做法，与 cgroups 无关。[原文§docker底层依托于linux怎么实现资源隔离的？](https://xiaolincoding.com/interview/docker.html#docker%E5%BA%95%E5%B1%82%E4%BE%9D%E6%89%98%E4%BA%8Elinux%E6%80%8E%E4%B9%88%E5%AE%9E%E7%8E%B0%E8%B5%84%E6%BA%90%E9%9A%94%E7%A6%BB%E7%9A%84)
- **Y1-9** Namespace 负责基于视图的隔离，cgroups 负责资源隔离。把两者分工说反、或说成都只做视图隔离、或把 Namespace 当成镜像分层存储，都不是原文的说法。[原文§docker底层依托于linux怎么实现资源隔离的？](https://xiaolincoding.com/interview/docker.html#docker%E5%BA%95%E5%B1%82%E4%BE%9D%E6%89%98%E4%BA%8Elinux%E6%80%8E%E4%B9%88%E5%AE%9E%E7%8E%B0%E8%B5%84%E6%BA%90%E9%9A%94%E7%A6%BB%E7%9A%84)
- **Y1-10** Docker 依托 Linux 的两项机制。一是 Namespace：每个容器都运行在自己的一组命名空间中，包括 PID（进程）、网络、挂载点、IPC（进程间通信）等，容器中的进程只能看到自己所在命名空间内的进程，不会影响其他容器中的进程，这是视图隔离。二是 cgroups：它是 Linux 内核的一个功能，允许在进程组之间分配、限制和优先处理 CPU、内存和磁盘 I/O 等系统资源，有助于资源限制、工作负载隔离以及在不同进程组之间进行资源优先处理，这是资源隔离。[原文§docker底层依托于linux怎么实现资源隔离的？](https://xiaolincoding.com/interview/docker.html#docker%E5%BA%95%E5%B1%82%E4%BE%9D%E6%89%98%E4%BA%8Elinux%E6%80%8E%E4%B9%88%E5%AE%9E%E7%8E%B0%E8%B5%84%E6%BA%90%E9%9A%94%E7%A6%BB%E7%9A%84)

### 讲讲cgroup v2.0

- **Y1-11** cgroup v2 是 Linux cgroup API 的下一个版本，提供一个具有增强资源管理能力的统一控制系统。它不是命名空间 API、不是 Docker 引擎的版本，也不是联合文件系统。[原文§讲讲cgroup v2.0](https://xiaolincoding.com/interview/docker.html#%E8%AE%B2%E8%AE%B2cgroup-v2-0)
- **Y1-12** 将重点放在简化层次结构上。v1 为每个控制器使用独立的树，正是 v2 要改掉的做法；v2 没有取消 CPU、内存的限制，更不是增加独立的控制器目录。[原文§讲讲cgroup v2.0](https://xiaolincoding.com/interview/docker.html#%E8%AE%B2%E8%AE%B2cgroup-v2-0)
- **Y1-13** v1 为每个控制器都使用独立的树（目录），例如 /sys/fs/cgroup/cpu/GROUPNAME 和 /sys/fs/cgroup/memory/GROUPNAME。所有控制器统一在 /sys/fs/cgroup/GROUPNAME 下的一棵树中，是 v2 的做法。[原文§讲讲cgroup v2.0](https://xiaolincoding.com/interview/docker.html#%E8%AE%B2%E8%AE%B2cgroup-v2-0)
- **Y1-14** cpu 目录下。每个目录代表一个 cgroup subsystem，限制 cpu 要到 cpu 目录下创建子目录（树），限制 memory 则要到 memory 目录下创建。/sys/fs/cgroup/GROUPNAME 是 v2 统一后的树。[原文§讲讲cgroup v2.0](https://xiaolincoding.com/interview/docker.html#%E8%AE%B2%E8%AE%B2cgroup-v2-0)
- **Y1-15** v1 中 Docker 会在 cpu、memory 等目录下都创建一个名为 docker 的目录，再在 docker 目录下根据 containerID 创建子目录来实现资源限制。目录名是 docker 而不是 test；子目录按 containerID 而不是控制器名称创建；v1 每个控制器各用一棵树，并不是在统一的 GROUPNAME 下建单个目录（那是 v2 的做法）。[原文§讲讲cgroup v2.0](https://xiaolincoding.com/interview/docker.html#%E8%AE%B2%E8%AE%B2cgroup-v2-0)
- **Y1-16** 正确的是：用户空间最后管理着多个非常类似的 hierarchy，并且在执行 hierarchy 管理操作时，每个 hierarchy 上都重复着相同的操作。所有控制器共用一个层次结构、加入一个目录后各控制器自动生效，描述的是 v2 的统一树，不是 v1 的结果。[原文§讲讲cgroup v2.0](https://xiaolincoding.com/interview/docker.html#%E8%AE%B2%E8%AE%B2cgroup-v2-0)
- **Y1-17** 正确的是：API 中单个统一的层次结构设计、更安全的子树委派给容器、新增压力阻塞信息（PSI）等功能特性。为每个控制器使用独立的树是 v1 的做法；v2 是统一核算不同类型的内存分配，而不是分开核算。[原文§讲讲cgroup v2.0](https://xiaolincoding.com/interview/docker.html#%E8%AE%B2%E8%AE%B2cgroup-v2-0)
- **Y1-18** 正确的是：跨多个资源的增强资源分配管理和隔离、统一核算不同类型的内存分配（网络内存、内核内存等）、考虑非即时资源变化（例如页面缓存回写）。每个 Subsystem 各自维护独立的树是 v1 的状态；v2 的改进是更安全地把子树委派给容器，而不是取消委派。[原文§讲讲cgroup v2.0](https://xiaolincoding.com/interview/docker.html#%E8%AE%B2%E8%AE%B2cgroup-v2-0)
- **Y1-19** PSI 是压力阻塞信息（Pressure Stall Information），是 v2 更新的功能特性之一。页面缓存回写、统一的内存核算、子树委派是原文列出的另外几项改进，答非所问。[原文§讲讲cgroup v2.0](https://xiaolincoding.com/interview/docker.html#%E8%AE%B2%E8%AE%B2cgroup-v2-0)
- **Y1-20** 统一核算不同类型的内存分配，例如网络内存、内核内存等。只核算用户空间内存、为各类内存各自建树，都与“统一核算”相反；原文还提到 v2 会考虑页面缓存回写这类非即时资源变化，而不是不再考虑。[原文§讲讲cgroup v2.0](https://xiaolincoding.com/interview/docker.html#%E8%AE%B2%E8%AE%B2cgroup-v2-0)
- **Y1-21** v2 将各控制器的树统一到 /sys/fs/cgroup/GROUPNAME 中，进程 X 加入 /sys/fs/cgroup/test 后，启用 test 的每个控制器都将控制进程 X。逐个控制器分别加入，是 v1 各控制器各用一棵树时的做法。[原文§讲讲cgroup v2.0](https://xiaolincoding.com/interview/docker.html#%E8%AE%B2%E8%AE%B2cgroup-v2-0)
- **Y1-22** v1 为每个控制器都使用独立的树（目录），例如限制 cpu 要到 cpu 目录下创建子目录，限制 memory 要到 memory 目录下创建，Docker 会在 cpu、memory 等目录下各建一个名为 docker 的目录，再按 containerID 创建子目录。各个 Subsystem 各自为政，结果是用户空间管理着多个非常类似的 hierarchy，而且在执行管理操作时每个 hierarchy 上都重复着相同的操作。v2 的最大更改是简化层次结构：把各控制器的树统一到 /sys/fs/cgroup/GROUPNAME 中，进程加入 /sys/fs/cgroup/test 后，启用 test 的每个控制器都将控制该进程。[原文§讲讲cgroup v2.0](https://xiaolincoding.com/interview/docker.html#%E8%AE%B2%E8%AE%B2cgroup-v2-0)
- **Y1-23** cgroup v2 是 Linux cgroup API 的下一个版本，提供具有增强资源管理能力的统一控制系统。相对 v1 的改进包括：API 中单个统一的层次结构设计、更安全的子树委派给容器、更新的功能特性（例如压力阻塞信息 PSI）、跨多个资源的增强资源分配管理和隔离、统一核算不同类型的内存分配（网络内存、内核内存等），以及考虑非即时资源变化（例如页面缓存回写）。v1 为每个控制器使用独立的树，各 Subsystem 各自为政，用户空间要管理多个类似的 hierarchy 并重复相同的操作；v2 的最大更改是简化层次结构，统一 /sys/fs/cgroup/GROUPNAME 中的树，进程加入后启用的每个控制器都会控制它。[原文§讲讲cgroup v2.0](https://xiaolincoding.com/interview/docker.html#%E8%AE%B2%E8%AE%B2cgroup-v2-0)

### Docker 和虚拟机有什么区别？

- **Y1-24** 2 个空依次是操作系统、进程。[原文§Docker 和虚拟机有什么区别？](https://xiaolincoding.com/interview/docker.html#docker-%E5%92%8C%E8%99%9A%E6%8B%9F%E6%9C%BA%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)
- **Y1-25** Hypervisor。虚拟机通过 Hypervisor 在宿主机上模拟一整套硬件。Namespace、cgroups 是容器做视图隔离和资源限制的机制，UnionFS 是镜像分层的底层，都不是虚拟机模拟硬件的方式。[原文§Docker 和虚拟机有什么区别？](https://xiaolincoding.com/interview/docker.html#docker-%E5%92%8C%E8%99%9A%E6%8B%9F%E6%9C%BA%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)
- **Y1-26** 每台 VM 都跑着一个完整的 Guest OS 内核，所以隔离性极强但开销大。共享宿主机 Linux 内核、本质上是一组被隔离起来的特殊进程，说的是 Docker 容器；只读模板说的是镜像。[原文§Docker 和虚拟机有什么区别？](https://xiaolincoding.com/interview/docker.html#docker-%E5%92%8C%E8%99%9A%E6%8B%9F%E6%9C%BA%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)
- **Y1-27** 所有容器共享宿主机的 Linux 内核。各自独立的 Guest OS 内核、Hypervisor 模拟的硬件是虚拟机的特点；每个容器有自己的文件系统读写层，并不共用同一份可写层。[原文§Docker 和虚拟机有什么区别？](https://xiaolincoding.com/interview/docker.html#docker-%E5%92%8C%E8%99%9A%E6%8B%9F%E6%9C%BA%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)
- **Y1-28** 2 个空依次是 Namespace、cgroups。[原文§Docker 和虚拟机有什么区别？](https://xiaolincoding.com/interview/docker.html#docker-%E5%92%8C%E8%99%9A%E6%8B%9F%E6%9C%BA%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)
- **Y1-29** 本质上容器就是一组被隔离起来的特殊进程。它不运行完整的 Guest OS，也不是 Hypervisor 模拟的硬件；只读的应用模板是镜像，不是容器。[原文§Docker 和虚拟机有什么区别？](https://xiaolincoding.com/interview/docker.html#docker-%E5%92%8C%E8%99%9A%E6%8B%9F%E6%9C%BA%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)
- **Y1-30** 正确的是：通过 Hypervisor 模拟一整套硬件、每台 VM 都跑完整的 Guest OS 内核、隔离性极强但开销大。共享宿主机内核、启动秒级、内存 MB 级别，是 Docker 容器的特点。[原文§Docker 和虚拟机有什么区别？](https://xiaolincoding.com/interview/docker.html#docker-%E5%92%8C%E8%99%9A%E6%8B%9F%E6%9C%BA%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)
- **Y1-31** 正确的是：共享宿主机的 Linux 内核；通过 Namespace 做视图隔离、cgroups 做资源限制；本质上是一组被隔离起来的特殊进程。运行完整 Guest OS、镜像几个 GB、启动几十秒是虚拟机的特点；容器还牺牲了一点隔离性（共用内核），并不比虚拟机更强。[原文§Docker 和虚拟机有什么区别？](https://xiaolincoding.com/interview/docker.html#docker-%E5%92%8C%E8%99%9A%E6%8B%9F%E6%9C%BA%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)
- **Y1-32** 按原文，容器启动秒级，虚拟机启动要几十秒。说反或说成没有差别，都不符合原文。[原文§Docker 和虚拟机有什么区别？](https://xiaolincoding.com/interview/docker.html#docker-%E5%92%8C%E8%99%9A%E6%8B%9F%E6%9C%BA%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)

### Docker 镜像的分层原理是什么？

- **Y1-55** Docker 镜像采用分层只读的结构，各层都是只读的。可读写的是容器启动时叠加在其上的容器层，不是镜像本身。[原文§Docker 镜像的分层原理是什么？](https://xiaolincoding.com/interview/docker.html#docker-%E9%95%9C%E5%83%8F%E7%9A%84%E5%88%86%E5%B1%82%E5%8E%9F%E7%90%86%E6%98%AF%E4%BB%80%E4%B9%88)
- **Y1-56** 2 个空依次是 UnionFS（联合文件系统）、overlay2。[原文§Docker 镜像的分层原理是什么？](https://xiaolincoding.com/interview/docker.html#docker-%E9%95%9C%E5%83%8F%E7%9A%84%E5%88%86%E5%B1%82%E5%8E%9F%E7%90%86%E6%98%AF%E4%BB%80%E4%B9%88)
- **Y1-57** Docker 会在所有只读层之上再叠加一层可写层（容器层）。叠加的不是缓存层、也不是复制镜像；Guest OS 内核是虚拟机才有的。[原文§Docker 镜像的分层原理是什么？](https://xiaolincoding.com/interview/docker.html#docker-%E9%95%9C%E5%83%8F%E7%9A%84%E5%88%86%E5%B1%82%E5%8E%9F%E7%90%86%E6%98%AF%E4%BB%80%E4%B9%88)
- **Y1-58** 容器对文件的任何修改都发生在可写层（容器层），通过 Copy-on-Write（写时复制）机制实现。只读层不会被修改；增量分发、构建缓存是分层的另外两项好处，不是修改文件的机制。[原文§Docker 镜像的分层原理是什么？](https://xiaolincoding.com/interview/docker.html#docker-%E9%95%9C%E5%83%8F%E7%9A%84%E5%88%86%E5%B1%82%E5%8E%9F%E7%90%86%E6%98%AF%E4%BB%80%E4%B9%88)
- **Y1-59** 3 个空是共享与复用、构建缓存、增量分发（顺序不限）。[原文§Docker 镜像的分层原理是什么？](https://xiaolincoding.com/interview/docker.html#docker-%E9%95%9C%E5%83%8F%E7%9A%84%E5%88%86%E5%B1%82%E5%8E%9F%E7%90%86%E6%98%AF%E4%BB%80%E4%B9%88)
- **Y1-60** 这属于“共享与复用”：多个镜像可以共享相同的底层，节省存储和网络传输。只执行变化的层属于构建缓存，只下载变化的层属于增量分发，都是答非所问；容器的修改发生在可写层，不会写进共享的底层。[原文§Docker 镜像的分层原理是什么？](https://xiaolincoding.com/interview/docker.html#docker-%E9%95%9C%E5%83%8F%E7%9A%84%E5%88%86%E5%B1%82%E5%8E%9F%E7%90%86%E6%98%AF%E4%BB%80%E4%B9%88)
- **Y1-61** 这是“构建缓存”：只要某一层没变就直接复用缓存，速度极快。重新执行该层、重新下载该层、转为可写层，都不是原文的说法。[原文§Docker 镜像的分层原理是什么？](https://xiaolincoding.com/interview/docker.html#docker-%E9%95%9C%E5%83%8F%E7%9A%84%E5%88%86%E5%B1%82%E5%8E%9F%E7%90%86%E6%98%AF%E4%BB%80%E4%B9%88)
- **Y1-62** 增量分发指 docker pull 只会下载变化的那一层。下载全部层、下载可写层、只下载共享底层，都不对；被多个镜像共享是“共享与复用”的内容。[原文§Docker 镜像的分层原理是什么？](https://xiaolincoding.com/interview/docker.html#docker-%E9%95%9C%E5%83%8F%E7%9A%84%E5%88%86%E5%B1%82%E5%8E%9F%E7%90%86%E6%98%AF%E4%BB%80%E4%B9%88)
- **Y1-63** 原文的原则是把“不常变的层”（如依赖安装）放在“常变的层”（如 COPY 源码）之前，这样缓存命中率更高、构建更快。顺序反过来、认为顺序无关、按体积排列，都不是原文的说法。[原文§Docker 镜像的分层原理是什么？](https://xiaolincoding.com/interview/docker.html#docker-%E9%95%9C%E5%83%8F%E7%9A%84%E5%88%86%E5%B1%82%E5%8E%9F%E7%90%86%E6%98%AF%E4%BB%80%E4%B9%88)
- **Y1-64** 正确的是：镜像的各层都是只读的；容器启动时在只读层之上叠加一层可写层；多个镜像可以共享相同的底层。容器的修改发生在可写层，而不是写入只读层；docker pull 只下载变化的那一层，而不是每次下载全部。[原文§Docker 镜像的分层原理是什么？](https://xiaolincoding.com/interview/docker.html#docker-%E9%95%9C%E5%83%8F%E7%9A%84%E5%88%86%E5%B1%82%E5%8E%9F%E7%90%86%E6%98%AF%E4%BB%80%E4%B9%88)
- **Y1-65** Docker 镜像采用分层只读的结构，底层基于 UnionFS（联合文件系统），按原文现代 Docker 主要使用 overlay2 作为默认存储驱动。容器启动时，Docker 会在所有只读层之上再叠加一层可写层（容器层），容器对文件的任何修改都发生在这一层，通过 Copy-on-Write（写时复制）机制实现。分层带来三项好处：共享与复用（多个镜像可共享相同的底层，节省存储和网络传输）、构建缓存（某一层没变就直接复用缓存）、增量分发（docker pull 只下载变化的那一层）。因此 Dockerfile 最佳实践是把不常变的层（如依赖安装）放在常变的层（如 COPY 源码）之前，缓存命中率更高、构建更快。[原文§Docker 镜像的分层原理是什么？](https://xiaolincoding.com/interview/docker.html#docker-%E9%95%9C%E5%83%8F%E7%9A%84%E5%88%86%E5%B1%82%E5%8E%9F%E7%90%86%E6%98%AF%E4%BB%80%E4%B9%88)

### Dockerfile 中 CMD 和 ENTRYPOINT 有什么区别？

- **Y2-13** 两者都用于指定容器启动时执行的命令，区别在于 docker run 后面跟的参数是覆盖 CMD，还是追加到 ENTRYPOINT 后面。构建阶段执行命令的是 RUN，声明监听端口的是 EXPOSE，拷贝文件的是 COPY / ADD。[原文§Dockerfile 中 CMD 和 ENTRYPOINT 有什么区别？](https://xiaolincoding.com/interview/docker.html#dockerfile-%E4%B8%AD-cmd-%E5%92%8C-entrypoint-%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)
- **Y2-14** CMD 提供默认命令，可以被 docker run 后面跟的参数完全覆盖。设置“主命令”、参数追加在它后面的是 ENTRYPOINT；声明监听端口的是 EXPOSE，只在 docker build 阶段有效的是 ARG。[原文§Dockerfile 中 CMD 和 ENTRYPOINT 有什么区别？](https://xiaolincoding.com/interview/docker.html#dockerfile-%E4%B8%AD-cmd-%E5%92%8C-entrypoint-%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)

- **Y2-16** 推荐 ENTRYPOINT 设主命令、CMD 设默认参数，这样用户既能使用默认行为，也能灵活传参。把两者角色对调，或只写其中一个，都不是原文推荐的组合。[原文§Dockerfile 中 CMD 和 ENTRYPOINT 有什么区别？](https://xiaolincoding.com/interview/docker.html#dockerfile-%E4%B8%AD-cmd-%E5%92%8C-entrypoint-%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)
- **Y2-17** 没有额外参数时，CMD 提供的默认参数会接在 ENTRYPOINT 后面，实际运行 java -jar app.jar --spring.profiles.active=prod。[原文§Dockerfile 中 CMD 和 ENTRYPOINT 有什么区别？](https://xiaolincoding.com/interview/docker.html#dockerfile-%E4%B8%AD-cmd-%E5%92%8C-entrypoint-%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)

- **Y2-31** 原文推荐在 RUN 里显式处理解压，这样更清晰。自动解压是 ADD 的功能，COPY 不具备，WORKDIR 是设置工作目录的。[原文§Dockerfile 中 COPY 和 ADD 有什么区别？](https://xiaolincoding.com/interview/docker.html#dockerfile-%E4%B8%AD-copy-%E5%92%8C-add-%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)

- **Y2-42** 按原文，最终镜像只基于 alpine（5MB）加上编译好的二进制，可能只有 15MB，瘦身 50 倍；传统做法则可能有 800MB+。这些体积数字是原文示例的写法。[原文§什么是多阶段构建（multi-stage build）？有什么好处？](https://xiaolincoding.com/interview/docker.html#%E4%BB%80%E4%B9%88%E6%98%AF%E5%A4%9A%E9%98%B6%E6%AE%B5%E6%9E%84%E5%BB%BA-multi-stage-build-%E6%9C%89%E4%BB%80%E4%B9%88%E5%A5%BD%E5%A4%84)
- **Y2-43** 最终只保留最后一个阶段的镜像；原文说 Java、Node.js、前端项目都适合用这种模式；示例的最终镜像基于 alpine 加编译好的二进制。并不是所有阶段都保留，也不是只适用于 Go（Go 只是原文的示例）。[原文§什么是多阶段构建（multi-stage build）？有什么好处？](https://xiaolincoding.com/interview/docker.html#%E4%BB%80%E4%B9%88%E6%98%AF%E5%A4%9A%E9%98%B6%E6%AE%B5%E6%9E%84%E5%BB%BA-multi-stage-build-%E6%9C%89%E4%BB%80%E4%B9%88%E5%A5%BD%E5%A4%84)
- **Y2-44** 多阶段构建是 Docker 17.05 引入的特性：允许在一个 Dockerfile 里写多个 FROM，每个 FROM 开启一个“构建阶段”，后面的阶段可以从前面的阶段拷贝文件，但最终只有最后一个阶段的镜像会被保留。核心价值是把“构建环境”和“运行环境”分开，大幅减小最终镜像体积。以原文的 Go 应用为例：传统做法（FROM golang:1.21 里直接编译并运行）最终镜像包含整个 Go 编译器、依赖和源码，可能有 800MB+；多阶段写法用 golang:1.21 AS builder 编译，再基于 alpine:3.18 用 COPY --from=builder 只拷贝编译好的二进制，最终镜像只基于 alpine（5MB）加二进制，可能只有 15MB，瘦身 50 倍。Java、Node.js、前端项目都适合用这种模式。[原文§什么是多阶段构建（multi-stage build）？有什么好处？](https://xiaolincoding.com/interview/docker.html#%E4%BB%80%E4%B9%88%E6%98%AF%E5%A4%9A%E9%98%B6%E6%AE%B5%E6%9E%84%E5%BB%BA-multi-stage-build-%E6%9C%89%E4%BB%80%E4%B9%88%E5%A5%BD%E5%A4%84)

### 如何减小 Docker 镜像体积？

- **Y2-45** 用 alpine 代替 ubuntu 属于“选小的基础镜像”。多阶段构建是把构建和运行分离，合并 RUN 是减少层数，.dockerignore 是排除不需要 COPY 的文件。这些体积数字是原文写法。[原文§如何减小 Docker 镜像体积？](https://xiaolincoding.com/interview/docker.html#%E5%A6%82%E4%BD%95%E5%87%8F%E5%B0%8F-docker-%E9%95%9C%E5%83%8F%E4%BD%93%E7%A7%AF)
- **Y2-46** 原文的两个例子是：用 alpine 代替 ubuntu，用 openjdk:17-jre-slim 代替 openjdk:17。反过来换成更大的镜像，不是减小体积的做法。[原文§如何减小 Docker 镜像体积？](https://xiaolincoding.com/interview/docker.html#%E5%A6%82%E4%BD%95%E5%87%8F%E5%B0%8F-docker-%E9%95%9C%E5%83%8F%E4%BD%93%E7%A7%AF)
- **Y2-47** 原文说每条 RUN 都会产生一个新层，用 && 把多个命令合并成一条 RUN 就能减少层数。[原文§如何减小 Docker 镜像体积？](https://xiaolincoding.com/interview/docker.html#%E5%A6%82%E4%BD%95%E5%87%8F%E5%B0%8F-docker-%E9%95%9C%E5%83%8F%E4%BD%93%E7%A7%AF)
- **Y2-48** 原文要求在同一条 RUN 里装完包就立刻清理缓存，例如 RUN apt-get update && apt-get install -y curl && rm -rf /var/lib/apt/lists/*。[原文§如何减小 Docker 镜像体积？](https://xiaolincoding.com/interview/docker.html#%E5%A6%82%E4%BD%95%E5%87%8F%E5%B0%8F-docker-%E9%95%9C%E5%83%8F%E4%BD%93%E7%A7%AF)
- **Y2-49** .dockerignore 像 .gitignore 一样，排除不需要 COPY 进镜像的文件。[原文§如何减小 Docker 镜像体积？](https://xiaolincoding.com/interview/docker.html#%E5%A6%82%E4%BD%95%E5%87%8F%E5%B0%8F-docker-%E9%95%9C%E5%83%8F%E4%BD%93%E7%A7%AF)
- **Y2-50** 原文给出的例子是 node_modules、.git 和日志文件，这些是不需要 COPY 进镜像的文件；运行需要的产物和配置文件当然要进镜像，不属于 .dockerignore 的排除对象。[原文§如何减小 Docker 镜像体积？](https://xiaolincoding.com/interview/docker.html#%E5%A6%82%E4%BD%95%E5%87%8F%E5%B0%8F-docker-%E9%95%9C%E5%83%8F%E4%BD%93%E7%A7%AF)
- **Y2-51** 原文建议避免在镜像里装无关调试工具：调试工具应该在需要时用 docker exec 临时装，不该塞进生产镜像。[原文§如何减小 Docker 镜像体积？](https://xiaolincoding.com/interview/docker.html#%E5%A6%82%E4%BD%95%E5%87%8F%E5%B0%8F-docker-%E9%95%9C%E5%83%8F%E4%BD%93%E7%A7%AF)
- **Y2-52** 选小的基础镜像、在同一条 RUN 里装完包就立刻清理缓存，都是原文列出的手段。预装调试工具会增大镜像，把每个命令单独写成 RUN 会增加层数，都与原文建议相反。[原文§如何减小 Docker 镜像体积？](https://xiaolincoding.com/interview/docker.html#%E5%A6%82%E4%BD%95%E5%87%8F%E5%B0%8F-docker-%E9%95%9C%E5%83%8F%E4%BD%93%E7%A7%AF)
- **Y2-53** 原文列出的常见手段：一、选小的基础镜像，用 alpine（5MB）代替 ubuntu（70MB+），用 openjdk:17-jre-slim 代替 openjdk:17；二、多阶段构建，构建和运行分离，最终镜像只保留运行所需的产物；三、合并 RUN 指令，每条 RUN 都会产生一个新层，用 && 把多个命令合并成一条 RUN 以减少层数；四、清理构建中间产物，在同一条 RUN 里装完包就立刻清理缓存，例如 rm -rf /var/lib/apt/lists/*；五、使用 .dockerignore，像 .gitignore 一样排除不需要 COPY 进镜像的文件，比如 node_modules、.git、日志文件；六、避免在镜像里装无关调试工具，需要时用 docker exec 临时装，不该塞进生产镜像。[原文§如何减小 Docker 镜像体积？](https://xiaolincoding.com/interview/docker.html#%E5%A6%82%E4%BD%95%E5%87%8F%E5%B0%8F-docker-%E9%95%9C%E5%83%8F%E4%BD%93%E7%A7%AF)

### docker commit 和 docker build 有什么区别？

- **Y2-54** docker commit 把正在运行的容器的当前状态打包成镜像，相当于“快照”。根据 Dockerfile 脚本构建的是 docker build。[原文§docker commit 和 docker build 有什么区别？](https://xiaolincoding.com/interview/docker.html#docker-commit-%E5%92%8C-docker-build-%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)
- **Y2-55** docker commit 的过程是手动的、隐式的，镜像里到底发生了什么只有操作者自己知道。可复现、可追溯、可版本控制是 docker build 的特点。[原文§docker commit 和 docker build 有什么区别？](https://xiaolincoding.com/interview/docker.html#docker-commit-%E5%92%8C-docker-build-%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)
- **Y2-56** docker build 根据 Dockerfile 脚本自动构建镜像，过程可复现、可追溯、可版本控制。[原文§docker commit 和 docker build 有什么区别？](https://xiaolincoding.com/interview/docker.html#docker-commit-%E5%92%8C-docker-build-%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)
- **Y2-57** 原文强调生产环境一定要用 docker build。[原文§docker commit 和 docker build 有什么区别？](https://xiaolincoding.com/interview/docker.html#docker-commit-%E5%92%8C-docker-build-%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)
- **Y2-58** 原文给出的理由包括：Dockerfile 可以提交到 Git，方便团队协作和代码审查；构建过程完全自动化，随时可以从代码重新构建出一模一样的镜像。手动、隐式的是 docker commit，它也谈不上可复现。[原文§docker commit 和 docker build 有什么区别？](https://xiaolincoding.com/interview/docker.html#docker-commit-%E5%92%8C-docker-build-%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)
- **Y2-59** docker commit 只在临时调试时用，比如在容器里手动改了点东西想快速保存验证一下。生产发布、团队协作、代码审查都应使用 docker build。[原文§docker commit 和 docker build 有什么区别？](https://xiaolincoding.com/interview/docker.html#docker-commit-%E5%92%8C-docker-build-%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)
- **Y2-60** 原文强调事后还是要把这些改动沉淀回 Dockerfile。[原文§docker commit 和 docker build 有什么区别？](https://xiaolincoding.com/interview/docker.html#docker-commit-%E5%92%8C-docker-build-%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)
- **Y2-61** 2 个空依次是快照、Dockerfile。[原文§docker commit 和 docker build 有什么区别？](https://xiaolincoding.com/interview/docker.html#docker-commit-%E5%92%8C-docker-build-%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)
- **Y2-62** 两者都能得到一个新镜像，但使用场景和推荐度完全不同。docker commit <container> <image> 把一个正在运行的容器的当前状态打包成镜像，相当于“快照”，过程手动、隐式，镜像里到底发生了什么只有操作者自己知道；docker build -f Dockerfile -t <image> . 根据 Dockerfile 脚本自动构建镜像，过程可复现、可追溯、可版本控制。生产环境一定要用 docker build：Dockerfile 可以提交到 Git，方便团队协作和代码审查；构建过程完全自动化，随时可以从代码重新构建出一模一样的镜像。docker commit 只在临时调试时用，比如在容器里手动改了点东西想快速保存验证，事后还是要把这些改动沉淀回 Dockerfile。[原文§docker commit 和 docker build 有什么区别？](https://xiaolincoding.com/interview/docker.html#docker-commit-%E5%92%8C-docker-build-%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)

### Docker 容器数据持久化有哪些方式？

- **Y3-1** 3 个空是 Volume（数据卷）、Bind Mount（目录挂载）、tmpfs（顺序不限）。容器本身是“用完即扔”的，想持久化数据必须用外部存储，Docker 提供的就是这三种方式。[原文§Docker 容器数据持久化有哪些方式？](https://xiaolincoding.com/interview/docker.html#docker-%E5%AE%B9%E5%99%A8%E6%95%B0%E6%8D%AE%E6%8C%81%E4%B9%85%E5%8C%96%E6%9C%89%E5%93%AA%E4%BA%9B%E6%96%B9%E5%BC%8F)
- **Y3-2** Volume（数据卷）由 Docker 管理，是 Docker 官方推荐的方式，原文称它最通用也最推荐。Bind Mount 是把宿主机的任意路径挂进容器，tmpfs 是挂载到宿主机内存，都不是由 Docker 管理的官方推荐方式；容器自身的可写层也不在原文列出的三种持久化方式之内。[原文§Docker 容器数据持久化有哪些方式？](https://xiaolincoding.com/interview/docker.html#docker-%E5%AE%B9%E5%99%A8%E6%95%B0%E6%8D%AE%E6%8C%81%E4%B9%85%E5%8C%96%E6%9C%89%E5%93%AA%E4%BA%9B%E6%96%B9%E5%BC%8F)
- **Y3-3** Volume 默认存储在宿主机的 /var/lib/docker/volumes/ 下。/sys/fs/cgroup/ 是 cgroup 的目录，/var/lib/mysql 是 Compose 示例里 db 服务在容器内的挂载路径，/home/user/code 是 Bind Mount 示例里的宿主机路径，都不是 Volume 的默认存储位置。[原文§Docker 容器数据持久化有哪些方式？](https://xiaolincoding.com/interview/docker.html#docker-%E5%AE%B9%E5%99%A8%E6%95%B0%E6%8D%AE%E6%8C%81%E4%B9%85%E5%8C%96%E6%9C%89%E5%93%AA%E4%BA%9B%E6%96%B9%E5%BC%8F)
- **Y3-4** 原文说 Volume 由 Docker 管理，可以用 docker volume 系列命令管理。其余几项不是原文给出的 Volume 管理命令。[原文§Docker 容器数据持久化有哪些方式？](https://xiaolincoding.com/interview/docker.html#docker-%E5%AE%B9%E5%99%A8%E6%95%B0%E6%8D%AE%E6%8C%81%E4%B9%85%E5%8C%96%E6%9C%89%E5%93%AA%E4%BA%9B%E6%96%B9%E5%BC%8F)
- **Y3-5** 原文把 docker run -v mydata:/app/data myimage 作为 Volume 的示例。以宿主机路径开头的 docker run -v /home/user/code:/app myimage 才是 Bind Mount 的示例；tmpfs 是挂载到宿主机内存；容器自身的可写层不属于原文列出的三种持久化方式。[原文§Docker 容器数据持久化有哪些方式？](https://xiaolincoding.com/interview/docker.html#docker-%E5%AE%B9%E5%99%A8%E6%95%B0%E6%8D%AE%E6%8C%81%E4%B9%85%E5%8C%96%E6%9C%89%E5%93%AA%E4%BA%9B%E6%96%B9%E5%BC%8F)
- **Y3-6** Bind Mount（目录挂载）把宿主机的任意路径直接挂进容器，灵活但耦合宿主机路径。挂载到宿主机内存的是 tmpfs；/var/lib/docker/volumes/ 是 Volume 默认的存储位置；镜像仓库用于存储和分发镜像，不是 Bind Mount 的挂载对象。[原文§Docker 容器数据持久化有哪些方式？](https://xiaolincoding.com/interview/docker.html#docker-%E5%AE%B9%E5%99%A8%E6%95%B0%E6%8D%AE%E6%8C%81%E4%B9%85%E5%8C%96%E6%9C%89%E5%93%AA%E4%BA%9B%E6%96%B9%E5%BC%8F)
- **Y3-7** 正确的是：可以挂载宿主机的任意路径，灵活但耦合宿主机路径、不利于迁移，适合开发阶段的热更新调试。错误的是：位于 /var/lib/docker/volumes/ 下、由 Docker 管理的是 Volume；容器停止后数据就没了的是挂载到内存的 tmpfs。[原文§Docker 容器数据持久化有哪些方式？](https://xiaolincoding.com/interview/docker.html#docker-%E5%AE%B9%E5%99%A8%E6%95%B0%E6%8D%AE%E6%8C%81%E4%B9%85%E5%8C%96%E6%9C%89%E5%93%AA%E4%BA%9B%E6%96%B9%E5%BC%8F)
- **Y3-8** tmpfs 挂载到宿主机内存，容器停止数据就没了。宿主机任意路径对应的是 Bind Mount，/var/lib/docker/volumes/ 是 Volume 的默认存储位置，这两种方式的数据都落在宿主机路径上；“停止后仍保留在内存中”与原文的“数据就没了”相反。[原文§Docker 容器数据持久化有哪些方式？](https://xiaolincoding.com/interview/docker.html#docker-%E5%AE%B9%E5%99%A8%E6%95%B0%E6%8D%AE%E6%8C%81%E4%B9%85%E5%8C%96%E6%9C%89%E5%93%AA%E4%BA%9B%E6%96%B9%E5%BC%8F)
- **Y3-9** tmpfs 挂载在内存里，容器停止数据就没了，所以适合存放敏感临时数据，如解密后的密钥、临时缓存。需要长期保留或跨宿主机迁移的数据不能放在会随容器停止消失的 tmpfs 里；开发阶段热更新调试的源码目录对应的是 Bind Mount。[原文§Docker 容器数据持久化有哪些方式？](https://xiaolincoding.com/interview/docker.html#docker-%E5%AE%B9%E5%99%A8%E6%95%B0%E6%8D%AE%E6%8C%81%E4%B9%85%E5%8C%96%E6%9C%89%E5%93%AA%E4%BA%9B%E6%96%B9%E5%BC%8F)
- **Y3-10** 2 个空依次是 Bind Mount（目录挂载）、Volume（数据卷）。[原文§Docker 容器数据持久化有哪些方式？](https://xiaolincoding.com/interview/docker.html#docker-%E5%AE%B9%E5%99%A8%E6%95%B0%E6%8D%AE%E6%8C%81%E4%B9%85%E5%8C%96%E6%9C%89%E5%93%AA%E4%BA%9B%E6%96%B9%E5%BC%8F)

- **Y3-12** 正确的是：Volume 由 Docker 管理且可用 docker volume 系列命令管理；tmpfs 挂载到内存、适合敏感临时数据；容器“用完即扔”，持久化必须用外部存储；Bind Mount 灵活但耦合宿主机路径。错误的是：官方推荐、最通用的是 Volume 而不是 Bind Mount；生产环境用 Volume 才能保证可移植性，Bind Mount 适合开发阶段热更新调试。[原文§Docker 容器数据持久化有哪些方式？](https://xiaolincoding.com/interview/docker.html#docker-%E5%AE%B9%E5%99%A8%E6%95%B0%E6%8D%AE%E6%8C%81%E4%B9%85%E5%8C%96%E6%9C%89%E5%93%AA%E4%BA%9B%E6%96%B9%E5%BC%8F)

### 如何进入一个运行中的容器？

- **Y4-15** 推荐答案是 docker exec -it <container> bash，即 docker exec。docker attach 是原文不推荐的老办法，docker logs -f 只是实时看日志，docker inspect 只是查看详细信息。[原文§如何进入一个运行中的容器？](https://xiaolincoding.com/interview/docker.html#%E5%A6%82%E4%BD%95%E8%BF%9B%E5%85%A5%E4%B8%80%E4%B8%AA%E8%BF%90%E8%A1%8C%E4%B8%AD%E7%9A%84%E5%AE%B9%E5%99%A8)
- **Y4-16** -i 表示交互式，保留 stdin。分配伪终端（TTY）的是 -t，要在容器里运行的 shell 是 bash / sh 这个位置的参数，后台运行是 docker run 的 -d。[原文§如何进入一个运行中的容器？](https://xiaolincoding.com/interview/docker.html#%E5%A6%82%E4%BD%95%E8%BF%9B%E5%85%A5%E4%B8%80%E4%B8%AA%E8%BF%90%E8%A1%8C%E4%B8%AD%E7%9A%84%E5%AE%B9%E5%99%A8)
- **Y4-17** -t 表示分配一个伪终端（TTY）。保留 stdin 的交互式是 -i，要运行的 shell 是 bash / sh 这个位置的参数，容器停止后自动删除是 docker run 的 --rm。[原文§如何进入一个运行中的容器？](https://xiaolincoding.com/interview/docker.html#%E5%A6%82%E4%BD%95%E8%BF%9B%E5%85%A5%E4%B8%80%E4%B8%AA%E8%BF%90%E8%A1%8C%E4%B8%AD%E7%9A%84%E5%AE%B9%E5%99%A8)
- **Y4-18** 镜像里没有 bash 时，把 bash 换成 sh，即 docker exec -it <container> sh。-d 是后台运行，attach 是原文不推荐的老办法，docker logs -f 只是看日志，原文都不是这样调整。[原文§如何进入一个运行中的容器？](https://xiaolincoding.com/interview/docker.html#%E5%A6%82%E4%BD%95%E8%BF%9B%E5%85%A5%E4%B8%80%E4%B8%AA%E8%BF%90%E8%A1%8C%E4%B8%AD%E7%9A%84%E5%AE%B9%E5%99%A8)
- **Y4-19** 不推荐 docker attach 的原因是：attach 进去后按 Ctrl+C 会直接杀掉容器的主进程，非常容易误操作。其余说法要么是 exec 的特点（并不是 attach 不推荐的原因），要么把两者说反了：更安全、面试里推荐的是 exec，不是 attach。[原文§如何进入一个运行中的容器？](https://xiaolincoding.com/interview/docker.html#%E5%A6%82%E4%BD%95%E8%BF%9B%E5%85%A5%E4%B8%80%E4%B8%AA%E8%BF%90%E8%A1%8C%E4%B8%AD%E7%9A%84%E5%AE%B9%E5%99%A8)
- **Y4-20** docker exec 是在容器里启动一个新的进程，退出时不会影响容器主进程；docker attach 进去后按 Ctrl+C 会直接杀掉容器的主进程。把两者说反、或说成两者一样，都不对。[原文§如何进入一个运行中的容器？](https://xiaolincoding.com/interview/docker.html#%E5%A6%82%E4%BD%95%E8%BF%9B%E5%85%A5%E4%B8%80%E4%B8%AA%E8%BF%90%E8%A1%8C%E4%B8%AD%E7%9A%84%E5%AE%B9%E5%99%A8)
- **Y4-21** 2 个空依次是 exec、attach。推荐 exec，因为它在容器里启动新进程，退出不影响主进程；attach 进去后按 Ctrl+C 会杀掉主进程，不推荐。[原文§如何进入一个运行中的容器？](https://xiaolincoding.com/interview/docker.html#%E5%A6%82%E4%BD%95%E8%BF%9B%E5%85%A5%E4%B8%80%E4%B8%AA%E8%BF%90%E8%A1%8C%E4%B8%AD%E7%9A%84%E5%AE%B9%E5%99%A8)
- **Y4-22** 正确的有三项：exec 是在容器里启动新进程；exec 退出时不会影响主进程；attach 后按 Ctrl+C 会直接杀掉主进程。错误的两项把两者说反了：不推荐、容易误操作的是 attach，面试里的推荐答案和最常用方式是 exec。[原文§如何进入一个运行中的容器？](https://xiaolincoding.com/interview/docker.html#%E5%A6%82%E4%BD%95%E8%BF%9B%E5%85%A5%E4%B8%80%E4%B8%AA%E8%BF%90%E8%A1%8C%E4%B8%AD%E7%9A%84%E5%AE%B9%E5%99%A8)
- **Y4-23** 最常用的方式是 docker exec -it <container> bash；镜像里没有 bash（比如 alpine 只有 sh）时改用 sh。其中 -i 表示交互式（保留 stdin），-t 表示分配一个伪终端（TTY），bash / sh 是要在容器里运行的 shell。另一个老办法是 docker attach，但不推荐：attach 进去后按 Ctrl+C 会直接杀掉容器的主进程，非常容易误操作。docker exec 是在容器里启动一个新的进程，退出时不会影响容器主进程，安全得多，面试里的推荐答案就是 exec。[原文§如何进入一个运行中的容器？](https://xiaolincoding.com/interview/docker.html#%E5%A6%82%E4%BD%95%E8%BF%9B%E5%85%A5%E4%B8%80%E4%B8%AA%E8%BF%90%E8%A1%8C%E4%B8%AD%E7%9A%84%E5%AE%B9%E5%99%A8)

### 容器启动后立刻退出，怎么排查？

- **Y4-24** 原文说“先看日志”：docker logs <container> 或 docker logs --tail 100 <container>，大部分问题从日志就能看出来（依赖缺失、端口冲突、配置错误）。覆盖 ENTRYPOINT 进 shell、检查 OOM、检查前台运行都是后面的排查步骤。[原文§容器启动后立刻退出，怎么排查？](https://xiaolincoding.com/interview/docker.html#%E5%AE%B9%E5%99%A8%E5%90%AF%E5%8A%A8%E5%90%8E%E7%AB%8B%E5%88%BB%E9%80%80%E5%87%BA-%E6%80%8E%E4%B9%88%E6%8E%92%E6%9F%A5)

- **Y4-26** 137 通常是 OOM 被杀（128+9）。0 是正常退出，139 是段错误，其他非 0 退出码就是应用报错。[原文§容器启动后立刻退出，怎么排查？](https://xiaolincoding.com/interview/docker.html#%E5%AE%B9%E5%99%A8%E5%90%AF%E5%8A%A8%E5%90%8E%E7%AB%8B%E5%88%BB%E9%80%80%E5%87%BA-%E6%80%8E%E4%B9%88%E6%8E%92%E6%9F%A5)
- **Y4-27** 其他非 0 的退出码就是应用报错。0 是正常退出，137 通常是 OOM 被杀（128+9），139 是段错误。[原文§容器启动后立刻退出，怎么排查？](https://xiaolincoding.com/interview/docker.html#%E5%AE%B9%E5%99%A8%E5%90%AF%E5%8A%A8%E5%90%8E%E7%AB%8B%E5%88%BB%E9%80%80%E5%87%BA-%E6%80%8E%E4%B9%88%E6%8E%92%E6%9F%A5)
- **Y4-28** 3 个空依次是正常退出、OOM 被杀（128+9）、段错误。每空可接受的说法：0 对应“正常退出”；137 对应“OOM 被杀”（128+9）；139 对应“段错误”。[原文§容器启动后立刻退出，怎么排查？](https://xiaolincoding.com/interview/docker.html#%E5%AE%B9%E5%99%A8%E5%90%AF%E5%8A%A8%E5%90%8E%E7%AB%8B%E5%88%BB%E9%80%80%E5%87%BA-%E6%80%8E%E4%B9%88%E6%8E%92%E6%9F%A5)

- **Y4-31** 原文的做法是 docker run -it --entrypoint sh <image>，临时把 ENTRYPOINT 覆盖成 shell 进去。docker logs、docker inspect、docker ps -a 都是在外面查看信息，不能进入容器的 shell。[原文§容器启动后立刻退出，怎么排查？](https://xiaolincoding.com/interview/docker.html#%E5%AE%B9%E5%99%A8%E5%90%AF%E5%8A%A8%E5%90%8E%E7%AB%8B%E5%88%BB%E9%80%80%E5%87%BA-%E6%80%8E%E4%B9%88%E6%8E%92%E6%9F%A5)

- **Y4-34** 检查资源限制，指的是是否因为 cgroups 内存限制太小被 OOM Killer 杀掉，可用 docker inspect 查看 OOMKilled: true。依赖缺失、端口冲突属于日志里能看出的问题，后台化启动命令属于 PID=1 问题，都是别的排查步骤。[原文§容器启动后立刻退出，怎么排查？](https://xiaolincoding.com/interview/docker.html#%E5%AE%B9%E5%99%A8%E5%90%AF%E5%8A%A8%E5%90%8E%E7%AB%8B%E5%88%BB%E9%80%80%E5%87%BA-%E6%80%8E%E4%B9%88%E6%8E%92%E6%9F%A5)
- **Y4-35** 属于排查做法的有：看日志、用 docker ps -a 看退出码、检查主进程是否前台运行、临时用 --entrypoint 覆盖成 shell 进去调试（原文还有检查 cgroups 内存限制）。docker system df 是查看磁盘占用的命令，不是排查步骤。[原文§容器启动后立刻退出，怎么排查？](https://xiaolincoding.com/interview/docker.html#%E5%AE%B9%E5%99%A8%E5%90%AF%E5%8A%A8%E5%90%8E%E7%AB%8B%E5%88%BB%E9%80%80%E5%87%BA-%E6%80%8E%E4%B9%88%E6%8E%92%E6%9F%A5)
- **Y4-36** 按原文有五步：一是先看日志，docker logs <container> 或 docker logs --tail 100 <container>，大部分问题（依赖缺失、端口冲突、配置错误）从日志就能看出来。二是看退出码，docker ps -a 的 STATUS 列显示 Exited (X)：0 是正常退出，137 通常是 OOM 被杀（128+9），139 是段错误，其他非 0 就是应用报错。三是思考 PID=1 问题：容器里的主进程必须前台运行，如果启动命令是后台化的程序（比如写成 nginx 而不是 nginx -g 'daemon off;'），主进程启动完立刻退出，容器也就结束了。四是临时用 shell 进去调试：docker run -it --entrypoint sh <image> 把 ENTRYPOINT 覆盖成 shell，进去后手动执行原来的启动命令，看看报什么错。五是检查资源限制：是否因为 cgroups 内存限制太小被 OOM Killer 杀掉，docker inspect 能看到 OOMKilled: true。[原文§容器启动后立刻退出，怎么排查？](https://xiaolincoding.com/interview/docker.html#%E5%AE%B9%E5%99%A8%E5%90%AF%E5%8A%A8%E5%90%8E%E7%AB%8B%E5%88%BB%E9%80%80%E5%87%BA-%E6%80%8E%E4%B9%88%E6%8E%92%E6%9F%A5)

### docker run 的常用参数有哪些？

- **Y4-37** -d 表示后台运行（detached）。交互式并分配终端是 -it，容器停止后自动删除是 --rm，以非 root 用户运行是 -u。[原文§docker run 的常用参数有哪些？](https://xiaolincoding.com/interview/docker.html#docker-run-%E7%9A%84%E5%B8%B8%E7%94%A8%E5%8F%82%E6%95%B0%E6%9C%89%E5%93%AA%E4%BA%9B)

- **Y4-42** --rm 表示容器停止后自动删除，适合一次性任务。自动重启策略是 --restart，后台运行是 -d，以非 root 用户运行是 -u。[原文§docker run 的常用参数有哪些？](https://xiaolincoding.com/interview/docker.html#docker-run-%E7%9A%84%E5%B8%B8%E7%94%A8%E5%8F%82%E6%95%B0%E6%9C%89%E5%93%AA%E4%BA%9B)

- **Y4-44** 2 个空是 always 和 unless-stopped（顺序不限）。[原文§docker run 的常用参数有哪些？](https://xiaolincoding.com/interview/docker.html#docker-run-%E7%9A%84%E5%B8%B8%E7%94%A8%E5%8F%82%E6%95%B0%E6%9C%89%E5%93%AA%E4%BA%9B)
- **Y4-45** -m 512m --cpus=1 是内存和 CPU 的资源限制。名称和网络是 --name 和 --network，端口映射和挂载是 -p 和 -v，环境变量和重启策略是 -e 和 --restart。[原文§docker run 的常用参数有哪些？](https://xiaolincoding.com/interview/docker.html#docker-run-%E7%9A%84%E5%B8%B8%E7%94%A8%E5%8F%82%E6%95%B0%E6%9C%89%E5%93%AA%E4%BA%9B)
- **Y4-46** -u 1000:1000 表示以非 root 用户运行。内存和 CPU 限制是 -m 和 --cpus，环境变量是 -e，端口映射是 -p。[原文§docker run 的常用参数有哪些？](https://xiaolincoding.com/interview/docker.html#docker-run-%E7%9A%84%E5%B8%B8%E7%94%A8%E5%8F%82%E6%95%B0%E6%9C%89%E5%93%AA%E4%BA%9B)
- **Y4-47** 原文的典型生产启动命令用到了 -d 后台运行、--restart unless-stopped、--network mynet、-m 1g --cpus=2（还有 --name、-p、-v、-e）。命令里没有 --entrypoint sh 和 -u 1000:1000。[原文§docker run 的常用参数有哪些？](https://xiaolincoding.com/interview/docker.html#docker-run-%E7%9A%84%E5%B8%B8%E7%94%A8%E5%8F%82%E6%95%B0%E6%9C%89%E5%93%AA%E4%BA%9B)
- **Y4-48** 正确的是 -d 后台运行、--rm 容器停止后自动删除、-e 设置环境变量。-u 1000:1000 是以非 root 用户运行，不是 root；-it 是交互式加分配终端，容器停止后自动删除的是 --rm。[原文§docker run 的常用参数有哪些？](https://xiaolincoding.com/interview/docker.html#docker-run-%E7%9A%84%E5%B8%B8%E7%94%A8%E5%8F%82%E6%95%B0%E6%9C%89%E5%93%AA%E4%BA%9B)
- **Y4-49** 常用参数：-d 后台运行（detached）；-it 交互式加分配终端，通常一起用；-p 8080:80 端口映射（宿主机:容器）；-v /host:/container 或 -v volname:/container 目录或数据卷挂载；--name web 给容器起名字；--network mynet 指定容器网络；-e KEY=VALUE 设置环境变量；--rm 容器停止后自动删除，适合一次性任务；--restart always / unless-stopped 自动重启策略；-m 512m --cpus=1 内存和 CPU 资源限制；-u 1000:1000 以非 root 用户运行。典型生产启动命令是 docker run -d --name myapp -p 8080:8080 -v mydata:/app/data -e SPRING_PROFILES_ACTIVE=prod --restart unless-stopped --network mynet -m 1g --cpus=2 myapp:1.0.0，即后台运行、命名、映射端口、挂载数据卷、传环境变量、设置重启策略、指定网络、限制内存和 CPU。[原文§docker run 的常用参数有哪些？](https://xiaolincoding.com/interview/docker.html#docker-run-%E7%9A%84%E5%B8%B8%E7%94%A8%E5%8F%82%E6%95%B0%E6%9C%89%E5%93%AA%E4%BA%9B)

### 如何清理 Docker 的无用镜像、容器和卷？

- **Y4-50** 原文说主要是悬空镜像（dangling images）、停止的容器、没人用的卷堆积。其余几组都改动了其中一项：运行中的容器、正在使用的卷不是“无用”资源，没被任何容器使用的所有镜像要加 -a 才会清理，也不是原文列的堆积物。[原文§如何清理 Docker 的无用镜像、容器和卷？](https://xiaolincoding.com/interview/docker.html#%E5%A6%82%E4%BD%95%E6%B8%85%E7%90%86-docker-%E7%9A%84%E6%97%A0%E7%94%A8%E9%95%9C%E5%83%8F%E3%80%81%E5%AE%B9%E5%99%A8%E5%92%8C%E5%8D%B7)
- **Y4-51** docker container prune 清理停止的容器。悬空镜像由 docker image prune 清理，无用的卷由 docker volume prune 清理，无用的网络由 docker network prune 清理。[原文§如何清理 Docker 的无用镜像、容器和卷？](https://xiaolincoding.com/interview/docker.html#%E5%A6%82%E4%BD%95%E6%B8%85%E7%90%86-docker-%E7%9A%84%E6%97%A0%E7%94%A8%E9%95%9C%E5%83%8F%E3%80%81%E5%AE%B9%E5%99%A8%E5%92%8C%E5%8D%B7)
- **Y4-52** docker image prune 清理悬空镜像。清理所有没被任何容器使用的镜像要加 -a，停止的容器、没人用的卷、无用的网络分别由 container prune、volume prune、network prune 清理。[原文§如何清理 Docker 的无用镜像、容器和卷？](https://xiaolincoding.com/interview/docker.html#%E5%A6%82%E4%BD%95%E6%B8%85%E7%90%86-docker-%E7%9A%84%E6%97%A0%E7%94%A8%E9%95%9C%E5%83%8F%E3%80%81%E5%AE%B9%E5%99%A8%E5%92%8C%E5%8D%B7)
- **Y4-53** 加上 -a 会清理所有无用镜像，包括没被任何容器使用的镜像。停止的容器、无用的网络、没人用的卷是别的 prune 子命令清理的对象；正在被容器使用的镜像不是无用镜像，不会被清理。[原文§如何清理 Docker 的无用镜像、容器和卷？](https://xiaolincoding.com/interview/docker.html#%E5%A6%82%E4%BD%95%E6%B8%85%E7%90%86-docker-%E7%9A%84%E6%97%A0%E7%94%A8%E9%95%9C%E5%83%8F%E3%80%81%E5%AE%B9%E5%99%A8%E5%92%8C%E5%8D%B7)
- **Y4-54** 2 个空依次是 volume、network，即 docker volume prune 和 docker network prune。[原文§如何清理 Docker 的无用镜像、容器和卷？](https://xiaolincoding.com/interview/docker.html#%E5%A6%82%E4%BD%95%E6%B8%85%E7%90%86-docker-%E7%9A%84%E6%97%A0%E7%94%A8%E9%95%9C%E5%83%8F%E3%80%81%E5%AE%B9%E5%99%A8%E5%92%8C%E5%8D%B7)
- **Y4-55** 不加选项的 docker system prune 清理停止容器、悬空镜像、无用网络。无用的卷要再加 --volumes 才会清理，没被使用的所有镜像要加 -a。[原文§如何清理 Docker 的无用镜像、容器和卷？](https://xiaolincoding.com/interview/docker.html#%E5%A6%82%E4%BD%95%E6%B8%85%E7%90%86-docker-%E7%9A%84%E6%97%A0%E7%94%A8%E9%95%9C%E5%83%8F%E3%80%81%E5%AE%B9%E5%99%A8%E5%92%8C%E5%8D%B7)
- **Y4-56** 加 -a 顺带清理没被使用的所有镜像。无用卷要再加 --volumes，无用网络和停止的容器本来就在不带 -a 的清理范围里。[原文§如何清理 Docker 的无用镜像、容器和卷？](https://xiaolincoding.com/interview/docker.html#%E5%A6%82%E4%BD%95%E6%B8%85%E7%90%86-docker-%E7%9A%84%E6%97%A0%E7%94%A8%E9%95%9C%E5%83%8F%E3%80%81%E5%AE%B9%E5%99%A8%E5%92%8C%E5%8D%B7)
- **Y4-57** 再加 --volumes 就会顺带清理无用的卷，即 docker system prune -a --volumes。--tail 100 是 docker logs 的参数，--restart always 和 --network mynet 是 docker run 的参数，都和清理无关。[原文§如何清理 Docker 的无用镜像、容器和卷？](https://xiaolincoding.com/interview/docker.html#%E5%A6%82%E4%BD%95%E6%B8%85%E7%90%86-docker-%E7%9A%84%E6%97%A0%E7%94%A8%E9%95%9C%E5%83%8F%E3%80%81%E5%AE%B9%E5%99%A8%E5%92%8C%E5%8D%B7)
- **Y4-58** 清理前可以先用 docker system df 查看占用分布。docker stats 看容器资源占用，docker images 只列出本地镜像，docker inspect 看单个容器的详细信息。[原文§如何清理 Docker 的无用镜像、容器和卷？](https://xiaolincoding.com/interview/docker.html#%E5%A6%82%E4%BD%95%E6%B8%85%E7%90%86-docker-%E7%9A%84%E6%97%A0%E7%94%A8%E9%95%9C%E5%83%8F%E3%80%81%E5%AE%B9%E5%99%A8%E5%92%8C%E5%8D%B7)
- **Y4-59** 原文的目的是避免磁盘爆满导致容器无法启动。OOM Killer 杀容器是内存限制问题，构建缓存和主进程前台运行也不是定期清理要解决的问题。[原文§如何清理 Docker 的无用镜像、容器和卷？](https://xiaolincoding.com/interview/docker.html#%E5%A6%82%E4%BD%95%E6%B8%85%E7%90%86-docker-%E7%9A%84%E6%97%A0%E7%94%A8%E9%95%9C%E5%83%8F%E3%80%81%E5%AE%B9%E5%99%A8%E5%92%8C%E5%8D%B7)
- **Y4-60** 正确的是 container prune 清理停止的容器、image prune -a 清理所有没被任何容器使用的镜像、image prune 清理悬空镜像。volume prune 清理的是卷，network prune 清理的是网络，这两项把对象说反了。[原文§如何清理 Docker 的无用镜像、容器和卷？](https://xiaolincoding.com/interview/docker.html#%E5%A6%82%E4%BD%95%E6%B8%85%E7%90%86-docker-%E7%9A%84%E6%97%A0%E7%94%A8%E9%95%9C%E5%83%8F%E3%80%81%E5%AE%B9%E5%99%A8%E5%92%8C%E5%8D%B7)
- **Y4-61** 磁盘占用变大主要是悬空镜像（dangling images）、停止的容器、没人用的卷堆积。分类清理：docker container prune 清理停止的容器，docker image prune 清理悬空镜像，docker image prune -a 清理所有无用镜像（包括没被任何容器使用的），docker volume prune 清理无用的卷，docker network prune 清理无用的网络。一键清理最常用的是 docker system prune，清理停止容器、悬空镜像、无用网络；加 -a 顺带清理没被使用的所有镜像；再加 --volumes 顺带清理无用卷。清理前可以先用 docker system df 查看占用分布。生产环境建议在 CI/CD 流水线或定时任务里定期执行清理，避免磁盘爆满导致容器无法启动。[原文§如何清理 Docker 的无用镜像、容器和卷？](https://xiaolincoding.com/interview/docker.html#%E5%A6%82%E4%BD%95%E6%B8%85%E7%90%86-docker-%E7%9A%84%E6%97%A0%E7%94%A8%E9%95%9C%E5%83%8F%E3%80%81%E5%AE%B9%E5%99%A8%E5%92%8C%E5%8D%B7)
