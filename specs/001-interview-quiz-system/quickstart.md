# Quickstart: 面试题答题系统 1.0

**Date**: 2026-10-13 | **Plan**: [plan.md](plan.md)

这是一份验证指南：怎样把系统跑起来，以及用哪些场景证明它按规格工作。命令在实现阶段搭好脚手架后生效；届时如有出入，以仓库根目录 `CLAUDE.md` 为准。

## 前置条件

- Node.js 24、npm
- Docker（本地 PostgreSQL）
- 仓库里已有 `interview-practice/` 题库

## 本地运行

```powershell
npm install
Copy-Item .env.example .env        # 本地默认 GRADER=fake，不需要 DeepSeek 密钥
docker compose up -d db            # 启动本地 PostgreSQL
npm run db:migrate                 # 建表
npm run content:build              # 解析题库、合并题目、校验，生成 content/dist/bank.json
npm run dev                        # http://localhost:3000
```

环境变量：

| 变量 | 说明 | 本地默认 |
| --- | --- | --- |
| `DATABASE_URL` | PostgreSQL 连接串 | 指向 docker compose 的库 |
| `GRADER` | `deepseek` 或 `fake` | `fake` |
| `DEEPSEEK_API_KEY` | `GRADER=deepseek` 时必填 | 空 |
| `DEEPSEEK_MODEL` | 评分模型 | `deepseek-flash` |
| `GRADING_DAILY_CAP` | 全站每日评分次数上限 | `5000` |
| `CONTENT_REQUIRE_ALL` | 设为 `1` 时要求全部章节已通过抽查 | 不设 |

## 自动化检查

```powershell
npm run typecheck
npm run lint
npm run content:validate           # 只校验内容，不生成文件
npm test                           # 单元测试加集成测试（需要本地 PostgreSQL 在运行）
npm run e2e                        # 端到端冒烟流程
```

预期：全部通过。`content:validate` 在设置 `CONTENT_REQUIRE_ALL=1` 后，只有 161 章全部为 `approved` 才通过。

## 验证场景

以下场景用假评分器即可完成。简答题里以“【对】”开头的答案判对，以“【错】”开头的判错，以“【失败】”开头的模拟评分失败（见 [contracts/grading.md](contracts/grading.md)）。

### 场景 1：做一章并看结果（User Story 1）

1. 注册并登录，进入做题模式，选一个同时含三种题型的章节。
2. 答题过程中打开浏览器的网络面板，查看取题接口的响应。
   **预期**：响应里没有正确答案、参考答案、引用和判定。
3. 单选题故意选错一道，多选题故意少选一项，简答题一道写“【对】……”、一道写“【错】……”，留一道不答。
4. 交卷。
   **预期**：提示还有 1 道未答，确认后才交卷。
5. 查看结果页。
   **预期**：正确率 = 判对题数 ÷ 本章总题数；少选的多选题判错；每道题有用户答案、正确答案、解答全文和原文链接；选择题标出各选项对错；“只看错题”只留下判错的题。

### 场景 2：进度与续做（User Story 2）

1. 开始另一章，答 3 道题后停在第 4 题，关闭页面并退出登录。
2. 重新登录，打开该章。
   **预期**：章节列表显示“进行中”；进入后 3 道题的答案都在，停在第 4 题。
3. 交卷后回到章节列表。
   **预期**：显示“已完成”和最近一次、最高正确率；专题的已完成章节数加一。
4. 重做该章并交卷，成绩不同于第一次。
   **预期**：最近一次正确率变化，最高正确率取两次中较高的；第一次的结果没有被覆盖。
5. 用第二个账号登录。
   **预期**：所有章节都是“未开始”；用第一个账号的作答地址直接访问得到“不存在”。

### 场景 3：错题与错误次数（User Story 3）

1. 沿用场景 1 的账号，打开该章的错题。
   **预期**：只有判错的题，每道错误次数为 1；未答的那道不在其中。
2. 重做该章：其中一道错题再次答错，另一道答对。
   **预期**：前者错误次数为 2；后者错误次数仍为 1，显示最近一次为“答对”，仍在列表里。
3. 按错误次数排序，并展开一道题。
   **预期**：错得最多的排在前面；展开后有题目、正确答案和解答。
4. 打开错题总览。
   **预期**：按专题和章节列出错题数量，与各章错题列表一致。

### 场景 4：错题本（User Story 4）

1. 新账号直接打开错题本。
   **预期**：显示如何添加题目的引导，不能开始练习。
2. 在结果页把一道答对的题和一道答错的题加入错题本；对其中一道再点一次添加。
   **预期**：错题本里共 2 道题，没有重复；这两道题在结果页和错题列表里都标为“已在错题本”。
3. 开始错题本练习，开始后再往错题本里加第 3 道题。
   **预期**：正在进行的练习仍是 2 道题。
4. 练习中答错一道并交卷。
   **预期**：结果页形式与章节作答一致；该题错误次数加一。
5. 从错题本移除一道题。
   **预期**：错题本少一道；该题在每章错题里的错误次数不变。

### 场景 5：模式入口（User Story 5）

1. 登录后查看首页。
   **预期**：有“做题模式”和“对战模式”两个入口。
2. 进入对战模式。
   **预期**：只看到尚未开放的说明和返回做题模式的途径。

### 场景 6：评分暂时不可用（FR-027）

1. 做一章，其中一道简答题写“【失败】……”，其余正常作答后交卷。
   **预期**：结果页立即显示，其余题目的结果和正确率正常；那道题显示“待评分”。
2. 等待超过一分钟后刷新。
   **预期**：仍为“待评分”（假评分器会持续失败），页面没有报错。数据库里该题的尝试次数在增加。

### 场景 7：限流与并发（FR-041、边界情况）

1. 10 分钟内连续交卷第 11 次。
   **预期**：提示稍后再试，这次作答仍是进行中。
2. 在两个浏览器里打开同一份进行中的作答，一边交卷后在另一边继续保存答案。
   **预期**：保存被拒绝，页面提示这次作答已经交卷。

### 场景 8：内容校验（FR-045、原则 III）

1. 在 `content/typed/` 里把某道单选题改成有两个正确选项，运行 `npm run content:validate`。
   **预期**：失败，并指出题号和违反的规则。
2. 把某个章节的状态改回 `draft`，运行 `npm run content:build` 并启动应用。
   **预期**：该章不出现在章节列表里。
3. 设置 `CONTENT_REQUIRE_ALL=1` 后再运行 `npm run content:build`。
   **预期**：失败，并列出不是 `approved` 的章节。

## 上线前的人工检查

这些无法自动化，上线前逐项完成。

| 检查 | 方法 | 标准 |
| --- | --- | --- |
| 题目质量 | 按 [contracts/content-format.md](contracts/content-format.md) 的抽查方式逐专题进行 | SC-008：抽查的选择题至少 95% 合格 |
| 评分一致性 | `GRADER=deepseek` 下运行 `npm run eval:grading` | SC-009：与人工判定的一致率不低于 90% |
| 长章节 | 用最长的一章（L2，71 题）完整走一遍场景 1，包括手机宽度 | 题目概览和跳题可用，交卷后 3 秒内出结果 |
| 真实评分耗时 | `GRADER=deepseek` 下做一章含 10 道以上简答题的章节 | SC-004：95% 的简答题在 30 秒内评出 |

## 部署到 Railway

1. 新建项目，添加 PostgreSQL 数据库，再从仓库添加应用服务。
2. 在应用服务的变量里引用数据库的 `DATABASE_URL`，并设置 `GRADER=deepseek`、`DEEPSEEK_API_KEY`、`CONTENT_REQUIRE_ALL=1`。
3. 预部署命令设为 `npm run db:migrate`，健康检查路径设为 `/api/health`。
4. 部署完成后，在线上重做场景 1 和场景 5，并确认 `/api/health` 返回正常。
