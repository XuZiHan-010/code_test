# Research: 面试题答题系统 1.0

**Date**: 2026-10-13 | **Spec**: [spec.md](spec.md)

规格和 PRD 里留下的技术未知项在这里逐个定下来。标“已核对”的事实在 2026-10-13 查过官方文档。

## 1. 应用形态与框架

- **Decision**: 一个 Next.js 全栈应用（App Router，TypeScript），前后端同一个服务。版本在搭脚手架时锁定为当时的稳定版（已核对：官方文档当前为 16.4）。运行时用 Node.js 24 LTS，包管理用 npm。
- **Rationale**: 规格要的是带登录的多页面网站加少量交互接口，一个服务就够。读页面由服务端直接渲染，不需要另写一套读接口；部署到 Railway 只有一个服务加一个数据库。本机已装 Node 24 和 npm。
- **Alternatives considered**:
  - 前端单页应用加独立后端服务：两个服务、两套构建、跨域和鉴权要多处理一遍，对这个规模没有收益。
  - Python 后端加模板渲染：答题页需要较多前端交互（跳题、自动保存、轮询评分结果），最终还是要引入一套前端构建。

## 2. 数据库与数据访问

- **Decision**: PostgreSQL（Railway 提供）。用 Drizzle ORM 加 drizzle-kit 生成 SQL 迁移文件，驱动用 node-postgres。
- **Rationale**: 用户记录是典型的关系数据，需要事务（交卷时同时更新作答和题目统计）、唯一约束（一个范围只有一份进行中的作答）和行锁（评分任务领取）。Drizzle 的迁移是可读的 SQL 文件，便于审查。
- **Alternatives considered**:
  - Prisma：功能相当，但多一个生成步骤和查询引擎，部分索引和行锁语句仍要写原生 SQL。
  - SQLite 文件库：Railway 上要挂卷，且评分任务的并发领取不如 PostgreSQL 直接。

## 3. 题目内容放在哪里

- **Decision**: 题目内容不进数据库。`interview-practice/` 的 Markdown 仍是知识点的唯一来源；题型、题干改写和选项另存为按专题划分的 JSON 文件（`content/typed/`）。构建时由脚本把两者合并、校验，生成一份 `content/dist/bank.json`，应用启动时读入内存。数据库只通过题号和章节编号引用题目。
- **Rationale**: 内容对所有用户相同、只在发布时变化，放内存查询最简单。校验挂在构建上，不合格的内容会让构建失败，从机制上保证“先校验后发布”（原则 III）。更新内容只需重新部署，不需要数据迁移（原则 II）。合并后的数据约几 MB，内存开销可以忽略。
- **Alternatives considered**:
  - 题目入库：每次内容更新都要写导入和迁移，还要处理库内内容与仓库内容不一致的情况。
  - 生成的 JSON 里重复存一份参考答案：同一内容两处维护，容易不一致。

## 4. 发布前检查与抽查怎么落实

- **Decision**: `content/typed/` 里每个章节带一个状态：`draft` 或 `approved`。只有 `approved` 的章节进入 `bank.json`。生成后先是 `draft`，人工抽查通过后改为 `approved`。生产构建设置 `CONTENT_REQUIRE_ALL=1`，此时只要有一章不是 `approved` 构建就失败。被删除的题号记入 `content/retired-ids.json`，校验器拒绝再次使用。本地开发可以设 `CONTENT_INCLUDE_DRAFTS=1` 把 `draft` 章节也放进数据，以便在抽查完成前开发页面；构建脚本拒绝在生产环境或与 `CONTENT_REQUIRE_ALL` 同时使用它。
- **Rationale**: FR-045 要求未通过检查的题目不得出现在网站上；章节级状态是能满足它的最小机制。`CONTENT_REQUIRE_ALL` 对应 SC-001（上线时 161 章全部可做），开发期间则允许只带部分章节运行。
- **Alternatives considered**:
  - 只靠口头约定“抽查后再发布”：没有任何东西阻止未抽查的章节上线。
  - 逐题审批：3122 题逐个标记，工作量与抽查的定位不符。

## 5. 3122 个知识点怎么转成三种题型

- **Decision**: 做一个项目内的 Claude Code skill（`.claude/skills/generate-questions/`），在开发会话里按章运行：读入一章的题干和参考答案，按规格 FR-002 判断题型，为选择题写题干和选项，写入 `content/typed/`，然后运行校验器。先用最小的专题（AI 编程，65 题）跑通并抽查，再铺开。
- **Rationale**: 这是一次性的离线内容工作，放在开发会话里做不需要额外的运行时设施，也自然带上人工审阅这一环。按章生成可以单独重跑。
- **Alternatives considered**:
  - 写脚本批量调用大模型接口：可重复，但要另外维护提示词、并发和失败重试，而且这套东西 1.0 的网站运行时并不需要（原则 VI）。等以后做用户专属题库时再建。

## 6. 简答题评分

- **Decision**: 调用 DeepSeek 的接口评分。已核对：接口与 OpenAI 格式兼容，基础地址 `https://api.deepseek.com`，官方示例使用 OpenAI SDK；当前模型为 `deepseek-flash` 和 `deepseek-v4-pro`。默认用 `deepseek-flash`，模型名通过环境变量配置。启用 JSON 输出（`response_format: {type: "json_object"}`），温度设为 0。评分器藏在一个接口后面，另有一个按固定规则返回结果的假评分器，供开发和测试使用。
- **Rationale**: 用户已确认使用 DeepSeek。判对错加一两句评语是简单任务，用较便宜的模型即可；JSON 输出便于解析。官方文档提示 JSON 模式偶尔会返回空内容，且提示词里必须出现“json”字样并给出示例，所以空内容和解析失败都按失败处理并重试。
- **Alternatives considered**:
  - 用 `deepseek-v4-pro`：更贵更慢，这类判定任务没有必要；保留为配置项，评分一致性不达标（SC-009）时再切换。
  - 直接用 `fetch` 调接口：少一个依赖，但超时、重试和错误分类都要自己写。

## 7. 评分在哪里执行

- **Decision**: 交卷请求只判选择题并立即返回；简答题先记为“待评分”。评分由应用进程内的一个执行器完成：交卷响应发出后立即触发（Next.js 的 `after`，已核对：稳定可用，Node 服务器部署受支持），另有一个定时器每分钟扫一次仍待评分的记录，用于重试失败项和进程重启后的恢复。执行器用 `FOR UPDATE SKIP LOCKED` 领取记录，限制并发数。结果页对“待评分”的题轮询。
- **Rationale**: 满足 SC-003（交卷后 3 秒内看到选择题结果）和 FR-027（评分不可用时其余结果照常显示、稍后补评）。数据库里的“待评分”状态本身就是任务队列，不需要引入额外的队列组件或单独的后台服务。行锁保证即使以后有多个实例也不会重复评分。
- **Alternatives considered**:
  - 在交卷请求里同步评完所有简答题：一章可能有几十道简答题，请求会持续几十秒，任何一次失败都会拖垮整个交卷。
  - 单独的后台服务加消息队列：多一个服务和一个组件，对几十人规模没有必要（原则 VI）。

## 8. 账号与会话

- **Decision**: 自己实现用户名加密码登录。密码用 argon2id 哈希。会话用服务端会话表加不透明的随机令牌：令牌放在 HttpOnly、SameSite=Lax 的 Cookie 里（生产环境加 Secure），数据库只存令牌的 SHA-256。有效期 30 天，剩余不足 15 天时访问即顺延。所有修改数据的接口校验请求来源（Origin）。
- **Rationale**: 需求只有用户名加密码，没有邮箱和第三方登录，通用认证库的大部分功能用不上，而“仅用户名”反而不是它们的常规路径。这套做法是成熟的标准模式，代码量小，可以完整测试。满足 FR-010 至 FR-013。
- **Alternatives considered**:
  - 认证库（如 Auth.js、better-auth）：引入的配置和概念多于需求本身。
  - 无状态的 JWT：不能在服务端使单个会话失效，退出登录要额外处理。

## 9. 使用限制与费用保护

- **Decision**:
  - 交卷：每个用户 10 分钟内最多 10 次，超出返回“稍后再试”（FR-041）。直接按作答表里的交卷时间统计，不另建表。
  - 简答题答案最长 2000 字，输入时即限制。
  - 全站每日评分次数上限，通过环境变量配置（默认 5000）。超出后新的简答题保持“待评分”，次日自动补评。
  - 登录和注册：按来源地址在进程内限流（登录 10 次 / 10 分钟，注册 5 次 / 小时）。
- **Rationale**: 评分用的是站点自己的密钥，而注册是开放的，没有上限就等于把费用敞口交给任何人。每日上限是最后一道保险，超出时的表现正好复用已有的“待评分”路径，不需要新的界面状态。
- **Alternatives considered**:
  - 只做每用户限流：挡不住批量注册账号。
  - 引入独立的限流组件：单实例部署下进程内计数和数据库统计已经够用。

## 10. 测试

- **Decision**: Vitest 跑单元测试和集成测试。集成测试连本地 Docker 里的真实 PostgreSQL（`docker compose` 启动），每次运行先执行迁移，测试之间清空表。另用 Playwright 写一条端到端冒烟流程（注册、做一章、交卷、看结果、加错题本），评分走假评分器。评分一致性（SC-009）用一组人工标注的样例手动评测，不进自动化测试。
- **Rationale**: 原则 V 要求数据存取规则对真实数据库测试；本机已装 Docker。对真实大模型的调用不稳定且有费用，不适合进自动化测试。
- **Alternatives considered**:
  - 进程内的 PostgreSQL 仿真：不是同一个服务端实现，行锁和部分索引的行为可能不同。
  - 模拟数据库：原则 V 明确禁止。

## 11. 部署

- **Decision**: Railway 上一个应用服务加一个 PostgreSQL。已核对：Railway 用 Railpack 自动构建 Node 项目并读取 `package.json` 的 `start` 脚本；数据库的 `DATABASE_URL` 通过引用变量提供给应用；迁移放在预部署命令里，它在构建之后、部署之前运行，失败则部署不继续。启动命令用 `next start`。提供 `/api/health` 作为健康检查。单实例运行。
- **Rationale**: 全部是 Railway 的默认路径，不需要自己写 Dockerfile。迁移失败会阻止部署，避免代码和表结构不一致。
- **实现时的调整（2026-10-13）**: 最初打算按 Railway 的 Next.js 指南使用 `output: "standalone"` 和 `node .next/standalone/server.js`。实现时改为普通的 `next start`：standalone 模式要另外把静态资源和 `content/dist/bank.json` 复制进输出目录，迁移脚本依赖的文件也不在其中，而这个项目并不需要它带来的镜像体积优化。部署时如果 `next start` 在 Railway 上有问题，再回到 standalone 并补上复制步骤。
- **Alternatives considered**:
  - 自写 Dockerfile：可控性更高，但现在没有默认构建满足不了的需求。
  - 应用启动时自动迁移：多实例时会并发执行，且失败时服务已经在接流量。

## 12. 界面

- **Decision**: Tailwind CSS，不引入组件库。界面为简体中文，按手机宽度优先设计。
- **Rationale**: 页面数量少（约十个），交互集中在答题页，自己写的组件足够。
- **Alternatives considered**: 引入完整组件库：体积和学习成本高于这几个页面的需要。
