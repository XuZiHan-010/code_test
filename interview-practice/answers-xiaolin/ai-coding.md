## 1. 大型仓库中的代码定位

原文：[1. Coding Agent 如何在大型代码仓库中定位相关代码？](https://xiaolinnote.com/ai/coding/1_code_localization.html)。

- **P1-1** 先缩小搜索范围，再沿代码关系补齐上下文：需求里的业务描述和源码命名不一定一致，要结合目录结构，把接口路径、报错文本、日志、字段名或堆栈转成可搜索的线索；命中后读取完整函数和相关类型，用跳转定义、查找引用确认符号，再看调用方、被调用方以及数据读写和事件传递关系，并核对配置和注册代码。[原文§💡 简要回答](https://xiaolinnote.com/ai/coding/1_code_localization.html#%F0%9F%92%A1-%E7%AE%80%E8%A6%81%E5%9B%9E%E7%AD%94)
- **P1-2** 仓库变大后同一个需求可能涉及接口层、业务层、数据访问层，还可能通过消息交给另一个服务；搜一个业务词可能找到几十个文件，里面有类型定义、测试数据、旧接口和正在使用的逻辑，文件与问题有关不代表其中的代码都要改。定位要回答两个问题：哪段代码承担当前要找的职责，哪些代码关系会影响这段实现。[原文§为什么命中了文件，还不一定找到了相关实现？](https://xiaolinnote.com/ai/coding/1_code_localization.html#%E4%B8%BA%E4%BB%80%E4%B9%88%E5%91%BD%E4%B8%AD%E4%BA%86%E6%96%87%E4%BB%B6-%E8%BF%98%E4%B8%8D%E4%B8%80%E5%AE%9A%E6%89%BE%E5%88%B0%E4%BA%86%E7%9B%B8%E5%85%B3%E5%AE%9E%E7%8E%B0)
- **P1-3** 通常是一组有关系的代码位置：关键函数、必要的类型或配置，以及与任务相关的调用方。例如调整字段的计算方式，只读计算函数可能漏掉调用方对空值的约定，只搜字段名又可能把只负责展示的代码误认为计算入口。[原文§为什么命中了文件，还不一定找到了相关实现？](https://xiaolinnote.com/ai/coding/1_code_localization.html#%E4%B8%BA%E4%BB%80%E4%B9%88%E5%91%BD%E4%B8%AD%E4%BA%86%E6%96%87%E4%BB%B6-%E8%BF%98%E4%B8%8D%E4%B8%80%E5%AE%9A%E6%89%BE%E5%88%B0%E4%BA%86%E7%9B%B8%E5%85%B3%E5%AE%9E%E7%8E%B0)
- **P1-4** 搜索和阅读要对应同一份代码版本：排查的是线上故障却读了已经改过的主分支，实现可能已不同；使用预建索引时要确认索引对应的提交，并回到当前源码核验候选；工作区里未提交的修改同样会影响实际内容。[原文§为什么命中了文件，还不一定找到了相关实现？](https://xiaolinnote.com/ai/coding/1_code_localization.html#%E4%B8%BA%E4%BB%80%E4%B9%88%E5%91%BD%E4%B8%AD%E4%BA%86%E6%96%87%E4%BB%B6-%E8%BF%98%E4%B8%8D%E4%B8%80%E5%AE%9A%E6%89%BE%E5%88%B0%E4%BA%86%E7%9B%B8%E5%85%B3%E5%AE%9E%E7%8E%B0)
- **P1-5** 源码里未必出现需求里的描述，例如“重复提交校验”可能被命名为 checkIdempotency，或放在公共中间件里，直接搜整句容易找不到，不断换同义词也只是在猜名字；更有效的是找需求与源码共有的标识：接口路径、错误码、日志字符串、堆栈中的函数名，以及页面字段、数据库列名、事件名，这些能在仓库里查找的标识就是搜索锚点。[原文§如何把需求转成可以搜索的线索？](https://xiaolinnote.com/ai/coding/1_code_localization.html#%E5%A6%82%E4%BD%95%E6%8A%8A%E9%9C%80%E6%B1%82%E8%BD%AC%E6%88%90%E5%8F%AF%E4%BB%A5%E6%90%9C%E7%B4%A2%E7%9A%84%E7%BA%BF%E7%B4%A2)
- **P1-6** 先读顶层目录、构建配置和模块入口，了解服务与模块怎样划分，目录名帮助选出候选范围，入口代码再确认职责；已有准确的文件路径或堆栈时可以直接从对应位置展开。初次搜索优先看项目源码，减少依赖目录、构建产物和生成文件的干扰，但堆栈指向某个依赖或关键接口由生成代码提供时，就要继续读那里。[原文§如何把需求转成可以搜索的线索？](https://xiaolinnote.com/ai/coding/1_code_localization.html#%E5%A6%82%E4%BD%95%E6%8A%8A%E9%9C%80%E6%B1%82%E8%BD%AC%E6%88%90%E5%8F%AF%E4%BB%A5%E6%90%9C%E7%B4%A2%E7%9A%84%E7%BA%BF%E7%B4%A2)
- **P1-7** 读到入口函数获得被调用的服务名，读到服务获得状态字段，查到字段写入位置又发现事件名；每次读取都应提供新的线索，让下一次搜索更具体。[原文§如何把需求转成可以搜索的线索？](https://xiaolinnote.com/ai/coding/1_code_localization.html#%E5%A6%82%E4%BD%95%E6%8A%8A%E9%9C%80%E6%B1%82%E8%BD%AC%E6%88%90%E5%8F%AF%E4%BB%A5%E6%90%9C%E7%B4%A2%E7%9A%84%E7%BA%BF%E7%B4%A2)
- **P1-8** 文本搜索适合查已知的名称或字符串，如接口路径、错误文本、字段名，但命中只说明这段文本存在；语义检索适合缺少明确名称时找候选，能跨过“防止请求重复处理”和“幂等校验”这类表述差异，但相似度高只表示可能相关；要确认某个调用究竟指向哪个函数，就用语言服务的跳转定义、查找引用等符号能力。[原文§怎样从搜索结果中确认真正相关的函数？](https://xiaolinnote.com/ai/coding/1_code_localization.html#%E6%80%8E%E6%A0%B7%E4%BB%8E%E6%90%9C%E7%B4%A2%E7%BB%93%E6%9E%9C%E4%B8%AD%E7%A1%AE%E8%AE%A4%E7%9C%9F%E6%AD%A3%E7%9B%B8%E5%85%B3%E7%9A%84%E5%87%BD%E6%95%B0)
- **P1-9** 符号是程序中有名称的对象，如函数、类和字段，作用域、所属类型和项目依赖决定一个名称具体指向谁；例如 CustomerRepository.save 和 InvoiceRepository.save 保存的对象不同，查找名称相同的文本无法区分这两种职责，注释和测试里也可能出现同样的名字。[原文§怎样从搜索结果中确认真正相关的函数？](https://xiaolinnote.com/ai/coding/1_code_localization.html#%E6%80%8E%E6%A0%B7%E4%BB%8E%E6%90%9C%E7%B4%A2%E7%BB%93%E6%9E%9C%E4%B8%AD%E7%A1%AE%E8%AE%A4%E7%9C%9F%E6%AD%A3%E7%9B%B8%E5%85%B3%E7%9A%84%E5%87%BD%E6%95%B0)
- **P1-10** 要给模型足够的上下文：孤立的一行赋值看不出改了哪个对象、什么条件下执行，要读所属函数的参数、分支和返回，再补上相关类型；同时控制范围，先看函数签名和主体，遇到不清楚的类型或辅助函数再补读，很长的函数先看整体结构再深入相关分支。[原文§怎样从搜索结果中确认真正相关的函数？](https://xiaolinnote.com/ai/coding/1_code_localization.html#%E6%80%8E%E6%A0%B7%E4%BB%8E%E6%90%9C%E7%B4%A2%E7%BB%93%E6%9E%9C%E4%B8%AD%E7%A1%AE%E8%AE%A4%E7%9C%9F%E6%AD%A3%E7%9B%B8%E5%85%B3%E7%9A%84%E5%87%BD%E6%95%B0)
- **P1-11** 它可以帮助找到函数、类等代码边界，避免固定长度切块把一个函数拆成几段；但识别语法边界和解析符号指向是不同能力，找到一处函数调用的语法结构，并不等于知道它运行时调用哪个实现。[原文§怎样从搜索结果中确认真正相关的函数？](https://xiaolinnote.com/ai/coding/1_code_localization.html#%E6%80%8E%E6%A0%B7%E4%BB%8E%E6%90%9C%E7%B4%A2%E7%BB%93%E6%9E%9C%E4%B8%AD%E7%A1%AE%E8%AE%A4%E7%9C%9F%E6%AD%A3%E7%9B%B8%E5%85%B3%E7%9A%84%E5%87%BD%E6%95%B0)
- **P1-12** 调用关系：调用方说明函数在什么条件下执行、传入什么参数，被调用方说明它把哪些工作交给了别的代码；数据关系：谁写入字段、谁读取字段，中间有没有默认值、格式转换或重新计算；消息关系：事件驱动的实现要从事件类型、发送位置、订阅注册和处理函数继续查。代码相似度替代不了关系分析。[原文§如何沿代码关系找到跨文件实现？](https://xiaolinnote.com/ai/coding/1_code_localization.html#%E5%A6%82%E4%BD%95%E6%B2%BF%E4%BB%A3%E7%A0%81%E5%85%B3%E7%B3%BB%E6%89%BE%E5%88%B0%E8%B7%A8%E6%96%87%E4%BB%B6%E5%AE%9E%E7%8E%B0)
- **P1-13** 代码存在不代表当前运行路径会使用它：接口可能有多个实现，由依赖注入配置决定选哪个；消费者可能已经写好，订阅配置却没有启用。所以必要的注册与配置也是定位范围的一部分。[原文§如何沿代码关系找到跨文件实现？](https://xiaolinnote.com/ai/coding/1_code_localization.html#%E5%A6%82%E4%BD%95%E6%B2%BF%E4%BB%A3%E7%A0%81%E5%85%B3%E7%B3%BB%E6%89%BE%E5%88%B0%E8%B7%A8%E6%96%87%E4%BB%B6%E5%AE%9E%E7%8E%B0)
- **P1-14** 不能直接排除，动态调用、反射和运行时注册会让静态分析不完整，要先确认项目分析是否完整、实现是否通过动态方式接入；扩展关系要带着具体问题，例如确认输入是否经过校验就查输入来源和校验分支，证据不支持原判断时再调整方向，而不是把整个依赖图搬进上下文。[原文§如何沿代码关系找到跨文件实现？](https://xiaolinnote.com/ai/coding/1_code_localization.html#%E5%A6%82%E4%BD%95%E6%B2%BF%E4%BB%A3%E7%A0%81%E5%85%B3%E7%B3%BB%E6%89%BE%E5%88%B0%E8%B7%A8%E6%96%87%E4%BB%B6%E5%AE%9E%E7%8E%B0)
- **P1-15** 取决于任务：新增功能或修改行为，要明确职责由哪个函数承担、输入输出有什么约定、修改可能影响哪些调用方，相关测试能帮助理解已约定的行为；故障排查还要检查候选原因能否解释实际现象，用日志或执行轨迹判断这次是否经过该路径，再用最小复现验证对应条件下能否出现同样的错误。[原文§怎样判断代码已经定位到位？](https://xiaolinnote.com/ai/coding/1_code_localization.html#%E6%80%8E%E6%A0%B7%E5%88%A4%E6%96%AD%E4%BB%A3%E7%A0%81%E5%B7%B2%E7%BB%8F%E5%AE%9A%E4%BD%8D%E5%88%B0%E4%BD%8D)
- **P1-16** 搜索结果被截断，不能据此断言其他位置没有实现；文件读取失败也不能当作代码不存在。Agent 需要缩小查询范围、补读缺失内容，或者明确留下尚未确认的部分。[原文§怎样判断代码已经定位到位？](https://xiaolinnote.com/ai/coding/1_code_localization.html#%E6%80%8E%E6%A0%B7%E5%88%A4%E6%96%AD%E4%BB%A3%E7%A0%81%E5%B7%B2%E7%BB%8F%E5%AE%9A%E4%BD%8D%E5%88%B0%E4%BD%8D)
- **P1-17** 保留关键路径、函数名、必要关系和验证依据即可；读过但已排除的文件不必一直占用上下文，需要重新核对时再按位置读取，这样后续修改能围绕已确认的代码展开，也能追溯定位判断来自哪里。[原文§怎样判断代码已经定位到位？](https://xiaolinnote.com/ai/coding/1_code_localization.html#%E6%80%8E%E6%A0%B7%E5%88%A4%E6%96%AD%E4%BB%A3%E7%A0%81%E5%B7%B2%E7%BB%8F%E5%AE%9A%E4%BD%8D%E5%88%B0%E4%BD%8D)

## 2. 过期的代码描述

原文：[2. Coding Agent 如何避免被过期的代码描述误导？](https://xiaolinnote.com/ai/coding/2_stale_code_description.html)。

- **P2-1** 把代码描述当作根据源码提炼的摘要，用它找相关实现，关键判断回到源码核验；生成描述时记录仓库、路径、符号和源码版本，并保存生成输入的内容指纹；代码变化后先把受影响的描述标为失效、停止作为当前信息返回，再增量重建，影响范围还包括依赖这些代码的上层摘要；检索描述和读取源码要对齐目标版本。[原文§💡 简要回答](https://xiaolinnote.com/ai/coding/2_stale_code_description.html#%F0%9F%92%A1-%E7%AE%80%E8%A6%81%E5%9B%9E%E7%AD%94)
- **P2-2** 描述是派生信息，生成器读源码后提炼出解释并保存，源码之后继续变化，它不会自动跟着变；函数删除或重命名容易暴露，更难发现的是函数名和路径都没变、职责却变了，旧描述仍能把 Agent 带到一个真实文件，解释的却是过去的行为。过期也可能只是部分内容不对，部分正确的描述反而更容易让人接受其中未核实的结论。[原文§代码描述为什么会过期？](https://xiaolinnote.com/ai/coding/2_stale_code_description.html#%E4%BB%A3%E7%A0%81%E6%8F%8F%E8%BF%B0%E4%B8%BA%E4%BB%80%E4%B9%88%E4%BC%9A%E8%BF%87%E6%9C%9F)
- **P2-3** 不能单独判断。昨天生成的描述可能已经失效，一年前生成的也可能仍然适用；判断过期要比较描述所依据的实现和当前任务要研究的实现，生成时间只能帮助排查更新延迟。[原文§代码描述为什么会过期？](https://xiaolinnote.com/ai/coding/2_stale_code_description.html#%E4%BB%A3%E7%A0%81%E6%8F%8F%E8%BF%B0%E4%B8%BA%E4%BB%80%E4%B9%88%E4%BC%9A%E8%BF%87%E6%9C%9F)
- **P2-4** 要带上仓库、文件路径和符号位置，让使用者能从摘要回到具体实现，行号只能辅助定位，代码增删会改变行号；还要记录源码版本，已提交的代码记提交号，只记分支名不够，因为同一分支会不断产生新提交；提交号也代表不了正在编辑的工作区，还要检查工作区中的修改、新增和删除。[原文§怎样判断一条描述对应哪份代码？](https://xiaolinnote.com/ai/coding/2_stale_code_description.html#%E6%80%8E%E6%A0%B7%E5%88%A4%E6%96%AD%E4%B8%80%E6%9D%A1%E6%8F%8F%E8%BF%B0%E5%AF%B9%E5%BA%94%E5%93%AA%E4%BB%BD%E4%BB%A3%E7%A0%81)
- **P2-5** 系统对生成时使用的内容计算 Hash 并保存，再次使用时对对应内容重新计算比较，就能发现输入是否变化，它只比较输入、不理解代码；范围要覆盖生成器实际读取的全部输入，读了函数主体、相关类型和配置就都要记录，只给函数主体算指纹，配置变了系统仍会认为描述没变。[原文§怎样判断一条描述对应哪份代码？](https://xiaolinnote.com/ai/coding/2_stale_code_description.html#%E6%80%8E%E6%A0%B7%E5%88%A4%E6%96%AD%E4%B8%80%E6%9D%A1%E6%8F%8F%E8%BF%B0%E5%AF%B9%E5%BA%94%E5%93%AA%E4%BB%BD%E4%BB%A3%E7%A0%81)
