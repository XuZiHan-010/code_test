## 1. Harness Engineering：从提示词到 Harness、六层结构与五个难题

原文：[Harness Engineering 是什么？AI Agent 越用越聪明的秘密](https://xiaolinnote.com/agent/engineering/harness-engineering.html)。

- **M1-1** 最早在 2026 年 2 月 5 日 Mitchell Hashimoto 的博客《My AI Adoption Journey》里被正式叫响，他把自己这套做法叫 Engineer the Harness；定义是：每次发现 Agent 犯了一个错误，就花点时间去工程化一个解决方案，让它永远不会再犯同样的错误。[原文§这个新词到底从哪儿冒出来的？](https://xiaolinnote.com/agent/engineering/harness-engineering.html#%E8%BF%99%E4%B8%AA%E6%96%B0%E8%AF%8D%E5%88%B0%E5%BA%95%E4%BB%8E%E5%93%AA%E5%84%BF%E5%86%92%E5%87%BA%E6%9D%A5%E7%9A%84)
- **M1-2** 第一步是扔掉对话框，不用聊天界面而用能自主执行任务的 Agent，因为聊天界面会给人“在和 AI 讨论”的幻觉，只有放开让 Agent 自己执行才能感知它的能力边界；第二步是强迫自己用 Agent 重做一部分早已手写过的代码，过程很折磨，但能精准校准它哪里行、哪里不行。[原文§这个新词到底从哪儿冒出来的？](https://xiaolinnote.com/agent/engineering/harness-engineering.html#%E8%BF%99%E4%B8%AA%E6%96%B0%E8%AF%8D%E5%88%B0%E5%BA%95%E4%BB%8E%E5%93%AA%E5%84%BF%E5%86%92%E5%87%BA%E6%9D%A5%E7%9A%84)
- **M1-3** 可以是给 AGENTS.md 加一条规则、加一个 linter、补一个自动化测试或搞一个 Git Hook，关键是修补必须沉淀到环境里，而不是留在人脑子里；每次犯错环境就变强一点，Agent 下次更少犯错，改进速度更快，时间一长 Harness 越来越坚固，Agent 在项目里越跑越稳。[原文§这个新词到底从哪儿冒出来的？](https://xiaolinnote.com/agent/engineering/harness-engineering.html#%E8%BF%99%E4%B8%AA%E6%96%B0%E8%AF%8D%E5%88%B0%E5%BA%95%E4%BB%8E%E5%93%AA%E5%84%BF%E5%86%92%E5%87%BA%E6%9D%A5%E7%9A%84)
- **M1-4** Mitchell 的博客发出一周后，OpenAI 发布官方博客《Harness engineering: leveraging Codex in an agent-first world》，讲内部一个从 3 人起步的小团队，从空仓库出发，用 5 个月靠 Agent 写出 100 万行代码、合并了 1500 个 PR，全程没人手动写过一行代码。[原文§这个新词到底从哪儿冒出来的？](https://xiaolinnote.com/agent/engineering/harness-engineering.html#%E8%BF%99%E4%B8%AA%E6%96%B0%E8%AF%8D%E5%88%B0%E5%BA%95%E4%BB%8E%E5%93%AA%E5%84%BF%E5%86%92%E5%87%BA%E6%9D%A5%E7%9A%84)
- **M1-5** 原文认为差的往往不是模型，而是围绕模型搭起来的那套东西，也就是 Harness，有没有做到位。[原文§从提示词到 Harness](https://xiaolinnote.com/agent/engineering/harness-engineering.html#%E4%BB%8E%E6%8F%90%E7%A4%BA%E8%AF%8D%E5%88%B0-harness)
- **M1-6** Prompt Engineering 解决怎么让模型听懂你想干啥；Context Engineering 解决怎么让模型知道该用什么信息；Harness Engineering 解决怎么让模型在真实执行里持续做对一连串的事。三个阶段不是谁取代谁，而是每一步都在上一步撞到天花板之后继续往前啃出来的，难度和工作量层层放大。[原文§从提示词到 Harness](https://xiaolinnote.com/agent/engineering/harness-engineering.html#%E4%BB%8E%E6%8F%90%E7%A4%BA%E8%AF%8D%E5%88%B0-harness)
- **M1-7** 把聊天界面的外壳扒掉，里面就是一个特别大的参数文件，存在硬盘上、加载到显卡内存里；配一个 HTTP 接口就成了大模型 API 服务，套聊天界面就是 ChatGPT，套代码编辑器就是 AI IDE。它做的事是根据输入预测下一个字最可能是什么，是预测而不是思考，输入越具体，猜的范围越收敛。[原文§第一阶段：Prompt Engineering，先让模型「听懂」你](https://xiaolinnote.com/agent/engineering/harness-engineering.html#%E7%AC%AC%E4%B8%80%E9%98%B6%E6%AE%B5-prompt-engineering-%E5%85%88%E8%AE%A9%E6%A8%A1%E5%9E%8B%E3%80%8C%E5%90%AC%E6%87%82%E3%80%8D%E4%BD%A0)
- **M1-8** 大模型本质上是一个对上下文极度敏感的概率生成器：给它角色身份，它就偏向用那个角色的思路回答；给它示例，它就沿着那个范式补全；强调某个约束，它就把约束当成重点。所以写提示词不是在命令模型，而是在塑造它的概率空间，每句话都在把输出往某个方向推。[原文§第一阶段：Prompt Engineering，先让模型「听懂」你](https://xiaolinnote.com/agent/engineering/harness-engineering.html#%E7%AC%AC%E4%B8%80%E9%98%B6%E6%AE%B5-prompt-engineering-%E5%85%88%E8%AE%A9%E6%A8%A1%E5%9E%8B%E3%80%8C%E5%90%AC%E6%87%82%E3%80%8D%E4%BD%A0)
- **M1-9** 角色设定（你是谁）、背景信息（当前在干什么）、参考资料（相关文档、历史对话、代码片段）、明确任务（具体要干什么）、约束条件（哪些不能做）和输出格式（以 JSON、Markdown 还是表格返回）。[原文§第一阶段：Prompt Engineering，先让模型「听懂」你](https://xiaolinnote.com/agent/engineering/harness-engineering.html#%E7%AC%AC%E4%B8%80%E9%98%B6%E6%AE%B5-prompt-engineering-%E5%85%88%E8%AE%A9%E6%A8%A1%E5%9E%8B%E3%80%8C%E5%90%AC%E6%87%82%E3%80%8D%E4%BD%A0)
- **M1-10** 提示词写得再漂亮，也替代不了事实本身：模型没看过你的财报、内部规范和已有的 API，就无从分析和调用。提示词擅长把任务表达清楚、把约束讲明白、激发模型已有的能力，但不擅长凭空补出模型不知道的知识、管理一大堆动态变化的信息，也不擅长在长链路任务里维持稳定的状态。[原文§第一阶段：Prompt Engineering，先让模型「听懂」你](https://xiaolinnote.com/agent/engineering/harness-engineering.html#%E7%AC%AC%E4%B8%80%E9%98%B6%E6%AE%B5-prompt-engineering-%E5%85%88%E8%AE%A9%E6%A8%A1%E5%9E%8B%E3%80%8C%E5%90%AC%E6%87%82%E3%80%8D%E4%BD%A0)
- **M1-11** 每一次发给大模型的所有信息加在一起就叫上下文，提示词只是其中很小的一部分，还包括用户输入、历史对话、检索到的资料、工具返回的结果、当前任务状态、中间产物、系统规则和安全约束等；Context Engineering 要解决的是，怎么在上下文窗口有限的前提下，把最相关的信息以最合理的方式送给模型。[原文§第二阶段：Context Engineering，让模型「知道」该用什么信息](https://xiaolinnote.com/agent/engineering/harness-engineering.html#%E7%AC%AC%E4%BA%8C%E9%98%B6%E6%AE%B5-context-engineering-%E8%AE%A9%E6%A8%A1%E5%9E%8B%E3%80%8C%E7%9F%A5%E9%81%93%E3%80%8D%E8%AF%A5%E7%94%A8%E4%BB%80%E4%B9%88%E4%BF%A1%E6%81%AF)
- **M1-12** 因为产品形态变了：以前做的是聊天机器人，问一句答一句，链路短、状态少；Agent 火了之后，模型要进到真实环境里干活，要多轮对话、调用工具、写代码、查数据库、在多个步骤之间传递中间结果，还要根据外部反馈修正计划，系统面对的不再是这一次回答对不对，而是整条链路能不能跑通。[原文§第二阶段：Context Engineering，让模型「知道」该用什么信息](https://xiaolinnote.com/agent/engineering/harness-engineering.html#%E7%AC%AC%E4%BA%8C%E9%98%B6%E6%AE%B5-context-engineering-%E8%AE%A9%E6%A8%A1%E5%9E%8B%E3%80%8C%E7%9F%A5%E9%81%93%E3%80%8D%E8%AF%A5%E7%94%A8%E4%BB%80%E4%B9%88%E4%BF%A1%E6%81%AF)
- **M1-13** 上下文窗口是大模型一次能处理的上下文上限，相当于短期记忆容量；即使窗口够大，注意力也不是均匀分布的，上下文塞得太满时模型会记不住前面的内容、前后矛盾、忽略最初定下的规则，这种现象叫上下文腐化。[原文§第二阶段：Context Engineering，让模型「知道」该用什么信息](https://xiaolinnote.com/agent/engineering/harness-engineering.html#%E7%AC%AC%E4%BA%8C%E9%98%B6%E6%AE%B5-context-engineering-%E8%AE%A9%E6%A8%A1%E5%9E%8B%E3%80%8C%E7%9F%A5%E9%81%93%E3%80%8D%E8%AF%A5%E7%94%A8%E4%BB%80%E4%B9%88%E4%BF%A1%E6%81%AF)
- **M1-14** 第一步召回，从一大堆资料里找出与当前任务最相关的部分，涉及 RAG 技术；第二步压缩，对每段先做摘要只送摘要，或把太老的对话压成一句话总结、只保留最近几轮原文；第三步组装，按一定顺序和格式组织，因为大模型对靠后的信息更敏感，重要的指令和当前任务往往放在靠后的位置。[原文§第二阶段：Context Engineering，让模型「知道」该用什么信息](https://xiaolinnote.com/agent/engineering/harness-engineering.html#%E7%AC%AC%E4%BA%8C%E9%98%B6%E6%AE%B5-context-engineering-%E8%AE%A9%E6%A8%A1%E5%9E%8B%E3%80%8C%E7%9F%A5%E9%81%93%E3%80%8D%E8%AF%A5%E7%94%A8%E4%BB%80%E4%B9%88%E4%BF%A1%E6%81%AF)
- **M1-15** 召回、压缩、组装这三步，不同的 AI 工具实现各不相同；同样用 Claude 模型，在 Claude Code、Cursor、Trae 里效果会差不少，模型是同一个，但每家的上下文工程策略不一样，最后的体验也就不一样。[原文§第二阶段：Context Engineering，让模型「知道」该用什么信息](https://xiaolinnote.com/agent/engineering/harness-engineering.html#%E7%AC%AC%E4%BA%8C%E9%98%B6%E6%AE%B5-context-engineering-%E8%AE%A9%E6%A8%A1%E5%9E%8B%E3%80%8C%E7%9F%A5%E9%81%93%E3%80%8D%E8%AF%A5%E7%94%A8%E4%BB%80%E4%B9%88%E4%BF%A1%E6%81%AF)
- **M1-16** 一开始只给模型看每个能力的目录，告诉它有哪些工具、SOP 和参考；等模型判断现在需要用某个工具时，再把那个工具的详细说明、参数定义和使用示例动态加载进来。它说明上下文优化的本质不是给得更多，而是按需给、分层给、在正确的时机给。[原文§第二阶段：Context Engineering，让模型「知道」该用什么信息](https://xiaolinnote.com/agent/engineering/harness-engineering.html#%E7%AC%AC%E4%BA%8C%E9%98%B6%E6%AE%B5-context-engineering-%E8%AE%A9%E6%A8%A1%E5%9E%8B%E3%80%8C%E7%9F%A5%E9%81%93%E3%80%8D%E8%AF%A5%E7%94%A8%E4%BB%80%E4%B9%88%E4%BF%A1%E6%81%AF)
- **M1-17** 原文称 Prompt 是对指令的工程化，Context 是对输入环境的工程化，Harness 是对整个运行系统的工程化，重点是有一整套机制持续观测、持续纠正并最终验收；三者是一层包一层的包含关系。[原文§第三阶段：Harness Engineering，让模型「做对」一连串的事](https://xiaolinnote.com/agent/engineering/harness-engineering.html#%E7%AC%AC%E4%B8%89%E9%98%B6%E6%AE%B5-harness-engineering-%E8%AE%A9%E6%A8%A1%E5%9E%8B%E3%80%8C%E5%81%9A%E5%AF%B9%E3%80%8D%E4%B8%80%E8%BF%9E%E4%B8%B2%E7%9A%84%E4%BA%8B)
- **M1-18** 计划做得很好但执行时突然跑偏；工具调对了却理解错了返回结果；跑着跑着忘了最初要干什么；在很长的任务链里已经悄悄偏离初衷，系统却完全没察觉。提示词工程优化意图的表达，上下文工程优化信息的供给，两者都还停留在输入侧，没有回答谁来监督、约束模型并在它跑偏时把它拉回来。[原文§第三阶段：Harness Engineering，让模型「做对」一连串的事](https://xiaolinnote.com/agent/engineering/harness-engineering.html#%E7%AC%AC%E4%B8%89%E9%98%B6%E6%AE%B5-harness-engineering-%E8%AE%A9%E6%A8%A1%E5%9E%8B%E3%80%8C%E5%81%9A%E5%AF%B9%E3%80%8D%E4%B8%80%E8%BF%9E%E4%B8%B2%E7%9A%84%E4%BA%8B)
- **M1-19** Harness 直译是马具或缰绳：马本身有强大的力量，没有缰绳和马具，这股力量就是失控的，马具的作用是让这股力量为你所用。放到 AI 系统里，模型从回答问题走向执行任务后，系统不能只负责喂信息，还要能驾驭整个执行过程，这就是 Harness Engineering 的出发点。[原文§第三阶段：Harness Engineering，让模型「做对」一连串的事](https://xiaolinnote.com/agent/engineering/harness-engineering.html#%E7%AC%AC%E4%B8%89%E9%98%B6%E6%AE%B5-harness-engineering-%E8%AE%A9%E6%A8%A1%E5%9E%8B%E3%80%8C%E5%81%9A%E5%AF%B9%E3%80%8D%E4%B8%80%E8%BF%9E%E4%B8%B2%E7%9A%84%E4%BA%8B)
- **M1-20** 等式是 Agent = Model + Harness：在一个 AI Agent 系统里，除了模型本身之外，几乎所有决定它能不能稳定交付的东西都属于 Harness；反过来推就是 Harness = Agent − Model。[原文§第三阶段：Harness Engineering，让模型「做对」一连串的事](https://xiaolinnote.com/agent/engineering/harness-engineering.html#%E7%AC%AC%E4%B8%89%E9%98%B6%E6%AE%B5-harness-engineering-%E8%AE%A9%E6%A8%A1%E5%9E%8B%E3%80%8C%E5%81%9A%E5%AF%B9%E3%80%8D%E4%B8%80%E8%BF%9E%E4%B8%B2%E7%9A%84%E4%BA%8B)
- **M1-21** 把任务讲清楚，告诉他先寒暄、介绍方案、问需求、确认下一步，是 Prompt Engineering；把客户背景、历史沟通、报价、竞品等资料准备齐全，是 Context Engineering；让他带 checklist、关键节点实时汇报、录音复盘、跑偏了马上电话纠正、拜访后按明确标准验收，这一整套就是 Harness。[原文§第三阶段：Harness Engineering，让模型「做对」一连串的事](https://xiaolinnote.com/agent/engineering/harness-engineering.html#%E7%AC%AC%E4%B8%89%E9%98%B6%E6%AE%B5-harness-engineering-%E8%AE%A9%E6%A8%A1%E5%9E%8B%E3%80%8C%E5%81%9A%E5%AF%B9%E3%80%8D%E4%B8%80%E8%BF%9E%E4%B8%B2%E7%9A%84%E4%BA%8B)
- **M1-22** 输入侧：上下文精细化管理回答“这一轮提供什么信息”，记忆与状态管理回答“跨轮保存什么”。动作侧：工具系统回答“用哪些工具行动”，执行编排回答“下一步执行什么”。校验侧：评估与观测回答“有何标准衡量效果”，约束与恢复回答“失败后如何恢复”。三组共同覆盖六层。[原文§Harness 拆开看，里面到底装了些啥？](https://xiaolinnote.com/agent/engineering/harness-engineering.html#harness-%E6%8B%86%E5%BC%80%E7%9C%8B-%E9%87%8C%E9%9D%A2%E5%88%B0%E5%BA%95%E8%A3%85%E4%BA%86%E4%BA%9B%E5%95%A5)
- **M1-23** 六层不是凭空发明的，而是不同团队在让 Agent 稳定工作时自然收敛出的结构；原文把每层要解决的问题列成表，当作路线图。[原文§Harness 拆开看，里面到底装了些啥？](https://xiaolinnote.com/agent/engineering/harness-engineering.html#harness-%E6%8B%86%E5%BC%80%E7%9C%8B-%E9%87%8C%E9%9D%A2%E5%88%B0%E5%BA%95%E8%A3%85%E4%BA%86%E4%BA%9B%E5%95%A5)
- **M1-24** 第一层上下文的精细化管的是空间：这一轮发给模型的那一坨上下文长什么样、装了什么、怎么排布；第四层记忆与状态管的是时间：上一轮发生过的事情怎么流动到下一轮。可以想成一台相机，第一层是取景框，第四层是胶卷。[原文§第一层，上下文的精细化管理](https://xiaolinnote.com/agent/engineering/harness-engineering.html#%E7%AC%AC%E4%B8%80%E5%B1%82-%E4%B8%8A%E4%B8%8B%E6%96%87%E7%9A%84%E7%B2%BE%E7%BB%86%E5%8C%96%E7%AE%A1%E7%90%86)
- **M1-25** 一是把角色和目标钉死，让模型知道自己是谁、当前任务和成功标准是什么，大部分 Agent 跑偏的根源就是这一步没说清；二是动态筛选而不是一次塞满，只把当前相关的信息拉进来，其余留在文件系统里按需再取；三是结构化组织，固定规则、动态证据和中间结论分开放，否则模型会用前面错的中间结论自我污染。[原文§第一层，上下文的精细化管理](https://xiaolinnote.com/agent/engineering/harness-engineering.html#%E7%AC%AC%E4%B8%80%E5%B1%82-%E4%B8%8A%E4%B8%8B%E6%96%87%E7%9A%84%E7%B2%BE%E7%BB%86%E5%8C%96%E7%AE%A1%E7%90%86)
- **M1-26** 塞给模型的无关信息越多，它的注意力越散，Anthropic 把这个现象命名为 context rot（上下文腐化）；给出的解法是 just-in-time retrieval，让 Agent 边干活边按需抓信息，而不是一上来就把所有可能有用的东西一股脑塞进去。[原文§第一层，上下文的精细化管理](https://xiaolinnote.com/agent/engineering/harness-engineering.html#%E7%AC%AC%E4%B8%80%E5%B1%82-%E4%B8%8A%E4%B8%8B%E6%96%87%E7%9A%84%E7%B2%BE%E7%BB%86%E5%8C%96%E7%AE%A1%E7%90%86)

- **M1-29** MCP（Model Context Protocol）本质上是在做工具层的标准化，让任何工具都能用同一种方式接到任何 Agent 上，大家不用再各自重复造轮子。[原文§第二层，工具系统的可控调用](https://xiaolinnote.com/agent/engineering/harness-engineering.html#%E7%AC%AC%E4%BA%8C%E5%B1%82-%E5%B7%A5%E5%85%B7%E7%B3%BB%E7%BB%9F%E7%9A%84%E5%8F%AF%E6%8E%A7%E8%B0%83%E7%94%A8)
- **M1-30** Agent 的本质是一个 for 循环：思考一步、行动一步、观察结果、再思考下一步，即 ReAct；但它常在每一步都会做、把步骤串起来就不会的地方翻车，交付一堆半成品。第三层的职责是给模型一条明确的工作轨道，让它知道自己现在在哪一步、下一步该干什么。[原文§第三层，任务执行的全局编排](https://xiaolinnote.com/agent/engineering/harness-engineering.html#%E7%AC%AC%E4%B8%89%E5%B1%82-%E4%BB%BB%E5%8A%A1%E6%89%A7%E8%A1%8C%E7%9A%84%E5%85%A8%E5%B1%80%E7%BC%96%E6%8E%92)
- **M1-31** Plan-and-Execute，先规划完整计划再执行，适合长链路任务；Reflexion，每次失败都让 Agent 反思一下再重试；Tree of Thoughts，同时探索多条思路再选最好的。不同场景用不同的编排策略。[原文§第三层，任务执行的全局编排](https://xiaolinnote.com/agent/engineering/harness-engineering.html#%E7%AC%AC%E4%B8%89%E5%B1%82-%E4%BB%BB%E5%8A%A1%E6%89%A7%E8%A1%8C%E7%9A%84%E5%85%A8%E5%B1%80%E7%BC%96%E6%8E%92)
- **M1-32** 任务状态，如今天处理到哪个 PR、还剩几个、各自打分，写在进度文件里，活到任务结束后归档；会话中间结果，是当前这一轮里的初步判断，活到当轮结束就可以丢；长期记忆和用户偏好，写在常驻文件里每次调用都注入，跨所有任务存在。三类混在一起就乱了，CLAUDE.md、.cursorrules 这类规则文件是长期记忆的典型实现。[原文§第四层，记忆与状态的分层管理](https://xiaolinnote.com/agent/engineering/harness-engineering.html#%E7%AC%AC%E5%9B%9B%E5%B1%82-%E8%AE%B0%E5%BF%86%E4%B8%8E%E7%8A%B6%E6%80%81%E7%9A%84%E5%88%86%E5%B1%82%E7%AE%A1%E7%90%86)
- **M1-33** Agent 的状态不应该放在上下文窗口里，而应该外化到文件系统；Anthropic 的具体做法是让 Agent 维护一个 claude-progress.txt 日志、一个 init.sh 启动脚本，加上完整的 git history，作为长期记忆介质，下一轮换一个干净的上下文窗口接手时，读这些文件就知道现在到哪一步了。[原文§第四层，记忆与状态的分层管理](https://xiaolinnote.com/agent/engineering/harness-engineering.html#%E7%AC%AC%E5%9B%9B%E5%B1%82-%E8%AE%B0%E5%BF%86%E4%B8%8E%E7%8A%B6%E6%80%81%E7%9A%84%E5%88%86%E5%B1%82%E7%AE%A1%E7%90%86)
- **M1-34** 一是有把尺子，即 Eval 集：手写一批典型任务并标注正确答案，每次改动 Harness（改规则文件、加工具、调编排）后让 Agent 重跑一遍，对比成功率；二是能看到每一次的量，即 Trace、日志和指标：看到 Agent 每一步做了什么决策、调了哪个工具、拿到什么返回、花了多少 token，才能定位失败发生在哪一步。[原文§第五层，独立的评估与观测体系](https://xiaolinnote.com/agent/engineering/harness-engineering.html#%E7%AC%AC%E4%BA%94%E5%B1%82-%E7%8B%AC%E7%AB%8B%E7%9A%84%E8%AF%84%E4%BC%B0%E4%B8%8E%E8%A7%82%E6%B5%8B%E4%BD%93%E7%B3%BB)
- **M1-35** 团队做出 Agent 高高兴兴上线，跑了两周才发现实际成功率只有 50%：它每次都出结果，但一半时候是错的，而这两周里没人发现，因为没有任何机制能告诉团队它这次到底做得对不对；没有 Eval 集，对 Agent 好坏的判断就永远停留在“感觉这次变好了”的玄学阶段。[原文§第五层，独立的评估与观测体系](https://xiaolinnote.com/agent/engineering/harness-engineering.html#%E7%AC%AC%E4%BA%94%E5%B1%82-%E7%8B%AC%E7%AB%8B%E7%9A%84%E8%AF%84%E4%BC%B0%E4%B8%8E%E8%A7%82%E6%B5%8B%E4%BD%93%E7%B3%BB)

- **M1-37** 约束：定义什么事 Agent 不能做，例如一次最多分析 20 个 PR、token 用量超过上限就立刻停下，最好硬编码到代码或 linter 规则里，而不是写在提示词里靠 Agent 自觉；校验：在每一步输出前后做自动检查，如格式校验、频道白名单；恢复：每一种典型失败都有明确的恢复路径，如限流后等待重试、发送失败先落本地队列、token 快耗光时保存进度下轮继续。[原文§第六层，约束校验与失败恢复机制](https://xiaolinnote.com/agent/engineering/harness-engineering.html#%E7%AC%AC%E5%85%AD%E5%B1%82-%E7%BA%A6%E6%9D%9F%E6%A0%A1%E9%AA%8C%E4%B8%8E%E5%A4%B1%E8%B4%A5%E6%81%A2%E5%A4%8D%E6%9C%BA%E5%88%B6)

- **M1-39** 模型对自己还剩多少上下文的估计很不准，常以为快用完了而实际还剩一大半，于是简化方案、跳过验证、急着宣布完成，这叫上下文焦虑。[原文§难题一，Agent 跑久了为啥会越走越偏？](https://xiaolinnote.com/agent/engineering/harness-engineering.html#%E9%9A%BE%E9%A2%98%E4%B8%80-agent-%E8%B7%91%E4%B9%85%E4%BA%86%E4%B8%BA%E5%95%A5%E4%BC%9A%E8%B6%8A%E8%B5%B0%E8%B6%8A%E5%81%8F)

- **M1-42** 首轮的任务是把环境信息、项目状态和约束条件整理好，写进进度日志、init.sh 启动脚本和初始 git commit；后续每轮读取这些文件后只推进一点。[原文§难题一，Agent 跑久了为啥会越走越偏？](https://xiaolinnote.com/agent/engineering/harness-engineering.html#%E9%9A%BE%E9%A2%98%E4%B8%80-agent-%E8%B7%91%E4%B9%85%E4%BA%86%E4%B8%BA%E5%95%A5%E4%BC%9A%E8%B6%8A%E8%B5%B0%E8%B6%8A%E5%81%8F)
- **M1-43** 后续轮次靠读取文件系统里的交接文档，来恢复自己现在在哪一步。[原文§难题一，Agent 跑久了为啥会越走越偏？](https://xiaolinnote.com/agent/engineering/harness-engineering.html#%E9%9A%BE%E9%A2%98%E4%B8%80-agent-%E8%B7%91%E4%B9%85%E4%BA%86%E4%B8%BA%E5%95%A5%E4%BC%9A%E8%B6%8A%E8%B5%B0%E8%B6%8A%E5%81%8F)

- **M1-49** 把产品目标拆解成 Agent 能力边界内的小任务，确保每件事 Agent 都接得住；Agent 反复失败时不去催它更努力，而是看环境里缺了什么能力，把那个能力补进环境；建立反馈链路，让 Agent 真正能看到自己工作的结果。工程师的价值不再是一天写多少行代码，而是能为 Agent 设计多好的运行环境。[原文§难题三，Agent 总是失败，工程师到底该干啥？](https://xiaolinnote.com/agent/engineering/harness-engineering.html#%E9%9A%BE%E9%A2%98%E4%B8%89-agent-%E6%80%BB%E6%98%AF%E5%A4%B1%E8%B4%A5-%E5%B7%A5%E7%A8%8B%E5%B8%88%E5%88%B0%E5%BA%95%E8%AF%A5%E5%B9%B2%E5%95%A5)
- **M1-50** 这个文件被当作系统提示词每次都注入，而上下文窗口是稀缺资源，文件越来越长时模型的注意力被严重稀释，看到的东西太多，反而抓不住当前任务真正需要的那部分；这正是上下文腐化在规则文件场景下的表现。[原文§难题四，规范文件越写越长，为啥 Agent 反而更糊涂？](https://xiaolinnote.com/agent/engineering/harness-engineering.html#%E9%9A%BE%E9%A2%98%E5%9B%9B-%E8%A7%84%E8%8C%83%E6%96%87%E4%BB%B6%E8%B6%8A%E5%86%99%E8%B6%8A%E9%95%BF-%E4%B8%BA%E5%95%A5-agent-%E5%8F%8D%E8%80%8C%E6%9B%B4%E7%B3%8A%E6%B6%82)
- **M1-51** 把它从百科全书改成目录页：主文件只保留约 100 行的核心索引，不写每条细节规则，只告诉 Agent 想看什么去哪儿看；详细内容拆到主题清晰的子文档里，如架构文档、设计原则、产品规格、执行计划、质量评分；Agent 平时只看目录，真的需要时才钻进对应的子文档。这就是渐进式披露，原则是规则文件宁缺毋滥。[原文§难题四，规范文件越写越长，为啥 Agent 反而更糊涂？](https://xiaolinnote.com/agent/engineering/harness-engineering.html#%E9%9A%BE%E9%A2%98%E5%9B%9B-%E8%A7%84%E8%8C%83%E6%96%87%E4%BB%B6%E8%B6%8A%E5%86%99%E8%B6%8A%E9%95%BF-%E4%B8%BA%E5%95%A5-agent-%E5%8F%8D%E8%80%8C%E6%9B%B4%E7%B3%8A%E6%B6%82)
- **M1-52** 原文称 Agent 会大量模仿仓库里已有的代码模式，好的坏的都复制；早期写歪的代码被当成惯例，越堆越多，整个代码库开始腐烂，这被称为 AI slop。[原文§难题五，Agent 写的代码越堆越烂，技术债怎么还？](https://xiaolinnote.com/agent/engineering/harness-engineering.html#%E9%9A%BE%E9%A2%98%E4%BA%94-agent-%E5%86%99%E7%9A%84%E4%BB%A3%E7%A0%81%E8%B6%8A%E5%A0%86%E8%B6%8A%E7%83%82-%E6%8A%80%E6%9C%AF%E5%80%BA%E6%80%8E%E4%B9%88%E8%BF%98)
- **M1-53** 原文说这些原则本是资深工程师脑中的隐性知识，只存在于 code review 的讨论里；写成显式规则后，后台 Agent 才能对照它扫描仓库、找出偏离并自动开修复 PR，例如优先用共享工具包、必须校验数据边界。[原文§难题五，Agent 写的代码越堆越烂，技术债怎么还？](https://xiaolinnote.com/agent/engineering/harness-engineering.html#%E9%9A%BE%E9%A2%98%E4%BA%94-agent-%E5%86%99%E7%9A%84%E4%BB%A3%E7%A0%81%E8%B6%8A%E5%A0%86%E8%B6%8A%E7%83%82-%E6%8A%80%E6%9C%AF%E5%80%BA%E6%80%8E%E4%B9%88%E8%BF%98)
- **M1-54** 由后台 Agent 对照 Golden Principles 定期扫描代码，自动开修复 PR，再由人类快速审完。[原文§难题五，Agent 写的代码越堆越烂，技术债怎么还？](https://xiaolinnote.com/agent/engineering/harness-engineering.html#%E9%9A%BE%E9%A2%98%E4%BA%94-agent-%E5%86%99%E7%9A%84%E4%BB%A3%E7%A0%81%E8%B6%8A%E5%A0%86%E8%B6%8A%E7%83%82-%E6%8A%80%E6%9C%AF%E5%80%BA%E6%80%8E%E4%B9%88%E8%BF%98)
- **M1-55** 每周拿整个周五人工集中清理的做法失败了，因为 Agent 的产出比人清理得快；改成后台 Agent 按固定节奏每天小额偿还后，大部分修复 PR 一分钟内就能审完并自动合并。[原文§难题五，Agent 写的代码越堆越烂，技术债怎么还？](https://xiaolinnote.com/agent/engineering/harness-engineering.html#%E9%9A%BE%E9%A2%98%E4%BA%94-agent-%E5%86%99%E7%9A%84%E4%BB%A3%E7%A0%81%E8%B6%8A%E5%A0%86%E8%B6%8A%E7%83%82-%E6%8A%80%E6%9C%AF%E5%80%BA%E6%80%8E%E4%B9%88%E8%BF%98)
- **M1-56** 技术债就像一笔高利息贷款，几乎永远应该每天小额还一点点，而不是攒着等某一天集中还；原则是技术债不是攒一堆集中还，而是每天让后台 Agent 自动偿还一点。[原文§难题五，Agent 写的代码越堆越烂，技术债怎么还？](https://xiaolinnote.com/agent/engineering/harness-engineering.html#%E9%9A%BE%E9%A2%98%E4%BA%94-agent-%E5%86%99%E7%9A%84%E4%BB%A3%E7%A0%81%E8%B6%8A%E5%A0%86%E8%B6%8A%E7%83%82-%E6%8A%80%E6%9C%AF%E5%80%BA%E6%80%8E%E4%B9%88%E8%BF%98)
- **M1-57** 原文给出三个原因：组合性好、API 稳定、训练数据里出现得多。老库的代码示例、问答和文章很多，模型熟悉各种用法；新框架只见过零星文档，容易张冠李戴。[原文§顺便提一个反直觉的发现：Agent 用「老技术」反而更稳](https://xiaolinnote.com/agent/engineering/harness-engineering.html#%E9%A1%BA%E4%BE%BF%E6%8F%90%E4%B8%80%E4%B8%AA%E5%8F%8D%E7%9B%B4%E8%A7%89%E7%9A%84%E5%8F%91%E7%8E%B0-agent-%E7%94%A8%E3%80%8C%E8%80%81%E6%8A%80%E6%9C%AF%E3%80%8D%E5%8F%8D%E8%80%8C%E6%9B%B4%E7%A8%B3)
- **M1-58** 因为自己写的代码 Agent 能完全理解和控制，而流行的第三方包里有它看不懂的黑盒行为。[原文§顺便提一个反直觉的发现：Agent 用「老技术」反而更稳](https://xiaolinnote.com/agent/engineering/harness-engineering.html#%E9%A1%BA%E4%BE%BF%E6%8F%90%E4%B8%80%E4%B8%AA%E5%8F%8D%E7%9B%B4%E8%A7%89%E7%9A%84%E5%8F%91%E7%8E%B0-agent-%E7%94%A8%E3%80%8C%E8%80%81%E6%8A%80%E6%9C%AF%E3%80%8D%E5%8F%8D%E8%80%8C%E6%9B%B4%E7%A8%B3)
- **M1-59** 共同点是它们都不是在调模型，而是在设计模型外面的那一整套环境，这是 Harness Engineering 的灵魂；五条原则是：重启胜过修补，生产验收分家，与其催模型不如改环境，规则宁缺毋滥，技术债天天还。[原文§顺便提一个反直觉的发现：Agent 用「老技术」反而更稳](https://xiaolinnote.com/agent/engineering/harness-engineering.html#%E9%A1%BA%E4%BE%BF%E6%8F%90%E4%B8%80%E4%B8%AA%E5%8F%8D%E7%9B%B4%E8%A7%89%E7%9A%84%E5%8F%91%E7%8E%B0-agent-%E7%94%A8%E3%80%8C%E8%80%81%E6%8A%80%E6%9C%AF%E3%80%8D%E5%8F%8D%E8%80%8C%E6%9B%B4%E7%A8%B3)
- **M1-60** 做一个要让 Agent 跑得稳的项目，选技术栈时不要一味追新；越老、文档越齐全、在开源社区沉淀越久的技术，Agent 越容易做对。OpenAI 在 Codex 项目里甚至会主动选择看起来很土、业界有点嫌弃的技术栈，就因为 Agent 能把它们用得更稳。[原文§顺便提一个反直觉的发现：Agent 用「老技术」反而更稳](https://xiaolinnote.com/agent/engineering/harness-engineering.html#%E9%A1%BA%E4%BE%BF%E6%8F%90%E4%B8%80%E4%B8%AA%E5%8F%8D%E7%9B%B4%E8%A7%89%E7%9A%84%E5%8F%91%E7%8E%B0-agent-%E7%94%A8%E3%80%8C%E8%80%81%E6%8A%80%E6%9C%AF%E3%80%8D%E5%8F%8D%E8%80%8C%E6%9B%B4%E7%A8%B3)

## 2. Loop Engineering：概念、组成与三盆冷水

原文：[Loop Engineering 是什么？AI 编程从 Prompt 到 Loop 的范式转变](https://xiaolinnote.com/agent/engineering/loop-engineering.html)。

- **M2-1** 点火的是开源 agent 项目 OpenClaw 的作者 Peter Steinberger，他 6 月 7 日发推说不该再给 coding agent 打 prompt，而该去设计那个给 agent 打 prompt 的 loop；给概念定名写长文的是 Google Cloud 的 AI 总监 Addy Osmani；Claude Code 创始人 Boris Cherny 在访谈里的说法等于提前为它背了书。[原文§Loop Engineering 是什么？AI 编程从 Prompt 到 Loop 的范式转变](https://xiaolinnote.com/agent/engineering/loop-engineering.html#loop-engineering-%E6%98%AF%E4%BB%80%E4%B9%88-ai-%E7%BC%96%E7%A8%8B%E4%BB%8E-prompt-%E5%88%B0-loop-%E7%9A%84%E8%8C%83%E5%BC%8F%E8%BD%AC%E5%8F%98)
- **M2-2** 原文称话术、材料、驾驶舱三道坎都迈过后，整条流水线上唯一还要人肉驱动的环节，就是人坐在屏幕前敲下一条 prompt，人一睡觉它就停工，所以最后的瓶颈是人自己。[原文§Q1：四个 engineering，到底都在 engineering 什么？](https://xiaolinnote.com/agent/engineering/loop-engineering.html#q1-%E5%9B%9B%E4%B8%AA-engineering-%E5%88%B0%E5%BA%95%E9%83%BD%E5%9C%A8-engineering-%E4%BB%80%E4%B9%88)
- **M2-3** 2023 年模型只会一问一答，瓶颈卡在怎么说，对应提示词工程；2025 年模型开始当 agent 干活，瓶颈移到喂什么，要把对的代码、文档、工具、历史记忆在对的时机塞进上下文窗口，对应上下文工程；2026 年初模型能连续干几个小时，瓶颈变成干活的环境，对应 harness。模型每变强一截，瓶颈就往外移一层。[原文§Q1：四个 engineering，到底都在 engineering 什么？](https://xiaolinnote.com/agent/engineering/loop-engineering.html#q1-%E5%9B%9B%E4%B8%AA-engineering-%E5%88%B0%E5%BA%95%E9%83%BD%E5%9C%A8-engineering-%E4%BB%80%E4%B9%88)
- **M2-4** 模型需要工具去执行命令、权限边界防止误伤、沙箱安全地试错、派出子 agent 分头探索、上下文管理机制防止越干越糊涂；这一整套围绕模型搭建的运行装备叫 harness，可以理解成 agent 的驾驶舱，公式是 Agent = 模型 + harness，同一个模型驾驶舱不一样，能力可以差出几倍。[原文§Q1：四个 engineering，到底都在 engineering 什么？](https://xiaolinnote.com/agent/engineering/loop-engineering.html#q1-%E5%9B%9B%E4%B8%AA-engineering-%E5%88%B0%E5%BA%95%E9%83%BD%E5%9C%A8-engineering-%E4%BB%80%E4%B9%88)
- **M2-5** 原文称过去是回合制：人写一条 prompt、读输出、再写下一条，每一步都靠人推进；Loop Engineering 把发现任务、布置任务、检查结果、决定下一步设计成能自己运转的循环，由循环去驱动 agent。[原文§Q2：Loop Engineering 到底是什么？](https://xiaolinnote.com/agent/engineering/loop-engineering.html#q2-loop-engineering-%E5%88%B0%E5%BA%95%E6%98%AF%E4%BB%80%E4%B9%88)
- **M2-6** Loop engineering 就是把亲自给 agent 写 prompt 的那个你替换掉，转而去设计那个代替你做这件事的系统；loop 本身可以理解为一个递归式的目标：你定义一个目的，AI 持续迭代，直到完成。一句话：你不再是 prompt 的作者，而是 prompt 生产系统的设计师。[原文§Q2：Loop Engineering 到底是什么？](https://xiaolinnote.com/agent/engineering/loop-engineering.html#q2-loop-engineering-%E5%88%B0%E5%BA%95%E6%98%AF%E4%BB%80%E4%B9%88)
- **M2-7** 以前写一条好 prompt，收益是这一次回答变好；现在设计一个好 loop，收益是之后每一次循环都变好，投入从消耗品变成了资产。但设计 loop 比写 prompt 难得多，要考虑触发、并行、验证、状态、止损，相当于从说一句话升级到设计一套制度，杠杆变长了，对握杠杆的人要求也变高了。[原文§Q2：Loop Engineering 到底是什么？](https://xiaolinnote.com/agent/engineering/loop-engineering.html#q2-loop-engineering-%E5%88%B0%E5%BA%95%E6%98%AF%E4%BB%80%E4%B9%88)
- **M2-8** 定时触发和事件触发并列为 loop 的心跳，例如每天早上自动扫一遍 CI 失败，或者每次 PR 合并自动跑一轮检查。[原文§第一件：自动化，loop 的心跳](https://xiaolinnote.com/agent/engineering/loop-engineering.html#%E7%AC%AC%E4%B8%80%E4%BB%B6-%E8%87%AA%E5%8A%A8%E5%8C%96-loop-%E7%9A%84%E5%BF%83%E8%B7%B3)
- **M2-9** 不算。自动化才让 loop 成为真正的 loop，否则它只是一个你跑过一次的任务；有了定时或事件触发这个心跳，循环才算活着。[原文§第一件：自动化，loop 的心跳](https://xiaolinnote.com/agent/engineering/loop-engineering.html#%E7%AC%AC%E4%B8%80%E4%BB%B6-%E8%87%AA%E5%8A%A8%E5%8C%96-loop-%E7%9A%84%E5%BF%83%E8%B7%B3)
- **M2-10** 麻烦是两个 agent 同时改同一个文件，像两个工程师挤在同一台电脑上改同一行代码；解法是 git 的 worktree 机制，给每个 agent 一个独立的工作目录和独立分支，共享同一份仓库历史，但物理上互不干扰，各干各的，最后各开各的 PR。[原文§第二件：worktree，让并行不变成打架](https://xiaolinnote.com/agent/engineering/loop-engineering.html#%E7%AC%AC%E4%BA%8C%E4%BB%B6-worktree-%E8%AE%A9%E5%B9%B6%E8%A1%8C%E4%B8%8D%E5%8F%98%E6%88%90%E6%89%93%E6%9E%B6)
- **M2-11** agent 每个会话都是冷启动，项目里的规范、约定和坑一概不知，没解释到的地方还会用一个自信的猜测填上；skill 把这些项目知识写成文件放在仓库里，让 agent 该用的时候自己读。没有 skill，loop 每个周期都从零重新推导你的项目；有了 skill，知识是复利的。[原文§第三件：skill，治好 agent 的「金鱼记忆」](https://xiaolinnote.com/agent/engineering/loop-engineering.html#%E7%AC%AC%E4%B8%89%E4%BB%B6-skill-%E6%B2%BB%E5%A5%BD-agent-%E7%9A%84%E3%80%8C%E9%87%91%E9%B1%BC%E8%AE%B0%E5%BF%86%E3%80%8D)
- **M2-12** 真实的工作流不止于代码，还要读 issue 工单、查监控、发消息、开 PR，connector 是基于 MCP 协议、把这些外部系统接进来的桥；只能看见文件系统的 loop 撑死算半个 loop，接上之后它会自己开好 PR、关联好工单，等 CI 变绿后自己去频道里通知人。[原文§第四件：connector，让 loop 摸到真实世界](https://xiaolinnote.com/agent/engineering/loop-engineering.html#%E7%AC%AC%E5%9B%9B%E4%BB%B6-connector-%E8%AE%A9-loop-%E6%91%B8%E5%88%B0%E7%9C%9F%E5%AE%9E%E4%B8%96%E7%95%8C)
- **M2-13** 因为写代码的那个模型给自己的作业打分时太手下留情；让 A 出方案，再让一个干净上下文的 B 来挑刺，B 没有“希望自己是对的”的包袱，挑出来的才是真问题。原文认为这是五大件里最有用的结构性设计。[原文§第五件：sub-agent，写的人和查的人必须分开](https://xiaolinnote.com/agent/engineering/loop-engineering.html#%E7%AC%AC%E4%BA%94%E4%BB%B6-sub-agent-%E5%86%99%E7%9A%84%E4%BA%BA%E5%92%8C%E6%9F%A5%E7%9A%84%E4%BA%BA%E5%BF%85%E9%A1%BB%E5%88%86%E5%BC%80)
- **M2-14** 把做完了什么、下一步是什么记在磁盘上，下一次循环读到这些记录就能接着做。[原文§第六件：记忆，loop 的命根子](https://xiaolinnote.com/agent/engineering/loop-engineering.html#%E7%AC%AC%E5%85%AD%E4%BB%B6-%E8%AE%B0%E5%BF%86-loop-%E7%9A%84%E5%91%BD%E6%A0%B9%E5%AD%90)
- **M2-15** 模型在两次运行之间会忘掉一切，今天的循环干了什么、哪些卡住了，明天的循环一概不知；所以记忆要放在一个 markdown 文件或任务看板这类活在单次对话之外的地方。Osmani 的总结是：agent 会忘，但 repo 不会。[原文§第六件：记忆，loop 的命根子](https://xiaolinnote.com/agent/engineering/loop-engineering.html#%E7%AC%AC%E5%85%AD%E4%BB%B6-%E8%AE%B0%E5%BF%86-loop-%E7%9A%84%E5%91%BD%E6%A0%B9%E5%AD%90)
- **M2-16** 原文的示例是：自动化每天早晨触发一个分诊 skill，它去读昨天的 CI 失败记录、还没关闭的 issue 和最近的提交，把哪些问题值得处理写进状态文件。[原文§Q4：拼起来之后，一个真实的 loop 长什么样？](https://xiaolinnote.com/agent/engineering/loop-engineering.html#q4-%E6%8B%BC%E8%B5%B7%E6%9D%A5%E4%B9%8B%E5%90%8E-%E4%B8%80%E4%B8%AA%E7%9C%9F%E5%AE%9E%E7%9A%84-loop-%E9%95%BF%E4%BB%80%E4%B9%88%E6%A0%B7)
- **M2-17** 先由分诊 skill 判断哪些问题值得处理并写入状态文件，再只为值得做的问题开 worktree、派 sub-agent 起草修复；搞不定的丢进待办收件箱，等真人来看。[原文§Q4：拼起来之后，一个真实的 loop 长什么样？](https://xiaolinnote.com/agent/engineering/loop-engineering.html#q4-%E6%8B%BC%E8%B5%B7%E6%9D%A5%E4%B9%8B%E5%90%8E-%E4%B8%80%E4%B8%AA%E7%9C%9F%E5%AE%9E%E7%9A%84-loop-%E9%95%BF%E4%BB%80%E4%B9%88%E6%A0%B7)
- **M2-18** 原文的示例除了定时触发，还把所有经过写回状态文件，让明天的循环从今天停下的地方继续，搞不定的问题则进入收件箱等人处理；人只在设计循环时和收件箱有东西时出现。[原文§Q4：拼起来之后，一个真实的 loop 长什么样？](https://xiaolinnote.com/agent/engineering/loop-engineering.html#q4-%E6%8B%BC%E8%B5%B7%E6%9D%A5%E4%B9%8B%E5%90%8E-%E4%B8%80%E4%B8%AA%E7%9C%9F%E5%AE%9E%E7%9A%84-loop-%E9%95%BF%E4%BB%80%E4%B9%88%E6%A0%B7)
- **M2-19** 第二个 sub-agent 对照项目的 skill 规范和现有测试，把修复草稿审一遍；审过之后，由 connector 自动开 PR、更新对应的工单。[原文§Q4：拼起来之后，一个真实的 loop 长什么样？](https://xiaolinnote.com/agent/engineering/loop-engineering.html#q4-%E6%8B%BC%E8%B5%B7%E6%9D%A5%E4%B9%8B%E5%90%8E-%E4%B8%80%E4%B8%AA%E7%9C%9F%E5%AE%9E%E7%9A%84-loop-%E9%95%BF%E4%BB%80%E4%B9%88%E6%A0%B7)
- **M2-20** 普通循环按节奏重复跑，例如每小时一次，跑完就结束，对不对另说；/goal 类能力则跑到写好的条件为真才停，并且每一轮结束后由一个独立的模型判断条件是否达成。[原文§Q5：工具已经追上来了，现在就能搭](https://xiaolinnote.com/agent/engineering/loop-engineering.html#q5-%E5%B7%A5%E5%85%B7%E5%B7%B2%E7%BB%8F%E8%BF%BD%E4%B8%8A%E6%9D%A5%E4%BA%86-%E7%8E%B0%E5%9C%A8%E5%B0%B1%E8%83%BD%E6%90%AD)
- **M2-21** 一年前搭一个 loop 意味着写一堆只有自己看得懂、还得永远自己维护的 bash 脚本；现在五大件全部内置在主流产品里，例如自动化在 Codex 里是 Automations 面板加分诊收件箱，在 Claude Code 里是计划任务、/loop 和 hooks，skill 对应 Agent Skills，connector 基于 MCP。[原文§Q5：工具已经追上来了，现在就能搭](https://xiaolinnote.com/agent/engineering/loop-engineering.html#q5-%E5%B7%A5%E5%85%B7%E5%B7%B2%E7%BB%8F%E8%BF%BD%E4%B8%8A%E6%9D%A5%E4%BA%86-%E7%8E%B0%E5%9C%A8%E5%B0%B1%E8%83%BD%E6%90%AD)
- **M2-22** 原文说明 /loop 依赖当前会话，适合当天的临时轮询，本机关掉后就停止；云端 Routines 把执行放到本机之外，才能在本机关掉后继续运行。这里比较的是会话内轮询与云端执行，不能把所有计划任务都理解为不依赖本机。[原文§实操：30 秒搭出你的第一个 loop](https://xiaolinnote.com/agent/engineering/loop-engineering.html#%E5%AE%9E%E6%93%8D-30-%E7%A7%92%E6%90%AD%E5%87%BA%E4%BD%A0%E7%9A%84%E7%AC%AC%E4%B8%80%E4%B8%AA-loop)
- **M2-23** 以“/loop 10m 检查当前分支 PR 的 CI 状态……”为例：10m 是心跳，每 10 分钟自动醒来跑一轮；中间那段是任务，即每一轮干什么；最后一句是停止条件加汇报，即什么时候算完、完了怎么交差。[原文§实操：30 秒搭出你的第一个 loop](https://xiaolinnote.com/agent/engineering/loop-engineering.html#%E5%AE%9E%E6%93%8D-30-%E7%A7%92%E6%90%AD%E5%87%BA%E4%BD%A0%E7%9A%84%E7%AC%AC%E4%B8%80%E4%B8%AA-loop)
- **M2-24** 把间隔省掉、直接 /loop 加任务时，节奏由模型自己定，它会根据 CI 一般要跑多久来决定多久看一次，不会一分钟刷一次。[原文§实操：30 秒搭出你的第一个 loop](https://xiaolinnote.com/agent/engineering/loop-engineering.html#%E5%AE%9E%E6%93%8D-30-%E7%A7%92%E6%90%AD%E5%87%BA%E4%BD%A0%E7%9A%84%E7%AC%AC%E4%B8%80%E4%B8%AA-loop)
- **M2-25** 不算，这是起点：最小 loop 只有心跳、任务和停止条件，先让它转起来，哪天觉得它自己改的代码不放心，再加上检查的 sub-agent，想同时盯几个 PR 再上 worktree；部件是一件一件长出来的，不是一天配齐的。[原文§实操：30 秒搭出你的第一个 loop](https://xiaolinnote.com/agent/engineering/loop-engineering.html#%E5%AE%9E%E6%93%8D-30-%E7%A7%92%E6%90%AD%E5%87%BA%E4%BD%A0%E7%9A%84%E7%AC%AC%E4%B8%80%E4%B8%AA-loop)
- **M2-26** 说明 loop 的设计正在变得工具无关，选 Codex 还是选 Claude Code 这类争论的重要性在下降；loop 的设计图纸才是你的资产，画好了放在哪家产品上都能转，值得积累的是图纸，而不是对某家工具的肌肉记忆。[原文§实操：30 秒搭出你的第一个 loop](https://xiaolinnote.com/agent/engineering/loop-engineering.html#%E5%AE%9E%E6%93%8D-30-%E7%A7%92%E6%90%AD%E5%87%BA%E4%BD%A0%E7%9A%84%E7%AC%AC%E4%B8%80%E4%B8%AA-loop)
- **M2-27** loop 改变了工作，但没有把你从工作中删除；而且有三个问题会随着 loop 越来越好用变得越来越尖锐。连给概念定名的 Osmani 本人也在博客里说，现在还早，自己持怀疑态度。[原文§Q6：三盆冷水：loop 越好用，这三个问题越尖锐](https://xiaolinnote.com/agent/engineering/loop-engineering.html#q6-%E4%B8%89%E7%9B%86%E5%86%B7%E6%B0%B4-loop-%E8%B6%8A%E5%A5%BD%E7%94%A8-%E8%BF%99%E4%B8%89%E4%B8%AA%E9%97%AE%E9%A2%98%E8%B6%8A%E5%B0%96%E9%94%90)
- **M2-28** 一个无人值守运行的 loop，也是一个无人值守犯错的 loop；就算配了负责检查的 sub-agent，它嘴里的 done 也只是一个声明，不是一个证明，它说没问题和真的没问题之间，还隔着你的眼睛。[原文§第一盆：验证仍然归你](https://xiaolinnote.com/agent/engineering/loop-engineering.html#%E7%AC%AC%E4%B8%80%E7%9B%86-%E9%AA%8C%E8%AF%81%E4%BB%8D%E7%84%B6%E5%BD%92%E4%BD%A0)
- **M2-29** 原文称理解债是仓库里实际存在的东西与人脑中真正理解的东西之间的鸿沟：代码可能不烂，但人不知道它为什么是对的，出问题那天面对的是一片自己拥有却不理解的代码。[原文§第二盆：理解债，越顺滑涨得越快](https://xiaolinnote.com/agent/engineering/loop-engineering.html#%E7%AC%AC%E4%BA%8C%E7%9B%86-%E7%90%86%E8%A7%A3%E5%80%BA-%E8%B6%8A%E9%A1%BA%E6%BB%91%E6%B6%A8%E5%BE%97%E8%B6%8A%E5%BF%AB)
- **M2-30** 技术债是代码烂；理解债是代码可能不烂，但人不知道它为什么对。loop 交付人没写过的代码越快，这条鸿沟越大，顺滑的 loop 只会让它涨得更快，除非坚持去读 loop 的产出。[原文§第二盆：理解债，越顺滑涨得越快](https://xiaolinnote.com/agent/engineering/loop-engineering.html#%E7%AC%AC%E4%BA%8C%E7%9B%86-%E7%90%86%E8%A7%A3%E5%80%BA-%E8%B6%8A%E9%A1%BA%E6%BB%91%E6%B6%A8%E5%BE%97%E8%B6%8A%E5%BF%AB)
- **M2-31** 办法是坚持去读 loop 产出的东西，否则理解债只会越涨越快。[原文§第二盆：理解债，越顺滑涨得越快](https://xiaolinnote.com/agent/engineering/loop-engineering.html#%E7%AC%AC%E4%BA%8C%E7%9B%86-%E7%90%86%E8%A7%A3%E5%80%BA-%E8%B6%8A%E9%A1%BA%E6%BB%91%E6%B6%A8%E5%BE%97%E8%B6%8A%E5%BF%AB)
- **M2-32** loop 是按循环烧 token 的，每多一个 sub-agent 就多一份模型和工具开销；原文建议把 sub-agent 用在值得买第二意见的地方，不要处处双保险。[原文§第三盆：认知投降，最舒服的姿势最危险](https://xiaolinnote.com/agent/engineering/loop-engineering.html#%E7%AC%AC%E4%B8%89%E7%9B%86-%E8%AE%A4%E7%9F%A5%E6%8A%95%E9%99%8D-%E6%9C%80%E8%88%92%E6%9C%8D%E7%9A%84%E5%A7%BF%E5%8A%BF%E6%9C%80%E5%8D%B1%E9%99%A9)
- **M2-33** 认知投降指不再对产出有自己的观点，它给什么就收什么。原文引述的说法是：带着判断力去设计 loop 是解药，为了逃避思考去设计 loop 是助燃剂，同一个动作结果相反。[原文§第三盆：认知投降，最舒服的姿势最危险](https://xiaolinnote.com/agent/engineering/loop-engineering.html#%E7%AC%AC%E4%B8%89%E7%9B%86-%E8%AE%A4%E7%9F%A5%E6%8A%95%E9%99%8D-%E6%9C%80%E8%88%92%E6%9C%8D%E7%9A%84%E5%A7%BF%E5%8A%BF%E6%9C%80%E5%8D%B1%E9%99%A9)
- **M2-34** 验证仍然归你、理解债、认知投降这三个问题都不是 loop 的 bug，而是 loop 的代价，并且由你来付。[原文§第三盆：认知投降，最舒服的姿势最危险](https://xiaolinnote.com/agent/engineering/loop-engineering.html#%E7%AC%AC%E4%B8%89%E7%9B%86-%E8%AE%A4%E7%9F%A5%E6%8A%95%E9%99%8D-%E6%9C%80%E8%88%92%E6%9C%8D%E7%9A%84%E5%A7%BF%E5%8A%BF%E6%9C%80%E5%8D%B1%E9%99%A9)
- **M2-35** 一个 loop 等于五大件加一份磁盘记忆：自动化是心跳，worktree 防打架，skill 治金鱼记忆，connector 摸到真实世界，sub-agent 写查分离，状态文件让明天接得上今天。[原文§最后](https://xiaolinnote.com/agent/engineering/loop-engineering.html#%E6%9C%80%E5%90%8E)

## 3. Loop 落地：上手路径、经济账与安全

原文：[Loop Engineering 怎么落地？一条从 0 到 1 的上手路径](https://xiaolinnote.com/agent/engineering/loop_engineering_handbook.html)。

- **M3-1** 原文把有没有一个能自动告诉你活砸了的裁判当作生死线，测试、类型检查、linter 或构建都行；没有裁判，loop 的产出还得人逐行读 diff 去验，也就没替人省下什么。[原文§先别急，你真需要 loop 吗？](https://xiaolinnote.com/agent/engineering/loop_engineering_handbook.html#%E5%85%88%E5%88%AB%E6%80%A5-%E4%BD%A0%E7%9C%9F%E9%9C%80%E8%A6%81-loop-%E5%90%97)
- **M3-2** loop 要花时间搭，一锤子买卖不如写个好 prompt；每周要干好几遍的活才值得。[原文§先别急，你真需要 loop 吗？](https://xiaolinnote.com/agent/engineering/loop_engineering_handbook.html#%E5%85%88%E5%88%AB%E6%80%A5-%E4%BD%A0%E7%9C%9F%E9%9C%80%E8%A6%81-loop-%E5%90%97)
- **M3-3** token 预算扛不扛得住浪费，loop 会反复读上下文、重试、试探，不出活也照样烧；agent 能不能跑它自己写的代码，要有日志、能复现、崩在哪看得见，否则没法自我修正；还有一道附加题：你打不打算 review 它产出的东西，不打算就别建。[原文§先别急，你真需要 loop 吗？](https://xiaolinnote.com/agent/engineering/loop_engineering_handbook.html#%E5%85%88%E5%88%AB%E6%80%A5-%E4%BD%A0%E7%9C%9F%E9%9C%80%E8%A6%81-loop-%E5%90%97)
- **M3-4** 架构、鉴权、支付、生产部署这几类，一出事就是大事，必须有人盯着；另外 loop 偏向花得起钱的人，token 管够的人用着顺手，背着消费套餐的人跑两轮可能就触顶，所以大部分人现在还用不上。[原文§先别急，你真需要 loop 吗？](https://xiaolinnote.com/agent/engineering/loop_engineering_handbook.html#%E5%85%88%E5%88%AB%E6%80%A5-%E4%BD%A0%E7%9C%9F%E9%9C%80%E8%A6%81-loop-%E5%90%97)
- **M3-5** automation，即 loop 的心跳，按定时或事件自动触发，停止条件一定要写死；skill，把框架、约定和踩过的坑写进文件放在仓库里，agent 每轮自己读；状态文件，记做完了什么、下一步干什么，让明天的循环接得上今天；闸门，即测试、类型检查、构建这类裁判，过不了就直接拦下，是 loop 唯一能挡住烂活的关卡。[原文§第一个 loop 该怎么搭？](https://xiaolinnote.com/agent/engineering/loop_engineering_handbook.html#%E7%AC%AC%E4%B8%80%E4%B8%AA-loop-%E8%AF%A5%E6%80%8E%E4%B9%88%E6%90%AD)
- **M3-6** 最简单是在仓库里放一个 STATE.md，跟代码一起管，改了能 diff，谁打开都看得懂，个人或小团队够用；想更正式就接到外部系统，如 Linear、GitHub Issues 甚至一张数据库表，好处是能跨多个仓库、随时能查，团队每个人都看得到 loop 在做什么，更适合上生产的 loop。[原文§第一个 loop 该怎么搭？](https://xiaolinnote.com/agent/engineering/loop_engineering_handbook.html#%E7%AC%AC%E4%B8%80%E4%B8%AA-loop-%E8%AF%A5%E6%80%8E%E4%B9%88%E6%90%AD)
- **M3-7** 大致分四块：进行中、今天完成、卡住了等人看、下一步；例如进行中是升级某个依赖、本地测试已过在等 CI，卡住的是复现不稳定的偶发超时，下一步是扫一遍本周新开的 issue、挑能自动改的。[原文§第一个 loop 该怎么搭？](https://xiaolinnote.com/agent/engineering/loop_engineering_handbook.html#%E7%AC%AC%E4%B8%80%E4%B8%AA-loop-%E8%AF%A5%E6%80%8E%E4%B9%88%E6%90%AD)
- **M3-8** 状态文件记的是它现在做到哪了，目标文件（VISION.md 或 AGENTS.md）管的是它最终要去哪，一个盯当下、一个盯方向；loop 跑久了容易跑偏，所以最好放一个常驻的目标文件，每轮开工前先让它读一遍，少了哪个它都会跑着跑着忘了自己在干什么。[原文§第一个 loop 该怎么搭？](https://xiaolinnote.com/agent/engineering/loop_engineering_handbook.html#%E7%AC%AC%E4%B8%80%E4%B8%AA-loop-%E8%AF%A5%E6%80%8E%E4%B9%88%E6%90%AD)
- **M3-9** 正确走法是先让一次手动运行稳稳跑通，再把背景沉淀成 skill，再包成 loop，最后才接上自动调度；新手常犯的错是一上来就想搭无所不能的系统，自动化、并行、写查分离、连一堆外部工具一步到位，结果被联调问题劝退，或搭出没法 debug 的庞然大物，出了岔子也分不清是哪一环的问题。[原文§第一个 loop 该怎么搭？](https://xiaolinnote.com/agent/engineering/loop_engineering_handbook.html#%E7%AC%AC%E4%B8%80%E4%B8%AA-loop-%E8%AF%A5%E6%80%8E%E4%B9%88%E6%90%AD)
- **M3-10** 自动化是心跳，按时间或事件触发；worktree 给并行的 agent 各分一间独立工作区；skill 存项目背景、约定和坑；connector 走 MCP 接上 GitHub、Slack、Jira；sub-agent 把写代码的和验收的拆成两个。在 Claude Code 里，自动化是 /loop 配上桌面端定时任务和云端 Routines，worktree 内置，skill 是 SKILL.md 文件，connector 走 MCP。[原文§完整的 loop 还缺哪几块？](https://xiaolinnote.com/agent/engineering/loop_engineering_handbook.html#%E5%AE%8C%E6%95%B4%E7%9A%84-loop-%E8%BF%98%E7%BC%BA%E5%93%AA%E5%87%A0%E5%9D%97)
- **M3-11** Anthropic 早在 2024 年底就写进了工程博客，叫 evaluator-optimizer；道理是让写代码的模型给自己打分会手下留情，换一个干净上下文、带着不同指令的第二个 agent 来挑刺才揪得出毛病。loop 是在人不看的时候跑的，一个信得过的验证器是敢撒手走开的唯一底气。[原文§完整的 loop 还缺哪几块？](https://xiaolinnote.com/agent/engineering/loop_engineering_handbook.html#%E5%AE%8C%E6%95%B4%E7%9A%84-loop-%E8%BF%98%E7%BC%BA%E5%93%AA%E5%87%A0%E5%9D%97)
- **M3-12** 内层 loop 负责干活；外层 loop 专门吸收人每次 review 时的反馈，拿去改进下一轮怎么干，让同样的问题下回不再犯。[原文§loop 到底能拿来干嘛？](https://xiaolinnote.com/agent/engineering/loop_engineering_handbook.html#loop-%E5%88%B0%E5%BA%95%E8%83%BD%E6%8B%BF%E6%9D%A5%E5%B9%B2%E5%98%9B)
- **M3-13** 最轻一档是盯自己手头的活，一条 /loop 命令就行，例如等 CI、监控部署、汇总消息；中间一档是每天定时清理，要用上各种构件，例如晨间分诊、定时修 CI、依赖升级；最重一档是让 loop 自己接活、自己验活，例如自动读 issue、对照愿景文档判断是否合方向、起草 PR 并让另一个 agent 先 review。[原文§loop 到底能拿来干嘛？](https://xiaolinnote.com/agent/engineering/loop_engineering_handbook.html#loop-%E5%88%B0%E5%BA%95%E8%83%BD%E6%8B%BF%E6%9D%A5%E5%B9%B2%E5%98%9B)
- **M3-14** /loop 绑在当前会话上，关掉终端它就停了，适合今天就盯这一件事的临时轮询；/schedule 这类方式把任务丢到云端，人下班、关了机，它还在云端接着跑。[原文§loop 到底能拿来干嘛？](https://xiaolinnote.com/agent/engineering/loop_engineering_handbook.html#loop-%E5%88%B0%E5%BA%95%E8%83%BD%E6%8B%BF%E6%9D%A5%E5%B9%B2%E5%98%9B)
- **M3-15** 普通 /loop 按固定节奏重复跑，例如每十分钟一轮，这轮干得对不对它不管；/goal 盯着一个写好的条件跑，比如所有测试都变绿，条件不达成就一直跑，达成了才收手，而且条件是否达成由另派的一个独立小模型来判，不让动手的 agent 自己下结论。[原文§loop 到底能拿来干嘛？](https://xiaolinnote.com/agent/engineering/loop_engineering_handbook.html#loop-%E5%88%B0%E5%BA%95%E8%83%BD%E6%8B%BF%E6%9D%A5%E5%B9%B2%E5%98%9B)
- **M3-16** 每天早上自动跑一轮，读昨天挂掉的 CI、还开着的 issue 和最近的提交，判断哪些值得处理并写进状态文件，能自己修的修掉提 PR，搞不定的丢进收件箱等人；类似的还有每天凌晨定时修 CI，以及依赖升级：定期查新版本，升完跑测试，绿了才提 PR。[原文§loop 到底能拿来干嘛？](https://xiaolinnote.com/agent/engineering/loop_engineering_handbook.html#loop-%E5%88%B0%E5%BA%95%E8%83%BD%E6%8B%BF%E6%9D%A5%E5%B9%B2%E5%98%9B)
- **M3-17** 一次调用的价格没有计入反复运行的 Token、算力和人工审查时间，也没有反映产出是否被接受。Loop 会持续消耗这些资源，被拒绝的改动也有成本；所以原文用这段时间的总成本除以真正被合并的改动数，衡量一次有效交付花了多少。[原文§你的 loop 是赚是亏？](https://xiaolinnote.com/agent/engineering/loop_engineering_handbook.html#%E4%BD%A0%E7%9A%84-loop-%E6%98%AF%E8%B5%9A%E6%98%AF%E4%BA%8F)
- **M3-18** 把这段时间烧的 token、占用的算力和人 review 花掉的时间全部加起来，再除以真正被合并的改动数；另外每多挂一个做检查的 sub-agent，就多一份模型和工具费用。[原文§你的 loop 是赚是亏？](https://xiaolinnote.com/agent/engineering/loop_engineering_handbook.html#%E4%BD%A0%E7%9A%84-loop-%E6%98%AF%E8%B5%9A%E6%98%AF%E4%BA%8F)
- **M3-19** 原文的解释是：被打回或直接扔掉的改动同样消耗了 token 和人的审查精力，这些废品的成本要摊到被接受的改动上，接受率太低时就超过了它省下的工作量。[原文§你的 loop 是赚是亏？](https://xiaolinnote.com/agent/engineering/loop_engineering_handbook.html#%E4%BD%A0%E7%9A%84-loop-%E6%98%AF%E8%B5%9A%E6%98%AF%E4%BA%8F)
- **M3-20** 原文把“接受率低于 50%”作为应当调整或关闭 Loop 的经验红线，理由是被拒绝的产出仍消耗模型资源和审查精力；实际成本核算仍看同节给出的“总成本 ÷ 被合并改动数”。[原文§你的 loop 是赚是亏？](https://xiaolinnote.com/agent/engineering/loop_engineering_handbook.html#%E4%BD%A0%E7%9A%84-loop-%E6%98%AF%E8%B5%9A%E6%98%AF%E4%BA%8F)
- **M3-21** sub-agent 是按个烧钱的，每多挂一个做检查的，就多花一份模型和工具的钱；所以“再请一个 agent 来挑刺”只用在真正值得买第二意见的地方，token 宽裕的人和精打细算的人搭出来的 loop 会很不一样。[原文§你的 loop 是赚是亏？](https://xiaolinnote.com/agent/engineering/loop_engineering_handbook.html#%E4%BD%A0%E7%9A%84-loop-%E6%98%AF%E8%B5%9A%E6%98%AF%E4%BA%8F)
- **M3-22** 闸门里除了测试和构建，还要加入 SAST 静态安全扫描、依赖审计和密钥扫描，让安全检查与功能检查同等对待。[原文§没人盯着，安全怎么办？](https://xiaolinnote.com/agent/engineering/loop_engineering_handbook.html#%E6%B2%A1%E4%BA%BA%E7%9B%AF%E7%9D%80-%E5%AE%89%E5%85%A8%E6%80%8E%E4%B9%88%E5%8A%9E)
- **M3-23** 原文引用的研究称 skill 泄露凭证的头号途径是调试日志，print、console.log 这类打到标准输出的操作占 73.5%；所以自动安装 skill 前要通读源码，生产上跑的 loop 要关掉 verbose 日志。[原文§没人盯着，安全怎么办？](https://xiaolinnote.com/agent/engineering/loop_engineering_handbook.html#%E6%B2%A1%E4%BA%BA%E7%9B%AF%E7%9D%80-%E5%AE%89%E5%85%A8%E6%80%8E%E4%B9%88%E5%8A%9E)
- **M3-24** 原文称权限蔓延是今天加一个写权限、明天再加一个，一个月后自己都说不清它能动哪些东西；办法是每 30 天把它的权限拉出来复审一遍，不再需要的收回。[原文§没人盯着，安全怎么办？](https://xiaolinnote.com/agent/engineering/loop_engineering_handbook.html#%E6%B2%A1%E4%BA%BA%E7%9B%AF%E7%9D%80-%E5%AE%89%E5%85%A8%E6%80%8E%E4%B9%88%E5%8A%9E)
- **M3-25** loop 在你不看的时候替你干活，同样在你不看的时候敞着一个没人守的口子：自动开 PR、自动装 skill、自动连外部工具，每一个口子都可能被人钻，所以原文建议把几条红线直接焊死在闸门里。[原文§没人盯着，安全怎么办？](https://xiaolinnote.com/agent/engineering/loop_engineering_handbook.html#%E6%B2%A1%E4%BA%BA%E7%9B%AF%E7%9D%80-%E5%AE%89%E5%85%A8%E6%80%8E%E4%B9%88%E5%8A%9E)
- **M3-26** 今年 4 月 arXiv 上的《Credential Leakage in LLM Agent Skills》从一个 skill 平台的十几万个 skill 里抽样分析了 17022 个，发现其中 520 个会泄露凭证，共 1708 处问题；这些泄露里将近九成不需要任何权限就能被利用。因此 skill 本身就是注入入口，自动安装前要把源码从头到尾读一遍。[原文§没人盯着，安全怎么办？](https://xiaolinnote.com/agent/engineering/loop_engineering_handbook.html#%E6%B2%A1%E4%BA%BA%E7%9B%AF%E7%9D%80-%E5%AE%89%E5%85%A8%E6%80%8E%E4%B9%88%E5%8A%9E)
- **M3-27** 这是工程师 Geoffrey Huntley 命名的失败模式：没有硬 gate，loop 会半途装作完工，还在那儿空烧钱；防法是用客观的 gate（比如测试过没过）判断完成，别让 agent 自己喊一声“干完了”就退出。[原文§最后：14 步清单带走](https://xiaolinnote.com/agent/engineering/loop_engineering_handbook.html#%E6%9C%80%E5%90%8E-14-%E6%AD%A5%E6%B8%85%E5%8D%95%E5%B8%A6%E8%B5%B0)
- **M3-28** 每周至少干一次、有 gate 能拒掉坏活、agent 跑得了代码、有硬性 stop、不可逆操作前有人把关。[原文§最后：14 步清单带走](https://xiaolinnote.com/agent/engineering/loop_engineering_handbook.html#%E6%9C%80%E5%90%8E-14-%E6%AD%A5%E6%B8%85%E5%8D%95%E5%B8%A6%E8%B5%B0)
- **M3-29** 安全税是代码上线前加安全扫描、skill 装前审源码、生产环境关 verbose 日志、权限每 30 天复审；还理解债是坚持读 diff、抽查闸门、别让 loop 碰架构。[原文§最后：14 步清单带走](https://xiaolinnote.com/agent/engineering/loop_engineering_handbook.html#%E6%9C%80%E5%90%8E-14-%E6%AD%A5%E6%B8%85%E5%8D%95%E5%B8%A6%E8%B5%B0)
- **M3-30** 难的不在中间搭建那段，构件工具早已备好；难的是头一段的“要不要做”和尾一段的“守不守得住”，全是关于人的判断。手册结尾的话是 Build the loop, stay the engineer：把 loop 搭起来，但人还得是那个工程师。[原文§最后：14 步清单带走](https://xiaolinnote.com/agent/engineering/loop_engineering_handbook.html#%E6%9C%80%E5%90%8E-14-%E6%AD%A5%E6%B8%85%E5%8D%95%E5%B8%A6%E8%B5%B0)

## 4. Graph Engineering：节点、边、状态与图式编排

原文：[Graph Engineering 是什么？一文讲透多 Agent 图式编排](https://xiaolinnote.com/agent/engineering/graph-engineering.html)。

- **M4-1** loop 可以看作只有一个节点、一条指回自身的边的最小 graph；loop 管节点内部的反复思考、调用工具和修正结果，graph 管节点之间的拆分、并行、汇合和返工，两者不冲突。[原文§什么是 Graph Engineering？](https://xiaolinnote.com/agent/engineering/graph-engineering.html#%E4%BB%80%E4%B9%88%E6%98%AF-graph-engineering)
- **M4-2** graph 是数据结构里节点加连线的那个图，节点叫 Node，连线叫边（Edge）；graph engineering 按照任务之间的依赖关系用 graph 来编排整个流程，该串行的串行、该并行的并行，每一块交给一个职责明确的节点去完成，提醒你别把本来可以并行、分支执行的任务强行改成全程串行。[原文§什么是 Graph Engineering？](https://xiaolinnote.com/agent/engineering/graph-engineering.html#%E4%BB%80%E4%B9%88%E6%98%AF-graph-engineering)
- **M4-3** 慢，明明后端、前端、测试能三路一起跑也得排队；没有状态和存档机制，全部家当只剩一长串聊天记录，中断了要么从头重跑、要么自己翻上下文抢救；很难中途暂停等人工审批、隔天从断点继续；也很难表达复杂分工，它擅长回答下一步做什么，不擅长表达谁来做、哪几个一起做、做完在哪里汇合。[原文§什么是 Graph Engineering？](https://xiaolinnote.com/agent/engineering/graph-engineering.html#%E4%BB%80%E4%B9%88%E6%98%AF-graph-engineering)
- **M4-4** 这两年模型完成单个步骤已经越来越可靠，真正容易翻车的是一百个步骤怎么协作起来；串行流程缺的不是脑子，而是任务调度和流程管理能力，即把任务分给多个 agent 同时执行、记录每一步的进度、执行中断后还能恢复，graph engineering 补上的就是这一层。[原文§什么是 Graph Engineering？](https://xiaolinnote.com/agent/engineering/graph-engineering.html#%E4%BB%80%E4%B9%88%E6%98%AF-graph-engineering)
- **M4-5** 原文说设计一条边要回答两个问题：下一个节点由代码规则还是模型决定，以及是否根据上一步结果分叉。条件边与确定性边、模型决策边不是并列关系，一条条件边既可以由代码判断，也可以由模型判断。[原文§Graph Engineering 的工作原理是什么？](https://xiaolinnote.com/agent/engineering/graph-engineering.html#graph-engineering-%E7%9A%84%E5%B7%A5%E4%BD%9C%E5%8E%9F%E7%90%86%E6%98%AF%E4%BB%80%E4%B9%88)
- **M4-6** 它会按测试结果走向不同节点，所以是条件边；而测试是否通过可以由写进代码的固定规则读取结果后判断，不需要模型参与，所以它同时是一条由代码判断的边。[原文§Graph Engineering 的工作原理是什么？](https://xiaolinnote.com/agent/engineering/graph-engineering.html#graph-engineering-%E7%9A%84%E5%B7%A5%E4%BD%9C%E5%8E%9F%E7%90%86%E6%98%AF%E4%BB%80%E4%B9%88)
- **M4-7** 原文要求定义三样：节点，即只干一件事的 agent、普通代码或人工环节；边，即下一步执行哪个节点、是否按结果分叉；状态，即字段结构固定、记录进度、产物和 token 消耗的对象，并在节点完成后保存下来。[原文§Graph Engineering 的工作原理是什么？](https://xiaolinnote.com/agent/engineering/graph-engineering.html#graph-engineering-%E7%9A%84%E5%B7%A5%E4%BD%9C%E5%8E%9F%E7%90%86%E6%98%AF%E4%BB%80%E4%B9%88)
- **M4-8** 用 graph 来编排并不会自动存档，还得靠运行框架，或者自己把状态写进数据库、文件；有了存档，中断后才能读档接着跑。[原文§Graph Engineering 的工作原理是什么？](https://xiaolinnote.com/agent/engineering/graph-engineering.html#graph-engineering-%E7%9A%84%E5%B7%A5%E4%BD%9C%E5%8E%9F%E7%90%86%E6%98%AF%E4%BB%80%E4%B9%88)
- **M4-9** 好节点只干一件事，单独就能测，哪天想换掉它别的节点也不受牵连，身兼五职的节点就是又一个大 loop；节点可以是一个跑着完整思考循环的 agent，也可以是一段按固定规则运行的普通代码或一次数据库查询，人也可以是节点，审批环节就是一个人类节点。[原文§Graph Engineering 的工作原理是什么？](https://xiaolinnote.com/agent/engineering/graph-engineering.html#graph-engineering-%E7%9A%84%E5%B7%A5%E4%BD%9C%E5%8E%9F%E7%90%86%E6%98%AF%E4%BB%80%E4%B9%88)
- **M4-10** 由提前写进代码的固定规则决定下一个节点的叫确定性边（Deterministic Edge），比如测试全部通过就进入部署；交给模型判断的叫模型决策边（Model-decided Edge），比如工单该派给退款节点还是投诉节点。设计的功夫在于分清哪条边该写死、哪条该交给模型，能写死的尽量写死，把模型的判断留给少数确实需要理解语义的分支。[原文§Graph Engineering 的工作原理是什么？](https://xiaolinnote.com/agent/engineering/graph-engineering.html#graph-engineering-%E7%9A%84%E5%B7%A5%E4%BD%9C%E5%8E%9F%E7%90%86%E6%98%AF%E4%BB%80%E4%B9%88)
- **M4-11** 状态是一个字段结构固定的对象，像一张任务进度表或一份结构化的 JSON，每个节点的产出、测试结果、消耗的 token 都是明确的字段；谁要看进度读这个对象就行，不用翻聊天记录，而且程序能直接读，条件判断读取测试结果字段后就知道该继续执行还是返回返工节点，存档和返工才转得起来。[原文§Graph Engineering 的工作原理是什么？](https://xiaolinnote.com/agent/engineering/graph-engineering.html#graph-engineering-%E7%9A%84%E5%B7%A5%E4%BD%9C%E5%8E%9F%E7%90%86%E6%98%AF%E4%BB%80%E4%B9%88)
- **M4-12** 让一个节点同时分出三条边、启动三个节点，这个动作叫分支并行（fan-out），干完再汇合叫 fan-in；想暂停等审批，就在流程中增加一个等待人工确认的节点；想中断后接着跑，读上一个存档点、重试那一个节点就行，不用从头来。[原文§Graph Engineering 的工作原理是什么？](https://xiaolinnote.com/agent/engineering/graph-engineering.html#graph-engineering-%E7%9A%84%E5%B7%A5%E4%BD%9C%E5%8E%9F%E7%90%86%E6%98%AF%E4%BB%80%E4%B9%88)
- **M4-13** 任务能拆成互相独立的子任务且需要缩短总耗时；不同环节需要不同的模型、工具、权限，比如干活的节点可写、审查的节点只读；流程中间有必须人工确认的环节；任务执行时间长、分支多，需要随时查看每个分支的进度、产物和 token 消耗。符合两三条再考虑，前提是先确保每个节点都能稳定完成一件事。[原文§真的需要用 graph 来编排吗？](https://xiaolinnote.com/agent/engineering/graph-engineering.html#%E7%9C%9F%E7%9A%84%E9%9C%80%E8%A6%81%E7%94%A8-graph-%E6%9D%A5%E7%BC%96%E6%8E%92%E5%90%97)
- **M4-14** 手上大部分任务按顺序执行就够了：写个脚本、修个 bug、做个简单调研，前后步骤很明确，强行用 graph 编排纯属给自己找罪受，一个人一下午能干完的任务没必要开项目启动会。[原文§真的需要用 graph 来编排吗？](https://xiaolinnote.com/agent/engineering/graph-engineering.html#%E7%9C%9F%E7%9A%84%E9%9C%80%E8%A6%81%E7%94%A8-graph-%E6%9D%A5%E7%BC%96%E6%8E%92%E5%90%97)
- **M4-15** 原文的前提是三路先约定同一份 API 契约，各自在独立的 git worktree 里开发、互不碰对方文件，并且每个节点完成后都保存过状态；因此只有出问题的那一路返工，另外两路保留已有结果。[原文§怎样用 graph 编排一个开发需求？](https://xiaolinnote.com/agent/engineering/graph-engineering.html#%E6%80%8E%E6%A0%B7%E7%94%A8-graph-%E7%BC%96%E6%8E%92%E4%B8%80%E4%B8%AA%E5%BC%80%E5%8F%91%E9%9C%80%E6%B1%82)
- **M4-16** 在共用同一份 API 契约的前提下，未出问题的分支可以直接保留结果，不必重做。[原文§怎样用 graph 编排一个开发需求？](https://xiaolinnote.com/agent/engineering/graph-engineering.html#%E6%80%8E%E6%A0%B7%E7%94%A8-graph-%E7%BC%96%E6%8E%92%E4%B8%80%E4%B8%AA%E5%BC%80%E5%8F%91%E9%9C%80%E6%B1%82)
- **M4-17** 规划节点把需求拆成后端、前端、测试三份任务，同时确定一份三方共用的 API 契约，一起写进状态对象，这一步用模型，因为拆任务和定契约需要判断；然后进入并行分支，三个开发节点同时启动，各自在独立的 git worktree 里干活，每个节点内部是一个标准的编码 loop：领任务、写代码、自测、提交。[原文§怎样用 graph 编排一个开发需求？](https://xiaolinnote.com/agent/engineering/graph-engineering.html#%E6%80%8E%E6%A0%B7%E7%94%A8-graph-%E7%BC%96%E6%8E%92%E4%B8%80%E4%B8%AA%E5%BC%80%E5%8F%91%E9%9C%80%E6%B1%82)
- **M4-18** 三个分支汇合到集成节点，合并后跑全量测试；接着是条件边，测试失败就把状态对象里对应模块的任务标记成返工，交回那个开发节点重做，测试全部通过则继续；最后停在人工确认节点，这个节点不执行自动化任务，只暂停流程等本人看 diff 点头，graph 才走完最后一条边、合入主干。[原文§怎样用 graph 编排一个开发需求？](https://xiaolinnote.com/agent/engineering/graph-engineering.html#%E6%80%8E%E6%A0%B7%E7%94%A8-graph-%E7%BC%96%E6%8E%92%E4%B8%80%E4%B8%AA%E5%BC%80%E5%8F%91%E9%9C%80%E6%B1%82)
- **M4-19** 示例注册了一个返工节点：测试失败就进入它，返工完成后回到集成节点，再跑一次测试。[原文§用 LangGraph 怎么写？](https://xiaolinnote.com/agent/engineering/graph-engineering.html#%E7%94%A8-langgraph-%E6%80%8E%E4%B9%88%E5%86%99)
- **M4-20** StateGraph(DevState) 创建一张 graph，DevState 是状态对象，每个节点都能读写它；add_node 把规划、后端、前端、测试、集成、返工和人工确认注册成节点；add_edge 把三个开发节点连到集成节点，表示必须三个都完成才能进入；add_conditional_edges 读取测试结果决定去人工确认还是返工；compile() 把节点和边组装成可执行的 graph。[原文§用 LangGraph 怎么写？](https://xiaolinnote.com/agent/engineering/graph-engineering.html#%E7%94%A8-langgraph-%E6%80%8E%E4%B9%88%E5%86%99)

- **M4-22** 一次 subagent 执行可以充当一个节点：在 .claude/agents/ 目录下，一个 md 文件定义一个专职 agent，写清职责、能用哪些工具、用哪个模型，干活的给写权限，审查的只给只读；hook 可以在特定时机强制执行固定检查，比如在 agent 结束任务前自动运行测试，没通过就继续修改。[原文§用 Claude Code 怎么玩？](https://xiaolinnote.com/agent/engineering/graph-engineering.html#%E7%94%A8-claude-code-%E6%80%8E%E4%B9%88%E7%8E%A9)
- **M4-23** 新版 Claude Code 内置了 workflow 编排能力，workflow 可以理解成一段负责拆任务、派 agent、等结果和处理分支的调度脚本；脚本不用人写，只要在对话框里把目标讲清楚，它会自己写出脚本、展示编排方案等人确认，再派出一队 subagent 在后台执行。[原文§用 Claude Code 怎么玩？](https://xiaolinnote.com/agent/engineering/graph-engineering.html#%E7%94%A8-claude-code-%E6%80%8E%E4%B9%88%E7%8E%A9)
- **M4-24** 它先讲清楚打算怎么拆，并主动写了一份 API 契约，让三路 agent 按同一份契约开发；编排方案分两个阶段，第一阶段三个 agent 并行开发，第二阶段负责集成和测试；跑完后报告测试用例全部通过并请人验收，人回复确认这一步就是人类节点，确认后才把代码合入主干。[原文§用 Claude Code 怎么玩？](https://xiaolinnote.com/agent/engineering/graph-engineering.html#%E7%94%A8-claude-code-%E6%80%8E%E4%B9%88%E7%8E%A9)
- **M4-25** 它是 Claude Code 内置的命令，会拆解问题、并行搜索、抓原文、交叉验证，最后合成一份带引用的报告；原文的实测里，它把调研拆成拆解、搜索、抓取、验证、综合五个阶段，其中搜索这一步又拆成 5 个角度，由 5 个 agent 并行去查。[原文§用 Claude Code 怎么玩？](https://xiaolinnote.com/agent/engineering/graph-engineering.html#%E7%94%A8-claude-code-%E6%80%8E%E4%B9%88%E7%8E%A9)
- **M4-26** 主会话只负责拆解任务、启动 subagent、等待结果和最终汇总，不再亲自完成中间每一步；具体的开发和搜索工作在各个 subagent 的独立上下文里进行，大量中间推理、工具输出和临时结果不必塞回主会话，只返回后续流程真正用得上的结果，避免主会话被中间过程占满。[原文§用 Claude Code 怎么玩？](https://xiaolinnote.com/agent/engineering/graph-engineering.html#%E7%94%A8-claude-code-%E6%80%8E%E4%B9%88%E7%8E%A9)
- **M4-27** Graph Engineering 是设计方法，关注任务怎么拆、哪些步骤可并行、下一步由什么决定、状态怎么记录、失败后怎么返工；LangGraph 是实现这套方法的一种框架，提供现成的节点、边、状态和流程控制，也可以换用别的框架或自己写调度代码。[原文§Graph Engineering 和 LangGraph 有什么区别？](https://xiaolinnote.com/agent/engineering/graph-engineering.html#graph-engineering-%E5%92%8C-langgraph-%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)
- **M4-28** 不是。新的是 graph engineering 这个名字，以及大家把注意力从单个 agent 怎么完成一步任务，转向多个 agent 怎么共同完成一条复杂流程；这个词刚开始刷屏，LangChain 官方就发博客说这套东西他们已经做了好几年。[原文§Graph Engineering 和 LangGraph 有什么区别？](https://xiaolinnote.com/agent/engineering/graph-engineering.html#graph-engineering-%E5%92%8C-langgraph-%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)
- **M4-29** 任务很小、按顺序就能完成的，直接交给一个 agent 跑完就行；只有当任务可以拆成多个并行分支、中间需要人工确认、执行中断后还要继续，或者需要长期追踪进度和产物时，graph 编排的价值才会体现出来。真正值得关注的是背后的问题：几十个步骤怎么稳定地协作起来。[原文§最后](https://xiaolinnote.com/agent/engineering/graph-engineering.html#%E6%9C%80%E5%90%8E)
