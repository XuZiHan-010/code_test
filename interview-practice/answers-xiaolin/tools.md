# LLM 工具调用 原文章节摘编

仅依据各题所列的小林面试笔记原文章节整理；本文件只整理原文口径，不作现行规格认证。原文未覆盖的部分明确标注，不使用其他网站补充。整理日期：2026-10-13。

## 1. Function Calling

原文：[1. 什么是 Function Calling ？原理是什么？](https://xiaolinnote.com/ai/tools/1_function_calling.html)。

- **C1-1** 开发者用 JSON schema 描述工具，模型需要时直接输出结构化的 JSON 调用请求，由代码按格式解析执行；此前只能靠解析自然语言判断模型想调什么，模型换个说法 if/else 就失配，也无法标准化。 [原文§背景，Function Calling 解决了什么问题](https://xiaolinnote.com/ai/tools/1_function_calling.html#%E8%83%8C%E6%99%AF-function-calling-%E8%A7%A3%E5%86%B3%E4%BA%86%E4%BB%80%E4%B9%88%E9%97%AE%E9%A2%98)[原文§💡 简要回答](https://xiaolinnote.com/ai/tools/1_function_calling.html#%F0%9F%92%A1-%E7%AE%80%E8%A6%81%E5%9B%9E%E7%AD%94)
- **C1-2** name 是工具的唯一标识，模型在 tool_calls 中用它指定工具；description 说明用途、适用条件和参数含义，影响是否调用与怎样填参；parameters 的 JSON Schema 列出参数字段、类型、枚举和必填项，例如 city 必填、unit 只能在两种温度单位中选择，用于约束调用参数的结构与取值。 [原文§工具定义，schema 的每个字段都有含义](https://xiaolinnote.com/ai/tools/1_function_calling.html#%E5%B7%A5%E5%85%B7%E5%AE%9A%E4%B9%89-schema-%E7%9A%84%E6%AF%8F%E4%B8%AA%E5%AD%97%E6%AE%B5%E9%83%BD%E6%9C%89%E5%90%AB%E4%B9%89)
- **C1-3** 由宿主程序代码执行。模型全程只是下指令：决定调哪个工具、参数填什么，它不亲自执行任何代码，也没有直接访问网络的权限。[原文§三个角色，把 Function Calling 理解成一场任务委托](https://xiaolinnote.com/ai/tools/1_function_calling.html#%E4%B8%89%E4%B8%AA%E8%A7%92%E8%89%B2-%E6%8A%8A-function-calling-%E7%90%86%E8%A7%A3%E6%88%90%E4%B8%80%E5%9C%BA%E4%BB%BB%E5%8A%A1%E5%A7%94%E6%89%98)
- **C1-4** 工具执行结果以 role 为 tool 的消息塞回对话历史后再次调用模型，模型有了工具结果、信息充分了，才能给出最终的自然语言答案。[原文§完整的调用流程，两轮对话加中间执行](https://xiaolinnote.com/ai/tools/1_function_calling.html#%E5%AE%8C%E6%95%B4%E7%9A%84%E8%B0%83%E7%94%A8%E6%B5%81%E7%A8%8B-%E4%B8%A4%E8%BD%AE%E5%AF%B9%E8%AF%9D%E5%8A%A0%E4%B8%AD%E9%97%B4%E6%89%A7%E8%A1%8C)
- **C1-5** 模型可以在一次响应里输出多个 tool_calls，代码同时执行后把所有结果一次性塞回对话；前提是这几个工具之间没有依赖关系，后一个调用依赖前一个结果时只能串行。[原文§并行工具调用](https://xiaolinnote.com/ai/tools/1_function_calling.html#%E5%B9%B6%E8%A1%8C%E5%B7%A5%E5%85%B7%E8%B0%83%E7%94%A8)

### 补充考点

- **C1-6** 描述越清晰，模型的选择越准确：只写获取天气，和写明查询指定城市的实时天气、包含哪些信息、仅支持哪些城市，对判断准确率的影响差距很明显；参数的 description 同理，格式要求、示例值和限制条件都要写进去，模型才能正确填写参数。[原文§工具定义，schema 的每个字段都有含义](https://xiaolinnote.com/ai/tools/1_function_calling.html#%E5%B7%A5%E5%85%B7%E5%AE%9A%E4%B9%89-schema-%E7%9A%84%E6%AF%8F%E4%B8%AA%E5%AD%97%E6%AE%B5%E9%83%BD%E6%9C%89%E5%90%AB%E4%B9%89)
- **C1-7** 没有并行调用时，每个工具都要单独走一轮对话，每轮都有一次模型推理和一次工具执行的延迟；有了并行调用，模型一次输出多个调用请求，代码同时执行这些工具，拿到全部结果后一次性塞回对话，再调一次模型就得到最终答案，从多轮对话压缩成一轮对话加并行执行。[原文§并行工具调用](https://xiaolinnote.com/ai/tools/1_function_calling.html#%E5%B9%B6%E8%A1%8C%E5%B7%A5%E5%85%B7%E8%B0%83%E7%94%A8)
- **C1-8** 互不影响的调用可以并行，例如分别查北京和上海的天气；第二个调用依赖第一个结果时只能串行，例如先查订单号、再用订单号查物流，模型也会分两轮输出。[原文§并行工具调用](https://xiaolinnote.com/ai/tools/1_function_calling.html#%E5%B9%B6%E8%A1%8C%E5%B7%A5%E5%85%B7%E8%B0%83%E7%94%A8)

## 2. 模型怎样学会调工具

原文：[2. LLM 是如何学会调用外部工具的？](https://xiaolinnote.com/ai/tools/2_llm_tool_learning.html)。

- **C2-1** 预训练只学给定前文预测下一个 token，全程在文本空间里进行，从未见过工具调用；即使提示词说可以调用 API，它也只会生成一段自然语言描述，而不是可以被程序解析的 JSON 调用请求。[原文§原始 LLM 的世界，为什么不会调工具](https://xiaolinnote.com/ai/tools/2_llm_tool_learning.html#%E5%8E%9F%E5%A7%8B-llm-%E7%9A%84%E4%B8%96%E7%95%8C-%E4%B8%BA%E4%BB%80%E4%B9%88%E4%B8%8D%E4%BC%9A%E8%B0%83%E5%B7%A5%E5%85%B7)
- **C2-2** 给模型看大量完整的示范对话：System 里的工具说明、用户提问、Assistant 输出的结构化 JSON 调用、Tool 返回的结果和最终回答；模型在几十万到上百万条样本上反复训练，学会识别工具定义、判断要不要调并输出格式规范的 JSON。[原文§第一阶段：SFT，让模型「见过」工具调用](https://xiaolinnote.com/ai/tools/2_llm_tool_learning.html#%E7%AC%AC%E4%B8%80%E9%98%B6%E6%AE%B5-sft-%E8%AE%A9%E6%A8%A1%E5%9E%8B%E3%80%8C%E8%A7%81%E8%BF%87%E3%80%8D%E5%B7%A5%E5%85%B7%E8%B0%83%E7%94%A8)
- **C2-3** SFT 样本里该调的场景占了绝大多数，模型在模仿中过拟合了积极调用的倾向，没见过足够多不该调的反例；训练信号也只告诉它这是正确答案，所以它的边界感天然就弱。[原文§SFT 的短板，会了，但不知道「该不该调」](https://xiaolinnote.com/ai/tools/2_llm_tool_learning.html#sft-%E7%9A%84%E7%9F%AD%E6%9D%BF-%E4%BC%9A%E4%BA%86-%E4%BD%86%E4%B8%8D%E7%9F%A5%E9%81%93%E3%80%8C%E8%AF%A5%E4%B8%8D%E8%AF%A5%E8%B0%83%E3%80%8D)
- **C2-4** RLHF 让模型对同一问题生成多种处理方式，由人类评判哪种更合理，用这些打分数据训练奖励模型当裁判，再用强化学习让主模型倾向于高分回答，从而学会能直接回答就不调、需要实时数据或执行操作才调。[原文§第二阶段：RLHF，用反馈建立边界感](https://xiaolinnote.com/ai/tools/2_llm_tool_learning.html#%E7%AC%AC%E4%BA%8C%E9%98%B6%E6%AE%B5-rlhf-%E7%94%A8%E5%8F%8D%E9%A6%88%E5%BB%BA%E7%AB%8B%E8%BE%B9%E7%95%8C%E6%84%9F)

### 补充考点

- **C2-5** SFT 即监督微调，核心思路是给模型看大量正确的示例，让它学会模仿；样本里的 System 消息相当于工具说明书，列出可用工具的名称、用途和参数，模型从这里认识工具，接着是 User 消息，即用户的提问。[原文§第一阶段：SFT，让模型「见过」工具调用](https://xiaolinnote.com/ai/tools/2_llm_tool_learning.html#%E7%AC%AC%E4%B8%80%E9%98%B6%E6%AE%B5-sft-%E8%AE%A9%E6%A8%A1%E5%9E%8B%E3%80%8C%E8%A7%81%E8%BF%87%E3%80%8D%E5%B7%A5%E5%85%B7%E8%B0%83%E7%94%A8)
- **C2-6** 一是人工标注，成本高但质量好，一般用来构造核心的种子数据；二是用更强的模型自动批量生成，再人工抽查，成本低、量大，是业界现在的主流做法。[原文§第一阶段：SFT，让模型「见过」工具调用](https://xiaolinnote.com/ai/tools/2_llm_tool_learning.html#%E7%AC%AC%E4%B8%80%E9%98%B6%E6%AE%B5-sft-%E8%AE%A9%E6%A8%A1%E5%9E%8B%E3%80%8C%E8%A7%81%E8%BF%87%E3%80%8D%E5%B7%A5%E5%85%B7%E8%B0%83%E7%94%A8)
- **C2-7** SFT 让模型学会了调工具这个动作，但它不知道什么时候该调、什么时候不该调，像刚培训完、过于热情的新员工，连 1+1 等于几也要去查手册。[原文§SFT 的短板，会了，但不知道「该不该调」](https://xiaolinnote.com/ai/tools/2_llm_tool_learning.html#sft-%E7%9A%84%E7%9F%AD%E6%9D%BF-%E4%BC%9A%E4%BA%86-%E4%BD%86%E4%B8%8D%E7%9F%A5%E9%81%93%E3%80%8C%E8%AF%A5%E4%B8%8D%E8%AF%A5%E8%B0%83%E3%80%8D)
- **C2-8** RLHF 即人类反馈强化学习，相当于持续给模型的表现打分，帮它建立判断力；奖励模型的打分能力是从人类标注员的偏好数据里学出来的，如果标注员水平不稳定、标准不一致，奖励模型就会学到歪的打分标准，主模型被它优化的方向也会跟着歪。[原文§第二阶段：RLHF，用反馈建立边界感](https://xiaolinnote.com/ai/tools/2_llm_tool_learning.html#%E7%AC%AC%E4%BA%8C%E9%98%B6%E6%AE%B5-rlhf-%E7%94%A8%E5%8F%8D%E9%A6%88%E5%BB%BA%E7%AB%8B%E8%BE%B9%E7%95%8C%E6%84%9F)
- **C2-9** RLAIF 是 RLHF 的变体，用另一个 AI 代替人类标注员打分，成本更低、速度更快，现在业界也很常用，效果和人工反馈相差不大。[原文§第二阶段：RLHF，用反馈建立边界感](https://xiaolinnote.com/ai/tools/2_llm_tool_learning.html#%E7%AC%AC%E4%BA%8C%E9%98%B6%E6%AE%B5-rlhf-%E7%94%A8%E5%8F%8D%E9%A6%88%E5%BB%BA%E7%AB%8B%E8%BE%B9%E7%95%8C%E6%84%9F)
- **C2-10** 应用代码把有哪些工具可用打包成 JSON 格式的 schema，连同用户问题一起发给模型；模型输出调用决策，应用执行工具后把返回结果塞回对话历史，再次调用模型，模型才组织成一句话回答用户。[原文§运行时，训练好之后怎么用](https://xiaolinnote.com/ai/tools/2_llm_tool_learning.html#%E8%BF%90%E8%A1%8C%E6%97%B6-%E8%AE%AD%E7%BB%83%E5%A5%BD%E4%B9%8B%E5%90%8E%E6%80%8E%E4%B9%88%E7%94%A8)
- **C2-11** LLM 擅长理解意图和推理，但不应该有直接操作系统资源的权限；宿主程序负责执行，可以做权限控制、参数校验、执行沙箱等安全措施，这样工具调用既灵活又安全，是目前主流工具调用框架的核心设计原则。[原文§一个关键认知：模型只负责「决策」，不负责「执行」](https://xiaolinnote.com/ai/tools/2_llm_tool_learning.html#%E4%B8%80%E4%B8%AA%E5%85%B3%E9%94%AE%E8%AE%A4%E7%9F%A5-%E6%A8%A1%E5%9E%8B%E5%8F%AA%E8%B4%9F%E8%B4%A3%E3%80%8C%E5%86%B3%E7%AD%96%E3%80%8D-%E4%B8%8D%E8%B4%9F%E8%B4%A3%E3%80%8C%E6%89%A7%E8%A1%8C%E3%80%8D)

## 3. Function Call 的训练

原文：[3. 大模型的 Function Call 能力是怎么训练出来的？](https://xiaolinnote.com/ai/tools/3_fc_training.html)。

- **C3-1** 包括注入了工具定义的 system 消息、user 提问、assistant 输出的结构化 JSON 调用请求、tool 角色返回的执行结果，以及 assistant 根据工具结果给出的最终自然语言答案。[原文§阶段一：SFT，让模型「学会怎么调」](https://xiaolinnote.com/ai/tools/3_fc_training.html#%E9%98%B6%E6%AE%B5%E4%B8%80-sft-%E8%AE%A9%E6%A8%A1%E5%9E%8B%E3%80%8C%E5%AD%A6%E4%BC%9A%E6%80%8E%E4%B9%88%E8%B0%83%E3%80%8D)
- **C3-2** 像 1+1 等于几、总结一段话这类问题不需要工具，模型要学会判断自己能解决；如果训练数据里全是调用工具的正例，模型会形成遇到问题就调工具的惯性，该直接回答时也去调。[原文§训练数据需要覆盖哪些场景](https://xiaolinnote.com/ai/tools/3_fc_training.html#%E8%AE%AD%E7%BB%83%E6%95%B0%E6%8D%AE%E9%9C%80%E8%A6%81%E8%A6%86%E7%9B%96%E5%93%AA%E4%BA%9B%E5%9C%BA%E6%99%AF)
- **C3-3** 训练数据要覆盖单工具调用、多工具并行调用、工具调用失败后的处理、不需要调用而直接回答、多轮对话中引用已有工具结果等场景。[原文§训练数据需要覆盖哪些场景](https://xiaolinnote.com/ai/tools/3_fc_training.html#%E8%AE%AD%E7%BB%83%E6%95%B0%E6%8D%AE%E9%9C%80%E8%A6%81%E8%A6%86%E7%9B%96%E5%93%AA%E4%BA%9B%E5%9C%BA%E6%99%AF)
- **C3-4** RLHF 的反馈来自人类标注员对多种回答的打分排序；RLAIF 用更强的 AI 模型代替人类做打分，成本能低 10 到 100 倍、速度也更快，但打分 AI 的偏见会传递给被训练的模型。 [原文§RLAIF：用 AI 代替人工打分](https://xiaolinnote.com/ai/tools/3_fc_training.html#rlaif-%E7%94%A8-ai-%E4%BB%A3%E6%9B%BF%E4%BA%BA%E5%B7%A5%E6%89%93%E5%88%86)[原文§阶段二：RLHF，对齐「该不该调」的边界感](https://xiaolinnote.com/ai/tools/3_fc_training.html#%E9%98%B6%E6%AE%B5%E4%BA%8C-rlhf-%E5%AF%B9%E9%BD%90%E3%80%8C%E8%AF%A5%E4%B8%8D%E8%AF%A5%E8%B0%83%E3%80%8D%E7%9A%84%E8%BE%B9%E7%95%8C%E6%84%9F)
- **C3-5** SFT 解决会不会调的问题，RLHF 解决该不该调的问题。[原文§两个阶段各司其职](https://xiaolinnote.com/ai/tools/3_fc_training.html#%E4%B8%A4%E4%B8%AA%E9%98%B6%E6%AE%B5%E5%90%84%E5%8F%B8%E5%85%B6%E8%81%8C)

### 补充考点

- **C3-6** 预训练语料里几乎没有给定一组工具 schema、在什么场景输出什么 JSON 这样的成对样本；预训练的权重更新都基于预测下一个最可能的 token，记住的是人类文字的统计规律，而输出固定格式的 tool_calls JSON 不是文字里自然存在的模式，所以必须靠专项微调来补。[原文§📝 详细解析](https://xiaolinnote.com/ai/tools/3_fc_training.html#%F0%9F%93%9D-%E8%AF%A6%E7%BB%86%E8%A7%A3%E6%9E%90)
- **C3-7** 通过反向传播：样本里有正确的 JSON 调用，模型的输出偏离正确答案时，损失函数产生惩罚信号，梯度往回传，一点点调整模型内部的参数权重，让下次输出更接近正确格式。[原文§阶段一：SFT，让模型「学会怎么调」](https://xiaolinnote.com/ai/tools/3_fc_training.html#%E9%98%B6%E6%AE%B5%E4%B8%80-sft-%E8%AE%A9%E6%A8%A1%E5%9E%8B%E3%80%8C%E5%AD%A6%E4%BC%9A%E6%80%8E%E4%B9%88%E8%B0%83%E3%80%8D)
- **C3-8** 现实中工具不可能百分百成功，API 超时、参数格式不对、权限不足都可能出现；模型要能识别错误信息并换个方式处理，而不是直接崩掉或者重复同样的调用。[原文§训练数据需要覆盖哪些场景](https://xiaolinnote.com/ai/tools/3_fc_training.html#%E8%AE%AD%E7%BB%83%E6%95%B0%E6%8D%AE%E9%9C%80%E8%A6%81%E8%A6%86%E7%9B%96%E5%93%AA%E4%BA%9B%E5%9C%BA%E6%99%AF)
- **C3-9** 这种做法业界也叫 Self-Instruct 或 Distillation，成本低、量大，是主流做法；隐患是上游模型如果生成了错误样本，下游模型会把错误一起学进去，叫做模型蒸馏的幻觉传递，所以人工抽查质量这一步不能省。[原文§训练数据从哪来](https://xiaolinnote.com/ai/tools/3_fc_training.html#%E8%AE%AD%E7%BB%83%E6%95%B0%E6%8D%AE%E4%BB%8E%E5%93%AA%E6%9D%A5)
- **C3-10** 奖励模型是用打分排序数据单独训练的神经网络，学会预测人类会给某个回答多少分，它不直接回答用户，只当裁判；之后用 PPO 等强化学习算法，拿奖励模型的打分信号持续调整主模型的参数，让它越来越倾向于输出高分的回答。[原文§阶段二：RLHF，对齐「该不该调」的边界感](https://xiaolinnote.com/ai/tools/3_fc_training.html#%E9%98%B6%E6%AE%B5%E4%BA%8C-rlhf-%E5%AF%B9%E9%BD%90%E3%80%8C%E8%AF%A5%E4%B8%8D%E8%AF%A5%E8%B0%83%E3%80%8D%E7%9A%84%E8%BE%B9%E7%95%8C%E6%84%9F)
- **C3-11** 两个务实的理由：一是相对稳定，训练过程不容易崩，传统策略梯度算法容易因为单步更新太大把模型调废；二是能限制每一步策略更新的幅度，让新旧模型的输出分布不要差太远，避免模型为讨好奖励模型而退化成只会重复几句套话。（原文说 PPO 内置 KL 散度约束；按 PPO 论文，常用的是裁剪目标，KL 惩罚是另一种变体，RLHF 里约束模型不偏离初始模型的 KL 项是另外加的。）[原文§阶段二：RLHF，对齐「该不该调」的边界感](https://xiaolinnote.com/ai/tools/3_fc_training.html#%E9%98%B6%E6%AE%B5%E4%BA%8C-rlhf-%E5%AF%B9%E9%BD%90%E3%80%8C%E8%AF%A5%E4%B8%8D%E8%AF%A5%E8%B0%83%E3%80%8D%E7%9A%84%E8%BE%B9%E7%95%8C%E6%84%9F)[核对来源：PPO 论文](https://arxiv.org/abs/1707.06347)
- **C3-12** 代价是 AI 的偏见会传递：打分的 AI 对某些场景有偏差或盲区，这些偏差也会被学进去，例如评委觉得数学题都该调计算器，被训练的模型也会学到这个倾向；所以业界很多训练混用 RLHF 和 RLAIF，关键数据用人工保质量，量大的地方用 AI 提效率。[原文§RLAIF：用 AI 代替人工打分](https://xiaolinnote.com/ai/tools/3_fc_training.html#rlaif-%E7%94%A8-ai-%E4%BB%A3%E6%9B%BF%E4%BA%BA%E5%B7%A5%E6%89%93%E5%88%86)

## 4. MCP 的核心

原文：[4. 什么是 MCP（模型上下文协议）？讲讲它的核心内容？](https://xiaolinnote.com/ai/tools/4_what_is_mcp.html)。

- **C4-1** 没有统一协议时，每个 AI 应用都要按自己的工具注册方式、执行接口和返回格式去适配同一个外部服务；MCP 把能力封装成 MCP Server，按统一方式提供工具清单、参数说明和调用入口，兼容的应用可以复用同一份实现，即常说的 M×N 变成 M+N。[原文§为什么需要 MCP：把重复对接变成共享协议](https://xiaolinnote.com/ai/tools/4_what_is_mcp.html#%E4%B8%BA%E4%BB%80%E4%B9%88%E9%9C%80%E8%A6%81-mcp-%E6%8A%8A%E9%87%8D%E5%A4%8D%E5%AF%B9%E6%8E%A5%E5%8F%98%E6%88%90%E5%85%B1%E4%BA%AB%E5%8D%8F%E8%AE%AE)
- **C4-2** Host 是 AI 应用，负责与模型交互、管理上下文、选择要接入的服务，并落实用户授权和权限控制；Client 是 Host 内部负责协议通信的组件，每个对接一个指定的 Server；Server 提供能力并处理请求，再去调用外部 API。[原文§Host、Client、Server：谁决定，谁通信，谁执行](https://xiaolinnote.com/ai/tools/4_what_is_mcp.html#host%E3%80%81client%E3%80%81server-%E8%B0%81%E5%86%B3%E5%AE%9A-%E8%B0%81%E9%80%9A%E4%BF%A1-%E8%B0%81%E6%89%A7%E8%A1%8C)
- **C4-3** 因为每个 Client 与一个 Server 是一对一的对接关系，Host 每接入一个 Server，例如 GitHub 或文件系统，就要再创建一个 Client。[原文§Host、Client、Server：谁决定，谁通信，谁执行](https://xiaolinnote.com/ai/tools/4_what_is_mcp.html#host%E3%80%81client%E3%80%81server-%E8%B0%81%E5%86%B3%E5%AE%9A-%E8%B0%81%E9%80%9A%E4%BF%A1-%E8%B0%81%E6%89%A7%E8%A1%8C)
- **C4-4** Tools 提供可调用的功能，可以只读，也可以改变外部状态；Resources 提供用 URI 标识的上下文数据，由 Host 放进模型上下文；Prompts 提供可复用的消息模板，获取它只是拿到消息，不会自动执行其中提到的工具操作。[原文§三类服务端能力：功能、上下文和提示模板](https://xiaolinnote.com/ai/tools/4_what_is_mcp.html#%E4%B8%89%E7%B1%BB%E6%9C%8D%E5%8A%A1%E7%AB%AF%E8%83%BD%E5%8A%9B-%E5%8A%9F%E8%83%BD%E3%80%81%E4%B8%8A%E4%B8%8B%E6%96%87%E5%92%8C%E6%8F%90%E7%A4%BA%E6%A8%A1%E6%9D%BF)
- **C4-5** Host 先通过 Client 获取 Server 的工具列表，并转换成模型支持的格式；模型输出包含工具名和参数的调用请求；Host 检查工具是否可用、用户授权是否满足后，经 Client 发送 tools/call；Server 执行并返回结果，Host 再把结果交给模型生成回答。[原文§一次工具调用，怎样从用户问题走到最终回答](https://xiaolinnote.com/ai/tools/4_what_is_mcp.html#%E4%B8%80%E6%AC%A1%E5%B7%A5%E5%85%B7%E8%B0%83%E7%94%A8-%E6%80%8E%E6%A0%B7%E4%BB%8E%E7%94%A8%E6%88%B7%E9%97%AE%E9%A2%98%E8%B5%B0%E5%88%B0%E6%9C%80%E7%BB%88%E5%9B%9E%E7%AD%94)
- **C4-6** 规定了请求、响应和通知三类消息：请求写明协议方法、参数和 id，响应用相同的 id 与请求对应，通知没有 id、不需要响应；协议层错误用 JSON-RPC error 返回，业务执行失败则可以在 result 中用 isError 表示。[原文§JSON-RPC 2.0：先看消息里写了什么](https://xiaolinnote.com/ai/tools/4_what_is_mcp.html#json-rpc-2-0-%E5%85%88%E7%9C%8B%E6%B6%88%E6%81%AF%E9%87%8C%E5%86%99%E4%BA%86%E4%BB%80%E4%B9%88)
- **C4-7** Host 仍要决定哪些能力允许使用、用户授权了哪些操作、哪些数据可以传给模型；Server 返回的文档、工具说明和提示模板可能含不可信内容，不能当成高优先级指令照办，否则可能被诱导泄露数据或调用其他工具。[原文§接通之后，还要处理权限和上下文](https://xiaolinnote.com/ai/tools/4_what_is_mcp.html#%E6%8E%A5%E9%80%9A%E4%B9%8B%E5%90%8E-%E8%BF%98%E8%A6%81%E5%A4%84%E7%90%86%E6%9D%83%E9%99%90%E5%92%8C%E4%B8%8A%E4%B8%8B%E6%96%87)
- **C4-8** 旧版通过 initialize 握手交换协议版本和能力信息，Streamable HTTP 还允许 Server 创建会话 ID；2026-07-28 版改为每个请求在 _meta 里携带版本与客户端能力，移除了初始化握手和协议级会话，所以不同版本的教程流程不同。[原文§协议版本：为什么有的教程先初始化，有的可以直接发请求](https://xiaolinnote.com/ai/tools/4_what_is_mcp.html#%E5%8D%8F%E8%AE%AE%E7%89%88%E6%9C%AC-%E4%B8%BA%E4%BB%80%E4%B9%88%E6%9C%89%E7%9A%84%E6%95%99%E7%A8%8B%E5%85%88%E5%88%9D%E5%A7%8B%E5%8C%96-%E6%9C%89%E7%9A%84%E5%8F%AF%E4%BB%A5%E7%9B%B4%E6%8E%A5%E5%8F%91%E8%AF%B7%E6%B1%82)

### 补充考点

- **C4-9** 要写调用 GitHub API 的代码并处理认证和结果，按该助手的工具接入方式登记工具和参数，再把模型的调用请求交给代码执行并把结果送回模型；M 个应用和 N 个服务原先可能需要 M×N 套专用适配，统一协议后双方各自实现协议支持即可复用，减少的是重复适配工作。[原文§为什么需要 MCP：把重复对接变成共享协议](https://xiaolinnote.com/ai/tools/4_what_is_mcp.html#%E4%B8%BA%E4%BB%80%E4%B9%88%E9%9C%80%E8%A6%81-mcp-%E6%8A%8A%E9%87%8D%E5%A4%8D%E5%AF%B9%E6%8E%A5%E5%8F%98%E6%88%90%E5%85%B1%E4%BA%AB%E5%8D%8F%E8%AE%AE)
- **C4-10** 内容相同，接口职责不同：Resource 提供上下文，Tool 执行一次调用；判断它属于哪一类，要看 Server 用什么接口提供它。[原文§三类服务端能力：功能、上下文和提示模板](https://xiaolinnote.com/ai/tools/4_what_is_mcp.html#%E4%B8%89%E7%B1%BB%E6%9C%8D%E5%8A%A1%E7%AB%AF%E8%83%BD%E5%8A%9B-%E5%8A%9F%E8%83%BD%E3%80%81%E4%B8%8A%E4%B8%8B%E6%96%87%E5%92%8C%E6%8F%90%E7%A4%BA%E6%A8%A1%E6%9D%BF)
- **C4-11** Tools 通常由模型根据任务选择，Resources 由应用决定如何加入上下文，Prompts 由用户主动选择使用；这些只是常见的交互方式，应用可以按需要设计，并非协议强制规定的唯一流程。[原文§三类服务端能力：功能、上下文和提示模板](https://xiaolinnote.com/ai/tools/4_what_is_mcp.html#%E4%B8%89%E7%B1%BB%E6%9C%8D%E5%8A%A1%E7%AB%AF%E8%83%BD%E5%8A%9B-%E5%8A%9F%E8%83%BD%E3%80%81%E4%B8%8A%E4%B8%8B%E6%96%87%E5%92%8C%E6%8F%90%E7%A4%BA%E6%A8%A1%E6%9D%BF)
- **C4-12** Function Calling 帮助模型用结构化格式表达调用意图；MCP 规范的是 Host 通过 Client 与 Server 发现和调用工具的过程。Host 要把两边的格式衔接起来，MCP 本身不规定模型如何推理，也不保证模型每次都能选对工具。[原文§一次工具调用，怎样从用户问题走到最终回答](https://xiaolinnote.com/ai/tools/4_what_is_mcp.html#%E4%B8%80%E6%AC%A1%E5%B7%A5%E5%85%B7%E8%B0%83%E7%94%A8-%E6%80%8E%E6%A0%B7%E4%BB%8E%E7%94%A8%E6%88%B7%E9%97%AE%E9%A2%98%E8%B5%B0%E5%88%B0%E6%9C%80%E7%BB%88%E5%9B%9E%E7%AD%94)
- **C4-13** stdio 通过进程的输入输出传递 JSON-RPC 消息，适合本地进程通信；Streamable HTTP 通过 POST 获得 JSON 或 SSE 响应，适合独立服务部署。是否使用 SSE 由实现选择，一个请求用 JSON 返回就能完成时不必使用，端点也不要求固定命名为 /mcp。[原文§stdio 和 Streamable HTTP：再看消息怎样传过去](https://xiaolinnote.com/ai/tools/4_what_is_mcp.html#stdio-%E5%92%8C-streamable-http-%E5%86%8D%E7%9C%8B%E6%B6%88%E6%81%AF%E6%80%8E%E6%A0%B7%E4%BC%A0%E8%BF%87%E5%8E%BB)
- **C4-14** 2024-11-05 版本的早期 HTTP+SSE 使用分开的 SSE 和 POST 两个端点，后来被弃用，作为兼容背景了解即可；新实现应优先采用 Streamable HTTP，接入时还要查看双方实际支持的协议版本。[原文§协议版本：为什么有的教程先初始化，有的可以直接发请求](https://xiaolinnote.com/ai/tools/4_what_is_mcp.html#%E5%8D%8F%E8%AE%AE%E7%89%88%E6%9C%AC-%E4%B8%BA%E4%BB%80%E4%B9%88%E6%9C%89%E7%9A%84%E6%95%99%E7%A8%8B%E5%85%88%E5%88%9D%E5%A7%8B%E5%8C%96-%E6%9C%89%E7%9A%84%E5%8F%AF%E4%BB%A5%E7%9B%B4%E6%8E%A5%E5%8F%91%E8%AF%B7%E6%B1%82)
- **C4-15** 应围绕具体操作和具体数据设计：搜索公开 Issue 和创建 Issue 的影响不同，读取公开 README 和读取含凭据的配置文件敏感性也不同，不能简单规定 Tools 都高风险、Resources 都可自由开放；用户应能了解和控制工具的使用，敏感操作需要相应的确认机制。[原文§接通之后，还要处理权限和上下文](https://xiaolinnote.com/ai/tools/4_what_is_mcp.html#%E6%8E%A5%E9%80%9A%E4%B9%8B%E5%90%8E-%E8%BF%98%E8%A6%81%E5%A4%84%E7%90%86%E6%9D%83%E9%99%90%E5%92%8C%E4%B8%8A%E4%B8%8B%E6%96%87)

## 5. MCP 的组成

原文：[5. MCP 由哪几部分组成？](https://xiaolinnote.com/ai/tools/5_mcp_components.html)。

- **C5-1** 拆成三层来讲：第一层是角色架构，说明谁和谁在通信；第二层是能力类型，说明 Server 能暴露什么给模型用；第三层是传输协议，说明消息是怎么传的。三层各自独立、互不耦合。[原文§先建立整体感：三层来看就清楚了](https://xiaolinnote.com/ai/tools/5_mcp_components.html#%E5%85%88%E5%BB%BA%E7%AB%8B%E6%95%B4%E4%BD%93%E6%84%9F-%E4%B8%89%E5%B1%82%E6%9D%A5%E7%9C%8B%E5%B0%B1%E6%B8%85%E6%A5%9A%E4%BA%86)
- **C5-2** 本篇的说法是 Tools 对应有副作用、会改变外部状态的操作，Resources 是没有副作用的只读数据，可以更宽松地暴露；这一口径与第 4 篇不一致：第 4 篇明确说 Tools 既可以只读，也可以改变外部状态，Resources 则是提供上下文数据的接口。 [原文§第二层：能力类型，Tools / Resources / Prompts](https://xiaolinnote.com/ai/tools/5_mcp_components.html#%E7%AC%AC%E4%BA%8C%E5%B1%82-%E8%83%BD%E5%8A%9B%E7%B1%BB%E5%9E%8B-tools-resources-prompts)[对照原文第4篇§三类服务端能力：功能、上下文和提示模板](https://xiaolinnote.com/ai/tools/4_what_is_mcp.html#%E4%B8%89%E7%B1%BB%E6%9C%8D%E5%8A%A1%E7%AB%AF%E8%83%BD%E5%8A%9B-%E5%8A%9F%E8%83%BD%E3%80%81%E4%B8%8A%E4%B8%8B%E6%96%87%E5%92%8C%E6%8F%90%E7%A4%BA%E6%A8%A1%E6%9D%BF)
- **C5-3** stdio 让 Server 作为本地子进程运行，通过管道通信，不需要网络、延迟极低，适合本地工具；Streamable HTTP 让 Server 作为 HTTP 服务独立部署，适合远程部署和多个 Client 共享同一个 Server。[原文§第三层：传输协议，JSON-RPC 2.0 + 传输方式](https://xiaolinnote.com/ai/tools/5_mcp_components.html#%E7%AC%AC%E4%B8%89%E5%B1%82-%E4%BC%A0%E8%BE%93%E5%8D%8F%E8%AE%AE-json-rpc-2-0-%E4%BC%A0%E8%BE%93%E6%96%B9%E5%BC%8F)
- **C5-4** 因为两者是解耦的：同一套 JSON-RPC 消息可以跑在任意传输层上，切换传输方式不影响上层的工具调用逻辑，所以 Server 既能作为本地进程运行，也能作为正式的微服务部署。[原文§第三层：传输协议，JSON-RPC 2.0 + 传输方式](https://xiaolinnote.com/ai/tools/5_mcp_components.html#%E7%AC%AC%E4%B8%89%E5%B1%82-%E4%BC%A0%E8%BE%93%E5%8D%8F%E8%AE%AE-json-rpc-2-0-%E4%BC%A0%E8%BE%93%E6%96%B9%E5%BC%8F)

### 补充考点

- **C5-5** Host 是整个系统的宿主，也就是 AI 应用本身，例如 Claude Desktop、Cursor、Windsurf；它负责启动和管理所有 MCP Client，控制连哪些 Server、什么时候断开连接，是整个系统的调度中心。[原文§第一层：角色架构，Host / Client / Server](https://xiaolinnote.com/ai/tools/5_mcp_components.html#%E7%AC%AC%E4%B8%80%E5%B1%82-%E8%A7%92%E8%89%B2%E6%9E%B6%E6%9E%84-host-client-server)
- **C5-6** Client 是 Host 内部的连接模块，一个 Client 对应一个 Server 连接；它负责初始化和 Server 的连接、向 Server 查询有哪些工具、资源和模板即能力发现，以及把模型的调用请求转发给 Server 并把结果带回来。Host 本身不直接和 Server 说话。[原文§第一层：角色架构，Host / Client / Server](https://xiaolinnote.com/ai/tools/5_mcp_components.html#%E7%AC%AC%E4%B8%80%E5%B1%82-%E8%A7%92%E8%89%B2%E6%9E%B6%E6%9E%84-host-client-server)
- **C5-7** Server 是工具提供方实现的独立进程，对外暴露自己的工具、资源和提示词模板，完全不关心上面是哪个 Host 在用它，只要按协议响应 Client 的请求；这正是 MCP 的核心价值：Server 写一次，任何支持 MCP 的 Host 都能直接用，一个 Host 还可以同时连多个 Server。[原文§第一层：角色架构，Host / Client / Server](https://xiaolinnote.com/ai/tools/5_mcp_components.html#%E7%AC%AC%E4%B8%80%E5%B1%82-%E8%A7%92%E8%89%B2%E6%9E%B6%E6%9E%84-host-client-server)
- **C5-8** Tools 是最核心、使用最频繁的能力，由模型主动触发，对应 Function Calling 里函数的概念；原文把它描述为有副作用、会改变外部世界状态的操作，例如创建文件、提交代码、发送消息、调用第三方 API，因为执行可能不可逆，通常需要用户授权确认。（按 MCP 规范，Tools 的特点是由模型控制，也可以是只读的查询，不一定有副作用。）[原文§第二层：能力类型，Tools / Resources / Prompts](https://xiaolinnote.com/ai/tools/5_mcp_components.html#%E7%AC%AC%E4%BA%8C%E5%B1%82-%E8%83%BD%E5%8A%9B%E7%B1%BB%E5%9E%8B-tools-resources-prompts)[核对来源：MCP 规范·Tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)
- **C5-9** 原文的说法是：Resources 是只读数据，没有副作用，只是把数据提供给模型看，例如读取日志文件、查询数据库记录、获取文档内容，所以可以比 Tools 更宽松地暴露。（按 MCP 规范，两者的本质区别是由谁控制：Tools 由模型决定调用，Resources 由宿主应用决定怎样取用；授权要按具体的数据和操作来定，不能只看能力类型。）[原文§第二层：能力类型，Tools / Resources / Prompts](https://xiaolinnote.com/ai/tools/5_mcp_components.html#%E7%AC%AC%E4%BA%8C%E5%B1%82-%E8%83%BD%E5%8A%9B%E7%B1%BB%E5%9E%8B-tools-resources-prompts)[核对来源：MCP 规范·Tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)[核对来源：MCP 规范·Resources](https://modelcontextprotocol.io/specification/2025-06-18/server/resources)
- **C5-10** Prompts 是预定义的、带参数占位符的提示词模板，解决每次都要手写重复 prompt 的问题：例如把团队固定的代码审查标准封装成模板，调用时只传编程语言和代码内容，自动展开成完整提示词，适合团队内部共享最佳实践。原文的概括是 Tools 改变世界，Resources 观察世界，Prompts 结构化表达。[原文§第二层：能力类型，Tools / Resources / Prompts](https://xiaolinnote.com/ai/tools/5_mcp_components.html#%E7%AC%AC%E4%BA%8C%E5%B1%82-%E8%83%BD%E5%8A%9B%E7%B1%BB%E5%9E%8B-tools-resources-prompts)
- **C5-11** 每条消息是一个 JSON 对象：Client 发请求时说明调哪个方法、参数是什么、这次请求的 ID 是多少，Server 返回响应时带上执行结果或错误信息，双方通过 ID 匹配请求和响应；JSON 格式易读、易调试，任何编程语言都能实现。[原文§第三层：传输协议，JSON-RPC 2.0 + 传输方式](https://xiaolinnote.com/ai/tools/5_mcp_components.html#%E7%AC%AC%E4%B8%89%E5%B1%82-%E4%BC%A0%E8%BE%93%E5%8D%8F%E8%AE%AE-json-rpc-2-0-%E4%BC%A0%E8%BE%93%E6%96%B9%E5%BC%8F)
- **C5-12** 早期方案是双端点：一个 GET 端点开 SSE 接收推送，一个 POST 端点发请求，2025 年 3 月的规范更新把它改成单端点的 Streamable HTTP，旧方案标记为 deprecated 但保留兼容；新方案没有抛弃 SSE，Client 用 POST 发请求，短请求直接回普通 JSON，长请求把响应升级为 SSE 流持续推送，对负载均衡器和 serverless 环境更友好。[原文§第三层：传输协议，JSON-RPC 2.0 + 传输方式](https://xiaolinnote.com/ai/tools/5_mcp_components.html#%E7%AC%AC%E4%B8%89%E5%B1%82-%E4%BC%A0%E8%BE%93%E5%8D%8F%E8%AE%AE-json-rpc-2-0-%E4%BC%A0%E8%BE%93%E6%96%B9%E5%BC%8F)

## 6. MCP 与 Function Calling

原文：[6. MCP 和 Function Calling 有什么区别？有没有实际跑过 MCP？](https://xiaolinnote.com/ai/tools/6_mcp_vs_fc.html)。

- **C6-1** Function Calling 管一次函数调用请求长什么样，即调用的消息格式；MCP 管一堆工具怎样被组织、发现和跨项目复用，是规范加生态约定。原文类比为 HTTP 与 REST 规范的关系。[原文§Function Calling 有了，为什么还需要 MCP？](https://xiaolinnote.com/ai/tools/6_mcp_vs_fc.html#function-calling-%E6%9C%89%E4%BA%86-%E4%B8%BA%E4%BB%80%E4%B9%88%E8%BF%98%E9%9C%80%E8%A6%81-mcp)
- **C6-2** Function Calling 的 schema 和对接逻辑写在各个项目里，换项目要复制重写，不同模型的格式不完全一样还得各自适配，工具接口一变要去每个项目逐一更新；它解决不了工具的管理、复用和跨平台兼容。[原文§Function Calling 的痛点，每次都是一次性的](https://xiaolinnote.com/ai/tools/6_mcp_vs_fc.html#function-calling-%E7%9A%84%E7%97%9B%E7%82%B9-%E6%AF%8F%E6%AC%A1%E9%83%BD%E6%98%AF%E4%B8%80%E6%AC%A1%E6%80%A7%E7%9A%84)
- **C6-3** MCP Client 连上 Server 后拉取全部工具定义，转换成模型原生的 Function Calling 格式传给模型；模型仍通过输出 tool_calls 表达要调哪个工具，Client 把请求路由到对应的 Server 执行，再把结果以 tool 消息喂回对话。[原文§最关键的联系，MCP 底层依然靠 Function Calling 驱动](https://xiaolinnote.com/ai/tools/6_mcp_vs_fc.html#%E6%9C%80%E5%85%B3%E9%94%AE%E7%9A%84%E8%81%94%E7%B3%BB-mcp-%E5%BA%95%E5%B1%82%E4%BE%9D%E7%84%B6%E9%9D%A0-function-calling-%E9%A9%B1%E5%8A%A8)
- **C6-4** 原文的示例是在 claude_desktop_config.json 的 mcpServers 里配置启动命令和参数，例如用 npx 启动文件系统 Server 并指定允许访问的目录，重启后自动发现工具；自己写 Server 则用 list_tools 声明工具、call_tool 实现逻辑，并以 stdio 方式运行。[原文§实际体验，接入一个 MCP Server](https://xiaolinnote.com/ai/tools/6_mcp_vs_fc.html#%E5%AE%9E%E9%99%85%E4%BD%93%E9%AA%8C-%E6%8E%A5%E5%85%A5%E4%B8%80%E4%B8%AA-mcp-server)

### 补充考点

- **C6-5** 困惑的根源是把能调工具和管好工具混在一起，这是两个层次的问题；原文的类比是 HTTP 协议出来后已经能在网络上传数据，但还需要 REST API 规范。[原文§Function Calling 有了，为什么还需要 MCP？](https://xiaolinnote.com/ai/tools/6_mcp_vs_fc.html#function-calling-%E6%9C%89%E4%BA%86-%E4%B8%BA%E4%BB%80%E4%B9%88%E8%BF%98%E9%9C%80%E8%A6%81-mcp)

## 7. 选用 FC 还是 MCP

原文：[7. Function Calling 也属于工具调用，请问什么场景下使用 Function Calling，什么场景下使用 MCP？](https://xiaolinnote.com/ai/tools/7_fc_vs_mcp_usage.html)。

- **C7-1** 工具只为这一个应用服务、不需要复用时，直接在代码里定义 schema 和调用逻辑即可，不用启动额外进程，也不需要额外配置；调用逻辑都在自己的代码里，加权限校验、参数处理和错误处理也更方便。[原文§Function Calling 的适用场景](https://xiaolinnote.com/ai/tools/7_fc_vs_mcp_usage.html#function-calling-%E7%9A%84%E9%80%82%E7%94%A8%E5%9C%BA%E6%99%AF)

- **C7-3** MCP Server 是独立进程，权限校验等定制逻辑要额外传递或约定；某些受限的云环境或 Serverless 平台不允许启动子进程，stdio 模式就用不了。[原文§Function Calling 的适用场景](https://xiaolinnote.com/ai/tools/7_fc_vs_mcp_usage.html#function-calling-%E7%9A%84%E9%80%82%E7%94%A8%E5%9C%BA%E6%99%AF)
- **C7-4** 不足以。原文不给绝对的数量门槛，要综合看工具的复杂度、团队规模和变更频率：复杂度高、多人协作、接口常改时即使只有 5 个工具也值得，两个极简单又几乎不动的工具则没必要引入独立 Server。[原文§MCP 的适用场景](https://xiaolinnote.com/ai/tools/7_fc_vs_mcp_usage.html#mcp-%E7%9A%84%E9%80%82%E7%94%A8%E5%9C%BA%E6%99%AF)

### 补充考点

- **C7-5** 核心问题只有一个：这个工具会不会在这个应用之外被用到；会的话，把它封装成 MCP Server 是更长远的选择。[原文§💡 简要回答](https://xiaolinnote.com/ai/tools/7_fc_vs_mcp_usage.html#%F0%9F%92%A1-%E7%AE%80%E8%A6%81%E5%9B%9E%E7%AD%94)

- **C7-7** 只用自己、只用一次、不需要复用才适合 Function Calling，其他情况优先考虑 MCP；两者不是竞争关系，宿主通常是把 MCP 工具转成 Function Calling 的工具定义交给模型，选哪个取决于工程需求，而不是技术上的优劣。[原文§一个实用的判断方法](https://xiaolinnote.com/ai/tools/7_fc_vs_mcp_usage.html#%E4%B8%80%E4%B8%AA%E5%AE%9E%E7%94%A8%E7%9A%84%E5%88%A4%E6%96%AD%E6%96%B9%E6%B3%95)[核对来源：MCP 规范·Tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)

## 8. 推理模型的工具兼容性

原文：[8. 为什么有些特定的推理模型不支持 MCP 协议？](https://xiaolinnote.com/ai/tools/8_reasoning_no_mcp.html)。

- **C8-1** 工具调用天然是多轮交互：模型生成调用请求，停下来等宿主程序执行，拿到结果后再继续生成，把工具结果纳入后续推理；原文把核心概括为“模型生成到一半，强制暂停，等外部执行完毕，再恢复生成”。（这是便于理解的比喻。实际 API 中，模型输出调用请求后本次响应即结束，并不是挂起一个进程；宿主执行工具后，把历史消息和工具结果放进新的请求，由模型继续生成，需要保留的推理内容由宿主按接口要求随历史回传，也就是在请求之间重建上下文，而不是原样恢复同一次生成。）[原文§工具调用的本质是「中途暂停」](https://xiaolinnote.com/ai/tools/8_reasoning_no_mcp.html#%E5%B7%A5%E5%85%B7%E8%B0%83%E7%94%A8%E7%9A%84%E6%9C%AC%E8%B4%A8%E6%98%AF%E3%80%8C%E4%B8%AD%E9%80%94%E6%9A%82%E5%81%9C%E3%80%8D)[核对来源：Anthropic 官方文档·Thinking](https://platform.claude.com/docs/en/build-with-claude/thinking)
- **C8-2** 不是。原文称 MCP 底层依赖 Function Calling：Client 要把工具定义转换成 Function Calling 格式，并等模型输出 tool_calls；原文认为模型不支持时这个翻译层失效，是底层能力缺失导致的连锁反应，不是 MCP 本身有问题。（但不稳定的 tool call 不能直接断定是模型底层能力缺失，也可能是工具定义（名称、描述、参数 schema）写得不好，或宿主的适配、解析出了问题，需要分别排查。这是常见的接入方式；MCP 规范只规定工具由模型来发现和调用，并不规定宿主必须用哪种机制把工具交给模型。）[原文§为什么不支持 Function Calling 就不支持 MCP？](https://xiaolinnote.com/ai/tools/8_reasoning_no_mcp.html#%E4%B8%BA%E4%BB%80%E4%B9%88%E4%B8%8D%E6%94%AF%E6%8C%81-function-calling-%E5%B0%B1%E4%B8%8D%E6%94%AF%E6%8C%81-mcp)[核对来源：MCP 规范·Tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)
- **C8-3** 早期的解法是让工具调用发生在思考阶段结束之后：模型先把推理链完整跑完，进入输出答案阶段才触发 Function Calling；Claude 还提供交错思考，允许在多次工具调用之间穿插思考。（现状：OpenAI 的 o3、o4-mini 已能在推理过程中直接调用工具，Claude 的交错思考也可以在每次工具结果之后继续推理，不再局限于想完再调。）[原文§后来是怎么解决的，折中方案](https://xiaolinnote.com/ai/tools/8_reasoning_no_mcp.html#%E5%90%8E%E6%9D%A5%E6%98%AF%E6%80%8E%E4%B9%88%E8%A7%A3%E5%86%B3%E7%9A%84-%E6%8A%98%E4%B8%AD%E6%96%B9%E6%A1%88)[核对来源：OpenAI o3/o4-mini 函数调用指南](https://github.com/openai/openai-cookbook/blob/main/examples/o-series/o3o4-mini_prompting_guide.ipynb)[核对来源：Anthropic 官方文档·Thinking](https://platform.claude.com/docs/en/build-with-claude/thinking)
- **C8-4** 思考阶段感知不到工具结果，对需要先查到数据再做深度推理的任务不够用；交错思考能在一定程度上缓解这个问题。[原文§后来是怎么解决的，折中方案](https://xiaolinnote.com/ai/tools/8_reasoning_no_mcp.html#%E5%90%8E%E6%9D%A5%E6%98%AF%E6%80%8E%E4%B9%88%E8%A7%A3%E5%86%B3%E7%9A%84-%E6%8A%98%E4%B8%AD%E6%96%B9%E6%A1%88)

### 补充考点

- **C8-5** 普通模型收到输入就开始生成 token，一路生成到结束；推理模型在给出最终答案之前，会先生成一大段内部思考，在里面推演、验证、反驳甚至推翻重来，想清楚后再输出最终答案，代表有 OpenAI o1/o3 系列、DeepSeek-R1 和 Claude 的扩展思考模式。这正是它在复杂推理上更强的原因，也是原文所说早期难以与工具调用配合的来源。[原文§先弄清楚推理模型是什么](https://xiaolinnote.com/ai/tools/8_reasoning_no_mcp.html#%E5%85%88%E5%BC%84%E6%B8%85%E6%A5%9A%E6%8E%A8%E7%90%86%E6%A8%A1%E5%9E%8B%E6%98%AF%E4%BB%80%E4%B9%88)
- **C8-6** 原文对早期推理模型的解释是：推理的中间状态即 KV Cache 体积非常庞大，一旦暂停就得原封不动占着一块 GPU 显存，工具执行的几秒到几十秒里这块显存不能给别的请求用，吞吐量大幅下降、延迟上升；对要同时服务成千上万请求的在线推理系统来说无法承受。（按现在公开的做法，推理内容以 thinking 块或推理项的形式随请求回传来延续，不需要在工具执行期间一直占着显存。）[原文§「那保存状态再恢复不就行了？」](https://xiaolinnote.com/ai/tools/8_reasoning_no_mcp.html#%E3%80%8C%E9%82%A3%E4%BF%9D%E5%AD%98%E7%8A%B6%E6%80%81%E5%86%8D%E6%81%A2%E5%A4%8D%E4%B8%8D%E5%B0%B1%E8%A1%8C%E4%BA%86-%E3%80%8D)[核对来源：Anthropic 官方文档·Thinking](https://platform.claude.com/docs/en/build-with-claude/thinking)[核对来源：OpenAI o3/o4-mini 函数调用指南](https://github.com/openai/openai-cookbook/blob/main/examples/o-series/o3o4-mini_prompting_guide.ipynb)
- **C8-7** 原文认为，这等于在模型想到一半时改变了输入：之前的思路是在还不知道工具结果的前提下建立的，工具结果来了之后要重新校准，原有的推理链和新结果可能矛盾，怎么融合没有简单的解法。[原文§「那保存状态再恢复不就行了？」](https://xiaolinnote.com/ai/tools/8_reasoning_no_mcp.html#%E3%80%8C%E9%82%A3%E4%BF%9D%E5%AD%98%E7%8A%B6%E6%80%81%E5%86%8D%E6%81%A2%E5%A4%8D%E4%B8%8D%E5%B0%B1%E8%A1%8C%E4%BA%86-%E3%80%8D)
- **C8-8** 原文的解释是：推理模型用强化学习大量奖励思考链完整且结论正确的输出，于是越来越倾向于一直想、想到底；Function Calling 的训练恰好相反，要模型学会在合适的时机打断自己，输出一段结构化的 JSON 调用请求，两种行为方向相反，训练数据的分布要两边兼顾。[原文§训练目标上的冲突](https://xiaolinnote.com/ai/tools/8_reasoning_no_mcp.html#%E8%AE%AD%E7%BB%83%E7%9B%AE%E6%A0%87%E4%B8%8A%E7%9A%84%E5%86%B2%E7%AA%81)
- **C8-9** 原文列了三种：一是模型思考到一半突然输出一段格式还出错的 JSON，两边都没做好；二是模型彻底偏向一边，要么思考链缩水变浅，要么干脆不会输出工具调用；三是融合处推理断裂，工具结果回来后的推理和之前的思考链对不上。原文认为这是早期推理模型宁可先放弃工具调用的原因。[原文§训练目标上的冲突](https://xiaolinnote.com/ai/tools/8_reasoning_no_mcp.html#%E8%AE%AD%E7%BB%83%E7%9B%AE%E6%A0%87%E4%B8%8A%E7%9A%84%E5%86%B2%E7%AA%81)
- **C8-10** OpenAI o1-preview 在 2024 年 9 月发布时明确不支持 Function Calling，官方文档直接标注了限制；2024 年 12 月发布的正式版 o1 已经加上支持。DeepSeek-R1 的早期版本也类似，推理很强但工具调用支持极弱。原文把这些限制解释为结构性冲突下的工程取舍，而不是懒得做。[原文§早期推理模型的真实情况](https://xiaolinnote.com/ai/tools/8_reasoning_no_mcp.html#%E6%97%A9%E6%9C%9F%E6%8E%A8%E7%90%86%E6%A8%A1%E5%9E%8B%E7%9A%84%E7%9C%9F%E5%AE%9E%E6%83%85%E5%86%B5)
- **C8-12** 好比正在专心写一篇复杂的推理论文，脑子里已经建立了整套逻辑框架，突然去接了 20 分钟电话，回来后很多细节想不起来，之前建立的推理脉络断了，只能重新梳理。推理模型的思考链也是这样：它是一个依赖完整上下文的连续生成过程，每一步推理都建立在前面所有推理内容之上，整条链是一个有机整体，原文认为中途强行打断，之前建立的推理状态会断掉，模型没办法从中间接着想，只能整个重来。（这是原文给早期推理模型的直觉类比，不是普遍规律：现行接口中，推理模型可在多次工具调用之间继续推理，宿主按要求回传推理内容即可，不必整个重来；见 C8-3、C8-6。）[原文§直觉类比，写推理过程中途被打断](https://xiaolinnote.com/ai/tools/8_reasoning_no_mcp.html#%E7%9B%B4%E8%A7%89%E7%B1%BB%E6%AF%94-%E5%86%99%E6%8E%A8%E7%90%86%E8%BF%87%E7%A8%8B%E4%B8%AD%E9%80%94%E8%A2%AB%E6%89%93%E6%96%AD)

## 9. Agent Skill

原文：[9. Skill 是什么？](https://xiaolinnote.com/ai/tools/9_skill.html)。

- **C9-1** Skill 把反复使用的指令、流程和模板打包成标准化模块，Agent 自己知道什么时候该用、怎么用；手动粘贴的 Prompt 每次新对话都要重贴，漏掉细节输出就不稳定，团队里每人贴的还不一样，标准无法统一。[原文§为什么需要 Skill？从「重复贴 prompt」的痛点说起](https://xiaolinnote.com/ai/tools/9_skill.html#%E4%B8%BA%E4%BB%80%E4%B9%88%E9%9C%80%E8%A6%81-skill-%E4%BB%8E%E3%80%8C%E9%87%8D%E5%A4%8D%E8%B4%B4-prompt%E3%80%8D%E7%9A%84%E7%97%9B%E7%82%B9%E8%AF%B4%E8%B5%B7)
- **C9-2** 一个 Skill 是一个文件夹：必须有 SKILL.md，顶部是含 name 和 description 的 frontmatter，下面是用 Markdown 写的指令和步骤；可选的有 scripts 里的可执行脚本、references 里的参考文档和 assets 里的模板、资源文件。[原文§Skill 的结构长什么样](https://xiaolinnote.com/ai/tools/9_skill.html#skill-%E7%9A%84%E7%BB%93%E6%9E%84%E9%95%BF%E4%BB%80%E4%B9%88%E6%A0%B7)
- **C9-3** 它分三层：启动时只加载每个 Skill 的 name 和 description，约 30 到 50 个 token；任务相关时才加载该 Skill 的 SKILL.md 正文；执行中用到模板、脚本或参考文档时才去读取。不相关的 Skill 始终不加载，不占上下文。[原文§渐进式加载：Skill 最聪明的设计](https://xiaolinnote.com/ai/tools/9_skill.html#%E6%B8%90%E8%BF%9B%E5%BC%8F%E5%8A%A0%E8%BD%BD-skill-%E6%9C%80%E8%81%AA%E6%98%8E%E7%9A%84%E8%AE%BE%E8%AE%A1)
- **C9-4** Tool（包括 MCP 工具）提供能力，让 Agent 能查数据库、调 API、读写文件；Skill 提供知识和流程，教 Agent 拿到工具后按什么步骤、标准和格式完成工作。两者互补。[原文§Skill 和 Tool、Prompt 分别是什么关系](https://xiaolinnote.com/ai/tools/9_skill.html#skill-%E5%92%8C-tool%E3%80%81prompt-%E5%88%86%E5%88%AB%E6%98%AF%E4%BB%80%E4%B9%88%E5%85%B3%E7%B3%BB)
- **C9-5** Skill 只是一个文件夹加一份 Markdown，不需要特殊的运行时，任何支持文件系统的 Agent 平台理论上都能实现，写一份有机会跨平台复用；但原文称目前主要还是 Claude 生态在用，能走到哪一步要看行业的采纳情况。[原文§Skill 从 Anthropic 走向开放标准](https://xiaolinnote.com/ai/tools/9_skill.html#skill-%E4%BB%8E-anthropic-%E8%B5%B0%E5%90%91%E5%BC%80%E6%94%BE%E6%A0%87%E5%87%86)

### 补充考点

- **C9-6** Anthropic 在 2025 年 10 月推出 Agent Skills，同年 12 月把规范作为开放标准发布，允许其他 Agent 平台按照这套格式兼容 Skills 生态。[原文§💡 简要回答](https://xiaolinnote.com/ai/tools/9_skill.html#%F0%9F%92%A1-%E7%AE%80%E8%A6%81%E5%9B%9E%E7%AD%94)
- **C9-7** 每次让 AI 做代码审查都要贴一大段指令，漏掉细节输出质量就不稳定；团队里十个人贴的 prompt 各不相同，审查标准没法统一；把 prompt 放进共享文档让大家复制，本质上还是靠人工维护和执行，版本一多就乱，质量把控做不到。[原文§为什么需要 Skill？从「重复贴 prompt」的痛点说起](https://xiaolinnote.com/ai/tools/9_skill.html#%E4%B8%BA%E4%BB%80%E4%B9%88%E9%9C%80%E8%A6%81-skill-%E4%BB%8E%E3%80%8C%E9%87%8D%E5%A4%8D%E8%B4%B4-prompt%E3%80%8D%E7%9A%84%E7%97%9B%E7%82%B9%E8%AF%B4%E8%B5%B7)
- **C9-8** 假设有 20 个 Skill，每个指令加参考文档平均 2000 token，全部加载就是 4 万 token 打底，在 20 万 token 的窗口里占掉五分之一，而且大部分 Skill 在当前任务里用不上；真正有用的任务信息会被淹没，Agent 的注意力被分散，输出质量反而下降。[原文§渐进式加载：Skill 最聪明的设计](https://xiaolinnote.com/ai/tools/9_skill.html#%E6%B8%90%E8%BF%9B%E5%BC%8F%E5%8A%A0%E8%BD%BD-skill-%E6%9C%80%E8%81%AA%E6%98%8E%E7%9A%84%E8%AE%BE%E8%AE%A1)
- **C9-9** Prompt 像口头说的一句话指令，说完就没了，是一次性、临时的，而 Skill 是持久化、可复用的；Slash Command 也把指令保存下来复用，但必须由用户手动触发，Skill 则可以被 Agent 自动发现和调用，由 Agent 自己判断任务需要哪个 Skill 并主动加载。[原文§Skill 和 Tool、Prompt 分别是什么关系](https://xiaolinnote.com/ai/tools/9_skill.html#skill-%E5%92%8C-tool%E3%80%81prompt-%E5%88%86%E5%88%AB%E6%98%AF%E4%BB%80%E4%B9%88%E5%85%B3%E7%B3%BB)

## 10. MCP 与 Skill

原文：[10. MCP 和 Agent Skill 的区别是什么？](https://xiaolinnote.com/ai/tools/10_mcp_vs_skill.html)。

- **C10-1** MCP 解决 Agent 怎么获得外部能力，把数据库、API、文件系统等标准化封装成服务，是从无到有的问题；Skill 解决有了这些能力之后该怎么用，提供先做什么后做什么、检查哪些维度、用什么格式输出等知识和流程。[原文§从定位说起：两者解决的不是同一个问题](https://xiaolinnote.com/ai/tools/10_mcp_vs_skill.html#%E4%BB%8E%E5%AE%9A%E4%BD%8D%E8%AF%B4%E8%B5%B7-%E4%B8%A4%E8%80%85%E8%A7%A3%E5%86%B3%E7%9A%84%E4%B8%8D%E6%98%AF%E5%90%8C%E4%B8%80%E4%B8%AA%E9%97%AE%E9%A2%98)
- **C10-2** Agent 匹配并加载 Skill 的 SKILL.md，按其中的步骤执行；需要读文件等动作时调用 MCP Server 提供的工具，再运行 Skill 自带的脚本、按 Skill 的模板输出报告。Skill 是编排者，MCP 是执行者。[原文§两者怎么配合工作](https://xiaolinnote.com/ai/tools/10_mcp_vs_skill.html#%E4%B8%A4%E8%80%85%E6%80%8E%E4%B9%88%E9%85%8D%E5%90%88%E5%B7%A5%E4%BD%9C)

### 补充考点

- **C10-3** MCP 就像给新员工配电脑、装软件、开各种系统权限，是他能做事的前提；Skill 是给他的操作手册，告诉他做代码审查时先检查什么、后检查什么、用什么标准判断、最后用什么模板写报告。[原文§从定位说起：两者解决的不是同一个问题](https://xiaolinnote.com/ai/tools/10_mcp_vs_skill.html#%E4%BB%8E%E5%AE%9A%E4%BD%8D%E8%AF%B4%E8%B5%B7-%E4%B8%A4%E8%80%85%E8%A7%A3%E5%86%B3%E7%9A%84%E4%B8%8D%E6%98%AF%E5%90%8C%E4%B8%80%E4%B8%AA%E9%97%AE%E9%A2%98)
- **C10-4** MCP Server 暴露的每个 Tool 每次调用只做一件明确完整的事，执行结果立刻返回，例如 read_file 或 query_database；模型能看到每个 Tool 的完整 schema，包括名字、参数和返回格式，这种精确的可见性是模型能准确判断该调哪个工具的基础。[原文§MCP：让 Agent 有「手」](https://xiaolinnote.com/ai/tools/10_mcp_vs_skill.html#mcp-%E8%AE%A9-agent-%E6%9C%89%E3%80%8C%E6%89%8B%E3%80%8D)
- **C10-5** 启动时只加载每个 Skill 的名字和一句话描述，每个大概只占 30 到 50 个 token；Agent 判断某个 Skill 和当前任务相关时才加载完整的指令正文；执行过程中用到模板或参考文档时，才进一步加载这些资源文件。[原文§Skill：给 Agent 一份「操作手册」](https://xiaolinnote.com/ai/tools/10_mcp_vs_skill.html#skill-%E7%BB%99-agent-%E4%B8%80%E4%BB%BD%E3%80%8C%E6%93%8D%E4%BD%9C%E6%89%8B%E5%86%8C%E3%80%8D)
- **C10-6** 例如流程规定改动涉及数据库表结构时要额外做权限合规检查：Agent 先调用一个 MCP Tool 扫描这次提交有没有改 schema，拿到结果后再决定是否走这条分支，要走就再调另一个 MCP Tool 查合规规则。Skill 像项目经理拿着流程图和判断标准指挥，每个 Tool 像只管做好一件小事的专业工人。[原文§两者怎么配合工作](https://xiaolinnote.com/ai/tools/10_mcp_vs_skill.html#%E4%B8%A4%E8%80%85%E6%80%8E%E4%B9%88%E9%85%8D%E5%90%88%E5%B7%A5%E4%BD%9C)
- **C10-7** 定位上，MCP 提供工具和数据的访问能力，解决 Agent 能不能做事，是能力；Skill 提供完成任务的知识和流程，解决该怎么做事，是知识。粒度上，MCP 是原子操作，schema 对模型完全可见；Skill 是工作流程，定义完成某类任务的完整步骤和标准，还可附带脚本、模板等资源并按需加载。[原文§🎯 面试总结](https://xiaolinnote.com/ai/tools/10_mcp_vs_skill.html#%F0%9F%8E%AF-%E9%9D%A2%E8%AF%95%E6%80%BB%E7%BB%93)

## 11. FC、MCP、Skill 的关系

原文：[11. Function Calling、Skill、MCP 这三个有什么区别？](https://xiaolinnote.com/ai/tools/11_fc_skill_mcp.html)。

- **C11-1** Function Calling 发生在模型和函数之间，是最底层的调用语言：模型生成 tool_calls JSON 告诉宿主程序调哪个函数、参数是什么，宿主程序执行完把结果以 tool 消息的形式喂回去。[原文§从「谁和谁通信」来看三者位置](https://xiaolinnote.com/ai/tools/11_fc_skill_mcp.html#%E4%BB%8E%E3%80%8C%E8%B0%81%E5%92%8C%E8%B0%81%E9%80%9A%E4%BF%A1%E3%80%8D%E6%9D%A5%E7%9C%8B%E4%B8%89%E8%80%85%E4%BD%8D%E7%BD%AE)
- **C11-2** MCP 发生在 AI 客户端与工具服务之间：Client 连上 Server 后自动发现工具列表，把工具定义转换成 Function Calling 格式交给模型；模型生成调用请求后，Client 把它路由到对应 Server 执行，再把结果交回模型继续处理。这样工具成为可独立提供、跨应用复用的标准化服务。 [原文§从「谁和谁通信」来看三者位置](https://xiaolinnote.com/ai/tools/11_fc_skill_mcp.html#%E4%BB%8E%E3%80%8C%E8%B0%81%E5%92%8C%E8%B0%81%E9%80%9A%E4%BF%A1%E3%80%8D%E6%9D%A5%E7%9C%8B%E4%B8%89%E8%80%85%E4%BD%8D%E7%BD%AE)[原文§用一个完整故事串联三者](https://xiaolinnote.com/ai/tools/11_fc_skill_mcp.html#%E7%94%A8%E4%B8%80%E4%B8%AA%E5%AE%8C%E6%95%B4%E6%95%85%E4%BA%8B%E4%B8%B2%E8%81%94%E4%B8%89%E8%80%85)
- **C11-3** Skill 发生在 Agent 和知识模块之间：Agent 扫描可用的 Skill，判断哪个与任务相关后加载 SKILL.md 里的执行指令、脚本和模板；它的粒度是一个完整的工作流，内部可能涉及好几个步骤、调用好几个 MCP 工具。[原文§从「谁和谁通信」来看三者位置](https://xiaolinnote.com/ai/tools/11_fc_skill_mcp.html#%E4%BB%8E%E3%80%8C%E8%B0%81%E5%92%8C%E8%B0%81%E9%80%9A%E4%BF%A1%E3%80%8D%E6%9D%A5%E7%9C%8B%E4%B8%89%E8%80%85%E4%BD%8D%E7%BD%AE)
- **C11-4** 本篇按 Skill（定义流程）→ MCP（提供工具）→ Function Calling（模型触发调用）说明层级依赖：Skill 的步骤借助 MCP 提供工具，MCP 的工具再以 Function Calling 格式交给模型触发。原文用菜谱、厨房和手类比，把三层视为缺一不可，认为跳过任何一层都会缺少相应能力。（这是本篇的简化模型：Skill 也可以只靠脚本和命令行完成步骤，不一定经过 MCP；MCP 规范也不规定宿主怎样把工具交给模型。）[原文§三者的层级依赖关系](https://xiaolinnote.com/ai/tools/11_fc_skill_mcp.html#%E4%B8%89%E8%80%85%E7%9A%84%E5%B1%82%E7%BA%A7%E4%BE%9D%E8%B5%96%E5%85%B3%E7%B3%BB)[核对来源：MCP 规范·Tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)

### 补充考点

- **C11-5** Function Calling 是模型说我要调这个函数，最先出现，解决模型只会生成文本、怎么触发外部调用的基础调用协议问题；MCP 是工具服务说我能提供这些函数，解决接入标准化；Skill 是操作手册说用这些工具按这个流程做，解决有了一堆工具却不知道按什么流程和标准使用的知识与流程复用问题。[原文§为什么会有三个概念](https://xiaolinnote.com/ai/tools/11_fc_skill_mcp.html#%E4%B8%BA%E4%BB%80%E4%B9%88%E4%BC%9A%E6%9C%89%E4%B8%89%E4%B8%AA%E6%A6%82%E5%BF%B5)
- **C11-6** Function Calling 是手，能拿刀、点火、翻锅；MCP 是厨房，里面有各种厨具和食材；Skill 是菜谱，告诉你先后步骤。没有手什么都做不了，没有厨房只能对着菜谱发呆，没有菜谱面对一桌食材不知道先切什么后炒什么。[原文§三者的层级依赖关系](https://xiaolinnote.com/ai/tools/11_fc_skill_mcp.html#%E4%B8%89%E8%80%85%E7%9A%84%E5%B1%82%E7%BA%A7%E4%BE%9D%E8%B5%96%E5%85%B3%E7%B3%BB)
- **C11-7** Skill 层：Agent 扫描可用的 Skill，发现数据分析报告这个 Skill 匹配，加载它的 SKILL.md，读到取数据、做趋势分析、按模板写报告的流程；MCP 层：执行取数据这一步时，MCP Client 已经连着数据库和 Python 执行器的 MCP Server，自动知道有 query_database、run_python 这些工具可用。[原文§用一个完整故事串联三者](https://xiaolinnote.com/ai/tools/11_fc_skill_mcp.html#%E7%94%A8%E4%B8%80%E4%B8%AA%E5%AE%8C%E6%95%B4%E6%95%85%E4%BA%8B%E4%B8%B2%E8%81%94%E4%B8%89%E8%80%85)

## 12. A2A

原文：[12. 什么是 A2A 协议？它和 MCP 协议的区别是什么？](https://xiaolinnote.com/ai/tools/12_a2a_protocol.html)。

- **C12-1** MCP 是 Agent 向下连工具，属于纵向连接；A2A 是 Agent 向外连其他 Agent，用来互相通信、委派任务和接收结果，属于横向连接。两个协议解决的是不同维度的问题，不存在谁替代谁。[原文§A2A 和 MCP 的关系，一纵一横，各管一层](https://xiaolinnote.com/ai/tools/12_a2a_protocol.html#a2a-%E5%92%8C-mcp-%E7%9A%84%E5%85%B3%E7%B3%BB-%E4%B8%80%E7%BA%B5%E4%B8%80%E6%A8%AA-%E5%90%84%E7%AE%A1%E4%B8%80%E5%B1%82)
- **C12-2** Agent Card 是发布在约定位置的一张 JSON 名片，写明自己叫什么、能做哪类任务的 Skill 列表及示例输入、是否支持流式返回、是否支持异步回调。[原文§多 Agent 的基础问题，Agent 之间怎么互相认识？](https://xiaolinnote.com/ai/tools/12_a2a_protocol.html#%E5%A4%9A-agent-%E7%9A%84%E5%9F%BA%E7%A1%80%E9%97%AE%E9%A2%98-agent-%E4%B9%8B%E9%97%B4%E6%80%8E%E4%B9%88%E4%BA%92%E7%9B%B8%E8%AE%A4%E8%AF%86)
- **C12-3** Task 有完整的生命周期状态：创建时是 submitted，执行中是 working，最后是 completed 或 failed；长任务可能要跑几分钟，调度方不可能同步等着，提交后可以去做别的事，再通过轮询或回调得知完成。[原文§Task，A2A 里的一等公民](https://xiaolinnote.com/ai/tools/12_a2a_protocol.html#task-a2a-%E9%87%8C%E7%9A%84%E4%B8%80%E7%AD%89%E5%85%AC%E6%B0%91)
- **C12-4** 调度 Agent 提交 Task 后，通过轮询状态或 push notification 得知任务进展，等状态变为 completed 再去取 artifacts，也就是文本、文件等产出；整个过程不需要知道对方内部用了什么工具。[原文§Task，A2A 里的一等公民](https://xiaolinnote.com/ai/tools/12_a2a_protocol.html#task-a2a-%E9%87%8C%E7%9A%84%E4%B8%80%E7%AD%89%E5%85%AC%E6%B0%91)
- **C12-5** 原文把 A2A 类比为 Agent 的微服务化：Agent Card 像 API 文档和注册中心里的一条记录，让其他 Agent 能自动发现它并知道怎么调用；Task 状态机像异步消息队列，支持提交任务后去做别的事、完成了再来取结果。[原文§A2A 的架构本质，Agent 的微服务化](https://xiaolinnote.com/ai/tools/12_a2a_protocol.html#a2a-%E7%9A%84%E6%9E%B6%E6%9E%84%E6%9C%AC%E8%B4%A8-agent-%E7%9A%84%E5%BE%AE%E6%9C%8D%E5%8A%A1%E5%8C%96)

### 补充考点

- **C12-6** 一是工具数量的限制，不可能给一个 Agent 装 100 个工具，模型处理起来效率低、容易混乱；二是上下文窗口的限制，复杂任务积累的搜索结果、草稿、反思记录会很快把窗口塞满；三是专业能力的限制，同一个 Agent 既做代码审查又做市场分析，不如专门配置或微调的 Agent。[原文§为什么单个 Agent 不够用，上下文和专业边界](https://xiaolinnote.com/ai/tools/12_a2a_protocol.html#%E4%B8%BA%E4%BB%80%E4%B9%88%E5%8D%95%E4%B8%AA-agent-%E4%B8%8D%E5%A4%9F%E7%94%A8-%E4%B8%8A%E4%B8%8B%E6%96%87%E5%92%8C%E4%B8%93%E4%B8%9A%E8%BE%B9%E7%95%8C)
- **C12-7** 调度 Agent 把子任务委托给专业 Agent，后者自己搜几十个网页、写草稿、反复迭代，这些中间过程都留在它自己的上下文里，完成后只把最终结论通过 A2A 返回；调度 Agent 的上下文里只多了一份摘要，调研过程的上下文压力被隔离在子 Agent 内部。[原文§为什么单个 Agent 不够用，上下文和专业边界](https://xiaolinnote.com/ai/tools/12_a2a_protocol.html#%E4%B8%BA%E4%BB%80%E4%B9%88%E5%8D%95%E4%B8%AA-agent-%E4%B8%8D%E5%A4%9F%E7%94%A8-%E4%B8%8A%E4%B8%8B%E6%96%87%E5%92%8C%E4%B8%93%E4%B8%9A%E8%BE%B9%E7%95%8C)
- **C12-8** 在 A 的代码里硬编码 B 可以做什么太脆弱：B 的能力一变，A 的代码就得改，根本没法维护；所以多 Agent 系统需要一种让 Agent 互相发现能力的机制。[原文§多 Agent 的基础问题，Agent 之间怎么互相认识？](https://xiaolinnote.com/ai/tools/12_a2a_protocol.html#%E5%A4%9A-agent-%E7%9A%84%E5%9F%BA%E7%A1%80%E9%97%AE%E9%A2%98-agent-%E4%B9%8B%E9%97%B4%E6%80%8E%E4%B9%88%E4%BA%92%E7%9B%B8%E8%AE%A4%E8%AF%86)
- **C12-9** 可以把它理解成 Agent 世界里的微服务架构。[原文§A2A 的架构本质，Agent 的微服务化](https://xiaolinnote.com/ai/tools/12_a2a_protocol.html#a2a-%E7%9A%84%E6%9E%B6%E6%9E%84%E6%9C%AC%E8%B4%A8-agent-%E7%9A%84%E5%BE%AE%E6%9C%8D%E5%8A%A1%E5%8C%96)
- **C12-10** MCP 像公司里每个员工的工具箱，决定这个人能用什么工具干活；A2A 像公司里的协作流程，决定不同岗位的人怎么分工、怎么交接任务。两者是互补而非竞争关系，在复杂的多 Agent 系统里通常同时使用，把 A2A 当成 MCP 的竞品是最大的误区。[原文§A2A 和 MCP 的关系，一纵一横，各管一层](https://xiaolinnote.com/ai/tools/12_a2a_protocol.html#a2a-%E5%92%8C-mcp-%E7%9A%84%E5%85%B3%E7%B3%BB-%E4%B8%80%E7%BA%B5%E4%B8%80%E6%A8%AA-%E5%90%84%E7%AE%A1%E4%B8%80%E5%B1%82)

## 13. MCP 通信

原文：[13. MCP 协议通常采用什么通信方式？](https://xiaolinnote.com/ai/tools/13_mcp_transport.html)。

- **C13-1** JSON-RPC 2.0 是消息格式，只定义消息怎么写，不关心底层怎么传；stdio 和 Streamable HTTP 是 MCP 在此基础上定义的两种传输层实现。[原文§MCP 的消息格式：JSON-RPC 2.0](https://xiaolinnote.com/ai/tools/13_mcp_transport.html#mcp-%E7%9A%84%E6%B6%88%E6%81%AF%E6%A0%BC%E5%BC%8F-json-rpc-2-0)
- **C13-2** Client 把 Server 作为子进程启动，通过 stdin 和 stdout 经操作系统的管道通信：延迟极低，不需要开端口、没有网络安全问题，Server 的生命周期随 Client 自动管理；边界是两个进程要在同一台机器上运行。[原文§传输方式一：stdio（标准输入输出）](https://xiaolinnote.com/ai/tools/13_mcp_transport.html#%E4%BC%A0%E8%BE%93%E6%96%B9%E5%BC%8F%E4%B8%80-stdio-%E6%A0%87%E5%87%86%E8%BE%93%E5%85%A5%E8%BE%93%E5%87%BA)
- **C13-3** Server 作为独立的 HTTP 服务可以部署在云端，多个 Client 共享同一个 Server，支持跨机器访问，适合团队统一管理工具服务；代价是多了网络开销，还要处理认证和网络中断重连。[原文§传输方式二：Streamable HTTP（当前标准的远程传输）](https://xiaolinnote.com/ai/tools/13_mcp_transport.html#%E4%BC%A0%E8%BE%93%E6%96%B9%E5%BC%8F%E4%BA%8C-streamable-http-%E5%BD%93%E5%89%8D%E6%A0%87%E5%87%86%E7%9A%84%E8%BF%9C%E7%A8%8B%E4%BC%A0%E8%BE%93)
- **C13-4** HTTP+SSE 是 2024-11-05 规范采用的双端点方案，2025 年 3 月被标记为 deprecated，但保留向后兼容；Streamable HTTP 把两条通道合并成一个端点，流式推送的部分底层仍是 SSE，新项目应直接使用它。[原文§为什么 SSE 被弃用了](https://xiaolinnote.com/ai/tools/13_mcp_transport.html#%E4%B8%BA%E4%BB%80%E4%B9%88-sse-%E8%A2%AB%E5%BC%83%E7%94%A8%E4%BA%86)

### 补充考点

- **C13-5** MCP 需要的是 Client 调用 Server 的方法、Server 返回结果的通信模式，本质上就是远程过程调用；JSON-RPC 2.0 是现成的、足够轻量的 RPC 规范，用 JSON 格式易读易调试，任何语言都能实现，不需要额外的序列化工具。[原文§MCP 的消息格式：JSON-RPC 2.0](https://xiaolinnote.com/ai/tools/13_mcp_transport.html#mcp-%E7%9A%84%E6%B6%88%E6%81%AF%E6%A0%BC%E5%BC%8F-json-rpc-2-0)
- **C13-6** 两个进程通过操作系统在内存里分配的管道缓冲区传递一行行 JSON，整个过程不经过网卡和 TCP/IP 协议栈，数据在内存里走一趟就到，所以延迟比网络请求低得多；使用时只需在客户端配置文件里写明用什么命令启动 Server。[原文§传输方式一：stdio（标准输入输出）](https://xiaolinnote.com/ai/tools/13_mcp_transport.html#%E4%BC%A0%E8%BE%93%E6%96%B9%E5%BC%8F%E4%B8%80-stdio-%E6%A0%87%E5%87%86%E8%BE%93%E5%85%A5%E8%BE%93%E5%87%BA)
- **C13-7** 架构上同一个对话被拆成两条通道：Client 发请求走 POST 端点，Server 推数据走另一条 SSE 长连接端点；这使状态管理变复杂，例如 POST 之后网络断了，消息是否被处理、SSE 会不会推回结果，Client 没有简单的办法判断，排查链路很长。[原文§为什么 SSE 被弃用了](https://xiaolinnote.com/ai/tools/13_mcp_transport.html#%E4%B8%BA%E4%BB%80%E4%B9%88-sse-%E8%A2%AB%E5%BC%83%E7%94%A8%E4%BA%86)
- **C13-8** 想当然地以为 MCP 用的是 WebSocket 或者 HTTP REST 接口。[原文§🎯 面试总结](https://xiaolinnote.com/ai/tools/13_mcp_transport.html#%F0%9F%8E%AF-%E9%9D%A2%E8%AF%95%E6%80%BB%E7%BB%93)
- **C13-9** 只需在客户端配置文件里写明用什么命令启动 Server。[原文§传输方式一：stdio（标准输入输出）](https://xiaolinnote.com/ai/tools/13_mcp_transport.html#%E4%BC%A0%E8%BE%93%E6%96%B9%E5%BC%8F%E4%B8%80-stdio-%E6%A0%87%E5%87%86%E8%BE%93%E5%85%A5%E8%BE%93%E5%87%BA)

## 14. SSE 与 WebSocket

原文：[14. 说说 WebSocket 和 SSE 通信的区别及局限性？](https://xiaolinnote.com/ai/tools/14_sse_vs_websocket.html)。

- **C14-1** SSE 只有服务端能主动推，客户端想发消息必须另起一个 HTTP 请求；WebSocket 是全双工，客户端和服务端都可以随时主动发消息，一条连接搞定两个方向。[原文§WebSocket：从 HTTP 升级成真正的双向信道](https://xiaolinnote.com/ai/tools/14_sse_vs_websocket.html#websocket-%E4%BB%8E-http-%E5%8D%87%E7%BA%A7%E6%88%90%E7%9C%9F%E6%AD%A3%E7%9A%84%E5%8F%8C%E5%90%91%E4%BF%A1%E9%81%93)
- **C14-2** 文字对话天然是单向推：模型在输出、用户在看，用户要回复时再发一个新的 POST 即可；SSE 轻量、HTTP 原生支持、运维简单，所以 OpenAI、Anthropic 的 API 都选 SSE。[原文§在 AI 场景下怎么选？](https://xiaolinnote.com/ai/tools/14_sse_vs_websocket.html#%E5%9C%A8-ai-%E5%9C%BA%E6%99%AF%E4%B8%8B%E6%80%8E%E4%B9%88%E9%80%89)
- **C14-3** 用户可以直接在同一条连接里发送停止指令，服务端立刻收到并停止生成；用 SSE 则要另发一个独立的 HTTP 请求（如 POST）来传递控制消息，因为 SSE 只负责服务端到客户端的单向推送。（原文写的是“只能先关掉当前 SSE 流，再发新的 POST，中间有明显的断开重连过程”；这并非必须：SSE 只限制该事件流的传输方向，不禁止流仍打开时用另一个请求发送取消命令，是否关闭、何时关闭属于应用设计。）[原文§WebSocket：从 HTTP 升级成真正的双向信道](https://xiaolinnote.com/ai/tools/14_sse_vs_websocket.html#websocket-%E4%BB%8E-http-%E5%8D%87%E7%BA%A7%E6%88%90%E7%9C%9F%E6%AD%A3%E7%9A%84%E5%8F%8C%E5%90%91%E4%BF%A1%E9%81%93)[核对来源：WHATWG·Server-sent events 的 EventSource 接口](https://html.spec.whatwg.org/multipage/server-sent-events.html#the-eventsource-interface)
- **C14-4** HTTP/1.1 下浏览器对同一域名最多 6 条连接，SSE 占着一条长连接，标签页开多了后面的请求会排队，HTTP/2 的多路复用能解决；SSE 只能传文本，语音或图片要先做 Base64 编码，数据量膨胀约 33%。[原文§SSE 的局限：不只是「单向」那么简单](https://xiaolinnote.com/ai/tools/14_sse_vs_websocket.html#sse-%E7%9A%84%E5%B1%80%E9%99%90-%E4%B8%8D%E5%8F%AA%E6%98%AF%E3%80%8C%E5%8D%95%E5%90%91%E3%80%8D%E9%82%A3%E4%B9%88%E7%AE%80%E5%8D%95)
- **C14-5** 每条连接建立时被路由到某一台后端，之后该用户的消息都必须发到同一台，因为连接状态保存在那里；扩容时新机器接不到老连接，常见办法是把状态外移到 Redis 并用发布订阅中转，架构变复杂，延迟也增加。[原文§WebSocket 的局限：有状态带来的扩展麻烦](https://xiaolinnote.com/ai/tools/14_sse_vs_websocket.html#websocket-%E7%9A%84%E5%B1%80%E9%99%90-%E6%9C%89%E7%8A%B6%E6%80%81%E5%B8%A6%E6%9D%A5%E7%9A%84%E6%89%A9%E5%B1%95%E9%BA%BB%E7%83%A6)

### 补充考点

- **C14-6** HTTP 下服务端不能主动推数据，只能被动等客户端来问；而模型生成完整回答要几秒甚至十几秒，等全部生成完再返回，用户只能看着空白屏幕，所以需要连接保持打开、服务端生成一个词就推一个词。[原文§先从 HTTP 的本质说起](https://xiaolinnote.com/ai/tools/14_sse_vs_websocket.html#%E5%85%88%E4%BB%8E-http-%E7%9A%84%E6%9C%AC%E8%B4%A8%E8%AF%B4%E8%B5%B7)
- **C14-7** 不是新协议，而是 HTTP/1.1 里本来就有的特性：客户端发一个普通 HTTP GET 请求，在请求头里声明 Accept: text/event-stream；服务端收到后不关闭连接，持续往里写数据，相当于一个响应体无限长的 HTTP 响应，是一根从服务端流向客户端的单向水管。[原文§SSE：用普通 HTTP「撑开」一条单向水管](https://xiaolinnote.com/ai/tools/14_sse_vs_websocket.html#sse-%E7%94%A8%E6%99%AE%E9%80%9A-http%E3%80%8C%E6%92%91%E5%BC%80%E3%80%8D%E4%B8%80%E6%9D%A1%E5%8D%95%E5%90%91%E6%B0%B4%E7%AE%A1)
- **C14-8** SSE 的数据是很简单的纯文本格式，每条消息以 data: 开头，后面跟数据内容，结尾是两个换行符；浏览器内置 EventSource API，打开连接后注册 onmessage 回调，每收到一条消息自动触发，不用自己解析底层数据流。[原文§SSE：用普通 HTTP「撑开」一条单向水管](https://xiaolinnote.com/ai/tools/14_sse_vs_websocket.html#sse-%E7%94%A8%E6%99%AE%E9%80%9A-http%E3%80%8C%E6%92%91%E5%BC%80%E3%80%8D%E4%B8%80%E6%9D%A1%E5%8D%95%E5%90%91%E6%B0%B4%E7%AE%A1)
- **C14-9** 模型输出是一个个 token 组成的连续文本，中间丢一个 token 意思可能全变，顺序乱了更无法阅读，所以需要每个 token 准确到达、不乱序，这正是 TCP 可靠有序传输的强项；这与语音场景相反，语音里 TCP 的重传会造成不可接受的延迟。[原文§SSE：用普通 HTTP「撑开」一条单向水管](https://xiaolinnote.com/ai/tools/14_sse_vs_websocket.html#sse-%E7%94%A8%E6%99%AE%E9%80%9A-http%E3%80%8C%E6%92%91%E5%BC%80%E3%80%8D%E4%B8%80%E6%9D%A1%E5%8D%95%E5%90%91%E6%B0%B4%E7%AE%A1)
- **C14-10** WebSocket 是建立在 TCP 之上的独立协议：客户端先发一个看起来像普通 HTTP 的请求，请求头里声明想升级成 WebSocket；服务端同意就返回 101 Switching Protocols，此后这条 TCP 连接不再遵循一问一答，变成双方都可以随时发消息的全双工信道。[原文§WebSocket：从 HTTP 升级成真正的双向信道](https://xiaolinnote.com/ai/tools/14_sse_vs_websocket.html#websocket-%E4%BB%8E-http-%E5%8D%87%E7%BA%A7%E6%88%90%E7%9C%9F%E6%AD%A3%E7%9A%84%E5%8F%8C%E5%90%91%E4%BF%A1%E9%81%93)
- **C14-11** SSE 有内置的重连机制，断线后会自动重连；但要接着上次继续而不丢消息，服务端必须支持 Last-Event-ID，客户端重连时带上最后收到的消息 ID，服务端从那条之后重放。很多实现省略了这一块，导致断线后丢失中间内容。[原文§SSE 的局限：不只是「单向」那么简单](https://xiaolinnote.com/ai/tools/14_sse_vs_websocket.html#sse-%E7%9A%84%E5%B1%80%E9%99%90-%E4%B8%8D%E5%8F%AA%E6%98%AF%E3%80%8C%E5%8D%95%E5%90%91%E3%80%8D%E9%82%A3%E4%B9%88%E7%AE%80%E5%8D%95)
- **C14-12** 很多企业的 HTTP 代理、老版本 CDN 和某些安全网关不支持 WebSocket 的 Upgrade 握手，会把它当成异常 HTTP 请求拒掉；所以早期 MCP 的远程传输选了 SSE 而不是 WebSocket，因为 SSE 对各种复杂网络环境的兼容性好得多。[原文§WebSocket 的局限：有状态带来的扩展麻烦](https://xiaolinnote.com/ai/tools/14_sse_vs_websocket.html#websocket-%E7%9A%84%E5%B1%80%E9%99%90-%E6%9C%89%E7%8A%B6%E6%80%81%E5%B8%A6%E6%9D%A5%E7%9A%84%E6%89%A9%E5%B1%95%E9%BA%BB%E7%83%A6)
- **C14-13** HTTP 里每个请求天然对应一个响应，而 WebSocket 里消息就是消息；要实现发出一条消息、等待特定响应，必须自己在消息里加请求 ID，并在客户端维护请求 ID 到等待回调的映射表，断线重连后还在等待响应的请求也要专门设计重试逻辑。[原文§WebSocket 的局限：有状态带来的扩展麻烦](https://xiaolinnote.com/ai/tools/14_sse_vs_websocket.html#websocket-%E7%9A%84%E5%B1%80%E9%99%90-%E6%9C%89%E7%8A%B6%E6%80%81%E5%B8%A6%E6%9D%A5%E7%9A%84%E6%89%A9%E5%B1%95%E9%BA%BB%E7%83%A6)
- **C14-14** 多人协同编辑有频繁的双向消息，适合 WebSocket；实时语音对话需要 UDP 和低延迟，适合 WebRTC，WebSocket 的 TCP 重传是瓶颈；MCP 远程 Server 用 Streamable HTTP，内部仍用 SSE 做流式，保留了代理穿透友好的特性。[原文§在 AI 场景下怎么选？](https://xiaolinnote.com/ai/tools/14_sse_vs_websocket.html#%E5%9C%A8-ai-%E5%9C%BA%E6%99%AF%E4%B8%8B%E6%80%8E%E4%B9%88%E9%80%89)
- **C14-15** 单向推送用 SSE，真正需要双向实时交互才上 WebSocket，例如用户要在模型说话过程中随时打断；LLM 文字对话绝大多数场景用 SSE 就够了，这也是 OpenAI 和 Anthropic 的选择。认为 WebSocket 功能更强所以更好，是最大的误区。[原文§🎯 面试总结](https://xiaolinnote.com/ai/tools/14_sse_vs_websocket.html#%F0%9F%8E%AF-%E9%9D%A2%E8%AF%95%E6%80%BB%E7%BB%93)

## 15. WebRTC

原文：[15. 为什么要用 WebRTC 协议？它和 WebSocket（WS）在 AI 对话流中的核心差异是什么？](https://xiaolinnote.com/ai/tools/15_webrtc_vs_ws.html)。

- **C15-1** 人对语音时序极其敏感，延迟超过 200ms 就明显感到卡顿；丢掉一个 20ms 的音频片段人耳感知不到，但为了等它重传会把后续音频都堵住，延迟累积到几百毫秒。语音容忍丢包、不容忍延迟，与 TCP 的设计正好相反。[原文§📝 详细解析](https://xiaolinnote.com/ai/tools/15_webrtc_vs_ws.html#%F0%9F%93%9D-%E8%AF%A6%E7%BB%86%E8%A7%A3%E6%9E%90)
- **C15-2** 不是。WebRTC 是一套协议组合：UDP 提供低延迟传输，DTLS 负责密钥协商和加密，SRTP 与 RTCP 负责媒体传输及质量反馈，ICE 处理 NAT 穿透；实际音频流走 WebRTC 的 UDP 通道，信令通道则交换 SDP，告知对方编解码格式、网络地址和加密参数。SDP 只是描述格式，可由 WebSocket、HTTP 等通道传递。 [原文§WebRTC 不是单一协议，而是一套协议组合](https://xiaolinnote.com/ai/tools/15_webrtc_vs_ws.html#webrtc-%E4%B8%8D%E6%98%AF%E5%8D%95%E4%B8%80%E5%8D%8F%E8%AE%AE-%E8%80%8C%E6%98%AF%E4%B8%80%E5%A5%97%E5%8D%8F%E8%AE%AE%E7%BB%84%E5%90%88)[原文§SDP 信令：WebRTC 握手的「协商书」](https://xiaolinnote.com/ai/tools/15_webrtc_vs_ws.html#sdp-%E4%BF%A1%E4%BB%A4-webrtc-%E6%8F%A1%E6%89%8B%E7%9A%84%E3%80%8C%E5%8D%8F%E5%95%86%E4%B9%A6%E3%80%8D)
- **C15-3** SDP 用来让双方互相告知自己的能力：支持哪些音视频编解码格式、网络地址是什么、加密参数是什么。它只是一种格式，不规定如何传输，要通过信令通道来交换。[原文§SDP 信令：WebRTC 握手的「协商书」](https://xiaolinnote.com/ai/tools/15_webrtc_vs_ws.html#sdp-%E4%BF%A1%E4%BB%A4-webrtc-%E6%8F%A1%E6%89%8B%E7%9A%84%E3%80%8C%E5%8D%8F%E5%95%86%E4%B9%A6%E3%80%8D)
- **C15-4** ICE 按优先级依次尝试三种方式：同一局域网内直接用内网地址直连；借 STUN 服务器发现自己的公网 IP 和端口后打洞建立 P2P 连接；打洞失败时由 TURN 服务器中转流量。[原文§NAT 穿透：ICE/STUN/TURN 解决的问题](https://xiaolinnote.com/ai/tools/15_webrtc_vs_ws.html#nat-%E7%A9%BF%E9%80%8F-ice-stun-turn-%E8%A7%A3%E5%86%B3%E7%9A%84%E9%97%AE%E9%A2%98)
- **C15-5** 包括回声消除、噪声抑制、自动增益控制和自适应码率控制：分别处理扬声器外放造成的回声、环境噪声、音量不稳定，并根据网络状况动态调整音频比特率。[原文§WebRTC 内置的音频处理能力](https://xiaolinnote.com/ai/tools/15_webrtc_vs_ws.html#webrtc-%E5%86%85%E7%BD%AE%E7%9A%84%E9%9F%B3%E9%A2%91%E5%A4%84%E7%90%86%E8%83%BD%E5%8A%9B)
- **C15-6** 原文的选型原则是文字对话用 SSE 或 WebSocket，实时语音用 WebRTC；WebRTC 需要信令服务器和 STUN/TURN 服务器，实现和运维复杂度高，换来的是低延迟和音频质量。[原文§WebSocket 和 WebRTC 的核心差异总结](https://xiaolinnote.com/ai/tools/15_webrtc_vs_ws.html#websocket-%E5%92%8C-webrtc-%E7%9A%84%E6%A0%B8%E5%BF%83%E5%B7%AE%E5%BC%82%E6%80%BB%E7%BB%93)

### 补充考点

- **C15-7** 人类大脑对语音时序极其敏感：对话中超过 200ms 的延迟就会明显感觉卡顿，超过 400ms 会出现说话串线，以为对方说完了开口，结果对方还没说完。[原文§📝 详细解析](https://xiaolinnote.com/ai/tools/15_webrtc_vs_ws.html#%F0%9F%93%9D-%E8%AF%A6%E7%BB%86%E8%A7%A3%E6%9E%90)
- **C15-8** WebSocket 底层是 TCP，每次网络轻微抖动导致丢包，TCP 就会触发重传等待，整条流的延迟随之堆积，无法避免；TCP 的可靠性设计在实时语音场景里反而是负担。[原文§📝 详细解析](https://xiaolinnote.com/ai/tools/15_webrtc_vs_ws.html#%F0%9F%93%9D-%E8%AF%A6%E7%BB%86%E8%A7%A3%E6%9E%90)
- **C15-9** WebRTC 是 Google 主导开发、W3C 和 IETF 联合标准化的协议族，2011 年开始推进，最初目的是让浏览器之间不装插件就能直接做实时音视频通话；最核心的决策是把底层从 TCP 换成 UDP，主动放弃可靠性。[原文§WebRTC 的根本：选择 UDP，主动放弃可靠性](https://xiaolinnote.com/ai/tools/15_webrtc_vs_ws.html#webrtc-%E7%9A%84%E6%A0%B9%E6%9C%AC-%E9%80%89%E6%8B%A9-udp-%E4%B8%BB%E5%8A%A8%E6%94%BE%E5%BC%83%E5%8F%AF%E9%9D%A0%E6%80%A7)
- **C15-10** 不等待重传，而是用丢包隐藏技术自动填补：用前后帧插值生成一段听起来合理的音频来替代，播放不中断，只有极短暂、人耳感知不到的音质下降；这是用偶尔轻微的音质损失换取稳定低延迟的工程权衡。[原文§WebRTC 的根本：选择 UDP，主动放弃可靠性](https://xiaolinnote.com/ai/tools/15_webrtc_vs_ws.html#webrtc-%E7%9A%84%E6%A0%B9%E6%9C%AC-%E9%80%89%E6%8B%A9-udp-%E4%B8%BB%E5%8A%A8%E6%94%BE%E5%BC%83%E5%8F%AF%E9%9D%A0%E6%80%A7)
- **C15-11** WebRTC 不是单一协议，而是在 UDP 之上叠加了好几层、各管一件事的协议全家桶；RTP 是专门为实时媒体设计的协议，每个包都带时间戳和序列号，接收方据此知道包的时序和是否有丢失，并配合 RTCP 做传输质量的监控和反馈。[原文§WebRTC 不是单一协议，而是一套协议组合](https://xiaolinnote.com/ai/tools/15_webrtc_vs_ws.html#webrtc-%E4%B8%8D%E6%98%AF%E5%8D%95%E4%B8%80%E5%8D%8F%E8%AE%AE-%E8%80%8C%E6%98%AF%E4%B8%80%E5%A5%97%E5%8D%8F%E8%AE%AE%E7%BB%84%E5%90%88)
- **C15-12** 最常见的原因是对称 NAT：它对每个目标地址分配不同的出口端口，STUN 探测到的端口在对端连进来时已经换了，打洞打不通；这时只能退一步，用一台双方都能访问的 TURN 中转服务器转发流量。[原文§NAT 穿透：ICE/STUN/TURN 解决的问题](https://xiaolinnote.com/ai/tools/15_webrtc_vs_ws.html#nat-%E7%A9%BF%E9%80%8F-ice-stun-turn-%E8%A7%A3%E5%86%B3%E7%9A%84%E9%97%AE%E9%A2%98)
- **C15-13** 回声消除 AEC：外放 AI 声音时麦克风会把它再采集进去，不处理就形成反馈循环；噪声抑制 NS：过滤背景噪声只传人声；自动增益控制 AGC：音量太小自动放大、太大自动降低。这些是用 WebSocket 传语音最难补齐的部分。[原文§WebRTC 内置的音频处理能力](https://xiaolinnote.com/ai/tools/15_webrtc_vs_ws.html#webrtc-%E5%86%85%E7%BD%AE%E7%9A%84%E9%9F%B3%E9%A2%91%E5%A4%84%E7%90%86%E8%83%BD%E5%8A%9B)
- **C15-14** 端到端延迟必须低于 300ms 才有自然的对话感；语音必须双向同时流动，不能等一方说完再切换；用户说话时必须能随时打断 AI；还要解决回声消除，麦克风不能把 AI 正在播放的声音再传回去。OpenAI 的 Realtime API 正是因此选择 WebRTC。[原文§OpenAI Realtime API 选择 WebRTC 的决策逻辑](https://xiaolinnote.com/ai/tools/15_webrtc_vs_ws.html#openai-realtime-api-%E9%80%89%E6%8B%A9-webrtc-%E7%9A%84%E5%86%B3%E7%AD%96%E9%80%BB%E8%BE%91)
- **C15-15** ICE 按优先级依次尝试三种方式：同一局域网内直接用内网地址直连；借 STUN 服务器发现自己的公网 IP 和端口后打洞，建立 P2P 连接；打洞失败时由 TURN 服务器中转流量。[原文§NAT 穿透：ICE/STUN/TURN 解决的问题](https://xiaolinnote.com/ai/tools/15_webrtc_vs_ws.html#nat-%E7%A9%BF%E9%80%8F-ice-stun-turn-%E8%A7%A3%E5%86%B3%E7%9A%84%E9%97%AE%E9%A2%98)

- **C16-5** 把问题向量化后在向量数据库里做相似度搜索，相似度超过阈值就直接返回历史答案，跳过 LLM 调用；需要个性化或强实时性的问答应在网关层识别出来绕过缓存，天气、股价这类信息的缓存有效期也只能设几分钟。[原文§语义缓存：省钱的同时降延迟](https://xiaolinnote.com/ai/tools/16_llm_gateway.html#%E8%AF%AD%E4%B9%89%E7%BC%93%E5%AD%98-%E7%9C%81%E9%92%B1%E7%9A%84%E5%90%8C%E6%97%B6%E9%99%8D%E5%BB%B6%E8%BF%9F)
- **C16-6** 网关集中记录每次调用的 token 用量、响应时间和错误率，可以直接对接 Langfuse、Prometheus 等监控系统，不需要在业务代码里手动埋点。[原文§成本追踪和可观测性：知道钱花在哪](https://xiaolinnote.com/ai/tools/16_llm_gateway.html#%E6%88%90%E6%9C%AC%E8%BF%BD%E8%B8%AA%E5%92%8C%E5%8F%AF%E8%A7%82%E6%B5%8B%E6%80%A7-%E7%9F%A5%E9%81%93%E9%92%B1%E8%8A%B1%E5%9C%A8%E5%93%AA)
- **C16-7** 原文按类型和特点对比了 LiteLLM、Bifrost、PortKey、Kong AI Gateway、One API 和自研方案，并提醒关注 LiteLLM 的安全公告，做好版本锁定和校验。[原文§常见网关框架对比](https://xiaolinnote.com/ai/tools/16_llm_gateway.html#%E5%B8%B8%E8%A7%81%E7%BD%91%E5%85%B3%E6%A1%86%E6%9E%B6%E5%AF%B9%E6%AF%94)

### 补充考点

- **C16-8** 网关是一个中间人，坐在应用和各个模型 API 之间；应用只认识网关，不需要直接对接多个 API。它集中拦截和处理所有出入流量，所以能在这个位置统一做很多事情。[原文§先建立直觉：网关是什么，放在哪](https://xiaolinnote.com/ai/tools/16_llm_gateway.html#%E5%85%88%E5%BB%BA%E7%AB%8B%E7%9B%B4%E8%A7%89-%E7%BD%91%E5%85%B3%E6%98%AF%E4%BB%80%E4%B9%88-%E6%94%BE%E5%9C%A8%E5%93%AA)
- **C16-9** 安全问题：API Key 散落在各服务的配置里，任何一处泄露都是事故；重复劳动：每个服务各写一套重试和限流逻辑，版本不一、难排查；成本黑箱：各服务各记各的，无法统计总花费和各团队用量；灵活性差：限制某团队调用量或换模型都得改代码。[原文§没有网关时的痛点](https://xiaolinnote.com/ai/tools/16_llm_gateway.html#%E6%B2%A1%E6%9C%89%E7%BD%91%E5%85%B3%E6%97%B6%E7%9A%84%E7%97%9B%E7%82%B9)
- **C16-10** 网关可以统一做输入输出的安全校验，包括检测 prompt 注入攻击、过滤身份证号和手机号等个人隐私信息、内容安全审核；集中处理后，不需要每个业务服务各自实现，安全策略统一更新，任何接入点都自动获得保护，不会再出现某个服务漏了检测。[原文§Prompt 安全和内容过滤：统一的安全防线](https://xiaolinnote.com/ai/tools/16_llm_gateway.html#prompt-%E5%AE%89%E5%85%A8%E5%92%8C%E5%86%85%E5%AE%B9%E8%BF%87%E6%BB%A4-%E7%BB%9F%E4%B8%80%E7%9A%84%E5%AE%89%E5%85%A8%E9%98%B2%E7%BA%BF)
- **C16-11** 普通 HTTP 缓存是精确匹配，内容一字不差才能命中；而 LLM 的问题有大量语义相近的变体，例如问北京天气的几种说法本质是同一个需求，精确匹配全部落空，每次都要完整调用模型。语义缓存先把问题转换成向量，按语义相似度匹配历史答案。[原文§语义缓存：省钱的同时降延迟](https://xiaolinnote.com/ai/tools/16_llm_gateway.html#%E8%AF%AD%E4%B9%89%E7%BC%93%E5%AD%98-%E7%9C%81%E9%92%B1%E7%9A%84%E5%90%8C%E6%97%B6%E9%99%8D%E5%BB%B6%E8%BF%9F)
- **C16-12** 阈值太高，例如 0.99，只有几乎一样的问题才命中，缓存形同虚设；太低，例如 0.7，可能让北京的问题命中上海的答案；通常在 0.85 到 0.95 之间调试。有效期按内容类型定：天气、股价这类实时信息缓存几分钟，产品 FAQ、技术文档这类稳定知识可以缓存几天甚至更久。[原文§语义缓存：省钱的同时降延迟](https://xiaolinnote.com/ai/tools/16_llm_gateway.html#%E8%AF%AD%E4%B9%89%E7%BC%93%E5%AD%98-%E7%9C%81%E9%92%B1%E7%9A%84%E5%90%8C%E6%97%B6%E9%99%8D%E5%BB%B6%E8%BF%9F)
- **C16-13** LiteLLM 是最活跃的开源 Python 项目，支持 100 多个模型，但 2026 年 3 月发生过供应链安全事件，生产使用要关注安全公告并锁定版本；One API 是 Go 写的开源项目，国内社区活跃、对国产模型支持好、部署简单；Bifrost 是 2026 年新兴的高性能网关，用 Go 编写，主打低延迟和高吞吐。（原文写的是用 Rust 编写，官方仓库的代码主体是 Go。）[原文§常见网关框架对比](https://xiaolinnote.com/ai/tools/16_llm_gateway.html#%E5%B8%B8%E8%A7%81%E7%BD%91%E5%85%B3%E6%A1%86%E6%9E%B6%E5%AF%B9%E6%AF%94)[核对来源：Bifrost 官方仓库](https://github.com/maximhq/bifrost)
- **C16-14** 不要把它等同于普通的负载均衡器或反向代理，也不要只说负载均衡和统一接口，这两点普通 API 网关也能做；面试官想听的是 LLM 场景特有的问题，例如 token 配额管理、语义缓存、prompt 安全过滤。[原文§🎯 面试总结](https://xiaolinnote.com/ai/tools/16_llm_gateway.html#%F0%9F%8E%AF-%E9%9D%A2%E8%AF%95%E6%80%BB%E7%BB%93)

## 17. Tool Routing

原文：[17. 工具很多时，Agent 如何做 Tool Routing，减少 Token 并避免选错工具？](https://xiaolinnote.com/ai/tools/17_tool_routing.html)。

- **C17-1** 会带来四类问题：工具定义占用上下文并增加输入成本；相似工具描述重叠导致选择混淆；把无权使用的工具暴露给模型，扩大误调用和提示词注入的攻击面；输入更长、候选空间更大，延迟上升。[原文§为什么不能把全部工具都塞进 Prompt？](https://xiaolinnote.com/ai/tools/17_tool_routing.html#%E4%B8%BA%E4%BB%80%E4%B9%88%E4%B8%8D%E8%83%BD%E6%8A%8A%E5%85%A8%E9%83%A8%E5%B7%A5%E5%85%B7%E9%83%BD%E5%A1%9E%E8%BF%9B-prompt)
- **C17-2** 至少包括唯一名称与命名空间、能做什么、什么时候用、什么时候不用、输入输出 Schema、标签、权限与风险等级、状态与环境，以及版本与成本。[原文§第一步，建立可路由的工具注册表](https://xiaolinnote.com/ai/tools/17_tool_routing.html#%E7%AC%AC%E4%B8%80%E6%AD%A5-%E5%BB%BA%E7%AB%8B%E5%8F%AF%E8%B7%AF%E7%94%B1%E7%9A%84%E5%B7%A5%E5%85%B7%E6%B3%A8%E5%86%8C%E8%A1%A8)
- **C17-3** 原则是先鉴权、再做相关性召回：检索器只能在当前请求有权看到的工具集合里搜索，不能先从全库召回再靠 Prompt 说明不能用；隐藏只是减少暴露，执行时仍要在服务端按具体参数和资源重新鉴权。[原文§第二步，先做确定性过滤](https://xiaolinnote.com/ai/tools/17_tool_routing.html#%E7%AC%AC%E4%BA%8C%E6%AD%A5-%E5%85%88%E5%81%9A%E7%A1%AE%E5%AE%9A%E6%80%A7%E8%BF%87%E6%BB%A4)
- **C17-4** 粗分类用规则或轻量模型把请求分到业务域或工具类别，偏向高召回；候选检索在相关类别内召回少量 Top-K 工具；动态绑定只把候选工具的完整描述和 Schema 交给 LLM，由它判断是否需要工具、选哪个并填写参数。 [原文§第五步，只把候选工具动态绑定给 LLM](https://xiaolinnote.com/ai/tools/17_tool_routing.html#%E7%AC%AC%E4%BA%94%E6%AD%A5-%E5%8F%AA%E6%8A%8A%E5%80%99%E9%80%89%E5%B7%A5%E5%85%B7%E5%8A%A8%E6%80%81%E7%BB%91%E5%AE%9A%E7%BB%99-llm)[原文§第三步，用粗分类缩小业务域](https://xiaolinnote.com/ai/tools/17_tool_routing.html#%E7%AC%AC%E4%B8%89%E6%AD%A5-%E7%94%A8%E7%B2%97%E5%88%86%E7%B1%BB%E7%BC%A9%E5%B0%8F%E4%B8%9A%E5%8A%A1%E5%9F%9F)[原文§第四步，在候选域里检索工具](https://xiaolinnote.com/ai/tools/17_tool_routing.html#%E7%AC%AC%E5%9B%9B%E6%AD%A5-%E5%9C%A8%E5%80%99%E9%80%89%E5%9F%9F%E9%87%8C%E6%A3%80%E7%B4%A2%E5%B7%A5%E5%85%B7)
- **C17-5** Tool Routing 决定当前 Agent 为完成这一步应看到哪些工具、最终调用哪个，输出是候选工具集合或具体工具；Multi-Agent Routing 决定任务或子任务交给哪个 Agent，输出是下一位执行者或一次 Handoff。[原文§先分清 Tool Routing 和 Multi-Agent Routing](https://xiaolinnote.com/ai/tools/17_tool_routing.html#%E5%85%88%E5%88%86%E6%B8%85-tool-routing-%E5%92%8C-multi-agent-routing)
- **C17-6** 要分层看：候选召回层看 Recall@K，即正确工具是否进入 Top-K，并记录候选集大小和 Schema Token；模型精选层看工具选择准确率、该直接回答时是否错误调用工具、参数的 Schema 合法率；业务层看任务成功率、延迟、成本和未授权工具暴露率。[原文§怎么评估 Tool Routing？](https://xiaolinnote.com/ai/tools/17_tool_routing.html#%E6%80%8E%E4%B9%88%E8%AF%84%E4%BC%B0-tool-routing)
- **C17-7** 多个相似工具分数接近且涉及付款、删除、发信等高风险动作时，应进入确定性规则或人工审批，不能靠相似度直接执行；置信度太低时可改写查询、扩大召回，仍不确定就让用户补充信息。[原文§路由失败怎么兜底？](https://xiaolinnote.com/ai/tools/17_tool_routing.html#%E8%B7%AF%E7%94%B1%E5%A4%B1%E8%B4%A5%E6%80%8E%E4%B9%88%E5%85%9C%E5%BA%95)
- **C17-8** Skill 启动时只暴露名称和简短描述，匹配到任务后才加载详细步骤；被选中的 Skill 可以指明这项任务先后使用哪些工具，或把检索范围缩小到某个工具命名空间，从而缩小工具候选。它不能替代权限过滤和执行鉴权。[原文§Skill 渐进加载怎样参与 Tool Routing？](https://xiaolinnote.com/ai/tools/17_tool_routing.html#skill-%E6%B8%90%E8%BF%9B%E5%8A%A0%E8%BD%BD%E6%80%8E%E6%A0%B7%E5%8F%82%E4%B8%8E-tool-routing)

### 补充考点

- **C17-9** 例如同时存在 order_get、order_search、order_detail 和 after_sale_query，描述又都写着查询订单信息，模型很容易在相似选项之间选错；问题往往不是模型不懂，而是工具边界根本没有讲清楚。[原文§为什么不能把全部工具都塞进 Prompt？](https://xiaolinnote.com/ai/tools/17_tool_routing.html#%E4%B8%BA%E4%BB%80%E4%B9%88%E4%B8%8D%E8%83%BD%E6%8A%8A%E5%85%A8%E9%83%A8%E5%B7%A5%E5%85%B7%E9%83%BD%E5%A1%9E%E8%BF%9B-prompt)
- **C17-10** 可以：先选 Agent 能缩小业务边界，Agent 内部再选工具能缩小能力边界；但不能为了规避工具过多就无原则地拆出几十个 Agent，否则只是把工具目录变成 Agent 目录，任务切换、状态同步和调试成本反而上升。[原文§先分清 Tool Routing 和 Multi-Agent Routing](https://xiaolinnote.com/ai/tools/17_tool_routing.html#%E5%85%88%E5%88%86%E6%B8%85-tool-routing-%E5%92%8C-multi-agent-routing)
- **C17-11** 命名最好体现业务域加动作，例如 orders.search、orders.cancel；描述不仅写功能，还要写适用条件和排除条件；参数 Schema 要有清楚的类型、必填项、枚举、格式和字段说明。因为路由器和 LLM 读不到实现代码，主要靠工具卡片判断，描述高度重叠时再强的模型也只是在猜。[原文§第一步，建立可路由的工具注册表](https://xiaolinnote.com/ai/tools/17_tool_routing.html#%E7%AC%AC%E4%B8%80%E6%AD%A5-%E5%BB%BA%E7%AB%8B%E5%8F%AF%E8%B7%AF%E7%94%B1%E7%9A%84%E5%B7%A5%E5%85%B7%E6%B3%A8%E5%86%8C%E8%A1%A8)
- **C17-12** 它们提供稳定的一级索引：用户提到退款，可以先命中 payments 和 orders 两个命名空间，再在里面精确选择，而不是扫描整个企业工具库。[原文§第一步，建立可路由的工具注册表](https://xiaolinnote.com/ai/tools/17_tool_routing.html#%E7%AC%AC%E4%B8%80%E6%AD%A5-%E5%BB%BA%E7%AB%8B%E5%8F%AF%E8%B7%AF%E7%94%B1%E7%9A%84%E5%B7%A5%E5%85%B7%E6%B3%A8%E5%86%8C%E8%A1%A8)
- **C17-13** 静态过滤处理长期不变的边界，例如客服 Agent 只允许用客户、订单和知识库工具，开发环境禁止挂真实支付工具，可在初始化或注册时用 Allowlist、Blocklist 固定；动态过滤跟每次运行的上下文有关，条件包括租户、用户身份与角色、功能开关、地区、会话阶段、任务状态、工具健康状态和关键参数是否已收集。[原文§第二步，先做确定性过滤](https://xiaolinnote.com/ai/tools/17_tool_routing.html#%E7%AC%AC%E4%BA%8C%E6%AD%A5-%E5%85%88%E5%81%9A%E7%A1%AE%E5%AE%9A%E6%80%A7%E8%BF%87%E6%BB%A4)
- **C17-14** 边界很清楚的请求优先用规则：例如明确出现订单号并询问物流，就路由到订单加物流类别；工作流已进入付款确认节点，就只开放支付查询类工具。规则速度快、可解释，也方便审计。[原文§第三步，用粗分类缩小业务域](https://xiaolinnote.com/ai/tools/17_tool_routing.html#%E7%AC%AC%E4%B8%89%E6%AD%A5-%E7%94%A8%E7%B2%97%E5%88%86%E7%B1%BB%E7%BC%A9%E5%B0%8F%E4%B8%9A%E5%8A%A1%E5%9F%9F)
- **C17-15** 关键词或 BM25 适合匹配产品名、接口名、字段名和缩写；Embedding 更擅长语义匹配，例如用户问包裹还在路上吗，也能召回描述为查询物流轨迹的工具。实际项目可以做混合检索，再用分数融合或轻量 Reranker 排序。[原文§第四步，在候选域里检索工具](https://xiaolinnote.com/ai/tools/17_tool_routing.html#%E7%AC%AC%E5%9B%9B%E6%AD%A5-%E5%9C%A8%E5%80%99%E9%80%89%E5%9F%9F%E9%87%8C%E6%A3%80%E7%B4%A2%E5%B7%A5%E5%85%B7)
- **C17-16** 少数高频、低风险的工具可以常驻，例如只读搜索和帮助工具；长尾工具按需加载。这样能减少额外检索的概率，也不会让大批低频 Schema 长期占着上下文；阈值和 Top-K 要根据评测集里的召回率、Token、延迟和误选情况来调。[原文§第五步，只把候选工具动态绑定给 LLM](https://xiaolinnote.com/ai/tools/17_tool_routing.html#%E7%AC%AC%E4%BA%94%E6%AD%A5-%E5%8F%AA%E6%8A%8A%E5%80%99%E9%80%89%E5%B7%A5%E5%85%B7%E5%8A%A8%E6%80%81%E7%BB%91%E5%AE%9A%E7%BB%99-llm)
- **C17-17** 不要只改 Prompt：先检查它们是不是职责重叠，能否合并，或者把一个大而全的工具拆成边界清楚的查询与执行工具；工具名要具体，描述要同时回答做什么、何时用、何时不用、返回什么，相似工具之间直接写出差异。[原文§工具描述和 Schema 质量决定路由上限](https://xiaolinnote.com/ai/tools/17_tool_routing.html#%E5%B7%A5%E5%85%B7%E6%8F%8F%E8%BF%B0%E5%92%8C-schema-%E8%B4%A8%E9%87%8F%E5%86%B3%E5%AE%9A%E8%B7%AF%E7%94%B1%E4%B8%8A%E9%99%90)
- **C17-18** 需要。Schema 能用枚举就不放任意字符串，必填项、日期、ID 和数值范围都写清楚，再配少量正例和反例；但 Schema 约束解决的是格式合法性，业务合法性仍要在工具内部校验。[原文§工具描述和 Schema 质量决定路由上限](https://xiaolinnote.com/ai/tools/17_tool_routing.html#%E5%B7%A5%E5%85%B7%E6%8F%8F%E8%BF%B0%E5%92%8C-schema-%E8%B4%A8%E9%87%8F%E5%86%B3%E5%AE%9A%E8%B7%AF%E7%94%B1%E4%B8%8A%E9%99%90)

## 18. 工具调用容错

## 19. CLI 封装

原文：[19. 为什么要把 Agent 的工具执行流程封装成 CLI？](https://xiaolinnote.com/ai/tools/19_cli_packaging.html)。

- **C19-1** 主要是让工具流程能独立运行并被不同调用方复用：业务逻辑与聊天状态分开后，同一套能力既能给 Agent 调用，也能给开发者调试、脚本和定时任务使用；CLI 有明确的参数、结果和退出状态，出错时可以拿对应输入单独运行，判断是工具本身的问题还是 Agent 选错工具、传错参数；流程里已确定的步骤也可以由工具代码统一组织。[原文§💡 简要回答](https://xiaolinnote.com/ai/tools/19_cli_packaging.html#%F0%9F%92%A1-%E7%AE%80%E8%A6%81%E5%9B%9E%E7%AD%94)
- **C19-2** 工具能力是实际工作，如解析文档、查询数据、转换格式或生成文件；调用入口规定调用方怎样把请求交给这份能力、怎样拿到结果，同一份能力可以通过函数接口、命令行或网络接口使用。CLI 即命令行接口，是一种程序接口：调用方指定程序与参数，程序执行后通过输出和退出状态交回结果，人和另一个程序都能调用。[原文§工具能力和调用入口，是两个不同层次](https://xiaolinnote.com/ai/tools/19_cli_packaging.html#%E5%B7%A5%E5%85%B7%E8%83%BD%E5%8A%9B%E5%92%8C%E8%B0%83%E7%94%A8%E5%85%A5%E5%8F%A3-%E6%98%AF%E4%B8%A4%E4%B8%AA%E4%B8%8D%E5%90%8C%E5%B1%82%E6%AC%A1)
- **C19-3** 例如文档转换要先检查格式、读取内容、执行转换、再核对产物，如果全部暴露成零散操作让模型每次重新安排，会增加决策和交互，还可能漏掉检查或顺序出错；封装后调用方给出输入和目标，程序按约定完成内部流程，模型仍负责决定何时使用它，但不必反复生成已确定的执行细节。[原文§把确定的工具流程交给代码，减少重复编排](https://xiaolinnote.com/ai/tools/19_cli_packaging.html#%E6%8A%8A%E7%A1%AE%E5%AE%9A%E7%9A%84%E5%B7%A5%E5%85%B7%E6%B5%81%E7%A8%8B%E4%BA%A4%E7%BB%99%E4%BB%A3%E7%A0%81-%E5%87%8F%E5%B0%91%E9%87%8D%E5%A4%8D%E7%BC%96%E6%8E%92)
- **C19-4** 一个命令应有清楚的业务目的、输入和结果；内部若需要新的用户决定，不能为了一步完成而悄悄猜参数或扩大权限。例如本地生成文件和把文件发布到外部是两项不同影响，可以分别提供入口，确需组合也要在命令约定中说明传播范围和执行条件。流程封装的收益函数或服务也能实现，CLI 额外提供的是可独立启动的入口。[原文§把确定的工具流程交给代码，减少重复编排](https://xiaolinnote.com/ai/tools/19_cli_packaging.html#%E6%8A%8A%E7%A1%AE%E5%AE%9A%E7%9A%84%E5%B7%A5%E5%85%B7%E6%B5%81%E7%A8%8B%E4%BA%A4%E7%BB%99%E4%BB%A3%E7%A0%81-%E5%87%8F%E5%B0%91%E9%87%8D%E5%A4%8D%E7%BC%96%E6%8E%92)
- **C19-5** 因为它的依赖没有变：函数从当前对话里读文件路径、从 Agent 的全局对象里拿配置、还要求初始化模型连接，调用方只想转换一个文件也得补齐整个 Agent 环境。要让工具接收明确输入、返回明确结果，聊天内容由 Agent 理解并转换，工具只处理收到的业务参数，必须的运行配置显式传入。[原文§从 Agent 中拆出工具，才能让同一能力被复用](https://xiaolinnote.com/ai/tools/19_cli_packaging.html#%E4%BB%8E-agent-%E4%B8%AD%E6%8B%86%E5%87%BA%E5%B7%A5%E5%85%B7-%E6%89%8D%E8%83%BD%E8%AE%A9%E5%90%8C%E4%B8%80%E8%83%BD%E5%8A%9B%E8%A2%AB%E5%A4%8D%E7%94%A8)
- **C19-6** 分成入口解析参数、业务核心执行处理、结果适配把返回值转成约定格式三部分，业务核心不需要知道会话编号或模型 SDK 怎样初始化；这样 CLI、函数入口和其他接口都复用同一份业务核心，开发者调试、自动化脚本和 Agent 适配器用的是同一份逻辑，避免各入口各复制一遍代码、修了一处其他入口仍是旧错误。[原文§从 Agent 中拆出工具，才能让同一能力被复用](https://xiaolinnote.com/ai/tools/19_cli_packaging.html#%E4%BB%8E-agent-%E4%B8%AD%E6%8B%86%E5%87%BA%E5%B7%A5%E5%85%B7-%E6%89%8D%E8%83%BD%E8%AE%A9%E5%90%8C%E4%B8%80%E8%83%BD%E5%8A%9B%E8%A2%AB%E5%A4%8D%E7%94%A8)
- **C19-7** 不是。另一种语言只要能启动程序并处理结果就能使用这份工具，不必把业务代码导入自己的进程；但目标机器仍要有可执行程序、所需运行时和依赖，通过本地 CLI 调用也不会自动变成远程服务调用。[原文§从 Agent 中拆出工具，才能让同一能力被复用](https://xiaolinnote.com/ai/tools/19_cli_packaging.html#%E4%BB%8E-agent-%E4%B8%AD%E6%8B%86%E5%87%BA%E5%B7%A5%E5%85%B7-%E6%89%8D%E8%83%BD%E8%AE%A9%E5%90%8C%E4%B8%80%E8%83%BD%E5%8A%9B%E8%A2%AB%E5%A4%8D%E7%94%A8)
- **C19-8** 一种方式是向模型暴露结构化业务工具：工具说明定义名称、用途和参数，模型生成调用请求，宿主解析标识、确认访问范围后调用固定的可执行程序，再把结果解析后送回模型；这层映射叫执行适配器，连接模型的请求格式与 CLI 的参数格式，业务核心不依赖模型接口。模型输出请求时操作还没发生，真正启动进程的是宿主。[原文§CLI 接入 Agent，还需要一层执行适配](https://xiaolinnote.com/ai/tools/19_cli_packaging.html#cli-%E6%8E%A5%E5%85%A5-agent-%E8%BF%98%E9%9C%80%E8%A6%81%E4%B8%80%E5%B1%82%E6%89%A7%E8%A1%8C%E9%80%82%E9%85%8D)

## 20. CLI 与 MCP 的选型

原文：[20. Agent 接入工具时应该如何选择 CLI 或 MCP？](https://xiaolinnote.com/ai/tools/20_cli_vs_mcp.html)。

- **C20-1** 主要看调用方的接入需求和维护成本：只有一个可控的宿主、已有稳定的 CLI 时，直接适配通常更简单；一项能力要被多个兼容 MCP 的宿主复用时，MCP 更有价值，工具描述、参数结构和调用方式通过统一协议提供，减少重复接入。两者可以组合，已有 CLI 可以由 MCP Server 包装，部署位置要单独考虑，不能按“本地用 CLI、远程用 MCP”来选。[原文§💡 简要回答](https://xiaolinnote.com/ai/tools/20_cli_vs_mcp.html#%F0%9F%92%A1-%E7%AE%80%E8%A6%81%E5%9B%9E%E7%AD%94)
- **C20-2** CLI 提供程序的执行入口：调用方指定可执行程序、子命令和参数，程序执行后交回输出与退出状态；MCP 即 Model Context Protocol，规范的是客户端与能力服务之间的交互，服务端按协议提供工具信息，客户端按协议发现并调用，业务怎样实现留给服务端。链路可以是 Agent 宿主、MCP 客户端、MCP Server、CLI 或业务函数、实际资源，CLI 是其中的执行入口，MCP 是它外面的接入层。[原文§先分清执行入口与接入协议](https://xiaolinnote.com/ai/tools/20_cli_vs_mcp.html#%E5%85%88%E5%88%86%E6%B8%85%E6%89%A7%E8%A1%8C%E5%85%A5%E5%8F%A3%E4%B8%8E%E6%8E%A5%E5%85%A5%E5%8D%8F%E8%AE%AE)
- **C20-3** 宿主是运行模型调用、管理工具并组织任务的应用程序；模型负责根据材料选择动作，宿主负责把动作请求送到实际实现。接入工具时，除了让代码运行起来，还要让宿主知道这项能力叫什么、接受哪些参数、返回什么结果。[原文§先分清执行入口与接入协议](https://xiaolinnote.com/ai/tools/20_cli_vs_mcp.html#%E5%85%88%E5%88%86%E6%B8%85%E6%89%A7%E8%A1%8C%E5%85%A5%E5%8F%A3%E4%B8%8E%E6%8E%A5%E5%85%A5%E5%8D%8F%E8%AE%AE)
- **C20-4** 宿主要提供工具名称、用途和参数说明；模型生成结构化请求后，把参数映射成程序参数并启动 CLI，例如把文件标识解析成路径并检查是否在允许范围；再把结果、诊断日志和退出状态按约定解释后转成工具返回，不能把所有终端文字拼在一起当业务结果。优势是链路短，调用方和命令由同一团队维护时，一份清楚的适配器往往就够了。[原文§直接调用 CLI，Agent 侧还需要做哪些适配？](https://xiaolinnote.com/ai/tools/20_cli_vs_mcp.html#%E7%9B%B4%E6%8E%A5%E8%B0%83%E7%94%A8-cli-agent-%E4%BE%A7%E8%BF%98%E9%9C%80%E8%A6%81%E5%81%9A%E5%93%AA%E4%BA%9B%E9%80%82%E9%85%8D)
- **C20-5** CLI 可以提供帮助或自定义的机器可读描述，但普通 CLI 并没有普遍遵循一套面向 Agent 的工具发现与调用协议，如何获取说明、转换参数和理解结果仍要调用方与工具协商；另一种接法是给模型通用命令执行能力，减少了专门映射，却扩大了模型可以提出的操作范围，也依赖它对命令的理解。[原文§直接调用 CLI，Agent 侧还需要做哪些适配？](https://xiaolinnote.com/ai/tools/20_cli_vs_mcp.html#%E7%9B%B4%E6%8E%A5%E8%B0%83%E7%94%A8-cli-agent-%E4%BE%A7%E8%BF%98%E9%9C%80%E8%A6%81%E5%81%9A%E5%93%AA%E4%BA%9B%E9%80%82%E9%85%8D)
- **C20-6** 客户端通过 tools/list 获取可用工具，工具信息包含名称、用途描述和输入 Schema，即参数的结构定义，如字段类型、必填项和取值限制；宿主把适合当前任务的工具提供给模型，模型决定调用后，客户端通过 tools/call 发送工具名和参数，服务端执行并返回结果。协议还约定了工具结果的表达方式，包括内容、可选的结构化结果和错误的表示。[原文§MCP 统一了哪些交互，又留下哪些实现责任？](https://xiaolinnote.com/ai/tools/20_cli_vs_mcp.html#mcp-%E7%BB%9F%E4%B8%80%E4%BA%86%E5%93%AA%E4%BA%9B%E4%BA%A4%E4%BA%92-%E5%8F%88%E7%95%99%E4%B8%8B%E5%93%AA%E4%BA%9B%E5%AE%9E%E7%8E%B0%E8%B4%A3%E4%BB%BB)
- **C20-7** 标准化不等于零适配：宿主仍要决定向模型展示哪些工具、怎样组织上下文，服务端仍负责业务实现、参数校验、权限检查和错误处理，具体业务字段也仍由工具定义；模型支持工具调用和宿主支持 MCP 要分别判断，不同协议版本和客户端支持的功能也可能不同，实际接入要确认双方兼容。[原文§MCP 统一了哪些交互，又留下哪些实现责任？](https://xiaolinnote.com/ai/tools/20_cli_vs_mcp.html#mcp-%E7%BB%9F%E4%B8%80%E4%BA%86%E5%93%AA%E4%BA%9B%E4%BA%A4%E4%BA%92-%E5%8F%88%E7%95%99%E4%B8%8B%E5%93%AA%E4%BA%9B%E5%AE%9E%E7%8E%B0%E8%B4%A3%E4%BB%BB)
- **C20-8** 不是，部署位置是独立的选择。MCP 的 stdio 传输通过进程的标准输入输出交流，客户端通常启动本地服务进程，这个服务也可以在内部调用远程系统；Streamable HTTP 通过 HTTP 承载 MCP 交互，适合集中部署、多个客户端连接同一服务；CLI 的入口运行在调用方环境，但它也能访问远程系统或充当网络服务的客户端。[原文§本地或远程，是独立于 CLI、MCP 的部署选择](https://xiaolinnote.com/ai/tools/20_cli_vs_mcp.html#%E6%9C%AC%E5%9C%B0%E6%88%96%E8%BF%9C%E7%A8%8B-%E6%98%AF%E7%8B%AC%E7%AB%8B%E4%BA%8E-cli%E3%80%81mcp-%E7%9A%84%E9%83%A8%E7%BD%B2%E9%80%89%E6%8B%A9)
- **C20-9** 不等于，通道相同不代表协议相同：CLI 接收业务参数、打印一份 JSON 结果后退出，stdio MCP 服务则要收发符合协议的消息，处理工具发现、调用和对应结果，JSON 只是编码形式；stdio 的协议输出还要保持可解析，普通日志不能混进 stdout 的消息通道，诊断信息可以写到 stderr。[原文§本地或远程，是独立于 CLI、MCP 的部署选择](https://xiaolinnote.com/ai/tools/20_cli_vs_mcp.html#%E6%9C%AC%E5%9C%B0%E6%88%96%E8%BF%9C%E7%A8%8B-%E6%98%AF%E7%8B%AC%E7%AB%8B%E4%BA%8E-cli%E3%80%81mcp-%E7%9A%84%E9%83%A8%E7%BD%B2%E9%80%89%E6%8B%A9)

## 21. 代码执行沙箱

原文：[21. Agent 的代码执行沙箱应该如何设计？](https://xiaolinnote.com/ai/tools/21_execution_sandbox.html)。

- **C21-1** 让代码只拿到当前任务需要的权限，并把资源消耗限制在预算里；模型生成的代码按不可信代码处理，不能只靠 Prompt 约束，也不应直接继承宿主的全部权限。执行环境只提供本次任务的输入并设为只读，给临时目录和输出目录写权限，用低权限身份运行，网络按需开放，再由沙箱外的运行器管理整个执行过程。[原文§💡 简要回答](https://xiaolinnote.com/ai/tools/21_execution_sandbox.html#%F0%9F%92%A1-%E7%AE%80%E8%A6%81%E5%9B%9E%E7%AD%94)
- **C21-2** 程序真正能做什么取决于它运行时拥有的能力：操作系统处理文件读取、网络连接和进程创建时，检查的是进程身份、访问权限和系统规则；用宿主账号运行，代码里的一个错误路径或依赖里的额外操作就能用上这些权限。Prompt 和代码审查替代不了运行时限制，真实访问发生时必须有执行环境能拒绝越界操作。[原文§为什么要限制运行环境，而不是只检查代码？](https://xiaolinnote.com/ai/tools/21_execution_sandbox.html#%E4%B8%BA%E4%BB%80%E4%B9%88%E8%A6%81%E9%99%90%E5%88%B6%E8%BF%90%E8%A1%8C%E7%8E%AF%E5%A2%83-%E8%80%8C%E4%B8%8D%E6%98%AF%E5%8F%AA%E6%A3%80%E6%9F%A5%E4%BB%A3%E7%A0%81)
- **C21-3** 访问限制决定能接触哪些文件、网络和系统能力，资源限制决定能消耗多少计算、内存和其他资源；代码看不到宿主文件仍可能占满内存，只运行几秒也可能在几秒内读走敏感数据，所以沙箱不能只做其中一项。[原文§为什么要限制运行环境，而不是只检查代码？](https://xiaolinnote.com/ai/tools/21_execution_sandbox.html#%E4%B8%BA%E4%BB%80%E4%B9%88%E8%A6%81%E9%99%90%E5%88%B6%E8%BF%90%E8%A1%8C%E7%8E%AF%E5%A2%83-%E8%80%8C%E4%B8%8D%E6%98%AF%E5%8F%AA%E6%A3%80%E6%9F%A5%E4%BB%A3%E7%A0%81)

## 22. Skill 加载机制

原文：[22. Agent 的 Skill 加载机制是如何实现的？](https://xiaolinnote.com/ai/tools/22_skill_loading.html)。

- **C22-1** 通常采用渐进式加载：宿主先发现可用的能力包，读取 SKILL.md 里的名称和描述形成轻量目录；模型根据任务和描述判断需要哪个 Skill，或由用户明确指定，再把对应正文读进上下文；详细参考、模板和脚本留在包里，执行到需要的步骤时再取用。加载只是补充模型当前的工作信息，不更新模型参数，也不等于执行脚本。[原文§💡 简要回答](https://xiaolinnote.com/ai/tools/22_skill_loading.html#%F0%9F%92%A1-%E7%AE%80%E8%A6%81%E5%9B%9E%E7%AD%94)
- **C22-2** 模型作判断时只能使用当前请求里提供的材料和运行程序通过工具交给它的信息，文件存在并不会自动改变模型这次看到的内容；要让它按手册工作，宿主需要把相关指令送进上下文，模型可以提出读取请求，真正找到文件、取得内容并传回去的是宿主和工具。[原文§加载 Skill，实际上是把工作方法交给模型](https://xiaolinnote.com/ai/tools/22_skill_loading.html#%E5%8A%A0%E8%BD%BD-skill-%E5%AE%9E%E9%99%85%E4%B8%8A%E6%98%AF%E6%8A%8A%E5%B7%A5%E4%BD%9C%E6%96%B9%E6%B3%95%E4%BA%A4%E7%BB%99%E6%A8%A1%E5%9E%8B)
- **C22-3** 加载正文后模型获得的是这类任务应该怎样处理的信息，可以据此选择步骤和工具，但模型权重没有更新；Markdown 指令不会因为被读到就成为已执行的代码，它影响的是模型后续的决策，具体操作还需要工具完成。[原文§加载 Skill，实际上是把工作方法交给模型](https://xiaolinnote.com/ai/tools/22_skill_loading.html#%E5%8A%A0%E8%BD%BD-skill-%E5%AE%9E%E9%99%85%E4%B8%8A%E6%98%AF%E6%8A%8A%E5%B7%A5%E4%BD%9C%E6%96%B9%E6%B3%95%E4%BA%A4%E7%BB%99%E6%A8%A1%E5%9E%8B)
- **C22-4** 靠元数据建立的能力目录：开放的 Agent Skills 格式在 SKILL.md 顶部用 YAML frontmatter 写结构化信息，最基本的字段是 name 和 description，分别说明能力名称和适用任务；宿主从允许的目录、服务或内置包中发现 Skill，解析元数据，保存名称、描述和内容位置，再把可用目录提供给模型。[原文§先用元数据建立能力目录](https://xiaolinnote.com/ai/tools/22_skill_loading.html#%E5%85%88%E7%94%A8%E5%85%83%E6%95%B0%E6%8D%AE%E5%BB%BA%E7%AB%8B%E8%83%BD%E5%8A%9B%E7%9B%AE%E5%BD%95)
- **C22-5** 名称便于识别，描述帮助选择：只写“处理文件”，模型很难区分表格清理、文档转换和图片压缩，要说明处理对象与任务边界才有匹配依据；内容位置必须保留，模型选定某个 Skill 后宿主要知道去哪里读正文，不能只有名字而没有实际来源。[原文§先用元数据建立能力目录](https://xiaolinnote.com/ai/tools/22_skill_loading.html#%E5%85%88%E7%94%A8%E5%85%83%E6%95%B0%E6%8D%AE%E5%BB%BA%E7%AB%8B%E8%83%BD%E5%8A%9B%E7%9B%AE%E5%BD%95)
- **C22-6** 不等于。发现阶段宿主可以把全文缓存在内存里，但只有实际交给模型的部分才占用本轮模型输入，程序缓存和模型上下文是两个不同位置；目录本身也有成本，Skill 很多时宿主可以按可见范围或相关性筛选目录，但要保留找到所需能力的途径。[原文§先用元数据建立能力目录](https://xiaolinnote.com/ai/tools/22_skill_loading.html#%E5%85%88%E7%94%A8%E5%85%83%E6%95%B0%E6%8D%AE%E5%BB%BA%E7%AB%8B%E8%83%BD%E5%8A%9B%E7%9B%AE%E5%BD%95)
- **C22-7** 常见做法是模型调用文件读取工具打开对应的 SKILL.md，内容作为工具结果返回；模型没有文件读取能力时可以提供专用加载工具，由模型提交 Skill 标识、宿主取出正文返回；用户显式指定时宿主也可以直接加载。模型输出“使用某个 Skill”只表达了选择，只有正文真正进入上下文，才具备按它工作的材料。[原文§选中 Skill 后，正文才进入上下文](https://xiaolinnote.com/ai/tools/22_skill_loading.html#%E9%80%89%E4%B8%AD-skill-%E5%90%8E-%E6%AD%A3%E6%96%87%E6%89%8D%E8%BF%9B%E5%85%A5%E4%B8%8A%E4%B8%8B%E6%96%87)
- **C22-8** 正文通常包含执行顺序、必要检查和交付要求，要提供足够的主流程，让模型读完知道从哪里开始，只写一句“详细内容见附件”是不够的；自动匹配不保证选对，描述相似、范围不清会导致误选，任务缺少关键要求时可能要先澄清。发现位置、触发方式和内容传递由宿主实现，Skill 格式只约定包内内容怎样组织。[原文§选中 Skill 后，正文才进入上下文](https://xiaolinnote.com/ai/tools/22_skill_loading.html#%E9%80%89%E4%B8%AD-skill-%E5%90%8E-%E6%AD%A3%E6%96%87%E6%89%8D%E8%BF%9B%E5%85%A5%E4%B8%8A%E4%B8%8B%E6%96%87)
- **C22-9** 元数据层提供名称与适用描述，解决当前任务该选哪个能力；操作正文层提供主流程与必要要求，解决选中以后怎样开展工作；辅助资源层提供详细参考、模板和脚本，解决当前步骤需要哪些额外材料或实现。三层不是都要无条件读完，资源层尤其要按正文与当前任务选择。[原文§正文与资源分层，形成渐进式加载](https://xiaolinnote.com/ai/tools/22_skill_loading.html#%E6%AD%A3%E6%96%87%E4%B8%8E%E8%B5%84%E6%BA%90%E5%88%86%E5%B1%82-%E5%BD%A2%E6%88%90%E6%B8%90%E8%BF%9B%E5%BC%8F%E5%8A%A0%E8%BD%BD)
- **C22-10** SKILL.md 放名称、描述和主流程，references 目录放特定字段的详细说明等参考资料，assets 目录放输出模板，scripts 目录放可执行的处理程序；模型读到某一步需要字段规则时再读对应参考文件，需要交付格式时再取模板，没进入这些步骤的任务不必携带它们。[原文§正文与资源分层，形成渐进式加载](https://xiaolinnote.com/ai/tools/22_skill_loading.html#%E6%AD%A3%E6%96%87%E4%B8%8E%E8%B5%84%E6%BA%90%E5%88%86%E5%B1%82-%E5%BD%A2%E6%88%90%E6%B8%90%E8%BF%9B%E5%BC%8F%E5%8A%A0%E8%BD%BD)
