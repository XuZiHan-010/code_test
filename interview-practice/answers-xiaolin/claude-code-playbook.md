# Claude Code 实践技巧 原文章节摘编

仅依据各题所列的小林面试笔记原文章节整理；本文件只整理原文口径，不作现行规格认证。原文未覆盖的部分明确标注，不使用其他网站补充。整理日期：2026-10-13。

## 1. `CLAUDE.md` 项目记忆

原文：[CLAUDE.md 指南：Claude Code 的项目记忆该怎么写？](https://xiaolinnote.com/claudecode/playbook/cc_claude_md.html)。

### 内容与规则质量

- **G1-1** 原文引用官方的话：README 是写给人看的，CLAUDE.md 是写给 agent 看的，读者不同、密度也不同。README 可以长、可以散，Claude 默认不会主动去读；CLAUDE.md 则被自动加载，每次都吃 token。[原文§01｜CLAUDE.md 到底是个什么东西？](https://xiaolinnote.com/claudecode/playbook/cc_claude_md.html#_01-claude-md-%E5%88%B0%E5%BA%95%E6%98%AF%E4%B8%AA%E4%BB%80%E4%B9%88%E4%B8%9C%E8%A5%BF)
- **G1-2** CLAUDE.md 在每次打开 Claude Code 时都会被自动读一遍，作为整段会话的默认前提；README 这类其他文档 Claude 默认不会主动去读，不告诉它去看就当不存在。[原文§01｜CLAUDE.md 到底是个什么东西？](https://xiaolinnote.com/claudecode/playbook/cc_claude_md.html#_01-claude-md-%E5%88%B0%E5%BA%95%E6%98%AF%E4%B8%AA%E4%BB%80%E4%B9%88%E4%B8%9C%E8%A5%BF)
- **G1-3** 原文给出两个原因：CLAUDE.md 每次启动都完整加载，行数越多越挤压对话、思考和工具结果的空间；模型注意力有限，规则越多每条的权重越被摊薄。原文引用的实测是 200 行以内遵守率约 92%，400 行以上明显下降。[原文§02｜写多了反而废？](https://xiaolinnote.com/claudecode/playbook/cc_claude_md.html#_02-%E5%86%99%E5%A4%9A%E4%BA%86%E5%8F%8D%E8%80%8C%E5%BA%9F)
- **G1-4** 架构会变，而复制进文件里的内容却停留在旧时代；正确做法是用一行话指向那份文档，Claude 需要时自己会去读。[原文§02｜写多了反而废？](https://xiaolinnote.com/claudecode/playbook/cc_claude_md.html#_02-%E5%86%99%E5%A4%9A%E4%BA%86%E5%8F%8D%E8%80%8C%E5%BA%9F)
- **G1-5** Repo、PR 这类通用术语 Claude 本来就懂，不必写；真正需要解释的是团队特有的黑话，例如某个代称指的是预发布环境，但原文也建议把它放到 docs/glossary.md 里。[原文§02｜写多了反而废？](https://xiaolinnote.com/claudecode/playbook/cc_claude_md.html#_02-%E5%86%99%E5%A4%9A%E4%BA%86%E5%8F%8D%E8%80%8C%E5%BA%9F)
- **G1-6** 关键差异是可验证：具体规则 Claude 写完自己就能检查，模糊规则需要外部标准，它只能猜你的偏好。例如测试一下你的修改就不如提交前跑 npm test 有效。[原文§03｜什么样的规则才真正「有效」？](https://xiaolinnote.com/claudecode/playbook/cc_claude_md.html#_03-%E4%BB%80%E4%B9%88%E6%A0%B7%E7%9A%84%E8%A7%84%E5%88%99%E6%89%8D%E7%9C%9F%E6%AD%A3%E3%80%8C%E6%9C%89%E6%95%88%E3%80%8D)
- **G1-7** 把抽象意图翻译成可执行的命令、可定位的路径和可验证的规则，例如 API 处理函数放在 src/api/handlers/ 目录下，组件文件用 PascalCase、工具函数用 kebab-case。[原文§03｜什么样的规则才真正「有效」？](https://xiaolinnote.com/claudecode/playbook/cc_claude_md.html#_03-%E4%BB%80%E4%B9%88%E6%A0%B7%E7%9A%84%E8%A7%84%E5%88%99%E6%89%8D%E7%9C%9F%E6%AD%A3%E3%80%8C%E6%9C%89%E6%95%88%E3%80%8D)
- **G1-8** 写明原因后 Claude 不仅知道规则，还知道规则的边界：例如知道禁止写生产库是为了防生产事故，被问到能否写预发布数据库时，就能基于规则的本质做判断，而不是机械地套字面。[原文§03｜什么样的规则才真正「有效」？](https://xiaolinnote.com/claudecode/playbook/cc_claude_md.html#_03-%E4%BB%80%E4%B9%88%E6%A0%B7%E7%9A%84%E8%A7%84%E5%88%99%E6%89%8D%E7%9C%9F%E6%AD%A3%E3%80%8C%E6%9C%89%E6%95%88%E3%80%8D)
- **G1-9** 规则摆在那儿，Claude 就会试图遵守，但规则本身已经过时，结果是花 token 买一份混乱；所以要把 CLAUDE.md 当活文档维护：Claude 在哪里犯错两次以上就加一条防御规则，老规则同样要删。[原文§03｜什么样的规则才真正「有效」？](https://xiaolinnote.com/claudecode/playbook/cc_claude_md.html#_03-%E4%BB%80%E4%B9%88%E6%A0%B7%E7%9A%84%E8%A7%84%E5%88%99%E6%89%8D%E7%9C%9F%E6%AD%A3%E3%80%8C%E6%9C%89%E6%95%88%E3%80%8D)
- **G1-10** 原文称模板里 Gotchas 部分价值最高，因为这些坑都是踩出来的经验，Claude 没法从代码里推断。[原文§06｜可以参考的模板](https://xiaolinnote.com/claudecode/playbook/cc_claude_md.html#_06-%E5%8F%AF%E4%BB%A5%E5%8F%82%E8%80%83%E7%9A%84%E6%A8%A1%E6%9D%BF)
- **G1-11** CLAUDE.md 没有标准模板，每个项目都该有自己的样子；别迷信任何人的最佳实践，包括原文自己，要把原则吃透后按项目的实际情况裁剪。[原文§03｜什么样的规则才真正「有效」？](https://xiaolinnote.com/claudecode/playbook/cc_claude_md.html#_03-%E4%BB%80%E4%B9%88%E6%A0%B7%E7%9A%84%E8%A7%84%E5%88%99%E6%89%8D%E7%9C%9F%E6%AD%A3%E3%80%8C%E6%9C%89%E6%95%88%E3%80%8D)

### 分层、引用与维护

- **G1-12** 项目根的 CLAUDE.md 写整个项目的通用约定，每次启动都加载；子目录的 CLAUDE.md 写模块特有的规则，工作到该目录才生效；~/.claude/CLAUDE.md 写跨项目的个人偏好。[原文§04｜CLAUDE.md 不只是一个文件](https://xiaolinnote.com/claudecode/playbook/cc_claude_md.html#_04-claude-md-%E4%B8%8D%E5%8F%AA%E6%98%AF%E4%B8%80%E4%B8%AA%E6%96%87%E4%BB%B6)
- **G1-13** 子目录的 CLAUDE.md 按需加载，Claude 工作到该目录才生效：改前端代码时才读前端的组件约定，改后端时前端那份规则不进上下文，既不互相污染，也节省 token。[原文§04｜CLAUDE.md 不只是一个文件](https://xiaolinnote.com/claudecode/playbook/cc_claude_md.html#_04-claude-md-%E4%B8%8D%E5%8F%AA%E6%98%AF%E4%B8%80%E4%B8%AA%E6%96%87%E4%BB%B6)
- **G1-14** 每个 rules 文件可以在顶部的 frontmatter 里用 paths 标注适用的文件路径，Claude 只在处理匹配路径的文件时才加载这份规则，例如测试规则只在改测试文件时加载。[原文§04｜CLAUDE.md 不只是一个文件](https://xiaolinnote.com/claudecode/playbook/cc_claude_md.html#_04-claude-md-%E4%B8%8D%E5%8F%AA%E6%98%AF%E4%B8%80%E4%B8%AA%E6%96%87%E4%BB%B6)
- **G1-15** 原文的做法是把规则写在一份文件里，另一份只留一行 @ 引用指令，Claude Code 加载时顺着引用把内容读进来，做到一份文件、零重复维护，规则一改不必改两遍。[原文§04｜CLAUDE.md 不只是一个文件](https://xiaolinnote.com/claudecode/playbook/cc_claude_md.html#_04-claude-md-%E4%B8%8D%E5%8F%AA%E6%98%AF%E4%B8%80%E4%B8%AA%E6%96%87%E4%BB%B6)
- **G1-16** 把所有规则写在 AGENTS.md 里，CLAUDE.md 只留一行 @AGENTS.md：Claude Code 顺着引用读入，Codex 本来就直接读 AGENTS.md，两个工具共用一份规则。[原文§04｜CLAUDE.md 不只是一个文件](https://xiaolinnote.com/claudecode/playbook/cc_claude_md.html#_04-claude-md-%E4%B8%8D%E5%8F%AA%E6%98%AF%E4%B8%80%E4%B8%AA%E6%96%87%E4%BB%B6)
- **G1-17** 原文引用官方说法：如果两条规则互相矛盾，Claude 可能会随便挑一条；模型没法判断哪条优先级更高。[原文§04｜CLAUDE.md 不只是一个文件](https://xiaolinnote.com/claudecode/playbook/cc_claude_md.html#_04-claude-md-%E4%B8%8D%E5%8F%AA%E6%98%AF%E4%B8%80%E4%B8%AA%E6%96%87%E4%BB%B6)
- **G1-18** /init 会扫一遍代码库，把分析出的技术栈、目录结构和常用命令起成草稿；草稿并不完美，需要 review 一遍，删掉不准的、补上漏掉的。[原文§05｜/init 起步、/memory 维护](https://xiaolinnote.com/claudecode/playbook/cc_claude_md.html#_05-init-%E8%B5%B7%E6%AD%A5%E3%80%81-memory-%E7%BB%B4%E6%8A%A4)
- **G1-19** 一是输入 /memory，会弹出 CLAUDE.md 供直接修改；二是直接对 Claude 说记一下这条规则，它会自动追加到合适的 CLAUDE.md 里。[原文§05｜/init 起步、/memory 维护](https://xiaolinnote.com/claudecode/playbook/cc_claude_md.html#_05-init-%E8%B5%B7%E6%AD%A5%E3%80%81-memory-%E7%BB%B4%E6%8A%A4)
- **G1-20** 原文的做法是分层之后定期 review，把过时的、冲突的规则清掉，作者每 1 到 2 周扫一次。[原文§04｜CLAUDE.md 不只是一个文件](https://xiaolinnote.com/claudecode/playbook/cc_claude_md.html#_04-claude-md-%E4%B8%8D%E5%8F%AA%E6%98%AF%E4%B8%80%E4%B8%AA%E6%96%87%E4%BB%B6)
- **G1-21** 项目概览用两三行说明技术栈和定位；命令列出常用且可直接执行的操作；架构简短指出目录职责和详细文档位置；团队约定记录真实使用的命名、API 返回格式和错误处理习惯；硬约束划清不能越过的边界并写明原因；坑点保存从代码里推断不出的历史经验。 [原文§06｜可以参考的模板](https://xiaolinnote.com/claudecode/playbook/cc_claude_md.html#_06-%E5%8F%AF%E4%BB%A5%E5%8F%82%E8%80%83%E7%9A%84%E6%A8%A1%E6%9D%BF)
- **G1-22** 原文建议先抄结构，再填自己项目的内容；复制完整内容只是换了个壳，规则还是不准。[原文§06｜可以参考的模板](https://xiaolinnote.com/claudecode/playbook/cc_claude_md.html#_06-%E5%8F%AF%E4%BB%A5%E5%8F%82%E8%80%83%E7%9A%84%E6%A8%A1%E6%9D%BF)
- **G1-23** Plan Mode 下 Claude 先出一份计划、确认后再执行，出计划时会把 CLAUDE.md 里的规则全部考虑进去，所以规则质量直接决定计划质量；作者称对 3 个文件以上的改动，这套组合的提升很明显。[原文§05｜/init 起步、/memory 维护](https://xiaolinnote.com/claudecode/playbook/cc_claude_md.html#_05-init-%E8%B5%B7%E6%AD%A5%E3%80%81-memory-%E7%BB%B4%E6%8A%A4)

### 补充考点

- **G1-24** 每次打开 Claude Code，在用户输入第一句话之前，Claude 都会先把这个文件自动读一遍，当作整段对话的 ground truth，也就是默认成立的前提；它不是可选的提示，而是默认的前提，规则写进去就相当于给 Claude 装了稳定的长期记忆。[原文§01｜CLAUDE.md 到底是个什么东西？](https://xiaolinnote.com/claudecode/playbook/cc_claude_md.html#_01-claude-md-%E5%88%B0%E5%BA%95%E6%98%AF%E4%B8%AA%E4%BB%80%E4%B9%88%E4%B8%9C%E8%A5%BF)
- **G1-25** src/utils/claudemd.ts 的逻辑是：从当前所在目录一路往上爬到文件系统根目录，把每一层目录记下来；然后反向遍历，从根目录往下读每一层的 CLAUDE.md 和 .claude/CLAUDE.md，全部合并喂给模型，所以一个项目可能同时有好几份在生效。[原文§01｜CLAUDE.md 到底是个什么东西？](https://xiaolinnote.com/claudecode/playbook/cc_claude_md.html#_01-claude-md-%E5%88%B0%E5%BA%95%E6%98%AF%E4%B8%AA%E4%BB%80%E4%B9%88%E4%B8%9C%E8%A5%BF)
- **G1-26** 把所有规则塞在一个 CLAUDE.md 里，控制在 200 行以内时，规则遵守率大约 92%；写到 400 行往上，遵守率就明显往下掉。[原文§02｜写多了反而废？](https://xiaolinnote.com/claudecode/playbook/cc_claude_md.html#_02-%E5%86%99%E5%A4%9A%E4%BA%86%E5%8F%8D%E8%80%8C%E5%BA%9F)
- **G1-27** 像希望测试覆盖率达到 90%、目标是 0 bug 这类话，Claude 没法判断希望和实际的差距，可能为了满足愿望乱补一堆没意义的测试；CLAUDE.md 里只写当下实际执行的规则，例如 PR 提交前必须跑 npm test。[原文§02｜写多了反而废？](https://xiaolinnote.com/claudecode/playbook/cc_claude_md.html#_02-%E5%86%99%E5%A4%9A%E4%BA%86%E5%8F%8D%E8%80%8C%E5%BA%9F)
- **G1-28** 每个文件聚焦一个主题，控制在 30 行以内，结构清爽、好维护；可以在文件头用 paths 指定生效的路径范围，例如只对测试文件或接口目录生效。[原文§04｜CLAUDE.md 不只是一个文件](https://xiaolinnote.com/claudecode/playbook/cc_claude_md.html#_04-claude-md-%E4%B8%8D%E5%8F%AA%E6%98%AF%E4%B8%80%E4%B8%AA%E6%96%87%E4%BB%B6)
- **G1-29** 用 CLAUDE.md 起步；长了就拆到 rules/；高频的工作流写到 commands/；可复用的能力封装成 skills/。[原文§04｜CLAUDE.md 不只是一个文件](https://xiaolinnote.com/claudecode/playbook/cc_claude_md.html#_04-claude-md-%E4%B8%8D%E5%8F%AA%E6%98%AF%E4%B8%80%E4%B8%AA%E6%96%87%E4%BB%B6)
- **G1-30** 第一，总行数约 50 行，给以后补规则留出空间；第二，Architecture 简短指路，不复述架构详情；第三，Hard Constraints 写明原因；第四，Gotchas 保存亲历的坑点，这类经验无法只靠读代码推断，原文认为它价值最高。 [原文§06｜可以参考的模板](https://xiaolinnote.com/claudecode/playbook/cc_claude_md.html#_06-%E5%8F%AF%E4%BB%A5%E5%8F%82%E8%80%83%E7%9A%84%E6%A8%A1%E6%9D%BF)

## 2. 大型代码库实战

原文：[Claude Code 大型代码库实战：百万行代码怎么扛得住？](https://xiaolinnote.com/claudecode/playbook/cc_large_codebase.html)。

### 上下文与定位

- **G2-1** 原文认为问题不在模型小，而在 Claude Code 靠 agentic search 找代码：它严重依赖一个好的起点 context，没有清晰的起点就会乱翻，等摸清结构时上下文已经被烧得差不多了。[原文§Q1：大代码库下 context 老爆，是不是模型太小了？](https://xiaolinnote.com/claudecode/playbook/cc_large_codebase.html#q1-%E5%A4%A7%E4%BB%A3%E7%A0%81%E5%BA%93%E4%B8%8B-context-%E8%80%81%E7%88%86-%E6%98%AF%E4%B8%8D%E6%98%AF%E6%A8%A1%E5%9E%8B%E5%A4%AA%E5%B0%8F%E4%BA%86)
- **G2-2** 原文指出即使窗口有 1M token，一个像样的项目也动辄几百万行代码，再大的窗口也塞不下整个代码库；所以关键不在窗口多大，而在怎样精准找到要改的那几行。[原文§Q1：大代码库下 context 老爆，是不是模型太小了？](https://xiaolinnote.com/claudecode/playbook/cc_large_codebase.html#q1-%E5%A4%A7%E4%BB%A3%E7%A0%81%E5%BA%93%E4%B8%8B-context-%E8%80%81%E7%88%86-%E6%98%AF%E4%B8%8D%E6%98%AF%E6%A8%A1%E5%9E%8B%E5%A4%AA%E5%B0%8F%E4%BA%86)
- **G2-3** 原文称 Anthropic 的 harness 共七层：CLAUDE.md、Hooks、Skills、Plugins、MCP，再加 LSP 和子 agent 两个增强；它是围绕模型搭的那套外壳，对实际效果的影响不亚于模型本身。[原文§Q1：大代码库下 context 老爆，是不是模型太小了？](https://xiaolinnote.com/claudecode/playbook/cc_large_codebase.html#q1-%E5%A4%A7%E4%BB%A3%E7%A0%81%E5%BA%93%E4%B8%8B-context-%E8%80%81%E7%88%86-%E6%98%AF%E4%B8%8D%E6%98%AF%E6%A8%A1%E5%9E%8B%E5%A4%AA%E5%B0%8F%E4%BA%86)
- **G2-4** 原文称换模型没用，问题在于怎么找代码，并引用官方观点 harness 与模型一样重要：context 爆是因为没给 Claude 一个好的起点，要靠把外围的 harness 一层层搭好来解决。[原文§Q1：大代码库下 context 老爆，是不是模型太小了？](https://xiaolinnote.com/claudecode/playbook/cc_large_codebase.html#q1-%E5%A4%A7%E4%BB%A3%E7%A0%81%E5%BA%93%E4%B8%8B-context-%E8%80%81%E7%88%86-%E6%98%AF%E4%B8%8D%E6%98%AF%E6%A8%A1%E5%9E%8B%E5%A4%AA%E5%B0%8F%E4%BA%86)

- **G2-6** 模块细节放到各子目录的 CLAUDE.md，根文件只留指针、关键坑点和跨包通用约定，避免根文件堆满各模块细节；专项流程放进 Skill，只有任务需要时才加载。原文还举例把支付部署 Skill 绑定到 services/payments/，避免改前端时引入支付流程。 [原文§第一步：先把高频操作做成 skill](https://xiaolinnote.com/claudecode/playbook/cc_large_codebase.html#%E7%AC%AC%E4%B8%80%E6%AD%A5-%E5%85%88%E6%8A%8A%E9%AB%98%E9%A2%91%E6%93%8D%E4%BD%9C%E5%81%9A%E6%88%90-skill) [原文§Q2：CLAUDE.md 到底写多长合适？写了 1000 行，Claude 反而变笨？](https://xiaolinnote.com/claudecode/playbook/cc_large_codebase.html#q2-claude-md-%E5%88%B0%E5%BA%95%E5%86%99%E5%A4%9A%E9%95%BF%E5%90%88%E9%80%82-%E5%86%99%E4%BA%86-1000-%E8%A1%8C-claude-%E5%8F%8D%E8%80%8C%E5%8F%98%E7%AC%A8)

### 跨文件工作与团队推广

- **G2-12** 原文称重构、迁移这类大动作里，Claude 前半段还在状态，后半段就开始忘前面、漏改、改错；让它一边读代码一边改代码，光读懂系统就要烧掉好几万 token。[原文§Q4：跨几十个文件的改动，Claude 总是改一半就崩，怎么救？](https://xiaolinnote.com/claudecode/playbook/cc_large_codebase.html#q4-%E8%B7%A8%E5%87%A0%E5%8D%81%E4%B8%AA%E6%96%87%E4%BB%B6%E7%9A%84%E6%94%B9%E5%8A%A8-claude-%E6%80%BB%E6%98%AF%E6%94%B9%E4%B8%80%E5%8D%8A%E5%B0%B1%E5%B4%A9-%E6%80%8E%E4%B9%88%E6%95%91)
- **G2-13** 按会话拆分：会话 1 只做探索、写 plan，不动代码；会话 2 加载 plan 实现一个模块并跑通测试；会话 3 实现下一个模块。每个会话都从干净的上下文开始，由 plan 文件串联。[原文§Q4：跨几十个文件的改动，Claude 总是改一半就崩，怎么救？](https://xiaolinnote.com/claudecode/playbook/cc_large_codebase.html#q4-%E8%B7%A8%E5%87%A0%E5%8D%81%E4%B8%AA%E6%96%87%E4%BB%B6%E7%9A%84%E6%94%B9%E5%8A%A8-claude-%E6%80%BB%E6%98%AF%E6%94%B9%E4%B8%80%E5%8D%8A%E5%B0%B1%E5%B4%A9-%E6%80%8E%E4%B9%88%E6%95%91)
- **G2-14** 原文的结论是跨大量文件的改动救不回来的不是 prompt，而是会话边界：正确解法是把任务拆成多个会话并用 subagent 做探索，而不是写更长的 prompt，让每个会话都从干净的上下文开始。[原文§Q4：跨几十个文件的改动，Claude 总是改一半就崩，怎么救？](https://xiaolinnote.com/claudecode/playbook/cc_large_codebase.html#q4-%E8%B7%A8%E5%87%A0%E5%8D%81%E4%B8%AA%E6%96%87%E4%BB%B6%E7%9A%84%E6%94%B9%E5%8A%A8-claude-%E6%80%BB%E6%98%AF%E6%94%B9%E4%B8%80%E5%8D%8A%E5%B0%B1%E5%B4%A9-%E6%80%8E%E4%B9%88%E6%95%91)
- **G2-15** 先用对话方式把迁移方案敲定，然后它一次性派出几十个并行的 subagent，每个在独立的 git worktree 里运行、自测并开 PR；不用守着屏幕，跑完直接得到一堆 PR 等 review。[原文§Q4：跨几十个文件的改动，Claude 总是改一半就崩，怎么救？](https://xiaolinnote.com/claudecode/playbook/cc_large_codebase.html#q4-%E8%B7%A8%E5%87%A0%E5%8D%81%E4%B8%AA%E6%96%87%E4%BB%B6%E7%9A%84%E6%94%B9%E5%8A%A8-claude-%E6%80%BB%E6%98%AF%E6%94%B9%E4%B8%80%E5%8D%8A%E5%B0%B1%E5%B4%A9-%E6%80%8E%E4%B9%88%E6%95%91)
- **G2-16** 原文建议第一步先把高频操作做成 skill，即针对具体任务的 SOP，并引用 Boris 的话：一件事一天做超过一次，就把它做成 skill。大项目的高频操作就那么几十种，做成 skill 可以全队共享。[原文§第一步：先把高频操作做成 skill](https://xiaolinnote.com/claudecode/playbook/cc_large_codebase.html#%E7%AC%AC%E4%B8%80%E6%AD%A5-%E5%85%88%E6%8A%8A%E9%AB%98%E9%A2%91%E6%93%8D%E4%BD%9C%E5%81%9A%E6%88%90-skill)

- **G2-21** 原文观察到推广最顺的组织会在大面积铺开之前，先安排一小队人把整套基础设施搭好再放开访问；因为第一印象如果是这东西不好使，后面要翻盘就太难了。[原文§第四步：得有人负责维护](https://xiaolinnote.com/claudecode/playbook/cc_large_codebase.html#%E7%AC%AC%E5%9B%9B%E6%AD%A5-%E5%BE%97%E6%9C%89%E4%BA%BA%E8%B4%9F%E8%B4%A3%E7%BB%B4%E6%8A%A4)
- **G2-22** 不用跳过权限的参数，而是用 /permissions 把常用的安全命令预先加白名单；复杂任务几乎都从 Plan Mode 开始，再切到 auto-accept；挂 PostToolUse hook 自动跑格式化；每天做超过一次的事都做成 slash command 或 skill；团队共享一份提交到 git 的 CLAUDE.md，发现做错立刻加进去。[原文§Q6：Boris 自己平时怎么用 Claude Code？](https://xiaolinnote.com/claudecode/playbook/cc_large_codebase.html#q6-boris-%E8%87%AA%E5%B7%B1%E5%B9%B3%E6%97%B6%E6%80%8E%E4%B9%88%E7%94%A8-claude-code)

### 补充考点

- **G2-25** 官方博客的原话是 The harness matters as much as the model，即 harness 跟模型一样重要；原文用厨师作比：大厨厉不厉害是模型能力，家里有没有趁手的灶台、菜刀、调料架才是 harness，灶台不行，再牛的厨师也炒不出锅气。[原文§Q1：大代码库下 context 老爆，是不是模型太小了？](https://xiaolinnote.com/claudecode/playbook/cc_large_codebase.html#q1-%E5%A4%A7%E4%BB%A3%E7%A0%81%E5%BA%93%E4%B8%8B-context-%E8%80%81%E7%88%86-%E6%98%AF%E4%B8%8D%E6%98%AF%E6%A8%A1%E5%9E%8B%E5%A4%AA%E5%B0%8F%E4%BA%86)
- **G2-26** 业内的主流答案是 RAG：把代码切片、做 embedding、塞进向量数据库，要查的时候用相似度召回；Cursor、Copilot、Windsurf 走的都是这条路，而 Anthropic 选了反主流的路线。[原文§Q1：大代码库下 context 老爆，是不是模型太小了？](https://xiaolinnote.com/claudecode/playbook/cc_large_codebase.html#q1-%E5%A4%A7%E4%BB%A3%E7%A0%81%E5%BA%93%E4%B8%8B-context-%E8%80%81%E7%88%86-%E6%98%AF%E4%B8%8D%E6%98%AF%E6%A8%A1%E5%9E%8B%E5%A4%AA%E5%B0%8F%E4%BA%86)
- **G2-27** 对每一行问自己：如果删掉这行，Claude 还会按这条规则做事吗？答案是会，说明常识或代码已经体现，就该删；答案是不会，才值得留。Boris 的口号是对 CLAUDE.md 下狠手，毫不留情地删。[原文§Q2：CLAUDE.md 到底写多长合适？写了 1000 行 Claude 反而变笨？](https://xiaolinnote.com/claudecode/playbook/cc_large_codebase.html#q2-claude-md-%E5%88%B0%E5%BA%95%E5%86%99%E5%A4%9A%E9%95%BF%E5%90%88%E9%80%82-%E5%86%99%E4%BA%86-1000-%E8%A1%8C-claude-%E5%8F%8D%E8%80%8C%E5%8F%98%E7%AC%A8)
- **G2-28** 以前为约束旧模型写的规则，例如每次重构只改一个文件，在新模型上可能反而成了枷锁，因为新模型已经能做跨文件的协调编辑；为弥补旧模型弱点写的 Hook、Skill，升级之后也可能直接成为多余负担。所以用得上不去时，先检查 CLAUDE.md 是不是过期了。[原文§Q2：CLAUDE.md 到底写多长合适？写了 1000 行 Claude 反而变笨？](https://xiaolinnote.com/claudecode/playbook/cc_large_codebase.html#q2-claude-md-%E5%88%B0%E5%BA%95%E5%86%99%E5%A4%9A%E9%95%BF%E5%90%88%E9%80%82-%E5%86%99%E4%BA%86-1000-%E8%A1%8C-claude-%E5%8F%8D%E8%80%8C%E5%8F%98%E7%AC%A8)
- **G2-29** Hooks 是事件钩子机制，可以在编辑完文件之后、会话开始之前、工具调用之前等时间点挂脚本；官方的洞察是，hook 真正的价值不是阻止 Claude 做错事，而是让整套设置自我进化。[原文§Q2：CLAUDE.md 到底写多长合适？写了 1000 行 Claude 反而变笨？](https://xiaolinnote.com/claudecode/playbook/cc_large_codebase.html#q2-claude-md-%E5%88%B0%E5%BA%95%E5%86%99%E5%A4%9A%E9%95%BF%E5%90%88%E9%80%82-%E5%86%99%E4%BA%86-1000-%E8%A1%8C-claude-%E5%8F%8D%E8%80%8C%E5%8F%98%E7%AC%A8)
- **G2-30** LSP 全称 Language Server Protocol；平时在 VS Code 里点 go to definition、find references，背后跑的就是它。[原文§Q3：大代码库里让 Claude 找一个函数，总找错文件，怎么办？](https://xiaolinnote.com/claudecode/playbook/cc_large_codebase.html#q3-%E5%A4%A7%E4%BB%A3%E7%A0%81%E5%BA%93%E9%87%8C%E8%AE%A9-claude-%E6%89%BE%E4%B8%80%E4%B8%AA%E5%87%BD%E6%95%B0-%E6%80%BB%E6%89%BE%E9%94%99%E6%96%87%E4%BB%B6-%E6%80%8E%E4%B9%88%E5%8A%9E)
- **G2-31** 他的说法是 Pour your effort into the plan so Claude can one-shot the implementation：与其用一个超长 prompt 让 Claude 一次搞定所有事，不如先单独花一轮把方案敲定，再分多个会话去实现。[原文§Q4：跨几十个文件的改动，Claude 总是改一半就崩，怎么救？](https://xiaolinnote.com/claudecode/playbook/cc_large_codebase.html#q4-%E8%B7%A8%E5%87%A0%E5%8D%81%E4%B8%AA%E6%96%87%E4%BB%B6%E7%9A%84%E6%94%B9%E5%8A%A8-claude-%E6%80%BB%E6%98%AF%E6%94%B9%E4%B8%80%E5%8D%8A%E5%B0%B1%E5%B4%A9-%E6%80%8E%E4%B9%88%E6%95%91)
- **G2-32** 高级工程师本机配了几十个 skill、hook 和 MCP server，旁边的实习生什么都没配，体验像用 demo 版；官方案例里，一家零售公司把少数人本地的数据分析 skill 打包成 plugin 全公司铺开，业务分析效率整体提高了一个档次。[原文§第二步：用 plugin 把好实践打包分发](https://xiaolinnote.com/claudecode/playbook/cc_large_codebase.html#%E7%AC%AC%E4%BA%8C%E6%AD%A5-%E7%94%A8-plugin-%E6%8A%8A%E5%A5%BD%E5%AE%9E%E8%B7%B5%E6%89%93%E5%8C%85%E5%88%86%E5%8F%91)
- **G2-33** 连接的桥梁叫 MCP server：装一个 Slack MCP，Claude 就能搜公司的 Slack 消息；装一个 BigQuery MCP，就能跑数据查询；装一个 Sentry MCP，就能拉线上错误日志。[原文§第三步：用 MCP 把团队内部系统接进来](https://xiaolinnote.com/claudecode/playbook/cc_large_codebase.html#%E7%AC%AC%E4%B8%89%E6%AD%A5-%E7%94%A8-mcp-%E6%8A%8A%E5%9B%A2%E9%98%9F%E5%86%85%E9%83%A8%E7%B3%BB%E7%BB%9F%E6%8E%A5%E8%BF%9B%E6%9D%A5)
- **G2-34** 没有人盯着这件事，再好的 plugin 也会变成某人两年前搭的、没人会改的部落知识。[原文§第四步：得有人负责维护](https://xiaolinnote.com/claudecode/playbook/cc_large_codebase.html#%E7%AC%AC%E5%9B%9B%E6%AD%A5-%E5%BE%97%E6%9C%89%E4%BA%BA%E8%B4%9F%E8%B4%A3%E7%BB%B4%E6%8A%A4)

## 3. Skill 的工程化使用

原文：[Claude Code Skill 揭秘：Skill 真的只是一份 markdown 吗？](https://xiaolinnote.com/claudecode/playbook/cc_skills.html)。

### 组成与九类用途

- **G3-1** 官方的定义是 skill 是一个文件夹：除了 SKILL.md，还可以放脚本、参考资料、数据文件和输出模板，Claude 能自己发现、探索和使用这些东西；只写一份 markdown 相当于只用了这个机制十分之一的能力。[原文§Q1：「skill 不就是一份 markdown 吗？」这可能是最大的误解](https://xiaolinnote.com/claudecode/playbook/cc_skills.html#q1-%E3%80%8Cskill-%E4%B8%8D%E5%B0%B1%E6%98%AF%E4%B8%80%E4%BB%BD-markdown-%E5%90%97-%E3%80%8D%E8%BF%99%E5%8F%AF%E8%83%BD%E6%98%AF%E6%9C%80%E5%A4%A7%E7%9A%84%E8%AF%AF%E8%A7%A3)
- **G3-2** SKILL.md 是唯一必需的文件，开头的 frontmatter 写名字和 description，正文写操作指引和坑点；references 放正文放不下的细节，scripts 放现成的可执行脚本，assets 等资源文件按需添加，目录名都不是强制的。[原文§Q1：「skill 不就是一份 markdown 吗？」这可能是最大的误解](https://xiaolinnote.com/claudecode/playbook/cc_skills.html#q1-%E3%80%8Cskill-%E4%B8%8D%E5%B0%B1%E6%98%AF%E4%B8%80%E4%BB%BD-markdown-%E5%90%97-%E3%80%8D%E8%BF%99%E5%8F%AF%E8%83%BD%E6%98%AF%E6%9C%80%E5%A4%A7%E7%9A%84%E8%AF%AF%E8%A7%A3)
- **G3-3** 原文表格的说法是教 Claude 正确使用某个内部库或 CLI，例子是内部计费库的边界情况和坑。[原文§Q2：Anthropic 内部几百个 skill，最后只归成了 9 类](https://xiaolinnote.com/claudecode/playbook/cc_skills.html#q2-anthropic-%E5%86%85%E9%83%A8%E5%87%A0%E7%99%BE%E4%B8%AA-skill-%E6%9C%80%E5%90%8E%E5%8F%AA%E5%BD%92%E6%88%90%E4%BA%86-9-%E7%B1%BB)
- **G3-4** 验证类 skill 教 Claude 测试自己写的代码，例如用无头浏览器把注册、邮箱验证、引导页一步步跑完，每一步都断言状态，甚至录一段视频展示它到底测了什么。[原文§Q2：Anthropic 内部几百个 skill，最后只归成了 9 类](https://xiaolinnote.com/claudecode/playbook/cc_skills.html#q2-anthropic-%E5%86%85%E9%83%A8%E5%87%A0%E7%99%BE%E4%B8%AA-skill-%E6%9C%80%E5%90%8E%E5%8F%AA%E5%BD%92%E6%88%90%E4%BA%86-9-%E7%B1%BB)
- **G3-5** 这类 skill 连接数据和监控系统，例子是告诉 Claude 该 join 哪些表才能看到转化漏斗。[原文§Q2：Anthropic 内部几百个 skill，最后只归成了 9 类](https://xiaolinnote.com/claudecode/playbook/cc_skills.html#q2-anthropic-%E5%86%85%E9%83%A8%E5%87%A0%E7%99%BE%E4%B8%AA-skill-%E6%9C%80%E5%90%8E%E5%8F%AA%E5%BD%92%E6%88%90%E4%BA%86-9-%E7%B1%BB)
- **G3-6** 这类 skill 把重复的工作流压成一条命令，例子是自动聚合工单和 PR，生成站会日报。[原文§Q2：Anthropic 内部几百个 skill，最后只归成了 9 类](https://xiaolinnote.com/claudecode/playbook/cc_skills.html#q2-anthropic-%E5%86%85%E9%83%A8%E5%87%A0%E7%99%BE%E4%B8%AA-skill-%E6%9C%80%E5%90%8E%E5%8F%AA%E5%BD%92%E6%88%90%E4%BA%86-9-%E7%B1%BB)
- **G3-7** 原文表格只说这类 skill 按团队规范生成样板代码，例子是新建一个预接好鉴权和日志的内部应用。[原文§Q2：Anthropic 内部几百个 skill，最后只归成了 9 类](https://xiaolinnote.com/claudecode/playbook/cc_skills.html#q2-anthropic-%E5%86%85%E9%83%A8%E5%87%A0%E7%99%BE%E4%B8%AA-skill-%E6%9C%80%E5%90%8E%E5%8F%AA%E5%BD%92%E6%88%90%E4%BA%86-9-%E7%B1%BB)
- **G3-8** 原文表格的例子是派一个全新视角的子 agent 做对抗式审查，用来在组织内强制执行代码质量。[原文§Q2：Anthropic 内部几百个 skill，最后只归成了 9 类](https://xiaolinnote.com/claudecode/playbook/cc_skills.html#q2-anthropic-%E5%86%85%E9%83%A8%E5%87%A0%E7%99%BE%E4%B8%AA-skill-%E6%9C%80%E5%90%8E%E5%8F%AA%E5%BD%92%E6%88%90%E4%BA%86-9-%E7%B1%BB)
- **G3-9** 这类 skill 负责拉取、推送和部署代码，例子是盯着 PR 重试不稳定的 CI、解决冲突。[原文§Q2：Anthropic 内部几百个 skill，最后只归成了 9 类](https://xiaolinnote.com/claudecode/playbook/cc_skills.html#q2-anthropic-%E5%86%85%E9%83%A8%E5%87%A0%E7%99%BE%E4%B8%AA-skill-%E6%9C%80%E5%90%8E%E5%8F%AA%E5%BD%92%E6%88%90%E4%BA%86-9-%E7%B1%BB)
- **G3-10** 原文表格的说法是从一个报警症状出发做多工具排查，例子是给一个请求 ID，把所有系统的相关日志拉齐。[原文§Q2：Anthropic 内部几百个 skill，最后只归成了 9 类](https://xiaolinnote.com/claudecode/playbook/cc_skills.html#q2-anthropic-%E5%86%85%E9%83%A8%E5%87%A0%E7%99%BE%E4%B8%AA-skill-%E6%9C%80%E5%90%8E%E5%8F%AA%E5%BD%92%E6%88%90%E4%BA%86-9-%E7%B1%BB)
- **G3-11** 原文表格的说法是带护栏的例行维护操作，例子是清理孤儿资源前先发 Slack 等人工确认。[原文§Q2：Anthropic 内部几百个 skill，最后只归成了 9 类](https://xiaolinnote.com/claudecode/playbook/cc_skills.html#q2-anthropic-%E5%86%85%E9%83%A8%E5%87%A0%E7%99%BE%E4%B8%AA-skill-%E6%9C%80%E5%90%8E%E5%8F%AA%E5%BD%92%E6%88%90%E4%BA%86-9-%E7%B1%BB)
- **G3-12** 官方的判断标准是最好的 skill 干干净净落在某一类里；想一次干太多事、横跨好几类的 skill 反而会把 agent 搞糊涂，对着九类扫一遍就能看出哪些越界了该拆。[原文§Q2：Anthropic 内部几百个 skill，最后只归成了 9 类](https://xiaolinnote.com/claudecode/playbook/cc_skills.html#q2-anthropic-%E5%86%85%E9%83%A8%E5%87%A0%E7%99%BE%E4%B8%AA-skill-%E6%9C%80%E5%90%8E%E5%8F%AA%E5%BD%92%E6%88%90%E4%BA%86-9-%E7%B1%BB)
- **G3-13** 原文称 Claude 写代码的能力已经够强，真正拉开差距的是它有没有办法确认自己写的东西是对的，没有验证手段它只能说应该没问题；官方实测验证类 skill 对输出质量的提升最明显。[原文§Q2：Anthropic 内部几百个 skill，最后只归成了 9 类](https://xiaolinnote.com/claudecode/playbook/cc_skills.html#q2-anthropic-%E5%86%85%E9%83%A8%E5%87%A0%E7%99%BE%E4%B8%AA-skill-%E6%9C%80%E5%90%8E%E5%8F%AA%E5%BD%92%E6%88%90%E4%BA%86-9-%E7%B1%BB)

### 触发、正文与高级能力

- **G3-14** 会话启动时只把每个 skill 的名字和 description 拼成清单注入上下文；任务匹配并调用时才加载 SKILL.md 全文；正文提到的参考文件等 Claude 真需要时才去读。一共三层，每层只在必要时打开。[原文§Q3：为什么你写的 skill Claude 从来不触发？](https://xiaolinnote.com/claudecode/playbook/cc_skills.html#q3-%E4%B8%BA%E4%BB%80%E4%B9%88%E4%BD%A0%E5%86%99%E7%9A%84-skill-claude-%E4%BB%8E%E6%9D%A5%E4%B8%8D%E8%A7%A6%E5%8F%91)
- **G3-15** 因为 Claude 决定用不用一个 skill，唯一的依据就是那一行 description，它没读过正文；所以 description 不是写给人看的摘要，而是写给模型看的触发条件。[原文§Q3：为什么你写的 skill Claude 从来不触发？](https://xiaolinnote.com/claudecode/playbook/cc_skills.html#q3-%E4%B8%BA%E4%BB%80%E4%B9%88%E4%BD%A0%E5%86%99%E7%9A%84-skill-claude-%E4%BB%8E%E6%9D%A5%E4%B8%8D%E8%A7%A6%E5%8F%91)
- **G3-16** 把人类视角的摘要改成模型视角的触发条件，例如把帮助处理数据库相关工作改成当用户要写数据库迁移、修改表结构或者遇到 migration 报错时使用。[原文§Q3：为什么你写的 skill Claude 从来不触发？](https://xiaolinnote.com/claudecode/playbook/cc_skills.html#q3-%E4%B8%BA%E4%BB%80%E4%B9%88%E4%BD%A0%E5%86%99%E7%9A%84-skill-claude-%E4%BB%8E%E6%9D%A5%E4%B8%8D%E8%A7%A6%E5%8F%91)
- **G3-17** 原文在源码里看到单个 skill 在清单中的描述最多 250 个字符，超出的部分直接被砍掉换成省略号，写在后面的触发条件模型根本看不到。[原文§Q3：为什么你写的 skill Claude 从来不触发？](https://xiaolinnote.com/claudecode/playbook/cc_skills.html#q3-%E4%B8%BA%E4%BB%80%E4%B9%88%E4%BD%A0%E5%86%99%E7%9A%84-skill-claude-%E4%BB%8E%E6%9D%A5%E4%B8%8D%E8%A7%A6%E5%8F%91)
- **G3-18** 整张 skill 清单只允许占上下文窗口的 1%；装得太多把预算挤爆后，会先按比例压缩所有 description，还装不下就降级成只显示名字，于是每个 skill 都更难被触发。[原文§Q3：为什么你写的 skill Claude 从来不触发？](https://xiaolinnote.com/claudecode/playbook/cc_skills.html#q3-%E4%B8%BA%E4%BB%80%E4%B9%88%E4%BD%A0%E5%86%99%E7%9A%84-skill-claude-%E4%BB%8E%E6%9D%A5%E4%B8%8D%E8%A7%A6%E5%8F%91)
- **G3-19** 加载全文时会在正文最前面加一句说明这个 skill 的根目录在哪里；references、scripts 里的东西系统不会自动加载，是 Claude 拿到根目录地址后，按 SKILL.md 的指引自己用读文件的工具去取的。[原文§Q3：为什么你写的 skill Claude 从来不触发？](https://xiaolinnote.com/claudecode/playbook/cc_skills.html#q3-%E4%B8%BA%E4%BB%80%E4%B9%88%E4%BD%A0%E5%86%99%E7%9A%84-skill-claude-%E4%BB%8E%E6%9D%A5%E4%B8%8D%E8%A7%A6%E5%8F%91)
- **G3-20** 写完代码要跑测试这类通用常识 Claude 本来就会，写进去只是往上下文里灌噪音；坑点是 Claude 靠读代码永远推断不出、只有踩过坑的人才知道的信息，是整个 skill 里信号最强的内容。[原文§Q4：一个 skill 里含金量最高的部分，是「坑点清单」](https://xiaolinnote.com/claudecode/playbook/cc_skills.html#q4-%E4%B8%80%E4%B8%AA-skill-%E9%87%8C%E5%90%AB%E9%87%91%E9%87%8F%E6%9C%80%E9%AB%98%E7%9A%84%E9%83%A8%E5%88%86-%E6%98%AF%E3%80%8C%E5%9D%91%E7%82%B9%E6%B8%85%E5%8D%95%E3%80%8D)
- **G3-21** 原文的例子是在坑点清单里直接写明：这个字段在 API 网关里叫 @request_id，在计费服务里叫 trace_id，它们是同一个值。[原文§Q4：一个 skill 里含金量最高的部分，是「坑点清单」](https://xiaolinnote.com/claudecode/playbook/cc_skills.html#q4-%E4%B8%80%E4%B8%AA-skill-%E9%87%8C%E5%90%AB%E9%87%91%E9%87%8F%E6%9C%80%E9%AB%98%E7%9A%84%E9%83%A8%E5%88%86-%E6%98%AF%E3%80%8C%E5%9D%91%E7%82%B9%E6%B8%85%E5%8D%95%E3%80%8D)
- **G3-22** Claude 对指令的服从度很高，步骤写得太死时，遇到指令没覆盖的情况它容易僵在轨道上硬走，该随机应变的地方也不敢变；应把它需要的信息给足，把怎么走的自由留给它。[原文§Q4：一个 skill 里含金量最高的部分，是「坑点清单」](https://xiaolinnote.com/claudecode/playbook/cc_skills.html#q4-%E4%B8%80%E4%B8%AA-skill-%E9%87%8C%E5%90%AB%E9%87%91%E9%87%8F%E6%9C%80%E9%AB%98%E7%9A%84%E9%83%A8%E5%88%86-%E6%98%AF%E3%80%8C%E5%9D%91%E7%82%B9%E6%B8%85%E5%8D%95%E3%80%8D)
- **G3-23** 让日报 skill 在自己的文件夹里维护一个日志文件，每发一次日报就追加一条记录；下次执行时 Claude 先读自己的历史，就知道只汇报上次之后的增量。[原文§玩法一：给 skill 装记忆](https://xiaolinnote.com/claudecode/playbook/cc_skills.html#%E7%8E%A9%E6%B3%95%E4%B8%80-%E7%BB%99-skill-%E8%A3%85%E8%AE%B0%E5%BF%86)
- **G3-24** 原文称官方为此准备了一个稳定的数据目录，在 skill 里通过环境变量 CLAUDE_PLUGIN_DATA 取得；它的特点是持久，plugin 升级换版本都不会被清掉，只有彻底卸载时才会删除。[原文§玩法一：给 skill 装记忆](https://xiaolinnote.com/claudecode/playbook/cc_skills.html#%E7%8E%A9%E6%B3%95%E4%B8%80-%E7%BB%99-skill-%E8%A3%85%E8%AE%B0%E5%BF%86)
- **G3-25** 把配置存进 skill 目录下的 config.json：每次执行先看配置在不在，在就直接用；不在说明是第一次运行，主动向用户把信息问齐并写进配置，下次就不用再问，还可以用选择题的形式来收集。[原文§玩法一：给 skill 装记忆](https://xiaolinnote.com/claudecode/playbook/cc_skills.html#%E7%8E%A9%E6%B3%95%E4%B8%80-%E7%BB%99-skill-%E8%A3%85%E8%AE%B0%E5%BF%86)
- **G3-26** skill 里预先放好函数库，把取数、清洗、对比这些底层工作封装成现成的函数后，Claude 不必每次现场手写整套样板代码，每个回合只需思考该组合哪几个函数，再写一段十几行的小脚本得出答案。[原文§玩法二：把脚本喂给 Claude，让它只管编排](https://xiaolinnote.com/claudecode/playbook/cc_skills.html#%E7%8E%A9%E6%B3%95%E4%BA%8C-%E6%8A%8A%E8%84%9A%E6%9C%AC%E5%96%82%E7%BB%99-claude-%E8%AE%A9%E5%AE%83%E5%8F%AA%E7%AE%A1%E7%BC%96%E6%8E%92)
- **G3-27** 原文的划分是：连数据源、拼查询、算留存这类底层重复工作适合封装成现成的函数；该组合哪些函数、怎样回答当前问题则留给 Claude 现场编排。[原文§玩法二：把脚本喂给 Claude，让它只管编排](https://xiaolinnote.com/claudecode/playbook/cc_skills.html#%E7%8E%A9%E6%B3%95%E4%BA%8C-%E6%8A%8A%E8%84%9A%E6%9C%AC%E5%96%82%E7%BB%99-claude-%E8%AE%A9%E5%AE%83%E5%8F%AA%E7%AE%A1%E7%BC%96%E6%8E%92)
- **G3-28** skill 自带的 hook 只在 skill 被调用时注册，会话结束就失效，直接在 skill 的 frontmatter 里声明，不需要去碰全局的 hook 配置；像阻断危险命令这种拦截若常驻开着会严重影响开发体验，只在需要时激活才合适。[原文§玩法三：挂只在 skill 激活期间生效的 hook](https://xiaolinnote.com/claudecode/playbook/cc_skills.html#%E7%8E%A9%E6%B3%95%E4%B8%89-%E6%8C%82%E5%8F%AA%E5%9C%A8-skill-%E6%BF%80%E6%B4%BB%E6%9C%9F%E9%97%B4%E7%94%9F%E6%95%88%E7%9A%84-hook)
- **G3-29** 原文举的 freeze skill 激活后禁止修改指定目录之外的任何文件，专门防止排查 bug 时只想加两行日志、Claude 却顺手把无关代码也改了。[原文§玩法三：挂只在 skill 激活期间生效的 hook](https://xiaolinnote.com/claudecode/playbook/cc_skills.html#%E7%8E%A9%E6%B3%95%E4%B8%89-%E6%8C%82%E5%8F%AA%E5%9C%A8-skill-%E6%BF%80%E6%B4%BB%E6%9C%9F%E9%97%B4%E7%94%9F%E6%95%88%E7%9A%84-hook)

### 分发与评估

- **G3-30** 把 skill 提交进仓库的 .claude/skills 目录，拉代码就同步，适合小团队、仓库不多的场景，但每个人每次会话都要承担这份清单开销；规模上来后做成 plugin 放进团队内部的 marketplace，谁需要谁安装。[原文§Q6：skill 怎么从你的本地走向全团队？](https://xiaolinnote.com/claudecode/playbook/cc_skills.html#q6-skill-%E6%80%8E%E4%B9%88%E4%BB%8E%E4%BD%A0%E7%9A%84%E6%9C%AC%E5%9C%B0%E8%B5%B0%E5%90%91%E5%85%A8%E5%9B%A2%E9%98%9F)
- **G3-31** Anthropic 内部没有中心化的审批团队：作者先把 skill 扔进 GitHub 上的沙盒文件夹，并在 Slack 里告知大家；用的人多了、口碑起来了，作者再提 PR 把它挪进正式的 marketplace。[原文§Q6：skill 怎么从你的本地走向全团队？](https://xiaolinnote.com/claudecode/playbook/cc_skills.html#q6-skill-%E6%80%8E%E4%B9%88%E4%BB%8E%E4%BD%A0%E7%9A%84%E6%9C%AC%E5%9C%B0%E8%B5%B0%E5%90%91%E5%85%A8%E5%9B%A2%E9%98%9F)
- **G3-32** 依赖管理目前没有原生支持；做法是在 skill 正文里直接写出另一个 skill 的名字，只要对方装了，模型自己会去调用。[原文§Q6：skill 怎么从你的本地走向全团队？](https://xiaolinnote.com/claudecode/playbook/cc_skills.html#q6-skill-%E6%80%8E%E4%B9%88%E4%BB%8E%E4%BD%A0%E7%9A%84%E6%9C%AC%E5%9C%B0%E8%B5%B0%E5%90%91%E5%85%A8%E5%9B%A2%E9%98%9F)
- **G3-33** 用一个 PreToolUse hook 监听 skill 工具的每一次调用，把谁在什么时候用了哪个 skill 记录下来，汇总成公司内部的使用统计。[原文§Q7：怎么知道一个 skill 到底有没有人用？](https://xiaolinnote.com/claudecode/playbook/cc_skills.html#q7-%E6%80%8E%E4%B9%88%E7%9F%A5%E9%81%93%E4%B8%80%E4%B8%AA-skill-%E5%88%B0%E5%BA%95%E6%9C%89%E6%B2%A1%E6%9C%89%E4%BA%BA%E7%94%A8)
- **G3-34** 一类是受欢迎的 skill，调用量大，值得重点维护、优先打磨；另一类是触发不足，预期该被高频使用，数据却显示几乎没人碰。[原文§Q7：怎么知道一个 skill 到底有没有人用？](https://xiaolinnote.com/claudecode/playbook/cc_skills.html#q7-%E6%80%8E%E4%B9%88%E7%9F%A5%E9%81%93%E4%B8%80%E4%B8%AA-skill-%E5%88%B0%E5%BA%95%E6%9C%89%E6%B2%A1%E6%9C%89%E4%BA%BA%E7%94%A8)
- **G3-35** undertriggering 即触发不足：预期该被高频使用的 skill，数据却显示几乎没人碰，多半是 description 没写对，模型扫一眼清单想不起它；用数据把该触发却没触发的 skill 筛出来，再回头修 description，形成闭环。[原文§Q7：怎么知道一个 skill 到底有没有人用？](https://xiaolinnote.com/claudecode/playbook/cc_skills.html#q7-%E6%80%8E%E4%B9%88%E7%9F%A5%E9%81%93%E4%B8%80%E4%B8%AA-skill-%E5%88%B0%E5%BA%95%E6%9C%89%E6%B2%A1%E6%9C%89%E4%BA%BA%E7%94%A8)
- **G3-36** 坑点清单要持续积累：每次 Claude 用这个 skill 又栽进一个新坑，就回头把它补进去。[原文§Q4：一个 skill 里含金量最高的部分，是「坑点清单」](https://xiaolinnote.com/claudecode/playbook/cc_skills.html#q4-%E4%B8%80%E4%B8%AA-skill-%E9%87%8C%E5%90%AB%E9%87%91%E9%87%8F%E6%9C%80%E9%AB%98%E7%9A%84%E9%83%A8%E5%88%86-%E6%98%AF%E3%80%8C%E5%9D%91%E7%82%B9%E6%B8%85%E5%8D%95%E3%80%8D)

### 补充考点

- **G3-37** 它整篇没教 Claude 怎么写 CSS，因为模型本来就会；而是专门列了一堆不要做的事，例如不要张口就用 Inter 字体、不要动不动用紫色渐变，全是冲着 Claude 的默认审美去纠偏的。[原文§Q4：一个 skill 里含金量最高的部分，是「坑点清单」](https://xiaolinnote.com/claudecode/playbook/cc_skills.html#q4-%E4%B8%80%E4%B8%AA-skill-%E9%87%8C%E5%90%AB%E9%87%91%E9%87%8F%E6%9C%80%E9%AB%98%E7%9A%84%E9%83%A8%E5%88%86-%E6%98%AF%E3%80%8C%E5%9D%91%E7%82%B9%E6%B8%85%E5%8D%95%E3%80%8D)
- **G3-38** 原文把它比作开源社区：好东西靠口碑自己长出来，而不是靠委员会评出来；审批环节越重，愿意分享的人越少，门槛低到扔进沙盒就行，几百个 skill 才攒得起来。[原文§Q6：skill 怎么从你的本地走向全团队？](https://xiaolinnote.com/claudecode/playbook/cc_skills.html#q6-skill-%E6%80%8E%E4%B9%88%E4%BB%8E%E4%BD%A0%E7%9A%84%E6%9C%AC%E5%9C%B0%E8%B5%B0%E5%90%91%E5%85%A8%E5%9B%A2%E9%98%9F)

## 4. SDD 规约驱动开发

原文：[SDD 规约驱动开发实战：在 Claude Code 里跑通先规约后编码](https://xiaolinnote.com/claudecode/playbook/spec_driven_dev.html)。

- **G4-1** 聊天式开发想到哪说到哪，双方脑子里都没有一张完整的图；AI 每次只看到当前这句话和眼前的上下文，做到后面可能已经忘了前面为什么那样设计，一不留神就把前面的东西推翻。根子是缺一份双方都认可的对齐。[原文§为什么你跟 AI 越聊越乱？](https://xiaolinnote.com/claudecode/playbook/spec_driven_dev.html#%E4%B8%BA%E4%BB%80%E4%B9%88%E4%BD%A0%E8%B7%9F-ai-%E8%B6%8A%E8%81%8A%E8%B6%8A%E4%B9%B1)
- **G4-2** 把要做成什么样写下来摆到明面上，并把一件事拆成几个台阶，在每个台阶上都停下来对一次；每一步的产物都能亲眼看到、能改、能拦，把对齐从模糊的默契变成白纸黑字的逐步确认。[原文§规约驱动，到底把什么摆到了明面上？](https://xiaolinnote.com/claudecode/playbook/spec_driven_dev.html#%E8%A7%84%E7%BA%A6%E9%A9%B1%E5%8A%A8-%E5%88%B0%E5%BA%95%E6%8A%8A%E4%BB%80%E4%B9%88%E6%91%86%E5%88%B0%E4%BA%86%E6%98%8E%E9%9D%A2%E4%B8%8A)
- **G4-3** 第一步只讲清楚要做什么、为什么做，不谈技术；第二步再定用什么技术和架构实现。分开之后，AI 把需求理解错在第一步就能看出来并纠正，技术方案不认同可以在第二步拦下。[原文§规约驱动，到底把什么摆到了明面上？](https://xiaolinnote.com/claudecode/playbook/spec_driven_dev.html#%E8%A7%84%E7%BA%A6%E9%A9%B1%E5%8A%A8-%E5%88%B0%E5%BA%95%E6%8A%8A%E4%BB%80%E4%B9%88%E6%91%86%E5%88%B0%E4%BA%86%E6%98%8E%E9%9D%A2%E4%B8%8A)
- **G4-4** constitution 用来先定几条这个项目从头到尾都要遵守的铁律，例如所有接口都要写测试、代码风格统一用某个规范；之后每一步 AI 都会拿这几条来对照。[原文§spec-kit 一套命令跑下来是什么体验？](https://xiaolinnote.com/claudecode/playbook/spec_driven_dev.html#spec-kit-%E4%B8%80%E5%A5%97%E5%91%BD%E4%BB%A4%E8%B7%91%E4%B8%8B%E6%9D%A5%E6%98%AF%E4%BB%80%E4%B9%88%E4%BD%93%E9%AA%8C)
- **G4-5** specify 阶段生成一份需求规约文档，把功能点、用户角色，以及每个功能算做完了的标准一条条列清楚；这一步只谈需求、不提技术。[原文§specify：先说清楚要做什么](https://xiaolinnote.com/claudecode/playbook/spec_driven_dev.html#specify-%E5%85%88%E8%AF%B4%E6%B8%85%E6%A5%9A%E8%A6%81%E5%81%9A%E4%BB%80%E4%B9%88)
- **G4-6** plan 阶段由用户给出技术栈和架构选型，Claude Code 基于前面的需求文档产出技术方案，包括大概分几个模块、接口怎么设计、数据表长什么样。[原文§plan：再定技术方案](https://xiaolinnote.com/claudecode/playbook/spec_driven_dev.html#plan-%E5%86%8D%E5%AE%9A%E6%8A%80%E6%9C%AF%E6%96%B9%E6%A1%88)
- **G4-7** tasks 会把技术方案拆成一条条具体的任务，例如搭项目骨架、建数据表、写接口、做前端组件。[原文§tasks：把方案拆成任务](https://xiaolinnote.com/claudecode/playbook/spec_driven_dev.html#tasks-%E6%8A%8A%E6%96%B9%E6%A1%88%E6%8B%86%E6%88%90%E4%BB%BB%E5%8A%A1)
- **G4-8** 它拿着任务清单一条条往下实现；因为该定的全都定了，这一趟它基本是个老老实实的执行者，不太会再冒出我觉得这样更好的想法而把设计改掉。[原文§implement：放手让它写代码](https://xiaolinnote.com/claudecode/playbook/spec_driven_dev.html#implement-%E6%94%BE%E6%89%8B%E8%AE%A9%E5%AE%83%E5%86%99%E4%BB%A3%E7%A0%81)
- **G4-9** 初始化时会弹出选择，让你挑用哪种脚本；Mac 上直接选 sh，即 POSIX shell。[原文§装工具、进项目](https://xiaolinnote.com/claudecode/playbook/spec_driven_dev.html#%E8%A3%85%E5%B7%A5%E5%85%B7%E3%80%81%E8%BF%9B%E9%A1%B9%E7%9B%AE)
- **G4-10** spec-kit 的斜杠命令底下是一组 skill，装在项目的 .claude/skills/ 目录下；skill 是 Claude Code 启动时才扫描加载的，所以必须先进到项目目录再启动 Claude Code，它才认得这些命令。[原文§装工具、进项目](https://xiaolinnote.com/claudecode/playbook/spec_driven_dev.html#%E8%A3%85%E5%B7%A5%E5%85%B7%E3%80%81%E8%BF%9B%E9%A1%B9%E7%9B%AE)
- **G4-11** 要看它有没有理解错；原文称这是整个流程里性价比最高的一次检查。[原文§specify：先说清楚要做什么](https://xiaolinnote.com/claudecode/playbook/spec_driven_dev.html#specify-%E5%85%88%E8%AF%B4%E6%B8%85%E6%A5%9A%E8%A6%81%E5%81%9A%E4%BB%80%E4%B9%88)
- **G4-12** 原文称一口气全塞给它，上下文太长，它反而容易顾此失彼；更稳的做法是分阶段：先让项目骨架和基本增删跑通并验证，再做看板拖拽，最后才加分配负责人。[原文§implement：放手让它写代码](https://xiaolinnote.com/claudecode/playbook/spec_driven_dev.html#implement-%E6%94%BE%E6%89%8B%E8%AE%A9%E5%AE%83%E5%86%99%E4%BB%A3%E7%A0%81)
- **G4-13** 最好在 specify 产出需求文档之后、开始 plan 之前运行；先把模糊点问清楚再定技术方案，否则需求是糊的，方案也跟着糊，等 plan、tasks 都做完再回头补就晚了。[原文§需求含糊、项目又大，靠什么兜底？](https://xiaolinnote.com/claudecode/playbook/spec_driven_dev.html#%E9%9C%80%E6%B1%82%E5%90%AB%E7%B3%8A%E3%80%81%E9%A1%B9%E7%9B%AE%E5%8F%88%E5%A4%A7-%E9%9D%A0%E4%BB%80%E4%B9%88%E5%85%9C%E5%BA%95)
- **G4-14** 它不急着往下走，而是盯着需求文档，把含糊、有歧义、没交代清楚的地方逐个提出来问；最好在 specify 出了需求文档、还没开始 plan 之前运行，否则需求是糊的，方案也跟着一起糊。[原文§需求含糊、项目又大，靠什么兜底？](https://xiaolinnote.com/claudecode/playbook/spec_driven_dev.html#%E9%9C%80%E6%B1%82%E5%90%AB%E7%B3%8A%E3%80%81%E9%A1%B9%E7%9B%AE%E5%8F%88%E5%A4%A7-%E9%9D%A0%E4%BB%80%E4%B9%88%E5%85%9C%E5%BA%95)
- **G4-15** analyze 一般在拆完任务、正式写代码之前用，把需求、方案和任务清单放在一起交叉比对，找出互相矛盾或遗漏的地方，例如需求要求实时更新而方案里没提，或者任务清单漏了需求里写明的功能。[原文§需求含糊、项目又大，靠什么兜底？](https://xiaolinnote.com/claudecode/playbook/spec_driven_dev.html#%E9%9C%80%E6%B1%82%E5%90%AB%E7%B3%8A%E3%80%81%E9%A1%B9%E7%9B%AE%E5%8F%88%E5%A4%A7-%E9%9D%A0%E4%BB%80%E4%B9%88%E5%85%9C%E5%BA%95)
- **G4-16** 传统瀑布流的文档是死的，评审签字后基本定死，中途想改要走变更流程；规约驱动的规约是活的，随时可以回去改，甚至推翻重来，因为这些规约 AI 几秒钟就能重新生成。[原文§这不就是又回到瀑布流了吗？](https://xiaolinnote.com/claudecode/playbook/spec_driven_dev.html#%E8%BF%99%E4%B8%8D%E5%B0%B1%E6%98%AF%E5%8F%88%E5%9B%9E%E5%88%B0%E7%80%91%E5%B8%83%E6%B5%81%E4%BA%86%E5%90%97)
- **G4-17** 几十行、跑一次就扔的小脚本不值得走完整流程，凭感觉写反而最快；判断标准是这东西是否打算长期维护、后面还要不断往上加功能。[原文§这不就是又回到瀑布流了吗？](https://xiaolinnote.com/claudecode/playbook/spec_driven_dev.html#%E8%BF%99%E4%B8%8D%E5%B0%B1%E6%98%AF%E5%8F%88%E5%9B%9E%E5%88%B0%E7%80%91%E5%B8%83%E6%B5%81%E4%BA%86%E5%90%97)

### 补充考点

- **G4-18** Spec-Driven Development 的核心就一句话：先把要做成什么样讲清楚，再让 AI 动手。原文认为换再强的模型，只要还是想一句说一句地喂它，结果也不会好，因为给它的东西本身就是碎的。[原文§SDD 规约驱动开发实战：在 Claude Code 里跑通先规约后编码](https://xiaolinnote.com/claudecode/playbook/spec_driven_dev.html#sdd-%E8%A7%84%E7%BA%A6%E9%A9%B1%E5%8A%A8%E5%BC%80%E5%8F%91%E5%AE%9E%E6%88%98-%E5%9C%A8-claude-code-%E9%87%8C%E8%B7%91%E9%80%9A%E5%85%88%E8%A7%84%E7%BA%A6%E5%90%8E%E7%BC%96%E7%A0%81)
- **G4-19** vibe coding 是聊天式的写法：想到哪说到哪，AI 做一步你看一步，不对就再说一句，凭感觉写；它不用写文档、不用画流程图，做小玩具、写一次性脚本、周末做个小 demo 非常合适。[原文§为什么你跟 AI 越聊越乱？](https://xiaolinnote.com/claudecode/playbook/spec_driven_dev.html#%E4%B8%BA%E4%BB%80%E4%B9%88%E4%BD%A0%E8%B7%9F-ai-%E8%B6%8A%E8%81%8A%E8%B6%8A%E4%B9%B1)
- **G4-20** 根子是没有给过它一张完整的、双方都认可的图，它手里只有一堆随口甩过来的碎片；问题不在模型笨，而在缺一份对齐，也就是你和 AI 之间少了一样两边都点头认可的东西。[原文§为什么你跟 AI 越聊越乱？](https://xiaolinnote.com/claudecode/playbook/spec_driven_dev.html#%E4%B8%BA%E4%BB%80%E4%B9%88%E4%BD%A0%E8%B7%9F-ai-%E8%B6%8A%E8%81%8A%E8%B6%8A%E4%B9%B1)
- **G4-21** 这一步告诉它要做什么、为什么做，只说需求，不提技术：不要急着说用哪个框架、哪个数据库，而是描述要一个什么样的工具、能完成哪些事。[原文§spec-kit 一套命令跑下来是什么体验？](https://xiaolinnote.com/claudecode/playbook/spec_driven_dev.html#spec-kit-%E4%B8%80%E5%A5%97%E5%91%BD%E4%BB%A4%E8%B7%91%E4%B8%8B%E6%9D%A5%E6%98%AF%E4%BB%80%E4%B9%88%E4%BD%93%E9%AA%8C)
- **G4-22** spec-kit 的命令行工具是 GitHub 官方提供的工具。原文用 uv tool install specify-cli --from git+https://github.com/github/spec-kit.git 安装，得到 specify 命令；再用 specify init my-kanban --integration claude 初始化 Claude Code 项目，选择脚本类型后创建项目目录并放入工作流 Skill。 [原文§装工具、进项目](https://xiaolinnote.com/claudecode/playbook/spec_driven_dev.html#%E8%A3%85%E5%B7%A5%E5%85%B7%E3%80%81%E8%BF%9B%E9%A1%B9%E7%9B%AE)
- **G4-23** 不是那几份文档本身，而是它逼着你把先想清楚再写这件事，从一句正确的废话变成了一道绕不过去的工序；含糊点如果现在不问清楚，AI 只能瞎猜着写下去，等验收时才发现不对，返工成本比现在回答几个问题高得多。[原文§需求含糊、项目又大，靠什么兜底？](https://xiaolinnote.com/claudecode/playbook/spec_driven_dev.html#%E9%9C%80%E6%B1%82%E5%90%AB%E7%B3%8A%E3%80%81%E9%A1%B9%E7%9B%AE%E5%8F%88%E5%A4%A7-%E9%9D%A0%E4%BB%80%E4%B9%88%E5%85%9C%E5%BA%95)

## 5. grill-me 需求澄清

原文：[grill-me 使用指南：写代码前，先让 Claude Code 审问你的需求](https://xiaolinnote.com/claudecode/playbook/grill_me.html)。

- **G5-1** 因为它不是在教 Claude 怎么做，而是在改变 Claude 用什么姿态跟你说话：从你提需求、它执行，变成它提问、你拍板，相当于一个翻转人机关系的开关。[原文§一个只有三句话的 skill，凭什么让人上头？](https://xiaolinnote.com/claudecode/playbook/grill_me.html#%E4%B8%80%E4%B8%AA%E5%8F%AA%E6%9C%89%E4%B8%89%E5%8F%A5%E8%AF%9D%E7%9A%84-skill-%E5%87%AD%E4%BB%80%E4%B9%88%E8%AE%A9%E4%BA%BA%E4%B8%8A%E5%A4%B4)
- **G5-2** grill-me 不急着产出东西，目标是先和用户想到一块去，所以一个一个慢慢问，把每个决定交还给用户；Plan Mode 急着给出计划好开工，问得很少，拿不准的地方常由它自己替你定了。[原文§那它跟 Plan Mode 差在哪？](https://xiaolinnote.com/claudecode/playbook/grill_me.html#%E9%82%A3%E5%AE%83%E8%B7%9F-plan-mode-%E5%B7%AE%E5%9C%A8%E5%93%AA)
- **G5-3** 原文引用设计树的概念：做任何东西背后都是一棵由决定组成的树，先做一个大决定，它再岔出好几个小决定，小决定底下又岔出更小的。[原文§为什么非得「一次只问一个」？](https://xiaolinnote.com/claudecode/playbook/grill_me.html#%E4%B8%BA%E4%BB%80%E4%B9%88%E9%9D%9E%E5%BE%97%E3%80%8C%E4%B8%80%E6%AC%A1%E5%8F%AA%E9%97%AE%E4%B8%80%E4%B8%AA%E3%80%8D)
- **G5-4** 上游的决定不定死，下游全是空中楼阁；真正导致大返工的往往是某个没意识到自己在选的岔路，随手挑了一条，走到底发现不对，那个岔口之后的活全白干。[原文§为什么非得「一次只问一个」？](https://xiaolinnote.com/claudecode/playbook/grill_me.html#%E4%B8%BA%E4%BB%80%E4%B9%88%E9%9D%9E%E5%BE%97%E3%80%8C%E4%B8%80%E6%AC%A1%E5%8F%AA%E9%97%AE%E4%B8%80%E4%B8%AA%E3%80%8D)
- **G5-5** 原文称一口气甩出一堆问题只会把人问懵；一次只问一个，问完等用户回话再问下一个，而且每个问题都要附上推荐的答案。[原文§一个只有三句话的 skill，凭什么让人上头？](https://xiaolinnote.com/claudecode/playbook/grill_me.html#%E4%B8%80%E4%B8%AA%E5%8F%AA%E6%9C%89%E4%B8%89%E5%8F%A5%E8%AF%9D%E7%9A%84-skill-%E5%87%AD%E4%BB%80%E4%B9%88%E8%AE%A9%E4%BA%BA%E4%B8%8A%E5%A4%B4)
- **G5-6** 每个问题都附带推荐答案后，用户要做的事很轻松，只需要从它给的选项里挑一个自己想要的。[原文§实操：让它审问我的「自动追热点小助手」](https://xiaolinnote.com/claudecode/playbook/grill_me.html#%E5%AE%9E%E6%93%8D-%E8%AE%A9%E5%AE%83%E5%AE%A1%E9%97%AE%E6%88%91%E7%9A%84%E3%80%8C%E8%87%AA%E5%8A%A8%E8%BF%BD%E7%83%AD%E7%82%B9%E5%B0%8F%E5%8A%A9%E6%89%8B%E3%80%8D)
- **G5-7** 这是 skill 的第三条指令：一个问题如果去翻代码就能自己搞清楚，就不要问用户，自己去翻。[原文§一个只有三句话的 skill，凭什么让人上头？](https://xiaolinnote.com/claudecode/playbook/grill_me.html#%E4%B8%80%E4%B8%AA%E5%8F%AA%E6%9C%89%E4%B8%89%E5%8F%A5%E8%AF%9D%E7%9A%84-skill-%E5%87%AD%E4%BB%80%E4%B9%88%E8%AE%A9%E4%BA%BA%E4%B8%8A%E5%A4%B4)
- **G5-8** 原文示例中 Claude 先去翻了用户已装的 skill 和 MCP 等工具，发现已有能搜平台、能推送、能定时的现成能力，于是把任务重新定义为编排这些能力，而不是自己写爬虫。[原文§实操：让它审问我的「自动追热点小助手」](https://xiaolinnote.com/claudecode/playbook/grill_me.html#%E5%AE%9E%E6%93%8D-%E8%AE%A9%E5%AE%83%E5%AE%A1%E9%97%AE%E6%88%91%E7%9A%84%E3%80%8C%E8%87%AA%E5%8A%A8%E8%BF%BD%E7%83%AD%E7%82%B9%E5%B0%8F%E5%8A%A9%E6%89%8B%E3%80%8D)
- **G5-9** 用户回答内容领域是 AI 编程和大模型动态后，它据此推断这类热点几乎都在英文源首发，X、HackerNews、GitHub 才是主战场，国内平台多是慢半拍的二手翻译；上游先定，下游才有方向。[原文§实操：让它审问我的「自动追热点小助手」](https://xiaolinnote.com/claudecode/playbook/grill_me.html#%E5%AE%9E%E6%93%8D-%E8%AE%A9%E5%AE%83%E5%AE%A1%E9%97%AE%E6%88%91%E7%9A%84%E3%80%8C%E8%87%AA%E5%8A%A8%E8%BF%BD%E7%83%AD%E7%82%B9%E5%B0%8F%E5%8A%A9%E6%89%8B%E3%80%8D)
- **G5-10** 助手每天独立起跑，不记得昨天推过什么；同一个热点如果在榜上挂三天，就可能连推三天。[原文§实操：让它审问我的「自动追热点小助手」](https://xiaolinnote.com/claudecode/playbook/grill_me.html#%E5%AE%9E%E6%93%8D-%E8%AE%A9%E5%AE%83%E5%AE%A1%E9%97%AE%E6%88%91%E7%9A%84%E3%80%8C%E8%87%AA%E5%8A%A8%E8%BF%BD%E7%83%AD%E7%82%B9%E5%B0%8F%E5%8A%A9%E6%89%8B%E3%80%8D)
- **G5-11** 原文的做法是先手动跑出第一版，把选题清单交给用户确认是不是想要的效果，确认之后再做飞书连通性测试和定时任务设置。[原文§实操：让它审问我的「自动追热点小助手」](https://xiaolinnote.com/claudecode/playbook/grill_me.html#%E5%AE%9E%E6%93%8D-%E8%AE%A9%E5%AE%83%E5%AE%A1%E9%97%AE%E6%88%91%E7%9A%84%E3%80%8C%E8%87%AA%E5%8A%A8%E8%BF%BD%E7%83%AD%E7%82%B9%E5%B0%8F%E5%8A%A9%E6%89%8B%E3%80%8D)
- **G5-12** 原文的顺序是先用 grill-me 把脑子里的糊涂账理清，得到一份想明白的方案，再进 Plan Mode 让它照着出计划、动手实现。[原文§那它跟 Plan Mode 差在哪？](https://xiaolinnote.com/claudecode/playbook/grill_me.html#%E9%82%A3%E5%AE%83%E8%B7%9F-plan-mode-%E5%B7%AE%E5%9C%A8%E5%93%AA)
- **G5-13** 那种要花好几个小时、一旦方向定错返工成本就很高的活；写代码之前是最便宜的纠错时机，这时多聊半小时比事后重写一天强得多。[原文§最后](https://xiaolinnote.com/claudecode/playbook/grill_me.html#%E6%9C%80%E5%90%8E)
- **G5-14** 改个错别字、调个颜色、加个一眼能看穿的小功能，这类改动再召唤它一本正经地问一串，纯属折磨。[原文§最后](https://xiaolinnote.com/claudecode/playbook/grill_me.html#%E6%9C%80%E5%90%8E)
- **G5-15** 原文称它审的不一定是代码：产品点子、没想透的选题、课程大纲等任何背后有一棵决策树的东西都可以交给它审，作者用它审选题方向时被问出了好几个原本没考虑到的角度。[原文§最后](https://xiaolinnote.com/claudecode/playbook/grill_me.html#%E6%9C%80%E5%90%8E)

### 补充考点

- **G5-16** 需求本来就模糊，里面藏着几十个自己都没想清楚的细节；AI 不会拦着你问，默认你都想好了，于是把这些空缺全替你猜了默认值，闷头就干，猜对一两个、猜错一大片，返工自然就来了。[原文§grill-me 使用指南：写代码前，先让 Claude Code 审问你的需求](https://xiaolinnote.com/claudecode/playbook/grill_me.html#grill-me-%E4%BD%BF%E7%94%A8%E6%8C%87%E5%8D%97-%E5%86%99%E4%BB%A3%E7%A0%81%E5%89%8D-%E5%85%88%E8%AE%A9-claude-code-%E5%AE%A1%E9%97%AE%E4%BD%A0%E7%9A%84%E9%9C%80%E6%B1%82)
- **G5-17** grill-me 是海外开发者 Matt Pocock 写的，放在他的 mattpocock/skills 仓库里；它的核心只有三小段大白话，没有脚本和配置，却把 Claude 从你说啥我做啥的执行工具，变成了一个揪着你不放的面试官。grill 在英文里就是拷问、盘问的意思。[原文§一个只有三句话的 skill，凭什么让人上头？](https://xiaolinnote.com/claudecode/playbook/grill_me.html#%E4%B8%80%E4%B8%AA%E5%8F%AA%E6%9C%89%E4%B8%89%E5%8F%A5%E8%AF%9D%E7%9A%84-skill-%E5%87%AD%E4%BB%80%E4%B9%88%E8%AE%A9%E4%BA%BA%E4%B8%8A%E5%A4%B4)
- **G5-18** 设计树是几十年前软件界前辈 Fred Brooks 提出的；就像装修要先定整体风格，才轮到墙面颜色和家具，上游的决定不定死，下游全是空中楼阁。所以 grill-me 一次只问一个，先把最上游、最模糊的决定钉死才往下问，顺序乱了，问了也白问。[原文§为什么非得「一次只问一个」？](https://xiaolinnote.com/claudecode/playbook/grill_me.html#%E4%B8%BA%E4%BB%80%E4%B9%88%E9%9D%9E%E5%BE%97%E3%80%8C%E4%B8%80%E6%AC%A1%E5%8F%AA%E9%97%AE%E4%B8%80%E4%B8%AA%E3%80%8D)
- **G5-19** 安装时在列表里勾上 grill-me，之后在 Claude Code 里敲 /grill-me 就能调用；作者拿自动追热点小助手的想法实测，它一轮轮往下问，一共问了十多轮。[原文§实操：让它审问我的「自动追热点小助手」](https://xiaolinnote.com/claudecode/playbook/grill_me.html#%E5%AE%9E%E6%93%8D-%E8%AE%A9%E5%AE%83%E5%AE%A1%E9%97%AE%E6%88%91%E7%9A%84%E3%80%8C%E8%87%AA%E5%8A%A8%E8%BF%BD%E7%83%AD%E7%82%B9%E5%B0%8F%E5%8A%A9%E6%89%8B%E3%80%8D)

## 6. superpowers 与 grill-me 的对比实验

原文：[superpowers vs grill-me：同一个需求实测，差距到底在哪？](https://xiaolinnote.com/claudecode/playbook/superpowers_vs_grillme.html)。

- **G6-1** grill-me 是一个只有三句话的 skill，单点、锋利，只做需求盘问；superpowers 是包含二十多个 skill 的插件，覆盖聊需求、写设计文档、拆任务、派子代理实现、强制测试驱动开发和代码审查的整条流水线，是一整套工作方法论。[原文§这俩压根不是一个物种？](https://xiaolinnote.com/claudecode/playbook/superpowers_vs_grillme.html#%E8%BF%99%E4%BF%A9%E5%8E%8B%E6%A0%B9%E4%B8%8D%E6%98%AF%E4%B8%80%E4%B8%AA%E7%89%A9%E7%A7%8D)
- **G6-2** 把同一句需求原样分别交给 grill-me 和 superpowers，两边各在一个空目录里运行。[原文§先看 grill-me 怎么审](https://xiaolinnote.com/claudecode/playbook/superpowers_vs_grillme.html#%E5%85%88%E7%9C%8B-grill-me-%E6%80%8E%E4%B9%88%E5%AE%A1) [原文§再看 superpowers 怎么审](https://xiaolinnote.com/claudecode/playbook/superpowers_vs_grillme.html#%E5%86%8D%E7%9C%8B-superpowers-%E6%80%8E%E4%B9%88%E5%AE%A1)
- **G6-3** 原文中用户在 grill-me 的美术风格一问上拒绝了推荐并自己选了风格，superpowers 则没有问这一项；作者认为两版游戏的颜值差距根源不在模型能力，而在于一个问了、一个没问。[原文§体验到底差在哪？](https://xiaolinnote.com/claudecode/playbook/superpowers_vs_grillme.html#%E4%BD%93%E9%AA%8C%E5%88%B0%E5%BA%95%E5%B7%AE%E5%9C%A8%E5%93%AA)
- **G6-4** grill-me 的提问是要把每个决定都摆到用户面前，逼用户亲手拍板每一处细节；superpowers 只问凑齐开工所需的最少信息，其余用合理默认值补齐。作者认为两版成品的差距不在模型能力，而在一个问了、一个没问。[原文§体验到底差在哪？](https://xiaolinnote.com/claudecode/playbook/superpowers_vs_grillme.html#%E4%BD%93%E9%AA%8C%E5%88%B0%E5%BA%95%E5%B7%AE%E5%9C%A8%E5%93%AA)
- **G6-5** 原文的例子是美术全部用 Canvas 程序绘制这一决定只出现在技术栈选项的说明文字里，用户没有被单独询问，游戏长什么样就被替他定了，成品观感因此与另一版差了一截。[原文§再看 superpowers 怎么审](https://xiaolinnote.com/claudecode/playbook/superpowers_vs_grillme.html#%E5%86%8D%E7%9C%8B-superpowers-%E6%80%8E%E4%B9%88%E5%AE%A1)
- **G6-6** superpowers 把聊出来的设计决定和任务计划都写成文档留在项目里，并配有 14 个 git 提交；几个月后忘了当初为什么这样设计时翻文档就有答案，新会话读完档案也能直接接手。grill-me 则片纸不留，共识只存在于对话里。[原文§再看 superpowers 怎么审](https://xiaolinnote.com/claudecode/playbook/superpowers_vs_grillme.html#%E5%86%8D%E7%9C%8B-superpowers-%E6%80%8E%E4%B9%88%E5%AE%A1)
- **G6-7** 原文称这些文档记录了当初定了什么、明确不做什么，配合提交记录可以定位哪次改动出了问题；对 AI 同样有用，新会话把档案一读，对项目的理解就到位，改起来不容易跑偏。[原文§再看 superpowers 怎么审](https://xiaolinnote.com/claudecode/playbook/superpowers_vs_grillme.html#%E5%86%8D%E7%9C%8B-superpowers-%E6%80%8E%E4%B9%88%E5%AE%A1)
- **G6-8** 每个任务派一个子代理去实现，完成后再派一个子代理审查，审出问题就派第三个子代理去修。[原文§再看 superpowers 怎么审](https://xiaolinnote.com/claudecode/playbook/superpowers_vs_grillme.html#%E5%86%8D%E7%9C%8B-superpowers-%E6%80%8E%E4%B9%88%E5%AE%A1)

### 补充考点

- **G6-17** 很多人以为两者是同类工具，其实真正和 grill-me 同台的是 superpowers 里负责问需求的那个 skill，叫 brainstorming；它俩做的是同一件事，都是在写代码之前把脑子里的糊涂账逼出来。安装上，grill-me 是社区 skill，用一行 npx 命令；superpowers 进了官方插件市场，也是一行命令。[原文§这俩压根不是一个物种？](https://xiaolinnote.com/claudecode/playbook/superpowers_vs_grillme.html#%E8%BF%99%E4%BF%A9%E5%8E%8B%E6%A0%B9%E4%B8%8D%E6%98%AF%E4%B8%80%E4%B8%AA%E7%89%A9%E7%A7%8D)
- **G6-18** 它先看目录，发现是空项目就从头聊设计；一次一问、每问带推荐答案，前一问的答案框住后一问的选项，共 12 问、用了 16 分钟。问完给出一张设计共识总览，列出定下来的和明确不做的内容；确认后不到十分钟生成一个 51KB 的 index.html，目录里除了这个文件什么都没有。[原文§先看 grill-me 怎么审](https://xiaolinnote.com/claudecode/playbook/superpowers_vs_grillme.html#%E5%85%88%E7%9C%8B-grill-me-%E6%80%8E%E4%B9%88%E5%AE%A1)
- **G6-19** 它推荐霓虹夜跑，并坦白这是扬长避短：没有美术资源、全靠代码画，夜色能隐藏远处细节的缺失；用户坚持选日间卡通后，它没有硬劝，而是表示会在细节上多下功夫补质感，例如给人物和障碍加投影、给天空做渐变加云。[原文§先看 grill-me 怎么审](https://xiaolinnote.com/claudecode/playbook/superpowers_vs_grillme.html#%E5%85%88%E7%9C%8B-grill-me-%E6%80%8E%E4%B9%88%E5%AE%A1)
- **G6-20** 它也是先翻目录再问，但用的是选项卡片，光标挑一个回车就行，还有多选题；只问了 4 个问题：视角、目标设备、要哪些附加功能、技术栈。4 问之后先给出三个技术方案让用户挑，再一口气输出完整设计，包括文件结构、玩法机制、渲染方案、错误处理和测试策略。[原文§再看 superpowers 怎么审](https://xiaolinnote.com/claudecode/playbook/superpowers_vs_grillme.html#%E5%86%8D%E7%9C%8B-superpowers-%E6%80%8E%E4%B9%88%E5%AE%A1)
- **G6-21** 它自动进入下一个 skill 写实施计划：10 个任务、54 项单元测试、16 项浏览器人工验证清单，每个任务都是先写失败的测试、再写实现的完整循环；写完后询问执行方式，作者选了它推荐的子代理模式。[原文§再看 superpowers 怎么审](https://xiaolinnote.com/claudecode/playbook/superpowers_vs_grillme.html#%E5%86%8D%E7%9C%8B-superpowers-%E6%80%8E%E4%B9%88%E5%AE%A1)

## 7. ELI5 可视化讲解

原文：[ELI5 Skill 使用指南：让 Claude Code 把复杂知识画给你看](https://xiaolinnote.com/claudecode/playbook/eli5_skill.html)。

- **G7-1** 这句提示词只定了三个要求：默认读者对主题完全不了解，内容要可视化，文字尽量少；于是 AI 的回答就从大段文字变成了大图少字的 HTML 页面。[原文§这个 Skill 到底写了什么？](https://xiaolinnote.com/claudecode/playbook/eli5_skill.html#%E8%BF%99%E4%B8%AA-skill-%E5%88%B0%E5%BA%95%E5%86%99%E4%BA%86%E4%BB%80%E4%B9%88)
- **G7-2** 原文称 ELI5 没有教 AI 怎么写网页，因为模型本来就会；它只规定目标，页面该分几块、画什么图、用什么颜色都交给 Claude 自己判断。[原文§这个 Skill 到底写了什么？](https://xiaolinnote.com/claudecode/playbook/eli5_skill.html#%E8%BF%99%E4%B8%AA-skill-%E5%88%B0%E5%BA%95%E5%86%99%E4%BA%86%E4%BB%80%E4%B9%88)
- **G7-3** 正文里的 Topic: $ARGUMENTS 是占位符，调用时写在命令后面的内容就成为要讲解的主题，所以同一个 Skill 可以讲任何主题。[原文§这个 Skill 到底写了什么？](https://xiaolinnote.com/claudecode/playbook/eli5_skill.html#%E8%BF%99%E4%B8%AA-skill-%E5%88%B0%E5%BA%95%E5%86%99%E4%BA%86%E4%BB%80%E4%B9%88)
- **G7-4** 原文的对比是：直接问 AI 得到的是长篇文字，信息堆在一起，读起来更累；ELI5 会先用图把关系讲清楚，再带着读者一点点往下理解，网页里还有可以操作的互动演示。[原文§实测 ELI5 的效果](https://xiaolinnote.com/claudecode/playbook/eli5_skill.html#%E5%AE%9E%E6%B5%8B-eli5-%E7%9A%84%E6%95%88%E6%9E%9C)
- **G7-5** 原文示例中它把后训练讲成预训练之后针对回答、推理等能力做的专项练习，用知道不等于会做来说明为什么练完会变强，并在网页里做了一套互动演示，让读者一步步看模型是怎么练出来的。[原文§实测 ELI5 的效果](https://xiaolinnote.com/claudecode/playbook/eli5_skill.html#%E5%AE%9E%E6%B5%8B-eli5-%E7%9A%84%E6%95%88%E6%9E%9C)
- **G7-6** 原文示例中它先把项目的三种工作模式列出来，再按前端、后端、Agent、存储和容器罗列技术栈。[原文§实测 ELI5 的效果](https://xiaolinnote.com/claudecode/playbook/eli5_skill.html#%E5%AE%9E%E6%B5%8B-eli5-%E7%9A%84%E6%95%88%E6%9E%9C)
- **G7-7** 还可以用它理解陌生项目、技术取舍和事故原因，例如问这个项目是怎么工作的、为什么要做这个技术取舍、是什么导致了这次事故。[原文§怎么安装和使用 ELI5？](https://xiaolinnote.com/claudecode/playbook/eli5_skill.html#%E6%80%8E%E4%B9%88%E5%AE%89%E8%A3%85%E5%92%8C%E4%BD%BF%E7%94%A8-eli5)
- **G7-8** 它并不是 Claude Code 专属，本质上就是一份 SKILL.md，所以也能安装到其他 Agent 里；装好之后，不管用哪个 Agent，调用方式都一样。[原文§怎么安装和使用 ELI5？](https://xiaolinnote.com/claudecode/playbook/eli5_skill.html#%E6%80%8E%E4%B9%88%E5%AE%89%E8%A3%85%E5%92%8C%E4%BD%BF%E7%94%A8-eli5)
- **G7-9** 新名词原来要在不同资料里来回查，现在可以先让 ELI5 画一张图，把大概脉络弄懂，再去看更详细的资料；它最有用的地方是先帮你跨过第一道门槛，不至于一上来就被满屏术语劝退。[原文§实测 ELI5 的效果](https://xiaolinnote.com/claudecode/playbook/eli5_skill.html#%E5%AE%9E%E6%B5%8B-eli5-%E7%9A%84%E6%95%88%E6%9E%9C)
- **G7-10** 正文要求把读者当成对主题完全不了解的人，用大图和少量文字做 HTML 页面；页面分几块、画什么图、用什么颜色由 Claude 判断。它不再教模型已有的网页编写能力，只明确目标和表现要求。 [原文§这个 Skill 到底写了什么？](https://xiaolinnote.com/claudecode/playbook/eli5_skill.html#%E8%BF%99%E4%B8%AA-skill-%E5%88%B0%E5%BA%95%E5%86%99%E4%BA%86%E4%BB%80%E4%B9%88)

- **G8-1** 原文示例把范围写成：把短信发送功能迁移到新版 SDK，所有发送入口都要完成迁移，清理旧依赖，现有测试通过；完成要写成能检查的标准，而不是一句做好。[原文§一、需求到底怎么说，Claude 才好干活？](https://xiaolinnote.com/claudecode/playbook/opus55_handbook.html#%E4%B8%80%E3%80%81%E9%9C%80%E6%B1%82%E5%88%B0%E5%BA%95%E6%80%8E%E4%B9%88%E8%AF%B4-claude-%E6%89%8D%E5%A5%BD%E5%B9%B2%E6%B4%BB)

- **G8-8** 普通的查文件、改代码可以继续往下做，但下一步若是删除数据、强推代码，用户仍希望先被问一句；所以该继续的事和该停的事要一起讲清楚，危险操作的权限确认要保留，提示词里的约定不能代替权限设置。[原文§二、长任务，怎么避免干一半就停？](https://xiaolinnote.com/claudecode/playbook/opus55_handbook.html#%E4%BA%8C%E3%80%81%E9%95%BF%E4%BB%BB%E5%8A%A1-%E6%80%8E%E4%B9%88%E9%81%BF%E5%85%8D%E5%B9%B2%E4%B8%80%E5%8D%8A%E5%B0%B1%E5%81%9C)
- **G8-9** 让 Claude Code 把待办写进 TASKS.md，完成一项就更新，发现新问题也补进去；接着往下做时先读一遍，就知道哪些已经做完、哪些还没动、哪些在等用户决定。[原文§二、长任务，怎么避免干一半就停？](https://xiaolinnote.com/claudecode/playbook/opus55_handbook.html#%E4%BA%8C%E3%80%81%E9%95%BF%E4%BB%BB%E5%8A%A1-%E6%80%8E%E4%B9%88%E9%81%BF%E5%85%8D%E5%B9%B2%E4%B8%80%E5%8D%8A%E5%B0%B1%E5%81%9C)
- **G8-10** 长任务的对话里会不断塞进代码、日志和工具结果，上下文接近上限时旧内容会被压缩，最早交代的细节可能不再完整；先读一遍清单，它才知道哪些已经做完、哪些还没动、哪些在等用户决定。[原文§二、长任务，怎么避免干一半就停？](https://xiaolinnote.com/claudecode/playbook/opus55_handbook.html#%E4%BA%8C%E3%80%81%E9%95%BF%E4%BB%BB%E5%8A%A1-%E6%80%8E%E4%B9%88%E9%81%BF%E5%85%8D%E5%B9%B2%E4%B8%80%E5%8D%8A%E5%B0%B1%E5%81%9C)
- **G8-11** 等用户决定的事如果藏在长篇总结的末尾，用户看了半天才发现该自己接手；所以把汇报格式写进 CLAUDE.md，分成待你处理、已完成、新发现三部分，先处理待决事项。[原文§三、Claude 说做完了，你先看什么？](https://xiaolinnote.com/claudecode/playbook/opus55_handbook.html#%E4%B8%89%E3%80%81claude-%E8%AF%B4%E5%81%9A%E5%AE%8C%E4%BA%86-%E4%BD%A0%E5%85%88%E7%9C%8B%E4%BB%80%E4%B9%88)
- **G8-12** 每条发现要写清文件名和行号、什么情况下会出错、原因是什么，以及怎样复现；只说这段可能有问题还不够，得给出能查下去的具体线索。[原文§三、Claude 说做完了，你先看什么？](https://xiaolinnote.com/claudecode/playbook/opus55_handbook.html#%E4%B8%89%E3%80%81claude-%E8%AF%B4%E5%81%9A%E5%AE%8C%E4%BA%86-%E4%BD%A0%E5%85%88%E7%9C%8B%E4%BB%80%E4%B9%88)
- **G8-13** 示例的做法是在审查提示词里要求只列出必须修复后才能合并的问题。[原文§三、Claude 说做完了，你先看什么？](https://xiaolinnote.com/claudecode/playbook/opus55_handbook.html#%E4%B8%89%E3%80%81claude-%E8%AF%B4%E5%81%9A%E5%AE%8C%E4%BA%86-%E4%BD%A0%E5%85%88%E7%9C%8B%E4%BB%80%E4%B9%88)
- **G8-14** 哪些结论有依据、哪些还没查实，要在报告里分开写，没查实的再说明已经找过哪里，这样才能分清哪些可以采用、哪些还得补查。[原文§三、Claude 说做完了，你先看什么？](https://xiaolinnote.com/claudecode/playbook/opus55_handbook.html#%E4%B8%89%E3%80%81claude-%E8%AF%B4%E5%81%9A%E5%AE%8C%E4%BA%86-%E4%BD%A0%E5%85%88%E7%9C%8B%E4%BB%80%E4%B9%88)
- **G8-15** 直接发原图再问具体问题，比自己把方框、箭头描述一遍省事，也保留了位置关系；原文称这一代模型对图表细节和位置关系的理解有所改进，箭头连着谁、数字属于哪一栏都可以直接问。[原文§四、在 Claude 应用里，怎么用得更顺手？](https://xiaolinnote.com/claudecode/playbook/opus55_handbook.html#%E5%9B%9B%E3%80%81%E5%9C%A8-claude-%E5%BA%94%E7%94%A8%E9%87%8C-%E6%80%8E%E4%B9%88%E7%94%A8%E5%BE%97%E6%9B%B4%E9%A1%BA%E6%89%8B)
- **G8-16** 原文称要求模型逐字公开内部思考过程可能触发安全标记或被拒绝，这类要求应从提示词和固定指令里删掉；想了解为什么选这个方案，可以直接问取舍和证据。[原文§五、聊着聊着，怎么换模型了？](https://xiaolinnote.com/claudecode/playbook/opus55_handbook.html#%E4%BA%94%E3%80%81%E8%81%8A%E7%9D%80%E8%81%8A%E7%9D%80-%E6%80%8E%E4%B9%88%E6%8D%A2%E6%A8%A1%E5%9E%8B%E4%BA%86)
- **G8-17** 日常跟进时可以约定已经回答清楚的问题沿用之前的答案，除非用户再次问起或指出问题；但做长篇分析时先别加这条，因为新材料可能改变前面的判断，这时回头检查才是把问题想完整。[原文§四、在 Claude 应用里，怎么用得更顺手？](https://xiaolinnote.com/claudecode/playbook/opus55_handbook.html#%E5%9B%9B%E3%80%81%E5%9C%A8-claude-%E5%BA%94%E7%94%A8%E9%87%8C-%E6%80%8E%E4%B9%88%E7%94%A8%E5%BE%97%E6%9B%B4%E9%A1%BA%E6%89%8B)
- **G8-18** 检查范围不只是刚发的那句话，前面的消息、文件和搜索结果也算；可以到 Settings 的 Capabilities 里关闭自动切换，让对话先暂停由用户决定，在 Claude Code 里则用 /model 切回、在 /config 里调整偏好。[原文§五、聊着聊着，怎么换模型了？](https://xiaolinnote.com/claudecode/playbook/opus55_handbook.html#%E4%BA%94%E3%80%81%E8%81%8A%E7%9D%80%E8%81%8A%E7%9D%80-%E6%80%8E%E4%B9%88%E6%8D%A2%E6%A8%A1%E5%9E%8B%E4%BA%86)
- **G8-19** 有些内容触发安全检查后会切换模型，正常请求也可能被误判；认为是误判时，可以新开一个对话再提需求，或者用 /feedback 反馈。[原文§五、聊着聊着，怎么换模型了？](https://xiaolinnote.com/claudecode/playbook/opus55_handbook.html#%E4%BA%94%E3%80%81%E8%81%8A%E7%9D%80%E8%81%8A%E7%9D%80-%E6%80%8E%E4%B9%88%E6%8D%A2%E6%A8%A1%E5%9E%8B%E4%BA%86)
- **G8-20** 原文称手册说明快速模式用的还是同一个模型，只是响应更快、费用更高；它目前处于研究预览，需要开启额外用量，同样的 token 用快速模式更贵。[原文§六、等回复太慢，能不能快一点？](https://xiaolinnote.com/claudecode/playbook/opus55_handbook.html#%E5%85%AD%E3%80%81%E7%AD%89%E5%9B%9E%E5%A4%8D%E5%A4%AA%E6%85%A2-%E8%83%BD%E4%B8%8D%E8%83%BD%E5%BF%AB%E4%B8%80%E7%82%B9)
- **G8-21** 看自己是不是在等：一直坐在屏幕前来回调代码，少等一会可能就值；任务交出去以后本来就要去忙别的，就不用急着开。[原文§六、等回复太慢，能不能快一点？](https://xiaolinnote.com/claudecode/playbook/opus55_handbook.html#%E5%85%AD%E3%80%81%E7%AD%89%E5%9B%9E%E5%A4%8D%E5%A4%AA%E6%85%A2-%E8%83%BD%E4%B8%8D%E8%83%BD%E5%BF%AB%E4%B8%80%E7%82%B9)
- **G8-22** 提需求时写清完成标准，清理多余的思考叮嘱并明确设计偏好；运行时约定继续和暂停条件，保留危险操作确认，按需分工并更新清单；看结果先处理待决事项，再看审查证据和未确认信息；看设置确认当前模型和自动切换偏好。 [原文§最后，一份使用检查清单](https://xiaolinnote.com/claudecode/playbook/opus55_handbook.html#%E6%9C%80%E5%90%8E-%E4%B8%80%E4%BB%BD%E4%BD%BF%E7%94%A8%E6%A3%80%E6%9F%A5%E6%B8%85%E5%8D%95)

### 补充考点

- **G8-23** 提要求时说清楚要查日期、数字、名称有没有前后打架；发现问题，把有矛盾的原句摘出来，再标上段落或页码，这样拿着原句就能回去核对，比一句帮我看看更有着落。[原文§四、在 Claude 应用里，怎么用得更顺手？](https://xiaolinnote.com/claudecode/playbook/opus55_handbook.html#%E5%9B%9B%E3%80%81%E5%9C%A8-claude-%E5%BA%94%E7%94%A8%E9%87%8C-%E6%80%8E%E4%B9%88%E7%94%A8%E5%BE%97%E6%9B%B4%E9%A1%BA%E6%89%8B)
- **G8-24** 要明确说要一份文件，并把文件格式、列名和每行代表什么说清楚，例如把项目清单整理成 Excel、按负责人和截止日期排列，交付后就能直接打开检查。[原文§四、在 Claude 应用里，怎么用得更顺手？](https://xiaolinnote.com/claudecode/playbook/opus55_handbook.html#%E5%9B%9B%E3%80%81%E5%9C%A8-claude-%E5%BA%94%E7%94%A8%E9%87%8C-%E6%80%8E%E4%B9%88%E7%94%A8%E5%BE%97%E6%9B%B4%E9%A1%BA%E6%89%8B)

## 9. AI 原生研发的六个阶段

原文：[AI 原生研发流程图解：从需求到上线，Claude Code 怎么参与六个阶段？](https://xiaolinnote.com/claudecode/playbook/anthropic_ai_native_sdlc.html)。

### 流程与产物

- **G9-1** 规划、审查和部署仍按人的速度运行，新的瓶颈堵在编码阶段的两边；Agent 一次生成几十个文件后，Reviewer 和安全团队的人数并没有增加，审查队列越积越长。[原文§01｜代码写快以后，旧流程为什么卡住了？](https://xiaolinnote.com/claudecode/playbook/anthropic_ai_native_sdlc.html#_01-%E4%BB%A3%E7%A0%81%E5%86%99%E5%BF%AB%E4%BB%A5%E5%90%8E-%E6%97%A7%E6%B5%81%E7%A8%8B%E4%B8%BA%E4%BB%80%E4%B9%88%E5%8D%A1%E4%BD%8F%E4%BA%86)
- **G9-2** 因为只加速编码会让代码要么一直排队等审查，要么未经充分检查就上线，对有安全和合规要求的公司都走不通；所以要让 AI 进入整个软件开发生命周期，并把人留在需要判断和授权的关键节点。[原文§01｜代码写快以后，旧流程为什么卡住了？](https://xiaolinnote.com/claudecode/playbook/anthropic_ai_native_sdlc.html#_01-%E4%BB%A3%E7%A0%81%E5%86%99%E5%BF%AB%E4%BB%A5%E5%90%8E-%E6%97%A7%E6%B5%81%E7%A8%8B%E4%B8%BA%E4%BB%80%E4%B9%88%E5%8D%A1%E4%BD%8F%E4%BA%86)
- **G9-3** 人的注意力有上限，没法同时认真审完多份代码；这套流程让 AI 先过滤机械问题，人把注意力集中在少数需要拍板的位置：需求有没有跑偏、风险能不能接受、代码能不能进入生产环境。[原文§最后](https://xiaolinnote.com/claudecode/playbook/anthropic_ai_native_sdlc.html#%E6%9C%80%E5%90%8E)
- **G9-4** 每个阶段结束时提交一份版本化的产物，下一阶段直接读取它继续工作，例如 intent.md、spec.md、plan.md；这些文件既能给人看，也能让 AI 接着执行，不必靠转述。[原文§02｜AI Native 到底改了什么？](https://xiaolinnote.com/claudecode/playbook/anthropic_ai_native_sdlc.html#_02-ai-native-%E5%88%B0%E5%BA%95%E6%94%B9%E4%BA%86%E4%BB%80%E4%B9%88)
- **G9-5** Git 提交历史成为审计记录：谁提出了需求、Claude 生成了什么、谁批准了方案，都能从版本记录里查回来。[原文§02｜AI Native 到底改了什么？](https://xiaolinnote.com/claudecode/playbook/anthropic_ai_native_sdlc.html#_02-ai-native-%E5%88%B0%E5%BA%95%E6%94%B9%E4%BA%86%E4%BB%80%E4%B9%88)
- **G9-6** intent.md 写清当前问题、期望结果、受影响的系统、数据限制和待确认的问题；它来自提出者与 Claude 的讨论，包括问题影响谁、希望达到什么结果、有哪些限制、这次明确不做什么。[原文§1. Plan，怎么把一个想法变成 intent.md？](https://xiaolinnote.com/claudecode/playbook/anthropic_ai_native_sdlc.html#_1-plan-%E6%80%8E%E4%B9%88%E6%8A%8A%E4%B8%80%E4%B8%AA%E6%83%B3%E6%B3%95%E5%8F%98%E6%88%90-intent-md)
- **G9-7** 提出者负责纠正 Claude 的理解偏差，他的原始意图直接留在文件里，工程团队不用经过几轮转述，再去猜他一开始到底想解决什么。[原文§1. Plan，怎么把一个想法变成 intent.md？](https://xiaolinnote.com/claudecode/playbook/anthropic_ai_native_sdlc.html#_1-plan-%E6%80%8E%E4%B9%88%E6%8A%8A%E4%B8%80%E4%B8%AA%E6%83%B3%E6%B3%95%E5%8F%98%E6%88%90-intent-md)
- **G9-8** spec.md 写清功能怎么工作、数据怎样流动、会影响哪些系统。[原文§2. Design，怎么把意图变成 spec.md？](https://xiaolinnote.com/claudecode/playbook/anthropic_ai_native_sdlc.html#_2-design-%E6%80%8E%E4%B9%88%E6%8A%8A%E6%84%8F%E5%9B%BE%E5%8F%98%E6%88%90-spec-md)
- **G9-9** Claude 读取 intent.md 后，加载团队已经整理好的品牌、安全、合规和用户体验 Skills 来生成 spec.md，把安全、合规问题从评审会提前到设计阶段发现。[原文§2. Design，怎么把意图变成 spec.md？](https://xiaolinnote.com/claudecode/playbook/anthropic_ai_native_sdlc.html#_2-design-%E6%80%8E%E4%B9%88%E6%8A%8A%E6%84%8F%E5%9B%BE%E5%8F%98%E6%88%90-spec-md)
- **G9-10** 在 Design 阶段：产品负责人检查方案有没有解决原来的问题，再把疑点交给安全、合规或技术负责人处理；原文称能提前发现的问题，就别拖到代码写完以后再返工。[原文§2. Design，怎么把意图变成 spec.md？](https://xiaolinnote.com/claudecode/playbook/anthropic_ai_native_sdlc.html#_2-design-%E6%80%8E%E4%B9%88%E6%8A%8A%E6%84%8F%E5%9B%BE%E5%8F%98%E6%88%90-spec-md)
- **G9-11** Plan Mode 下 Claude 先读代码库，列出准备修改哪些文件、按什么顺序实现、可能影响什么、要运行哪些测试；在工程师接受计划之前它不能直接修改代码，工程师还可以追问风险和其他方案。[原文§3. Build，为什么一定要先做计划？](https://xiaolinnote.com/claudecode/playbook/anthropic_ai_native_sdlc.html#_3-build-%E4%B8%BA%E4%BB%80%E4%B9%88%E4%B8%80%E5%AE%9A%E8%A6%81%E5%85%88%E5%81%9A%E8%AE%A1%E5%88%92)
- **G9-12** CLAUDE.md 记录构建和测试命令、目录职责、代码约定，以及 Claude 经常犯的错误；需要强制执行的红线，例如禁止读取密钥或修改受保护文件，则交给 Hook 拦截。[原文§3. Build，为什么一定要先做计划？](https://xiaolinnote.com/claudecode/playbook/anthropic_ai_native_sdlc.html#_3-build-%E4%B8%BA%E4%BB%80%E4%B9%88%E4%B8%80%E5%AE%9A%E8%A6%81%E5%85%88%E5%81%9A%E8%AE%A1%E5%88%92)
- **G9-13** 任务太复杂时拆给 Subagent，不同任务放进独立的 Git worktree，几个 Claude Code 会话就能同时工作，又不会挤在一起修改同一份文件。[原文§3. Build，为什么一定要先做计划？](https://xiaolinnote.com/claudecode/playbook/anthropic_ai_native_sdlc.html#_3-build-%E4%B8%BA%E4%BB%80%E4%B9%88%E4%B8%80%E5%AE%9A%E8%A6%81%E5%85%88%E5%81%9A%E8%AE%A1%E5%88%92)

### 验证、发布与维护

- **G9-14** 不听它说已经完成，而看它能不能拿出结果：让 Claude 自己运行测试和构建、读取失败结果、修改后再次验证，直到满足计划里约定的完成条件；最后再开一个没参与实现的新会话，只负责复核。[原文§4. Test，怎么证明 AI 真的做完了？](https://xiaolinnote.com/claudecode/playbook/anthropic_ai_native_sdlc.html#_4-test-%E6%80%8E%E4%B9%88%E8%AF%81%E6%98%8E-ai-%E7%9C%9F%E7%9A%84%E5%81%9A%E5%AE%8C%E4%BA%86)
- **G9-15** 测试和构建验证的是这一次的功能能不能运行；Evals 是一套固定的 Agent 评测任务，用来检查更换模型或修改 CLAUDE.md、Skill、Hook 之后通过率有没有下降。[原文§4. Test，怎么证明 AI 真的做完了？](https://xiaolinnote.com/claudecode/playbook/anthropic_ai_native_sdlc.html#_4-test-%E6%80%8E%E4%B9%88%E8%AF%81%E6%98%8E-ai-%E7%9C%9F%E7%9A%84%E5%81%9A%E5%AE%8C%E4%BA%86)
- **G9-16** 因为通过率下降就说明这次配置调整带来了退步，所以每次更换模型，或者修改 CLAUDE.md、Skill 和 Hook，都要重新运行这些固定任务。[原文§4. Test，怎么证明 AI 真的做完了？](https://xiaolinnote.com/claudecode/playbook/anthropic_ai_native_sdlc.html#_4-test-%E6%80%8E%E4%B9%88%E8%AF%81%E6%98%8E-ai-%E7%9C%9F%E7%9A%84%E5%81%9A%E5%AE%8C%E4%BA%86)
- **G9-17** 线上发生过的问题要加入 Evals，变成以后长期运行的回归测试。[原文§4. Test，怎么证明 AI 真的做完了？](https://xiaolinnote.com/claudecode/playbook/anthropic_ai_native_sdlc.html#_4-test-%E6%80%8E%E4%B9%88%E8%AF%81%E6%98%8E-ai-%E7%9C%9F%E7%9A%84%E5%81%9A%E5%AE%8C%E4%BA%86)
- **G9-18** Claude 可以同时充当 PR 作者和 Reviewer，按团队规则检查逻辑与安全问题，并对照 spec.md 和 plan.md 确认实现没有跑偏；PR 通过后进入 CI/CD，完成构建、测试和不同环境的部署准备。[原文§5. Deploy，AI 可以走到哪一步？](https://xiaolinnote.com/claudecode/playbook/anthropic_ai_native_sdlc.html#_5-deploy-ai-%E5%8F%AF%E4%BB%A5%E8%B5%B0%E5%88%B0%E5%93%AA%E4%B8%80%E6%AD%A5)
- **G9-19** 低风险改动可以经过多层 Agent 审查，高风险和受监管的代码继续交给人复核。[原文§5. Deploy，AI 可以走到哪一步？](https://xiaolinnote.com/claudecode/playbook/anthropic_ai_native_sdlc.html#_5-deploy-ai-%E5%8F%AF%E4%BB%A5%E8%B5%B0%E5%88%B0%E5%93%AA%E4%B8%80%E6%AD%A5)
- **G9-20** 原文称开发环境可以多放一些权限，到了生产环境规则就得收紧，并且必须保留最后一道闸门。[原文§5. Deploy，AI 可以走到哪一步？](https://xiaolinnote.com/claudecode/playbook/anthropic_ai_native_sdlc.html#_5-deploy-ai-%E5%8F%AF%E4%BB%A5%E8%B5%B0%E5%88%B0%E5%93%AA%E4%B8%80%E6%AD%A5)
- **G9-21** 可以让它走到生产闸门前，但不能让它自己跨过去：Agent 可以完成上线之前的所有工作，但生产环境必须保留最后一道闸门。[原文§5. Deploy，AI 可以走到哪一步？](https://xiaolinnote.com/claudecode/playbook/anthropic_ai_native_sdlc.html#_5-deploy-ai-%E5%8F%AF%E4%BB%A5%E8%B5%B0%E5%88%B0%E5%93%AA%E4%B8%80%E6%AD%A5)
- **G9-22** Agent 可以完成上线之前的所有工作，真正执行发布时 Hook 会拦住命令，等一位具名负责人批准后才继续。[原文§5. Deploy，AI 可以走到哪一步？](https://xiaolinnote.com/claudecode/playbook/anthropic_ai_native_sdlc.html#_5-deploy-ai-%E5%8F%AF%E4%BB%A5%E8%B5%B0%E5%88%B0%E5%93%AA%E4%B8%80%E6%AD%A5)
- **G9-23** Agent 持续监控错误率、延迟和其他生产指标；指标超过预设阈值后开始做只读诊断，整理可能的原因和修复建议。[原文§6. Maintain，怎么让线上问题回到开发流程？](https://xiaolinnote.com/claudecode/playbook/anthropic_ai_native_sdlc.html#_6-maintain-%E6%80%8E%E4%B9%88%E8%AE%A9%E7%BA%BF%E4%B8%8A%E9%97%AE%E9%A2%98%E5%9B%9E%E5%88%B0%E5%BC%80%E5%8F%91%E6%B5%81%E7%A8%8B)
- **G9-24** 涉及回滚或生产修改时，只能使用团队提前批准并演练过的方案。处理后由工程师确认结果，再把线上问题写成新的 intent.md，进入下一轮 Plan。 [原文§6. Maintain，怎么让线上问题回到开发流程？](https://xiaolinnote.com/claudecode/playbook/anthropic_ai_native_sdlc.html#_6-maintain-%E6%80%8E%E4%B9%88%E8%AE%A9%E7%BA%BF%E4%B8%8A%E9%97%AE%E9%A2%98%E5%9B%9E%E5%88%B0%E5%BC%80%E5%8F%91%E6%B5%81%E7%A8%8B)
- **G9-25** 工程师确认处理结果后，团队把这次线上问题写成新的 intent.md，重新回到 Plan 阶段，整套循环由此闭合。[原文§6. Maintain，怎么让线上问题回到开发流程？](https://xiaolinnote.com/claudecode/playbook/anthropic_ai_native_sdlc.html#_6-maintain-%E6%80%8E%E4%B9%88%E8%AE%A9%E7%BA%BF%E4%B8%8A%E9%97%AE%E9%A2%98%E5%9B%9E%E5%88%B0%E5%BC%80%E5%8F%91%E6%B5%81%E7%A8%8B)
- **G9-26** 六个阶段是一个需求的执行顺序；团队落地时不需要从 Plan 一路改到 Maintain，而是按依赖关系先做没有前置条件的几项，例如 intent.md、CLAUDE.md、测试反馈循环、Hook 和 Plan Mode。[原文§04｜这套流程该按什么顺序落地？](https://xiaolinnote.com/claudecode/playbook/anthropic_ai_native_sdlc.html#_04-%E8%BF%99%E5%A5%97%E6%B5%81%E7%A8%8B%E8%AF%A5%E6%8C%89%E4%BB%80%E4%B9%88%E9%A1%BA%E5%BA%8F%E8%90%BD%E5%9C%B0)
- **G9-27** 现在最卡哪一步就先补哪一块：需求最慢就先改 Plan，审查队列最严重就先改 Deploy；需求经常走样先用 intent.md，Claude 经常重复犯错就维护 CLAUDE.md，做完拿不出证据就建立测试反馈循环。[原文§04｜这套流程该按什么顺序落地？](https://xiaolinnote.com/claudecode/playbook/anthropic_ai_native_sdlc.html#_04-%E8%BF%99%E5%A5%97%E6%B5%81%E7%A8%8B%E8%AF%A5%E6%8C%89%E4%BB%80%E4%B9%88%E9%A1%BA%E5%BA%8F%E8%90%BD%E5%9C%B0)
- **G9-28** 让 AI 先过滤信息：代码生成前，人先审核 intent.md、spec.md 和 plan.md，趁内容少把方向定住；生成以后由测试、固定评测和多层 Agent 审查先过滤机械问题；最后人主要判断需求有没有跑偏、风险能否接受、代码能否进入生产环境。[原文§最后](https://xiaolinnote.com/claudecode/playbook/anthropic_ai_native_sdlc.html#%E6%9C%80%E5%90%8E)

### 补充考点

- **G9-29** 过去有了产品想法，通常要先写工单，再找产品经理开会补用户故事和验收标准；现在可以先用自己的话和 Claude 讨论，不用一上来就写一份格式完整的需求文档。[原文§1. Plan，怎么把一个想法变成 intent.md？](https://xiaolinnote.com/claudecode/playbook/anthropic_ai_native_sdlc.html#_1-plan-%E6%80%8E%E4%B9%88%E6%8A%8A%E4%B8%80%E4%B8%AA%E6%83%B3%E6%B3%95%E5%8F%98%E6%88%90-intent-md)

## 10. 老项目改造的准备与验收

原文：[Claude Code 老项目改造指南：怎样让 AI 稳妥地升级旧系统？](https://xiaolinnote.com/claudecode/playbook/claude_code_modernization.html)。

### 目标与验收

- **G10-1** 原文称写得出来，改得对不对还是得有人确认：Agent 一下交来一堆修改，谁来验、谁来审、最后谁点上线都要落实；代码可以批量生成，负责审核的同事不会跟着批量出现。[原文§Claude Code 老项目改造指南：怎样让 AI 稳妥地升级旧系统？](https://xiaolinnote.com/claudecode/playbook/claude_code_modernization.html#claude-code-%E8%80%81%E9%A1%B9%E7%9B%AE%E6%94%B9%E9%80%A0%E6%8C%87%E5%8D%97-%E6%80%8E%E6%A0%B7%E8%AE%A9-ai-%E7%A8%B3%E5%A6%A5%E5%9C%B0%E5%8D%87%E7%BA%A7%E6%97%A7%E7%B3%BB%E7%BB%9F)
- **G10-2** 升级版本要写清目标运行时版本和依赖包；换技术栈要提前定好用什么语言、框架和架构，并让系统继续按原来的业务规则处理请求；重新设计除了技术要求，还得写清新系统应该怎样处理业务，并和使用方确认。[原文§一、旧系统到底要改成什么？](https://xiaolinnote.com/claudecode/playbook/claude_code_modernization.html#%E4%B8%80%E3%80%81%E6%97%A7%E7%B3%BB%E7%BB%9F%E5%88%B0%E5%BA%95%E8%A6%81%E6%94%B9%E6%88%90%E4%BB%80%E4%B9%88)
- **G10-3** 不同角色的期望不一样：有人只想换技术栈、业务逻辑别动，有人想顺手还技术债，业务方还想顺便加需求；不先分清这次是哪一种改造，等 AI 交卷了，这份代码到底算改对还是改错就没有标准。[原文§一、旧系统到底要改成什么？](https://xiaolinnote.com/claudecode/playbook/claude_code_modernization.html#%E4%B8%80%E3%80%81%E6%97%A7%E7%B3%BB%E7%BB%9F%E5%88%B0%E5%BA%95%E8%A6%81%E6%94%B9%E6%88%90%E4%BB%80%E4%B9%88)
- **G10-4** assess 把项目用了哪些语言、代码有多复杂、积累了哪些技术债整理成评估报告；map 把哪些模块互相调用、数据经过哪些地方画成关系图；extract-rules 把藏在代码里的业务规则整理成说明。[原文§一、旧系统到底要改成什么？](https://xiaolinnote.com/claudecode/playbook/claude_code_modernization.html#%E4%B8%80%E3%80%81%E6%97%A7%E7%B3%BB%E7%BB%9F%E5%88%B0%E5%BA%95%E8%A6%81%E6%94%B9%E6%88%90%E4%BB%80%E4%B9%88)
- **G10-5** Claude 把规则的触发条件和处理动作提取出来，并在旁边标上对应的文件和行号；人拿着这份说明就能回到代码里核对，判断这条规则升级后要不要保留。[原文§一、旧系统到底要改成什么？](https://xiaolinnote.com/claudecode/playbook/claude_code_modernization.html#%E4%B8%80%E3%80%81%E6%97%A7%E7%B3%BB%E7%BB%9F%E5%88%B0%E5%BA%95%E8%A6%81%E6%94%B9%E6%88%90%E4%BB%80%E4%B9%88)
- **G10-6** 业务同事平时怎么用、开发者记得哪些历史约定，代码里看不出来，还得找人问并结合内部文档补充；否则看着像没用的老逻辑，说不定还有人在依赖。确认之后再决定哪些保留、哪些修改、哪些删掉。[原文§一、旧系统到底要改成什么？](https://xiaolinnote.com/claudecode/playbook/claude_code_modernization.html#%E4%B8%80%E3%80%81%E6%97%A7%E7%B3%BB%E7%BB%9F%E5%88%B0%E5%BA%95%E8%A6%81%E6%94%B9%E6%88%90%E4%BB%80%E4%B9%88)
- **G10-7** 旧运行时停止支持、漏洞没法修、懂这套系统的人越来越少，继续拖着也有代价；很多改造最重要的收益就是降低这些风险，所以讨论预算和上线风险时，不能只算改了可能出什么事。[原文§一、旧系统到底要改成什么？](https://xiaolinnote.com/claudecode/playbook/claude_code_modernization.html#%E4%B8%80%E3%80%81%E6%97%A7%E7%B3%BB%E7%BB%9F%E5%88%B0%E5%BA%95%E8%A6%81%E6%94%B9%E6%88%90%E4%BB%80%E4%B9%88)
- **G10-8** 立项时要把改造的理由和目标讲给管理层、系统负责人和依赖这套系统的团队；大家认可目标并愿意投入人力和资源，后面讨论预算、排期和风险取舍才有依据；只说一句支持、需要人时却抽不出来，项目还是推不动。[原文§一、旧系统到底要改成什么？](https://xiaolinnote.com/claudecode/playbook/claude_code_modernization.html#%E4%B8%80%E3%80%81%E6%97%A7%E7%B3%BB%E7%BB%9F%E5%88%B0%E5%BA%95%E8%A6%81%E6%94%B9%E6%88%90%E4%BB%80%E4%B9%88)
- **G10-9** 条件能自动检查，Agent 才能反复修改、验证，实在过不了再交给人处理；每份修改还要带上测试结果、检查报告等通过验收的证据。[原文§二、AI 改完了，怎么证明改对了？](https://xiaolinnote.com/claudecode/playbook/claude_code_modernization.html#%E4%BA%8C%E3%80%81ai-%E6%94%B9%E5%AE%8C%E4%BA%86-%E6%80%8E%E4%B9%88%E8%AF%81%E6%98%8E%E6%94%B9%E5%AF%B9%E4%BA%86)
- **G10-10** 覆盖率至少多少、性能允许在什么范围内波动，都要先约定好；否则结果出来后，一个人觉得这点变化没关系，另一个人觉得这怎么能上线，无法达成一致。[原文§二、AI 改完了，怎么证明改对了？](https://xiaolinnote.com/claudecode/playbook/claude_code_modernization.html#%E4%BA%8C%E3%80%81ai-%E6%94%B9%E5%AE%8C%E4%BA%86-%E6%80%8E%E4%B9%88%E8%AF%81%E6%98%8E%E6%94%B9%E5%AF%B9%E4%BA%86)
- **G10-11** 把同一批输入交给新旧系统并比较输出，可以发现处理结果的差异；检查两个版本能不能读懂彼此保存的数据和发出的消息，可以发现字段丢失或含义改变，例如新版本保存的数据旧版本还能不能正常读取。[原文§二、AI 改完了，怎么证明改对了？](https://xiaolinnote.com/claudecode/playbook/claude_code_modernization.html#%E4%BA%8C%E3%80%81ai-%E6%94%B9%E5%AE%8C%E4%BA%86-%E6%80%8E%E4%B9%88%E8%AF%81%E6%98%8E%E6%94%B9%E5%AF%B9%E4%BA%86)
- **G10-12** 让修改后的系统在预发布环境跑一段约定的时间，观察错误率有没有升高、响应有没有变慢、告警有没有增多；有界面的系统还可以让 Claude 操作界面，检查原来能用的功能有没有被改坏。[原文§二、AI 改完了，怎么证明改对了？](https://xiaolinnote.com/claudecode/playbook/claude_code_modernization.html#%E4%BA%8C%E3%80%81ai-%E6%94%B9%E5%AE%8C%E4%BA%86-%E6%80%8E%E4%B9%88%E8%AF%81%E6%98%8E%E6%94%B9%E5%AF%B9%E4%BA%86)
- **G10-13** 继续沿用写代码时的对话，Claude 可能顺着之前的思路判断，把当时没考虑到的问题又漏过去；在新的对话里只提供审查所需的代码、要求和资料，让它独立查找必须修复才能上线的问题。[原文§二、AI 改完了，怎么证明改对了？](https://xiaolinnote.com/claudecode/playbook/claude_code_modernization.html#%E4%BA%8C%E3%80%81ai-%E6%94%B9%E5%AE%8C%E4%BA%86-%E6%80%8E%E4%B9%88%E8%AF%81%E6%98%8E%E6%94%B9%E5%AF%B9%E4%BA%86)
- **G10-14** 单纯升级版本时，旧测试可以作为验收的核心；换了语言和框架后，旧测试往往没法直接跑，就更需要对比新旧系统的处理结果。[原文§二、AI 改完了，怎么证明改对了？](https://xiaolinnote.com/claudecode/playbook/claude_code_modernization.html#%E4%BA%8C%E3%80%81ai-%E6%94%B9%E5%AE%8C%E4%BA%86-%E6%80%8E%E4%B9%88%E8%AF%81%E6%98%8E%E6%94%B9%E5%AF%B9%E4%BA%86)
- **G10-15** 请求回放是把线上记录下来的请求再交给新系统处理；并行运行是让旧系统继续提供服务，新系统在旁边处理同样的输入，观察两边的结果有没有差异。[原文§二、AI 改完了，怎么证明改对了？](https://xiaolinnote.com/claudecode/playbook/claude_code_modernization.html#%E4%BA%8C%E3%80%81ai-%E6%94%B9%E5%AE%8C%E4%BA%86-%E6%80%8E%E4%B9%88%E8%AF%81%E6%98%8E%E6%94%B9%E5%AF%B9%E4%BA%86)
- **G10-16** 要先写清新系统遇到什么情况该怎样处理，和使用方确认后再据此写测试，并让 Claude 在独立的一轮审查里检查是否符合；文字说明可能有歧义，依赖模型判断的地方更多，发现说明有缺口还要补充并同步调整验收条件。[原文§二、AI 改完了，怎么证明改对了？](https://xiaolinnote.com/claudecode/playbook/claude_code_modernization.html#%E4%BA%8C%E3%80%81ai-%E6%94%B9%E5%AE%8C%E4%BA%86-%E6%80%8E%E4%B9%88%E8%AF%81%E6%98%8E%E6%94%B9%E5%AF%B9%E4%BA%86)
- **G10-17** 把开发者、使用方和业务负责人拉进来，拿着准备检查的项目问：真都通过了，你愿不愿意合并？不放心就接着问还缺哪项检查；这总比 AI 全改完了，审核的人才说这些结果我不认要好。[原文§二、AI 改完了，怎么证明改对了？](https://xiaolinnote.com/claudecode/playbook/claude_code_modernization.html#%E4%BA%8C%E3%80%81ai-%E6%94%B9%E5%AE%8C%E4%BA%86-%E6%80%8E%E4%B9%88%E8%AF%81%E6%98%8E%E6%94%B9%E5%AF%B9%E4%BA%86)
- **G10-18** 测试没几条、时过时不过、监控也不齐时，不能直接拿来放心验收；可以先让 Claude 补测试、搭请求回放工具，或者准备好对比新旧系统的环境，再推进后面的改造。[原文§二、AI 改完了，怎么证明改对了？](https://xiaolinnote.com/claudecode/playbook/claude_code_modernization.html#%E4%BA%8C%E3%80%81ai-%E6%94%B9%E5%AE%8C%E4%BA%86-%E6%80%8E%E4%B9%88%E8%AF%81%E6%98%8E%E6%94%B9%E5%AF%B9%E4%BA%86)

### 审核、准备与推广

- **G10-19** 如果每份修改都要人逐行看，Agent 交得越快，待审的代码就可能堆得越多，人反而从熬夜写变成熬夜审；所以要提前给修改分级，决定不同修改需要多深的人工审核。[原文§三、代码改得这么快，人怎么审得过来？](https://xiaolinnote.com/claudecode/playbook/claude_code_modernization.html#%E4%B8%89%E3%80%81%E4%BB%A3%E7%A0%81%E6%94%B9%E5%BE%97%E8%BF%99%E4%B9%88%E5%BF%AB-%E4%BA%BA%E6%80%8E%E4%B9%88%E5%AE%A1%E5%BE%97%E8%BF%87%E6%9D%A5)
- **G10-20** 先看修改会影响哪些功能，再结合测试结果、审查发现以及 Agent 标出的不确定之处；有现成的风险分类就沿用，涉及支付、账务等关键业务流程仍然要完整地人工检查。[原文§三、代码改得这么快，人怎么审得过来？](https://xiaolinnote.com/claudecode/playbook/claude_code_modernization.html#%E4%B8%89%E3%80%81%E4%BB%A3%E7%A0%81%E6%94%B9%E5%BE%97%E8%BF%99%E4%B9%88%E5%BF%AB-%E4%BA%BA%E6%80%8E%E4%B9%88%E5%AE%A1%E5%BE%97%E8%BF%87%E6%9D%A5)
- **G10-21** 让他们先看样例，提前说清哪些检查结果最有用、报告怎么排才好查，后面审核时就能直接找到高风险修改和 Agent 标出的疑点；专家认可了样例和检查结果，团队才有依据判断哪些把握较大的修改可以减少人工审核。[原文§三、代码改得这么快，人怎么审得过来？](https://xiaolinnote.com/claudecode/playbook/claude_code_modernization.html#%E4%B8%89%E3%80%81%E4%BB%A3%E7%A0%81%E6%94%B9%E5%BE%97%E8%BF%99%E4%B9%88%E5%BF%AB-%E4%BA%BA%E6%80%8E%E4%B9%88%E5%AE%A1%E5%BE%97%E8%BF%87%E6%9D%A5)
- **G10-22** 要回头修工作流或验收规则；否则专家每天都在纠正同一个错误，Agent 再快也省不下多少工夫。[原文§三、代码改得这么快，人怎么审得过来？](https://xiaolinnote.com/claudecode/playbook/claude_code_modernization.html#%E4%B8%89%E3%80%81%E4%BB%A3%E7%A0%81%E6%94%B9%E5%BE%97%E8%BF%99%E4%B9%88%E5%BF%AB-%E4%BA%BA%E6%80%8E%E4%B9%88%E5%AE%A1%E5%BE%97%E8%BF%87%E6%9D%A5)
- **G10-23** 原文称在受监管的企业里，审核深度和风险取舍最好由管理层牵头确定，并按已有的变更管理流程执行，不能让点批准的人独自背锅；前提是验收证据足够扎实，审核的人看得懂 Claude 为什么这样改、做过哪些检查。[原文§三、代码改得这么快，人怎么审得过来？](https://xiaolinnote.com/claudecode/playbook/claude_code_modernization.html#%E4%B8%89%E3%80%81%E4%BB%A3%E7%A0%81%E6%94%B9%E5%BE%97%E8%BF%99%E4%B9%88%E5%BF%AB-%E4%BA%BA%E6%80%8E%E4%B9%88%E5%AE%A1%E5%BE%97%E8%BF%87%E6%9D%A5)
- **G10-24** 给 Agent 准备一台专用远程主机，让 Claude 能访问代码和相关资料；再按验收要求配好测试资源、线上监控数据、用于回放的请求记录，或者让新旧系统同时运行并对比结果的环境。[原文§四、开工前，还要准备什么？](https://xiaolinnote.com/claudecode/playbook/claude_code_modernization.html#%E5%9B%9B%E3%80%81%E5%BC%80%E5%B7%A5%E5%89%8D-%E8%BF%98%E8%A6%81%E5%87%86%E5%A4%87%E4%BB%80%E4%B9%88)
- **G10-25** 插件生成的依赖图可以作为起点，还要结合构建日志、代码里导入了哪些模块，以及实际运行时的调用记录来核对；同时要定下哪些依赖要替换、是否需要兼容性检查。[原文§四、开工前，还要准备什么？](https://xiaolinnote.com/claudecode/playbook/claude_code_modernization.html#%E5%9B%9B%E3%80%81%E5%BC%80%E5%B7%A5%E5%89%8D-%E8%BF%98%E8%A6%81%E5%87%86%E5%A4%87%E4%BB%80%E4%B9%88)
- **G10-26** 先确认公司允许通过当前的 Claude Code 接入方式处理源码，再只给必要的权限：让 Agent 只能写入改造分支，不给生产环境的账号、密码和访问密钥；改造分支里的敏感信息和个人信息要清理或脱敏。[原文§四、开工前，还要准备什么？](https://xiaolinnote.com/claudecode/playbook/claude_code_modernization.html#%E5%9B%9B%E3%80%81%E5%BC%80%E5%B7%A5%E5%89%8D-%E8%BF%98%E8%A6%81%E5%87%86%E5%A4%87%E4%BB%80%E4%B9%88)
- **G10-27** 每个 PR 都附上 Agent 的执行记录和验收结果，方便查清代码是怎样改出来的。[原文§四、开工前，还要准备什么？](https://xiaolinnote.com/claudecode/playbook/claude_code_modernization.html#%E5%9B%9B%E3%80%81%E5%BC%80%E5%B7%A5%E5%89%8D-%E8%BF%98%E8%A6%81%E5%87%86%E5%A4%87%E4%BB%80%E4%B9%88)
- **G10-28** 先挑小范围试运行，让业务专家检查改出的代码、Agent 的处理过程和交上来的验收证据，提取出的业务规则和项目专用 Skills 也先由专家核对；目的是让团队对扩大执行后的结果有把握，也愿意按约定的规则审核、合并。[原文§五、怎么把这些要求交给 Agent？](https://xiaolinnote.com/claudecode/playbook/claude_code_modernization.html#%E4%BA%94%E3%80%81%E6%80%8E%E4%B9%88%E6%8A%8A%E8%BF%99%E4%BA%9B%E8%A6%81%E6%B1%82%E4%BA%A4%E7%BB%99-agent)
- **G10-29** 试跑十处有五处犯同一种错，后面还有几百处；只把这五处手工修完解决不了问题，要调整 Agent 的操作步骤或检查规则，避免下一批修改再犯同样的错。[原文§五、怎么把这些要求交给 Agent？](https://xiaolinnote.com/claudecode/playbook/claude_code_modernization.html#%E4%BA%94%E3%80%81%E6%80%8E%E4%B9%88%E6%8A%8A%E8%BF%99%E4%BA%9B%E8%A6%81%E6%B1%82%E4%BA%A4%E7%BB%99-agent)
- **G10-30** 选一小部分代码，从修改、验收一路走到审核、合并上线：代码改得对，和这份代码能按团队的流程上线，中间还隔着几道关；哪里不顺就趁范围小的时候修好，跑到有把握再扩大。[原文§六、怎么推到整个项目？](https://xiaolinnote.com/claudecode/playbook/claude_code_modernization.html#%E5%85%AD%E3%80%81%E6%80%8E%E4%B9%88%E6%8E%A8%E5%88%B0%E6%95%B4%E4%B8%AA%E9%A1%B9%E7%9B%AE)
- **G10-31** 你在升级时同事也没闲着，原项目每天还在进新代码，两份代码就得不停地同步；同步工作太多，或者系统需要持续运行时，可以考虑在现有项目里分批升级。[原文§六、怎么推到整个项目？](https://xiaolinnote.com/claudecode/playbook/claude_code_modernization.html#%E5%85%AD%E3%80%81%E6%80%8E%E4%B9%88%E6%8E%A8%E5%88%B0%E6%95%B4%E4%B8%AA%E9%A1%B9%E7%9B%AE)
- **G10-32** 先按模块之间的依赖关系排序：A 调用 B、B 调用 C，就从末端的 C 开始，再处理 B 和 A；每次只暂停一个模块的日常修改，完成升级和检查后再推进下一个。有循环依赖时要先梳理哪些部分需要一起处理。[原文§六、怎么推到整个项目？](https://xiaolinnote.com/claudecode/playbook/claude_code_modernization.html#%E5%85%AD%E3%80%81%E6%80%8E%E4%B9%88%E6%8E%A8%E5%88%B0%E6%95%B4%E4%B8%AA%E9%A1%B9%E7%9B%AE)
- **G10-33** 防止后来的提交又引入旧版本依赖或不兼容的写法；这样还在开发的同事也清楚哪些地方已经采用了新要求。[原文§六、怎么推到整个项目？](https://xiaolinnote.com/claudecode/playbook/claude_code_modernization.html#%E5%85%AD%E3%80%81%E6%80%8E%E4%B9%88%E6%8E%A8%E5%88%B0%E6%95%B4%E4%B8%AA%E9%A1%B9%E7%9B%AE)
- **G10-34** Claude 要读多少、改多少，检查有多复杂、要补多少测试、已有测试要修多少，都会影响 token 开销；其他团队同时在合并代码，同步这些修改也要花工夫；在受监管的环境里，验证往往比写修改更费 token。[原文§七、这样改一遍，要花多少钱？](https://xiaolinnote.com/claudecode/playbook/claude_code_modernization.html#%E4%B8%83%E3%80%81%E8%BF%99%E6%A0%B7%E6%94%B9%E4%B8%80%E9%81%8D-%E8%A6%81%E8%8A%B1%E5%A4%9A%E5%B0%91%E9%92%B1)
- **G10-35** 试点没覆盖到的情况，比如持续开发带来的同步工作，目前还估不准，后面可能需要追加预算；所以这个估算更适合作为成本下限，不能当成最终报价。[原文§七、这样改一遍，要花多少钱？](https://xiaolinnote.com/claudecode/playbook/claude_code_modernization.html#%E4%B8%83%E3%80%81%E8%BF%99%E6%A0%B7%E6%94%B9%E4%B8%80%E9%81%8D-%E8%A6%81%E8%8A%B1%E5%A4%9A%E5%B0%91%E9%92%B1)
- **G10-36** 翻试点的用量记录看 token 主要花在哪一步；便宜的检查放前面，通过后再跑耗资源的验证；重复性强、数量多且能自动判断对错的任务用 Sonnet 这类兼顾成本和能力的模型，复杂逻辑改写和找漏洞的审查留给更强的模型。[原文§七、这样改一遍，要花多少钱？](https://xiaolinnote.com/claudecode/playbook/claude_code_modernization.html#%E4%B8%83%E3%80%81%E8%BF%99%E6%A0%B7%E6%94%B9%E4%B8%80%E9%81%8D-%E8%A6%81%E8%8A%B1%E5%A4%9A%E5%B0%91%E9%92%B1)
- **G10-37** 不能只看单价：便宜模型反复返工几次，账单可能比强模型一次做完还高；试点时要把重试次数也记下来，再结合用量数据判断哪里值得调整。[原文§七、这样改一遍，要花多少钱？](https://xiaolinnote.com/claudecode/playbook/claude_code_modernization.html#%E4%B8%83%E3%80%81%E8%BF%99%E6%A0%B7%E6%94%B9%E4%B8%80%E9%81%8D-%E8%A6%81%E8%8A%B1%E5%A4%9A%E5%B0%91%E9%92%B1)
- **G10-38** 团队还会留下跑过的工作流、大家认可的验收条件、审核上线规则，以及每次修改的证据记录；把这些整理好，下次升级就能接着用。[原文§最后](https://xiaolinnote.com/claudecode/playbook/claude_code_modernization.html#%E6%9C%80%E5%90%8E)
