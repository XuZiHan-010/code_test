# 图解 Agent：RAG、GraphRAG 与 LightRAG 原文章节摘编

仅依据各题所列的小林面试笔记原文章节整理；本文件只整理原文口径，不作现行规格认证。原文未覆盖的部分明确标注，不使用其他网站补充。整理日期：2026-10-13。

## 1. RAG 总览：流程、切割、重排、Embedding、召回、评估与幻觉

原文：[RAG 是什么？RAG 检索增强面试题万字图解](https://xiaolinnote.com/agent/rag/rag.html)。

- **L1-1** 一是知识有截止日期，训练数据有时间窗口，截止日期之后发生的事它不知道；二是不知道公司的私有数据，产品文档、内部规章、客户信息从未出现在训练集中；三是会幻觉，会非常自信地说出听起来专业但完全编造的内容，这在医疗、法律、金融等需要高准确性的场景中不可接受。[原文§大模型的「知识困局」](https://xiaolinnote.com/agent/rag/rag.html#%E5%A4%A7%E6%A8%A1%E5%9E%8B%E7%9A%84%E3%80%8C%E7%9F%A5%E8%AF%86%E5%9B%B0%E5%B1%80%E3%80%8D)
- **L1-2** RAG 全称 Retrieval-Augmented Generation，即检索增强生成：先从外部知识库中检索出和用户问题相关的资料，再把检索到的资料作为增强上下文和用户问题一起给到大模型，最后大模型基于这些真实资料生成回答。这样知识可以随时更新，私有数据也能用，幻觉也大幅减少。[原文§那怎么办？给大模型「开卷考试」](https://xiaolinnote.com/agent/rag/rag.html#%E9%82%A3%E6%80%8E%E4%B9%88%E5%8A%9E-%E7%BB%99%E5%A4%A7%E6%A8%A1%E5%9E%8B%E3%80%8C%E5%BC%80%E5%8D%B7%E8%80%83%E8%AF%95%E3%80%8D)
- **L1-3** 最早由 Facebook（现 Meta）的研究团队在 2020 年提出，思路是在模型回答之前先从外部文档检索相关内容，再作为参考喂给模型；当时只是学术圈在讨论，真正火起来是 2023 年 ChatGPT 爆红之后，大家发现大模型在实际应用中有很多局限，而 RAG 恰好能解决。[原文§RAG 这个概念是怎么来的？](https://xiaolinnote.com/agent/rag/rag.html#rag-%E8%BF%99%E4%B8%AA%E6%A6%82%E5%BF%B5%E6%98%AF%E6%80%8E%E4%B9%88%E6%9D%A5%E7%9A%84)
- **L1-4** 不是。它解决的是大模型缺乏特定知识的问题，但改变不了大模型的推理能力，模型本身推理不行，给再多资料也没用；也改变不了输出风格，想要特定风格需要微调。更准确的定位是让大模型基于真实、可更新的知识回答问题的技术方案，与微调、Prompt Engineering 是互补而非替代关系。[原文§RAG 不是万能的](https://xiaolinnote.com/agent/rag/rag.html#rag-%E4%B8%8D%E6%98%AF%E4%B8%87%E8%83%BD%E7%9A%84)
- **L1-5** 索引阶段对应考试前把参考书整理好：贴标签、做目录索引、标注重点，是考前完成的准备工作，不需要实时响应；查询阶段对应考试中拿到题目后先理解题意、在参考书里快速找到相关章节、阅读后组织答案，是实时进行的，需要快速响应。[原文§先用一个生活化的例子来理解](https://xiaolinnote.com/agent/rag/rag.html#%E5%85%88%E7%94%A8%E4%B8%80%E4%B8%AA%E7%94%9F%E6%B4%BB%E5%8C%96%E7%9A%84%E4%BE%8B%E5%AD%90%E6%9D%A5%E7%90%86%E8%A7%A3)
- **L1-6** 第一步文档加载，把 PDF、Word、Excel、PPT、HTML、Markdown 等格式统一转成纯文本；第二步文档切割，把长文档切成几百到几千个字符的文本块；第三步向量化，用 Embedding 模型把每个文本块转成向量，语义相近的文本距离也相近；第四步把向量存入向量数据库，供相似度搜索找出最相近的 Top-K 个向量。[原文§索引阶段：把知识「整理好」](https://xiaolinnote.com/agent/rag/rag.html#%E7%B4%A2%E5%BC%95%E9%98%B6%E6%AE%B5-%E6%8A%8A%E7%9F%A5%E8%AF%86%E3%80%8C%E6%95%B4%E7%90%86%E5%A5%BD%E3%80%8D)
- **L1-7** 第一步用同样的 Embedding 模型把用户问题转成向量；第二步拿问题向量去向量数据库做相似度搜索，找到语义最相近的 Top-K 个文本块；第三步把检索出的文本块和用户原始问题拼在一起，构造增强版 Prompt；第四步把增强版 Prompt 发给大模型，由它基于这些参考资料生成回答。[原文§查询阶段：让大模型「翻书找答案」](https://xiaolinnote.com/agent/rag/rag.html#%E6%9F%A5%E8%AF%A2%E9%98%B6%E6%AE%B5-%E8%AE%A9%E5%A4%A7%E6%A8%A1%E5%9E%8B%E3%80%8C%E7%BF%BB%E4%B9%A6%E6%89%BE%E7%AD%94%E6%A1%88%E3%80%8D)
- **L1-8** 索引阶段的文档加载、切割、向量化、入库，加上查询阶段的用户提问、问题向量化、向量检索、构造增强 Prompt、大模型生成回答，这套最基础的流程被称为 Naive RAG（朴素 RAG）；实际生产中为了提升效果，还会加入查询改写、多路召回、重排序（Re-rank）等高级技术。[原文§完整流程一览](https://xiaolinnote.com/agent/rag/rag.html#%E5%AE%8C%E6%95%B4%E6%B5%81%E7%A8%8B%E4%B8%80%E8%A7%88)
- **L1-9** 微调是拿一个已经预训练好的大模型，用自己的数据进一步训练，让它在特定领域或任务上表现更好。全量微调更新模型所有参数，效果最好但成本极高；参数高效微调如 LoRA 只训练一个很小的低秩适配器、不动模型主体，一张消费级显卡就能跑；指令微调用“指令-回答”格式的数据，让模型学会按指令回答。[原文§先搞清楚什么是微调](https://xiaolinnote.com/agent/rag/rag.html#%E5%85%88%E6%90%9E%E6%B8%85%E6%A5%9A%E4%BB%80%E4%B9%88%E6%98%AF%E5%BE%AE%E8%B0%83)
- **L1-10** 微调相当于让模型去上了一门课，知识内化到脑子里，考试时是闭卷，靠记忆回答，记忆可能出错，新知识需要重新训练；RAG 相当于给模型配了一个参考书架，考试时是开卷，可以翻书找答案，参考书可以随时更新，新增知识不需要重新训练模型。[原文§用一个最直观的类比来理解区别](https://xiaolinnote.com/agent/rag/rag.html#%E7%94%A8%E4%B8%80%E4%B8%AA%E6%9C%80%E7%9B%B4%E8%A7%82%E7%9A%84%E7%B1%BB%E6%AF%94%E6%9D%A5%E7%90%86%E8%A7%A3%E5%8C%BA%E5%88%AB)
- **L1-11** 知识更新上，微调要重新训练模型，成本高、周期长，RAG 只需替换知识库里的旧文档并重新索引，模型不用动，几乎可以实时更新；准确性上，微调更多是让模型学到数据的模式和风格，对具体事实的准确性不一定有保障，RAG 的回答基于检索到的真实文档，可追溯、可验证。[原文§核心维度的对比](https://xiaolinnote.com/agent/rag/rag.html#%E6%A0%B8%E5%BF%83%E7%BB%B4%E5%BA%A6%E7%9A%84%E5%AF%B9%E6%AF%94)
- **L1-12** 风格控制是微调的强项，文言文、特定客服话术、模仿某人的说话方式都能在训练中学会，RAG 检索到的内容只是参考，最终怎么组织语言取决于模型本身；成本上微调初始成本高，要准备高质量训练数据、租 GPU，但推理成本相对低，RAG 初始成本低，但每次查询都有检索开销，token 消耗也更多。[原文§核心维度的对比](https://xiaolinnote.com/agent/rag/rag.html#%E6%A0%B8%E5%BF%83%E7%BB%B4%E5%BA%A6%E7%9A%84%E5%AF%B9%E6%AF%94)
- **L1-13** 大多数场景优先选 RAG，尤其是回答必须严格基于特定文档、知识更新频繁、涉及大量私有数据或需要回答可追溯时；微调更适合需要特定风格或格式、需要模型学会某种能力而不只是知识、数据量不大且不常更新又对推理速度要求很高的需求。最成熟的做法是微调加 RAG 结合：先用微调适应领域和风格，再用 RAG 提供实时准确的知识。[原文§什么时候用微调，什么时候用 RAG？](https://xiaolinnote.com/agent/rag/rag.html#%E4%BB%80%E4%B9%88%E6%97%B6%E5%80%99%E7%94%A8%E5%BE%AE%E8%B0%83-%E4%BB%80%E4%B9%88%E6%97%B6%E5%80%99%E7%94%A8-rag)
- **L1-14** 大模型的上下文窗口有限，不可能把知识库所有文档塞进一次请求，必须先检索出最相关的部分；而要精确匹配到相关片段，就得先把文档切成小块。两难在于：切得太小，每块信息太少、可能丢失上下文；切得太大，每块信息太多、检索精度下降，还浪费上下文窗口。[原文§为什么文档切割这么重要？](https://xiaolinnote.com/agent/rag/rag.html#%E4%B8%BA%E4%BB%80%E4%B9%88%E6%96%87%E6%A1%A3%E5%88%87%E5%89%B2%E8%BF%99%E4%B9%88%E9%87%8D%E8%A6%81)
- **L1-15** 它按固定的字符数或 token 数来切，好处是简单、可预测、容易实现，缺点是完全不考虑文本的语义和结构，很可能把一句话或一个段落从中间切开；通常会引入重叠，让相邻两个文本块之间有一段重复内容以保持连贯，但重叠不能解决所有问题，只能算一个补丁。[原文§策略一：固定大小切割](https://xiaolinnote.com/agent/rag/rag.html#%E7%AD%96%E7%95%A5%E4%B8%80-%E5%9B%BA%E5%AE%9A%E5%A4%A7%E5%B0%8F%E5%88%87%E5%89%B2)
- **L1-16** 它维护一个分隔符优先级列表，先用双换行按段落切，块仍太大就用单换行，再用句号等标点，依次往下，直到块的大小符合要求；这样能尽量保持段落、句子的自然完整，不把一句话从中间切开。[原文§策略二：递归字符切割](https://xiaolinnote.com/agent/rag/rag.html#%E7%AD%96%E7%95%A5%E4%BA%8C-%E9%80%92%E5%BD%92%E5%AD%97%E7%AC%A6%E5%88%87%E5%89%B2)
- **L1-17** 按文档自身的结构来切：Markdown 按标题层级切，代码文件按函数、类切，HTML 按标签切，PDF 按页面切；好处是充分尊重文档结构，切出来的块语义完整，缺点是只适用于格式规范的文档，文档结构混乱或没有明显格式标记时就不太好用。[原文§策略三：基于文档结构的切割](https://xiaolinnote.com/agent/rag/rag.html#%E7%AD%96%E7%95%A5%E4%B8%89-%E5%9F%BA%E4%BA%8E%E6%96%87%E6%A1%A3%E7%BB%93%E6%9E%84%E7%9A%84%E5%88%87%E5%89%B2)
- **L1-18** 先把文档按句子切分，用 Embedding 把句子转成向量，计算相邻句子的余弦相似度；相似度高说明在讲同一话题、放进同一块，相似度突然下降的地方就是切割点。[原文§策略四：语义切割](https://xiaolinnote.com/agent/rag/rag.html#%E7%AD%96%E7%95%A5%E5%9B%9B-%E8%AF%AD%E4%B9%89%E5%88%87%E5%89%B2)
- **L1-19** Agent 驱动的切割先用其他方法生成初始文本块，再让 LLM 逐块审视内容是否完整、是否需要与相邻块合并或拆分；它依靠 LLM 对内容的理解，理论上效果最好，但要大量调用 LLM，成本也最高。[原文§策略五：Agent 驱动的智能切割](https://xiaolinnote.com/agent/rag/rag.html#%E7%AD%96%E7%95%A5%E4%BA%94-agent-%E9%A9%B1%E5%8A%A8%E7%9A%84%E6%99%BA%E8%83%BD%E5%88%87%E5%89%B2)
- **L1-20** 起步阶段直接用递归字符切割，块大小 256 到 512 tokens、重叠 10% 到 20%，能覆盖大多数场景；优化阶段，文档有清晰结构（Markdown、HTML）时切换到基于文档结构的切割；进阶阶段尝试语义切割或父子块策略，即存储小块用于精准检索，返回给大模型的是包含上下文的父块。[原文§实战中的建议](https://xiaolinnote.com/agent/rag/rag.html#%E5%AE%9E%E6%88%98%E4%B8%AD%E7%9A%84%E5%BB%BA%E8%AE%AE)
- **L1-21** Bi-Encoder 把查询和文档分别编码成向量再算余弦相似度。一是信息压缩损失，几百字的文本被压缩成一串数字，细微但关键的信息可能丢失；二是缺乏查询意图感知，文档向量在索引阶段就预先算好，不管用户是问事实、做对比还是查步骤，同一篇文档的向量都一样，无法针对具体问题做判断。[原文§先理解一个核心问题](https://xiaolinnote.com/agent/rag/rag.html#%E5%85%88%E7%90%86%E8%A7%A3%E4%B8%80%E4%B8%AA%E6%A0%B8%E5%BF%83%E9%97%AE%E9%A2%98)
- **L1-22** Cross-Encoder 把查询和文档拼成一个输入送进 Transformer，通过自注意力让查询中的每个词与文档中的每个词交互，判断文档是否真正满足查询意图；Bi-Encoder 则是把两者分别编码成向量再算相似度。[原文§Cross-Encoder：让查询和文档「面对面交流」](https://xiaolinnote.com/agent/rag/rag.html#cross-encoder-%E8%AE%A9%E6%9F%A5%E8%AF%A2%E5%92%8C%E6%96%87%E6%A1%A3%E3%80%8C%E9%9D%A2%E5%AF%B9%E9%9D%A2%E4%BA%A4%E6%B5%81%E3%80%8D)
- **L1-23** Bi-Encoder 的文档向量可以预先算好，检索时只需计算查询向量再做相似度搜索；Cross-Encoder 要把查询和每个候选文档拼在一起做一次完整推理，只能等查询到来后算，所以实际只用它对 Top-50 到 Top-100 的候选重排。[原文§为什么不直接用 Cross-Encoder？](https://xiaolinnote.com/agent/rag/rag.html#%E4%B8%BA%E4%BB%80%E4%B9%88%E4%B8%8D%E7%9B%B4%E6%8E%A5%E7%94%A8-cross-encoder)
- **L1-24** 第一阶段用 Bi-Encoder 即向量检索，快速从全部文档中筛出候选，追求的是速度和召回率，宁可多捞一些，也不能漏掉相关的；第二阶段用 Cross-Encoder 即 Re-rank 对候选做精细化重排序，因为候选数量已经很少，较慢的 Cross-Encoder 也能在可接受的时间内完成。[原文§为什么不直接用 Cross-Encoder？](https://xiaolinnote.com/agent/rag/rag.html#%E4%B8%BA%E4%BB%80%E4%B9%88%E4%B8%8D%E7%9B%B4%E6%8E%A5%E7%94%A8-cross-encoder)
- **L1-25** Cohere Rerank 是用得最多的商业方案之一，是 SaaS API 服务，效果好、接入简单，适合预算充足、不想自己部署的项目；BGE-Reranker 是智源研究院出品的开源标杆，中文表现好、可本地部署；ms-marco-MiniLM 是微软的轻量级 Cross-Encoder，体积小、推理快，适合资源有限或对延迟要求高的场景；另外还有支持多语言的 Jina Reranker 和网易有道开源的双语模型 bce-reranker。[原文§主流的 Re-rank 模型有哪些？](https://xiaolinnote.com/agent/rag/rag.html#%E4%B8%BB%E6%B5%81%E7%9A%84-re-rank-%E6%A8%A1%E5%9E%8B%E6%9C%89%E5%93%AA%E4%BA%9B)
- **L1-26** 在需要多跳推理、要串联多个文档的复杂查询场景下，准确率提升可达 40% 到 50%；在简单的事实查询场景下提升相对小一些，大约 18%；在用户表述不太精确的模糊查询场景下，提升约 30% 到 40%。[原文§Re-rank 带来了多大的提升？](https://xiaolinnote.com/agent/rag/rag.html#re-rank-%E5%B8%A6%E6%9D%A5%E4%BA%86%E5%A4%9A%E5%A4%A7%E7%9A%84%E6%8F%90%E5%8D%87)
- **L1-27** 候选数量上，先检索 50 到 100 个候选，再重排到 Top-5 或 Top-10，性价比最高，候选太多会增加耗时，太少又可能漏掉真正相关的文档；不需要所有查询都做 Re-rank，简单事实查询可以设置条件触发，比如只在初排 Top-1 分数低于某个阈值时才启动，复杂查询则建议始终开启。[原文§实战中的建议](https://xiaolinnote.com/agent/rag/rag.html#%E5%AE%9E%E6%88%98%E4%B8%AD%E7%9A%84%E5%BB%BA%E8%AE%AE-1)
- **L1-28** 计算机只能理解数字、不能理解文字；Embedding 把文本转换成高维空间中的数值向量，让语义相近的文本在向量空间中的距离也相近，这样计算机就能通过计算距离来判断语义相似度。[原文§从一个根本问题说起](https://xiaolinnote.com/agent/rag/rag.html#%E4%BB%8E%E4%B8%80%E4%B8%AA%E6%A0%B9%E6%9C%AC%E9%97%AE%E9%A2%98%E8%AF%B4%E8%B5%B7)
- **L1-29** Word2Vec 由 Google 在 2013 年提出，是 Embedding 技术的奠基之作，核心思想来自“上下文相似的词，语义也相似”这一语言学假说；两种训练方式是 CBOW（连续词袋模型），用上下文预测中间的词，和 Skip-Gram（跳字模型），用一个词预测它的上下文。它还能做词语类比，例如国王减男人加女人约等于女王。[原文§第一代：静态词向量时代（2013 年）](https://xiaolinnote.com/agent/rag/rag.html#%E7%AC%AC%E4%B8%80%E4%BB%A3-%E9%9D%99%E6%80%81%E8%AF%8D%E5%90%91%E9%87%8F%E6%97%B6%E4%BB%A3-2013-%E5%B9%B4)
- **L1-30** 它给每个词只生成一个固定的向量，因此无法处理多义词：“苹果”在“我吃了一个苹果”和“苹果发布了新 iPhone”里意思完全不同，向量却是一样的。同一时代的 GloVe（全局向量）和 FastText（支持子词级别的表示）思路也差不多。[原文§第一代：静态词向量时代（2013 年）](https://xiaolinnote.com/agent/rag/rag.html#%E7%AC%AC%E4%B8%80%E4%BB%A3-%E9%9D%99%E6%80%81%E8%AF%8D%E5%90%91%E9%87%8F%E6%97%B6%E4%BB%A3-2013-%E5%B9%B4)
- **L1-31** BERT 由 Google 在 2018 年提出，能根据上下文给同一个词生成不同的向量，从而区分多义词；预训练任务是 MLM（遮盖语言模型），随机遮盖 15% 的词让模型靠上下文预测，和 NSP（下一句预测），判断第二句是否是第一句的下一句。局限是早期版本上下文窗口只有 512 tokens，而且它是通用语言理解模型，并非专为检索设计。[原文§第二代：上下文嵌入时代（2018 年）](https://xiaolinnote.com/agent/rag/rag.html#%E7%AC%AC%E4%BA%8C%E4%BB%A3-%E4%B8%8A%E4%B8%8B%E6%96%87%E5%B5%8C%E5%85%A5%E6%97%B6%E4%BB%A3-2018-%E5%B9%B4)
- **L1-32** 原文称 BGE-M3 一次推理能得到三种输出：稠密向量用于语义检索，经线性变换得到的稀疏向量用于关键词匹配，多向量表示用于更精细的匹配。[原文§第三代：融合与优化时代（2023 年至今）](https://xiaolinnote.com/agent/rag/rag.html#%E7%AC%AC%E4%B8%89%E4%BB%A3-%E8%9E%8D%E5%90%88%E4%B8%8E%E4%BC%98%E5%8C%96%E6%97%B6%E4%BB%A3-2023-%E5%B9%B4%E8%87%B3%E4%BB%8A)
- **L1-33** Multi-Granularity（多粒度）：能处理句子、段落、篇章、文档等不同粒度的输入，最大支持 8192 tokens；Multi-Functionality（多功能）：一站式集成稠密检索、稀疏检索和多向量检索三种能力；Multi-Language（多语言）：支持 100 多种语言。[原文§第三代：融合与优化时代（2023 年至今）](https://xiaolinnote.com/agent/rag/rag.html#%E7%AC%AC%E4%B8%89%E4%BB%A3-%E8%9E%8D%E5%90%88%E4%B8%8E%E4%BC%98%E5%8C%96%E6%97%B6%E4%BB%A3-2023-%E5%B9%B4%E8%87%B3%E4%BB%8A)
- **L1-34** 2023 年 Embedding 进入第三代，要做又长又专的模型，代表是智源研究院的 BGE 系列和 OpenAI 的 text-embedding 系列；后者从早期的 text-embedding-ada-002 到 2024 年发布的 text-embedding-3-small 和 text-embedding-3-large，其中 text-embedding-3-large 的维度高达 3072，在 MTEB 榜单上表现优异。[原文§第三代：融合与优化时代（2023 年至今）](https://xiaolinnote.com/agent/rag/rag.html#%E7%AC%AC%E4%B8%89%E4%BB%A3-%E8%9E%8D%E5%90%88%E4%B8%8E%E4%BC%98%E5%8C%96%E6%97%B6%E4%BB%A3-2023-%E5%B9%B4%E8%87%B3%E4%BB%8A)
- **L1-35** 原文称大模型直接输出的向量质量并不好，所有向量都挤在一起、区分不开，需要经过专门的训练才能用于检索。[原文§第四代：基于大模型的 Embedding（2025 年）](https://xiaolinnote.com/agent/rag/rag.html#%E7%AC%AC%E5%9B%9B%E4%BB%A3-%E5%9F%BA%E4%BA%8E%E5%A4%A7%E6%A8%A1%E5%9E%8B%E7%9A%84-embedding-2025-%E5%B9%B4)
- **L1-36** 前三代的基座都是 BERT 这种编码器模型，第四代的思路是把大模型远超传统编码器的语义理解能力迁移到 Embedding 生成上；代表工作包括 LLM2Vec、Qwen3-Embedding 和字节跳动的 Seed1.5-Embedding，后者 2025 年在 MTEB 榜单上达到了中英文 SOTA 水平。[原文§第四代：基于大模型的 Embedding（2025 年）](https://xiaolinnote.com/agent/rag/rag.html#%E7%AC%AC%E5%9B%9B%E4%BB%A3-%E5%9F%BA%E4%BA%8E%E5%A4%A7%E6%A8%A1%E5%9E%8B%E7%9A%84-embedding-2025-%E5%B9%B4)
- **L1-37** 看榜单，参考最权威的 MTEB 排行榜；中文场景优先选国产模型，BGE、M3E、ACGE 系列在中文下通常优于 OpenAI 的模型；关注上下文窗口，文档很长时选支持长上下文的模型，如 BGE-M3 的 8192 tokens；考虑部署方式，对数据安全有要求、需私有化部署就选开源模型，追求省事就用 API 服务。[原文§怎么选 Embedding 模型？](https://xiaolinnote.com/agent/rag/rag.html#%E6%80%8E%E4%B9%88%E9%80%89-embedding-%E6%A8%A1%E5%9E%8B)
- **L1-38** 假设有 100 万个 1536 维的向量，暴力搜索每次查询都要逐一计算相似度，速度不可接受；向量数据库使用 HNSW、IVF、PQ 等特殊的索引结构，能在海量向量中实现毫秒级的近似最近邻搜索（ANN）。[原文§向量数据库解决什么问题？](https://xiaolinnote.com/agent/rag/rag.html#%E5%90%91%E9%87%8F%E6%95%B0%E6%8D%AE%E5%BA%93%E8%A7%A3%E5%86%B3%E4%BB%80%E4%B9%88%E9%97%AE%E9%A2%98)
- **L1-39** 核心都是用空间换时间、提前构建索引。HNSW 给所有向量建多层导航图，从粗到细层层缩小范围，查询极快、召回率高，是多数向量数据库的默认选择；IVF 先把向量按相似度聚成若干个桶，查询时只搜最可能的几个桶，内存效率高但损失一点召回率；PQ 把向量切成几段做压缩表示，省内存，通常和 IVF 结合使用。[原文§向量数据库的核心原理](https://xiaolinnote.com/agent/rag/rag.html#%E5%90%91%E9%87%8F%E6%95%B0%E6%8D%AE%E5%BA%93%E7%9A%84%E6%A0%B8%E5%BF%83%E5%8E%9F%E7%90%86)
- **L1-40** Milvus 开源、能扛十亿到百亿级向量，索引丰富，但部署维护有门槛，通常需要 Kubernetes；Pinecone 是全托管 SaaS，零运维，但付费且数据存在第三方；Weaviate 原生支持混合检索并内置 Embedding 集成，大规模性能弱于 Milvus；Chroma 轻量简单，适合原型验证，不支持分布式、没有安全机制；Qdrant 用 Rust 写成，单机性能强，分布式方案相对较新。[原文§主流向量数据库对比](https://xiaolinnote.com/agent/rag/rag.html#%E4%B8%BB%E6%B5%81%E5%90%91%E9%87%8F%E6%95%B0%E6%8D%AE%E5%BA%93%E5%AF%B9%E6%AF%94)
- **L1-41** 快速做 POC 用 Chroma；中小规模生产应用，预算充足可选 Pinecone，需要私有化部署可选 Weaviate；数据量上亿的大规模企业级应用基本要选 Milvus；对性能有极致要求、想自建又不想用那么重的方案可试 Qdrant；已经在用 PostgreSQL 或 Elasticsearch 的项目，用 pgvector 插件或 ES 的向量搜索也是务实的选择，中小规模完全够用。[原文§选型建议](https://xiaolinnote.com/agent/rag/rag.html#%E9%80%89%E5%9E%8B%E5%BB%BA%E8%AE%AE)
- **L1-42** 向量检索擅长捕捉语义相似性，例如“怎么修改密码”能检索出“重置登录凭据”，但在精确匹配上有短板：搜“iPhone 15 Pro Max 256GB”可能把“iPhone 14 Pro Max 512GB”也搜出来，因为两个型号语义太像；搜内部产品编号“PRD-2024-089”这类没有语义的编号，也很可能匹配不上。[原文§单路召回的局限性](https://xiaolinnote.com/agent/rag/rag.html#%E5%8D%95%E8%B7%AF%E5%8F%AC%E5%9B%9E%E7%9A%84%E5%B1%80%E9%99%90%E6%80%A7)
- **L1-43** 第一路向量检索（Dense Retrieval），用稠密向量做相似度搜索，擅长语义匹配，是主力召回通道；第二路关键词检索（Sparse Retrieval/BM25），基于词频和文档频率计算相关性，擅长精确关键词匹配，对专有名词、产品编号、人名有天然优势；第三路知识图谱检索（可选），用图查询召回，擅长实体关系推理。[原文§多路召回的核心思想](https://xiaolinnote.com/agent/rag/rag.html#%E5%A4%9A%E8%B7%AF%E5%8F%AC%E5%9B%9E%E7%9A%84%E6%A0%B8%E5%BF%83%E6%80%9D%E6%83%B3)
- **L1-44** RRF 即倒数排名融合（Reciprocal Rank Fusion），是多路召回中最常用的融合方法，用来把各路结果合并去重并综合排序；它不看每个文档的绝对分数，只看它在各路召回中的排名，排名越靠前得分越高，被越多路召回命中的文档综合得分也越高。[原文§多路召回的核心思想](https://xiaolinnote.com/agent/rag/rag.html#%E5%A4%9A%E8%B7%AF%E5%8F%AC%E5%9B%9E%E7%9A%84%E6%A0%B8%E5%BF%83%E6%80%9D%E6%83%B3)
- **L1-45** 用户提问后同时发起两路检索：向量检索把问题转成向量，在向量数据库中搜 Top-K 个相似文档；BM25 检索把问题分词后在倒排索引中搜 Top-K 个相关文档；再用 RRF 合并两路结果，可选做 Re-rank 精排，取最终 Top-N 个文档送入大模型。效果通常比单路检索好 10% 到 30%，需要精确匹配关键词时提升更明显。[原文§混合检索的具体实现](https://xiaolinnote.com/agent/rag/rag.html#%E6%B7%B7%E5%90%88%E6%A3%80%E7%B4%A2%E7%9A%84%E5%85%B7%E4%BD%93%E5%AE%9E%E7%8E%B0)
- **L1-46** 查询改写是在检索前用 LLM 把原始问题改写成更适合检索的形式，可改写成多个查询分别检索再合并；HyDE 是先让 LLM 根据问题生成一个假设性的答案文档，再用这个假设文档的向量去检索，因为它在表述上更接近真实的答案文档；多查询扩展是把一个问题用 LLM 改写成多个不同角度的子问题，分别检索后合并结果。[原文§还有哪些高级召回策略？](https://xiaolinnote.com/agent/rag/rag.html#%E8%BF%98%E6%9C%89%E5%93%AA%E4%BA%9B%E9%AB%98%E7%BA%A7%E5%8F%AC%E5%9B%9E%E7%AD%96%E7%95%A5)
- **L1-47** RAG 系统由检索器和生成器两大组件组成，检索器负责从知识库找到相关文档，生成器负责基于这些文档生成回答；所以不能只看最终回答好不好，还要分别评估检索质量和生成质量，才能定位问题出在哪一环，就像菜不好吃要分清是食材采购的问题还是厨师的问题。[原文§为什么评估 RAG 比评估普通 LLM 更复杂？](https://xiaolinnote.com/agent/rag/rag.html#%E4%B8%BA%E4%BB%80%E4%B9%88%E8%AF%84%E4%BC%B0-rag-%E6%AF%94%E8%AF%84%E4%BC%B0%E6%99%AE%E9%80%9A-llm-%E6%9B%B4%E5%A4%8D%E6%9D%82)
- **L1-48** 按原文的定义，Recall@5 是 Top-5 里找到的相关文档占全部相关文档的比例，即 3/10，也就是 30%；Precision@5 是返回结果中相关文档所占的比例，即 3/5，也就是 60%。[原文§检索质量的评估指标](https://xiaolinnote.com/agent/rag/rag.html#%E6%A3%80%E7%B4%A2%E8%B4%A8%E9%87%8F%E7%9A%84%E8%AF%84%E4%BC%B0%E6%8C%87%E6%A0%87)
- **L1-49** NDCG 是更综合的指标：除了找得全不全、准不准，还看排得对不对，即高度相关的文档是否排在前面、部分相关的是否排在后面。[原文§检索质量的评估指标](https://xiaolinnote.com/agent/rag/rag.html#%E6%A3%80%E7%B4%A2%E8%B4%A8%E9%87%8F%E7%9A%84%E8%AF%84%E4%BC%B0%E6%8C%87%E6%A0%87)
- **L1-50** MAP 关注所有相关文档的整体排序质量，MRR 关注第一个相关文档排在第几位。[原文§检索质量的评估指标](https://xiaolinnote.com/agent/rag/rag.html#%E6%A3%80%E7%B4%A2%E8%B4%A8%E9%87%8F%E7%9A%84%E8%AF%84%E4%BC%B0%E6%8C%87%E6%A0%87)
- **L1-51** Faithfulness（忠实度）最重要，衡量回答是否忠实于检索到的文档、有没有编造文档中不存在的信息；Answer Relevance（答案相关性）衡量回答是否真正回答了用户的问题、有没有跑题；Context Relevance（上下文相关性）衡量检索到的文档是否和用户问题相关。[原文§生成质量的评估指标](https://xiaolinnote.com/agent/rag/rag.html#%E7%94%9F%E6%88%90%E8%B4%A8%E9%87%8F%E7%9A%84%E8%AF%84%E4%BC%B0%E6%8C%87%E6%A0%87)
- **L1-52** 先把生成的回答拆分成一个个独立的陈述，然后检查每个陈述是否能从检索到的文档中找到支撑；如果有 10 个陈述，8 个能找到支撑、2 个是编造的，忠实度就是 0.8。[原文§生成质量的评估指标](https://xiaolinnote.com/agent/rag/rag.html#%E7%94%9F%E6%88%90%E8%B4%A8%E9%87%8F%E7%9A%84%E8%AF%84%E4%BC%B0%E6%8C%87%E6%A0%87)
- **L1-53** RAGAS 是目前 RAG 评估领域最流行的开源框架，核心思路是用一个更强大的 LLM（如 GPT-4）作为裁判，自动化评估 RAG 系统的输出质量；使用时准备一个包含 question（问题）、contexts（检索到的文档）、answer（模型生成的回答）、ground_truth（标准答案）的数据集，再调用 evaluate 函数。[原文§RAGAS：RAG 评估的事实标准](https://xiaolinnote.com/agent/rag/rag.html#ragas-rag-%E8%AF%84%E4%BC%B0%E7%9A%84%E4%BA%8B%E5%AE%9E%E6%A0%87%E5%87%86)
- **L1-54** DeepEval 把 RAG 评估融入单元测试框架，适合工程化团队；TruLens 提供 RAG 应用的深度可观测性和诊断能力；ARES 用 LLM 生成合成评估数据，解决人工标注数据不足的问题。[原文§RAGAS：RAG 评估的事实标准](https://xiaolinnote.com/agent/rag/rag.html#ragas-rag-%E8%AF%84%E4%BC%B0%E7%9A%84%E4%BA%8B%E5%AE%9E%E6%A0%87%E5%87%86)
- **L1-55** 先建基线再做优化，之后每次改动都对比基线；测试数据要有代表性，包含简单事实查询、复杂推理问题、多跳问题、模糊问题等类型；定期评估、持续监控，因为效果会随知识库更新和模型版本变化而波动；把评估自动化，融入 CI/CD 流程，每次更新自动跑一轮评估，效果下降及时报警。[原文§评估的最佳实践](https://xiaolinnote.com/agent/rag/rag.html#%E8%AF%84%E4%BC%B0%E7%9A%84%E6%9C%80%E4%BD%B3%E5%AE%9E%E8%B7%B5)
- **L1-56** 幻觉是大模型自信地说出一些听起来很专业但实际上是编造的内容；它不等于错误，模型说“我不知道这个问题的答案”不叫幻觉，幻觉是模型不知道却假装知道，用流畅、自信的语言编造错误信息。[原文§什么是大模型幻觉？](https://xiaolinnote.com/agent/rag/rag.html#%E4%BB%80%E4%B9%88%E6%98%AF%E5%A4%A7%E6%A8%A1%E5%9E%8B%E5%B9%BB%E8%A7%89)
- **L1-57** 分为两大类。事实性幻觉指生成内容与客观事实不符，又分为内在幻觉（生成内容与输入的上下文信息矛盾）和外在幻觉（生成内容无法从输入上下文或任何已知知识中验证）；忠实性幻觉在 RAG 场景中更常见，指模型拿到了正确的检索文档，却在生成时偏离文档内容、加入文档中没有的信息或曲解文档含义。[原文§幻觉有哪些类型？](https://xiaolinnote.com/agent/rag/rag.html#%E5%B9%BB%E8%A7%89%E6%9C%89%E5%93%AA%E4%BA%9B%E7%B1%BB%E5%9E%8B)
- **L1-58** 数据层面，训练数据可能包含错误、偏见或过时的知识，而且生日、具体时间这类没有规律的事实只能靠记住；训练层面，训练目标是预测下一个 token，追求流畅连贯而非正确，主流评估方式里不答和答错都是零分，鼓励模型蒙答案；推理层面，用户问题若包含错误前提，模型往往顺着错误前提继续编造。[原文§幻觉是怎么产生的？](https://xiaolinnote.com/agent/rag/rag.html#%E5%B9%BB%E8%A7%89%E6%98%AF%E6%80%8E%E4%B9%88%E4%BA%A7%E7%94%9F%E7%9A%84)
- **L1-59** 注入真实知识，模型基于真实存在的资料生成回答，研究表明能将事实性幻觉降低 20% 到 40%；注意力机制偏向，Prompt 中包含检索文档时约 70% 到 80% 的注意力集中在检索片段；可追溯可验证，回答能追溯到具体文档来源。但它不能完全消除幻觉，检索到错误文档、模型曲解文档或做越界推断时幻觉依然会发生。[原文§RAG 是怎么降低幻觉的？](https://xiaolinnote.com/agent/rag/rag.html#rag-%E6%98%AF%E6%80%8E%E4%B9%88%E9%99%8D%E4%BD%8E%E5%B9%BB%E8%A7%89%E7%9A%84)
- **L1-60** 明确要求只能基于给定资料回答，资料中没有相关信息就直接说无法回答，不要自行推测；要求在每个关键陈述后标注出处，让模型更谨慎也方便人工核查；允许并鼓励模型在不确定时说“我不确定”；要求分步回答，先列出确定的事实，再基于事实推理并标注哪些是推理部分。[原文§方法一：Prompt 工程约束](https://xiaolinnote.com/agent/rag/rag.html#%E6%96%B9%E6%B3%95%E4%B8%80-prompt-%E5%B7%A5%E7%A8%8B%E7%BA%A6%E6%9D%9F)
- **L1-61** 输出验证是事后检查，在回答到达用户之前加一层验证：用另一个模型交叉验证，逐一检查每个事实陈述能否在参考资料中找到支撑，这也叫 LLM-as-Judge，是自动化幻觉检测最主流的方式；用规则引擎校验数字、日期、人名、金额等关键信息；基于一致性的多次采样，同一问题生成多个回答，关键事实说法不一致就很可能是幻觉。[原文§方法二：输出验证（独立校验）](https://xiaolinnote.com/agent/rag/rag.html#%E6%96%B9%E6%B3%95%E4%BA%8C-%E8%BE%93%E5%87%BA%E9%AA%8C%E8%AF%81-%E7%8B%AC%E7%AB%8B%E6%A0%A1%E9%AA%8C)
- **L1-62** 通用大模型在医疗、法律、金融等领域的知识基础可能比较薄弱，容易编造内容，微调相当于补一门专业课。做法一是有监督微调（SFT），用人工审核过的“问题-正确答案”对训练；做法二是在 RLHF 阶段奖励说真话或坦率承认不知道。微调成本较高，通常在 Prompt 工程和 RAG 都试过、效果仍不够时再考虑。[原文§方法三：领域微调](https://xiaolinnote.com/agent/rag/rag.html#%E6%96%B9%E6%B3%95%E4%B8%89-%E9%A2%86%E5%9F%9F%E5%BE%AE%E8%B0%83)
- **L1-63** 研究指出当前的 RLHF 机制系统性地鼓励模型在不确定时猜测，因为“蒙对得分、不答零分”；如果在 RLHF 中改为“蒙错扣分，不答零分”，模型就会学会在不确定时说“我不知道”。[原文§方法三：领域微调](https://xiaolinnote.com/agent/rag/rag.html#%E6%96%B9%E6%B3%95%E4%B8%89-%E9%A2%86%E5%9F%9F%E5%BE%AE%E8%B0%83)
- **L1-64** 把 token 概率当作置信度信号：很多 token 的概率都很低，说明模型对回答不太确定，幻觉风险高；可以用 token 概率的平均值或最小值来估计模型对整个回答的置信度。[原文§方法四：不确定性量化（UQ）](https://xiaolinnote.com/agent/rag/rag.html#%E6%96%B9%E6%B3%95%E5%9B%9B-%E4%B8%8D%E7%A1%AE%E5%AE%9A%E6%80%A7%E9%87%8F%E5%8C%96-uq)
- **L1-65** 原文称这类方法需要白盒访问模型的内部状态，所以只能用于自己部署的开源模型；它通过监控隐藏状态的激活模式是锐利还是模糊来检测幻觉。[原文§方法四：不确定性量化（UQ）](https://xiaolinnote.com/agent/rag/rag.html#%E6%96%B9%E6%B3%95%E5%9B%9B-%E4%B8%8D%E7%A1%AE%E5%AE%9A%E6%80%A7%E9%87%8F%E5%8C%96-uq)
- **L1-66** 核心是让模型对输出给出置信度分数，分数低意味着可能存在幻觉。路线有三条：基于 token 概率，基于多次采样的一致性，基于模型内部状态。检测到置信度很低时，系统可以触发人工审核、拒答，或者降低回答的确定性，加上“根据现有信息推测，但不确定是否准确”之类的声明。[原文§方法四：不确定性量化（UQ）](https://xiaolinnote.com/agent/rag/rag.html#%E6%96%B9%E6%B3%95%E5%9B%9B-%E4%B8%8D%E7%A1%AE%E5%AE%9A%E6%80%A7%E9%87%8F%E5%8C%96-uq)
- **L1-67** 传统 RAG 只能检索文档片段，对需要全局理解的问题效果不好。GraphRAG 由微软提出，先让 LLM 从文档中提取实体和关系构建知识图谱，再基于图谱做检索和回答，更适合需要推理的问题；LightRAG 是 GraphRAG 的轻量版，通过融合图增强文本索引和双层检索范式，解决了 token 开销大、动态更新成本高的问题。[原文§方法五：GraphRAG 和 LightRAG](https://xiaolinnote.com/agent/rag/rag.html#%E6%96%B9%E6%B3%95%E4%BA%94-graphrag-%E5%92%8C-lightrag)
- **L1-68** 核心原则是分层设防、按需组合：第一道 Prompt 工程约束，零成本、立即生效，所有场景都应该做；第二道 RAG 检索增强，中等成本，是需要准确知识场景的标配；第三道输出验证，增加延迟和成本，但在医疗、法律、金融等高风险场景不可或缺；第四道领域微调加不确定性量化，成本最高，适合对准确性要求极高的场景。[原文§实际项目中的组合策略](https://xiaolinnote.com/agent/rag/rag.html#%E5%AE%9E%E9%99%85%E9%A1%B9%E7%9B%AE%E4%B8%AD%E7%9A%84%E7%BB%84%E5%90%88%E7%AD%96%E7%95%A5)
- **L1-69** 高风险场景（医疗诊断、法律建议、金融决策）必须 RAG 加人工审核加明确免责声明，输出验证必备；中风险场景（客户服务、内容生产、代码辅助）用 Prompt 约束、RAG、输出验证和置信度阈值；低风险场景（头脑风暴、草稿起草、创意生成）做基础 Prompt 优化即可。核心原则是把幻觉当作工程问题而非模型缺陷，用系统设计约束 AI 的行为边界。[原文§按风险等级分层管控](https://xiaolinnote.com/agent/rag/rag.html#%E6%8C%89%E9%A3%8E%E9%99%A9%E7%AD%89%E7%BA%A7%E5%88%86%E5%B1%82%E7%AE%A1%E6%8E%A7)

### 补充考点

- **L1-70** 优化阶段，文档有清晰结构（Markdown、HTML）时切换到基于文档结构的切割；进阶阶段尝试语义切割或父子块策略。父子块策略是存储小块用于精准检索，返回给大模型的是包含上下文的父块。[原文§实战中的建议](https://xiaolinnote.com/agent/rag/rag.html#%E5%AE%9E%E6%88%98%E4%B8%AD%E7%9A%84%E5%BB%BA%E8%AE%AE)
- **L1-71** 原文介绍的是取 BERT 输出的 [CLS] token 的向量作为整段文本的向量表示。（这是原文对普通 BERT 的历史介绍，不是 RAG 检索的通用推荐：未经相似度训练的 BERT，其 [CLS] 向量在语义相似度上效果很差；实际检索应使用经过检索/相似度训练的 embedding 模型，pooling 取哪个位置取决于模型，例如 Sentence-BERT 默认用 mean pooling。）[原文§第二代：上下文嵌入时代（2018 年）](https://xiaolinnote.com/agent/rag/rag.html#%E7%AC%AC%E4%BA%8C%E4%BB%A3-%E4%B8%8A%E4%B8%8B%E6%96%87%E5%B5%8C%E5%85%A5%E6%97%B6%E4%BB%A3-2018-%E5%B9%B4)[核对来源：Sentence-BERT 论文](https://aclanthology.org/D19-1410.pdf)
- **L1-72** Weaviate 原生支持混合检索并内置 Embedding 集成，大规模性能弱于 Milvus；Qdrant 用 Rust 写成，单机性能强，分布式方案相对较新。[原文§主流向量数据库对比](https://xiaolinnote.com/agent/rag/rag.html#%E4%B8%BB%E6%B5%81%E5%90%91%E9%87%8F%E6%95%B0%E6%8D%AE%E5%BA%93%E5%AF%B9%E6%AF%94)
- **L1-73** 用 pgvector 插件或 ES 的向量搜索也是务实的选择，中小规模完全够用。[原文§选型建议](https://xiaolinnote.com/agent/rag/rag.html#%E9%80%89%E5%9E%8B%E5%BB%BA%E8%AE%AE)
- **L1-74** 查询改写是在检索前用 LLM 把原始问题改写成更适合检索的形式，可以改写成多个查询分别检索再合并；多查询扩展是把一个问题用 LLM 改写成多个不同角度的子问题，分别检索后合并结果。[原文§还有哪些高级召回策略？](https://xiaolinnote.com/agent/rag/rag.html#%E8%BF%98%E6%9C%89%E5%93%AA%E4%BA%9B%E9%AB%98%E7%BA%A7%E5%8F%AC%E5%9B%9E%E7%AD%96%E7%95%A5)

## 2. GraphRAG 与 LightRAG：原理、对比与选型

原文：[GraphRAG 和 LightRAG 详解：原理、对比与选型](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html)。

- **L2-1** 需要“A 关联到 B、B 关联到 C，再从 A 推到 C”的问题叫多跳推理（Multi-hop Reasoning），例如“爱因斯坦的导师的导师是谁”；信息分散在多个文档里，传统 RAG 只能把检索到的文本块一股脑扔给大模型，没有机制把几组结果做交集或做链式推理，答案要么不完整，要么瞎编。[原文§痛点一：跨文档的「多跳推理」干不了](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html#%E7%97%9B%E7%82%B9%E4%B8%80-%E8%B7%A8%E6%96%87%E6%A1%A3%E7%9A%84%E3%80%8C%E5%A4%9A%E8%B7%B3%E6%8E%A8%E7%90%86%E3%80%8D%E5%B9%B2%E4%B8%8D%E4%BA%86)
- **L2-2** 全局性问题的答案不在某一个文本块里，需要通读所有文档、归纳总结才能得出，例如“这本小说的主题思想是什么”；传统 RAG 的本质是检索，只会找 Top-K 个最像问题的文本块，拿到的多是零散片段。微软 GraphRAG 论文把它叫做 Query-Focused Summarization（查询聚焦的摘要）问题，本质是全局归纳任务而非检索任务。[原文§痛点二：全局性问题，它根本答不上](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html#%E7%97%9B%E7%82%B9%E4%BA%8C-%E5%85%A8%E5%B1%80%E6%80%A7%E9%97%AE%E9%A2%98-%E5%AE%83%E6%A0%B9%E6%9C%AC%E7%AD%94%E4%B8%8D%E4%B8%8A)
- **L2-3** 一段完整的论述可能横跨几个段落，按字符数切会把完整的观点拦腰斩开，检索时只召回上半段，答案就不完整；例如“卡托普利属于 ACEI 类药物，但严重肾功能不全者禁用”被切到两个块里，大模型拿到后可能错误地说成“卡托普利属于禁忌症药物”。[原文§痛点三：切块带来的「语义断裂」](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html#%E7%97%9B%E7%82%B9%E4%B8%89-%E5%88%87%E5%9D%97%E5%B8%A6%E6%9D%A5%E7%9A%84%E3%80%8C%E8%AF%AD%E4%B9%89%E6%96%AD%E8%A3%82%E3%80%8D)
- **L2-4** 根本原因是它不理解关系：向量检索在找长得像的句子上很强，但没有机制去理解两个实体之间是什么关系、两条信息之间有没有因果链。所以只是找某条具体事实时传统 RAG 完全够用，一旦问题涉及关系、推理、全局归纳，它就力不从心。[原文§痛点背后的根本原因：它不「理解关系」](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html#%E7%97%9B%E7%82%B9%E8%83%8C%E5%90%8E%E7%9A%84%E6%A0%B9%E6%9C%AC%E5%8E%9F%E5%9B%A0-%E5%AE%83%E4%B8%8D%E3%80%8C%E7%90%86%E8%A7%A3%E5%85%B3%E7%B3%BB%E3%80%8D)
- **L2-5** 原文称 GraphRAG 有两层含义：狭义指微软研究院 2024 年 4 月发布的论文和配套开源项目，广义指所有基于知识图谱做 RAG 的方法，业界还有很多变种；文章后面如无特别说明，指的都是微软这一套。[原文§先搞清楚 GraphRAG 到底是什么](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html#%E5%85%88%E6%90%9E%E6%B8%85%E6%A5%9A-graphrag-%E5%88%B0%E5%BA%95%E6%98%AF%E4%BB%80%E4%B9%88)
- **L2-6** 传统 RAG 的知识以离散的文本块存储，每个文本块相互独立，块和块之间没有联系；GraphRAG 的知识以图的形式存储，文档里的实体和它们之间的关系被显式提取出来，形成结构化的关系网络。例如“张三创立了 A 公司，李四是 A 公司的 CTO”，传统 RAG 把这段话整体存成一个文本块，GraphRAG 则表示成节点和边，每个节点是谁、每条边是什么关系，都是明确的、可追溯的。[原文§传统 RAG 和 GraphRAG 的核心差异是什么？](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html#%E4%BC%A0%E7%BB%9F-rag-%E5%92%8C-graphrag-%E7%9A%84%E6%A0%B8%E5%BF%83%E5%B7%AE%E5%BC%82%E6%98%AF%E4%BB%80%E4%B9%88)
- **L2-7** 多跳查询变成图遍历：从一个节点出发，沿着边逐层筛选相连的节点，图天然擅长这种顺藤摸瓜，GraphRAG 在 HotpotQA 这类多跳问答任务上的 F1 比传统 RAG 高 5% 以上；实体和关系已提前抽出，分散在原文两处的信息能通过同一个实体节点连起来，检索时不会丢掉因果关系。[原文§为什么要搞成图？这么做到底好在哪？](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html#%E4%B8%BA%E4%BB%80%E4%B9%88%E8%A6%81%E6%90%9E%E6%88%90%E5%9B%BE-%E8%BF%99%E4%B9%88%E5%81%9A%E5%88%B0%E5%BA%95%E5%A5%BD%E5%9C%A8%E5%93%AA)
- **L2-8** 社区是图里互相抱团、关系特别密切的一群节点，例如《三国演义》里刘关张是一个小社区、曹操集团是一个社区；社区内部的关系非常紧密，社区之间的连接比较稀疏。[原文§为什么要搞成图？这么做到底好在哪？](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html#%E4%B8%BA%E4%BB%80%E4%B9%88%E8%A6%81%E6%90%9E%E6%88%90%E5%9B%BE-%E8%BF%99%E4%B9%88%E5%81%9A%E5%88%B0%E5%BA%95%E5%A5%BD%E5%9C%A8%E5%93%AA)
- **L2-9** 文档先切成 Text Unit；LLM 从每个块里抽取实体和关系；同一实体或关系的多处描述再汇总成综合描述；然后在实体关系图上用 Leiden 算法划出层次化社区；最后为每个社区生成 Community Report。每一步都以上一步的产物为输入。[原文§索引阶段：5 步把文档变成知识图谱](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html#%E7%B4%A2%E5%BC%95%E9%98%B6%E6%AE%B5-5-%E6%AD%A5%E6%8A%8A%E6%96%87%E6%A1%A3%E5%8F%98%E6%88%90%E7%9F%A5%E8%AF%86%E5%9B%BE%E8%B0%B1)
- **L2-10** 同一实体在多个文本块里被抽到的描述各不相同，GraphRAG 把它们汇总起来，让 LLM 合成一段更完整的综合描述；这段描述向量化后存入向量数据库，供 Local Search 定位入口实体。[原文§索引阶段：5 步把文档变成知识图谱](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html#%E7%B4%A2%E5%BC%95%E9%98%B6%E6%AE%B5-5-%E6%AD%A5%E6%8A%8A%E6%96%87%E6%A1%A3%E5%8F%98%E6%88%90%E7%9F%A5%E8%AF%86%E5%9B%BE%E8%B0%B1)
- **L2-11** 把一个社区内的全部实体、关系和可选的 claim 交给 LLM，由它生成这个社区的报告。[原文§索引阶段：5 步把文档变成知识图谱](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html#%E7%B4%A2%E5%BC%95%E9%98%B6%E6%AE%B5-5-%E6%AD%A5%E6%8A%8A%E6%96%87%E6%A1%A3%E5%8F%98%E6%88%90%E7%9F%A5%E8%AF%86%E5%9B%BE%E8%B0%B1)

- **L2-38** 适合有明显时间属性的数据，如新闻、月度报告、季度财报：按时间段分开建图，每个季度一张图；优点是每张图相对小、更新隔离性好，老数据不受新数据影响。[原文§业界应对增量问题的几种思路](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html#%E4%B8%9A%E7%95%8C%E5%BA%94%E5%AF%B9%E5%A2%9E%E9%87%8F%E9%97%AE%E9%A2%98%E7%9A%84%E5%87%A0%E7%A7%8D%E6%80%9D%E8%B7%AF)
- **L2-39** LightRAG 由香港大学（HKU）数据智能实验室的团队在 2024 年 10 月发布，论文先发在 arXiv 上，后来被 EMNLP 2025 的 Findings Track 接收，项目开源在 GitHub 的 HKUDS/LightRAG；它是为解决 GraphRAG 痛点而生的轻量化、工程友好型替代方案。[原文§LightRAG 的身世背景](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html#lightrag-%E7%9A%84%E8%BA%AB%E4%B8%96%E8%83%8C%E6%99%AF)
- **L2-40** 一是缺乏动态更新能力，很难高效处理新信息的加入，数据一变整个图谱就得大改；二是全局查询的暴力搜索太低效，GraphRAG 的 Global Search 用 Map-Reduce 遍历所有社区摘要，在大规模语料上又慢又贵。LightRAG 的目标就是同时解决这两个问题。[原文§为什么会有 LightRAG？直接原因就是 GraphRAG 的痛](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html#%E4%B8%BA%E4%BB%80%E4%B9%88%E4%BC%9A%E6%9C%89-lightrag-%E7%9B%B4%E6%8E%A5%E5%8E%9F%E5%9B%A0%E5%B0%B1%E6%98%AF-graphrag-%E7%9A%84%E7%97%9B)
- **L2-41** 它只保留实体节点和关系边，不做 Leiden 社区检测，也不生成社区摘要；全局性问题改为在查询时把问题拆成低层和高层两组关键词，分别检索实体和关系，再把两类信息组装成上下文。[原文§LightRAG 的三个核心创新](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html#lightrag-%E7%9A%84%E4%B8%89%E4%B8%AA%E6%A0%B8%E5%BF%83%E5%88%9B%E6%96%B0)
- **L2-42** 主要牺牲了全局深度洞察：GraphRAG 的社区摘要是经过 LLM 加工、具有层次抽象的全局知识视图，对需要深度宏观归纳的问题能提供更好的洞察；LightRAG 的双层检索本质上是基于查询现场拼凑全局视角，面对极其复杂的全局归纳问题，深度可能不如 GraphRAG。[原文§LightRAG 的代价是什么？](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html#lightrag-%E7%9A%84%E4%BB%A3%E4%BB%B7%E6%98%AF%E4%BB%80%E4%B9%88)
- **L2-43** Key 是便于检索匹配的短语，例如实体名或关系关键词，查询关键词靠它快速定位；Value 是一段详细的描述信息，命中后直接取出来组装上下文。[原文§索引阶段：轻量化的图构建](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html#%E7%B4%A2%E5%BC%95%E9%98%B6%E6%AE%B5-%E8%BD%BB%E9%87%8F%E5%8C%96%E7%9A%84%E5%9B%BE%E6%9E%84%E5%BB%BA)
- **L2-44** 关系关键词描述的是一条关系所代表的主题或概念，例如张三创立 A 公司对应创业、企业创立；它是高层检索命中相关关系的钥匙，其向量会存入向量库。[原文§索引阶段：轻量化的图构建](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html#%E7%B4%A2%E5%BC%95%E9%98%B6%E6%AE%B5-%E8%BD%BB%E9%87%8F%E5%8C%96%E7%9A%84%E5%9B%BE%E6%9E%84%E5%BB%BA)
- **L2-45** 不是。原文虽说键值设计省掉了复杂的嵌入匹配和 chunk 遍历，但同一节又说明索引后还有一份向量数据库，存着实体描述、关系描述和关系关键词的向量，查询关键词正是去向量库里检索的。[原文§索引阶段：轻量化的图构建](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html#%E7%B4%A2%E5%BC%95%E9%98%B6%E6%AE%B5-%E8%BD%BB%E9%87%8F%E5%8C%96%E7%9A%84%E5%9B%BE%E6%9E%84%E5%BB%BA)
- **L2-46** LightRAG 的去重比较朴素，主要基于名称匹配：同名实体合并成一个节点，但不处理张三与 Zhang San 这类同人不同名的情况，语义相近的实体会保留为多个节点。[原文§索引阶段：轻量化的图构建](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html#%E7%B4%A2%E5%BC%95%E9%98%B6%E6%AE%B5-%E8%BD%BB%E9%87%8F%E5%8C%96%E7%9A%84%E5%9B%BE%E6%9E%84%E5%BB%BA)
- **L2-47** 知识图谱默认用 NetworkX 作存储后端；实体和关系用 LLM 抽取，它们的描述还要向量化后存入向量库。[原文§索引阶段：轻量化的图构建](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html#%E7%B4%A2%E5%BC%95%E9%98%B6%E6%AE%B5-%E8%BD%BB%E9%87%8F%E5%8C%96%E7%9A%84%E5%9B%BE%E6%9E%84%E5%BB%BA)
- **L2-48** 低层关键词盯着具体的实体、细节和术语，例如贸易协定、关税、货币汇率；高层关键词关注更抽象的主题和总体概念，例如国际贸易、全球经济稳定、经济影响。[原文§查询阶段：双层检索的精髓](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html#%E6%9F%A5%E8%AF%A2%E9%98%B6%E6%AE%B5-%E5%8F%8C%E5%B1%82%E6%A3%80%E7%B4%A2%E7%9A%84%E7%B2%BE%E9%AB%93)
- **L2-49** 用低层关键词去向量库里搜实体节点，再从这些入口实体出发，在图上扩展到它们的一跳邻居，收集相关的关系和描述。[原文§查询阶段：双层检索的精髓](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html#%E6%9F%A5%E8%AF%A2%E9%98%B6%E6%AE%B5-%E5%8F%8C%E5%B1%82%E6%A3%80%E7%B4%A2%E7%9A%84%E7%B2%BE%E9%AB%93)
- **L2-50** 用高层关键词去向量库里搜关系边，再从这些关系出发，聚合它们涉及的实体和更高层的语义。[原文§查询阶段：双层检索的精髓](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html#%E6%9F%A5%E8%AF%A2%E9%98%B6%E6%AE%B5-%E5%8F%8C%E5%B1%82%E6%A3%80%E7%B4%A2%E7%9A%84%E7%B2%BE%E9%AB%93)
- **L2-51** 组装上下文时会控制总 token 数，优先保留相关性最高的内容。[原文§查询阶段：双层检索的精髓](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html#%E6%9F%A5%E8%AF%A2%E9%98%B6%E6%AE%B5-%E5%8F%8C%E5%B1%82%E6%A3%80%E7%B4%A2%E7%9A%84%E7%B2%BE%E9%AB%93)
- **L2-52** Naive 是纯向量检索文本块，也就是传统 RAG；Local 只用低层检索找具体实体；Global 只用高层检索找关系主题；Hybrid 同时使用低层和高层检索，是默认推荐的模式。[原文§四种查询模式：灵活应对不同场景](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html#%E5%9B%9B%E7%A7%8D%E6%9F%A5%E8%AF%A2%E6%A8%A1%E5%BC%8F-%E7%81%B5%E6%B4%BB%E5%BA%94%E5%AF%B9%E4%B8%8D%E5%90%8C%E5%9C%BA%E6%99%AF)
- **L2-53** 因为它没有社区这一层，不用重新检测社区，也不用重新生成摘要；但仍要对新文档切块、用 LLM 抽取实体和关系、与同名节点合并描述或新增节点和边，并把新描述向量化后追加到向量库。[原文§增量更新：真正的「轻量友好」](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html#%E5%A2%9E%E9%87%8F%E6%9B%B4%E6%96%B0-%E7%9C%9F%E6%AD%A3%E7%9A%84%E3%80%8C%E8%BD%BB%E9%87%8F%E5%8F%8B%E5%A5%BD%E3%80%8D)
- **L2-54** LightRAG 对语义冲突不敏感：先后抽到的两条矛盾关系会同时保留，不会自动判定哪条更新，需要自己在上层加逻辑。[原文§增量更新：真正的「轻量友好」](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html#%E5%A2%9E%E9%87%8F%E6%9B%B4%E6%96%B0-%E7%9C%9F%E6%AD%A3%E7%9A%84%E3%80%8C%E8%BD%BB%E9%87%8F%E5%8F%8B%E5%A5%BD%E3%80%8D)
- **L2-55** 原文的对比是：GraphRAG 的 Global Search 用 Map-Reduce 遍历相关社区的摘要，逐个生成中间答案再汇总；LightRAG 则是用高层关键词检索关系并聚合涉及的实体，没有社区摘要这一层。[原文§维度三：查询阶段的差异](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html#%E7%BB%B4%E5%BA%A6%E4%B8%89-%E6%9F%A5%E8%AF%A2%E9%98%B6%E6%AE%B5%E7%9A%84%E5%B7%AE%E5%BC%82)
- **L2-56** 原文称删除文档时把对应的节点和边删除即可；按 LightRAG 官方文档，按文档 ID 删除的过程是：删掉该文档的全部文本块，只删除仅属于这篇文档的实体和关系，其他文档仍在使用的实体和关系要重建，再更新相关的向量索引并清理文档状态记录。[原文§维度四：增量更新能力](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html#%E7%BB%B4%E5%BA%A6%E5%9B%9B-%E5%A2%9E%E9%87%8F%E6%9B%B4%E6%96%B0%E8%83%BD%E5%8A%9B)[核对来源：LightRAG 官方文档·Delete by Document ID](https://github.com/HKUDS/LightRAG/blob/main/docs/ProgramingWithCore.md)
- **L2-57** GraphRAG 的成本主要在建库：索引 100 万 token 约 4 到 7 美元甚至更高，Global 查询还要几百次调用、约 13000 token；LightRAG 的索引约 0.15 美元，查询时只需几次调用，单次约 100 到 1000 token。[原文§维度五：成本对比（真刀真枪的数字）](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html#%E7%BB%B4%E5%BA%A6%E4%BA%94-%E6%88%90%E6%9C%AC%E5%AF%B9%E6%AF%94-%E7%9C%9F%E5%88%80%E7%9C%9F%E6%9E%AA%E7%9A%84%E6%95%B0%E5%AD%97)
- **L2-58** 数字都带着条件：按索引 100 万 token 计，区分原版与贵模型，查询按单次计，并注明 Global Search 的调用特别多。[原文§维度五：成本对比（真刀真枪的数字）](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html#%E7%BB%B4%E5%BA%A6%E4%BA%94-%E6%88%90%E6%9C%AC%E5%AF%B9%E6%AF%94-%E7%9C%9F%E5%88%80%E7%9C%9F%E6%9E%AA%E7%9A%84%E6%95%B0%E5%AD%97)
- **L2-59** 按 LightRAG 论文的基准测试，LightRAG 在 Agriculture、Computer Science、Legal、Mix 四个数据集上，全面性、多样性、赋能性、整体四个维度都胜过 NaiveRAG、RQ-RAG 和 HyDE；对微软 GraphRAG 是多数领先，多样性上大幅领先，但在 Mix 数据集上全面性、赋能性和整体三项略低于 GraphRAG。在需要极深度全局归纳、或实体消歧要求严格的金融合同、医疗诊断等场景，GraphRAG 仍有优势。（原文写的是四个维度全部击败 GraphRAG，与论文表格不符。）[原文§维度六：精度表现（效果谁更好？）](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html#%E7%BB%B4%E5%BA%A6%E5%85%AD-%E7%B2%BE%E5%BA%A6%E8%A1%A8%E7%8E%B0-%E6%95%88%E6%9E%9C%E8%B0%81%E6%9B%B4%E5%A5%BD)[核对来源：LightRAG 论文](https://arxiv.org/abs/2410.05779)
- **L2-60** 例如多篇研究报告的综述，像“过去十年这个行业的主要发展脉络是什么”，GraphRAG 能通过社区报告提炼出主题层面的宏观答案；又如大规模专利或学术论文分析，要在数万篇论文上做主题发现和演进追踪，层次化社区结构能很好地支持。[原文§场景一：需要「全局洞察」的深度内容分析](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html#%E5%9C%BA%E6%99%AF%E4%B8%80-%E9%9C%80%E8%A6%81%E3%80%8C%E5%85%A8%E5%B1%80%E6%B4%9E%E5%AF%9F%E3%80%8D%E7%9A%84%E6%B7%B1%E5%BA%A6%E5%86%85%E5%AE%B9%E5%88%86%E6%9E%90)
- **L2-61** 共同点是回答一个问题要跨多个文档做关系推理，而且答错代价很大：合规与审计追踪，要打通客户、公司关联、监管记录、信贷档案几类数据；医疗诊断辅助，要准确追溯疾病、药物、禁忌症的关系；还有法律案例检索和金融研报深度分析。按微软官方基准测试，这类关系遍历型查询的精度比传统 RAG 提升 40% 到 60%。[原文§场景二：跨文档多跳推理的高价值场景](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html#%E5%9C%BA%E6%99%AF%E4%BA%8C-%E8%B7%A8%E6%96%87%E6%A1%A3%E5%A4%9A%E8%B7%B3%E6%8E%A8%E7%90%86%E7%9A%84%E9%AB%98%E4%BB%B7%E5%80%BC%E5%9C%BA%E6%99%AF)
- **L2-62** 因为它的增量更新成本高，最适合建好之后长期服务的静态知识库，如规章制度库、历史档案、法律条文库、已归档的项目资料；数据一年只更新一两次时，花一笔钱建好索引，之后的查询收益是长期的，成本能慢慢摊薄。[原文§场景三：数据相对静态、更新不频繁的知识库](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html#%E5%9C%BA%E6%99%AF%E4%B8%89-%E6%95%B0%E6%8D%AE%E7%9B%B8%E5%AF%B9%E9%9D%99%E6%80%81%E3%80%81%E6%9B%B4%E6%96%B0%E4%B8%8D%E9%A2%91%E7%B9%81%E7%9A%84%E7%9F%A5%E8%AF%86%E5%BA%93)
- **L2-63** 它的知识是显式的图结构，每个答案都能追溯到具体的实体、关系和原始文本块，“节点-边-社区”结构天然可审计；这对金融合规、医疗诊断、法律咨询、政府政务等需要审计追踪、每个回答都要有据可查的场景非常关键。[原文§场景四：对精度和可解释性要求极高的场景](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html#%E5%9C%BA%E6%99%AF%E5%9B%9B-%E5%AF%B9%E7%B2%BE%E5%BA%A6%E5%92%8C%E5%8F%AF%E8%A7%A3%E9%87%8A%E6%80%A7%E8%A6%81%E6%B1%82%E6%9E%81%E9%AB%98%E7%9A%84%E5%9C%BA%E6%99%AF)
- **L2-64** 数据量很小，比如不到 10 万 token；业务变化快、数据每天都在更新，维护成本过高；预算紧张的初创公司和个人项目；做 C 端实时交互的产品，Global Search 的延迟用户忍不了；单跳简单事实问答就能搞定的业务，比如客服 FAQ、产品说明书问答。[原文§什么场景下不要上 GraphRAG？](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html#%E4%BB%80%E4%B9%88%E5%9C%BA%E6%99%AF%E4%B8%8B%E4%B8%8D%E8%A6%81%E4%B8%8A-graphrag)
- **L2-65** 是需要数据持续增量更新的业务：企业知识库的日常维护，新文档来了直接 insert，几乎零维护成本；新闻聚合和实时资讯，新闻进来几分钟后就能被查询；客户支持系统每天新增的工单和解决方案；以及 GitHub 项目文档、API 文档、内部 wiki 这类几乎每天都在变的技术文档。[原文§场景一：数据频繁更新的业务](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html#%E5%9C%BA%E6%99%AF%E4%B8%80-%E6%95%B0%E6%8D%AE%E9%A2%91%E7%B9%81%E6%9B%B4%E6%96%B0%E7%9A%84%E4%B8%9A%E5%8A%A1)
- **L2-66** LightRAG 把索引成本降到几美分量级，个人开发者都能玩得起；适合创业公司做 MVP、个人知识管理、教育和学习场景（可用 Ollama 加 Qwen 这类开源模型本地跑，零 API 成本），以及 SaaS 产品的多租户知识库，因为 GraphRAG 的成本会随客户数线性放大。[原文§场景二：成本敏感的中小团队和初创公司](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html#%E5%9C%BA%E6%99%AF%E4%BA%8C-%E6%88%90%E6%9C%AC%E6%95%8F%E6%84%9F%E7%9A%84%E4%B8%AD%E5%B0%8F%E5%9B%A2%E9%98%9F%E5%92%8C%E5%88%9D%E5%88%9B%E5%85%AC%E5%8F%B8)
- **L2-67** LightRAG 的查询延迟是秒级的，Hybrid 查询通常 1 到 3 秒就能出结果，适合客服聊天机器人、AI 助理和语音交互；带语音的 AI 应用延迟超过 3 秒用户就会觉得卡，GraphRAG 的 Global Search 满足不了这个要求。[原文§场景三：实时性要求高的 C 端应用](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html#%E5%9C%BA%E6%99%AF%E4%B8%89-%E5%AE%9E%E6%97%B6%E6%80%A7%E8%A6%81%E6%B1%82%E9%AB%98%E7%9A%84-c-%E7%AB%AF%E5%BA%94%E7%94%A8)
- **L2-68** 它可以在普通 CPU 机器上跑，不强依赖 GPU：可以部署到工厂车间的边缘盒子；可以配合本地开源大模型（如 Qwen2.5、GLM）在内网完全离线运行，数据不出内网；用 Ollama 跑本地模型，普通笔记本就能跑起一个可用的知识库问答系统。[原文§场景四：轻量部署、本地化环境](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html#%E5%9C%BA%E6%99%AF%E5%9B%9B-%E8%BD%BB%E9%87%8F%E9%83%A8%E7%BD%B2%E3%80%81%E6%9C%AC%E5%9C%B0%E5%8C%96%E7%8E%AF%E5%A2%83)
- **L2-69** 少于 10 万 token 用传统 RAG，没必要上图；10 万到 500 万 token 时 LightRAG 最佳；500 万到 5000 万 token 时两者都可以，看业务侧重；大于 5000 万 token 时 GraphRAG 更合适，规模越大社区摘要的价值越大。中小规模是 LightRAG 的甜蜜区。[原文§场景五：中小规模知识库](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html#%E5%9C%BA%E6%99%AF%E4%BA%94-%E4%B8%AD%E5%B0%8F%E8%A7%84%E6%A8%A1%E7%9F%A5%E8%AF%86%E5%BA%93)
- **L2-70** 原文的混合架构是：稳定的、历史性的核心知识用 GraphRAG 建一次索引做深度分析，动态的日常增量数据用 LightRAG 做实时响应，查询时由路由器按查询类型分流到对应的系统。[原文§混合架构：两个都要，分而治之](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html#%E6%B7%B7%E5%90%88%E6%9E%B6%E6%9E%84-%E4%B8%A4%E4%B8%AA%E9%83%BD%E8%A6%81-%E5%88%86%E8%80%8C%E6%B2%BB%E4%B9%8B)
- **L2-71** GraphRAG 是深度分析的重型武器，LightRAG 是日常使用的轻巧刀具；大多数企业的 RAG 落地用 LightRAG 就能覆盖 80% 的需求，剩下 20% 的深度分析需求再上 GraphRAG 做补充。[原文§一句话总结](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html#%E4%B8%80%E5%8F%A5%E8%AF%9D%E6%80%BB%E7%BB%93)
- **L2-72** 2012 年谷歌就提出过 Knowledge Graph，把知识图谱和 RAG 结合的想法也有人试过，但一直不温不火，因为构建知识图谱太痛苦：要么靠人工标注，成本很高，要么靠专门训练的 NLP 模型，效果一般，实体和关系抽取、消歧、对齐每一步都是技术壁垒。大模型出现后这些工作可以交给 LLM，写几个提示词就能从文本里抽出实体、关系和属性，“从文档自动构建知识图谱”从需要专门团队做半年降到写个 Pipeline 跑几个小时；所以根本原因不是思路新，而是 LLM 让这个思路变得可实现。[原文§GraphRAG 的诞生背景](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html#graphrag-%E7%9A%84%E8%AF%9E%E7%94%9F%E8%83%8C%E6%99%AF)
- **L2-73** 传统 RAG 像去一个没有任何分类的图书馆找书，所有书按出版日期摆在一起，想找某个话题的书只能靠关键字搜索一本本翻，问“这个图书馆近几年主要收藏哪几个方向的书”没人能回答；GraphRAG 像进了一个带导游的主题书店，导游事先把书按主题分好类，每个主题区贴了一张概览海报，查具体细节时导游带你精准定位，问宏观主题时导游把各主题的概览海报念给你听。[原文§一个更形象的类比：从「图书馆找书」到「带导游游书店」](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html#%E4%B8%80%E4%B8%AA%E6%9B%B4%E5%BD%A2%E8%B1%A1%E7%9A%84%E7%B1%BB%E6%AF%94-%E4%BB%8E%E3%80%8C%E5%9B%BE%E4%B9%A6%E9%A6%86%E6%89%BE%E4%B9%A6%E3%80%8D%E5%88%B0%E3%80%8C%E5%B8%A6%E5%AF%BC%E6%B8%B8%E6%B8%B8%E4%B9%A6%E5%BA%97%E3%80%8D)
- **L2-74** GraphRAG 的哲学是“预计算全局视角”，索引阶段就通过社区检测和社区摘要把数据集的全局结构准备好，查询时直接用现成的摘要；LightRAG 的哲学是“按需检索，延迟聚合”，索引阶段只做最核心的实体关系抽取，不做全局预计算，查询时通过双层关键词临时拼出局部和全局视角。原文的评价是各有优劣：前者查得快但维护贵，后者查得灵活但深度略浅。[原文§维度一：设计哲学上的分歧](https://xiaolinnote.com/agent/rag/graphrag-lightrag.html#%E7%BB%B4%E5%BA%A6%E4%B8%80-%E8%AE%BE%E8%AE%A1%E5%93%B2%E5%AD%A6%E4%B8%8A%E7%9A%84%E5%88%86%E6%AD%A7)
