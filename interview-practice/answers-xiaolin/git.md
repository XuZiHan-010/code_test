## 1. 基础与工作区域

原文：[Git 面试题 · 基础与工作区域](https://xiaolincoding.com/interview/git.html#git-%E4%BD%BF%E7%94%A8%E7%86%9F%E7%BB%83%E5%90%97)。

### Git 使用熟练吗？

- **X1-1** 4 个空依次是工作区、暂存区、仓库区（或本地仓库）、远程仓库。[原文§Git 使用熟练吗？](https://xiaolincoding.com/interview/git.html#git-%E4%BD%BF%E7%94%A8%E7%86%9F%E7%BB%83%E5%90%97)
- **X1-2** Index / Stage 译为暂存区。Workspace 是工作区，Repository 是仓库区（或本地仓库），Remote 是远程仓库。[原文§Git 使用熟练吗？](https://xiaolincoding.com/interview/git.html#git-%E4%BD%BF%E7%94%A8%E7%86%9F%E7%BB%83%E5%90%97)
- **X1-3** 先执行 git pull 获取远程仓库的最新代码，再编写代码。git add . 把工作区修改加入暂存区，git commit -m 把暂存区代码提交到本地仓库，git push 推送到远程仓库，这三步都在开发完成之后。[原文§Git 使用熟练吗？](https://xiaolincoding.com/interview/git.html#git-%E4%BD%BF%E7%94%A8%E7%86%9F%E7%BB%83%E5%90%97)
- **X1-4** git add . 将工作区代码的修改添加到暂存区。提交到本地仓库是 git commit -m 的作用，推送到远程仓库是 git push，获取远程最新代码是 git pull。[原文§Git 使用熟练吗？](https://xiaolincoding.com/interview/git.html#git-%E4%BD%BF%E7%94%A8%E7%86%9F%E7%BB%83%E5%90%97)
- **X1-5** git commit -m 将暂存区代码提交到本地仓库，并添加相应的注释。把工作区修改加入暂存区的是 git add .，推送到远程仓库的是 git push。[原文§Git 使用熟练吗？](https://xiaolincoding.com/interview/git.html#git-%E4%BD%BF%E7%94%A8%E7%86%9F%E7%BB%83%E5%90%97)
- **X1-6** 3 个空依次是 git add .、git commit -m（附上注释）、git push。[原文§Git 使用熟练吗？](https://xiaolincoding.com/interview/git.html#git-%E4%BD%BF%E7%94%A8%E7%86%9F%E7%BB%83%E5%90%97)
- **X1-7** git reset --soft HEAD^ 把本地仓库回退到上一个版本，改动保留在暂存区和工作区。git reset --mixed HEAD^ 还会回退 git add，改动只保留在工作区；git push origin xxx --force 是撤回 push 时的强制推送；git pull 是获取远程更新。[原文§Git 使用熟练吗？](https://xiaolincoding.com/interview/git.html#git-%E4%BD%BF%E7%94%A8%E7%86%9F%E7%BB%83%E5%90%97)
- **X1-8** --mixed 不止回退了 git commit，还回退了 git add，代码的改动只保留在工作区。同时保留在暂存区和工作区的是 --soft。[原文§Git 使用熟练吗？](https://xiaolincoding.com/interview/git.html#git-%E4%BD%BF%E7%94%A8%E7%86%9F%E7%BB%83%E5%90%97)
- **X1-9** --soft 只回退 git commit，改动保留在暂存区和工作区。只保留在工作区的是 --mixed（它连 git add 也一起回退了）。[原文§Git 使用熟练吗？](https://xiaolincoding.com/interview/git.html#git-%E4%BD%BF%E7%94%A8%E7%86%9F%E7%BB%83%E5%90%97)
- **X1-10** --mixed 是 git reset 命令的默认选项，所以 git reset HEAD^ 就是 git reset --mixed HEAD^。--soft 需要显式写出。[原文§Git 使用熟练吗？](https://xiaolincoding.com/interview/git.html#git-%E4%BD%BF%E7%94%A8%E7%86%9F%E7%BB%83%E5%90%97)
- **X1-11** --soft 只回退 git commit；--mixed 不止回退 git commit，还回退了 git add 操作，所以改动只剩在工作区。[原文§Git 使用熟练吗？](https://xiaolincoding.com/interview/git.html#git-%E4%BD%BF%E7%94%A8%E7%86%9F%E7%BB%83%E5%90%97)
- **X1-12** HEAD^ 表示当前版本的上一个版本，也就是刚刚还没提交的时候。[原文§Git 使用熟练吗？](https://xiaolincoding.com/interview/git.html#git-%E4%BD%BF%E7%94%A8%E7%86%9F%E7%BB%83%E5%90%97)
- **X1-13** 先用 git reset HEAD^ 回退本地仓库，再用 git push origin xxx --force 把本地当前版本的代码强制推送到远程仓库。git reset HEAD^ 只回退本地，不会改动远程。[原文§Git 使用熟练吗？](https://xiaolincoding.com/interview/git.html#git-%E4%BD%BF%E7%94%A8%E7%86%9F%E7%BB%83%E5%90%97)
- **X1-14** git reset HEAD^ 即 --mixed，代码的修改保留在工作区。随后还要用 git push origin xxx --force 才能让远程仓库一并回退。[原文§Git 使用熟练吗？](https://xiaolincoding.com/interview/git.html#git-%E4%BD%BF%E7%94%A8%E7%86%9F%E7%BB%83%E5%90%97)
- **X1-15** --soft 保留暂存区和工作区的改动；--mixed 是默认模式；按原文撤回 push 的流程，需本地回退后再强制推送。--mixed 会回退暂存区，相关改动只保留在工作区；本地 reset 不会让远程自动回退。[原文§Git 使用熟练吗？](https://xiaolincoding.com/interview/git.html#git-%E4%BD%BF%E7%94%A8%E7%86%9F%E7%BB%83%E5%90%97)
- **X1-16** 可以用 git reset --soft HEAD^，把本地仓库回退到当前版本的上一个版本，也就是刚刚还没提交的时候，代码的改动保留在暂存区和工作区。也可以用 git reset --mixed HEAD^，不止回退 git commit，还回退了 git add，改动只保留在工作区；--mixed 是 git reset 的默认选项，所以可以写成 git reset HEAD^。[原文§Git 使用熟练吗？](https://xiaolincoding.com/interview/git.html#git-%E4%BD%BF%E7%94%A8%E7%86%9F%E7%BB%83%E5%90%97)
- **X1-17** 基础流程：先 git pull 获取远程仓库的最新代码并编写代码；完成功能后 git add . 把工作区修改加入暂存区，再 git commit -m 把暂存区代码提交到本地仓库并添加注释，最后 git push 推送到远程仓库。撤回 git commit：用 git reset --soft HEAD^ 回退到上一个版本，改动保留在暂存区和工作区；或用 git reset --mixed HEAD^（即 git reset HEAD^），连 git add 也回退，改动只在工作区。撤回 git push：先 git reset HEAD^ 把本地仓库回退到上一个版本，修改保留在工作区，再用 git push origin xxx --force 把本地当前版本强制推送到远程仓库。[原文§Git 使用熟练吗？](https://xiaolincoding.com/interview/git.html#git-%E4%BD%BF%E7%94%A8%E7%86%9F%E7%BB%83%E5%90%97)

### Git 有哪几个工作区域？它们之间是怎么流转的？

- **X1-18** 3 个空是暂存区（Index / Stage）、本地仓库（Local Repository）、远程仓库（Remote Repository）（顺序不限）。[原文§Git 有哪几个工作区域？它们之间是怎么流转的？](https://xiaolincoding.com/interview/git.html#git-%E6%9C%89%E5%93%AA%E5%87%A0%E4%B8%AA%E5%B7%A5%E4%BD%9C%E5%8C%BA%E5%9F%9F-%E5%AE%83%E4%BB%AC%E4%B9%8B%E9%97%B4%E6%98%AF%E6%80%8E%E4%B9%88%E6%B5%81%E8%BD%AC%E7%9A%84)
- **X1-19** 工作区是本地磁盘上你能直接看到和修改的项目目录。.git/index 是暂存区的索引文件，记录文件路径及内容对象 ID，记录 commit 的本地 .git 目录是本地仓库，托管在远程服务器上的是远程仓库。（原文将 git add 后的文件快照描述为暂存在 .git/index 里；这里区分索引记录和 blob 内容本体）[原文§Git 有哪几个工作区域？它们之间是怎么流转的？](https://xiaolincoding.com/interview/git.html#git-%E6%9C%89%E5%93%AA%E5%87%A0%E4%B8%AA%E5%B7%A5%E4%BD%9C%E5%8C%BA%E5%9F%9F-%E5%AE%83%E4%BB%AC%E4%B9%8B%E9%97%B4%E6%98%AF%E6%80%8E%E4%B9%88%E6%B5%81%E8%BD%AC%E7%9A%84)[核对来源：Git 索引数据模型](https://git-scm.com/docs/gitdatamodel#index)
- **X1-20** 暂存区索引通常保存在 .git/index 中。git add 将文件内容写为 blob 对象，并更新索引中对应的路径和内容对象 ID；文件内容本体不直接保存在索引文件中。（原文将 git add 后的文件快照描述为暂存在 .git/index 里；这里区分索引记录和 blob 内容本体）[原文§Git 有哪几个工作区域？它们之间是怎么流转的？](https://xiaolincoding.com/interview/git.html#git-%E6%9C%89%E5%93%AA%E5%87%A0%E4%B8%AA%E5%B7%A5%E4%BD%9C%E5%8C%BA%E5%9F%9F-%E5%AE%83%E4%BB%AC%E4%B9%8B%E9%97%B4%E6%98%AF%E6%80%8E%E4%B9%88%E6%B5%81%E8%BD%AC%E7%9A%84)[核对来源：Git 索引数据模型](https://git-scm.com/docs/gitdatamodel#index)
- **X1-21** git commit 之后，暂存区的内容被固化成一条 commit，记录到本地的 .git 目录，也就是本地仓库。同步到远程服务器是 git push 做的。[原文§Git 有哪几个工作区域？它们之间是怎么流转的？](https://xiaolincoding.com/interview/git.html#git-%E6%9C%89%E5%93%AA%E5%87%A0%E4%B8%AA%E5%B7%A5%E4%BD%9C%E5%8C%BA%E5%9F%9F-%E5%AE%83%E4%BB%AC%E4%B9%8B%E9%97%B4%E6%98%AF%E6%80%8E%E4%B9%88%E6%B5%81%E8%BD%AC%E7%9A%84)
- **X1-22** git push 把本地 commit 同步到托管在 GitHub、GitLab 等服务器上的远程仓库。暂存是 git add，固化成 commit 是 git commit，从远程更新是 git fetch/pull 一类的反向流转。（原文将 git add 后的文件快照描述为暂存在 .git/index 里；这里区分索引记录和 blob 内容本体）[原文§Git 有哪几个工作区域？它们之间是怎么流转的？](https://xiaolincoding.com/interview/git.html#git-%E6%9C%89%E5%93%AA%E5%87%A0%E4%B8%AA%E5%B7%A5%E4%BD%9C%E5%8C%BA%E5%9F%9F-%E5%AE%83%E4%BB%AC%E4%B9%8B%E9%97%B4%E6%98%AF%E6%80%8E%E4%B9%88%E6%B5%81%E8%BD%AC%E7%9A%84)[核对来源：Git 索引数据模型](https://git-scm.com/docs/gitdatamodel#index)
- **X1-23** 远程仓库（Remote Repository）是托管在 GitHub、GitLab 等远程服务器上的仓库，git push 把本地 commit 同步过去。其余三项分别是工作区、本地仓库和暂存区的描述。（原文将 git add 后的文件快照描述为暂存在 .git/index 里；这里区分索引记录和 blob 内容本体）[原文§Git 有哪几个工作区域？它们之间是怎么流转的？](https://xiaolincoding.com/interview/git.html#git-%E6%9C%89%E5%93%AA%E5%87%A0%E4%B8%AA%E5%B7%A5%E4%BD%9C%E5%8C%BA%E5%9F%9F-%E5%AE%83%E4%BB%AC%E4%B9%8B%E9%97%B4%E6%98%AF%E6%80%8E%E4%B9%88%E6%B5%81%E8%BD%AC%E7%9A%84)[核对来源：Git 索引数据模型](https://git-scm.com/docs/gitdatamodel#index)
- **X1-24** 3 个空依次是 git add、git commit、git push。[原文§Git 有哪几个工作区域？它们之间是怎么流转的？](https://xiaolincoding.com/interview/git.html#git-%E6%9C%89%E5%93%AA%E5%87%A0%E4%B8%AA%E5%B7%A5%E4%BD%9C%E5%8C%BA%E5%9F%9F-%E5%AE%83%E4%BB%AC%E4%B9%8B%E9%97%B4%E6%98%AF%E6%80%8E%E4%B9%88%E6%B5%81%E8%BD%AC%E7%9A%84)
- **X1-25** 从远程仓库获取更新用 git fetch 或 git pull。简图中的下一步若要从本地提交恢复工作区文件，应指定来源，如 git checkout <commit> -- <file> 或 git restore --source=<commit> <file>；裸 git restore <file> 默认从暂存区索引恢复工作区。git add、git push 属于正向数据流。（原文简图写作“本地仓库 --git checkout/restore--> 工作区”，未注明恢复来源；这里补明指定提交与默认 index 来源的区别）[原文§Git 有哪几个工作区域？它们之间是怎么流转的？](https://xiaolincoding.com/interview/git.html#git-%E6%9C%89%E5%93%AA%E5%87%A0%E4%B8%AA%E5%B7%A5%E4%BD%9C%E5%8C%BA%E5%9F%9F-%E5%AE%83%E4%BB%AC%E4%B9%8B%E9%97%B4%E6%98%AF%E6%80%8E%E4%B9%88%E6%B5%81%E8%BD%AC%E7%9A%84)[核对来源：git-restore 默认来源](https://git-scm.com/docs/git-restore#_description)
- **X1-26** 从本地仓库的指定提交恢复工作区文件可用 git checkout <commit> -- <file> 或 git restore --source=<commit> <file>。裸 git restore <file> 默认以暂存区索引为来源。git fetch/pull 用于获取远程更新，git add/commit 属于正向数据流。（原文简图写作“本地仓库 --git checkout/restore--> 工作区”，未注明恢复来源；这里补明指定提交与默认 index 来源的区别）[原文§Git 有哪几个工作区域？它们之间是怎么流转的？](https://xiaolincoding.com/interview/git.html#git-%E6%9C%89%E5%93%AA%E5%87%A0%E4%B8%AA%E5%B7%A5%E4%BD%9C%E5%8C%BA%E5%9F%9F-%E5%AE%83%E4%BB%AC%E4%B9%8B%E9%97%B4%E6%98%AF%E6%80%8E%E4%B9%88%E6%B5%81%E8%BD%AC%E7%9A%84)[核对来源：git-restore 默认来源](https://git-scm.com/docs/git-restore#_description)
- **X1-27** 正向数据流：工作区 --git add--> 暂存区 --git commit--> 本地仓库 --git push--> 远程仓库。git commit 在暂存区与本地仓库之间；工作区与暂存区之间是 git add，本地仓库与远程仓库之间是 git push。[原文§Git 有哪几个工作区域？它们之间是怎么流转的？](https://xiaolincoding.com/interview/git.html#git-%E6%9C%89%E5%93%AA%E5%87%A0%E4%B8%AA%E5%B7%A5%E4%BD%9C%E5%8C%BA%E5%9F%9F-%E5%AE%83%E4%BB%AC%E4%B9%8B%E9%97%B4%E6%98%AF%E6%80%8E%E4%B9%88%E6%B5%81%E8%BD%AC%E7%9A%84)
- **X1-28** git add 更新暂存区索引，记录待提交版本的引用；远程仓库托管在远程服务器；git commit 根据暂存区内容生成本地提交。工作区是本地磁盘上可见、可修改的项目目录，不是索引文件；git push 同步本地 commit，不会直接推送尚未 add 的工作区修改。（原文将 git add 后的文件快照描述为暂存在 .git/index 里；这里区分索引记录和 blob 内容本体）[原文§Git 有哪几个工作区域？它们之间是怎么流转的？](https://xiaolincoding.com/interview/git.html#git-%E6%9C%89%E5%93%AA%E5%87%A0%E4%B8%AA%E5%B7%A5%E4%BD%9C%E5%8C%BA%E5%9F%9F-%E5%AE%83%E4%BB%AC%E4%B9%8B%E9%97%B4%E6%98%AF%E6%80%8E%E4%B9%88%E6%B5%81%E8%BD%AC%E7%9A%84)[核对来源：Git 索引数据模型](https://git-scm.com/docs/gitdatamodel#index)
- **X1-29** Git 内部主要有四个区域：工作区是本地磁盘上能直接看到和修改的项目目录；暂存区（Index / Stage）逻辑上表示待提交的快照，.git/index 索引记录文件路径及内容对象 ID，内容本体存为 blob 对象；本地仓库是 git commit 之后暂存区内容固化成的 commit，记录在本地 .git 目录；远程仓库托管在 GitHub、GitLab 等远程服务器上。正向数据流：工作区 --git add--> 暂存区 --git commit--> 本地仓库 --git push--> 远程仓库。反向数据流：远程仓库 --git fetch/pull--> 本地仓库 --指定提交来源的 git checkout/restore--> 工作区；裸 git restore <file> 则默认从暂存区索引恢复工作区。理解这四个区域是理解 git reset、git stash、git diff 的基础。（原文将 git add 后的文件快照描述为暂存在 .git/index 里；这里区分索引记录和 blob 内容本体）（原文简图写作“本地仓库 --git checkout/restore--> 工作区”，未注明恢复来源；这里补明指定提交与默认 index 来源的区别）[原文§Git 有哪几个工作区域？它们之间是怎么流转的？](https://xiaolincoding.com/interview/git.html#git-%E6%9C%89%E5%93%AA%E5%87%A0%E4%B8%AA%E5%B7%A5%E4%BD%9C%E5%8C%BA%E5%9F%9F-%E5%AE%83%E4%BB%AC%E4%B9%8B%E9%97%B4%E6%98%AF%E6%80%8E%E4%B9%88%E6%B5%81%E8%BD%AC%E7%9A%84)[核对来源：Git 索引数据模型](https://git-scm.com/docs/gitdatamodel#index)[核对来源：git-restore 默认来源](https://git-scm.com/docs/git-restore#_description)

### git pull 和 git fetch 有什么区别？

- **X1-30** git fetch 只把远程仓库的最新 commit 拉到本地的远程跟踪分支，比如 origin/main，不会改动当前工作区和本地分支。[原文§git pull 和 git fetch 有什么区别？](https://xiaolincoding.com/interview/git.html#git-pull-%E5%92%8C-git-fetch-%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)
- **X1-31** git fetch 不会改动当前工作区和本地分支，相当于只“下载”。会拉取后立刻合并到当前分支的是采用 merge 策略的 git pull。（原文此节将 git pull 概括为 fetch + merge；实际整合方式取决于参数和配置，本组明确采用 merge 策略）[原文§git pull 和 git fetch 有什么区别？](https://xiaolincoding.com/interview/git.html#git-pull-%E5%92%8C-git-fetch-%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)[核对来源：git-pull 策略](https://git-scm.com/docs/git-pull#_description)

- **X1-44** 2 个空依次是工作区、暂存区。口诀是：默认对比工作区，--cached 对比暂存区。[原文§git diff 有哪些常见用法？](https://xiaolincoding.com/interview/git.html#git-diff-%E6%9C%89%E5%93%AA%E4%BA%9B%E5%B8%B8%E8%A7%81%E7%94%A8%E6%B3%95)
- **X1-45** git diff 默认对比工作区与暂存区；--cached 与 --staged 等价；git diff HEAD 对比工作区与 HEAD，原文称这是最常用的写法。--cached 对比的是暂存区与 HEAD，不是工作区与 HEAD；不带参数的 git diff 也不是对比暂存区与 HEAD。[原文§git diff 有哪些常见用法？](https://xiaolincoding.com/interview/git.html#git-diff-%E6%9C%89%E5%93%AA%E4%BA%9B%E5%B8%B8%E8%A7%81%E7%94%A8%E6%B3%95)

### git reset 的 --soft、--mixed、--hard 三种模式有什么区别？

- **X2-1** 两个空是暂存区、工作区（顺序不限）。三个参数决定的是 reset 对本地仓库 HEAD、暂存区、工作区三个区域的影响范围。[原文§git reset 的 --soft、--mixed、--hard 三种模式有什么区别？](https://xiaolincoding.com/interview/git.html#git-reset-%E7%9A%84-soft%E3%80%81-mixed%E3%80%81-hard-%E4%B8%89%E7%A7%8D%E6%A8%A1%E5%BC%8F%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)
- **X2-2** --soft 回退本地仓库 HEAD，暂存区和工作区都保留。暂存区回退、工作区保留是 --mixed 的效果，暂存区和工作区都回退是 --hard 的效果。[原文§git reset 的 --soft、--mixed、--hard 三种模式有什么区别？](https://xiaolincoding.com/interview/git.html#git-reset-%E7%9A%84-soft%E3%80%81-mixed%E3%80%81-hard-%E4%B8%89%E7%A7%8D%E6%A8%A1%E5%BC%8F%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)
- **X2-3** --mixed 是默认行为：本地仓库 HEAD 和暂存区回退，工作区保留。只回退 HEAD 的是 --soft，三个区域都回退的是 --hard；--mixed 并不是只回退 HEAD。[原文§git reset 的 --soft、--mixed、--hard 三种模式有什么区别？](https://xiaolincoding.com/interview/git.html#git-reset-%E7%9A%84-soft%E3%80%81-mixed%E3%80%81-hard-%E4%B8%89%E7%A7%8D%E6%A8%A1%E5%BC%8F%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)
- **X2-4** --soft 相当于“只撤销 commit、保留 add”，修改还在暂存区，可以直接重新 commit。撤销 commit 和 add 是 --mixed，按目标提交恢复受跟踪内容并丢弃相应本地修改的是 --hard。（原文将 --hard 概括为“撤销一切”“工作区也清空”；准确范围是按目标提交恢复受跟踪内容，不能理解为清空整个目录）[原文§git reset 的 --soft、--mixed、--hard 三种模式有什么区别？](https://xiaolincoding.com/interview/git.html#git-reset-%E7%9A%84-soft%E3%80%81-mixed%E3%80%81-hard-%E4%B8%89%E7%A7%8D%E6%A8%A1%E5%BC%8F%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)[核对来源：git-reset --hard](https://git-scm.com/docs/git-reset)
- **X2-5** --mixed 相当于“撤销 commit 和 add”，修改还在工作区，需要重新 add + commit。修改还在暂存区、可以直接 commit 的是 --soft；--hard 会按目标提交恢复受跟踪内容，丢弃相应本地修改。（原文将 --hard 概括为“撤销一切”“工作区也清空”；准确范围是按目标提交恢复受跟踪内容，不能理解为清空整个目录）[原文§git reset 的 --soft、--mixed、--hard 三种模式有什么区别？](https://xiaolincoding.com/interview/git.html#git-reset-%E7%9A%84-soft%E3%80%81-mixed%E3%80%81-hard-%E4%B8%89%E7%A7%8D%E6%A8%A1%E5%BC%8F%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)[核对来源：git-reset --hard](https://git-scm.com/docs/git-reset)
- **X2-6** --hard 按目标提交恢复暂存区和工作区中的受跟踪内容，相应的未提交本地修改会丢失；这不等于清空整个项目目录。--soft 保留暂存区和工作区，--mixed 保留工作区。（原文将 --hard 概括为“撤销一切”“工作区也清空”；准确范围是按目标提交恢复受跟踪内容，不能理解为清空整个目录）[原文§git reset 的 --soft、--mixed、--hard 三种模式有什么区别？](https://xiaolincoding.com/interview/git.html#git-reset-%E7%9A%84-soft%E3%80%81-mixed%E3%80%81-hard-%E4%B8%89%E7%A7%8D%E6%A8%A1%E5%BC%8F%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)[核对来源：git-reset --hard](https://git-scm.com/docs/git-reset)

### git reset 和 git revert 的区别是什么？

- **X2-12** git reset 把 HEAD 指针往回移动到指定 commit，本质是改写历史。生成反向新 commit 的是 git revert。[原文§git reset 和 git revert 的区别是什么？](https://xiaolincoding.com/interview/git.html#git-reset-%E5%92%8C-git-revert-%E7%9A%84%E5%8C%BA%E5%88%AB%E6%98%AF%E4%BB%80%E4%B9%88)
- **X2-13** git revert 生成一条新的 commit，内容正好是指定 commit 的反向（undo）。让后面的 commit “消失”的是 git reset。[原文§git reset 和 git revert 的区别是什么？](https://xiaolincoding.com/interview/git.html#git-reset-%E5%92%8C-git-revert-%E7%9A%84%E5%8C%BA%E5%88%AB%E6%98%AF%E4%BB%80%E4%B9%88)
- **X2-14** reset 把 HEAD 往回移动，后面的 commit 会“消失”。原来的 commit 依然保留在历史中、并新增反向 commit 的是 revert 的做法。[原文§git reset 和 git revert 的区别是什么？](https://xiaolincoding.com/interview/git.html#git-reset-%E5%92%8C-git-revert-%E7%9A%84%E5%8C%BA%E5%88%AB%E6%98%AF%E4%BB%80%E4%B9%88)
- **X2-15** revert 通过新增一条反向 commit 来撤销，原来的 commit 依然保留在历史中，不会改写历史。[原文§git reset 和 git revert 的区别是什么？](https://xiaolincoding.com/interview/git.html#git-reset-%E5%92%8C-git-revert-%E7%9A%84%E5%8C%BA%E5%88%AB%E6%98%AF%E4%BB%80%E4%B9%88)
- **X2-16** reset 本质是改写历史，对已 push 到共享远程的 commit 使用，会和其他人的本地历史冲突。生成反向 commit 的是 revert，不是 reset；reset 会让后面的 commit 消失，而不是保留。[原文§git reset 和 git revert 的区别是什么？](https://xiaolincoding.com/interview/git.html#git-reset-%E5%92%8C-git-revert-%E7%9A%84%E5%8C%BA%E5%88%AB%E6%98%AF%E4%BB%80%E4%B9%88)
- **X2-17** revert 不改写历史，安全，适合在共享分支上回滚已发布的改动，原文说共享分支永远优先用 revert。reset 会改写历史，不适合已 push 的 commit。[原文§git reset 和 git revert 的区别是什么？](https://xiaolincoding.com/interview/git.html#git-reset-%E5%92%8C-git-revert-%E7%9A%84%E5%8C%BA%E5%88%AB%E6%98%AF%E4%BB%80%E4%B9%88)
- **X2-18** 正确的是：reset 改写历史；revert 生成反向 commit 并保留原 commit；revert 适合共享分支上回滚已发布的改动。reset 不适合已 push 到共享远程的 commit，会让后面 commit 消失的是 reset，不是 revert。[原文§git reset 和 git revert 的区别是什么？](https://xiaolincoding.com/interview/git.html#git-reset-%E5%92%8C-git-revert-%E7%9A%84%E5%8C%BA%E5%88%AB%E6%98%AF%E4%BB%80%E4%B9%88)
- **X2-19** 两个空依次是“把时间倒回去”“走一步后退的步子”。[原文§git reset 和 git revert 的区别是什么？](https://xiaolincoding.com/interview/git.html#git-reset-%E5%92%8C-git-revert-%E7%9A%84%E5%8C%BA%E5%88%AB%E6%98%AF%E4%BB%80%E4%B9%88)
- **X2-20** git reset 指定 commit 把 HEAD 指针往回移动到指定 commit，后面的 commit 会“消失”，本质是改写历史，不适合已经 push 到共享远程的 commit，否则会和其他人的本地历史冲突。git revert 指定 commit 生成一条新的 commit，内容正好是指定 commit 的反向（undo），原来的 commit 依然保留在历史中，不改写历史，安全，适合在共享分支上回滚已发布的改动。口诀：reset 是“把时间倒回去”，revert 是“走一步后退的步子”，共享分支永远优先用 revert。[原文§git reset 和 git revert 的区别是什么？](https://xiaolincoding.com/interview/git.html#git-reset-%E5%92%8C-git-revert-%E7%9A%84%E5%8C%BA%E5%88%AB%E6%98%AF%E4%BB%80%E4%B9%88)

- **X2-31** Git 2.23 之前，git checkout 一个命令同时承担切换分支和恢复文件两个完全不同的职责，这种“一词多义”容易把新手绕晕。[原文§git checkout、git switch、git restore 有什么关系？](https://xiaolincoding.com/interview/git.html#git-checkout%E3%80%81git-switch%E3%80%81git-restore-%E6%9C%89%E4%BB%80%E4%B9%88%E5%85%B3%E7%B3%BB)

### git rebase和merge的区别

- **X3-1** Rebase 是把一个分支上的提交逐个地应用到另一个分支上。在非快进合并时，用新合并提交连接两个分支的历史的是 Merge，不是 Rebase；“把目标分支的提交应用到共同祖先上”也不是原文的说法。（原文此节概括 Merge“会创建一个新的合并提交”；快进合并是例外，只前移分支引用，不创建新 merge commit）[原文§git rebase和merge的区别](https://xiaolincoding.com/interview/git.html#git-rebase%E5%92%8Cmerge%E7%9A%84%E5%8C%BA%E5%88%AB)[核对来源：git-merge 快进合并](https://git-scm.com/docs/git-merge#_fast_forward_merge)
- **X3-2** Rebase 的效果是使提交历史变得更加线性。新增合并提交、保留各分支提交记录、把两个分支的修改包含在一个合并提交中，属于这里所比较的非快进 Merge 的特点。（原文此节概括 Merge“会创建一个新的合并提交”；快进合并是例外，只前移分支引用，不创建新 merge commit）[原文§git rebase和merge的区别](https://xiaolincoding.com/interview/git.html#git-rebase%E5%92%8Cmerge%E7%9A%84%E5%8C%BA%E5%88%AB)[核对来源：git-merge 快进合并](https://git-scm.com/docs/git-merge#_fast_forward_merge)
- **X3-3** 执行非快进 Merge 时，Git 会创建一个新的合并提交，把两个分支的提交历史连接在一起。逐个应用提交是 Rebase 的做法；原文说合并后的历史会保留每个分支的提交记录，因此也不是丢弃源分支的提交记录。（原文此节概括 Merge“会创建一个新的合并提交”；快进合并是例外，只前移分支引用，不创建新 merge commit）[原文§git rebase和merge的区别](https://xiaolincoding.com/interview/git.html#git-rebase%E5%92%8Cmerge%E7%9A%84%E5%8C%BA%E5%88%AB)[核对来源：git-merge 快进合并](https://git-scm.com/docs/git-merge#_fast_forward_merge)
- **X3-4** 非快进 Merge 合并后的历史会保留每个分支的提交记录。让历史更线性、把提交复制到目标分支是 Rebase 的特点；“抹去各分支提交记录”与原文相反。（原文此节概括 Merge“会创建一个新的合并提交”；快进合并是例外，只前移分支引用，不创建新 merge commit）[原文§git rebase和merge的区别](https://xiaolincoding.com/interview/git.html#git-rebase%E5%92%8Cmerge%E7%9A%84%E5%8C%BA%E5%88%AB)[核对来源：git-merge 快进合并](https://git-scm.com/docs/git-merge#_fast_forward_merge)
- **X3-5** 原文说 Rebase 的过程可以看作是将源分支上的每个提交复制到目标分支上。将两边修改纳入合并提交、用新提交连接历史，描述的是非快进 Merge；方向反过来的复制也不对。（原文此节概括 Merge“会创建一个新的合并提交”；快进合并是例外，只前移分支引用，不创建新 merge commit）[原文§git rebase和merge的区别](https://xiaolincoding.com/interview/git.html#git-rebase%E5%92%8Cmerge%E7%9A%84%E5%8C%BA%E5%88%AB)[核对来源：git-merge 快进合并](https://git-scm.com/docs/git-merge#_fast_forward_merge)
- **X3-6** 非快进 Merge 会创建一个新的合并提交，两个分支的修改都会包含在这个合并提交中。逐个复制提交是 Rebase 的方式，共同祖先和目标分支原有的最新提交都不会包含对方分支的修改。（原文此节概括 Merge“会创建一个新的合并提交”；快进合并是例外，只前移分支引用，不创建新 merge commit）[原文§git rebase和merge的区别](https://xiaolincoding.com/interview/git.html#git-rebase%E5%92%8Cmerge%E7%9A%84%E5%8C%BA%E5%88%AB)[核对来源：git-merge 快进合并](https://git-scm.com/docs/git-merge#_fast_forward_merge)
- **X3-7** 非快进 Merge 会创建新的合并提交、把两个分支的提交历史连接在一起，合并后保留每个分支的提交记录。“逐个应用到另一个分支上”和“使历史更线性”是 Rebase 的特点。（原文此节概括 Merge“会创建一个新的合并提交”；快进合并是例外，只前移分支引用，不创建新 merge commit）[原文§git rebase和merge的区别](https://xiaolincoding.com/interview/git.html#git-rebase%E5%92%8Cmerge%E7%9A%84%E5%8C%BA%E5%88%AB)[核对来源：git-merge 快进合并](https://git-scm.com/docs/git-merge#_fast_forward_merge)
- **X3-8** Rebase 把提交逐个应用到另一个分支上，使历史更线性，过程可看作把源分支的每个提交复制到目标分支。创建合并提交、保留各分支提交记录是此处所比较的非快进 Merge 的特点。（原文此节概括 Merge“会创建一个新的合并提交”；快进合并是例外，只前移分支引用，不创建新 merge commit）[原文§git rebase和merge的区别](https://xiaolincoding.com/interview/git.html#git-rebase%E5%92%8Cmerge%E7%9A%84%E5%8C%BA%E5%88%AB)[核对来源：git-merge 快进合并](https://git-scm.com/docs/git-merge#_fast_forward_merge)
- **X3-9** Rebase（变基）是将一个分支上的提交逐个地应用到另一个分支上，过程可以看作把源分支上的每个提交复制到目标分支，使提交历史变得更加线性。Merge（合并）在非快进合并或使用 --no-ff 强制生成合并提交时，会创建一个新的合并提交，把两个分支的提交历史连接在一起，两个分支的修改都包含在这个合并提交中，合并后的历史保留每个分支的提交记录。（原文此节概括 Merge“会创建一个新的合并提交”；快进合并是例外，只前移分支引用，不创建新 merge commit）[原文§git rebase和merge的区别](https://xiaolincoding.com/interview/git.html#git-rebase%E5%92%8Cmerge%E7%9A%84%E5%8C%BA%E5%88%AB)[核对来源：git-merge 快进合并](https://git-scm.com/docs/git-merge#_fast_forward_merge)

### git pull 和 git pull --rebase 的区别是什么？

- **X3-20** 明确采用 merge 策略时，git pull 相当于 fetch 后执行 merge；git pull --rebase 则是 fetch 后执行 rebase。（原文把裸 git pull 概括为 fetch + merge；实际策略受参数及 pull.rebase 等配置影响，本组明确比较 merge 与 rebase 策略）[原文§git pull 和 git pull --rebase 的区别是什么？](https://xiaolincoding.com/interview/git.html#git-pull-%E5%92%8C-git-pull-rebase-%E7%9A%84%E5%8C%BA%E5%88%AB%E6%98%AF%E4%BB%80%E4%B9%88)[核对来源：git-pull 策略](https://git-scm.com/docs/git-pull#_description)
- **X3-21** 原文：git pull --rebase = fetch + rebase。fetch + merge 对应明确采用 merge 策略的 git pull，不能仅凭省略 --rebase 判断策略。（原文把裸 git pull 概括为 fetch + merge；实际策略受参数及 pull.rebase 等配置影响，本组明确比较 merge 与 rebase 策略）[原文§git pull 和 git pull --rebase 的区别是什么？](https://xiaolincoding.com/interview/git.html#git-pull-%E5%92%8C-git-pull-rebase-%E7%9A%84%E5%8C%BA%E5%88%AB%E6%98%AF%E4%BB%80%E4%B9%88)[核对来源：git-pull 策略](https://git-scm.com/docs/git-pull#_description)
- **X3-22** 本地和远程已经分叉时，采用 merge 策略的 git pull 先 fetch，再生成 merge commit 连接并保留两边的历史；不是拉取才造成分叉。把本地提交在远程最新提交之后重放、得到线性历史，是本题比较的 rebase 策略。（原文把裸 git pull 概括为 fetch + merge；实际策略受参数及 pull.rebase 等配置影响，本组明确比较 merge 与 rebase 策略）[原文§git pull 和 git pull --rebase 的区别是什么？](https://xiaolincoding.com/interview/git.html#git-pull-%E5%92%8C-git-pull-rebase-%E7%9A%84%E5%8C%BA%E5%88%AB%E6%98%AF%E4%BB%80%E4%B9%88)[核对来源：git-pull 策略](https://git-scm.com/docs/git-pull#_description)
- **X3-23** git pull --rebase 把本地 commit “搬”到远程分支最新 commit 的后面，保持线性历史。在两边已经分叉时，采用 merge 策略的 git pull 会额外生成 merge commit，原文也没有说会丢弃本地 commit。（原文把裸 git pull 概括为 fetch + merge；实际策略受参数及 pull.rebase 等配置影响，本组明确比较 merge 与 rebase 策略）[原文§git pull 和 git pull --rebase 的区别是什么？](https://xiaolincoding.com/interview/git.html#git-pull-%E5%92%8C-git-pull-rebase-%E7%9A%84%E5%8C%BA%E5%88%AB%E6%98%AF%E4%BB%80%E4%B9%88)[核对来源：git-pull 策略](https://git-scm.com/docs/git-pull#_description)

- **X3-26** 原文提醒：rebase 会改写本地 commit 的 hash，所以不要对已经 push 的 commit 做 rebase。[原文§git pull 和 git pull --rebase 的区别是什么？](https://xiaolincoding.com/interview/git.html#git-pull-%E5%92%8C-git-pull-rebase-%E7%9A%84%E5%8C%BA%E5%88%AB%E6%98%AF%E4%BB%80%E4%B9%88)

- **X3-30** 本题明确比较 merge 策略与 rebase 策略，4 个空依次是：fetch、merge、fetch、rebase。（原文把裸 git pull 概括为 fetch + merge；实际策略受参数及 pull.rebase 等配置影响，本组明确比较 merge 与 rebase 策略）[原文§git pull 和 git pull --rebase 的区别是什么？](https://xiaolincoding.com/interview/git.html#git-pull-%E5%92%8C-git-pull-rebase-%E7%9A%84%E5%8C%BA%E5%88%AB%E6%98%AF%E4%BB%80%E4%B9%88)[核对来源：git-pull 策略](https://git-scm.com/docs/git-pull#_description)
- **X3-31** 明确采用 merge 策略时，git pull = fetch + merge；本地与远程已经分叉、各有对方没有的新 commit 时，会产生额外的 merge commit，连接并保留两边已有的分叉历史；若可快进则无需新 merge commit。git pull --rebase = fetch + rebase，会把本地 commit “搬”到远程分支最新 commit 的后面，保持线性历史。在多人协作的长期分支上推荐用 git pull --rebase，避免大量无意义的 merge commit 污染历史，很多团队甚至配置 git config --global pull.rebase true 让它成为默认行为。需要注意 rebase 会改写本地 commit 的 hash，所以不要对已经 push 到远程、被别人拉过的 commit 做 rebase，否则会给协作者带来巨大的历史同步问题。（原文把裸 git pull 概括为 fetch + merge；实际策略受参数及 pull.rebase 等配置影响，本组明确比较 merge 与 rebase 策略）[原文§git pull 和 git pull --rebase 的区别是什么？](https://xiaolincoding.com/interview/git.html#git-pull-%E5%92%8C-git-pull-rebase-%E7%9A%84%E5%8C%BA%E5%88%AB%E6%98%AF%E4%BB%80%E4%B9%88)[核对来源：git-pull 策略](https://git-scm.com/docs/git-pull#_description)

### 什么是 Fast-Forward 合并？和普通 merge 有什么区别？

- **X3-32** 将 feat/a 合入 main 时，若当前 main 的 tip 是 feat/a tip 的祖先，就可以直接把 main 引用前移到 feat/a，完成快进，不产生新 merge commit。双方分叉、各有对方没有的提交时，不能这样快进。[原文§什么是 Fast-Forward 合并？和普通 merge 有什么区别？](https://xiaolincoding.com/interview/git.html#%E4%BB%80%E4%B9%88%E6%98%AF-fast-forward-%E5%90%88%E5%B9%B6-%E5%92%8C%E6%99%AE%E9%80%9A-merge-%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)
- **X3-33** Fast-Forward 时 Git 只需把 main 的指针直接往前挪到 feat/a 的位置。创建 merge commit 把历史连起来是 Non-Fast-Forward 合并的做法。[原文§什么是 Fast-Forward 合并？和普通 merge 有什么区别？](https://xiaolincoding.com/interview/git.html#%E4%BB%80%E4%B9%88%E6%98%AF-fast-forward-%E5%90%88%E5%B9%B6-%E5%92%8C%E6%99%AE%E9%80%9A-merge-%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)
- **X3-34** Fast-Forward 不会产生新的 merge commit，提交历史保持线性。会产生 merge commit 的是 Non-Fast-Forward 合并或使用 --no-ff 的情况。[原文§什么是 Fast-Forward 合并？和普通 merge 有什么区别？](https://xiaolincoding.com/interview/git.html#%E4%BB%80%E4%B9%88%E6%98%AF-fast-forward-%E5%90%88%E5%B9%B6-%E5%92%8C%E6%99%AE%E9%80%9A-merge-%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)
- **X3-35** 两个分支有分叉时，Git 会创建一个新的 merge commit，把两条历史连起来，这就是 Non-Fast-Forward 合并。把指针直接前移的是 Fast-Forward。[原文§什么是 Fast-Forward 合并？和普通 merge 有什么区别？](https://xiaolincoding.com/interview/git.html#%E4%BB%80%E4%B9%88%E6%98%AF-fast-forward-%E5%90%88%E5%B9%B6-%E5%92%8C%E6%99%AE%E9%80%9A-merge-%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)
- **X3-36** git merge --no-ff feat/a 可以强制生成 merge commit。普通的 git merge 在可以快进时只会前移指针；git pull --rebase 和 git cherry-pick 不是强制生成 merge commit 的写法。[原文§什么是 Fast-Forward 合并？和普通 merge 有什么区别？](https://xiaolincoding.com/interview/git.html#%E4%BB%80%E4%B9%88%E6%98%AF-fast-forward-%E5%90%88%E5%B9%B6-%E5%92%8C%E6%99%AE%E9%80%9A-merge-%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)
- **X3-37** --no-ff 会强制生成 merge commit，好处是历史中能清晰看到这是一次 feature 分支的合并，方便回溯和回滚。保持线性、不产生 merge commit、直接前移指针是 Fast-Forward 的特点。[原文§什么是 Fast-Forward 合并？和普通 merge 有什么区别？](https://xiaolincoding.com/interview/git.html#%E4%BB%80%E4%B9%88%E6%98%AF-fast-forward-%E5%90%88%E5%B9%B6-%E5%92%8C%E6%99%AE%E9%80%9A-merge-%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)
- **X3-38** Fast-Forward 只需前移指针，不产生新的 merge commit，历史保持线性。创建 merge commit、两个分支各自有新 commit 属于 Non-Fast-Forward。[原文§什么是 Fast-Forward 合并？和普通 merge 有什么区别？](https://xiaolincoding.com/interview/git.html#%E4%BB%80%E4%B9%88%E6%98%AF-fast-forward-%E5%90%88%E5%B9%B6-%E5%92%8C%E6%99%AE%E9%80%9A-merge-%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)
- **X3-39** --no-ff 强制生成 merge commit，历史里能看出是一次 feature 合并，方便回溯和回滚，很多团队在 feature 合入 main 时强制使用。它在本可 Fast-Forward 时同样生成 merge commit，不是只在有分叉时才生效。[原文§什么是 Fast-Forward 合并？和普通 merge 有什么区别？](https://xiaolincoding.com/interview/git.html#%E4%BB%80%E4%B9%88%E6%98%AF-fast-forward-%E5%90%88%E5%B9%B6-%E5%92%8C%E6%99%AE%E9%80%9A-merge-%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)
- **X3-40** 2 个空依次是：指针、merge commit。[原文§什么是 Fast-Forward 合并？和普通 merge 有什么区别？](https://xiaolincoding.com/interview/git.html#%E4%BB%80%E4%B9%88%E6%98%AF-fast-forward-%E5%90%88%E5%B9%B6-%E5%92%8C%E6%99%AE%E9%80%9A-merge-%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)
- **X3-41** Fast-Forward（快进）合并是指将 feat/a 合入 main 时，当前 main 的 tip 是 feat/a tip 的祖先，Git 只需把 main 的指针直接往前挪到 feat/a 的位置，不会产生新的 merge commit，提交历史保持线性。Non-Fast-Forward 合并是两个分支有分叉、各自都有新 commit，Git 会创建一个新的 merge commit 把两条历史连起来。可以用 git merge --no-ff feat/a 在本可快进时强制生成 merge commit，这样能在历史中清晰看到这是一次 feature 分支的合并，方便回溯和回滚，很多团队在 feature 合入 main 时会强制加 --no-ff。[原文§什么是 Fast-Forward 合并？和普通 merge 有什么区别？](https://xiaolincoding.com/interview/git.html#%E4%BB%80%E4%B9%88%E6%98%AF-fast-forward-%E5%90%88%E5%B9%B6-%E5%92%8C%E6%99%AE%E9%80%9A-merge-%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)

- **X3-42** git cherry-pick <commit> 把某个 commit 的改动“挑”到当前分支。合并整个分支是 merge 的作用，原文没有说它会重排或删除 commit。[原文§git cherry-pick 是做什么的？什么场景用？](https://xiaolincoding.com/interview/git.html#git-cherry-pick-%E6%98%AF%E5%81%9A%E4%BB%80%E4%B9%88%E7%9A%84-%E4%BB%80%E4%B9%88%E5%9C%BA%E6%99%AF%E7%94%A8)

- **X3-48** cherry-pick 用于把单个修复搬到别的分支，或把 hotfix 同步到多个长期分支。整体合并分支用 merge，清理失效的跟踪分支用 git fetch --prune。[原文§git cherry-pick 是做什么的？什么场景用？](https://xiaolincoding.com/interview/git.html#git-cherry-pick-%E6%98%AF%E5%81%9A%E4%BB%80%E4%B9%88%E7%9A%84-%E4%BB%80%E4%B9%88%E5%9C%BA%E6%99%AF%E7%94%A8)
- **X3-49** 遇到冲突时，手动解决后 git add，再 git cherry-pick --continue；想放弃就 git cherry-pick --abort。Git 并不会自动解决冲突，--continue 也不是放弃。[原文§git cherry-pick 是做什么的？什么场景用？](https://xiaolincoding.com/interview/git.html#git-cherry-pick-%E6%98%AF%E5%81%9A%E4%BB%80%E4%B9%88%E7%9A%84-%E4%BB%80%E4%B9%88%E5%9C%BA%E6%99%AF%E7%94%A8)

- **X3-52** 小写 -d 是安全删除，只有已经合并过的分支才允许删。强制删除是大写 -D，删除远程分支用 git push origin --delete，清理失效的跟踪分支用 git fetch --prune。[原文§如何删除本地分支和远程分支？](https://xiaolincoding.com/interview/git.html#%E5%A6%82%E4%BD%95%E5%88%A0%E9%99%A4%E6%9C%AC%E5%9C%B0%E5%88%86%E6%94%AF%E5%92%8C%E8%BF%9C%E7%A8%8B%E5%88%86%E6%94%AF)

- **X3-60** 清理失效的跟踪分支用 git fetch --prune 或 git remote prune origin。git branch -d 删除本地分支，git push origin --delete 删除远程分支。[原文§如何删除本地分支和远程分支？](https://xiaolincoding.com/interview/git.html#%E5%A6%82%E4%BD%95%E5%88%A0%E9%99%A4%E6%9C%AC%E5%9C%B0%E5%88%86%E6%94%AF%E5%92%8C%E8%BF%9C%E7%A8%8B%E5%88%86%E6%94%AF)

- **X3-62** 2 个空依次是：--prune、prune。[原文§如何删除本地分支和远程分支？](https://xiaolincoding.com/interview/git.html#%E5%A6%82%E4%BD%95%E5%88%A0%E9%99%A4%E6%9C%AC%E5%9C%B0%E5%88%86%E6%94%AF%E5%92%8C%E8%BF%9C%E7%A8%8B%E5%88%86%E6%94%AF)
- **X3-63** 删除本地分支：git branch -d feat/xxx 是安全删除，只有已经合并过的分支才允许删；git branch -D feat/xxx（大写 D）是强制删除，未合并的也能删，要小心丢代码。删除远程分支：推荐 git push origin --delete feat/xxx，或等价写法 git push origin :feat/xxx（把“空”推上去，相当于删除）。清理已经在远程被删除但本地还缓存的跟踪分支用 git fetch --prune 或 git remote prune origin，这一步容易被忽略，但能解决 git branch -r 里一堆早就没了的分支这种尴尬情况。[原文§如何删除本地分支和远程分支？](https://xiaolincoding.com/interview/git.html#%E5%A6%82%E4%BD%95%E5%88%A0%E9%99%A4%E6%9C%AC%E5%9C%B0%E5%88%86%E6%94%AF%E5%92%8C%E8%BF%9C%E7%A8%8B%E5%88%86%E6%94%AF)

## 4. 协作与排查

原文：[Git 面试题 · 协作与排查](https://xiaolincoding.com/interview/git.html#%E5%B8%B8%E8%A7%81%E7%9A%84-git-%E5%B7%A5%E4%BD%9C%E6%B5%81%E6%9C%89%E5%93%AA%E4%BA%9B)。

### 常见的 Git 工作流有哪些？

- **X4-1** 两个空是 GitLab Flow、Trunk-Based Development（主干开发）（顺序不限）。业界主流的四种工作流是 Git Flow、GitHub Flow、GitLab Flow 和 Trunk-Based Development。[原文§常见的 Git 工作流有哪些？](https://xiaolincoding.com/interview/git.html#%E5%B8%B8%E8%A7%81%E7%9A%84-git-%E5%B7%A5%E4%BD%9C%E6%B5%81%E6%9C%89%E5%93%AA%E4%BA%9B)
- **X4-2** Git Flow 有 master、develop、feature/*、release/*、hotfix/* 多种长期和临时分支，规则严谨。只有 main 一个长期分支加短生命周期 feature 分支的是 GitHub Flow；在其基础上加入 production、pre-production 环境分支的是 GitLab Flow；所有人直接在 main 上开发的是 Trunk-Based Development。[原文§常见的 Git 工作流有哪些？](https://xiaolincoding.com/interview/git.html#%E5%B8%B8%E8%A7%81%E7%9A%84-git-%E5%B7%A5%E4%BD%9C%E6%B5%81%E6%9C%89%E5%93%AA%E4%BA%9B)
- **X4-3** Git Flow 规则严谨，适合版本化发布的产品，比如客户端 App、大型企业产品。持续部署的 Web 应用对应 GitHub Flow，需要明确发布环境的场景对应 GitLab Flow，依赖成熟 CI/CD 和测试体系的是 Trunk-Based Development。[原文§常见的 Git 工作流有哪些？](https://xiaolincoding.com/interview/git.html#%E5%B8%B8%E8%A7%81%E7%9A%84-git-%E5%B7%A5%E4%BD%9C%E6%B5%81%E6%9C%89%E5%93%AA%E4%BA%9B)
- **X4-4** Git Flow 的缺点是流程太重，对快速迭代不友好；它的优点恰恰是规则严谨、适合版本化发布。需要成熟 CI/CD 和测试体系、长分支寿命不超过一两天，都是 Trunk-Based Development 的特点。[原文§常见的 Git 工作流有哪些？](https://xiaolincoding.com/interview/git.html#%E5%B8%B8%E8%A7%81%E7%9A%84-git-%E5%B7%A5%E4%BD%9C%E6%B5%81%E6%9C%89%E5%93%AA%E4%BA%9B)
- **X4-5** GitHub Flow 只有 main 一个长期分支加多个短生命周期的 feature 分支，全部通过 Pull Request 合并，简单、灵活。多种长期和临时分支是 Git Flow，增加环境分支是 GitLab Flow，直接在 main 上开发并配合 feature flag 是 Trunk-Based Development。[原文§常见的 Git 工作流有哪些？](https://xiaolincoding.com/interview/git.html#%E5%B8%B8%E8%A7%81%E7%9A%84-git-%E5%B7%A5%E4%BD%9C%E6%B5%81%E6%9C%89%E5%93%AA%E4%BA%9B)
- **X4-6** GitHub Flow 简单、灵活，适合持续部署的 Web 应用。版本化发布的客户端 App、大型企业产品更适合 Git Flow，需要明确发布环境的场景适合 GitLab Flow。[原文§常见的 Git 工作流有哪些？](https://xiaolincoding.com/interview/git.html#%E5%B8%B8%E8%A7%81%E7%9A%84-git-%E5%B7%A5%E4%BD%9C%E6%B5%81%E6%9C%89%E5%93%AA%E4%BA%9B)
- **X4-7** GitLab Flow 介于 Git Flow 与 GitHub Flow 之间，在 GitHub Flow 的基础上加入了 production、pre-production 等环境分支。它并不比 Git Flow 更重，feature flag 属于 Trunk-Based Development，GitHub Flow 才是全部通过 Pull Request 合并。[原文§常见的 Git 工作流有哪些？](https://xiaolincoding.com/interview/git.html#%E5%B8%B8%E8%A7%81%E7%9A%84-git-%E5%B7%A5%E4%BD%9C%E6%B5%81%E6%9C%89%E5%93%AA%E4%BA%9B)
- **X4-8** GitLab Flow 加入了 production、pre-production 等环境分支，适合需要明确发布环境的场景。持续部署的 Web 应用对应 GitHub Flow，版本化发布的客户端 App 对应 Git Flow，所有人直接在 main 上开发对应 Trunk-Based Development。[原文§常见的 Git 工作流有哪些？](https://xiaolincoding.com/interview/git.html#%E5%B8%B8%E8%A7%81%E7%9A%84-git-%E5%B7%A5%E4%BD%9C%E6%B5%81%E6%9C%89%E5%93%AA%E4%BA%9B)
- **X4-9** 依次填：main、feature flag。主干开发中所有人直接在 main 上开发，配合 feature flag 控制功能开关。[原文§常见的 Git 工作流有哪些？](https://xiaolincoding.com/interview/git.html#%E5%B8%B8%E8%A7%81%E7%9A%84-git-%E5%B7%A5%E4%BD%9C%E6%B5%81%E6%9C%89%E5%93%AA%E4%BA%9B)
- **X4-10** 主干开发的特点是：所有人直接在 main 上开发，配合 feature flag 控制功能开关，长分支寿命不超过一两天，并且需要成熟的 CI/CD 和测试体系。develop、release/*、hotfix/* 等多种分支是 Git Flow 的特点，加入 production、pre-production 环境分支的是 GitLab Flow。[原文§常见的 Git 工作流有哪些？](https://xiaolincoding.com/interview/git.html#%E5%B8%B8%E8%A7%81%E7%9A%84-git-%E5%B7%A5%E4%BD%9C%E6%B5%81%E6%9C%89%E5%93%AA%E4%BA%9B)
- **X4-11** 主干开发需要成熟的 CI/CD 和测试体系，Google、Facebook 等大厂主推这种模式。develop、release 分支属于 Git Flow，环境分支属于 GitLab Flow；主干开发要求长分支寿命不超过一两天，而不是长期保留 feature 分支。[原文§常见的 Git 工作流有哪些？](https://xiaolincoding.com/interview/git.html#%E5%B8%B8%E8%A7%81%E7%9A%84-git-%E5%B7%A5%E4%BD%9C%E6%B5%81%E6%9C%89%E5%93%AA%E4%BA%9B)
- **X4-12** 原文指出 Git Flow 现在已经被很多团队认为过时。中小团队用得最多的是 GitHub Flow 或 Trunk-Based 的变体，大厂主推的是 Trunk-Based Development，持续部署的 Web 应用适合 GitHub Flow。[原文§常见的 Git 工作流有哪些？](https://xiaolincoding.com/interview/git.html#%E5%B8%B8%E8%A7%81%E7%9A%84-git-%E5%B7%A5%E4%BD%9C%E6%B5%81%E6%9C%89%E5%93%AA%E4%BA%9B)
- **X4-13** 原文说实际中小团队用得最多的是 GitHub Flow 或者 Trunk-Based 的变体，Git Flow 现在已经被很多团队认为过时。[原文§常见的 Git 工作流有哪些？](https://xiaolincoding.com/interview/git.html#%E5%B8%B8%E8%A7%81%E7%9A%84-git-%E5%B7%A5%E4%BD%9C%E6%B5%81%E6%9C%89%E5%93%AA%E4%BA%9B)
- **X4-14** 业界主流有四种。Git Flow：有 master、develop、feature/*、release/*、hotfix/* 多种长期和临时分支，规则严谨，适合版本化发布的产品（比如客户端 App、大型企业产品），缺点是流程太重，对快速迭代不友好。GitHub Flow：只有 main 一个长期分支加多个短生命周期的 feature 分支，全部通过 Pull Request 合并，简单、灵活，适合持续部署的 Web 应用。GitLab Flow：介于两者之间，在 GitHub Flow 的基础上加入 production、pre-production 等环境分支，适合需要明确发布环境的场景。Trunk-Based Development（主干开发）：所有人直接在 main 上开发，配合 feature flag 控制功能开关，长分支寿命不超过一两天，需要成熟的 CI/CD 和测试体系，是 Google、Facebook 等大厂主推的模式。实际中小团队用得最多的是 GitHub Flow 或 Trunk-Based 的变体，Git Flow 现在已经被很多团队认为过时。[原文§常见的 Git 工作流有哪些？](https://xiaolincoding.com/interview/git.html#%E5%B8%B8%E8%A7%81%E7%9A%84-git-%E5%B7%A5%E4%BD%9C%E6%B5%81%E6%9C%89%E5%93%AA%E4%BA%9B)

### Fork、Clone、Pull Request 在 GitHub 协作中分别是什么？

- **X4-15** Fork 是在 GitHub 上把别人的仓库复制一份到自己的账号下，是服务器端操作。把远程仓库下载到本地是 Clone，请求维护者合并改动是 Pull Request。[原文§Fork、Clone、Pull Request 在 GitHub 协作中分别是什么？](https://xiaolincoding.com/interview/git.html#fork%E3%80%81clone%E3%80%81pull-request-%E5%9C%A8-github-%E5%8D%8F%E4%BD%9C%E4%B8%AD%E5%88%86%E5%88%AB%E6%98%AF%E4%BB%80%E4%B9%88)
- **X4-16** Clone 是把一个远程仓库下载到本地，是本地操作。在 GitHub 上把仓库复制到自己账号下的是 Fork，请求维护者合并改动的是 Pull Request。[原文§Fork、Clone、Pull Request 在 GitHub 协作中分别是什么？](https://xiaolincoding.com/interview/git.html#fork%E3%80%81clone%E3%80%81pull-request-%E5%9C%A8-github-%E5%8D%8F%E4%BD%9C%E4%B8%AD%E5%88%86%E5%88%AB%E6%98%AF%E4%BB%80%E4%B9%88)
- **X4-17** 原文明确区分：Fork 在 GitHub 上进行，是服务器端操作；Clone 把代码下载到本地，是本地操作。[原文§Fork、Clone、Pull Request 在 GitHub 协作中分别是什么？](https://xiaolincoding.com/interview/git.html#fork%E3%80%81clone%E3%80%81pull-request-%E5%9C%A8-github-%E5%8D%8F%E4%BD%9C%E4%B8%AD%E5%88%86%E5%88%AB%E6%98%AF%E4%BB%80%E4%B9%88)
- **X4-18** Fork 出的仓库和原仓库保持关联，但你可以自由往自己 fork 的仓库推代码，不影响原作者。需要维护者 review 并决定是否合并的是之后发起的 Pull Request，而不是往自己的 fork 推代码。[原文§Fork、Clone、Pull Request 在 GitHub 协作中分别是什么？](https://xiaolincoding.com/interview/git.html#fork%E3%80%81clone%E3%80%81pull-request-%E5%9C%A8-github-%E5%8D%8F%E4%BD%9C%E4%B8%AD%E5%88%86%E5%88%AB%E6%98%AF%E4%BB%80%E4%B9%88)
- **X4-19** 把仓库克隆到本地后，便于在本地编辑、测试和编译代码。复制仓库到自己账号下的是 Fork；fork 出的仓库可以自由推送代码；Clone 是本地操作而非服务器端操作。（原文说“只有 clone 下来的代码才能在本地编辑、测试、编译”；官方 archive 文档可导出并解压源码归档，据此可知本地源码不只来自 clone）[原文§Fork、Clone、Pull Request 在 GitHub 协作中分别是什么？](https://xiaolincoding.com/interview/git.html#fork%E3%80%81clone%E3%80%81pull-request-%E5%9C%A8-github-%E5%8D%8F%E4%BD%9C%E4%B8%AD%E5%88%86%E5%88%AB%E6%98%AF%E4%BB%80%E4%B9%88)[核对来源：git-archive 源码归档示例](https://git-scm.com/docs/git-archive#_examples)
- **X4-20** PR 是在自己 fork 的仓库改完代码推上去后，发起一个“请求”，请求原仓库的维护者把你的改动合并进来。复制仓库是 Fork，下载到本地是 Clone，推送到自己 fork 的仓库是 Push，都不是 PR。[原文§Fork、Clone、Pull Request 在 GitHub 协作中分别是什么？](https://xiaolincoding.com/interview/git.html#fork%E3%80%81clone%E3%80%81pull-request-%E5%9C%A8-github-%E5%8D%8F%E4%BD%9C%E4%B8%AD%E5%88%86%E5%88%AB%E6%98%AF%E4%BB%80%E4%B9%88)
- **X4-21** 正确的有：Fork 是服务器端操作；Clone 是本地操作；PR 是请求原仓库维护者合并改动；原作者可以 review 代码、讨论，最终 merge 或者拒绝。把仓库复制到自己账号下的是 Fork 而不是 Clone，下载到本地的是 Clone 而不是 Fork。[原文§Fork、Clone、Pull Request 在 GitHub 协作中分别是什么？](https://xiaolincoding.com/interview/git.html#fork%E3%80%81clone%E3%80%81pull-request-%E5%9C%A8-github-%E5%8D%8F%E4%BD%9C%E4%B8%AD%E5%88%86%E5%88%AB%E6%98%AF%E4%BB%80%E4%B9%88)
- **X4-22** 依次填：Clone、Push 到自己的 Fork。完整流程：Fork（在 GitHub 上）→ Clone（到本地）→ 改代码 + commit → Push 到自己的 Fork → 发 Pull Request → 维护者 Review & Merge。[原文§Fork、Clone、Pull Request 在 GitHub 协作中分别是什么？](https://xiaolincoding.com/interview/git.html#fork%E3%80%81clone%E3%80%81pull-request-%E5%9C%A8-github-%E5%8D%8F%E4%BD%9C%E4%B8%AD%E5%88%86%E5%88%AB%E6%98%AF%E4%BB%80%E4%B9%88)
- **X4-23** 标准流程是 Fork → Clone → 改代码 + commit → Push 到自己的 Fork → 发 Pull Request。推到自己的 Fork 不影响原作者，之后再通过 PR 请求维护者合并。[原文§Fork、Clone、Pull Request 在 GitHub 协作中分别是什么？](https://xiaolincoding.com/interview/git.html#fork%E3%80%81clone%E3%80%81pull-request-%E5%9C%A8-github-%E5%8D%8F%E4%BD%9C%E4%B8%AD%E5%88%86%E5%88%AB%E6%98%AF%E4%BB%80%E4%B9%88)
- **X4-24** 内部团队协作也可以用同样的流程，只不过一般不 fork，而是直接在同一个仓库里建 feature 分支，再发 PR/MR。[原文§Fork、Clone、Pull Request 在 GitHub 协作中分别是什么？](https://xiaolincoding.com/interview/git.html#fork%E3%80%81clone%E3%80%81pull-request-%E5%9C%A8-github-%E5%8D%8F%E4%BD%9C%E4%B8%AD%E5%88%86%E5%88%AB%E6%98%AF%E4%BB%80%E4%B9%88)
- **X4-25** 这是开源协作的标准流程。Fork：在 GitHub 上把别人的仓库复制一份到自己的账号下，是服务器端操作；Fork 出的仓库和原仓库保持关联，可以自由往里推代码，不影响原作者。Clone：把一个远程仓库下载到本地，是本地操作；把仓库克隆到本地便于编辑、测试和编译代码。Pull Request：在自己 fork 的仓库改完代码推上去后，发起一个“请求”，请求原仓库的维护者把改动合并进来，原作者可以 review 代码、讨论，最终 merge 或者拒绝。标准流程是 Fork（在 GitHub 上）→ Clone（到本地）→ 改代码 + commit → Push 到自己的 Fork → 发 Pull Request → 维护者 Review & Merge。内部团队协作也可以用同样的流程，只不过一般不 fork，而是直接在同一个仓库里建 feature 分支，再发 PR/MR。（原文说“只有 clone 下来的代码才能在本地编辑、测试、编译”；官方 archive 文档可导出并解压源码归档，据此可知本地源码不只来自 clone）[原文§Fork、Clone、Pull Request 在 GitHub 协作中分别是什么？](https://xiaolincoding.com/interview/git.html#fork%E3%80%81clone%E3%80%81pull-request-%E5%9C%A8-github-%E5%8D%8F%E4%BD%9C%E4%B8%AD%E5%88%86%E5%88%AB%E6%98%AF%E4%BB%80%E4%B9%88)[核对来源：git-archive 源码归档示例](https://git-scm.com/docs/git-archive#_examples)

### git log 常用参数有哪些？

- **X4-26** --oneline 让每个 commit 只占一行，简洁直观。用 ASCII 图形显示分支 / 合并关系的是 --graph，显示完整 diff 的是 -p，只看最近 5 条的是 -n 5。[原文§git log 常用参数有哪些？](https://xiaolincoding.com/interview/git.html#git-log-%E5%B8%B8%E7%94%A8%E5%8F%82%E6%95%B0%E6%9C%89%E5%93%AA%E4%BA%9B)
- **X4-27** --graph 用 ASCII 图形显示分支 / 合并关系。一行显示一个 commit 的是 --oneline，按作者过滤的是 --author，显示修改文件和增删行数的是 --stat。[原文§git log 常用参数有哪些？](https://xiaolincoding.com/interview/git.html#git-log-%E5%B8%B8%E7%94%A8%E5%8F%82%E6%95%B0%E6%9C%89%E5%93%AA%E4%BA%9B)
- **X4-28** -n 5 的作用是只看最近 5 条。按作者过滤用 --author，按时间过滤用 --since / --until，显示完整 diff 用 -p。[原文§git log 常用参数有哪些？](https://xiaolincoding.com/interview/git.html#git-log-%E5%B8%B8%E7%94%A8%E5%8F%82%E6%95%B0%E6%9C%89%E5%93%AA%E4%BA%9B)
- **X4-29** --author="name" 按作者过滤。按 commit message 关键字过滤的是 --grep，按时间过滤的是 --since / --until，查看某个文件修改历史的是 git log -- <file>。[原文§git log 常用参数有哪些？](https://xiaolincoding.com/interview/git.html#git-log-%E5%B8%B8%E7%94%A8%E5%8F%82%E6%95%B0%E6%9C%89%E5%93%AA%E4%BA%9B)
- **X4-30** --since 和 --until 用来按时间过滤。按作者过滤用 --author，按 commit message 关键字过滤用 --grep，只看最近若干条用 -n。[原文§git log 常用参数有哪些？](https://xiaolincoding.com/interview/git.html#git-log-%E5%B8%B8%E7%94%A8%E5%8F%82%E6%95%B0%E6%9C%89%E5%93%AA%E4%BA%9B)
- **X4-31** --grep="fix" 按 commit message 关键字过滤。--author 按作者过滤，--since 按时间过滤，--stat 显示每个 commit 修改了哪些文件及增删行数。[原文§git log 常用参数有哪些？](https://xiaolincoding.com/interview/git.html#git-log-%E5%B8%B8%E7%94%A8%E5%8F%82%E6%95%B0%E6%9C%89%E5%93%AA%E4%BA%9B)
- **X4-32** -p 显示每个 commit 的完整 diff。只显示修改了哪些文件、增删行数的是 --stat，一行显示一个 commit 的是 --oneline，按关键字过滤的是 --grep。[原文§git log 常用参数有哪些？](https://xiaolincoding.com/interview/git.html#git-log-%E5%B8%B8%E7%94%A8%E5%8F%82%E6%95%B0%E6%9C%89%E5%93%AA%E4%BA%9B)
- **X4-33** --stat 显示每个 commit 修改了哪些文件、增删行数。-p 显示的是完整 diff，--graph 显示分支 / 合并关系，--oneline 让每个 commit 只占一行。[原文§git log 常用参数有哪些？](https://xiaolincoding.com/interview/git.html#git-log-%E5%B8%B8%E7%94%A8%E5%8F%82%E6%95%B0%E6%9C%89%E5%93%AA%E4%BA%9B)
- **X4-34** git log -- <file> 用来查看某个文件的修改历史。按作者过滤的是 --author，完整 diff 是 -p，分支 / 合并关系是 --graph。[原文§git log 常用参数有哪些？](https://xiaolincoding.com/interview/git.html#git-log-%E5%B8%B8%E7%94%A8%E5%8F%82%E6%95%B0%E6%9C%89%E5%93%AA%E4%BA%9B)
- **X4-35** 按作者过滤用 --author，按时间过滤用 --since / --until，按 commit message 关键字过滤用 --grep。--oneline、--graph、--decorate 只改变显示方式，--stat 显示每个 commit 修改了哪些文件、增删行数，都不是过滤。[原文§git log 常用参数有哪些？](https://xiaolincoding.com/interview/git.html#git-log-%E5%B8%B8%E7%94%A8%E5%8F%82%E6%95%B0%E6%9C%89%E5%93%AA%E4%BA%9B)
- **X4-36** 两个空是 --decorate、--all（顺序不限）。完整组合是 git log --oneline --graph --decorate --all。[原文§git log 常用参数有哪些？](https://xiaolincoding.com/interview/git.html#git-log-%E5%B8%B8%E7%94%A8%E5%8F%82%E6%95%B0%E6%9C%89%E5%93%AA%E4%BA%9B)
- **X4-37** 这个组合是日常最常用的一个组合，可以在终端里画出完整的分支图，非常好用。按作者、按时间过滤和查看文件修改历史需要的是 --author、--since / --until 和 -- <file>。[原文§git log 常用参数有哪些？](https://xiaolincoding.com/interview/git.html#git-log-%E5%B8%B8%E7%94%A8%E5%8F%82%E6%95%B0%E6%9C%89%E5%93%AA%E4%BA%9B)
- **X4-38** 原文建议把常用组合起个别名：git config --global alias.lg "log --oneline --graph --decorate --all"。它只是给组合起别名，并不会保存文件，也不会让 git log 默认限制条数或按作者过滤。[原文§git log 常用参数有哪些？](https://xiaolincoding.com/interview/git.html#git-log-%E5%B8%B8%E7%94%A8%E5%8F%82%E6%95%B0%E6%9C%89%E5%93%AA%E4%BA%9B)
- **X4-39** git log 配合参数能非常强大。--oneline：一行显示一个 commit，简洁直观；--graph：用 ASCII 图形显示分支 / 合并关系；-n 5：只看最近 5 条；--author="name"：按作者过滤；--since="1 week ago" --until="yesterday"：按时间过滤；--grep="fix"：按 commit message 关键字过滤；-p：显示每个 commit 的完整 diff；--stat：显示每个 commit 修改了哪些文件、增删行数；git log -- <file>：查看某个文件的修改历史。日常最常用的组合是 git log --oneline --graph --decorate --all，可以在终端里画出完整的分支图，还可以用 git config --global alias.lg "log --oneline --graph --decorate --all" 给它起个别名。[原文§git log 常用参数有哪些？](https://xiaolincoding.com/interview/git.html#git-log-%E5%B8%B8%E7%94%A8%E5%8F%82%E6%95%B0%E6%9C%89%E5%93%AA%E4%BA%9B)

### git tag 有什么用？轻量标签和附注标签有什么区别？

- **X4-40** git tag 用于给某个 commit 打一个固定的名字（通常是版本号，比如 v1.0.0），方便以后找到发布版本、里程碑这类关键节点。逐行显示修改者的是 git blame，二分查找 bug 的是 git bisect。[原文§git tag 有什么用？轻量标签和附注标签有什么区别？](https://xiaolincoding.com/interview/git.html#git-tag-%E6%9C%89%E4%BB%80%E4%B9%88%E7%94%A8-%E8%BD%BB%E9%87%8F%E6%A0%87%E7%AD%BE%E5%92%8C%E9%99%84%E6%B3%A8%E6%A0%87%E7%AD%BE%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)
- **X4-41** 轻量标签只是一个指向 commit 的指针，没有额外的标签对象信息。作为独立对象存储并包含打标签者、日期、说明乃至 GPG 签名的是附注标签；原文示例使用 git tag -a v1.0 -m "Release version 1.0"。D 所说“必须同时带 -a 和 -m”本身也不成立：指定 -a 而不提供 -m/-F 时可在编辑器输入说明，只指定 -m 也可隐含 -a。[原文§git tag 有什么用？轻量标签和附注标签有什么区别？](https://xiaolincoding.com/interview/git.html#git-tag-%E6%9C%89%E4%BB%80%E4%B9%88%E7%94%A8-%E8%BD%BB%E9%87%8F%E6%A0%87%E7%AD%BE%E5%92%8C%E9%99%84%E6%B3%A8%E6%A0%87%E7%AD%BE%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)[核对来源：git-tag 参数说明](https://git-scm.com/docs/git-tag#_description)
- **X4-42** 附注标签会作为独立的对象存储在 Git 里，包含打标签者、日期、说明、甚至 GPG 签名。只是指针、没有额外信息、更像一次性临时书签的是轻量标签。[原文§git tag 有什么用？轻量标签和附注标签有什么区别？](https://xiaolincoding.com/interview/git.html#git-tag-%E6%9C%89%E4%BB%80%E4%B9%88%E7%94%A8-%E8%BD%BB%E9%87%8F%E6%A0%87%E7%AD%BE%E5%92%8C%E9%99%84%E6%B3%A8%E6%A0%87%E7%AD%BE%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)
- **X4-43** 附注标签用 git tag -a v1.0 -m "release 1.0" 创建。git tag v1.0 创建的是轻量标签，git push origin --tags 是推送所有本地标签，git push origin --delete v1.0 是删除远程标签。[原文§git tag 有什么用？轻量标签和附注标签有什么区别？](https://xiaolincoding.com/interview/git.html#git-tag-%E6%9C%89%E4%BB%80%E4%B9%88%E7%94%A8-%E8%BD%BB%E9%87%8F%E6%A0%87%E7%AD%BE%E5%92%8C%E9%99%84%E6%B3%A8%E6%A0%87%E7%AD%BE%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)
- **X4-44** 三个空是打标签者、日期、说明（顺序不限）。附注标签还可以带 GPG 签名。[原文§git tag 有什么用？轻量标签和附注标签有什么区别？](https://xiaolincoding.com/interview/git.html#git-tag-%E6%9C%89%E4%BB%80%E4%B9%88%E7%94%A8-%E8%BD%BB%E9%87%8F%E6%A0%87%E7%AD%BE%E5%92%8C%E9%99%84%E6%B3%A8%E6%A0%87%E7%AD%BE%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)
- **X4-45** 发布版本时应该用附注标签，因为它带有完整的元数据，可追溯性更好；轻量标签更像是一次性的临时书签。[原文§git tag 有什么用？轻量标签和附注标签有什么区别？](https://xiaolincoding.com/interview/git.html#git-tag-%E6%9C%89%E4%BB%80%E4%B9%88%E7%94%A8-%E8%BD%BB%E9%87%8F%E6%A0%87%E7%AD%BE%E5%92%8C%E9%99%84%E6%B3%A8%E6%A0%87%E7%AD%BE%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)
- **X4-46** git push origin v1.0 推送单个标签。git push origin --tags 一次推送所有本地标签，git push origin --delete v1.0 删除远程标签，git tag -d v1.0 删除本地标签。[原文§git tag 有什么用？轻量标签和附注标签有什么区别？](https://xiaolincoding.com/interview/git.html#git-tag-%E6%9C%89%E4%BB%80%E4%B9%88%E7%94%A8-%E8%BD%BB%E9%87%8F%E6%A0%87%E7%AD%BE%E5%92%8C%E9%99%84%E6%B3%A8%E6%A0%87%E7%AD%BE%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)
- **X4-47** git push origin --tags 一次推送所有本地标签；推送单个标签用 git push origin v1.0；删除远程标签用 git push origin --delete v1.0。[原文§git tag 有什么用？轻量标签和附注标签有什么区别？](https://xiaolincoding.com/interview/git.html#git-tag-%E6%9C%89%E4%BB%80%E4%B9%88%E7%94%A8-%E8%BD%BB%E9%87%8F%E6%A0%87%E7%AD%BE%E5%92%8C%E9%99%84%E6%B3%A8%E6%A0%87%E7%AD%BE%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)

- **X4-49** 删除远程标签用 git push origin --delete v1.0。git tag -d v1.0 只删除本地标签，git push origin --tags 是推送所有本地标签，git tag -a 是创建附注标签。[原文§git tag 有什么用？轻量标签和附注标签有什么区别？](https://xiaolincoding.com/interview/git.html#git-tag-%E6%9C%89%E4%BB%80%E4%B9%88%E7%94%A8-%E8%BD%BB%E9%87%8F%E6%A0%87%E7%AD%BE%E5%92%8C%E9%99%84%E6%B3%A8%E6%A0%87%E7%AD%BE%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)
- **X4-50** 正确的有：轻量标签只是指向 commit 的指针；附注标签作为独立对象存储；发布版本应该用附注标签；git push origin --tags 一次推送所有本地标签。打标签者、日期、说明是附注标签才有的；git tag -d v1.0 只删除本地标签，远程标签要用 git push origin --delete v1.0。[原文§git tag 有什么用？轻量标签和附注标签有什么区别？](https://xiaolincoding.com/interview/git.html#git-tag-%E6%9C%89%E4%BB%80%E4%B9%88%E7%94%A8-%E8%BD%BB%E9%87%8F%E6%A0%87%E7%AD%BE%E5%92%8C%E9%99%84%E6%B3%A8%E6%A0%87%E7%AD%BE%E6%9C%89%E4%BB%80%E4%B9%88%E5%8C%BA%E5%88%AB)

### git blame 和 git bisect 分别是做什么的？

- **X4-52** git blame 逐行显示一个文件每一行最后是谁、在哪个 commit、什么时候修改的，用于定位一行具体代码的“作者”和“出处”。二分查找引入 bug 的 commit 是 git bisect 的作用。[原文§git blame 和 git bisect 分别是做什么的？](https://xiaolincoding.com/interview/git.html#git-blame-%E5%92%8C-git-bisect-%E5%88%86%E5%88%AB%E6%98%AF%E5%81%9A%E4%BB%80%E4%B9%88%E7%9A%84)
- **X4-53** git blame 的输出每行前面都标注了 commit hash、作者和时间。good / bad 标记和二分轮数是 git bisect 排查过程中的内容，不是 blame 的输出。[原文§git blame 和 git bisect 分别是做什么的？](https://xiaolincoding.com/interview/git.html#git-blame-%E5%92%8C-git-bisect-%E5%88%86%E5%88%AB%E6%98%AF%E5%81%9A%E4%BB%80%E4%B9%88%E7%9A%84)
- **X4-54** git bisect 用二分查找定位引入 bug 的 commit。逐行显示每行修改者的是 git blame，给 commit 打固定名字的是 git tag，查看文件修改历史的是 git log -- <file>。[原文§git blame 和 git bisect 分别是做什么的？](https://xiaolincoding.com/interview/git.html#git-blame-%E5%92%8C-git-bisect-%E5%88%86%E5%88%AB%E6%98%AF%E5%81%9A%E4%BB%80%E4%B9%88%E7%9A%84)
- **X4-55** 当你知道某个 commit 是好的、某个 commit 是坏的，但不知道中间是哪个 commit 引入了 bug 时，git bisect 可以帮你自动二分。想知道某行代码是谁改的用 git blame。[原文§git blame 和 git bisect 分别是做什么的？](https://xiaolincoding.com/interview/git.html#git-blame-%E5%92%8C-git-bisect-%E5%88%86%E5%88%AB%E6%98%AF%E5%81%9A%E4%BB%80%E4%B9%88%E7%9A%84)
- **X4-56** 这两个命令都是排查“这个问题是谁引入的”的利器，但思路完全不同：blame 逐行定位某一行代码的作者和出处，bisect 用二分查找定位引入 bug 的 commit。[原文§git blame 和 git bisect 分别是做什么的？](https://xiaolincoding.com/interview/git.html#git-blame-%E5%92%8C-git-bisect-%E5%88%86%E5%88%AB%E6%98%AF%E5%81%9A%E4%BB%80%E4%B9%88%E7%9A%84)
- **X4-57** 依次填：bad、good、reset。流程是 git bisect start → git bisect bad（标记当前 HEAD 是坏的）→ git bisect good <old-commit>（标记一个早期好的 commit）→ 测试并继续标记 good 或 bad → git bisect reset（结束排查，回到原来的 HEAD）。[原文§git blame 和 git bisect 分别是做什么的？](https://xiaolincoding.com/interview/git.html#git-blame-%E5%92%8C-git-bisect-%E5%88%86%E5%88%AB%E6%98%AF%E5%81%9A%E4%BB%80%E4%B9%88%E7%9A%84)
- **X4-58** Git 自动跳到中间某个 commit 后，你测试一下，再用 git bisect good 或 git bisect bad 标记；几轮之后 Git 会告诉你就是哪个 commit 引入了 bug，最后用 git bisect reset 结束排查。[原文§git blame 和 git bisect 分别是做什么的？](https://xiaolincoding.com/interview/git.html#git-blame-%E5%92%8C-git-bisect-%E5%88%86%E5%88%AB%E6%98%AF%E5%81%9A%E4%BB%80%E4%B9%88%E7%9A%84)
- **X4-59** git bisect reset 结束排查，回到原来的 HEAD。标记当前 HEAD 为坏的是 git bisect bad，标记早期好的 commit 是 git bisect good <old-commit>，自动跳到中间 commit 是 bisect 在你标记之后自动做的。[原文§git blame 和 git bisect 分别是做什么的？](https://xiaolincoding.com/interview/git.html#git-blame-%E5%92%8C-git-bisect-%E5%88%86%E5%88%AB%E6%98%AF%E5%81%9A%E4%BB%80%E4%B9%88%E7%9A%84)
- **X4-60** 二分查找每轮把范围缩小一半，一个有几百个 commit 的区间，bisect 只需要 log₂(n) 次就能定位，极其高效。[原文§git blame 和 git bisect 分别是做什么的？](https://xiaolincoding.com/interview/git.html#git-blame-%E5%92%8C-git-bisect-%E5%88%86%E5%88%AB%E6%98%AF%E5%81%9A%E4%BB%80%E4%B9%88%E7%9A%84)
- **X4-61** 两个命令都是排查“这个问题是谁引入的”的利器，但思路完全不同。git blame <file> 逐行显示一个文件每一行最后是谁、在哪个 commit、什么时候修改的（输出每行前面标注 commit hash、作者、时间），用于定位一行具体代码的“作者”和“出处”。git bisect 用二分查找定位引入 bug 的 commit：当你知道某个 commit 是好的、某个 commit 是坏的，但不知道中间是哪个 commit 引入了 bug 时，依次执行 git bisect start、git bisect bad（标记当前 HEAD 是坏的）、git bisect good <old-commit>（标记一个早期好的 commit）；Git 自动跳到中间某个 commit，你测试一下后标记 good 或 bad；几轮之后 Git 会告诉你就是这个 commit 引入了 bug；最后用 git bisect reset 结束排查，回到原来的 HEAD。一个有几百个 commit 的区间，bisect 只需要 log₂(n) 次就能定位，极其高效。[原文§git blame 和 git bisect 分别是做什么的？](https://xiaolincoding.com/interview/git.html#git-blame-%E5%92%8C-git-bisect-%E5%88%86%E5%88%AB%E6%98%AF%E5%81%9A%E4%BB%80%E4%B9%88%E7%9A%84)

### .gitignore 里加了文件为什么不生效？

- **X4-62** 核心原因是 .gitignore 只对“还没被 Git 追踪的文件”生效。如果文件已经被 git add + commit 过，再加到 .gitignore 是没用的。取反规则和以 / 结尾的规则是另外的坑，而且以 / 结尾的规则匹配的是目录。[原文§.gitignore 里加了文件为什么不生效？](https://xiaolincoding.com/interview/git.html#gitignore-%E9%87%8C%E5%8A%A0%E4%BA%86%E6%96%87%E4%BB%B6%E4%B8%BA%E4%BB%80%E4%B9%88%E4%B8%8D%E7%94%9F%E6%95%88)
- **X4-63** 已经被 git add + commit 过的文件，之后再加到 .gitignore 是没用的，Git 依然会继续追踪它的改动，因为它已经在版本控制中了。[原文§.gitignore 里加了文件为什么不生效？](https://xiaolincoding.com/interview/git.html#gitignore-%E9%87%8C%E5%8A%A0%E4%BA%86%E6%96%87%E4%BB%B6%E4%B8%BA%E4%BB%80%E4%B9%88%E4%B8%8D%E7%94%9F%E6%95%88)
- **X4-64** 第一步是 git rm --cached <file>，从暂存区移除追踪但保留本地文件，然后再 git commit -m "stop tracking xxx"。git check-ignore -v 用来调试规则，git rm -r --cached <dir> 用于整个目录。[原文§.gitignore 里加了文件为什么不生效？](https://xiaolincoding.com/interview/git.html#gitignore-%E9%87%8C%E5%8A%A0%E4%BA%86%E6%96%87%E4%BB%B6%E4%B8%BA%E4%BB%80%E4%B9%88%E4%B8%8D%E7%94%9F%E6%95%88)
- **X4-65** git rm --cached <file> 从暂存区移除追踪，但保留本地文件。查看文件被哪条规则忽略的是 git check-ignore -v，取反规则是在 .gitignore 里以 ! 开头的规则。[原文§.gitignore 里加了文件为什么不生效？](https://xiaolincoding.com/interview/git.html#gitignore-%E9%87%8C%E5%8A%A0%E4%BA%86%E6%96%87%E4%BB%B6%E4%B8%BA%E4%BB%80%E4%B9%88%E4%B8%8D%E7%94%9F%E6%95%88)
- **X4-66** 对于整个目录可以用 git rm -r --cached <dir>。git rm --cached <file> 针对单个文件，git check-ignore -v 只是调试规则，git commit 是之后提交这次改动的步骤。[原文§.gitignore 里加了文件为什么不生效？](https://xiaolincoding.com/interview/git.html#gitignore-%E9%87%8C%E5%8A%A0%E4%BA%86%E6%96%87%E4%BB%B6%E4%B8%BA%E4%BB%80%E4%B9%88%E4%B8%8D%E7%94%9F%E6%95%88)
- **X4-67** 依次填：--cached、commit。先 git rm --cached <file> 从暂存区移除追踪（保留本地文件），再 git commit -m "stop tracking xxx"，之后 .gitignore 就会对它生效。[原文§.gitignore 里加了文件为什么不生效？](https://xiaolincoding.com/interview/git.html#gitignore-%E9%87%8C%E5%8A%A0%E4%BA%86%E6%96%87%E4%BB%B6%E4%B8%BA%E4%BB%80%E4%B9%88%E4%B8%8D%E7%94%9F%E6%95%88)
- **X4-68** 按原文，.gitignore 里的规则是相对于这个 .gitignore 文件所在的目录生效的，规则写错了位置也会导致不生效。[原文§.gitignore 里加了文件为什么不生效？](https://xiaolincoding.com/interview/git.html#gitignore-%E9%87%8C%E5%8A%A0%E4%BA%86%E6%96%87%E4%BB%B6%E4%B8%BA%E4%BB%80%E4%B9%88%E4%B8%8D%E7%94%9F%E6%95%88)

- **X4-71** git check-ignore -v <file> 会告诉你这个文件是被哪条规则忽略的。git rm --cached 用来停止追踪，git blame 逐行显示修改者，git log -- <file> 查看文件修改历史。[原文§.gitignore 里加了文件为什么不生效？](https://xiaolincoding.com/interview/git.html#gitignore-%E9%87%8C%E5%8A%A0%E4%BA%86%E6%96%87%E4%BB%B6%E4%B8%BA%E4%BB%80%E4%B9%88%E4%B8%8D%E7%94%9F%E6%95%88)
