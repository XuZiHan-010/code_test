# Claude Code 源码解析 原文章节摘编

仅依据各题所列的小林面试笔记原文章节整理；本文件只整理原文口径，不作现行规格认证。原文未覆盖的部分明确标注，不使用其他网站补充。整理日期：2026-10-13。

## 1. 整体架构与核心机制

原文：[Claude Code 源码拆解：51 万行泄漏代码里的架构设计](https://xiaolinnote.com/claudecode/source/cc_source.html)。

### 分层架构与工具循环

- **H1-1** 原文描述的是四层：引擎层负责协调输入、分发工具调用和决定继续还是结束，不含业务逻辑；工具层是全部能力，每个工具遵循统一规范；服务层是共享的基础设施，如调模型 API、上下文压缩和 MCP；安全与治理层像安全网罩在所有层之上，包括权限、Hook 和 Bash 安全分析。[原文§二、架构设计](https://xiaolinnote.com/claudecode/source/cc_source.html#%E4%BA%8C%E3%80%81%E6%9E%B6%E6%9E%84%E8%AE%BE%E8%AE%A1)
- **H1-2** 引擎层只做协调、分发和决策，不知道怎么读文件、改代码、搜索，这些都由工具层负责；这样新增能力只需要新增一个工具，引擎层完全不用改。[原文§二、架构设计](https://xiaolinnote.com/claudecode/source/cc_source.html#%E4%BA%8C%E3%80%81%E6%9E%B6%E6%9E%84%E8%AE%BE%E8%AE%A1)
- **H1-3** 所有工具遵循一个统一的规范，除了定义能做什么，还强制声明三个安全属性：是只读还是会修改、是否具有破坏性需要额外确认、能否与其他工具同时执行；漏掉任何一个，代码就编译不过。[原文§二、架构设计](https://xiaolinnote.com/claudecode/source/cc_source.html#%E4%BA%8C%E3%80%81%E6%9E%B6%E6%9E%84%E8%AE%BE%E8%AE%A1)
- **H1-4** 服务层是所有层共享的基础设施：调大模型 API 不管是主循环还是子 Agent 发起都走这一层，上下文压缩和 MCP 协议也在这里，就像大楼的水电煤，谁也不会各自铺设一套。[原文§二、架构设计](https://xiaolinnote.com/claudecode/source/cc_source.html#%E4%BA%8C%E3%80%81%E6%9E%B6%E6%9E%84%E8%AE%BE%E8%AE%A1)
- **H1-5** 安全与治理层不是各管一块，而是像一张安全网罩在所有层上面：权限系统决定哪些操作要用户确认、哪些可以自动执行，Hook 系统在工具执行前后插入自定义行为，Bash 安全模块分析 Shell 命令。[原文§二、架构设计](https://xiaolinnote.com/claudecode/source/cc_source.html#%E4%BA%8C%E3%80%81%E6%9E%B6%E6%9E%84%E8%AE%BE%E8%AE%A1)
- **H1-6** Bash 安全模块对 Shell 命令做语法级别的分析，检测命令注入、路径逃逸等危险模式，而不是简单地用正则匹配关键词。[原文§二、架构设计](https://xiaolinnote.com/claudecode/source/cc_source.html#%E4%BA%8C%E3%80%81%E6%9E%B6%E6%9E%84%E8%AE%BE%E8%AE%A1)
- **H1-7** ReAct 把每一步拆成三个阶段：Thought 是模型先输出一段思考，说明下一步要做什么；Action 是选择一个工具调用；Observation 是拿到工具结果。三步不断循环，直到模型认为任务完成。[原文§什么是 ReAct](https://xiaolinnote.com/claudecode/source/cc_source.html#%E4%BB%80%E4%B9%88%E6%98%AF-react)
- **H1-8** Claude 的 API 原生支持工具调用，模型直接返回 tool_use 类型的响应，不需要用正则表达式从文本里提取 Action，消除了 ReAct 的格式解析问题，应用层代码变得很简洁。[原文§为什么比 ReAct 更好](https://xiaolinnote.com/claudecode/source/cc_source.html#%E4%B8%BA%E4%BB%80%E4%B9%88%E6%AF%94-react-%E6%9B%B4%E5%A5%BD)
- **H1-9** 模型返回 tool_use 表示要用某个工具，应用层执行该工具，把结果拼入消息列表，再继续循环调用模型；如此往复，直到模型不再请求工具。[原文§Tool-Use Loop](https://xiaolinnote.com/claudecode/source/cc_source.html#tool-use-loop)
- **H1-10** 模型返回 end_turn 表示说完了，循环就 break 跳出，把最终结果返回给用户；返回 tool_use 则 continue 回到循环开头。[原文§Tool-Use Loop](https://xiaolinnote.com/claudecode/source/cc_source.html#tool-use-loop)
- **H1-11** 不是。原文称模型通过 Extended Thinking 在生成最终回复之前先在内部进行一段不可见的深度推理，不占用应用的上下文空间，也不需要应用层解析，所以不必在输出里显式写出 Thought。[原文§为什么比 ReAct 更好](https://xiaolinnote.com/claudecode/source/cc_source.html#%E4%B8%BA%E4%BB%80%E4%B9%88%E6%AF%94-react-%E6%9B%B4%E5%A5%BD)
- **H1-12** 原文自己的对比表也区分了适用场景：ReAct 适合弱模型加简单工具，Tool-Use Loop 适合强模型加复杂工具集；它的优势依赖模型的内部推理能力，以及 API 原生的 tool_use 和 end_turn 支持。[原文§为什么比 ReAct 更好](https://xiaolinnote.com/claudecode/source/cc_source.html#%E4%B8%BA%E4%BB%80%E4%B9%88%E6%AF%94-react-%E6%9B%B4%E5%A5%BD)
- **H1-13** Plan Mode 不是独立的框架，而是在同一个 Tool-Use Loop 里通过 EnterPlanMode 和 ExitPlanMode 两个工具实现：进入后权限降为只读，只能用 Read、Grep、Glob 探索，再把计划写入指定目录；退出时需要用户确认，批准后权限才恢复。[原文§Plan Mode](https://xiaolinnote.com/claudecode/source/cc_source.html#plan-mode)

### 系统提示词与操作安全

- **H1-14** 开场先定义角色：一个帮助用户完成软件工程任务的交互式代理，暗示它应主动采取行动；紧接着划安全红线，例如不能编造 URL，再给出一段安全约束，先说明允许什么，再划定不能做什么。[原文§角色定义与安全红线](https://xiaolinnote.com/claudecode/source/cc_source.html#%E8%A7%92%E8%89%B2%E5%AE%9A%E4%B9%89%E4%B8%8E%E5%AE%89%E5%85%A8%E7%BA%A2%E7%BA%BF)
- **H1-15** 原文称这段约束先说可以做什么，例如已授权的安全测试和 CTF，再划定不能做什么，例如 DoS 和供应链攻击；这种先肯定再约束的写法给了模型清晰的判断依据，比纯禁止清单效果好。[原文§角色定义与安全红线](https://xiaolinnote.com/claudecode/source/cc_source.html#%E8%A7%92%E8%89%B2%E5%AE%9A%E4%B9%89%E4%B8%8E%E5%AE%89%E5%85%A8%E7%BA%A2%E7%BA%BF)
- **H1-16** 提示词要求方案失败后先诊断原因：读报错信息、检查自己的假设、尝试有针对性的修复；不要盲目重试完全相同的操作，也不要因为一次失败就放弃一个可行的方案。[原文§行为准则](https://xiaolinnote.com/claudecode/source/cc_source.html#%E8%A1%8C%E4%B8%BA%E5%87%86%E5%88%99)
- **H1-17** 用可逆性和影响范围两个维度来判断：本地的、可逆的操作，例如编辑文件、运行测试，可以直接执行；难以撤销、影响共享系统或对他人可见的操作，例如删除、强推、推送代码、发消息，要先和用户确认。[原文§操作安全](https://xiaolinnote.com/claudecode/source/cc_source.html#%E6%93%8D%E4%BD%9C%E5%AE%89%E5%85%A8)
- **H1-18** 提示词写明用户批准某个操作一次，并不意味着他在所有场景下都批准这个操作；授权仅对指定的范围有效，不能超出范围。原文称这是为了解决权限蔓延。[原文§操作安全](https://xiaolinnote.com/claudecode/source/cc_source.html#%E6%93%8D%E4%BD%9C%E5%AE%89%E5%85%A8)
- **H1-19** 一是可审查性：调用 Read 工具时界面会清楚显示 Agent 正在读取哪个文件，而执行 cat 时用户只看到一条命令和一大段输出；二是专用工具有专用的权限检查，例如检查文件路径是否在允许范围内。[原文§工具使用指南](https://xiaolinnote.com/claudecode/source/cc_source.html#%E5%B7%A5%E5%85%B7%E4%BD%BF%E7%94%A8%E6%8C%87%E5%8D%97)
- **H1-20** 绝不修改 git config；除非用户明确要求，不执行 push --force、reset --hard 等破坏性命令，不跳过 hooks；始终创建新的 commit 而不用 --amend，因为 commit 若被 pre-commit hook 拒绝其实没有发生，这时 amend 会改到上一个不相关的 commit，可能导致代码丢失。[原文§Git 安全协议](https://xiaolinnote.com/claudecode/source/cc_source.html#git-%E5%AE%89%E5%85%A8%E5%8D%8F%E8%AE%AE)
- **H1-21** 三类：破坏性操作，如删除文件或分支、删表、rm -rf；难以逆转的操作，如 force-push、git reset --hard、修改已发布的 commit；对他人可见的操作，如推送代码、创建或关闭 PR、发送消息。[原文§操作安全](https://xiaolinnote.com/claudecode/source/cc_source.html#%E6%93%8D%E4%BD%9C%E5%AE%89%E5%85%A8)
- **H1-22** 读取文件用 Read，而不是 cat、head、tail 或 sed；编辑文件用 Edit，而不是 sed 或 awk；创建文件用 Write，而不是 echo 重定向；搜索文件用 Glob，而不是 find 或 ls；搜索内容用 Grep，而不是 grep 或 rg。[原文§工具使用指南](https://xiaolinnote.com/claudecode/source/cc_source.html#%E5%B7%A5%E5%85%B7%E4%BD%BF%E7%94%A8%E6%8C%87%E5%8D%97)
- **H1-23** 每次对话开始时把主工作目录、是否为 Git 仓库、操作系统平台、Shell 类型、当前模型等信息注入 System Prompt；没有这些信息，模型可能在 macOS 上执行 apt-get install，或者在 zsh 环境里用 bash 语法。[原文§环境信息注入](https://xiaolinnote.com/claudecode/source/cc_source.html#%E7%8E%AF%E5%A2%83%E4%BF%A1%E6%81%AF%E6%B3%A8%E5%85%A5)
- **H1-24** 提示词要求直奔重点、极度简洁：工具调用之间的文字不超过 25 个词，最终回复不超过 100 个词，先给出答案或行动，不复述用户说过的话；目的是避免 Agent 在每次操作前都写一段废话。[原文§输出风格约束](https://xiaolinnote.com/claudecode/source/cc_source.html#%E8%BE%93%E5%87%BA%E9%A3%8E%E6%A0%BC%E7%BA%A6%E6%9D%9F)
- **H1-25** System Prompt 中间插入了一条分割标记：之上的角色定义、行为准则等对所有用户完全一样，之下的工作目录、CLAUDE.md、记忆和 MCP 服务因人而异。前缀完全相同才能命中 Prompt Cache，所以把稳定内容放在前面可以共享缓存。[原文§分割线与三级缓存](https://xiaolinnote.com/claudecode/source/cc_source.html#%E5%88%86%E5%89%B2%E7%BA%BF%E4%B8%8E%E4%B8%89%E7%BA%A7%E7%BC%93%E5%AD%98)
- **H1-26** 全局缓存是分割线之上的内容跨组织、跨用户共享；组织缓存在同一组织内跨会话共享；会话缓存是同一个 Section 在一次会话内只计算一次。[原文§分割线与三级缓存](https://xiaolinnote.com/claudecode/source/cc_source.html#%E5%88%86%E5%89%B2%E7%BA%BF%E4%B8%8E%E4%B8%89%E7%BA%A7%E7%BC%93%E5%AD%98)
- **H1-27** 只有两次请求的 Prompt 前缀完全相同，API 才会复用上次的计算结果，费用可以降低 90%；对几万 Token 的 System Prompt 来说，命中与否意味着每次请求几美分与几美元的差距。[原文§分割线与三级缓存](https://xiaolinnote.com/claudecode/source/cc_source.html#%E5%88%86%E5%89%B2%E7%BA%BF%E4%B8%8E%E4%B8%89%E7%BA%A7%E7%BC%93%E5%AD%98)

### 记忆与上下文总览

- **H1-28** user 记用户画像：角色、偏好、知识水平；feedback 记行为反馈：该做什么、不该做什么，并记录原因和怎么应用；project 记项目动态：谁在做什么、截止日期和重要决策，相对日期要转成绝对日期；reference 记外部指针：去哪里能找到什么信息。[原文§记什么：四类型分类](https://xiaolinnote.com/claudecode/source/cc_source.html#%E8%AE%B0%E4%BB%80%E4%B9%88-%E5%9B%9B%E7%B1%BB%E5%9E%8B%E5%88%86%E7%B1%BB)
- **H1-29** 核心原则是可以从当前代码推导出来的信息一律不存：代码随时在变，记忆存下来就定格了，一旦代码重构，记忆里的旧位置就成了权威的错误，比没有记忆还糟；这类信息用 grep、git、CLAUDE.md 就能获取。[原文§不记什么：排除清单](https://xiaolinnote.com/claudecode/source/cc_source.html#%E4%B8%8D%E8%AE%B0%E4%BB%80%E4%B9%88-%E6%8E%92%E9%99%A4%E6%B8%85%E5%8D%95)
- **H1-30** 每条记忆存成一个独立的 .md 文件，另有一个不超过 200 行、25KB 的 MEMORY.md 作索引；索引始终加载进 System Prompt，让 Agent 知道有哪些记忆，独立文件只按需加载真正相关的那几条。[原文§怎么存：索引 + 独立文件](https://xiaolinnote.com/claudecode/source/cc_source.html#%E6%80%8E%E4%B9%88%E5%AD%98-%E7%B4%A2%E5%BC%95-%E7%8B%AC%E7%AB%8B%E6%96%87%E4%BB%B6)
- **H1-31** 原文的做法是只读每个记忆文件的头部信息，拼成清单连同用户输入发给便宜的小模型，由它返回最多 5 个相关文件名，再加载这些文件的完整内容；原文在本章开头称用向量相似度检索行为指令效果很差，容易匹配到只含关键词的无关内容。[原文§怎么召回：Sonnet 当秘书](https://xiaolinnote.com/claudecode/source/cc_source.html#%E6%80%8E%E4%B9%88%E5%8F%AC%E5%9B%9E-sonnet-%E5%BD%93%E7%A7%98%E4%B9%A6) [原文§五、记忆系统](https://xiaolinnote.com/claudecode/source/cc_source.html#%E4%BA%94%E3%80%81%E8%AE%B0%E5%BF%86%E7%B3%BB%E7%BB%9F)
- **H1-32** 记忆是某个时间点的观察，不是实时状态；超过 1 天的记忆在注入时会附加一段警告，提醒其中关于代码行为或文件行号的说法可能已经过时，当作事实引用之前要先对照当前代码验证。[原文§怎么召回：Sonnet 当秘书](https://xiaolinnote.com/claudecode/source/cc_source.html#%E6%80%8E%E4%B9%88%E5%8F%AC%E5%9B%9E-sonnet-%E5%BD%93%E7%A7%98%E4%B9%A6)
- **H1-33** 小模型的记忆选择不是等主模型需要时才触发，而是用户提交消息后立刻开始，与主模型的 API 调用并行执行；小模型的延迟只有几百毫秒，主模型的响应回来时选择早已完成，几乎不增加额外延迟。[原文§性能优化：并行预取](https://xiaolinnote.com/claudecode/source/cc_source.html#%E6%80%A7%E8%83%BD%E4%BC%98%E5%8C%96-%E5%B9%B6%E8%A1%8C%E9%A2%84%E5%8F%96)
- **H1-34** 用户正在使用某个工具时，该工具的使用文档类记忆会被过滤掉，因为模型已经在用它，用法文档此刻是噪声；但该工具的已知 bug 和注意事项类记忆仍会被选中，因为正在用的时候最需要知道坑在哪里。[原文§性能优化：并行预取](https://xiaolinnote.com/claudecode/source/cc_source.html#%E6%80%A7%E8%83%BD%E4%BC%98%E5%8C%96-%E5%B9%B6%E8%A1%8C%E9%A2%84%E5%8F%96)
- **H1-35** 单个工具结果超过约 50KB 时，完整内容写到磁盘，消息里只留一个约 2KB 的预览；完整内容并没有丢，模型之后需要某个片段时可以再用 Read 工具读取特定的行范围。[原文§第 1 步：大结果存磁盘](https://xiaolinnote.com/claudecode/source/cc_source.html#%E7%AC%AC-1-%E6%AD%A5-%E5%A4%A7%E7%BB%93%E6%9E%9C%E5%AD%98%E7%A3%81%E7%9B%98)
- **H1-36** Snip 直接移除对话开头的一批老消息，然后插入一个边界标记，告诉模型这之前的内容已经被清理了；它还把释放的 Token 数传给后面的 Auto-Compact，避免两层同时做无谓的压缩。[原文§第 2 步：砍掉远古消息](https://xiaolinnote.com/claudecode/source/cc_source.html#%E7%AC%AC-2-%E6%AD%A5-%E7%A0%8D%E6%8E%89%E8%BF%9C%E5%8F%A4%E6%B6%88%E6%81%AF)
- **H1-37** 可以裁剪的都是可重新获取的工具结果：Read 可以再读、Bash 可以再执行、搜索可以再搜，裁掉后用一个标记占位，模型需要时可以自行重新获取；子 Agent 的输出、任务状态这类不可重复的结果永远不会被裁剪。[原文§第 3 步：裁剪老的工具输出](https://xiaolinnote.com/claudecode/source/cc_source.html#%E7%AC%AC-3-%E6%AD%A5-%E8%A3%81%E5%89%AA%E8%80%81%E7%9A%84%E5%B7%A5%E5%85%B7%E8%BE%93%E5%87%BA)
- **H1-38** Context Collapse 不修改原始消息列表，只在调用 API 的那一刻动态计算一个压缩视图给模型看，完整历史仍然保留；它在上下文达到 90% 和 95% 两级阈值时触发，并且运行在全量摘要之前。[原文§第 4 步：读时投影](https://xiaolinnote.com/claudecode/source/cc_source.html#%E7%AC%AC-4-%E6%AD%A5-%E8%AF%BB%E6%97%B6%E6%8A%95%E5%BD%B1)
- **H1-39** 全量摘要要调用大模型把整段对话总结成结构化摘要，并替换压缩边界之前的所有消息，是代价最高的一层；压缩后模型不记得刚读过的文件，所以还要重新注入最近访问的最多 5 个文件等内容。[原文§第 5 步：全量摘要](https://xiaolinnote.com/claudecode/source/cc_source.html#%E7%AC%AC-5-%E6%AD%A5-%E5%85%A8%E9%87%8F%E6%91%98%E8%A6%81)
- **H1-40** 压缩一定有信息损失，而且每一步的代价递增：存磁盘几乎无损，裁剪旧消息和旧工具输出损失较少且可以重新获取，读时投影中等，全量摘要最大；所以先用代价最小的手段，不够再升级，大部分情况下前三层就够用。[原文§压缩五步走](https://xiaolinnote.com/claudecode/source/cc_source.html#%E5%8E%8B%E7%BC%A9%E4%BA%94%E6%AD%A5%E8%B5%B0)
- **H1-41** 全量摘要连续失败 3 次（比如 API 超时）后系统会自动放弃，不再无限重试，这是熔断器模式，防止一个失败的压缩操作拖垮整个 Agent。[原文§第 5 步：全量摘要](https://xiaolinnote.com/claudecode/source/cc_source.html#%E7%AC%AC-5-%E6%AD%A5-%E5%85%A8%E9%87%8F%E6%91%98%E8%A6%81)

### 补充考点

- **H1-42** 原文的解释是：与其祈求大模型变聪明、别产生幻觉，不如老老实实给这匹野马套上缰绳，用系统去约束它的行为、划好赛道；这反映了从拼模型智商到拼系统求稳的转变，Claude Code 约 80% 的代码都在死磕可靠性，而不是让 AI 更聪明。[原文§Claude Code 源码拆解：51 万行泄漏代码里的架构设计](https://xiaolinnote.com/claudecode/source/cc_source.html#claude-code-%E6%BA%90%E7%A0%81%E6%8B%86%E8%A7%A3-51-%E4%B8%87%E8%A1%8C%E6%B3%84%E6%BC%8F%E4%BB%A3%E7%A0%81%E9%87%8C%E7%9A%84%E6%9E%B6%E6%9E%84%E8%AE%BE%E8%AE%A1)
- **H1-43** ChatBot 是你问一句它答一句的一次性问答；Copilot 是在你写代码时给补全建议，本质上也是一次性预测；Claude Code 的本质是一个 AI Agent，原文强调它和这两者区别很大，不能混为一谈。[原文§一、Claude Code 是什么](https://xiaolinnote.com/claudecode/source/cc_source.html#%E4%B8%80%E3%80%81claude-code-%E6%98%AF%E4%BB%80%E4%B9%88)
- **H1-44** 一般来说，不要对没有阅读过的代码提出修改建议；用户要求查看或修改某个文件时，先把它读一遍，在提出修改建议之前先理解现有代码。[原文§行为准则](https://xiaolinnote.com/claudecode/source/cc_source.html#%E8%A1%8C%E4%B8%BA%E5%87%86%E5%88%99)
- **H1-45** 因为无约束的记忆会迅速膨胀成垃圾堆；限定四种类型是在逼 Agent 做分类决策，每存一条记忆都必须想清楚它到底属于哪一类，而不是一股脑往里塞。[原文§记什么：四类型分类](https://xiaolinnote.com/claudecode/source/cc_source.html#%E8%AE%B0%E4%BB%80%E4%B9%88-%E5%9B%9B%E7%B1%BB%E5%9E%8B%E5%88%86%E7%B1%BB)
- **H1-46** 光记住规则本身不够：遇到边缘情况，例如一个不涉及数据库迁移的纯单元测试，Agent 需要根据 Why 来判断这条规则在这个场景下是否适用；没有 Why，它只能盲目遵守，可能在不该用真实数据库的地方也强行连接。[原文§记什么：四类型分类](https://xiaolinnote.com/claudecode/source/cc_source.html#%E8%AE%B0%E4%BB%80%E4%B9%88-%E5%9B%9B%E7%B1%BB%E5%9E%8B%E5%88%86%E7%B1%BB)
- **H1-47** 因为有人可能只写了 199 行，但每行 500 字，行数没超而字节数爆了；同时检查两个维度才能堵住这个漏洞。[原文§怎么存：索引 + 独立文件](https://xiaolinnote.com/claudecode/source/cc_source.html#%E6%80%8E%E4%B9%88%E5%AD%98-%E7%B4%A2%E5%BC%95-%E7%8B%AC%E7%AB%8B%E6%96%87%E4%BB%B6)

## 2. 主循环 Query

原文：[Claude Code 主循环 Query 图解：一轮对话是怎么跑起来的？](https://xiaolinnote.com/claudecode/source/cc_query_loop.html)。

### 调用链与正常路径

- **H2-1** 模型第一次回复的可能不是答案，而是需要先看某个文件；Claude Code 去读文件并把内容塞回去再问，模型可能又要求跑测试，如此来回好几轮，直到模型给出最终结果。这个调模型、看结果、决定下一步的循环就是主循环。[原文§一、敲完回车，Claude Code 内部到底发生了什么？](https://xiaolinnote.com/claudecode/source/cc_query_loop.html#%E4%B8%80%E3%80%81%E6%95%B2%E5%AE%8C%E5%9B%9E%E8%BD%A6-claude-code-%E5%86%85%E9%83%A8%E5%88%B0%E5%BA%95%E5%8F%91%E7%94%9F%E4%BA%86%E4%BB%80%E4%B9%88)
- **H2-2** 四层从外到内：ask 是 SDK 的一次性调用入口，只负责新建 QueryEngine 并转交；QueryEngine.submitMessage 管会话状态，如消息历史、文件缓存、权限拒绝记录；query 是边干边吐事件的异步生成器；queryLoop 才是 while(true) 的循环本体。[原文§二、从 ask 到 queryLoop：一句话怎么穿过四层调用？](https://xiaolinnote.com/claudecode/source/cc_query_loop.html#%E4%BA%8C%E3%80%81%E4%BB%8E-ask-%E5%88%B0-queryloop-%E4%B8%80%E5%8F%A5%E8%AF%9D%E6%80%8E%E4%B9%88%E7%A9%BF%E8%BF%87%E5%9B%9B%E5%B1%82%E8%B0%83%E7%94%A8)
- **H2-3** query 这层包装把对话生命周期的收尾工作，比如最后还要通知一些清理事件，与核心循环逻辑解耦，让 queryLoop 只管循环，不必操心结束之后还要通知谁。[原文§二、从 ask 到 queryLoop：一句话怎么穿过四层调用？](https://xiaolinnote.com/claudecode/source/cc_query_loop.html#%E4%BA%8C%E3%80%81%E4%BB%8E-ask-%E5%88%B0-queryloop-%E4%B8%80%E5%8F%A5%E8%AF%9D%E6%80%8E%E4%B9%88%E7%A9%BF%E8%BF%87%E5%9B%9B%E5%B1%82%E8%B0%83%E7%94%A8)
- **H2-4** 异步生成器在干活过程中每完成一件事就立刻把结果抛出去；每一层都用 yield* 接力，最里面 queryLoop 抛出的每个事件都能原样传到最外层的调用方，所以模型每吐一段字、每跑完一个工具，界面都能立刻显示。[原文§二、从 ask 到 queryLoop：一句话怎么穿过四层调用？](https://xiaolinnote.com/claudecode/source/cc_query_loop.html#%E4%BA%8C%E3%80%81%E4%BB%8E-ask-%E5%88%B0-queryloop-%E4%B8%80%E5%8F%A5%E8%AF%9D%E6%80%8E%E4%B9%88%E7%A9%BF%E8%BF%87%E5%9B%9B%E5%B1%82%E8%B0%83%E7%94%A8)
- **H2-5** 每一轮开始，主循环要拿到截至目前的完整对话历史，准备发给模型；其中包含之前各轮 assistant 的回复和工具结果。[原文§三、主循环转一圈，到底跑了哪些动作？](https://xiaolinnote.com/claudecode/source/cc_query_loop.html#%E4%B8%89%E3%80%81%E4%B8%BB%E5%BE%AA%E7%8E%AF%E8%BD%AC%E4%B8%80%E5%9C%88-%E5%88%B0%E5%BA%95%E8%B7%91%E4%BA%86%E5%93%AA%E4%BA%9B%E5%8A%A8%E4%BD%9C)
- **H2-6** 先按原样发送消息，只有 API 返回 prompt_too_long（413）拒收时才补救压缩并重试。hasAttemptedReactiveCompact 记录本轮是否已经尝试；压完仍超长就退出，不在同一轮继续压，进入新一轮后才重置。原文的理由是压缩也会调用模型、消耗 token，能不压就不压。 [原文§三、主循环转一圈，到底跑了哪些动作？](https://xiaolinnote.com/claudecode/source/cc_query_loop.html#%E4%B8%89%E3%80%81%E4%B8%BB%E5%BE%AA%E7%8E%AF%E8%BD%AC%E4%B8%80%E5%9C%88-%E5%88%B0%E5%BA%95%E8%B7%91%E4%BA%86%E5%93%AA%E4%BA%9B%E5%8A%A8%E4%BD%9C)
- **H2-7** 主循环一边流式接收一边做两件事：把文字块往上抛出去，让用户即时看到模型在输出；把 tool_use 块攒起来，准备稍后执行。[原文§三、主循环转一圈，到底跑了哪些动作？](https://xiaolinnote.com/claudecode/source/cc_query_loop.html#%E4%B8%89%E3%80%81%E4%B8%BB%E5%BE%AA%E7%8E%AF%E8%BD%AC%E4%B8%80%E5%9C%88-%E5%88%B0%E5%BA%95%E8%B7%91%E4%BA%86%E5%93%AA%E4%BA%9B%E5%8A%A8%E4%BD%9C)
- **H2-8** 判断只有一条：模型返回里有 tool_use 块，就把 needsFollowUp 标记为 true，执行工具后继续循环；没有 tool_use 块，说明模型在直接回答，循环结束并返回 completed。[原文§四、Agent 怎么知道「该用工具」还是「该停下来」？](https://xiaolinnote.com/claudecode/source/cc_query_loop.html#%E5%9B%9B%E3%80%81agent-%E6%80%8E%E4%B9%88%E7%9F%A5%E9%81%93%E3%80%8C%E8%AF%A5%E7%94%A8%E5%B7%A5%E5%85%B7%E3%80%8D%E8%BF%98%E6%98%AF%E3%80%8C%E8%AF%A5%E5%81%9C%E4%B8%8B%E6%9D%A5%E3%80%8D)
- **H2-9** 工具结果跑完后要当作 user 角色的消息塞回消息历史，更新跨轮状态后回到循环开头，模型才能基于这些结果决定下一步。[原文§三、主循环转一圈，到底跑了哪些动作？](https://xiaolinnote.com/claudecode/source/cc_query_loop.html#%E4%B8%89%E3%80%81%E4%B8%BB%E5%BE%AA%E7%8E%AF%E8%BD%AC%E4%B8%80%E5%9C%88-%E5%88%B0%E5%BA%95%E8%B7%91%E4%BA%86%E5%93%AA%E4%BA%9B%E5%8A%A8%E4%BD%9C)
- **H2-10** 每跑一轮，消息历史都会变长，第 20 轮发给模型的历史里就有前 19 轮所有的对话和工具结果；它像滚雪球一样越滚越大，不压缩就会超出上下文窗口。[原文§三、主循环转一圈，到底跑了哪些动作？](https://xiaolinnote.com/claudecode/source/cc_query_loop.html#%E4%B8%89%E3%80%81%E4%B8%BB%E5%BE%AA%E7%8E%AF%E8%BD%AC%E4%B8%80%E5%9C%88-%E5%88%B0%E5%BA%95%E8%B7%91%E4%BA%86%E5%93%AA%E4%BA%9B%E5%8A%A8%E4%BD%9C)
- **H2-11** 退出时主循环会附带一个退出原因码 reason：正常完成是 completed；其他如轮数封顶 max_turns、流式或工具执行时被中断、输入超长、输出超长救不回来、被 Stop Hook 拦下等，各有各的原因码。[原文§四、Agent 怎么知道「该用工具」还是「该停下来」？](https://xiaolinnote.com/claudecode/source/cc_query_loop.html#%E5%9B%9B%E3%80%81agent-%E6%80%8E%E4%B9%88%E7%9F%A5%E9%81%93%E3%80%8C%E8%AF%A5%E7%94%A8%E5%B7%A5%E5%85%B7%E3%80%8D%E8%BF%98%E6%98%AF%E3%80%8C%E8%AF%A5%E5%81%9C%E4%B8%8B%E6%9D%A5%E3%80%8D)
- **H2-12** 调用方传了 maxTurns 参数时才生效：跑到上限就强行止损，防止模型跑飞烧钱；不传则不封顶，由其他退出条件兜底。[原文§四、Agent 怎么知道「该用工具」还是「该停下来」？](https://xiaolinnote.com/claudecode/source/cc_query_loop.html#%E5%9B%9B%E3%80%81agent-%E6%80%8E%E4%B9%88%E7%9F%A5%E9%81%93%E3%80%8C%E8%AF%A5%E7%94%A8%E5%B7%A5%E5%85%B7%E3%80%8D%E8%BF%98%E6%98%AF%E3%80%8C%E8%AF%A5%E5%81%9C%E4%B8%8B%E6%9D%A5%E3%80%8D)
- **H2-13** 返回结构化的 reason，让外层调用者知道是什么原因结束的，方便上报、重试或者给用户友好的提示。[原文§四、Agent 怎么知道「该用工具」还是「该停下来」？](https://xiaolinnote.com/claudecode/source/cc_query_loop.html#%E5%9B%9B%E3%80%81agent-%E6%80%8E%E4%B9%88%E7%9F%A5%E9%81%93%E3%80%8C%E8%AF%A5%E7%94%A8%E5%B7%A5%E5%85%B7%E3%80%8D%E8%BF%98%E6%98%AF%E3%80%8C%E8%AF%A5%E5%81%9C%E4%B8%8B%E6%9D%A5%E3%80%8D)

### 流式执行与并发

- **H2-14** 主循环在模型流式输出时持续监听，一旦识别出一个完整的 tool_use 块，就用 StreamingToolExecutor 的 addTool 把它丢到后台执行，不等模型流完；流完后再用 getRemainingResults 把结果一次性收回来。[原文§五、模型还在吐字、工具就开跑了？这怎么做到的？](https://xiaolinnote.com/claudecode/source/cc_query_loop.html#%E4%BA%94%E3%80%81%E6%A8%A1%E5%9E%8B%E8%BF%98%E5%9C%A8%E5%90%90%E5%AD%97%E3%80%81%E5%B7%A5%E5%85%B7%E5%B0%B1%E5%BC%80%E8%B7%91%E4%BA%86-%E8%BF%99%E6%80%8E%E4%B9%88%E5%81%9A%E5%88%B0%E7%9A%84)
- **H2-15** 第一步等模型完整流完，把所有 tool_use 块收齐；第二步挨个执行这些工具，等全部跑完；第三步把结果塞回去进入下一轮。流程能跑通，但模型吐字时工具在干等，工具执行时模型又在干等，两段时间完全串行。[原文§五、模型还在吐字、工具就开跑了？这怎么做到的？](https://xiaolinnote.com/claudecode/source/cc_query_loop.html#%E4%BA%94%E3%80%81%E6%A8%A1%E5%9E%8B%E8%BF%98%E5%9C%A8%E5%90%90%E5%AD%97%E3%80%81%E5%B7%A5%E5%85%B7%E5%B0%B1%E5%BC%80%E8%B7%91%E4%BA%86-%E8%BF%99%E6%80%8E%E4%B9%88%E5%81%9A%E5%88%B0%E7%9A%84)
- **H2-16** 原文列了最有代表性的 8 个，源码里实际定义了 17 种 reason，其余多是细分子情况；这说明一个工业级的 Agent 主循环要兜住的从来不是正常退出，而是十几种异常退出，每一种背后都对应一个曾经踩过的坑。[原文§四、Agent 怎么知道「该用工具」还是「该停下来」？](https://xiaolinnote.com/claudecode/source/cc_query_loop.html#%E5%9B%9B%E3%80%81agent-%E6%80%8E%E4%B9%88%E7%9F%A5%E9%81%93%E3%80%8C%E8%AF%A5%E7%94%A8%E5%B7%A5%E5%85%B7%E3%80%8D%E8%BF%98%E6%98%AF%E3%80%8C%E8%AF%A5%E5%81%9C%E4%B8%8B%E6%9D%A5%E3%80%8D)
- **H2-17** 朴素做法里模型输出时工具在等、工具执行时模型在等，两段时间完全串行；流式并行让模型生成时间和工具执行时间高度重叠，模型流完时最早启动的工具可能已经返回结果了。[原文§五、模型还在吐字、工具就开跑了？这怎么做到的？](https://xiaolinnote.com/claudecode/source/cc_query_loop.html#%E4%BA%94%E3%80%81%E6%A8%A1%E5%9E%8B%E8%BF%98%E5%9C%A8%E5%90%90%E5%AD%97%E3%80%81%E5%B7%A5%E5%85%B7%E5%B0%B1%E5%BC%80%E8%B7%91%E4%BA%86-%E8%BF%99%E6%80%8E%E4%B9%88%E5%81%9A%E5%88%B0%E7%9A%84)
- **H2-18** 每个工具在定义时就有一个属性，标明它是只读还是会改东西的：只读工具如 Read、Grep、Glob 可以并行，会改状态的工具如 Edit、Write、Bash 必须串行。[原文§五、模型还在吐字、工具就开跑了？这怎么做到的？](https://xiaolinnote.com/claudecode/source/cc_query_loop.html#%E4%BA%94%E3%80%81%E6%A8%A1%E5%9E%8B%E8%BF%98%E5%9C%A8%E5%90%90%E5%AD%97%E3%80%81%E5%B7%A5%E5%85%B7%E5%B0%B1%E5%BC%80%E8%B7%91%E4%BA%86-%E8%BF%99%E6%80%8E%E4%B9%88%E5%81%9A%E5%88%B0%E7%9A%84)
- **H2-19** 如果开发者忘了声明这个属性，框架会 fail-closed 兜底，默认当成会改东西的工具，强制串行执行；宁可慢一点，也不会因为漏写而出现并发踩踏。[原文§五、模型还在吐字、工具就开跑了？这怎么做到的？](https://xiaolinnote.com/claudecode/source/cc_query_loop.html#%E4%BA%94%E3%80%81%E6%A8%A1%E5%9E%8B%E8%BF%98%E5%9C%A8%E5%90%90%E5%AD%97%E3%80%81%E5%B7%A5%E5%85%B7%E5%B0%B1%E5%BC%80%E8%B7%91%E4%BA%86-%E8%BF%99%E6%80%8E%E4%B9%88%E5%81%9A%E5%88%B0%E7%9A%84)
- **H2-20** 同时读 10 个文件互不干扰，所以只读工具可以随便并行；两个写文件操作如果并发跑，可能互相覆盖，所以会改状态的工具必须串行。[原文§五、模型还在吐字、工具就开跑了？这怎么做到的？](https://xiaolinnote.com/claudecode/source/cc_query_loop.html#%E4%BA%94%E3%80%81%E6%A8%A1%E5%9E%8B%E8%BF%98%E5%9C%A8%E5%90%90%E5%AD%97%E3%80%81%E5%B7%A5%E5%85%B7%E5%B0%B1%E5%BC%80%E8%B7%91%E4%BA%86-%E8%BF%99%E6%80%8E%E4%B9%88%E5%81%9A%E5%88%B0%E7%9A%84)
- **H2-21** 因为决定下一步做什么本身就是大模型的工作：只要看它最后吐出来的是文字还是工具调用请求，就知道它的意图了，所以不需要复杂的状态机、意图识别或投票表决。[原文§四、Agent 怎么知道「该用工具」还是「该停下来」？](https://xiaolinnote.com/claudecode/source/cc_query_loop.html#%E5%9B%9B%E3%80%81agent-%E6%80%8E%E4%B9%88%E7%9F%A5%E9%81%93%E3%80%8C%E8%AF%A5%E7%94%A8%E5%B7%A5%E5%85%B7%E3%80%8D%E8%BF%98%E6%98%AF%E3%80%8C%E8%AF%A5%E5%81%9C%E4%B8%8B%E6%9D%A5%E3%80%8D)
- **H2-22** 模型还在流式吐字时被中断，对应 aborted_streaming；工具跑到一半时被中断，对应 aborted_tools。[原文§四、Agent 怎么知道「该用工具」还是「该停下来」？](https://xiaolinnote.com/claudecode/source/cc_query_loop.html#%E5%9B%9B%E3%80%81agent-%E6%80%8E%E4%B9%88%E7%9F%A5%E9%81%93%E3%80%8C%E8%AF%A5%E7%94%A8%E5%B7%A5%E5%85%B7%E3%80%8D%E8%BF%98%E6%98%AF%E3%80%8C%E8%AF%A5%E5%81%9C%E4%B8%8B%E6%9D%A5%E3%80%8D)

### 状态与容错

- **H2-23** 把所有跨轮要传的字段打包进一个 State 对象，每轮开头读出来、结尾构造一个新的写回去；状态如果藏在闭包变量里，调试时根本不知道循环为什么继续，摊在一个对象里，每一轮的现场都一目了然。[原文§6.1 跨轮状态对象：为什么不能用「全局变量」糊弄？](https://xiaolinnote.com/claudecode/source/cc_query_loop.html#_6-1-%E8%B7%A8%E8%BD%AE%E7%8A%B6%E6%80%81%E5%AF%B9%E8%B1%A1-%E4%B8%BA%E4%BB%80%E4%B9%88%E4%B8%8D%E8%83%BD%E7%94%A8%E3%80%8C%E5%85%A8%E5%B1%80%E5%8F%98%E9%87%8F%E3%80%8D%E7%B3%8A%E5%BC%84)
- **H2-24** 原文列出的字段有累积的消息历史、当前轮数、输出截断已恢复的次数 maxOutputTokensRecoveryCount，以及本轮是否已触发过压缩 hasAttemptedReactiveCompact；后两者是计数器和防重复标志，用来避免无限循环。[原文§6.1 跨轮状态对象：为什么不能用「全局变量」糊弄？](https://xiaolinnote.com/claudecode/source/cc_query_loop.html#_6-1-%E8%B7%A8%E8%BD%AE%E7%8A%B6%E6%80%81%E5%AF%B9%E8%B1%A1-%E4%B8%BA%E4%BB%80%E4%B9%88%E4%B8%8D%E8%83%BD%E7%94%A8%E3%80%8C%E5%85%A8%E5%B1%80%E5%8F%98%E9%87%8F%E3%80%8D%E7%B3%8A%E5%BC%84)
- **H2-25** 每一轮迭代的结尾构造一个新的状态对象写回去，而不是散落地修改外部变量；所有还要不要继续的标志都摊在明处，不会因为某个藏起来的变量没复位而出错。[原文§6.1 跨轮状态对象：为什么不能用「全局变量」糊弄？](https://xiaolinnote.com/claudecode/source/cc_query_loop.html#_6-1-%E8%B7%A8%E8%BD%AE%E7%8A%B6%E6%80%81%E5%AF%B9%E8%B1%A1-%E4%B8%BA%E4%BB%80%E4%B9%88%E4%B8%8D%E8%83%BD%E7%94%A8%E3%80%8C%E5%85%A8%E5%B1%80%E5%8F%98%E9%87%8F%E3%80%8D%E7%B3%8A%E5%BC%84)
- **H2-26** API 协议规定每个 tool_use 块必须有一个对应的 tool_result 块与它配对；如果消息历史里有孤立的 tool_use 没有结果，下一轮请求会被 API 直接拒收，报错说工具调用 ID 对不上。[原文§6.2 工具跑挂之后，对话凭什么还能继续？](https://xiaolinnote.com/claudecode/source/cc_query_loop.html#_6-2-%E5%B7%A5%E5%85%B7%E8%B7%91%E6%8C%82%E4%B9%8B%E5%90%8E-%E5%AF%B9%E8%AF%9D%E5%87%AD%E4%BB%80%E4%B9%88%E8%BF%98%E8%83%BD%E7%BB%A7%E7%BB%AD)
- **H2-27** 合成一个工具结果塞回去：类型标明是 tool_result，内容写明这个工具因为什么错误没有执行，打上 is_error 标记，并附上对应的 tool_use_id，让 API 能配对上。[原文§6.2 工具跑挂之后，对话凭什么还能继续？](https://xiaolinnote.com/claudecode/source/cc_query_loop.html#_6-2-%E5%B7%A5%E5%85%B7%E8%B7%91%E6%8C%82%E4%B9%8B%E5%90%8E-%E5%AF%B9%E8%AF%9D%E5%87%AD%E4%BB%80%E4%B9%88%E8%BF%98%E8%83%BD%E7%BB%A7%E7%BB%AD)
- **H2-28** 用户按 Ctrl+C 打断后，主循环为那个没有结果的工具调用补上一条带错误标记的 tool_result，使消息序列仍满足配对规则，下一句话就能接着发给模型。[原文§6.2 工具跑挂之后，对话凭什么还能继续？](https://xiaolinnote.com/claudecode/source/cc_query_loop.html#_6-2-%E5%B7%A5%E5%85%B7%E8%B7%91%E6%8C%82%E4%B9%8B%E5%90%8E-%E5%AF%B9%E8%AF%9D%E5%87%AD%E4%BB%80%E4%B9%88%E8%BF%98%E8%83%BD%E7%BB%A7%E7%BB%AD)
- **H2-29** 模型刚吐完 tool_use 块网络突然断了，工具根本没开始跑；工具跑到一半用户按了 Ctrl+C；模型出了问题、主循环临时切换到备用模型即模型降级，前一个模型吐出的 tool_use 没机会执行。[原文§6.2 工具跑挂之后，对话凭什么还能继续？](https://xiaolinnote.com/claudecode/source/cc_query_loop.html#_6-2-%E5%B7%A5%E5%85%B7%E8%B7%91%E6%8C%82%E4%B9%8B%E5%90%8E-%E5%AF%B9%E8%AF%9D%E5%87%AD%E4%BB%80%E4%B9%88%E8%BF%98%E8%83%BD%E7%BB%A7%E7%BB%AD)
- **H2-30** 原文称每一种异常退出都需要做必要的清理，比如取消正在跑的工具、解锁资源，然后再返回结构化的 reason。[原文§四、Agent 怎么知道「该用工具」还是「该停下来」？](https://xiaolinnote.com/claudecode/source/cc_query_loop.html#%E5%9B%9B%E3%80%81agent-%E6%80%8E%E4%B9%88%E7%9F%A5%E9%81%93%E3%80%8C%E8%AF%A5%E7%94%A8%E5%B7%A5%E5%85%B7%E3%80%8D%E8%BF%98%E6%98%AF%E3%80%8C%E8%AF%A5%E5%81%9C%E4%B8%8B%E6%9D%A5%E3%80%8D)
- **H2-31** 输出超过单次 token 上限时会被截断，原文称 API 中这种状态叫输出 token 上限错误。恢复分两段：首次低上限截断时静默调高上限并重试；仍截断就向模型发续写提示，要求从断点继续、不道歉和回顾、把剩余工作拆小。 [原文§6.3 模型输出被截断了，怎么让用户根本感觉不到？](https://xiaolinnote.com/claudecode/source/cc_query_loop.html#_6-3-%E6%A8%A1%E5%9E%8B%E8%BE%93%E5%87%BA%E8%A2%AB%E6%88%AA%E6%96%AD%E4%BA%86-%E6%80%8E%E4%B9%88%E8%AE%A9%E7%94%A8%E6%88%B7%E6%A0%B9%E6%9C%AC%E6%84%9F%E8%A7%89%E4%B8%8D%E5%88%B0)
- **H2-32** Claude Code 常规默认是 32k，某些灰度场景下由特性开关压到 8k 以控费；模型第一次触发 8k 截断时，主循环不报错，悄悄把上限调到 64k 后重试这一轮，用户只觉得这次答得稍微慢了点。[原文§6.3 模型输出被截断了，怎么让用户根本感觉不到？](https://xiaolinnote.com/claudecode/source/cc_query_loop.html#_6-3-%E6%A8%A1%E5%9E%8B%E8%BE%93%E5%87%BA%E8%A2%AB%E6%88%AA%E6%96%AD%E4%BA%86-%E6%80%8E%E4%B9%88%E8%AE%A9%E7%94%A8%E6%88%B7%E6%A0%B9%E6%9C%AC%E6%84%9F%E8%A7%89%E4%B8%8D%E5%88%B0)
- **H2-33** 因为这种轻推续写不能无限循环，否则会陷入死锁；源码里写死最多 3 次，续写 3 次还不行，主循环就退出，返回输出超长救不回来的原因。[原文§6.3 模型输出被截断了，怎么让用户根本感觉不到？](https://xiaolinnote.com/claudecode/source/cc_query_loop.html#_6-3-%E6%A8%A1%E5%9E%8B%E8%BE%93%E5%87%BA%E8%A2%AB%E6%88%AA%E6%96%AD%E4%BA%86-%E6%80%8E%E4%B9%88%E8%AE%A9%E7%94%A8%E6%88%B7%E6%A0%B9%E6%9C%AC%E6%84%9F%E8%A7%89%E4%B8%8D%E5%88%B0)
- **H2-34** stop_hook_prevented 是被用户配置的自定义钩子主动喊停，例如规定 git push 前必须先跑 lint，没过就拦下；prompt_too_long 是消息历史太长，连压缩之后都塞不进上下文窗口，输入超长救不回来。[原文§四、Agent 怎么知道「该用工具」还是「该停下来」？](https://xiaolinnote.com/claudecode/source/cc_query_loop.html#%E5%9B%9B%E3%80%81agent-%E6%80%8E%E4%B9%88%E7%9F%A5%E9%81%93%E3%80%8C%E8%AF%A5%E7%94%A8%E5%B7%A5%E5%85%B7%E3%80%8D%E8%BF%98%E6%98%AF%E3%80%8C%E8%AF%A5%E5%81%9C%E4%B8%8B%E6%9D%A5%E3%80%8D)
- **H2-35** 原文的做法是先静默恢复：调高上限重试，再提示续写最多 3 次，用户感知不到；超过上限后才退出并返回明确的原因。原文认为工业级的容错是让用户根本感觉不到出过错。[原文§6.3 模型输出被截断了，怎么让用户根本感觉不到？](https://xiaolinnote.com/claudecode/source/cc_query_loop.html#_6-3-%E6%A8%A1%E5%9E%8B%E8%BE%93%E5%87%BA%E8%A2%AB%E6%88%AA%E6%96%AD%E4%BA%86-%E6%80%8E%E4%B9%88%E8%AE%A9%E7%94%A8%E6%88%B7%E6%A0%B9%E6%9C%AC%E6%84%9F%E8%A7%89%E4%B8%8D%E5%88%B0)

### 补充考点

- **H2-36** 秘密不在于模型多聪明，而在于工程上把每一段空闲时间都榨干：流式加并行的设计把模型生成时间和工具执行时间高度重叠，最大化利用每一秒。[原文§五、模型还在吐字、工具就开跑了？这怎么做到的？](https://xiaolinnote.com/claudecode/source/cc_query_loop.html#%E4%BA%94%E3%80%81%E6%A8%A1%E5%9E%8B%E8%BF%98%E5%9C%A8%E5%90%90%E5%AD%97%E3%80%81%E5%B7%A5%E5%85%B7%E5%B0%B1%E5%BC%80%E8%B7%91%E4%BA%86-%E8%BF%99%E6%80%8E%E4%B9%88%E5%81%9A%E5%88%B0%E7%9A%84)

## 3. Compact 上下文压缩

原文：[Claude Code 上下文管理图解：Compact 压缩机制怎么实现？](https://xiaolinnote.com/claudecode/source/cc_compact.html)。

### 问题与五层策略

- **H3-1** 每次请求都要把 system prompt、所有历史对话和当前问题一起塞给模型，这些内容加起来的总长度上限就叫上下文窗口；单位是 token，中文一个字往往占 1 到 2 个 token，英文一个单词平均算 1 个 token。[原文§上下文窗口是个啥？](https://xiaolinnote.com/claudecode/source/cc_compact.html#%E4%B8%8A%E4%B8%8B%E6%96%87%E7%AA%97%E5%8F%A3%E6%98%AF%E4%B8%AA%E5%95%A5)
- **H3-2** 窗口压力来自三处叠加：开局的 system prompt、工具描述和 CLAUDE.md 就要占 5k 到 10k token；每次工具调用留下 tool_use 和 tool_result 两条记录，结果内容会在后续每一轮被反复加载；读大文件动辄几千上万 token。[原文§为什么 agent 更费窗口？](https://xiaolinnote.com/claudecode/source/cc_compact.html#%E4%B8%BA%E4%BB%80%E4%B9%88-agent-%E6%9B%B4%E8%B4%B9%E7%AA%97%E5%8F%A3)
- **H3-3** 原文列了三个硬伤：上下文越长单次推理的 token 消耗越大，账单跟着膨胀；Attention 的计算复杂度与序列长度平方相关，首个 token 的延迟越来越高；还有 Lost in the Middle，中间段的信息模型照样看不清。[原文§加大窗口能解决吗？](https://xiaolinnote.com/claudecode/source/cc_compact.html#%E5%8A%A0%E5%A4%A7%E7%AA%97%E5%8F%A3%E8%83%BD%E8%A7%A3%E5%86%B3%E5%90%97)
- **H3-4** 上下文非常长时，大模型对首尾信息记得清楚，对中间段记忆模糊，塞进去的内容模型可能瞟一眼就过去了；原文称这是注意力机制的固有特性，与窗口多大无关，窗口扩得再大中间段照样看不清。[原文§加大窗口能解决吗？](https://xiaolinnote.com/claudecode/source/cc_compact.html#%E5%8A%A0%E5%A4%A7%E7%AA%97%E5%8F%A3%E8%83%BD%E8%A7%A3%E5%86%B3%E5%90%97)
- **H3-5** 滑动窗口从最老的消息开始砍，而关键决策往往就在最开始，例如用户开局说的这次目标是 A、一定要避免 B 这类全局性指令；被砍掉后 Agent 就会去做被禁止的事。被砍掉的 tool_result 还会让后面的引用变成无源之水。[原文§方案一：滑动窗口](https://xiaolinnote.com/claudecode/source/cc_compact.html#%E6%96%B9%E6%A1%88%E4%B8%80-%E6%BB%91%E5%8A%A8%E7%AA%97%E5%8F%A3)
- **H3-6** 触发时机太死板：某 10 轮可能正是关键节点，一刀切下去关键细节就丢了；某 5 轮可能什么都没干也被压一遍，反而把好好的对话切碎。摘要粒度也粗，一段话装不下细微的状态、错误的修复过程和用户中途改的需求。[原文§方案二：每 N 轮做摘要](https://xiaolinnote.com/claudecode/source/cc_compact.html#%E6%96%B9%E6%A1%88%E4%BA%8C-%E6%AF%8F-n-%E8%BD%AE%E5%81%9A%E6%91%98%E8%A6%81)
- **H3-7** 原文列了三个问题：Agent 的上下文强时序依赖，按相似度召回不管顺序，可能只召回后一步；tool_use 和 tool_result 必须成对出现，切片可能把两者切开；召回 top-k 一定会漏，关键决策可能藏在相似度不高的消息里。[原文§方案三：向量召回历史](https://xiaolinnote.com/claudecode/source/cc_compact.html#%E6%96%B9%E6%A1%88%E4%B8%89-%E5%90%91%E9%87%8F%E5%8F%AC%E5%9B%9E%E5%8E%86%E5%8F%B2)
- **H3-8** 五层从轻到重：大结果存磁盘对付单个超大的工具结果，Snip 砍掉开头已经没用的远古消息，Micro-Compact 按时间衰减清空旧的可重新获取的工具结果，Context Collapse 在调用 API 时投影出压缩视图，Auto-Compact 在逼近窗口上限时全量摘要。[原文§三、Claude Code 的 5 层压缩金字塔](https://xiaolinnote.com/claudecode/source/cc_compact.html#%E4%B8%89%E3%80%81claude-code-%E7%9A%84-5-%E5%B1%82%E5%8E%8B%E7%BC%A9%E9%87%91%E5%AD%97%E5%A1%94)
- **H3-9** 单个工具结果超过 50KB 会被直接拦截，完整内容写到磁盘文件，消息里只留 2KB 预览；同一条消息里所有工具结果加起来还有 200KB 的总量上限，超了就挑大的存磁盘。[原文§第 1 层：大结果存磁盘](https://xiaolinnote.com/claudecode/source/cc_compact.html#%E7%AC%AC-1-%E5%B1%82-%E5%A4%A7%E7%BB%93%E6%9E%9C%E5%AD%98%E7%A3%81%E7%9B%98)
- **H3-10** 完整内容写到磁盘文件，消息里只留一个 2KB 的预览；完整内容并没有丢，模型需要时可以再次用 Read 拿回来，这一层零 API 开销。[原文§第 1 层：大结果存磁盘](https://xiaolinnote.com/claudecode/source/cc_compact.html#%E7%AC%AC-1-%E5%B1%82-%E5%A4%A7%E7%BB%93%E6%9E%9C%E5%AD%98%E7%A3%81%E7%9B%98)
- **H3-11** 删哪些远古消息不是写死的规则：模型在正常回答的那一回合里，顺手用专门的 snip 工具按消息 id 把没用的几条标记出来，真正的删除动作在本地完成，并插入一条这之前的内容已被清理的边界标记。[原文§第 2 层：Snip 砍掉远古消息](https://xiaolinnote.com/claudecode/source/cc_compact.html#%E7%AC%AC-2-%E5%B1%82-snip-%E7%A0%8D%E6%8E%89%E8%BF%9C%E5%8F%A4%E6%B6%88%E6%81%AF)
- **H3-12** Snip 没有独立的摘要调用，只是搭着模型本来就要跑的那一回合做，但要多注入一小段提示、给每条消息加 id 标签，会多花一点 token；所以原文说它不是字面意义上的零 API、纯本地，只是一层很轻的开销。[原文§第 2 层：Snip 砍掉远古消息](https://xiaolinnote.com/claudecode/source/cc_compact.html#%E7%AC%AC-2-%E5%B1%82-snip-%E7%A0%8D%E6%8E%89%E8%BF%9C%E5%8F%A4%E6%B6%88%E6%81%AF)
- **H3-13** Snip 释放出来的 token 数会传给第 5 层 Auto-Compact，目的是避免两层重复压缩。[原文§第 2 层：Snip 砍掉远古消息](https://xiaolinnote.com/claudecode/source/cc_compact.html#%E7%AC%AC-2-%E5%B1%82-snip-%E7%A0%8D%E6%8E%89%E8%BF%9C%E5%8F%A4%E6%B6%88%E6%81%AF)
- **H3-14** Micro-Compact 只清空可重新获取的工具结果，即 Read、Bash、Grep、Glob、WebSearch、Edit、Write 的结果，并保留最近 5 个；子 Agent 输出、Task 状态这类不可重复的结果绝不裁剪。[原文§第 3 层：Micro-Compact 时间衰减](https://xiaolinnote.com/claudecode/source/cc_compact.html#%E7%AC%AC-3-%E5%B1%82-micro-compact-%E6%97%B6%E9%97%B4%E8%A1%B0%E5%87%8F)
- **H3-15** 原文的逻辑是：超过这个时间，大模型 API 端的 Prompt Cache 大概率已经过期了，那不如顺手清掉旧的工具结果。[原文§第 3 层：Micro-Compact 时间衰减](https://xiaolinnote.com/claudecode/source/cc_compact.html#%E7%AC%AC-3-%E5%B1%82-micro-compact-%E6%97%B6%E9%97%B4%E8%A1%B0%E5%87%8F)
- **H3-16** Claude Code 的上下文管理不是一招制敌，而是一套从轻到重的 5 层金字塔；设计原则是能不压就不压，必须压的时候从最轻的手段开始。[原文§三、Claude Code 的 5 层压缩金字塔](https://xiaolinnote.com/claudecode/source/cc_compact.html#%E4%B8%89%E3%80%81claude-code-%E7%9A%84-5-%E5%B1%82%E5%8E%8B%E7%BC%A9%E9%87%91%E5%AD%97%E5%A1%94)
- **H3-17** Context Collapse 不修改原始消息，只在调用 API 的那一刻动态计算一个压缩视图给模型；原对话历史在本地完整保留，模型看到的是压缩版，原文称之为写时不动、读时投影。[原文§第 4 层：Context Collapse 读时投影](https://xiaolinnote.com/claudecode/source/cc_compact.html#%E7%AC%AC-4-%E5%B1%82-context-collapse-%E8%AF%BB%E6%97%B6%E6%8A%95%E5%BD%B1)
- **H3-18** 两者是二选一而非叠着用：内部有个开关决定这次走哪一套，Context Collapse 启用后 Auto-Compact 的触发判断会被直接短路。原因是触发线咬得太近，前者在 90% 和 95% 动作，后者卡在 93%，同时跑会把前者正准备细粒度保存的上下文一锅端掉。[原文§为什么要分 5 层](https://xiaolinnote.com/claudecode/source/cc_compact.html#%E4%B8%BA%E4%BB%80%E4%B9%88%E8%A6%81%E5%88%86-5-%E5%B1%82)

### 触发与信息恢复

- **H3-19** 原文称绝对值阈值的好处是可预测：不管模型窗口未来扩到 500k 还是 1M，触发线永远是上限减掉固定的 20k 加 13k；若用 80% 这种比例，窗口越大剩余预算越大，而摘要任务实际需要的预算没怎么变，那就是浪费。[原文§阈值是怎么算的？](https://xiaolinnote.com/claudecode/source/cc_compact.html#%E9%98%88%E5%80%BC%E6%98%AF%E6%80%8E%E4%B9%88%E7%AE%97%E7%9A%84)
- **H3-20** 原始窗口是模型本身的窗口大小；有效上下文窗口是先从原始窗口里抠掉 20k 之后的值，这 20k 专门留给摘要输出，依据是摘要输出 p99.99 为 17,387 token；触发阈值再从有效窗口里减去 13k 的独立缓冲。[原文§阈值是怎么算的？](https://xiaolinnote.com/claudecode/source/cc_compact.html#%E9%98%88%E5%80%BC%E6%98%AF%E6%80%8E%E4%B9%88%E7%AE%97%E7%9A%84)
- **H3-21** 要记住是两层缓冲叠在一起：真正离原始窗口的距离是 20k 加 13k 约 33k，而不是单看到的 13k；只盯着 13k 去和 17.3k 的实测输出比，会误以为留的冗余比实际输出还小，那是漏看了前面的 20k。[原文§阈值是怎么算的？](https://xiaolinnote.com/claudecode/source/cc_compact.html#%E9%98%88%E5%80%BC%E6%98%AF%E6%80%8E%E4%B9%88%E7%AE%97%E7%9A%84)
- **H3-22** 常见思路有按对话轮数，例如每 50 轮压一次；按 token 数比例，例如占满窗口 80% 就压；按时间间隔，例如每隔 30 分钟压一次。Claude Code 都没用，用的是距离上限的固定缓冲。[原文§五、什么时候触发压缩？](https://xiaolinnote.com/claudecode/source/cc_compact.html#%E4%BA%94%E3%80%81%E4%BB%80%E4%B9%88%E6%97%B6%E5%80%99%E8%A7%A6%E5%8F%91%E5%8E%8B%E7%BC%A9)
- **H3-23** 手动模式可以传一段 customInstructions，告诉摘要器这次压缩请特别关注某方面；例如正在调一个特定的 bug，希望摘要时把这个 bug 的上下文重点保留。[原文§手动和自动触发的区别](https://xiaolinnote.com/claudecode/source/cc_compact.html#%E6%89%8B%E5%8A%A8%E5%92%8C%E8%87%AA%E5%8A%A8%E8%A7%A6%E5%8F%91%E7%9A%84%E5%8C%BA%E5%88%AB)
- **H3-24** 自动压缩通常发生在 Agent 正在干长任务时；如果摘要里塞了一个请问优先 A 还是 B 的问题，下一轮 Agent 就会卡在这里等用户回答，任务流被打断，所以自动模式打开 suppressFollowUpQuestions 禁止生成这类问题。[原文§让模型无缝接活的小心思](https://xiaolinnote.com/claudecode/source/cc_compact.html#%E8%AE%A9%E6%A8%A1%E5%9E%8B%E6%97%A0%E7%BC%9D%E6%8E%A5%E6%B4%BB%E7%9A%84%E5%B0%8F%E5%BF%83%E6%80%9D)
- **H3-25** 自动模式有 circuit breaker：auto-compact 连续失败 3 次，系统就停止重试。源码注释称曾有 1000 多个会话因为反复触发压缩失败、不停重试而烧掉大量 API 费用，这个机制是踩坑踩出来的。[原文§熔断和递归守卫](https://xiaolinnote.com/claudecode/source/cc_compact.html#%E7%86%94%E6%96%AD%E5%92%8C%E9%80%92%E5%BD%92%E5%AE%88%E5%8D%AB)
- **H3-26** 跑摘要本质上也是开了一个子 Agent 调模型，它自己消耗 token，若又触发 auto-compact 就会进入死循环；源码判断 querySource 是 compact 或 session_memory 时直接返回 false，不再触发压缩，把无限递归堵死。[原文§熔断和递归守卫](https://xiaolinnote.com/claudecode/source/cc_compact.html#%E7%86%94%E6%96%AD%E5%92%8C%E9%80%92%E5%BD%92%E5%AE%88%E5%8D%AB)
- **H3-27** 多数框架保留最近 20 轮，把前面的压成一段摘要；Claude Code 把全部消息都送进摘要器重新写一份。原文的理由是即使保留最近几轮，模型对中间部分也看不清，不如全部压成结构化的精华，最近的关键上下文另走附件通道。[原文§全量重写整段对话](https://xiaolinnote.com/claudecode/source/cc_compact.html#%E5%85%A8%E9%87%8F%E9%87%8D%E5%86%99%E6%95%B4%E6%AE%B5%E5%AF%B9%E8%AF%9D)
- **H3-28** 原文按信息的半衰期区分：用户想给登录接口加验证码、方案改成 JWT 这类语义信息，压成一两句话基本不损失，走摘要；某文件第 42 行有个 bug 在改、读到第 100 行、子任务输出在哪里这类状态信息，差一个字就接不上，必须原样恢复，走附件。[原文§全量重写整段对话](https://xiaolinnote.com/claudecode/source/cc_compact.html#%E5%85%A8%E9%87%8F%E9%87%8D%E5%86%99%E6%95%B4%E6%AE%B5%E5%AF%B9%E8%AF%9D)
- **H3-29** 先把对话里占大头的工具调用结果清空，只留一个元数据占位符，涉及 Read、Bash、Grep、Glob、WebFetch、WebSearch、Edit、Write 等工具；对话瞬间瘦一圈，再送进摘要器，摘要器的负担变小，摘要质量也更高。[原文§microcompact 预处理](https://xiaolinnote.com/claudecode/source/cc_compact.html#microcompact-%E9%A2%84%E5%A4%84%E7%90%86)
- **H3-30** 按最近活跃度排序，最近被 Read 过的优先；压缩之后最多重新加载 5 个文件，每个文件最多 5k token，总预算不超过 50k token。[原文§文件恢复：5 个、5K、50K](https://xiaolinnote.com/claudecode/source/cc_compact.html#%E6%96%87%E4%BB%B6%E6%81%A2%E5%A4%8D-5-%E4%B8%AA%E3%80%815k%E3%80%8150k)
- **H3-31** 这三个参数把最近文件这个概念量化了：不是模糊地说保留最近的，而是用 5 个文件、每个 5k、总额 50k 工程化地定义死，这样不管对话多复杂，文件恢复的开销都是可控的。[原文§文件恢复：5 个、5K、50K](https://xiaolinnote.com/claudecode/source/cc_compact.html#%E6%96%87%E4%BB%B6%E6%81%A2%E5%A4%8D-5-%E4%B8%AA%E3%80%815k%E3%80%8150k)
- **H3-32** Context Collapse 目前还是 Anthropic 内部灰度的实验特性，对外发布的版本会把这部分代码整个裁掉；所以公开源码里大概率只能看到 Auto-Compact 这一条线，这也是原文把它当兜底主力来拆的原因。[原文§为什么要分 5 层](https://xiaolinnote.com/claudecode/source/cc_compact.html#%E4%B8%BA%E4%BB%80%E4%B9%88%E8%A6%81%E5%88%86-5-%E5%B1%82)
- **H3-33** CLAUDE.md 不会被注入到压缩后的消息里：它是永久存活的上下文，每一轮都会自动重新加载，不需要塞进压缩后的消息里占地方；原文称全局指令和当下对话由两套机制管理，互不干扰。[原文§CLAUDE.md 不进摘要](https://xiaolinnote.com/claudecode/source/cc_compact.html#claude-md-%E4%B8%8D%E8%BF%9B%E6%91%98%E8%A6%81)
- **H3-34** CLAUDE.md 的内容放在 getUserContext 这个用户级上下文缓存里，每次对话开始先查缓存；压缩时系统把这个缓存清掉，下一轮发起时发现缓存空了，就会从磁盘重新读 CLAUDE.md。[原文§CLAUDE.md 不进摘要](https://xiaolinnote.com/claudecode/source/cc_compact.html#claude-md-%E4%B8%8D%E8%BF%9B%E6%91%98%E8%A6%81)
- **H3-35** system prompt 完全不参与压缩；压缩之后用 buildEffectiveSystemPrompt 重新构造一份，注入最新的工具列表、权限设置和 MCP server 列表，所以对话中途新加的工具，压缩后 Agent 立刻就能用上。[原文§system prompt 和异步任务](https://xiaolinnote.com/claudecode/source/cc_compact.html#system-prompt-%E5%92%8C%E5%BC%82%E6%AD%A5%E4%BB%BB%E5%8A%A1)
- **H3-36** Claude Code 把后台子 Agent 任务的状态，即正在跑、跑完了还是出错了，作为附件重新注入，确保压缩之后主 Agent 依然能看到子任务的进度。[原文§system prompt 和异步任务](https://xiaolinnote.com/claudecode/source/cc_compact.html#system-prompt-%E5%92%8C%E5%BC%82%E6%AD%A5%E4%BB%BB%E5%8A%A1)

### 摘要格式与接续

- **H3-37** 做摘要是让模型只生成文字、总结历史，不是做新动作；模型看到对话里提到某个文件，容易手痒去 Read 或跑 Bash，一旦调了工具这次摘要就废了，所以 prompt 在开头和结尾各警告一遍只能返回文本。[原文§防呆设计：禁止工具调用](https://xiaolinnote.com/claudecode/source/cc_compact.html#%E9%98%B2%E5%91%86%E8%AE%BE%E8%AE%A1-%E7%A6%81%E6%AD%A2%E5%B7%A5%E5%85%B7%E8%B0%83%E7%94%A8)
- **H3-38** 原文称 9 个清单不是凑数，每一项都有它要解决的问题：意图不丢、技术方向不丢、文件状态不丢、错误教训不丢、用户每句话不丢、待办不丢、当前进度不丢。[原文§第 8 项：最细颗粒度的当前进度](https://xiaolinnote.com/claudecode/source/cc_compact.html#%E7%AC%AC-8-%E9%A1%B9-%E6%9C%80%E7%BB%86%E9%A2%97%E7%B2%92%E5%BA%A6%E7%9A%84%E5%BD%93%E5%89%8D%E8%BF%9B%E5%BA%A6)
- **H3-39** 摘要必须包含 9 个固定章节：主要请求和意图、关键技术概念、涉及的文件和代码段、碰到的错误和修复方式、解决的问题、所有用户消息、待办任务、当前正在做的事、下一步建议。[原文§输出格式：XML + 9 部分清单](https://xiaolinnote.com/claudecode/source/cc_compact.html#%E8%BE%93%E5%87%BA%E6%A0%BC%E5%BC%8F-xml-9-%E9%83%A8%E5%88%86%E6%B8%85%E5%8D%95)
- **H3-40** 用户可能在第 30 轮改了需求、第 80 轮提了新约束、第 150 轮说放弃之前的方向，这些是任务方向变化的关键信号，丢一个 Agent 就可能走偏；所以这一项是枚举而不是概括，所有不是 tool result 的用户消息都要列出来。[原文§第 6 项：枚举所有用户消息](https://xiaolinnote.com/claudecode/source/cc_compact.html#%E7%AC%AC-6-%E9%A1%B9-%E6%9E%9A%E4%B8%BE%E6%89%80%E6%9C%89%E7%94%A8%E6%88%B7%E6%B6%88%E6%81%AF)
- **H3-41** 压缩后 Agent 收到摘要的第一件事就是问自己刚才做到哪了；这一项写得越细，接续工作越流畅，写粗了 Agent 会陷入迷茫，可能把上下文重新探索一遍，浪费 token 和时间，所以要细到具体的文件和函数。[原文§第 8 项：最细颗粒度的当前进度](https://xiaolinnote.com/claudecode/source/cc_compact.html#%E7%AC%AC-8-%E9%A1%B9-%E6%9C%80%E7%BB%86%E9%A2%97%E7%B2%92%E5%BA%A6%E7%9A%84%E5%BD%93%E5%89%8D%E8%BF%9B%E5%BA%A6)
- **H3-42** Claude Code 用当前对话的同一个模型做摘要：一是保证质量，便宜的小模型丢东西多，下一轮就接不上；二是能复用主对话 system prompt 部分的 Prompt Cache，省下来的钱比换小模型省的还多。[原文§摘要用什么模型？](https://xiaolinnote.com/claudecode/source/cc_compact.html#%E6%91%98%E8%A6%81%E7%94%A8%E4%BB%80%E4%B9%88%E6%A8%A1%E5%9E%8B)
- **H3-43** buildPostCompactMessages 把对话重写成四段：边界标记记录压缩是自动还是手动、压缩前的 token 数和最后一条消息的 ID；摘要消息承载全部历史；附件包含最近读过的文件、计划文件、激活的技能和异步任务状态；最后是 Hook 的执行结果。[原文§全量重写整段对话](https://xiaolinnote.com/claudecode/source/cc_compact.html#%E5%85%A8%E9%87%8F%E9%87%8D%E5%86%99%E6%95%B4%E6%AE%B5%E5%AF%B9%E8%AF%9D)
- **H3-44** 压缩流水线的第二步会清空 readFileState 文件状态缓存、loadedNestedMemoryPaths 嵌套记忆路径缓存和 getUserContext 用户上下文缓存，保证下一轮对话所有的状态都从干净的起点开始。[原文§压缩流水线五步走](https://xiaolinnote.com/claudecode/source/cc_compact.html#%E5%8E%8B%E7%BC%A9%E6%B5%81%E6%B0%B4%E7%BA%BF%E4%BA%94%E6%AD%A5%E8%B5%B0)
- **H3-45** 第一步把当前所有消息送进摘要器生成摘要文本；第二步清空各种缓存；第三步并发而不是顺序地生成最近文件、异步 Agent 状态、技能配置等附件；第四步用 buildPostCompactMessages 组装成新的消息链；最后用新消息链替换旧的，对话继续。[原文§压缩流水线五步走](https://xiaolinnote.com/claudecode/source/cc_compact.html#%E5%8E%8B%E7%BC%A9%E6%B5%81%E6%B0%B4%E7%BA%BF%E4%BA%94%E6%AD%A5%E8%B5%B0)
- **H3-46** 在对话本身里，旧消息被压缩后回不来，压缩是一次性的、破坏性的操作；只有打开 Kairos 模式这种 transcript 备份机制时，旧消息才会写到本地的 transcript 文件里，可以事后回查。[原文§旧消息真的丢了吗？](https://xiaolinnote.com/claudecode/source/cc_compact.html#%E6%97%A7%E6%B6%88%E6%81%AF%E7%9C%9F%E7%9A%84%E4%B8%A2%E4%BA%86%E5%90%97)
- **H3-47** 原文称旧消息真的丢了，除非打开 Kairos 模式把旧消息写进本地 transcript 文件；不允许回滚是因为那样要维护压缩前后两套消息，状态很复杂，token 也省不下来。[原文§旧消息真的丢了吗？](https://xiaolinnote.com/claudecode/source/cc_compact.html#%E6%97%A7%E6%B6%88%E6%81%AF%E7%9C%9F%E7%9A%84%E4%B8%A2%E4%BA%86%E5%90%97)
- **H3-48** 摘要开头会包上一句话，说明本会话是从之前一次因上下文耗尽而中断的对话延续过来的；模型看到后就不会再问用户想做什么，而是顺着摘要的 Current Work 往下接活，末尾还附带 transcript 文件路径供查细节。[原文§让模型无缝接活的小心思](https://xiaolinnote.com/claudecode/source/cc_compact.html#%E8%AE%A9%E6%A8%A1%E5%9E%8B%E6%97%A0%E7%BC%9D%E6%8E%A5%E6%B4%BB%E7%9A%84%E5%B0%8F%E5%BF%83%E6%80%9D)
- **H3-49** 原文建议先亮观点：Claude Code 用的不是滑动窗口、定期摘要、向量召回那类常见方案，而是全量重写加分通道恢复的工程化思路；最后收口为这套设计反映的不是省 token 的小聪明，而是信息分通道管理的工程哲学。[原文§九、面试该怎么答？](https://xiaolinnote.com/claudecode/source/cc_compact.html#%E4%B9%9D%E3%80%81%E9%9D%A2%E8%AF%95%E8%AF%A5%E6%80%8E%E4%B9%88%E7%AD%94)

### 补充考点

- **H3-50** analysis 块是草稿区，让模型先想清楚再写；它最终会被剥离掉，不进入压缩后的对话，存在的目的纯粹是给模型一个思考的空间，让写出来的摘要质量更高。真正进入对话的是 summary 块。[原文§输出格式：XML + 9 部分清单](https://xiaolinnote.com/claudecode/source/cc_compact.html#%E8%BE%93%E5%87%BA%E6%A0%BC%E5%BC%8F-xml-9-%E9%83%A8%E5%88%86%E6%B8%85%E5%8D%95)
- **H3-51** Errors and fixes 让 Agent 不会重复踩同一个坑，Pending Tasks 让 Agent 知道还有哪些事没干完；原文称剩下的几项也都各司其职。[原文§第 8 项：最细颗粒度的当前进度](https://xiaolinnote.com/claudecode/source/cc_compact.html#%E7%AC%AC-8-%E9%A1%B9-%E6%9C%80%E7%BB%86%E9%A2%97%E7%B2%92%E5%BA%A6%E7%9A%84%E5%BD%93%E5%89%8D%E8%BF%9B%E5%BA%A6)

## 4. 代码检索与 RAG 的取舍

原文：[Claude Code 代码检索图解：为什么用 grep 而不用 RAG？](https://xiaolinnote.com/claudecode/source/cc_grep.html)。

- **H4-1** 模型不能直接看磁盘上的代码，只能看到塞进上下文里的文字，而整个项目的代码又远超上下文窗口；代码检索就是从一堆代码里精准地捞出和当前任务相关的几个片段，再塞给模型。[原文§一、先搞懂「代码检索」到底要解决什么问题](https://xiaolinnote.com/claudecode/source/cc_grep.html#%E4%B8%80%E3%80%81%E5%85%88%E6%90%9E%E6%87%82%E3%80%8C%E4%BB%A3%E7%A0%81%E6%A3%80%E7%B4%A2%E3%80%8D%E5%88%B0%E5%BA%95%E8%A6%81%E8%A7%A3%E5%86%B3%E4%BB%80%E4%B9%88%E9%97%AE%E9%A2%98)
- **H4-2** 四步：切片是把代码文件按函数、按类或按固定行数切成小片段；向量化是让每个片段过 embedding 模型，转成高维向量；建索引是把向量存进 Faiss、Pinecone、Milvus 这类向量数据库；召回是把问题也向量化，找最相似的 Top-K 个片段拼进 prompt。[原文§二、绕不开的 RAG：「先建库再查」的经典思路](https://xiaolinnote.com/claudecode/source/cc_grep.html#%E4%BA%8C%E3%80%81%E7%BB%95%E4%B8%8D%E5%BC%80%E7%9A%84-rag-%E3%80%8C%E5%85%88%E5%BB%BA%E5%BA%93%E5%86%8D%E6%9F%A5%E3%80%8D%E7%9A%84%E7%BB%8F%E5%85%B8%E6%80%9D%E8%B7%AF)
- **H4-3** 代码有严格的结构：一个 200 行的函数按 100 行切开，上半段是 if 的开头、下半段是 else 的结尾，两个片段都没法用；函数 A 调用函数 B 却落在不同片段里，模型只看到 A，不知道 B 是干什么的，幻觉概率大增。[原文§痛点 1：代码不像散文，切不动](https://xiaolinnote.com/claudecode/source/cc_grep.html#%E7%97%9B%E7%82%B9-1-%E4%BB%A3%E7%A0%81%E4%B8%8D%E5%83%8F%E6%95%A3%E6%96%87-%E5%88%87%E4%B8%8D%E5%8A%A8)
- **H4-4** 向量召回的本质是找相似的，不是找对的：要看 getUserById 的实现，它会把 getUserByName、getUserByEmail、fetchUserInfo、queryUser 等一堆相关函数都找来；向量擅长模糊，而代码很多时候要的是精确。[原文§痛点 2：精确匹配的活，向量干不了](https://xiaolinnote.com/claudecode/source/cc_grep.html#%E7%97%9B%E7%82%B9-2-%E7%B2%BE%E7%A1%AE%E5%8C%B9%E9%85%8D%E7%9A%84%E6%B4%BB-%E5%90%91%E9%87%8F%E5%B9%B2%E4%B8%8D%E4%BA%86)
- **H4-5** 一个 commit 改 20 个文件、新增 3 个函数后：重建索引要整个项目重新切片和 embedding，频繁提交时成本很高；不重建，模型查到的全是旧版本；做增量更新又有一堆边界情况，例如哪些 chunk 要删、跨文件的引用关系怎么同步。[原文§痛点 3：代码每天在变，索引咋办](https://xiaolinnote.com/claudecode/source/cc_grep.html#%E7%97%9B%E7%82%B9-3-%E4%BB%A3%E7%A0%81%E6%AF%8F%E5%A4%A9%E5%9C%A8%E5%8F%98-%E7%B4%A2%E5%BC%95%E5%92%8B%E5%8A%9E)
- **H4-6** 在百万行的代码库上跑 RAG，光是建索引就要十几分钟甚至更久，用户打开工具要看着进度条等几分钟才能开始用；原文称这与 Claude Code 打开就能用的设计理念相悖。[原文§痛点 4：冷启动慢得要命](https://xiaolinnote.com/claudecode/source/cc_grep.html#%E7%97%9B%E7%82%B9-4-%E5%86%B7%E5%90%AF%E5%8A%A8%E6%85%A2%E5%BE%97%E8%A6%81%E5%91%BD)
- **H4-7** 召回回来 5 个片段，为什么是这 5 个，模型和工程师都说不清；模型答错时，分不清是召回错了，还是召回对了但模型理解错了，追溯链路非常痛苦。[原文§痛点 5：黑盒，不可解释](https://xiaolinnote.com/claudecode/source/cc_grep.html#%E7%97%9B%E7%82%B9-5-%E9%BB%91%E7%9B%92-%E4%B8%8D%E5%8F%AF%E8%A7%A3%E9%87%8A)
- **H4-8** RAG 是一次性召回 Top-K 个片段、模型据此一次性生成答案，中间没有循环和反悔，召回错了只能将错就错；Claude Code 是边查边推理的循环，模型每一步看到上一步的结果再决定搜什么、读什么，召回错了下一轮自己调整。[原文§七、再深一层：LLM-driven 的多轮迭代循环](https://xiaolinnote.com/claudecode/source/cc_grep.html#%E4%B8%83%E3%80%81%E5%86%8D%E6%B7%B1%E4%B8%80%E5%B1%82-llm-driven-%E7%9A%84%E5%A4%9A%E8%BD%AE%E8%BF%AD%E4%BB%A3%E5%BE%AA%E7%8E%AF)
- **H4-9** Glob 按文件名 pattern 找文件，对应 find；Grep 按内容关键字找代码，对应 grep -r；Read 按需读文件内容，对应 cat 和编辑器跳转。[原文§四、Claude Code 的反向思路：把检索还给模型自己](https://xiaolinnote.com/claudecode/source/cc_grep.html#%E5%9B%9B%E3%80%81claude-code-%E7%9A%84%E5%8F%8D%E5%90%91%E6%80%9D%E8%B7%AF-%E6%8A%8A%E6%A3%80%E7%B4%A2%E8%BF%98%E7%BB%99%E6%A8%A1%E5%9E%8B%E8%87%AA%E5%B7%B1)
- **H4-10** 原文讲了三层考虑：权限统一管控，Bash 是万能工具，把 grep 单独包成工具相当于在这个高频操作上单独画一道权限闸门；输出格式可控，能给出结构化输出和三种粒度，token 浪费更少；性能，底层用 ripgrep。[原文§5.1 Grep：基于 ripgrep，但绝不是简单封装](https://xiaolinnote.com/claudecode/source/cc_grep.html#_5-1-grep-%E5%9F%BA%E4%BA%8E-ripgrep-%E4%BD%86%E7%BB%9D%E4%B8%8D%E6%98%AF%E7%AE%80%E5%8D%95%E5%B0%81%E8%A3%85)
- **H4-11** Grep 的底层是 ripgrep 而不是传统 grep：它用 Rust 写成，多线程并行，并且自动尊重 .gitignore，不去搜 node_modules 这类目录，性能远好于老牌 grep。[原文§5.1 Grep：基于 ripgrep，但绝不是简单封装](https://xiaolinnote.com/claudecode/source/cc_grep.html#_5-1-grep-%E5%9F%BA%E4%BA%8E-ripgrep-%E4%BD%86%E7%BB%9D%E4%B8%8D%E6%98%AF%E7%AE%80%E5%8D%95%E5%B0%81%E8%A3%85)
- **H4-12** 工具描述写明搜索任务永远使用 Grep，绝对不要用 Bash 命令调用 grep 或 rg，并说明 Grep 已针对权限和访问做过优化；这是 Anthropic 在用 system prompt 强制模型走专用工具，不许用 bash 抄近路。[原文§5.1 Grep：基于 ripgrep，但绝不是简单封装](https://xiaolinnote.com/claudecode/source/cc_grep.html#_5-1-grep-%E5%9F%BA%E4%BA%8E-ripgrep-%E4%BD%86%E7%BB%9D%E4%B8%8D%E6%98%AF%E7%AE%80%E5%8D%95%E5%B0%81%E8%A3%85)
- **H4-13** content 返回匹配的具体行；files_with_matches 只返回文件路径，也是默认模式；count 返回匹配数量。模型可以按所需输出粒度选择，减少无用内容占用 token。 [原文§5.1 Grep：基于 ripgrep，但绝不是简单封装](https://xiaolinnote.com/claudecode/source/cc_grep.html#_5-1-grep-%E5%9F%BA%E4%BA%8E-ripgrep-%E4%BD%86%E7%BB%9D%E4%B8%8D%E6%98%AF%E7%AE%80%E5%8D%95%E5%B0%81%E8%A3%85)
- **H4-14** 工具描述的最后一行写明：开放式、需要多轮迭代的搜索，请用 Agent 工具；原文称这是为后面派子 Agent 探索埋下的伏笔。[原文§5.1 Grep：基于 ripgrep，但绝不是简单封装](https://xiaolinnote.com/claudecode/source/cc_grep.html#_5-1-grep-%E5%9F%BA%E4%BA%8E-ripgrep-%E4%BD%86%E7%BB%9D%E4%B8%8D%E6%98%AF%E7%AE%80%E5%8D%95%E5%B0%81%E8%A3%85)
- **H4-15** Glob 按文件名找：例如想看项目里所有的 .tsx 文件，此时没有内容关键字、只知道扩展名，Grep 用不上，而 Glob 支持 **/*.tsx 这种 pattern。[原文§5.2 Glob：按文件名找，按修改时间排序](https://xiaolinnote.com/claudecode/source/cc_grep.html#_5-2-glob-%E6%8C%89%E6%96%87%E4%BB%B6%E5%90%8D%E6%89%BE-%E6%8C%89%E4%BF%AE%E6%94%B9%E6%97%B6%E9%97%B4%E6%8E%92%E5%BA%8F)
- **H4-16** Glob 的结果按修改时间倒序排列，理由是大部分时候最近改过的就是和当前任务最相关的；原文称这是个很朴素但很有效的启发式规则，并未说它总是成立。[原文§5.2 Glob：按文件名找，按修改时间排序](https://xiaolinnote.com/claudecode/source/cc_grep.html#_5-2-glob-%E6%8C%89%E6%96%87%E4%BB%B6%E5%90%8D%E6%89%BE-%E6%8C%89%E4%BF%AE%E6%94%B9%E6%97%B6%E9%97%B4%E6%8E%92%E5%BA%8F)
- **H4-17** Glob 的结果有 100 个文件的硬上限，超出会截断，避免输出爆炸把上下文塞满；模型如果还想看更多，可以收紧 pattern 再搜一次。[原文§5.2 Glob：按文件名找，按修改时间排序](https://xiaolinnote.com/claudecode/source/cc_grep.html#_5-2-glob-%E6%8C%89%E6%96%87%E4%BB%B6%E5%90%8D%E6%89%BE-%E6%8C%89%E4%BF%AE%E6%94%B9%E6%97%B6%E9%97%B4%E6%8E%92%E5%BA%8F)
- **H4-18** Read 默认只读 2000 行，超出会截断；模型可以指定 offset 和 limit 分段读取，例如先读 1 到 2000 行看大概结构，确定位置后再用 offset=3500、limit=500 精准读那一段。[原文§5.3 Read：按需读取，绝不贪心](https://xiaolinnote.com/claudecode/source/cc_grep.html#_5-3-read-%E6%8C%89%E9%9C%80%E8%AF%BB%E5%8F%96-%E7%BB%9D%E4%B8%8D%E8%B4%AA%E5%BF%83)
- **H4-19** 原文的组合用法是先用 Glob 找候选文件，再用 Grep 在这些文件里搜关键字、定位到具体的命中行，最后用 Read 只读命中文件的相关行段；每一步都基于上一步的结果调整方向，而不是一次性召回所有相关代码。[原文§5.4 三件套的组合用法](https://xiaolinnote.com/claudecode/source/cc_grep.html#_5-4-%E4%B8%89%E4%BB%B6%E5%A5%97%E7%9A%84%E7%BB%84%E5%90%88%E7%94%A8%E6%B3%95)
- **H4-20** Read 每次都直接 stat 磁盘文件、读取最新内容，不缓存、不索引、不预处理；刚改完的文件下一次 Read 立刻能看到新内容，原文称没有索引层，就没有索引滞后。[原文§5.3 Read：按需读取，绝不贪心](https://xiaolinnote.com/claudecode/source/cc_grep.html#_5-3-read-%E6%8C%89%E9%9C%80%E8%AF%BB%E5%8F%96-%E7%BB%9D%E4%B8%8D%E8%B4%AA%E5%BF%83)
- **H4-21** 程序员先看目录结构，再全局搜关键字，然后挨个打开候选文件看上下文，是找文件、找内容、看具体代码的三件套，现用现找，不提前建索引；Claude Code 的检索哲学就是让模型像程序员一样自己去找，不预处理、不建库、不算向量。[原文§四、Claude Code 的反向思路：把检索还给模型自己](https://xiaolinnote.com/claudecode/source/cc_grep.html#%E5%9B%9B%E3%80%81claude-code-%E7%9A%84%E5%8F%8D%E5%90%91%E6%80%9D%E8%B7%AF-%E6%8A%8A%E6%A3%80%E7%B4%A2%E8%BF%98%E7%BB%99%E6%A8%A1%E5%9E%8B%E8%87%AA%E5%B7%B1)
- **H4-22** 子 Agent 拿到的是一个精简的工具池，通常是只读工具：Grep、Glob、Read 和只能执行只读命令的 Bash；它不能 Edit、不能 Write，也不能再派子 Agent，以防层层嵌套递归。[原文§六、当三件套不够用：派子 agent 去探索](https://xiaolinnote.com/claudecode/source/cc_grep.html#%E5%85%AD%E3%80%81%E5%BD%93%E4%B8%89%E4%BB%B6%E5%A5%97%E4%B8%8D%E5%A4%9F%E7%94%A8-%E6%B4%BE%E5%AD%90-agent-%E5%8E%BB%E6%8E%A2%E7%B4%A2)
- **H4-23** 调研类任务要 grep 多个关键词、读多个文件，可能要十几次工具调用，主 Agent 的上下文很快被中间结果塞满，真正要解决的问题被挤到角落；子 Agent 有独立的上下文，中间结果留在它那里，只把最终结论返回。[原文§六、当三件套不够用：派子 agent 去探索](https://xiaolinnote.com/claudecode/source/cc_grep.html#%E5%85%AD%E3%80%81%E5%BD%93%E4%B8%89%E4%BB%B6%E5%A5%97%E4%B8%8D%E5%A4%9F%E7%94%A8-%E6%B4%BE%E5%AD%90-agent-%E5%8E%BB%E6%8E%A2%E7%B4%A2)
- **H4-24** 简单、目标明确的定向搜索直接用 Grep、Glob、Read；范围更广的开放式探索和深度研究派 Explore 子 Agent。临界点大约是预期超过 3 次查询：少于 3 次别折腾派 Agent，多于 3 次就别污染主 Agent 的上下文。[原文§六、当三件套不够用：派子 agent 去探索](https://xiaolinnote.com/claudecode/source/cc_grep.html#%E5%85%AD%E3%80%81%E5%BD%93%E4%B8%89%E4%BB%B6%E5%A5%97%E4%B8%8D%E5%A4%9F%E7%94%A8-%E6%B4%BE%E5%AD%90-agent-%E5%8E%BB%E6%8E%A2%E7%B4%A2)
- **H4-25** 模型每一轮都能根据上一步的结果调整方向：Grep 结果是空的就改个关键字再搜；Read 出来的逻辑和预想不一样就再 Grep 几个相关函数；发现这个文件引用了另一个文件，就跟过去看那个文件。[原文§七、再深一层：LLM-driven 的多轮迭代循环](https://xiaolinnote.com/claudecode/source/cc_grep.html#%E4%B8%83%E3%80%81%E5%86%8D%E6%B7%B1%E4%B8%80%E5%B1%82-llm-driven-%E7%9A%84%E5%A4%9A%E8%BD%AE%E8%BF%AD%E4%BB%A3%E5%BE%AA%E7%8E%AF)
- **H4-26** 它是一个 while 循环：每一轮调用模型，模型的回复可能带 tool_use，系统执行工具并把结果回填到对话历史，模型再继续；直到模型不再调用工具，循环才停下来。[原文§七、再深一层：LLM-driven 的多轮迭代循环](https://xiaolinnote.com/claudecode/source/cc_grep.html#%E4%B8%83%E3%80%81%E5%86%8D%E6%B7%B1%E4%B8%80%E5%B1%82-llm-driven-%E7%9A%84%E5%A4%9A%E8%BD%AE%E8%BF%AD%E4%BB%A3%E5%BE%AA%E7%8E%AF)
- **H4-27** 原文列了三种：巨型代码库加跨仓库检索，例如几十个 monorepo、上千万行代码，grep 的性能扛不住；纯语义查询，即描述性、模糊性的问题，用关键字不好搜；多人协作的知识库类查询，代码、文档和 Wiki 混合检索。[原文§九、那 RAG 是不是该被淘汰了？](https://xiaolinnote.com/claudecode/source/cc_grep.html#%E4%B9%9D%E3%80%81%E9%82%A3-rag-%E6%98%AF%E4%B8%8D%E6%98%AF%E8%AF%A5%E8%A2%AB%E6%B7%98%E6%B1%B0%E4%BA%86)
- **H4-28** 最适合单项目、探索式开发、需要精确性、要求实时性的场景，这恰好是大部分 AI 编程工具的主战场；原文同时强调工具是为场景服务的，没有银弹。[原文§九、那 RAG 是不是该被淘汰了？](https://xiaolinnote.com/claudecode/source/cc_grep.html#%E4%B9%9D%E3%80%81%E9%82%A3-rag-%E6%98%AF%E4%B8%8D%E6%98%AF%E8%AF%A5%E8%A2%AB%E6%B7%98%E6%B1%B0%E4%BA%86)
- **H4-29** 冷启动：grep 毫秒级开箱即用，RAG 要先建索引；实时性：grep 现读磁盘，索引会滞后；精确性：grep 是确定性匹配，向量是近似匹配；Token 经济：按需读取，不必给整个代码库做 embedding；可解释性：每步检索透明可审计；决策权：由 LLM 自己决定每一轮搜什么。[原文§八、回到原题：到底为什么 Claude Code 不用 RAG？](https://xiaolinnote.com/claudecode/source/cc_grep.html#%E5%85%AB%E3%80%81%E5%9B%9E%E5%88%B0%E5%8E%9F%E9%A2%98-%E5%88%B0%E5%BA%95%E4%B8%BA%E4%BB%80%E4%B9%88-claude-code-%E4%B8%8D%E7%94%A8-rag)
- **H4-30** 原文明确说没有说 RAG 该淘汰，RAG 仍有它的舞台，只是不在 Claude Code 这种场景里：巨型跨仓库检索、纯语义查询、混合知识库查询都适合 RAG；工具是为场景服务的，没有银弹。[原文§九、那 RAG 是不是该被淘汰了？](https://xiaolinnote.com/claudecode/source/cc_grep.html#%E4%B9%9D%E3%80%81%E9%82%A3-rag-%E6%98%AF%E4%B8%8D%E6%98%AF%E8%AF%A5%E8%A2%AB%E6%B7%98%E6%B1%B0%E4%BA%86)

### 补充考点

- **H4-31** 子 Agent 可以并行派多个：例如同时调研认证、支付、订单三个模块，主 Agent 可以一次性派出三个子 Agent 各干一块，干完同时回来报告，这种并发探索能极大缩短整体时延。[原文§六、当三件套不够用：派子 agent 去探索](https://xiaolinnote.com/claudecode/source/cc_grep.html#%E5%85%AD%E3%80%81%E5%BD%93%E4%B8%89%E4%BB%B6%E5%A5%97%E4%B8%8D%E5%A4%9F%E7%94%A8-%E6%B4%BE%E5%AD%90-agent-%E5%8E%BB%E6%8E%A2%E7%B4%A2)

## 5. 静态规则与动态记忆

原文：[Claude Code 记忆机制图解：为什么不用向量数据库？](https://xiaolinnote.com/claudecode/source/cc_memory.html)。

### 分层与信息结构

- **H5-1** LLM 本身记不住任何东西，是彻头彻尾无状态的：每次都是把系统提示词、所有历史对话和当前问题全部塞进去从头看一遍；所谓记得，是客户端把历史消息又一起发了过去。[原文§LLM 的「金鱼记忆」是怎么回事](https://xiaolinnote.com/claudecode/source/cc_memory.html#llm-%E7%9A%84%E3%80%8C%E9%87%91%E9%B1%BC%E8%AE%B0%E5%BF%86%E3%80%8D%E6%98%AF%E6%80%8E%E4%B9%88%E5%9B%9E%E4%BA%8B)
- **H5-2** 短期记忆就是上下文窗口本身，装着当前这轮对话，窗口快满了就把旧消息压缩一下腾地方；长期记忆持久化存到磁盘、能跨会话活下来，保留的是用户画像、行为偏好、项目动态和外部指针这四类东西。[原文§agent 真正缺的是哪种记忆](https://xiaolinnote.com/claudecode/source/cc_memory.html#agent-%E7%9C%9F%E6%AD%A3%E7%BC%BA%E7%9A%84%E6%98%AF%E5%93%AA%E7%A7%8D%E8%AE%B0%E5%BF%86)
- **H5-3** 原文逐个点评：滑动窗口把关键信息和无关信息混在一起丢，例如第 1 轮说的我是后端工程师；对话摘要会把重要细节压糊，例如网关用的是 Kong 被压成讨论了一些技术栈细节；向量检索相似不等于相关，会召回一堆噪音。[原文§二、业界主流的记忆方案为什么不够看？](https://xiaolinnote.com/claudecode/source/cc_memory.html#%E4%BA%8C%E3%80%81%E4%B8%9A%E7%95%8C%E4%B8%BB%E6%B5%81%E7%9A%84%E8%AE%B0%E5%BF%86%E6%96%B9%E6%A1%88%E4%B8%BA%E4%BB%80%E4%B9%88%E4%B8%8D%E5%A4%9F%E7%9C%8B)
- **H5-4** 分层方案要让 Agent 自己管理三层记忆，每个 prompt 都得训练它什么时候搬、搬哪条，复杂度翻倍；而搬数据的依据本质上还是相关性匹配，依然靠 embedding 召回，向量检索的那几个硬伤一个都没躲过去。[原文§方案四：分层存储 Memory](https://xiaolinnote.com/claudecode/source/cc_memory.html#%E6%96%B9%E6%A1%88%E5%9B%9B-%E5%88%86%E5%B1%82%E5%AD%98%E5%82%A8-memory)
- **H5-5** 原文把重检索、轻写入列为共同病根之一：所有方案都把精力花在怎么查到，对该不该存、存什么基本放任，结果是垃圾进、垃圾出；加上自由文本无约束，记忆库会迅速膨胀成垃圾堆。[原文§这四类方案的共同病根](https://xiaolinnote.com/claudecode/source/cc_memory.html#%E8%BF%99%E5%9B%9B%E7%B1%BB%E6%96%B9%E6%A1%88%E7%9A%84%E5%85%B1%E5%90%8C%E7%97%85%E6%A0%B9)
- **H5-6** 静态层是 CLAUDE.md 体系，属于声明式指令，写好后启动时全量加载，解决怎么协作、项目要遵守什么规则这类确定性的事；动态层是自动记忆系统，属于学习式偏好，Agent 把互动中值得记的事写成记忆文件，下次按需检索。[原文§三、Claude Code 的两层记忆架构鸟瞰](https://xiaolinnote.com/claudecode/source/cc_memory.html#%E4%B8%89%E3%80%81claude-code-%E7%9A%84%E4%B8%A4%E5%B1%82%E8%AE%B0%E5%BF%86%E6%9E%B6%E6%9E%84%E9%B8%9F%E7%9E%B0)
- **H5-7** Managed 放在系统级路径，只有管理员能改，承载公司级强制策略；User 放在用户家目录，是个人的全局偏好，在哪个项目都生效；Project 是项目根目录的 CLAUDE.md 或 .claude/CLAUDE.md，签入 git 让团队共享。[原文§六个层级各管一摊](https://xiaolinnote.com/claudecode/source/cc_memory.html#%E5%85%AD%E4%B8%AA%E5%B1%82%E7%BA%A7%E5%90%84%E7%AE%A1%E4%B8%80%E6%91%8A)
- **H5-8** 原文称规则的来源不同，可见范围和谁能改也不同：项目自己的规则要签入 git 给团队共享，而本地调试用的约定不想签入 git，只想在自己机器上读到；硬塞进一个文件只会打架或混乱。[原文§为什么不能只有一个 CLAUDE.md](https://xiaolinnote.com/claudecode/source/cc_memory.html#%E4%B8%BA%E4%BB%80%E4%B9%88%E4%B8%8D%E8%83%BD%E5%8F%AA%E6%9C%89%E4%B8%80%E4%B8%AA-claude-md)
- **H5-9** Auto 是项目级的自动记忆目录，存 Claude Code 自动写入的偏好；Team 是在 Auto 目录下再开的 team/ 子目录，存团队共享的 AI 学到的偏好，需要 feature flag 开启。这两层存的其实是 MEMORY.md 文件，不是 CLAUDE.md。[原文§六个层级各管一摊](https://xiaolinnote.com/claudecode/source/cc_memory.html#%E5%85%AD%E4%B8%AA%E5%B1%82%E7%BA%A7%E5%90%84%E7%AE%A1%E4%B8%80%E6%91%8A)
- **H5-10** 六层之间是叠加关系而不是覆盖关系：Claude Code 启动时把它们全部拼接进 system prompt，让模型一起看到。[原文§六个层级各管一摊](https://xiaolinnote.com/claudecode/source/cc_memory.html#%E5%85%AD%E4%B8%AA%E5%B1%82%E7%BA%A7%E5%90%84%E7%AE%A1%E4%B8%80%E6%91%8A)
- **H5-11** 在 CLAUDE.md 里写一行 @ 加文件路径，加载时就自动把那个文件的内容读进来拼上，思路和 C 语言的 #include 一样，通用规范不必每个项目复制一遍；背后还要防循环引用和路径遍历。[原文§@include：让 CLAUDE.md 互相引用](https://xiaolinnote.com/claudecode/source/cc_memory.html#include-%E8%AE%A9-claude-md-%E4%BA%92%E7%9B%B8%E5%BC%95%E7%94%A8)
- **H5-12** .claude/rules/ 下每条规则是一个独立的 md 文件，frontmatter 的 paths 字段用 glob 匹配文件路径；加载时比对当前编辑的文件路径，只有匹配上的规则才拼进 system prompt，例如前端规范只在编辑 .tsx 时加载。[原文§条件规则：编辑 .tsx 才加载前端规范](https://xiaolinnote.com/claudecode/source/cc_memory.html#%E6%9D%A1%E4%BB%B6%E8%A7%84%E5%88%99-%E7%BC%96%E8%BE%91-tsx-%E6%89%8D%E5%8A%A0%E8%BD%BD%E5%89%8D%E7%AB%AF%E8%A7%84%E8%8C%83)
- **H5-13** 只限行数不够：团队观察到的极端情况是一个 MEMORY.md 不到 200 行却有 197KB，光看行数察觉不到，塞进 system prompt 就是灾难；所以设了 200 行和 25,000 字节两个限制，任意一个先触发就截断。[原文§截断双保险：防长行索引炸弹](https://xiaolinnote.com/claudecode/source/cc_memory.html#%E6%88%AA%E6%96%AD%E5%8F%8C%E4%BF%9D%E9%99%A9-%E9%98%B2%E9%95%BF%E8%A1%8C%E7%B4%A2%E5%BC%95%E7%82%B8%E5%BC%B9)
- **H5-14** 截断时会主动追加一条警告，告诉模型这个索引被截过了、部分内容没有加载进来，让模型自己有数。[原文§截断双保险：防长行索引炸弹](https://xiaolinnote.com/claudecode/source/cc_memory.html#%E6%88%AA%E6%96%AD%E5%8F%8C%E4%BF%9D%E9%99%A9-%E9%98%B2%E9%95%BF%E8%A1%8C%E7%B4%A2%E5%BC%95%E7%82%B8%E5%BC%B9)
- **H5-15** user 记你是谁，例如写了十年 Go、刚接触 React；feedback 记你不喜欢什么以及确认有效的做法；project 记项目正在发生什么，相对日期要转成绝对日期；reference 记去哪里查什么，例如某类 bug 在哪个项目里追踪。[原文§四种类型为什么这么分](https://xiaolinnote.com/claudecode/source/cc_memory.html#%E5%9B%9B%E7%A7%8D%E7%B1%BB%E5%9E%8B%E4%B8%BA%E4%BB%80%E4%B9%88%E8%BF%99%E4%B9%88%E5%88%86)
- **H5-16** 原文称 feedback 是 Claude Code 最看重的一类，因为它直接决定 Agent 下一次行为对不对；正文必须包含规则本身、Why 和 How to apply 三段，因为只记规则不记原因，遇到边界情况就无法判断该不该破例。[原文§四种类型为什么这么分](https://xiaolinnote.com/claudecode/source/cc_memory.html#%E5%9B%9B%E7%A7%8D%E7%B1%BB%E5%9E%8B%E4%B8%BA%E4%BB%80%E4%B9%88%E8%BF%99%E4%B9%88%E5%88%86)
- **H5-17** 代码是活的，记忆是死的：代码随时在变，记忆存进去就定格了；如果记忆说某个服务在某路径第 42 行，而代码已经重构，这条记忆就成了权威的错误，比没有记忆还糟，所以只记代码推不出来的东西。[原文§该存什么 vs 不该存什么](https://xiaolinnote.com/claudecode/source/cc_memory.html#%E8%AF%A5%E5%AD%98%E4%BB%80%E4%B9%88-vs-%E4%B8%8D%E8%AF%A5%E5%AD%98%E4%BB%80%E4%B9%88)
- **H5-18** 原文设想放任 Agent 自由发挥，它会记下用户今天问了什么问题、上次改了 5 行代码这类流水账和活动日志；三天下来记忆库就成了啥都有、啥都查不准的垃圾桶，所以只允许四种类型。[原文§四种类型为什么这么分](https://xiaolinnote.com/claudecode/source/cc_memory.html#%E5%9B%9B%E7%A7%8D%E7%B1%BB%E5%9E%8B%E4%B8%BA%E4%BB%80%E4%B9%88%E8%BF%99%E4%B9%88%E5%88%86)
- **H5-19** frontmatter 有三个字段：name 是标识；description 说明这条记忆是什么，原文强调这一句话决定了它能不能被检索到；type 是四种类型之一。[原文§存储设计：单文件 + 索引](https://xiaolinnote.com/claudecode/source/cc_memory.html#%E5%AD%98%E5%82%A8%E8%AE%BE%E8%AE%A1-%E5%8D%95%E6%96%87%E4%BB%B6-%E7%B4%A2%E5%BC%95)
- **H5-20** 全部塞进 system prompt 会被记忆撑爆，完全不塞模型又不知道有这些记忆；Claude Code 只塞目录不塞正文：MEMORY.md 索引始终加载，Agent 看 name 和 description 就知道有哪些可选，需要某条时再加载完整内容。[原文§存储设计：单文件 + 索引](https://xiaolinnote.com/claudecode/source/cc_memory.html#%E5%AD%98%E5%82%A8%E8%AE%BE%E8%AE%A1-%E5%8D%95%E6%96%87%E4%BB%B6-%E7%B4%A2%E5%BC%95)

### 抽取、选择与使用

- **H5-21** 让主对话自己写有两个坑：模型分心，要分神去想这条要不要记、属于哪类，回复质量打折；每轮都得在 system prompt 里塞一段记偏好的指令，浪费 token。所以改为每轮对话结束后由后台代理单独抽取。[原文§写入：Extract Memories 代理](https://xiaolinnote.com/claudecode/source/cc_memory.html#%E5%86%99%E5%85%A5-extract-memories-%E4%BB%A3%E7%90%86)
- **H5-22** 触发时机是每轮 query loop 完整结束，也就是模型给出最终回复、没有任何 tool call 之后；通过一个 stopHook 钩子触发，在后台单独跑一个代理来抽取记忆。[原文§写入：Extract Memories 代理](https://xiaolinnote.com/claudecode/source/cc_memory.html#%E5%86%99%E5%85%A5-extract-memories-%E4%BB%A3%E7%90%86)
- **H5-23** 抽取代理不是从零启动一个新对话，而是完美 fork 主对话，共享父对话的 prompt cache；它不用重新加载几千 token 的 system prompt，只需要看着对话历史判断有没有值得记的东西，多花的钱很少。[原文§写入：Extract Memories 代理](https://xiaolinnote.com/claudecode/source/cc_memory.html#%E5%86%99%E5%85%A5-extract-memories-%E4%BB%A3%E7%90%86)
- **H5-24** 抽取代理会把这一轮的内容与现有记忆比对，看有没有重复；还会主动检测 hasMemoryWritesSince，过滤掉它刚刚写过的内容，避免对同一件事反复写记忆。[原文§写入：Extract Memories 代理](https://xiaolinnote.com/claudecode/source/cc_memory.html#%E5%86%99%E5%85%A5-extract-memories-%E4%BB%A3%E7%90%86)
- **H5-25** 先扫一遍这一轮对话里用户的反馈、纠正和信息；再跟现有记忆比对，看有没有重复；如果有新的值得记的内容，就按四种类型分类，写成一个新文件。[原文§写入：Extract Memories 代理](https://xiaolinnote.com/claudecode/source/cc_memory.html#%E5%86%99%E5%85%A5-extract-memories-%E4%BB%A3%E7%90%86)
- **H5-26** 第一步只扫描每个记忆文件的前 30 行，足够提取 frontmatter，不读取记忆的完整内容；这样即使有 200 个记忆文件，扫描开销也很小。[原文§检索：用 Sonnet 选 top-5](https://xiaolinnote.com/claudecode/source/cc_memory.html#%E6%A3%80%E7%B4%A2-%E7%94%A8-sonnet-%E9%80%89-top-5)
- **H5-27** 第一步扫描所有记忆文件的头部信息，只读每个文件的前 30 行；第二步把所有记忆的标题清单拼成一段文本，连同用户当前的问题发给 Sonnet；第三步让 Sonnet 用 JSON schema 返回 top-5 文件名。[原文§检索：用 Sonnet 选 top-5](https://xiaolinnote.com/claudecode/source/cc_memory.html#%E6%A3%80%E7%B4%A2-%E7%94%A8-sonnet-%E9%80%89-top-5)
- **H5-28** 选择器的系统提示词要求只选根据名称和描述确定会有帮助的记忆，不确定的就别选；原文的理解是一旦把错的记忆塞进上下文，整个回复都会被污染，容错率非常低，所以宁可少选，不可错选。[原文§检索：用 Sonnet 选 top-5](https://xiaolinnote.com/claudecode/source/cc_memory.html#%E6%A3%80%E7%B4%A2-%E7%94%A8-sonnet-%E9%80%89-top-5)
- **H5-29** 原文的理解是 Sonnet 比 Haiku 准很多，记忆相关性判错的代价远大于多花的那点钱，所以宁可贵一点也要选准，没有选更便宜的 Haiku。[原文§检索：用 Sonnet 选 top-5](https://xiaolinnote.com/claudecode/source/cc_memory.html#%E6%A3%80%E7%B4%A2-%E7%94%A8-sonnet-%E9%80%89-top-5)
- **H5-30** 上一轮对话已经露过脸的记忆，这次直接排除，让 Sonnet 把 5 个名额花在新候选上，而不是反复挑同样的。[原文§检索：用 Sonnet 选 top-5](https://xiaolinnote.com/claudecode/source/cc_memory.html#%E6%A3%80%E7%B4%A2-%E7%94%A8-sonnet-%E9%80%89-top-5)
- **H5-31** 最近用过的工具的用法参考文档不选，因为当前对话里已经在实际使用这些工具，再塞一份文档是噪音；但工具的警告、坑点、已知问题类记忆要保留，正在用的时候恰好是这些警告最该出现的时候。[原文§检索：用 Sonnet 选 top-5](https://xiaolinnote.com/claudecode/source/cc_memory.html#%E6%A3%80%E7%B4%A2-%E7%94%A8-sonnet-%E9%80%89-top-5)
- **H5-32** 得你主动写：CLAUDE.md 不会自己长出新内容，昨天抱怨过的事，今天换个会话依然要重新强调；动态层要解决的就是让 Agent 在聊天过程中自动把学到的东西记下来，自己学、自己写、自己用。[原文§为什么还需要动态记忆](https://xiaolinnote.com/claudecode/source/cc_memory.html#%E4%B8%BA%E4%BB%80%E4%B9%88%E8%BF%98%E9%9C%80%E8%A6%81%E5%8A%A8%E6%80%81%E8%AE%B0%E5%BF%86)
- **H5-33** 直接拼到 user message 里，模型可能把它当成用户刚说的话；Claude Code 用 system-reminder 标签包裹后注入，并写明这条记忆保存于几天前、据此行动之前先核实是否仍然准确。[原文§注入：system-reminder 包裹 + 老化警告](https://xiaolinnote.com/claudecode/source/cc_memory.html#%E6%B3%A8%E5%85%A5-system-reminder-%E5%8C%85%E8%A3%B9-%E8%80%81%E5%8C%96%E8%AD%A6%E5%91%8A)
- **H5-34** 记忆不是真理，而是历史快照：模型对待记忆应像对待 git log，这是过去发生的事，不是现在的状态；把记忆当成 ground truth，就会闭着眼睛相信已经过时的内容。[原文§第四条：时间感知 + 主动验证](https://xiaolinnote.com/claudecode/source/cc_memory.html#%E7%AC%AC%E5%9B%9B%E6%9D%A1-%E6%97%B6%E9%97%B4%E6%84%9F%E7%9F%A5-%E4%B8%BB%E5%8A%A8%E9%AA%8C%E8%AF%81)
- **H5-35** 今天和昨天的记忆不警告，2 天以前的主动加警告，提醒这是过去的快照；模型应主动验证：记忆里写了文件路径就先检查文件是否存在，写了函数名或 flag 就先 grep，发现冲突就更新或忽略它。[原文§注入：system-reminder 包裹 + 老化警告](https://xiaolinnote.com/claudecode/source/cc_memory.html#%E6%B3%A8%E5%85%A5-system-reminder-%E5%8C%85%E8%A3%B9-%E8%80%81%E5%8C%96%E8%AD%A6%E5%91%8A)
- **H5-36** 相似度只是一个数值，是否相关要靠难定的阈值，错召回了也不知道哪一步出错；小模型给出的是可以解释的自然语言判断，调起来比调阈值容易，一次选择几百 token，成本也比维护向量数据库低。只要候选集合在几百以内，用小模型选择就优于向量检索。[原文§第三条：廉价模型做选择题](https://xiaolinnote.com/claudecode/source/cc_memory.html#%E7%AC%AC%E4%B8%89%E6%9D%A1-%E5%BB%89%E4%BB%B7%E6%A8%A1%E5%9E%8B%E5%81%9A%E9%80%89%E6%8B%A9%E9%A2%98)
- **H5-37** 自由文本无约束就等于垃圾堆，几个月后里面什么都有、什么都查不准；强制四种类型和 frontmatter，是逼 Agent 在写之前先做一次分类决策，想清楚才能写。迁移到自己的项目，就是给记忆定一个 schema，强制每条都填齐。[原文§第一条：结构化优于自由文本](https://xiaolinnote.com/claudecode/source/cc_memory.html#%E7%AC%AC%E4%B8%80%E6%9D%A1-%E7%BB%93%E6%9E%84%E5%8C%96%E4%BC%98%E4%BA%8E%E8%87%AA%E7%94%B1%E6%96%87%E6%9C%AC)
- **H5-38** 不只适用于记忆系统：任何内容总量大但只有少数需要展开的场景都可以套，例如长 RAG 文档、知识库、tool 列表、历史 PR，都可以做成索引加按需展开。[原文§第二条：索引常驻 + 内容按需](https://xiaolinnote.com/claudecode/source/cc_memory.html#%E7%AC%AC%E4%BA%8C%E6%9D%A1-%E7%B4%A2%E5%BC%95%E5%B8%B8%E9%A9%BB-%E5%86%85%E5%AE%B9%E6%8C%89%E9%9C%80)
- **H5-39** 抽取负责写、检索负责读，一写一读让记忆系统转起来；整套机制没有一行 embedding，没有一个向量数据库，全是结构化文件加一个小模型当选择器。[原文§完整闭环图](https://xiaolinnote.com/claudecode/source/cc_memory.html#%E5%AE%8C%E6%95%B4%E9%97%AD%E7%8E%AF%E5%9B%BE)
- **H5-40** 最大的风险不是召回不准，而是召回了一条已经过时的记忆、Agent 闭着眼睛相信；两道防线是时间感知，给 2 天前的记忆主动加 stale 警告，以及主动验证，记忆里写了文件路径、函数或 flag，使用前先 grep 一下。[原文§第四条：时间感知 + 主动验证](https://xiaolinnote.com/claudecode/source/cc_memory.html#%E7%AC%AC%E5%9B%9B%E6%9D%A1-%E6%97%B6%E9%97%B4%E6%84%9F%E7%9F%A5-%E4%B8%BB%E5%8A%A8%E9%AA%8C%E8%AF%81)

### 补充考点

- **H5-41** 原文把 LLM 比作得了失忆症的实习生，每天上班都要靠工位上的便签才知道自己是谁、在做什么；记忆机制要解决的核心问题就是这些便签贴在哪、谁来贴、什么时候撕掉。[原文§agent 真正缺的是哪种记忆](https://xiaolinnote.com/claudecode/source/cc_memory.html#agent-%E7%9C%9F%E6%AD%A3%E7%BC%BA%E7%9A%84%E6%98%AF%E5%93%AA%E7%A7%8D%E8%AE%B0%E5%BF%86)
- **H5-42** 原理是把最近 N 轮对话原样保留，超过 N 轮的就丢掉；LangChain 早期的 buffer window memory 就是这个思路，在新版本里已被官方标记弃用，但思路仍散落在很多框架里。[原文§方案一：滑动窗口 Memory](https://xiaolinnote.com/claudecode/source/cc_memory.html#%E6%96%B9%E6%A1%88%E4%B8%80-%E6%BB%91%E5%8A%A8%E7%AA%97%E5%8F%A3-memory)
- **H5-43** 不直接砍掉旧对话，而是定期用 LLM 把旧对话总结一下，把摘要塞回上下文；对应 LangChain 早期的 summary memory。[原文§方案二：对话摘要 Memory](https://xiaolinnote.com/claudecode/source/cc_memory.html#%E6%96%B9%E6%A1%88%E4%BA%8C-%E5%AF%B9%E8%AF%9D%E6%91%98%E8%A6%81-memory)
- **H5-44** 把每条对话或记忆转成 embedding 向量存进向量数据库，新对话来时把用户的问题也转成向量，召回最相似的前 K 条塞回上下文；代表方案有 Mem0、Letta（原名 MemGPT）和 Zep，其中 Mem0 的论文称在 LoCoMo 长对话记忆基准上能到 91.6 分。[原文§方案三：向量检索 Memory](https://xiaolinnote.com/claudecode/source/cc_memory.html#%E6%96%B9%E6%A1%88%E4%B8%89-%E5%90%91%E9%87%8F%E6%A3%80%E7%B4%A2-memory)

## 6. SubAgent 与多 Agent 协作

原文：[Claude Code 多 Agent 图解：SubAgent 实现机制怎么做？](https://xiaolinnote.com/claudecode/source/cc_multi_agent.html)。

### 分工、隔离与通信

- **H6-1** 原文列了三个麻烦：上下文会爆炸，调研、实现、评审三个阶段的内容全塞进一个上下文，token 不断上涨；职责混乱，一个 Agent 身兼研究员、程序员和评审员，容易跑偏；没法并发，一次只能做一件事。[原文§为什么一个 agent 不够用？](https://xiaolinnote.com/claudecode/source/cc_multi_agent.html#%E4%B8%BA%E4%BB%80%E4%B9%88%E4%B8%80%E4%B8%AA-agent-%E4%B8%8D%E5%A4%9F%E7%94%A8)
- **H6-2** 父子型：主 Agent 遇到子问题时派 subagent 搞定，拿结果回来接着干，最常见；平级协作型：几个 Agent 职责对等，靠共享状态或消息协作，状态同步麻烦、较难落地；主从型：协调者自己不干活，只派 worker、收结果、做合成，是高并发场景的标配。[原文§Multi-Agent 的三种常见形态](https://xiaolinnote.com/claudecode/source/cc_multi_agent.html#multi-agent-%E7%9A%84%E4%B8%89%E7%A7%8D%E5%B8%B8%E8%A7%81%E5%BD%A2%E6%80%81)
- **H6-3** 原文称 subagent 是主 Agent 通过一个特定工具派出去的另一个独立 Agent 实例：每个 subagent 都是真实存在的执行单元，有自己的工具池、上下文和生命周期，跑完把结果打包交回主 Agent。[原文§subagent 在 Claude Code 里到底长啥样？](https://xiaolinnote.com/claudecode/source/cc_multi_agent.html#subagent-%E5%9C%A8-claude-code-%E9%87%8C%E5%88%B0%E5%BA%95%E9%95%BF%E5%95%A5%E6%A0%B7)
- **H6-4** 常规 Subagent 对应父子型；Coordinator 模式对应主从型；Fork Subagent 是父子型的一个特殊优化版本，与缓存有关。[原文§Multi-Agent 的三种常见形态](https://xiaolinnote.com/claudecode/source/cc_multi_agent.html#multi-agent-%E7%9A%84%E4%B8%89%E7%A7%8D%E5%B8%B8%E8%A7%81%E5%BD%A2%E6%80%81)
- **H6-5** 多 Agent 共处一个进程、共享一个底层运行时，隔离不好就会出现子 Agent 污染父 Agent 的状态，或者调了不该调的工具；所以隔离分两个维度：工具隔离管不给子 Agent 不该有的工具，上下文隔离管不让它搅乱父的运行时状态。[原文§二、Subagent 的隔离机制](https://xiaolinnote.com/claudecode/source/cc_multi_agent.html#%E4%BA%8C%E3%80%81subagent-%E7%9A%84%E9%9A%94%E7%A6%BB%E6%9C%BA%E5%88%B6)
- **H6-6** 三道准入门依次判定：所有 subagent 通用的黑名单，禁掉派新 subagent、主动问用户、切换规划模式、停止其他任务的工具；用户自定义的 Agent 再多套一层黑名单；后台异步 Agent 走白名单，只准用事先圈定的一小批工具。[原文§第一维度：给子 agent 发一个定制工具箱](https://xiaolinnote.com/claudecode/source/cc_multi_agent.html#%E7%AC%AC%E4%B8%80%E7%BB%B4%E5%BA%A6-%E7%BB%99%E5%AD%90-agent-%E5%8F%91%E4%B8%80%E4%B8%AA%E5%AE%9A%E5%88%B6%E5%B7%A5%E5%85%B7%E7%AE%B1)
- **H6-7** 如果 subagent 也能调用派新 subagent 的工具，它就能派子子 Agent，子子 Agent 又接着派，层层嵌套没完没了，token 消耗直接起飞；所以通用黑名单首先禁掉能派新 subagent 的工具。[原文§第一维度：给子 agent 发一个定制工具箱](https://xiaolinnote.com/claudecode/source/cc_multi_agent.html#%E7%AC%AC%E4%B8%80%E7%BB%B4%E5%BA%A6-%E7%BB%99%E5%AD%90-agent-%E5%8F%91%E4%B8%80%E4%B8%AA%E5%AE%9A%E5%88%B6%E5%B7%A5%E5%85%B7%E7%AE%B1)
- **H6-8** 原文称子 Agent 不该抢主 Agent 的对话权，因为用户是在跟主 Agent 说话，所以能主动问用户问题的工具在通用黑名单里被禁掉。[原文§第一维度：给子 agent 发一个定制工具箱](https://xiaolinnote.com/claudecode/source/cc_multi_agent.html#%E7%AC%AC%E4%B8%80%E7%BB%B4%E5%BA%A6-%E7%BB%99%E5%AD%90-agent-%E5%8F%91%E4%B8%80%E4%B8%AA%E5%AE%9A%E5%88%B6%E5%B7%A5%E5%85%B7%E7%AE%B1)
- **H6-9** 用户自己写的 Agent，例如在项目里配置的 Markdown agent，没有经过官方审核，所以比内置 Agent 管得再严一点，多防一道更安全。[原文§第一维度：给子 agent 发一个定制工具箱](https://xiaolinnote.com/claudecode/source/cc_multi_agent.html#%E7%AC%AC%E4%B8%80%E7%BB%B4%E5%BA%A6-%E7%BB%99%E5%AD%90-agent-%E5%8F%91%E4%B8%80%E4%B8%AA%E5%AE%9A%E5%88%B6%E5%B7%A5%E5%85%B7%E7%AE%B1)
- **H6-10** Claude Code 按字段决策：读文件的缓存复制一份给子 Agent；写全局状态对子 Agent 直接关闭，改成空操作；注册和结束后台任务的通路保留；每个 subagent 发独立 ID，深度在父的基础上加 1。[原文§第二维度：搭一个隔离的运行环境](https://xiaolinnote.com/claudecode/source/cc_multi_agent.html#%E7%AC%AC%E4%BA%8C%E7%BB%B4%E5%BA%A6-%E6%90%AD%E4%B8%80%E4%B8%AA%E9%9A%94%E7%A6%BB%E7%9A%84%E8%BF%90%E8%A1%8C%E7%8E%AF%E5%A2%83)
- **H6-11** 父 Agent 读过某文件前 100 行，子 Agent 接着读到 200 行，共享的文件读缓存就被刷成 200，父下次会以为自己读过而跳过；全局 UI 状态若让异步 subagent 也能改，会出现两边同时改同一份状态、对不上的问题。[原文§第二维度：搭一个隔离的运行环境](https://xiaolinnote.com/claudecode/source/cc_multi_agent.html#%E7%AC%AC%E4%BA%8C%E7%BB%B4%E5%BA%A6-%E6%90%AD%E4%B8%80%E4%B8%AA%E9%9A%94%E7%A6%BB%E7%9A%84%E8%BF%90%E8%A1%8C%E7%8E%AF%E5%A2%83)
- **H6-12** 默认形态下 subagent 更像一次重型工具调用，父派它出去、它跑完把结果交回来，父没法中途给在跑的子 Agent 插话，消息基本是子到父的单向通知；团队模式开启后才升级成双向消息驱动，父能往子的信箱里扔字条。[原文§三、父子 Agent 是怎么通信的](https://xiaolinnote.com/claudecode/source/cc_multi_agent.html#%E4%B8%89%E3%80%81%E7%88%B6%E5%AD%90-agent-%E6%98%AF%E6%80%8E%E4%B9%88%E9%80%9A%E4%BF%A1%E7%9A%84)
- **H6-13** 父到子发消息依赖 SendMessage 工具，而它的 isEnabled 挂的就是有没有开 agent-teams：没开团队模式，主 Agent 的工具箱里根本没有它；团队模式是实验特性，外部用户要显式开启，所以默认形态只是单向。[原文§团队（agent-teams）模式：父子之间才真正双向对讲](https://xiaolinnote.com/claudecode/source/cc_multi_agent.html#%E5%9B%A2%E9%98%9F-agent-teams-%E6%A8%A1%E5%BC%8F-%E7%88%B6%E5%AD%90%E4%B9%8B%E9%97%B4%E6%89%8D%E7%9C%9F%E6%AD%A3%E5%8F%8C%E5%90%91%E5%AF%B9%E8%AE%B2)
- **H6-14** subagent 很快跑完时，父 Agent 在前台阻塞等待，结果作为工具调用的返回值交回；跑超过 2 分钟会自动转到后台，完成时把通知拼成一段 XML、伪装成一条用户消息，放进父 Agent 的待处理消息队列。[原文§默认形态：派出去，跑完把结果交回来](https://xiaolinnote.com/claudecode/source/cc_multi_agent.html#%E9%BB%98%E8%AE%A4%E5%BD%A2%E6%80%81-%E6%B4%BE%E5%87%BA%E5%8E%BB-%E8%B7%91%E5%AE%8C%E6%8A%8A%E7%BB%93%E6%9E%9C%E4%BA%A4%E5%9B%9E%E6%9D%A5)
- **H6-15** 三点理由：LLM 对 XML 非常友好，能自然解析出语义；XML 是纯文本，可以直接塞进对话历史，不必再走工具结果的字段结构；伪装成用户消息后，天然复用 agentic loop 的处理逻辑，父 Agent 不需要额外的状态机去等通知。[原文§默认形态：派出去，跑完把结果交回来](https://xiaolinnote.com/claudecode/source/cc_multi_agent.html#%E9%BB%98%E8%AE%A4%E5%BD%A2%E6%80%81-%E6%B4%BE%E5%87%BA%E5%8E%BB-%E8%B7%91%E5%AE%8C%E6%8A%8A%E7%BB%93%E6%9E%9C%E4%BA%A4%E5%9B%9E%E6%9D%A5)
- **H6-16** 调函数等返回的同步思路无法在子任务跑的几分钟里递进新要求，也难以同时指挥多个 subagent；消息驱动下，父往子的信箱里扔一张字条就走、不站着等，子干完通过另一条信道把结果送回，没有主线程阻塞。[原文§团队（agent-teams）模式：父子之间才真正双向对讲](https://xiaolinnote.com/claudecode/source/cc_multi_agent.html#%E5%9B%A2%E9%98%9F-agent-teams-%E6%A8%A1%E5%BC%8F-%E7%88%B6%E5%AD%90%E4%B9%8B%E9%97%B4%E6%89%8D%E7%9C%9F%E6%AD%A3%E5%8F%8C%E5%90%91%E5%AF%B9%E8%AE%B2)
- **H6-17** subagent 的 agentic loop 在每一轮工具调用结束后去看一眼自己的信箱，有新字条就作为用户消息注入自己的对话历史，带着新消息进入下一轮 LLM 调用。[原文§团队（agent-teams）模式：父子之间才真正双向对讲](https://xiaolinnote.com/claudecode/source/cc_multi_agent.html#%E5%9B%A2%E9%98%9F-agent-teams-%E6%A8%A1%E5%BC%8F-%E7%88%B6%E5%AD%90%E4%B9%8B%E9%97%B4%E6%89%8D%E7%9C%9F%E6%AD%A3%E5%8F%8C%E5%90%91%E5%AF%B9%E8%AE%B2)
- **H6-18** Claude Code 会自动把它唤醒：从磁盘上保存的对话 transcript 里恢复子 Agent 的完整对话历史，拼上新消息，重新跑起来；所以 subagent 即使完成了也不是死了，父 Agent 随时可以叫醒它继续干。[原文§团队（agent-teams）模式：父子之间才真正双向对讲](https://xiaolinnote.com/claudecode/source/cc_multi_agent.html#%E5%9B%A2%E9%98%9F-agent-teams-%E6%A8%A1%E5%BC%8F-%E7%88%B6%E5%AD%90%E4%B9%8B%E9%97%B4%E6%89%8D%E7%9C%9F%E6%AD%A3%E5%8F%8C%E5%90%91%E5%AF%B9%E8%AE%B2)

### Fork 与缓存

- **H6-19** Claude Code 的 system prompt 有上万 token；每派一个带独立 system prompt 的 subagent，API 就得把这一万多 token 重新从头算一遍，代价是 input token 重新计费和首 token 延迟变长，派得越频繁开销越大。[原文§subagent 的隐藏成本](https://xiaolinnote.com/claudecode/source/cc_multi_agent.html#subagent-%E7%9A%84%E9%9A%90%E8%97%8F%E6%88%90%E6%9C%AC)
- **H6-20** 让子 Agent 的 API 请求前缀与父 Agent 字节级一致：system prompt 内容、用户上下文、系统上下文、工具池的顺序和定义、对话历史的前缀这五样都必须和父完全相同，Anthropic 一侧识别出前缀就走缓存。[原文§Fork 的核心思路：派一个「字节级相同」的分身](https://xiaolinnote.com/claudecode/source/cc_multi_agent.html#fork-%E7%9A%84%E6%A0%B8%E5%BF%83%E6%80%9D%E8%B7%AF-%E6%B4%BE%E4%B8%80%E4%B8%AA%E3%80%8C%E5%AD%97%E8%8A%82%E7%BA%A7%E7%9B%B8%E5%90%8C%E3%80%8D%E7%9A%84%E5%88%86%E8%BA%AB)
- **H6-21** prompt 缓存命中的条件是字节级别完全相同，而不是内容大致相同：系统 prompt 一个字不一样、工具列表顺序不一样，甚至空格位置不一样，都会直接没命中缓存。[原文§subagent 的隐藏成本](https://xiaolinnote.com/claudecode/source/cc_multi_agent.html#subagent-%E7%9A%84%E9%9A%90%E8%97%8F%E6%88%90%E6%9C%AC)
- **H6-22** 重新调用一次生成函数，可能因为某个功能开关的缓存状态或某个动态字段的值变了，生成的 prompt 与父 Agent 差一个字符，缓存就没了；所以 Fork 的生成函数返回空串，直接原样使用父已经渲染好的那份字节。[原文§一个有意思的细节：system prompt 不重新生成](https://xiaolinnote.com/claudecode/source/cc_multi_agent.html#%E4%B8%80%E4%B8%AA%E6%9C%89%E6%84%8F%E6%80%9D%E7%9A%84%E7%BB%86%E8%8A%82-system-prompt-%E4%B8%8D%E9%87%8D%E6%96%B0%E7%94%9F%E6%88%90)
- **H6-23** FORK_AGENT 的工具设为通配，直接用父的完整工具池；模型设为 inherit，继承父的模型；权限模式是 bubble，权限弹窗浮到父终端；最大轮数 200；生成 system prompt 的函数直接返回空字符串。[原文§一个有意思的细节：system prompt 不重新生成](https://xiaolinnote.com/claudecode/source/cc_multi_agent.html#%E4%B8%80%E4%B8%AA%E6%9C%89%E6%84%8F%E6%80%9D%E7%9A%84%E7%BB%86%E8%8A%82-system-prompt-%E4%B8%8D%E9%87%8D%E6%96%B0%E7%94%9F%E6%88%90)
- **H6-24** API 请求的前缀如果和之前某次请求一样，这段前缀可以不重新算、直接走缓存，价钱只要原来的 10%，延迟也大幅降低。[原文§subagent 的隐藏成本](https://xiaolinnote.com/claudecode/source/cc_multi_agent.html#subagent-%E7%9A%84%E9%9A%90%E8%97%8F%E6%88%90%E6%9C%AC)
- **H6-25** 需要父 Agent 的完整上下文、又不想污染父主循环的任务适合 Fork，例如生成 PR 描述、运行 /btw 做 post-turn 总结；有明确专业分工的任务，例如专门搜代码或专门做规划，适合 system prompt 定制的常规 subagent。[原文§什么时候用 Fork，什么时候用常规 subagent？](https://xiaolinnote.com/claudecode/source/cc_multi_agent.html#%E4%BB%80%E4%B9%88%E6%97%B6%E5%80%99%E7%94%A8-fork-%E4%BB%80%E4%B9%88%E6%97%B6%E5%80%99%E7%94%A8%E5%B8%B8%E8%A7%84-subagent)
- **H6-26** Fork 机制和 Coordinator 模式互斥：isForkSubagentEnabled 在功能开关打开后，遇到协调者模式或非交互会话就返回 false。原因是协调者派的 worker 本来就是异步的，两个机制职责重叠，只留一个。[原文§什么时候用 Fork，什么时候用常规 subagent？](https://xiaolinnote.com/claudecode/source/cc_multi_agent.html#%E4%BB%80%E4%B9%88%E6%97%B6%E5%80%99%E7%94%A8-fork-%E4%BB%80%E4%B9%88%E6%97%B6%E5%80%99%E7%94%A8%E5%B8%B8%E8%A7%84-subagent)
- **H6-27** 在缓存友好的场景下，Fork 能把 subagent 的成本降到原来的 10% 左右；这意味着 subagent 可以调得更频繁，原本因为成本不敢派的活现在都能派了，系统的能力边界随之扩大，所以成本优化本身就是能力的一部分。[原文§Fork 的工程启示](https://xiaolinnote.com/claudecode/source/cc_multi_agent.html#fork-%E7%9A%84%E5%B7%A5%E7%A8%8B%E5%90%AF%E7%A4%BA)

### Coordinator 与 worker

- **H6-28** 常规模式下主 Agent 是全能型选手，读代码、写代码、跑测试、做规划都干，只在需要时派 subagent；Coordinator 模式下它不干实际工作，只做派 worker、收结果、合成答案三件事，这一角色由 system prompt 强制约束。[原文§核心设计：主 agent 退化成「纯协调者」](https://xiaolinnote.com/claudecode/source/cc_multi_agent.html#%E6%A0%B8%E5%BF%83%E8%AE%BE%E8%AE%A1-%E4%B8%BB-agent-%E9%80%80%E5%8C%96%E6%88%90%E3%80%8C%E7%BA%AF%E5%8D%8F%E8%B0%83%E8%80%85%E3%80%8D)
- **H6-29** 原文用老板带团队来解释：把任务拆给不同的专家后，每个专家的上下文是干净的，只装自己领域的信息；职责也清楚，研究员就好好查资料别去写代码；多个专家还能同时开工。[原文§老板派活的思路](https://xiaolinnote.com/claudecode/source/cc_multi_agent.html#%E8%80%81%E6%9D%BF%E6%B4%BE%E6%B4%BB%E7%9A%84%E6%80%9D%E8%B7%AF)
- **H6-30** 合成阶段由协调者亲自做，这是它存在的意义：理解全局、做决策。prompt 反复强调不要让 worker 根据你的发现去实现修复，而要自己读懂 findings、写成具体的规格再派下去；只转发的协调者没有存在价值。[原文§协调者的「任务流水线」](https://xiaolinnote.com/claudecode/source/cc_multi_agent.html#%E5%8D%8F%E8%B0%83%E8%80%85%E7%9A%84%E3%80%8C%E4%BB%BB%E5%8A%A1%E6%B5%81%E6%B0%B4%E7%BA%BF%E3%80%8D)
- **H6-31** 派 worker 的工具，派完立刻返回 worker 的 ID；创建和解散团队的工具，用来批量管理 worker 组；给已派出的 worker 发后续指令的 SendMessage；合成最终输出的工具，把最终回复交给用户；停止 worker 的工具，发现某个 worker 跑错方向时停掉它省 token。[原文§三大内部工具](https://xiaolinnote.com/claudecode/source/cc_multi_agent.html#%E4%B8%89%E5%A4%A7%E5%86%85%E9%83%A8%E5%B7%A5%E5%85%B7)
- **H6-32** Coordinator 模式不是默认开的，要显式打开，需要同时满足编译时的功能开关和运行时的环境变量 CLAUDE_CODE_COORDINATOR_MODE=1 两个条件。[原文§Coordinator 模式的启用](https://xiaolinnote.com/claudecode/source/cc_multi_agent.html#coordinator-%E6%A8%A1%E5%BC%8F%E7%9A%84%E5%90%AF%E7%94%A8)
- **H6-33** 四个阶段：调研由 worker 并行完成，调查代码库、找文件、理解问题；合成由协调者本人读完发现、理解问题并写出实现规格；实现由 worker 按规格做具体修改并提交；验证由 worker 测试改动是否真的工作。[原文§协调者的「任务流水线」](https://xiaolinnote.com/claudecode/source/cc_multi_agent.html#%E5%8D%8F%E8%B0%83%E8%80%85%E7%9A%84%E3%80%8C%E4%BB%BB%E5%8A%A1%E6%B5%81%E6%B0%B4%E7%BA%BF%E3%80%8D)
- **H6-34** prompt 写明并行是你的超能力：worker 全是异步的，独立的 worker 要尽量并发启动，能同时跑的工作不要串行，并多找机会一口气派出去。[原文§并行才是真本事](https://xiaolinnote.com/claudecode/source/cc_multi_agent.html#%E5%B9%B6%E8%A1%8C%E6%89%8D%E6%98%AF%E7%9C%9F%E6%9C%AC%E4%BA%8B)
- **H6-35** 派 worker 的工具调用可以在同一条 assistant 消息里出现多次，底层一起并发执行；串行是派一个、等结果再派下一个，用户要等十分钟，并行是同时派三个，结果陆续到，只等三分钟多一点。[原文§并行才是真本事](https://xiaolinnote.com/claudecode/source/cc_multi_agent.html#%E5%B9%B6%E8%A1%8C%E6%89%8D%E6%98%AF%E7%9C%9F%E6%9C%AC%E4%BA%8B)
- **H6-36** 新任务与 worker 现有的上下文高度相关时，例如刚查过的文件现在要改，就给老 worker 发消息续命，因为它已经知道那些文件了，沟通成本低。[原文§Continue vs Spawn：老 worker 还是新 worker？](https://xiaolinnote.com/claudecode/source/cc_multi_agent.html#continue-vs-spawn-%E8%80%81-worker-%E8%BF%98%E6%98%AF%E6%96%B0-worker)
- **H6-37** 原文称验证这种需要新鲜眼光的工作永远派新 worker，不能让刚写完代码的 worker 自己验自己；这和人类团队一样，有的活换个人做才能避免认知偏差。[原文§Continue vs Spawn：老 worker 还是新 worker？](https://xiaolinnote.com/claudecode/source/cc_multi_agent.html#continue-vs-spawn-%E8%80%81-worker-%E8%BF%98%E6%98%AF%E6%96%B0-worker)
- **H6-38** 协调者专属的内部工具不给 worker 用，这是一个递归防护：如果 worker 也能派 worker，整个系统就变成没完没了的递归树；收回 worker 的派人权，系统才保持一个协调者加一堆 worker 的扁平形态。[原文§Worker 的工具限制](https://xiaolinnote.com/claudecode/source/cc_multi_agent.html#worker-%E7%9A%84%E5%B7%A5%E5%85%B7%E9%99%90%E5%88%B6)
- **H6-39** 它其实是一张给 worker 用的黑名单：Coordinator 模式下，系统把创建团队、解散团队、发消息、合成输出这几样工具从 worker 的工具池里摘掉，让 worker 只管干活；它不是说只有协调者才有这些工具，SendMessage 也并非 Coordinator 模式专属。[原文§三大内部工具](https://xiaolinnote.com/claudecode/source/cc_multi_agent.html#%E4%B8%89%E5%A4%A7%E5%86%85%E9%83%A8%E5%B7%A5%E5%85%B7)
- **H6-40** 它们是两个独立的开关：agent-teams 管的是父子之间双向发消息、派队友；Coordinator 是更进一步的编排模式，让主 Agent 退化成纯协调者；不能把两者当成一回事。[原文§三大内部工具](https://xiaolinnote.com/claudecode/source/cc_multi_agent.html#%E4%B8%89%E5%A4%A7%E5%86%85%E9%83%A8%E5%B7%A5%E5%85%B7)
- **H6-41** 每派一个 subagent 都给它一个独立的 ID，并在父 Agent 的深度基础上加 1，系统随时知道当前这个 Agent 处于嵌套的第几层；深度超过阈值，例如 5 层，就报警甚至强制停止，防止意外嵌套失控。[原文§第二维度：搭一个隔离的运行环境](https://xiaolinnote.com/claudecode/source/cc_multi_agent.html#%E7%AC%AC%E4%BA%8C%E7%BB%B4%E5%BA%A6-%E6%90%AD%E4%B8%80%E4%B8%AA%E9%9A%94%E7%A6%BB%E7%9A%84%E8%BF%90%E8%A1%8C%E7%8E%AF%E5%A2%83)
- **H6-42** 原文总结的原则是：不要假设所有 Agent 都能用所有工具，要按 Agent 类型做细粒度的权限控制；每个 subagent 拿到的是量身定制的工具池，既够它干活，又不会越权。[原文§第一维度：给子 agent 发一个定制工具箱](https://xiaolinnote.com/claudecode/source/cc_multi_agent.html#%E7%AC%AC%E4%B8%80%E7%BB%B4%E5%BA%A6-%E7%BB%99%E5%AD%90-agent-%E5%8F%91%E4%B8%80%E4%B8%AA%E5%AE%9A%E5%88%B6%E5%B7%A5%E5%85%B7%E7%AE%B1)
- **H6-43** 主 Agent 角色：常规是全能选手，Coordinator 是纯协调者；subagent 执行：常规是同步、2 分钟后才转后台，Coordinator 默认异步；并发程度：偶尔并发对最大化并发；适合场景：单个任务加临时帮手对大任务加高并发拆解；系统形态：父子树对协调者加 worker 的扁平层。[原文§跟常规 subagent 对比](https://xiaolinnote.com/claudecode/source/cc_multi_agent.html#%E8%B7%9F%E5%B8%B8%E8%A7%84-subagent-%E5%AF%B9%E6%AF%94)

### 补充考点

- **H6-44** 用户按 Ctrl+C 想中止整个任务时，主线程会把中止信号广播出去；子 Agent 如果用的是全新上下文，就收不到这个信号，对外面发生的事一无所知，会自顾自继续跑，等于和外界完全脱节。[原文§第二维度：搭一个隔离的运行环境](https://xiaolinnote.com/claudecode/source/cc_multi_agent.html#%E7%AC%AC%E4%BA%8C%E7%BB%B4%E5%BA%A6-%E6%90%AD%E4%B8%80%E4%B8%AA%E9%9A%94%E7%A6%BB%E7%9A%84%E8%BF%90%E8%A1%8C%E7%8E%AF%E5%A2%83)
- **H6-45** 对着父 Agent 的每项状态问一句：子 Agent 拿这个状态干什么，会不会影响父；这样逐项决策，就能避开大部分坑，而不是粗暴地给子 Agent 一个空 context。[原文§原则 1：上下文隔离要按字段粒度做](https://xiaolinnote.com/claudecode/source/cc_multi_agent.html#%E5%8E%9F%E5%88%99-1-%E4%B8%8A%E4%B8%8B%E6%96%87%E9%9A%94%E7%A6%BB%E8%A6%81%E6%8C%89%E5%AD%97%E6%AE%B5%E7%B2%92%E5%BA%A6%E5%81%9A)

## 7. Skill 按需加载的实现

原文：[Claude Code Skill 原理图解：几个 Markdown 文件，怎么做到按需加载？](https://xiaolinnote.com/claudecode/source/cc_skill.html)。

### 发现与三层加载

- **H7-1** 核心是一个必须叫 SKILL.md 的主文件：开头的 frontmatter 里最重要的是 name 和 description 两个字段，name 是名字，description 描述它是干什么的、什么时候该用；往下的正文是一份操作指南，告诉模型该用什么工具、复杂情况去读哪个补充文档。[原文§一、Skill 到底是个什么东西？](https://xiaolinnote.com/claudecode/source/cc_skill.html#%E4%B8%80%E3%80%81skill-%E5%88%B0%E5%BA%95%E6%98%AF%E4%B8%AA%E4%BB%80%E4%B9%88%E4%B8%9C%E8%A5%BF)
- **H7-2** 这个格式已经不是 Claude Code 的私有玩法：Anthropic 把它定名为 Agent Skills 并且开源，想把给 Agent 写说明书这件事变成行业通用标准。[原文§一、Skill 到底是个什么东西？](https://xiaolinnote.com/claudecode/source/cc_skill.html#%E4%B8%80%E3%80%81skill-%E5%88%B0%E5%BA%95%E6%98%AF%E4%B8%AA%E4%BB%80%E4%B9%88%E4%B8%9C%E8%A5%BF)
- **H7-3** 原文算了一笔账：装 50 个 skill、每份手册平均 3000 token，全文塞进系统提示词就是 15 万 token，而上下文窗口一共才 20 万；并且这 50 本手册在当前这轮对话里可能一本都用不上，纯属浪费。[原文§二、五分钟写一个最小 skill](https://xiaolinnote.com/claudecode/source/cc_skill.html#%E4%BA%8C%E3%80%81%E4%BA%94%E5%88%86%E9%92%9F%E5%86%99%E4%B8%80%E4%B8%AA%E6%9C%80%E5%B0%8F-skill)
- **H7-4** 原文用书架作比：第一层只常驻书脊，即所有 skill 的名字和描述拼成的清单；第二层在模型选中某个 skill 时，才把 SKILL.md 的完整正文读进来；第三层是附录，补充文档和脚本等模型真需要时再自己用 Read 读取。[原文§三、渐进式披露：Claude 怎么做到「用时才翻书」？](https://xiaolinnote.com/claudecode/source/cc_skill.html#%E4%B8%89%E3%80%81%E6%B8%90%E8%BF%9B%E5%BC%8F%E6%8A%AB%E9%9C%B2-claude-%E6%80%8E%E4%B9%88%E5%81%9A%E5%88%B0%E3%80%8C%E7%94%A8%E6%97%B6%E6%89%8D%E7%BF%BB%E4%B9%A6%E3%80%8D)
- **H7-5** 清单就摆在模型眼前，模型每轮生成回复之前都要通读上下文，用户的需求和哪行描述对得上，靠的是模型自己的阅读理解；描述由 description 和可选的 when_to_use 拼成，是模型做判断的全部依据。[原文§四、Claude 是怎么知道该用哪个 skill 的？](https://xiaolinnote.com/claudecode/source/cc_skill.html#%E5%9B%9B%E3%80%81claude-%E6%98%AF%E6%80%8E%E4%B9%88%E7%9F%A5%E9%81%93%E8%AF%A5%E7%94%A8%E5%93%AA%E4%B8%AA-skill-%E7%9A%84)
- **H7-6** 源码把整份 skill 清单的预算定为上下文窗口的 1%，按 20 万 token 的窗口约 2000 token，单条描述硬上限 250 个字符；源码注释称清单只用来做发现，正文调用时会完整加载，描述写太长只是浪费 token。[原文§第一层：常驻的只有「书脊」](https://xiaolinnote.com/claudecode/source/cc_skill.html#%E7%AC%AC%E4%B8%80%E5%B1%82-%E5%B8%B8%E9%A9%BB%E7%9A%84%E5%8F%AA%E6%9C%89%E3%80%8C%E4%B9%A6%E8%84%8A%E3%80%8D)
- **H7-7** 工具说明里有一段措辞强硬的指令：只要有 skill 与用户请求匹配，调用它就是 BLOCKING REQUIREMENT，必须先调用相关 Skill 再生成其他回应；后面还规定绝不允许嘴上提到 skill 却不真正调用。[原文§四、Claude 是怎么知道该用哪个 skill 的？](https://xiaolinnote.com/claudecode/source/cc_skill.html#%E5%9B%9B%E3%80%81claude-%E6%98%AF%E6%80%8E%E4%B9%88%E7%9F%A5%E9%81%93%E8%AF%A5%E7%94%A8%E5%93%AA%E4%B8%AA-skill-%E7%9A%84)
- **H7-8** 降级时先尝试全量描述，超预算就按剩余空间把每条描述等比截短，再不行则第三方 skill 只留名字、描述全砍；官方内置 skill 的描述永远不被截断，所以空间紧张时先受损的是第三方 skill。[原文§第一层：常驻的只有「书脊」](https://xiaolinnote.com/claudecode/source/cc_skill.html#%E7%AC%AC%E4%B8%80%E5%B1%82-%E5%B8%B8%E9%A9%BB%E7%9A%84%E5%8F%AA%E6%9C%89%E3%80%8C%E4%B9%A6%E8%84%8A%E3%80%8D)
- **H7-9** 完整正文被包装成一条用户消息直接插进对话流，并标记 isMeta 为 true：模型能看到，界面上不会像真的用户发言那样显示。[原文§第二层：选中了，才把整本书抽出来](https://xiaolinnote.com/claudecode/source/cc_skill.html#%E7%AC%AC%E4%BA%8C%E5%B1%82-%E9%80%89%E4%B8%AD%E4%BA%86-%E6%89%8D%E6%8A%8A%E6%95%B4%E6%9C%AC%E4%B9%A6%E6%8A%BD%E5%87%BA%E6%9D%A5)
- **H7-10** 系统提示词在整个会话里要反复使用，改动它会导致 Prompt Cache 大面积失效，每轮都重新计费；追加一条消息是纯增量，前面的缓存一点不受影响。[原文§第二层：选中了，才把整本书抽出来](https://xiaolinnote.com/claudecode/source/cc_skill.html#%E7%AC%AC%E4%BA%8C%E5%B1%82-%E9%80%89%E4%B8%AD%E4%BA%86-%E6%89%8D%E6%8A%8A%E6%95%B4%E6%9C%AC%E4%B9%A6%E6%8A%BD%E5%87%BA%E6%9D%A5)
- **H7-11** 参考文档和脚本在第二层注入时依然不会被加载，SKILL.md 正文只留几句指路的话；模型真遇到对应任务时才自己用 Read 把文件读进来，不需要任何专门机制，属于按需付费。[原文§第三层：附录，连第二层都懒得进](https://xiaolinnote.com/claudecode/source/cc_skill.html#%E7%AC%AC%E4%B8%89%E5%B1%82-%E9%99%84%E5%BD%95-%E8%BF%9E%E7%AC%AC%E4%BA%8C%E5%B1%82%E9%83%BD%E6%87%92%E5%BE%97%E8%BF%9B)
- **H7-12** 固定的机械操作，例如某种固定格式的转换，与其在正文里教模型一步步做，不如写成脚本放进 scripts 目录，正文里只写一句执行这个脚本；因为模型现想有失败率，今天想对了明天可能想歪，脚本跑一万次一个样。[原文§八、怎么写好一个 skill？](https://xiaolinnote.com/claudecode/source/cc_skill.html#%E5%85%AB%E3%80%81%E6%80%8E%E4%B9%88%E5%86%99%E5%A5%BD%E4%B8%80%E4%B8%AA-skill)
- **H7-13** Claude Code 不用向量检索、意图分类或关键词匹配，只把清单摆在模型眼前靠阅读理解：好处是不外挂额外系统，少一处故障点和维护负担，能力还随模型升级变强；软肋是 skill 到几百个、描述被截断时匹配准确率会掉。[原文§四、Claude 是怎么知道该用哪个 skill 的？](https://xiaolinnote.com/claudecode/source/cc_skill.html#%E5%9B%9B%E3%80%81claude-%E6%98%AF%E6%80%8E%E4%B9%88%E7%9F%A5%E9%81%93%E8%AF%A5%E7%94%A8%E5%93%AA%E4%B8%AA-skill-%E7%9A%84)
- **H7-14** skill 数量真到几百个、描述行被截得只剩名字的时候，匹配准确率肯定会掉；不过对绝大多数只装几十个 skill 的用户来说，这个天花板还远碰不到。[原文§四、Claude 是怎么知道该用哪个 skill 的？](https://xiaolinnote.com/claudecode/source/cc_skill.html#%E5%9B%9B%E3%80%81claude-%E6%98%AF%E6%80%8E%E4%B9%88%E7%9F%A5%E9%81%93%E8%AF%A5%E7%94%A8%E5%93%AA%E4%B8%AA-skill-%E7%9A%84)

### 调用入口、动态内容与信任

- **H7-15** 源码里 slash command 和 skill 已经统一成一套 Command 体系，用同一个数据结构，加载和执行走同一条路；所以一个 skill 天生有两个触发入口：人敲斜杠加名字手动触发，模型判断匹配时自主触发。[原文§五、你敲的 /命令 和 skill，其实是同一个东西](https://xiaolinnote.com/claudecode/source/cc_skill.html#%E4%BA%94%E3%80%81%E4%BD%A0%E6%95%B2%E7%9A%84-%E5%91%BD%E4%BB%A4-%E5%92%8C-skill-%E5%85%B6%E5%AE%9E%E6%98%AF%E5%90%8C%E4%B8%80%E4%B8%AA%E4%B8%9C%E8%A5%BF)
- **H7-16** 第一步建目录，用户级 skill 放在家目录的 .claude/skills/ 下，一个 skill 一个文件夹；第二步在里面创建 SKILL.md 并写上 frontmatter；第三步往正文里写规则。整个过程不用编译、不用注册，也不需要重启。[原文§二、五分钟写一个最小 skill](https://xiaolinnote.com/claudecode/source/cc_skill.html#%E4%BA%8C%E3%80%81%E4%BA%94%E5%88%86%E9%92%9F%E5%86%99%E4%B8%80%E4%B8%AA%E6%9C%80%E5%B0%8F-skill)
- **H7-17** disable-model-invocation 设为 true 后，模型不许自主调用，只有人手敲才能触发，模型调用会被拦截报错；适合危险操作，例如一键发布上线这类 skill，必须留给人来触发。[原文§五、你敲的 /命令 和 skill，其实是同一个东西](https://xiaolinnote.com/claudecode/source/cc_skill.html#%E4%BA%94%E3%80%81%E4%BD%A0%E6%95%B2%E7%9A%84-%E5%91%BD%E4%BB%A4-%E5%92%8C-skill-%E5%85%B6%E5%AE%9E%E6%98%AF%E5%90%8C%E4%B8%80%E4%B8%AA%E4%B8%9C%E8%A5%BF)
- **H7-18** user-invocable 设为 false 后，skill 从斜杠命令菜单里消失，只有模型能调；适合纯背景知识类的 skill，例如本项目的数据库表结构说明，它不是一个动作，人敲它没有意义，但模型干活时随时可能要翻。[原文§五、你敲的 /命令 和 skill，其实是同一个东西](https://xiaolinnote.com/claudecode/source/cc_skill.html#%E4%BA%94%E3%80%81%E4%BD%A0%E6%95%B2%E7%9A%84-%E5%91%BD%E4%BB%A4-%E5%92%8C-skill-%E5%85%B6%E5%AE%9E%E6%98%AF%E5%90%8C%E4%B8%80%E4%B8%AA%E4%B8%9C%E8%A5%BF)
- **H7-19** 正文里可以写 $ARGUMENTS 占位符：用户在斜杠命令后面跟的那串话会被原样填进占位符的位置，模型自主调用时同样可以传参。[原文§六、skill 不只是静态文档：参数和动态内容](https://xiaolinnote.com/claudecode/source/cc_skill.html#%E5%85%AD%E3%80%81skill-%E4%B8%8D%E5%8F%AA%E6%98%AF%E9%9D%99%E6%80%81%E6%96%87%E6%A1%A3-%E5%8F%82%E6%95%B0%E5%92%8C%E5%8A%A8%E6%80%81%E5%86%85%E5%AE%B9)
- **H7-20** 正文里可以用感叹号加反引号包住的语法嵌一段 shell 命令；例如官方的 /commit 在正文里嵌了 git diff，调用的瞬间把代码变更抓进上下文，模型看着真实的 diff 写提交信息。[原文§六、skill 不只是静态文档：参数和动态内容](https://xiaolinnote.com/claudecode/source/cc_skill.html#%E5%85%AD%E3%80%81skill-%E4%B8%8D%E5%8F%AA%E6%98%AF%E9%9D%99%E6%80%81%E6%96%87%E6%A1%A3-%E5%8F%82%E6%95%B0%E5%92%8C%E5%8A%A8%E6%80%81%E5%86%85%E5%AE%B9)
- **H7-21** 在 skill 被调用的那一刻：Claude Code 先做参数替换，再把嵌入的命令跑完、把输出填进正文，然后才把填好的成品交给模型，模型读到的是已经填满实时数据的版本。[原文§六、skill 不只是静态文档：参数和动态内容](https://xiaolinnote.com/claudecode/source/cc_skill.html#%E5%85%AD%E3%80%81skill-%E4%B8%8D%E5%8F%AA%E6%98%AF%E9%9D%99%E6%80%81%E6%96%87%E6%A1%A3-%E5%8F%82%E6%95%B0%E5%92%8C%E5%8A%A8%E6%80%81%E5%86%85%E5%AE%B9)
- **H7-22** 源码有一道防线：来自 MCP 服务器的远程 skill 永远不执行正文里嵌的命令，注释写明 MCP skill 是远程内容，不可信；否则有人发布带恶意命令的 skill 就会被直接执行。[原文§六、skill 不只是静态文档：参数和动态内容](https://xiaolinnote.com/claudecode/source/cc_skill.html#%E5%85%AD%E3%80%81skill-%E4%B8%8D%E5%8F%AA%E6%98%AF%E9%9D%99%E6%80%81%E6%96%87%E6%A1%A3-%E5%8F%82%E6%95%B0%E5%92%8C%E5%8A%A8%E6%80%81%E5%86%85%E5%AE%B9)
- **H7-23** 例如在正文里加一行用内嵌命令 cat $ARGUMENTS：用户敲斜杠命令加文件名时，Claude Code 先执行 cat 把代码读出来填进 prompt，模型看到的是检查清单和待检查的代码已经并排摆好，一步到位。[原文§六、skill 不只是静态文档：参数和动态内容](https://xiaolinnote.com/claudecode/source/cc_skill.html#%E5%85%AD%E3%80%81skill-%E4%B8%8D%E5%8F%AA%E6%98%AF%E9%9D%99%E6%80%81%E6%96%87%E6%A1%A3-%E5%8F%82%E6%95%B0%E5%92%8C%E5%8A%A8%E6%80%81%E5%86%85%E5%AE%B9)
- **H7-24** 原文列了五个来处：官方内置，随 Claude Code 发行；用户级，家目录 ~/.claude/skills/ 下，走到哪跟到哪；项目级，仓库 .claude/skills/ 下，只在该项目生效并随 git 共享；插件带来的；MCP 远程服务器动态提供的。[原文§七、这些 skill 都是从哪里冒出来的？](https://xiaolinnote.com/claudecode/source/cc_skill.html#%E4%B8%83%E3%80%81%E8%BF%99%E4%BA%9B-skill-%E9%83%BD%E6%98%AF%E4%BB%8E%E5%93%AA%E9%87%8C%E5%86%92%E5%87%BA%E6%9D%A5%E7%9A%84)
- **H7-25** 全文常驻的方案要 15 万 token；渐进式披露下，第一层清单撑死 2000 token，第二层只在用到时加载一本手册的几千 token，第三层按需读取；相当于 75% 的窗口占用变成 1%。[原文§第三层：附录，连第二层都懒得进](https://xiaolinnote.com/claudecode/source/cc_skill.html#%E7%AC%AC%E4%B8%89%E5%B1%82-%E9%99%84%E5%BD%95-%E8%BF%9E%E7%AC%AC%E4%BA%8C%E5%B1%82%E9%83%BD%E6%87%92%E5%BE%97%E8%BF%9B)
- **H7-26** 扫描按固定顺序进行，同一个文件身份先到先得，后来的重名直接跳过并记一条日志；项目级排在用户级后面加载，所以不能指望在项目里覆盖用户级的同名 skill，起名的时候错开才是正道。[原文§七、这些 skill 都是从哪里冒出来的？](https://xiaolinnote.com/claudecode/source/cc_skill.html#%E4%B8%83%E3%80%81%E8%BF%99%E4%BA%9B-skill-%E9%83%BD%E6%98%AF%E4%BB%8E%E5%93%AA%E9%87%8C%E5%86%92%E5%87%BA%E6%9D%A5%E7%9A%84)
- **H7-27** Skill 目录里没有二进制文件、依赖包和安装脚本，全是人也能直接读的文本；它像发给聪明实习生的入职手册，模型本身的能力一点没变，变的是手头多了一份你家业务的说明书。[原文§一、Skill 到底是个什么东西？](https://xiaolinnote.com/claudecode/source/cc_skill.html#%E4%B8%80%E3%80%81skill-%E5%88%B0%E5%BA%95%E6%98%AF%E4%B8%AA%E4%BB%80%E4%B9%88%E4%B8%9C%E8%A5%BF)
- **H7-28** 还有不少可选字段，例如限制这个 skill 能用哪些工具的 allowed-tools，以及指定用哪个模型来执行的 model；原文称这些偏进阶，先记住 name 和 description 两个主角即可。[原文§一、Skill 到底是个什么东西？](https://xiaolinnote.com/claudecode/source/cc_skill.html#%E4%B8%80%E3%80%81skill-%E5%88%B0%E5%BA%95%E6%98%AF%E4%B8%AA%E4%BB%80%E4%B9%88%E4%B8%9C%E8%A5%BF)
- **H7-29** 按广告词的标准写，重点写什么时候用我：它是 skill 唯一的广告位，进清单时最多保留 250 个字符，应放弃功能罗列，把字数花在触发场景上，用用户嘴里会说出来的动词。[原文§八、怎么写好一个 skill？](https://xiaolinnote.com/claudecode/source/cc_skill.html#%E5%85%AB%E3%80%81%E6%80%8E%E4%B9%88%E5%86%99%E5%A5%BD%E4%B8%80%E4%B8%AA-skill)
- **H7-30** SKILL.md 只写高频的主干流程，把低频的、超长的细节拆到 references 目录，正文里留一句指路的话；这样第二层注入又轻又准。原文给的经验标准是 SKILL.md 超过 500 行就该考虑拆附录。[原文§八、怎么写好一个 skill？](https://xiaolinnote.com/claudecode/source/cc_skill.html#%E5%85%AB%E3%80%81%E6%80%8E%E4%B9%88%E5%86%99%E5%A5%BD%E4%B8%80%E4%B8%AA-skill)
- **H7-31** 项目级 skill 放在仓库的 .claude/skills/ 里，会跟着代码一起进 git；新同事克隆项目的那一刻，团队沉淀的操作手册自动就位。以前这些东西写在 wiki 里写完就烂，现在是能被 Agent 直接执行的活文档，谁用谁更新。[原文§七、这些 skill 都是从哪里冒出来的？](https://xiaolinnote.com/claudecode/source/cc_skill.html#%E4%B8%83%E3%80%81%E8%BF%99%E4%BA%9B-skill-%E9%83%BD%E6%98%AF%E4%BB%8E%E5%93%AA%E9%87%8C%E5%86%92%E5%87%BA%E6%9D%A5%E7%9A%84)
- **H7-32** 原文称 skill 的内容确实就是提示词，区别不在内容而在加载方式：提示词一股脑全塞进上下文，skill 走渐进式披露、分层按需加载；提示词是知识本身，skill 是知识的加载策略。[原文§最后总结](https://xiaolinnote.com/claudecode/source/cc_skill.html#%E6%9C%80%E5%90%8E%E6%80%BB%E7%BB%93)
