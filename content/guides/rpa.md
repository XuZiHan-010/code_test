# RPA 开发终面复习手册

面向联想消费业务销售团队 RPA 开发岗位的终面准备，2026-10-16 整理。重心放在三件事上：读懂销售业务，围绕影刀和飞书多维表格设计自动化方案，讲清楚如何交付和衡量收益。

> 本手册是面试准备材料，不是官方文档。影刀的指令名称、飞书接口的条数上限和行数上限等细节，以实际使用的版本和官方文档为准。联想的公开资料只说明联想重视渠道数字化，不能说明面试团队负责这些系统。

## 1. 终面在比什么 {#positioning}

进入二选一，双方技术底子大概率都过关。面试官更想判断的是：谁能更快理解销售业务，能独立对接业务人员，并把方案真正交付上线。

### 三项竞争力 {#strengths}

| 竞争力 | 证明方式 |
| --- | --- |
| 业务理解 | 能把“报表太麻烦”这类描述拆成输入、规则、输出、异常和验收标准；讲得出销售指标的含义。 |
| 技术迁移 | Python、API、SQL、工作流都会用，不依赖某一个 RPA 平台，能判断什么时候用 API、什么时候用 RPA。 |
| 稳定交付 | 考虑登录失效、页面改版、重复执行、数据异常；有日志、告警、人工兜底和回归测试。 |

### 一分钟自我介绍 {#intro}

1. 我是谁，最相关的一段经历（一句话）。
2. 一个能代表你的自动化项目：业务问题是什么，你做了什么，结果如何（尽量带数字：耗时从多少降到多少、覆盖多少门店或报表）。
3. 技术面：影刀、Python、API、飞书，各用一句话说明用在什么地方。
4. 为什么是这个岗位：想做贴近销售业务、能直接看到效果的自动化。

> AI Agent 是差异化优势，但不要主动反复提。等面试官问到 AI、未来规划或“传统 RPA 处理不了的场景”时再展开，并强调“先保证稳定，再引入 AI”。

## 2. 销售业务速览 {#business}

联想公开资料提到的方向有：官网与微信小程序的线上线下融合（OMO）、线下门店的数字化管理（进销存、收银、经营数据、总部消息下达），以及面向经销商的报备、伙伴商城、AI 报价和 AI 问数。面试时用“我了解到公开资料提到……”的口吻，**不要把这些系统说成面试团队负责的项目**。

OMO 指线上线下融合：官网、小程序、门店、会员、服务打通。同一用户和订单会跨渠道，所以订单归属口径要统一，库存要跨渠道可见，SKU 和会员 ID 要能互相映射。自动化在其中适合做跨系统汇总、比对和预警，强一致的实时同步交给系统接口。

### 三类渠道 {#channels}

| 渠道 | 典型系统 | 典型数据 | 自动化痛点 |
| --- | --- | --- | --- |
| 电商 | 京东、天猫、抖音等商家后台；官网商城、小程序 | 订单、退款、结算、流量、价格、库存 | 平台多、格式各异、登录有验证、大促期间要求时效 |
| 线下门店 | 门店收银、进销存系统；表格上报 | 销售日报、库存、到货、样机、陈列 | 门店多、上报格式不统一、有人漏报、门店系统环境不同 |
| 经销商 / 渠道 | 伙伴平台、报备系统、ERP | 商机报备、进货、返利、价格政策 | 跨系统核对、口径不一致、人工对账量大 |

### 适合与不适合 RPA 的工作 {#fit}

- 典型重复工作：多平台订单、销量、结算报表下载汇总；大促战报；价格巡检；门店日报收集与催交；库存与到货核对；总部通知下发与回执统计；经销商报备数据整理；跨系统对账。
- 适合 RPA：高频、规则清晰、输入结构化、系统稳定、没有可用接口。
- 不适合：需要人判断或谈判、规则每周在变、一次性任务、流程本身不合理（应先优化流程再自动化）。
- 大促（618、双 11）期间最需要：小时级战报、价格巡检防破价、库存预警、异常订单提醒。提前压测运行时长，后台高峰时会变慢，要加长等待和重试；关键流程准备人工 SOP，告警直达值班人，大促前冻结流程变更；遵守平台规则，控制采集频率。

### 销售指标 {#metrics}

| 指标 | 含义 | 自动化里的用处 |
| --- | --- | --- |
| GMV / 销售额 | 成交总额；注意是否含退款、是否含税 | 日报核心数，先统一口径再汇总 |
| 销量、客单价 | 客单价 = 销售额 ÷ 订单数 | 环比突变可作为异常信号 |
| SKU | 最小库存单位，同一型号不同配置是不同 SKU | 跨平台汇总的关键是 SKU 映射表 |
| 库存周转天数 | 库存 ÷ 日均销量 | 识别积压和即将断货 |
| 售罄率 / 动销率 | 售罄率 = 已售 ÷ 进货；动销率 = 有销售的 SKU 占比 | 门店铺货效果 |
| 缺货率、破价 | 有需求无库存；售价低于指导价 | 预警类流程的触发条件 |

日报里可以设置的异常指标：某门店销售额环比波动超过 50%、某 SKU 可售天数低于 7 天、有门店未提交日报。

### 接到需求的第一步 {#first-step}

业务同事说“每天做报表太麻烦，帮我自动化一下”，不要急着开发：

1. 访谈并请对方演示一遍：数据从哪来、怎么加工、发给谁、多久一次、花多久。
2. 问清异常：数据缺了怎么办、谁核对、口径有没有例外。
3. 确认验收标准：几点前出、哪些数字必须对上。
4. 输出流程图和需求说明，对方确认后再做 PoC。

## 3. 场景题六步答题法 {#method}

任何“你怎么设计”的问题都按这六步讲，每步一两句，讲完再等追问。

1. **澄清需求**：谁在用、多频繁、现在怎么做、花多久、结果给谁看、怎样算做对。
2. **数据来源与选型**：有授权 API 用 API；只能在页面操作用 RPA；非结构化文档（合同、截图、邮件）考虑 OCR 或大模型，加人工复核。
3. **流程设计**：获取 → 清洗与字段映射 → 校验 → 写入（飞书多维表格、Excel 或业务系统）→ 通知。
4. **异常与稳定性**：登录失效、页面改版、超时、重复执行、数据缺失；重试、幂等、日志截图、告警、人工兜底。
5. **交付**：先做一个平台或一家门店的 PoC，业务用真实数据做 UAT，上线后有运维说明和负责人。
6. **衡量效果**：节省工时、出数时间提前多少、错误率下降、覆盖范围。

### API、RPA 与 AI 怎么选 {#choose}

不预设工具，先了解流程、数据来源、频率和目标。

- 系统间数据交换且有稳定接口：优先 API，更快、更稳。
- 没有接口，必须在页面操作：用 RPA。
- 大量非结构化内容（合同、截图、邮件）：OCR 或大模型抽取，加人工复核。
- 最后综合开发成本、维护成本、执行稳定性和实际节省的人力来决定。

## 4. 六个业务场景 {#scenarios}

> 这些是根据岗位方向假设的场景，并非已确认的项目清单。

### 场景一：多电商平台订单汇总 {#scenario-orders}

流程：各平台商家后台 → API 或 RPA 导出报表 → 字段映射、SKU 映射 → 按订单号去重 → 写入多维表格 → 飞书推送战报。

- 有授权 API 用 API；没有则 RPA 登录后台，优先用后台的“导出”功能，比逐行抓页面稳定得多。
- 每个平台一个子流程，账号、导出路径、字段映射放在配置表里；单个平台失败不影响其他平台，新增平台只加配置和一个子流程。
- 写入时按订单号先查后写，保证重复执行不会产生重复数据；校验必填和金额。
- 风险：登录态过期、验证码、导出文件生成慢（等待文件出现）、大促期间后台卡顿、平台对自动化的规则限制。失败截图、告警、人工兜底。
- 平台改版导致流程失败、第二天业务就要数：先启用人工 SOP 保证当天出数，再看失败截图修复选择器，回归后上线。

### 场景二：全国门店销售日报 {#scenario-stores}

流程：门店通过飞书表单提交 → 多维表格明细 → 定时检查未提交门店 → @店长催交 → 汇总与异常校验 → 推送区域战报。

- 源头治理比事后清洗更重要：用表单、单选字段、关联门店表，从入口统一格式。
- 过渡期仍有门店用 Excel 上报：维护字段别名映射表，自动定位表头行并按映射重命名列；清洗日期、金额，把 SKU 映射到标准编码；不合规文件进异常清单，通知门店修改。
- 漏报：定时对比门店表和当日明细，@店长催交，截止时间后升级给区域经理。
- 校验：环比异常、负数、超大值进异常表。
- 汇总结果每个数都能追溯到原始记录（保留门店、日期、提交人、原始文件链接）。

> RPA 的价值不只是把人工操作自动化，更是让销售数据更及时、更准确、更容易被管理者使用。

### 场景三：线上线下库存比对与预警 {#scenario-inventory}

线上商城显示某款 ThinkPad 有 10 台，门店实际只有 3 台，可能导致超卖、调货失败或客户投诉。

- 先定位原因：同步频率低、SKU 映射错误、门店未及时录入、预占库存口径不同。
- RPA 适合做：定时获取各渠道库存，SKU 统一后比对，差异超过阈值或可售天数过低时告警并记录。
- 改库存要谨慎：强实时、高并发、要求一致性的同步应由系统接口或消息机制完成，RPA 只做巡检和兜底。
- 如果有授权接口需要回写：保证幂等、记录变更日志、可以回滚。

### 场景四：平台结算对账 {#scenario-reconcile}

- 平台结算单与内部订单或 ERP 数据按订单号匹配，分成四类：一致、金额不一致、仅平台有、仅内部有。
- 先统一口径：退款、优惠券、运费、平台佣金、税是否计入。
- 差异明细写入异常表，指派负责人处理，处理结果回填，形成闭环。
- 输出对账汇总：差异条数和金额，按原因分类。

### 场景五：价格巡检（防破价） {#scenario-price}

- SKU 清单和指导价表作为输入；定时抓取各平台展示价，低于阈值即告警并截图留证。
- 页面价格可能受地区、登录态、优惠券影响，记录抓取条件（地区、是否登录、是否含券），避免误报。
- 控制频率，遵守平台规则；页面结构变化要有失败告警；处理结果回填。

### 场景六：多门店复用与审批通知 {#scenario-reuse}

- 门店系统相同：一套标准流程加配置表（门店编码、账号、路径、选择器版本），多实例运行。
- 门店系统不同：公共部分（清洗、写表、通知、日志）做成公共子流程，采集部分按系统类型分支，而不是按门店复制流程。
- 发布前选几家代表性门店试点；用统一的运行日志看各店成功率。
- 审批与通知：多维表格自动化或飞书审批触发，RPA 或脚本执行后回写状态。

## 5. 影刀 RPA 要点 {#yingdao}

> 按通用能力整理，具体指令名称和菜单位置以实际使用的版本为准。

| 主题 | 要讲到的点 |
| --- | --- |
| 元素定位 | 元素捕获后编辑选择器：去掉动态 id 和序号，保留稳定属性（文本、name、class 组合）；用父元素锚定或相对定位；必要时手写 XPath 或 CSS。图像识别和坐标点击只做最后兜底，因为受分辨率和缩放影响。 |
| 等待 | 用“等待元素出现或消失”代替固定延时；导出文件用“等待文件出现”。关键步骤后校验页面状态。 |
| 数据抓取 | 相似元素批量抓取列表并设置翻页，或循环“抓取当前页、点下一页”直到下一页不可用；有导出功能或授权接口时优先用，数据更完整、更稳定；大量抓取注意频率。 |
| 网页与桌面 | 网页自动化基于浏览器 DOM；桌面自动化基于 Windows 控件，受分辨率、窗口状态影响更大。 |
| 流程结构 | 主流程加子流程；变量、全局变量、流程参数；条件、循环（遍历表格行、遍历文件）。 |
| 异常处理 | 指令级的出错处理（重试次数和间隔、忽略、抛出）；用异常捕获包住关键段落；失败时截图、记日志、发飞书告警。暂时性错误（超时、网络、限流）重试，业务错误（数据不合规）不重试，直接进异常表。 |
| 数据处理 | Excel 读写、数据表格；复杂清洗交给 Python 代码块（pandas）。 |
| Python 代码块 | 适合复杂数据清洗、HTTP 接口调用、签名计算、JSON 解析、正则提取、批量计算。分工原则：RPA 管界面操作，Python 管数据和接口。 |
| 运行方式 | 定时等触发方式，或由调度控制台统一派发；无人值守需要机器不锁屏、不休眠，分辨率和缩放固定；系统和浏览器更新可能导致失败。 |
| 登录 | 复用浏览器登录态；检测到登录页走重新登录子流程。验证码和短信二次验证：优先申请官方接口、长期授权或白名单，其次设置人工介入节点，不用技术手段绕过平台风控。 |
| 凭据 | 账号密码不写死在流程里，用凭据管理或加密配置；专用机器人账号，最小权限。 |

### 口述一个影刀流程 {#yingdao-example}

“每天 8 点触发 → 打开浏览器复用登录态 → 进入订单报表页，设置昨日日期，点导出 → 等待下载文件出现 → Python 代码块读取并清洗、映射字段 → 调多维表格接口分批写入，以订单号判断新增或更新 → 成功发送汇总消息，失败截图并 @负责人。每个平台一个子流程，单个平台失败不影响其他平台。”

### 稳定运行的流程突然失败 {#yingdao-debug}

1. 先止损：通知业务，必要时启用人工 SOP。
2. 看日志和失败截图，定位到哪一步。
3. 判断原因：页面改版、网络、账号或密码过期、数据异常、环境更新。
4. 本地复现并修复（更新选择器、加等待、处理新的数据情况）。
5. 回归测试后上线，补充对应的监控和校验，记录变更。

## 6. 飞书多维表格 {#feishu}

结构：多维表格（由 app_token 标识）→ 数据表（由 table_id 标识）→ 字段与记录 → 视图；另有表单、仪表盘和自动化流程。

和 Excel 的区别：字段有类型约束；表之间可以关联、查找引用；同一份数据有多种视图；支持行列级权限；有自动化流程和开放接口；多人实时协作，适合收集数据。

### 字段类型 {#feishu-fields}

常用字段：文本、数字、单选、多选、日期、人员、附件、复选框、链接、公式、查找引用、单向或双向关联、自动编号、创建时间、修改人等。

- 枚举值用单选，防止写法不一。
- 人用人员字段，才能 @ 到人、按人筛选。
- 主数据（门店、SKU）用关联字段，只维护一份。

### 门店销售日报建表示例 {#feishu-design}

| 数据表 | 关键字段 |
| --- | --- |
| 门店 | 门店编码、名称、区域（单选）、店长（人员）、状态 |
| SKU | SKU 编码、型号、品类、指导价 |
| 日报明细 | 日期、门店（关联）、SKU（关联）、销量、销售额、区域（查找引用）、唯一键（公式：日期+门店+SKU）、提交人 |
| 异常 | 来源记录、异常类型、负责人、处理状态、处理说明 |
| 运行日志 | 流程名、开始和结束时间、结果、处理条数、错误信息、截图 |

视图：按区域分组的表格视图、按处理状态的看板视图、当日未提交门店的筛选视图；仪表盘放销售额、销量排行和提交率。

### 自动化流程 {#feishu-automation}

- 触发：新增记录、记录满足条件、定时、表单提交、点击按钮等。
- 动作：发飞书消息、新增或修改记录、发送 HTTP 请求等。
- 适合：满足条件就通知、改状态、简单派单。
- 交给 RPA 或脚本：需要登录其他系统、复杂计算、大批量处理、跨系统写入。

### 用开放接口写数据 {#feishu-api}

1. 在开放平台建自建应用，开通多维表格相关权限，并让应用能访问这张表（加为协作者或授权）。
2. 用 app_id 和 app_secret 换 tenant_access_token；有效期约两小时，缓存并提前刷新。
3. 从表格链接里取 app_token 和 table_id。
4. 查询、新增、更新都有批量接口，单次条数有上限，大数据量要分批；遇到频率限制按退避重试。
5. 字段格式：日期写毫秒时间戳，人员写用户 ID，关联字段写被关联记录的 record_id 列表。

### 避免重复写入 {#feishu-idempotent}

接口没有现成的“存在则更新”。常见做法：定义业务唯一键（订单号，或日期 + 门店 + SKU），按唯一键先查询，存在就更新、不存在就新增；或在本地维护“唯一键 → record_id”的映射；也可以按日期整体覆盖，先删除当日批次再写入，注意记录批次号。重复执行不会产生重复记录，这就是幂等。

### 权限与机器人 {#feishu-permission}

- 区域经理只看本区域：用高级权限按角色设置可见记录的条件（区域 = 本区域）和字段权限。**视图筛选不是权限**，别人切换视图就能看到全部数据。也可以按区域拆分推送内容。
- 自定义机器人：在群里加 webhook 就能推送，可设置签名校验、关键词、IP 白名单，适合单向通知，如每日战报、失败告警。
- 应用机器人：需要建应用和授权，可以单聊、@人、发交互卡片、调用其他接口，适合需要交互的场景，如点击按钮确认、催办。
- 数据量很大时：历史数据归档或按月分表，汇总表只存聚合；明细放数据库或数据平台，多维表格只做协作和展示层；减少复杂公式和大范围查找引用。具体行数上限以官方文档为准。

## 7. 稳定性清单 {#stability}

| 问题 | 做法 |
| --- | --- |
| 重复执行 | 业务唯一键加先查后写；按批次号或日期覆盖重跑。同一操作执行一次和多次结果相同，叫幂等。有副作用的操作（提交订单、发消息）执行前检查是否已做过。 |
| 中途失败 | 逐条记录处理状态，重跑时跳过已完成的（断点续跑）。 |
| 暂时性错误 | 超时、网络、限流：有限次数重试，间隔递增；业务错误不重试，直接进异常表。 |
| 页面改版 | 稳定选择器；关键步骤后校验页面状态；失败截图帮助快速定位。 |
| 登录失效 | 复用登录态，检测到登录页就走重新登录子流程；验证码和二次验证走人工介入节点或申请接口，不绕过平台风控。 |
| 数据错误 | 写入前校验必填、类型、范围；写入后核对总数和金额，与上一日环比超过阈值就告警，异常时先告警不发布。 |
| 静默失败 | 运行日志表、失败告警、每日运行摘要；“该跑没跑”也要监控，到点没收到结果就告警。 |
| 兜底 | 写清人工操作 SOP，机器人失败时业务仍能手工完成当天工作。 |

### 日志与告警 {#logging}

- 运行日志：流程名、开始结束时间、结果、处理条数、错误信息、截图链接。
- 告警：失败立即推送负责人；连续失败升级。
- 每日摘要：各流程成功率、处理量。

### RPA 的局限 {#limits}

- 依赖界面，改版就可能失败，维护成本不低。
- 速度慢、并发受限，不适合强实时、高并发。
- 账号与合规风险：平台规则、凭据泄露。
- 可能把不合理的流程固化下来，所以先优化流程再自动化。
- 机器人数量多了需要统一调度和运维。

## 8. 找流程、排优先级、算收益 {#roi}

入职后负责人让你找三个值得用 RPA 优化的流程，这是最值得准备的一道题。

### 怎么发现 {#roi-find}

- 访谈和跟岗：请业务同事演示一遍日常工作，记录每一步、耗时和出错点。
- 找信号：每天或每周固定要做、多人做同样的事、经常抱怨“又要导表”、经常出错被追责、大促时人手不够。
- 列流程清单：名称、频次、单次耗时、涉及人数、涉及系统、规则是否清晰、是否有接口。

### 怎么排优先级 {#roi-priority}

| 维度 | 倾向优先 |
| --- | --- |
| 收益 | 频次高、耗时长、人数多、出错代价大、时效要求高 |
| 可行性 | 规则清晰、输入结构化、系统稳定不常改版、能拿到账号权限 |
| 推广 | 能复用到多个门店或平台、业务方配合度高、结果容易被看见 |

第一个项目选“收益明显且做得成”的，尽快拿出可见成果建立信任，再做难的。

### 怎么算收益 {#roi-calc}

> 年节省工时 = 单次耗时 × 每年频次 × 涉及人数 × (1 − 仍需人工的比例)。成本 = 开发工时 + 每年维护工时 + 授权与机器成本。

示例：40 家门店的店长每天花 20 分钟整理日报，一年按 300 天，约 40 × 20 × 300 ÷ 60 = 4000 小时；自动化后每人只剩 3 分钟确认，节省约 85%。这类数要在访谈里实测，不要拍脑袋。

不好折算但要讲的收益：报表从中午提前到早上 9 点、错误率下降、大促期间不用加班。

向领导汇报价值：每月节省工时、出数时间提前多少、错误率变化、覆盖门店或平台数；成功率和平均故障恢复时间；业务用这些数据做了什么决策；开发和维护投入，算回报周期。

## 9. 沟通与交付 {#delivery}

- **需求确认**：输出流程图和需求说明，标出输入、输出、规则、异常、验收标准，业务方确认后再开发。
- **PoC**：先做一个平台或一家门店，用真实数据跑通，确认可行再推广。
- **开发自测**：正常数据、异常数据、空数据、大数据量、网络慢。
- **UAT**：业务方用真实场景验收，包括节假日、月末等边界情况。
- **上线**：试运行期间与人工结果并行比对，一致后再停掉人工。
- **运维**：运行日志、告警接收人、操作说明、人工 SOP、变更记录；业务规则变化要走需求流程。

### 常见沟通问题 {#communication}

- **需求频繁变更**：开发前用流程图和需求说明确认，变更有记录；评估影响后排期，区分“这次必须改”和“下个版本”；把容易变的规则（阈值、映射、名单）做成配置，业务方改配置不用改流程；阶段性给业务看效果，早发现偏差。
- **业务方不愿改变习惯**：先理解原因（多了工作量、不熟悉、担心被考核）；让新方式更省事，例如表单比原来填 Excel 更快、自动带出门店信息；找试点门店先用，用效果说话；需要时请上级或区域经理推动，定截止时间并提供培训。
- **多个部门同时提需求**：统一收集到需求池，用相同维度评估收益、紧急程度、可行性、影响范围；和负责人对齐优先级，不自己拍板；对暂时排不上的需求说明原因和预计时间。
- **报表数据出错且已上报领导**：先止损，立即告知业务方，给出正确数据和影响范围，协助更正；定位原因并修复；补校验（写入前后总数核对、环比异常阈值，异常时先告警不发布）；复盘并记录。

### 讲项目与讲优势 {#story}

- 讲项目用 STAR：情境（什么业务、什么痛点、原来怎么做、花多少时间）→ 任务（你负责什么、目标和验收标准）→ 行动（选型理由、流程设计、最大困难和解决办法）→ 结果（量化数字、上线后的维护情况、如果重做会改进什么）。
- 为什么选这个岗位：贴近销售业务，自动化效果能直接看到，场景丰富（电商、门店、渠道）。
- 你的优势：业务理解（能把需求拆清楚）、技术迁移（Python、API、SQL，不依赖单一平台）、稳定交付意识；也持续学习 AI 相关技术，但以稳定和业务需求为先。不评价另一位候选人，只讲自己。

## 10. 反问与避坑 {#ask}

### 推荐反问 {#ask-questions}

1. 团队目前的 RPA 需求主要集中在销售数据整合、订单处理、库存，还是其他流程？
2. **（最推荐）** 面向门店的交付，更偏向一套标准流程多门店复用，还是按门店系统定制？这能区分岗位偏产品化、规模化，还是大量单店实施。
3. 除了影刀和飞书，团队是否也结合 Python、API 或 AI 处理传统 RPA 难做的流程？
4. 这个岗位入职前三个月，您最希望看到什么成果？

### 避坑 {#pitfalls}

- 不要一上来就说用 RPA 或 Agent，先问清楚需求和数据来源。
- 不要把公开资料里的系统说成是这个团队负责的项目。
- 不要只讲技术动作，每个方案收尾都落到业务价值和衡量方式。
- 不会的工具细节，说“我会先查官方文档确认”，再讲思路，不要编。
- 不要贬低前同事或业务方，遇到冲突讲“我怎么推动”。
